01项目背景

1.1 问题的提出

建筑三维资产一旦被导出成网格，就固化了。它同时带来三重代价，而这三者并非并列，而是层层递进：先要让交付成本降到可接受，才谈得上携带信息；要携带足够信息，才谈得上修改；要能安全修改，才谈得上工作台与协作。

其一，体积。建筑还原成三角网格后，顶点与面就以坐标形式被逐点写入文件，体积随细节快速膨胀。本项目实测的 204 个场景合计 422 万三角面，按常规网格格式估算需 433 MB；而承载同样设计意图的参数描述只需约 5 MB。这个量级的差距，直接决定交付、传输与归档是否可行。

这不是理论上的估算。面向网页端的 3D 去中心化数字世界同样需要建筑资产，而浏览器端的加载与传输预算决定了常规建筑软件导出的网格文件无法直接使用——这类场景恰恰是参数化轻量格式的适用区间。

其二，语义。即使体积降下来，交付物若只是「更小的网格」，依旧改不动。一扇窗在文件里只是一片三角面，无法回答它是哪类窗、装在哪面墙、能否改成推拉窗。体积解决的是「带得走」，语义解决的是「改得动」。

其三，校验。改得动之后出现新的问题：一次修改就可能破坏既有约束——移动一面墙可能让门窗失去宿主，改一个参数可能让整栋建筑无法重建。能改不代表改得对，这是最难补的一环。

在传统 DCC→引擎管线中，这三重代价还被进一步放大：为了在运行时引擎中加载，必须导出为 glTF / FBX / OBJ 这类以网格为单位的运行时格式，构件语义与参数结构在这一步被主动舍弃；非几何层（材质、灯光、配景）虽可在引擎侧调整，却与几何变更脱步——在引擎里调好的材质，几何一改就会丢失。

递进关系决定了实现顺序：体积是起点，语义是前提，校验是保障。轻量化不是事后做的优化，而是让后两级能力得以成立的前提——这也是本项目把「轻量化」作为起点约束，而非附加指标的原因。

大模型带来了一个看似直接的解法：用自然语言描述，让模型直接产出三维场景。但要让这条路成为可用产品，必须先回答三个问题：生成的产物是否可编辑？生成的过程能否被约束和纠正？错误能否在交付前被发现？后续各节将分别说明系统对这三问给出了什么层次的回答，以及哪些部分仍未解决。

1.2 三类既有产物形态及其局限

同样的设计意图，在现有技术中有三种主要的承载方式。差别不在「用什么工具」，而在 产物本身是什么形态——这一条差别，决定了后续所有能力的天花板。

形态一：网格产物

这是建筑三维最主流的交付形态。传统管线由 3ds Max、Maya 等 DCC 建模后导出 glTF / FBX / OBJ； 近年的 AI 资产生成工具（Meshy、Tripo 一类）则从文本或单图直接生成三角网格。 前者质感可控但生产周期长，后者上手门槛低、出图快，但产物同构：顶点、面与纹理。

网格路线保存的是几何结果，不含构件语义与参数结构。一扇窗在文件里只是一片三角形区域， 无法回答「这是哪类窗、装在哪面墙、宽高多少、能否换成推拉窗」。体积也随细节快速膨胀。 这类资产适合展示，不适合作为需要按构件理解、调整和复用的建筑主体。

形态二：代码产物

让大模型直接输出渲染代码（Three.js 一类）确实可以得到能跑的场景，迭代反馈也快。 但它本质上是一次性代码：每份场景是一段独立程序，参数散落在语句里，没有统一的数据契约， 跨场景复用几乎不可能；修改一个参数往往需要重新生成。

更关键的是不可校验：校验需要的是声明式数据，而代码是命令式过程—— 你可以逐字段检查一份数据，却无法逐字段检查一段程序的意图。 场景一旦复杂，截断、格式漂移与静默出错便随之而来。

形态三：参数化表示

参数化方向并非无人走过。Grasshopper 用可视化组件替代手工建模， 是确定性数据流驱动几何的成熟先例；Houdini 以程序化节点与缓存复用解决了 「改动即重跑」，且支持无头批处理；IFC（ISO 10303-21）则长期试图统一建筑语义。 三者共同确立了「参数化表示是建筑数字化的正确方向」这一判断。

它们的缺口同样明确：Grasshopper 的 .gh 文档不脱离 Rhino 会话便无法解释； Houdini 的产出是程序（节点图与 VEX）而非可被非编程人员直接编辑的数据结构，建模门槛高； IFC 语义完整，却体积庞大、渲染器支持参差，难以承载运行时交互。

缺口指向同一个位置。把 1.1 的三重代价与这三个缺口对起来看： 要轻，就得交付参数而非网格或代码（对应体积）；要开放，产物就必须脱离宿主软件独立解析（对应语义）； 要可校验，产物就必须是声明式数据而非程序（对应校验）。 三条同时满足，才是本项目选择的位置：足够轻、足够开放、足够可校验。

形态一丢失的是参数结构，形态二丢失的是数据契约，形态三则在开放性、门槛与体积上各有折中。 要同时拿到语义、可编辑性与可校验性，就必须在中间引入一层独立的、可被程序精确解释的结构化表示——也就是本项目的 WILD 蓝图（见 1.3）：它与设计文档同为结构化数据，区别在于每个字段都对应确定的几何后果，因此可被程序而非模型解释。

1.3 项目定位

如 1.2 所述，这里要补上的正是那一层「可被程序精确解释的结构化表示」。WildAgent 选择引入一层自定义参数化蓝图语言 WILD 作为中间表示， 并把整个系统划分为「设计」与「实现」两层：

  • 设计层由模型负责——决定体量关系、立面分格、屋顶形式、构件需求与材质意图，产出语义化的设计文档；
  • 实现层由确定性代码负责——把设计编译为蓝图、把蓝图重建为几何、把蓝图校验为可交付或不可交付，全程不依赖模型。

但这两层并不等价。实现层是不可替换的部分——WILD 语言本身与确定性几何引擎， 决定了产物是否可复现、可校验、可移交。设计层则是可替换的：当前由 Agent 实现， 只因为自然语言是目前最省事的入口；换成表单、换成脚本、换成其他工具，都不影响蓝图本身的确定性与可校验性。

因此本项目的底座是「一套建筑数据协议 + 一个确定性解释器」， Agent 是架在这层之上的一层应用，而不是反过来。项目名中的「Agent」描述的是当前形态，不是不可替换的本体。

这条分界线不是「谁更聪明」，而是产出是否需要被验证。 模型擅长生成与判断，但输出是概率性的——不可复现，也无法被程序逐字段验证； 程序擅长计算与校验，但输出是确定性的——可复现、可被自动验证。 把两类工作分给两类执行者，系统才能同时获得「设计有灵气」与「落地可信」。

由此推出一条更硬的原则：实现层不产生设计。 图纸写了什么，蓝图就建成什么；图纸没写的，编译器不会替它补全。 这样「设计」与「实现」之间就不存在隐藏的隐式转换，每一处设计判断都可被追溯回图纸本身。

WILD 蓝图本身不含任何网格数据，只描述构件、尺寸、坐标、依附关系与材质， 因此它既是交付格式，也是可版本化、可复用的存档格式——在同等内容下， 其体积较网格产物小约两个数量级（实测见 1.4 与创新点 07）。

1.4 轻量化：一个贯穿全栈的取舍

如 1.1 所述，体积是三重代价的起点：体积降不下来，就谈不上携带足够语义； 携带不了语义，就谈不上编辑；编辑不了，就谈不上工作台。 因此轻量化在本项目里不是事后做的优化，而是从技术选型阶段就开始遵守的约束。

它在四个互不替代的层面同时成立——分别对应代码、数据、部署与推理， 每一层都可以被独立度量。某一层做得再小，也补不上另一层的失控。

层面 做法 实测结果
引擎依赖 几何引擎不引入任何第三方运行时库，唯一依赖是用于类型检查的 TypeScript；不绑定任何商用引擎 整套几何引擎 50 个源文件、7660 行、326 KB，包清单中运行时依赖为空
产物体积 交付参数描述而非网格，几何按需重建 同等内容下平均每三角面仅占 1.26 字节，较未压缩网格小约 85 倍——而单个顶点的坐标（3 个 float32）本身就要 12 字节，光一个顶点就比整个三角面的参数描述贵近 10 倍（详见创新点 07）

上下文成本 知识库按能力边界建设，单轮只注入最相关的少量分片 知识库总量约 33 万字符，与引擎源码同量级；单轮注入上限 18000 字符，仅占其十八分之一（详见创新点 09）

这四个层面指向同一个取向：把确定性、可复算的部分交给尽可能小的代码， 把不确定性约束在尽可能窄的环节里。 几何引擎不需要庞大，是因为它只做参数到网格的确定性计算，不承担材质资产、动画系统、物理模拟与通用编辑功能； 产物不需要庞大，是因为它保存的是设计意图而不是计算结果； 上下文不需要庞大，是因为补给的只是模型不知道的协议与边界，而不是它已经会的通识。

轻量化同时也是可移植性的前提。正因为几何引擎不依赖任何图形运行时， 它才能在浏览器 Worker、服务端离线校验与命令行评测三种环境中复用同一份实现，而不是维护三套。

1.5 从轻量交付到建筑工作台

项目分两个阶段推进，两者各有独立的成立条件：前一阶段不成立，后一阶段无从谈起。 需要说明的是，工作台的完整能力已在 2.7 与第 03 章分别从工程实现与应用两个角度展开； 本节只陈述它成立的前提条件。

第一阶段：轻量交付。以参数描述替代网格，把建筑资产从数百 MB 降到 MB 量级，同时保留构件、尺寸与依附关系。这一阶段解决的是「带得走、带得动」，其产出本身已可作为独立交付物使用。

该阶段已确定的下游方向是面向网页端的 3D 去中心化数字世界：这类世界需要可进入、可交互的建筑，而浏览器端无法承载常规建筑软件导出的文件体积。WILD 蓝图能在 MB 量级内同时携带构件语义、依附关系与行为约束，为其供给建筑资产。该方向当前具备接入条件，接入本身尚未落地。

第二阶段：建筑工作台。在第一阶段之上，才谈得上面板调参、场景树增删、增量补丁、人机协同与交付前校验。这些能力的共同前提是：蓝图中每个构件都有语义、每次改动都可结构化表达、每次改动后都能重新编译并校验。换言之，工作台不是轻量化的延伸，而是语义层与校验层建立之后的直接结果。

这一方向最终落到四项终局能力：自由构件组合——构件库可自由增删与排列，不受生成路径约束；参数可调——尺寸、坐标与材质以属性暴露，随改随重建；拖拽摆放——在场景中直接操作，而不必先用语言描述意图；人机协同——用户与 Agent 通过统一补丁格式合入改动，而不是相互覆盖。其中后三项当前已可使用，工程实现见 2.7，应用形态见第 03 章。

1.6 本项目不占优的地方

需要明确的是，本项目在「生成能力」这一项上并不领先。通用编程 Agent（如 Codex、Claude 一类） 在读取 WILD 规范、引擎源码与若干份成功蓝图之后，同样能写出可渲染、甚至相当精细的建筑—— 这条基础能力并不专属于本项目。

本项目当前的实际能力上限是低复杂度建筑的稳定产出。更精细的构件组合与更高的一致性仍在量化之中， 尚不能承诺稳定复现；不同建筑类型的生成成功率、设计与成品的一致性都有待持续统计。

因此本项目不主张「生成得更好」，而主张生成过程的三件事： 知识不随会话蒸发——构件约定沉淀在项目内，不必每次重读引擎源码； 小修改不必经过对话——拖拽、调参、增删构件都不消耗模型调用，也不会出现「顺手改了别处」； 产物始终留在同一工作台——生成结果直接进入编辑，不存在导出后再手工处理这一步。

需要说明的是：以上三点是架构差异，不是已验证的优劣结论。 专门化实现是否真的更好，应当在相同模型、相近任务与一致验收标准下， 比较成功率、耗时、Token 消耗、修改准确性与最终渲染效果后判定。当前尚无这组对比数据。

02技术架构

2.1 总体架构

系统由三个可独立运行的包组成，依赖方向严格单向，不存在循环引用。 分层的核心目的是：让几何算法在全系统只有一份实现， 避免后端与前端各自解释同一份蓝图而产生不一致。

wild-core 几何引擎。无框架依赖、无 npm 运行时依赖，唯一公开入口；对外只暴露「蓝图进、几何出」。
wild-web 编辑器。负责交互、状态与渲染适配，不实现任何几何算法，重建在 Web Worker 中执行以避免阻塞交互。
wild-server 服务端。负责模型调用、知识检索、生成编排与交付校验，同时作为可独立接入的微服务。

2.2 三个核心数据契约

系统复杂度的主要来源不是代码量，而是三类数据在不同阶段的职责边界。 明确划分后，绝大多数复杂问题都可以归因到「某个契约被越界使用」。

三者构成一条清晰的链路：设计 → 蓝图 → 修改。 模型负责前两段的语义判断，确定性代码负责第三段的执行与回滚。 「设计未定不许建」「校验不过不许存」「补丁失败不留脏」三条规则， 构成了系统可靠性的基本骨架。

2.3 生成主链路

LangGraph 只承担编排，不承载业务判断。图拓扑集中定义在一处，节点实现分散在各领域包， 并由测试强制「节点入口文件不超过 100 行」「节点之间不得互相导入」「领域包不得反向依赖入口层」。 这条约束保证了任何一次功能扩展都不会退化成核心文件持续膨胀。

两个关键设计

  • 任务展开不调用模型。图纸批准后，构件条目由程序按图纸标记做差集确定性推导得出。 这一步把「该建哪些构件」从模型的自由发挥变成程序的计算结果， 直接消除了漏生成、重复生成和类型发散这一类问题的源头。
  • 循环有明确边界。重规划受四重上界约束：单条目执行上限 3 次、计划修订上限 2 轮、 单条目替换上限 1 次、连续无进展上限 2 轮。任一上界触发即转入收尾， 不允许出现无限自我修复消耗预算的情况。

2.4 确定性边界：纯函数编译器

这是整个系统最核心的工程决策。设计文档到蓝图的转换由 app/agent/compiler/compile.py 完成，该模块被约束为：

  • 无 IO——不读写文件、不访问网络；
  • 无模型调用——编译过程中不存在任何 LLM 交互；
  • 无全局状态——不依赖可变的模块级变量。

三条约束共同保证了一件事：同一份设计文档，无论编译多少次、在哪台机器上编译， 输出都逐字节相同。这使得蓝图成为可信的版本化产物—— 可以比对差异、可以回滚、可以在不同环境下复现，也使得「模型输出是否正确」 这一问题被收敛为「编译缺陷是否为空」这一可判定问题。

编译器遵循另一条原则：它不产生设计。 如果图纸中某项内容超出引擎能力，编译器不会猜测或补全，而是将其作为编译缺陷报出， 交回上游处理。这保证了「图纸写了什么」与「蓝图建成什么」之间不存在隐藏的隐式转换。

2.5 知识库与检索

知识库按能力边界而非「尽可能全」的原则建设。核心判断是： 模型已有的通识不需要入库，真正需要补给模型的是协议规范与引擎能力边界—— 即「这个系统的构件怎么写」「哪种形态当前引擎做不到」。 这一点直接决定了召回质量：一旦把模型本来就会的常识写进知识库， 召回结果中就会出现大量与当前任务无关的片段，反而干扰生成。

知识组织 按语义分片，标题路径与业务实体元数据随分片继承，保证分片独立可用且可过滤
检索链路 向量检索 + 元数据过滤 + 业务规则重排；单轮注入上限为最相关 6 个分片、约 18000 字符
效果量化 以 Hit@K、Recall@K、MRR 三个指标离线评测，避免凭主观判断调整
门控策略 默认只观测不拦截；待用当前 embedding 的正负样本校准距离阈值后再切换为拦截，避免未校准阈值误伤正常请求
候选入库 网络检索获得的候选知识先写入隔离区，经批准后由唯一晋升脚本入库并同步向量索引
完整性 构建阶段逐项校验正式文档清单，缺少任一必需文档即构建失败

要解决的问题：知识库的默认做法是「能加就加」。但一旦把模型本来就会的通用常识写进知识库， 召回结果中就会出现大量与当前任务无关的片段，反而干扰生成，且这类冗余无法被察觉。

解法：把知识库的建设标准定为能力边界，而非覆盖广度。 只收录两类内容——协议规范（这个系统的构件怎么写）与 引擎能力边界（哪种形态当前做不到）。 模型通识一律不入库。网络检索获得的候选内容先写入隔离区， 经人工批准后由唯一晋升脚本入库，避免未经验证的内容直接进入召回路径。

价值：真正的取舍不在检索侧，而在准入侧——收录标准从「覆盖广度」 改为「是否属于本项目专有、且模型不可能知道的内容」。这是一条可执行的收录规则，而不是一次检索调优。 更反直觉的一点是：知识库规模与模型能力增长是负相关的——模型越强，需要补给的知识越少。 按这一标准，模型通识入库不只是冗余，它会主动挤占检索位，把真正专有的片段挤出 top-k， 而这种损失无法从召回结果本身察觉。

上下文成本由此得到结构性控制：知识库总计约 33 万字符，与几何引擎源码处于同一量级； 而单轮注入量约为其十八分之一，且取其中最相关的极小部分。与「每次会话先通读整个项目」的通用 Agent 路径相比， 这份知识沉淀在项目内部，不随会话结束而消失。

2.6 校验与可靠性闭环

这是 Agent 类系统最容易被做成「看起来在工作、实际在碰运气」的部分。 WildAgent 的处理原则是：不让模型承担它无法被约束的判断—— 能由程序判定的问题一律程序判定，必须由模型处理的场景一律先定义准入条件。

两级校验结构

层级 职责 执行者
结构校验 顶层结构、元数据完整性、几何容器与构件身份、构件类型闭集、资产清单格式、材质通道取值范围 Pydantic 模型 + 纯函数，逐字段判定，无歧义

校验流水线按固定顺序执行，包含两条容易被忽略但很关键的规则： 早退——基础结构校验未通过时，后续空间校验全部跳过并直接返回，避免在错误的对象上做几何计算； 尾递归复查——自动修复执行完毕后，以「不修复」模式再完整跑一遍流水线， 复查被后续修复动作意外改动的事实。这保证了最终交付状态是自洽的，而不是逐次修复的叠加结果。

修复的单调性门禁

当校验失败需要模型介入时，系统不直接接受模型的输出，而是先定义修复的准入条件： 候选蓝图必须同时满足两个条件才允许提交——

  1. 修复后错误数量严格减少；
  2. 修复后没有引入任何新的「错误码 + 实体」组合。

任一条件不满足，候选蓝图整体丢弃，场景保留在修复前的状态，并把尝试记录写入审计。 此外，模型被限制只能调用白名单内的局部修复动作，且只能修改本轮失败的实体， 不允许修改实体的标识与类型、引用不存在的父墙或材质。

这条规则的意义在于：系统保证了「修复只会让情况变好或保持不变」， 从机制上排除了模型自我纠错时越修越坏的可能。这比单纯增加重试次数要可靠得多—— 重试次数无法保证方向，而单调性可以。

能力边界的显式声明

另一类容易被忽略的风险是静默降级：模型描述了一种形态， 引擎做不到，于是悄悄省略了它，用户直到看到成品才发现缺东西。 WildAgent 采用相反的做法——把当前不具备的能力显式声明在代码中， 当用户需求命中时，将对应条目标记为不可支持并写入交付清单， 同时说明本次实际会交付什么、以及用户如何获得可用结果。

当前显式声明的能力缺口有两类：室内房间平面与房间布局、 场地语义（车库、后院、花园等室外空间划分）。 与「能力缺失」不同，用户要求「平面图」这类交付媒介不一致的表述只记提示、不判为失败—— 因为体量与立面的语义都在，只是呈现形式不同。 这条区分避免了把正常的表述差异误判为系统缺陷。

人机协同的失效保护

设计审核使用 LangGraph 的 interrupt 机制暂停图、以 Command(resume=…) 恢复。 审核结论的落地带有校验：恢复时比对设计文档的内容指纹与解析器版本， 若图纸在审核期间被改动，则拒绝沿用旧审核结论，要求重新审核。 这条保护针对的是一个真实存在的人机协作事故—— 人看到的图纸与最终建成的图纸不是同一版，任何静默接受都会产生难以察觉的错误。

2.7 前端工作台

前端不是「结果查看器」，而是完整的工作台。除对话与步骤展示外， 提供属性面板调参、场景树增删构件、构件库直接新增、三轴拖拽移动等直接操作能力。 这带来一个重要的使用特征：小修改不需要经过对话。 拖动一扇窗、调整墙厚、删除一个构件都不消耗模型调用，也不存在模型「顺手改了别的地方」的风险。 在生成质量尚未完全稳定的阶段，这个特性比任何自动化能力都更有实际价值。

  • 几何重建在 Web Worker 中执行，不阻塞画布交互；
  • 补丁应用带事务性：预检与完整校验通过后才提交，失败则回滚蓝图并恢复上一版网格；
  • 状态按请求与会话归属：消息、步骤、思考过程、诊断与产物均绑定请求标识，迟到的结果不会覆盖已切换的画布；
  • 表现层与生成分离：世界光影设置、材质包、程序化材质各有独立面板与运行时，可单独编写、单独调试、即时渲染，不牵动生成链路。

03应用场景

3.1 建筑方案生成与深化

最直接的场景：用自然语言描述一座建筑，系统生成可校验、可版本化、可继续编辑的蓝图， 并实时渲染为 3D 场景。生成不是终点，产物直接进入编辑流程。

该场景的价值不在「一次生成」而在于迭代成本低。 由于蓝图是结构化的参数描述，调整一层的层高、改变立面分格密度、更换屋顶形式都不需要重新生成整栋建筑， 而是作为一次结构化修改被精确应用。对需要多轮比选的设计前期工作，这决定了实际可用性。

3.2 方案比选与设计交流

在教学、竞赛或方案前期阶段，经常需要在多个体量方案之间比较。 由于产物是可复现的参数化蓝图，同一套构件知识与渲染条件可以保证不同方案的呈现差异 只来自设计本身，而不受模型输出随机性的干扰。 配合确定性的编译器与实时渲染，方案比选从「渲染出图再对比」简化为「改参数看结果」。

3.3 增量编辑与人机协同

已生成的场景可以持续演进，路径有二，且两者使用统一的补丁格式、可叠加：

  • Agent 修改——通过对话提出结构化修改意图，由 Agent 生成补丁提案；
  • 用户直接修改——通过属性面板、场景树、构件库与拖拽直接操作。

由于所有修改都必须经过同一套预检与完整校验，双方在同一条规则下协作， 不存在「用户改的格式」与「Agent 改的格式」不兼容的问题。 对诸如「把车库移到侧面」这类跨构件的修改，系统会一并处理位置、关联构件与既有场景的约束关系。

3.4 精细度分级与预算控制

生成精细度是用户显式选择的四档，而非模型临时决定，且同一档位同时约束设计范围与资源预算。 这一设计的目的是让成本可预期：使用者在发起生成前就知道大致会消耗多少模型调用、能得到什么程度的细节。

3.5 建筑之外的参数化物件

系统按交付对象区分两条并列的链路：建筑链产出体量、立面、屋顶与结构； 物件链产出家具、器物等单体对象。二者共用同一套构件体系、材质契约与校验流水线， 因此项目同样适用于家具、亭台、景观构件及其他参数化物件的设计。

引擎侧的几何构建能力按成熟度分为三档，这一分级本身即是能力边界的一部分： 墙、楼板、楼梯、通用几何体为稳定级；柱、梁、屋顶、洞口、家具、简化人物为部分支持； 程序化红砖为实验级。组合构件编译器覆盖 11 类构件并支持贴墙、贴路径、贴面三种附着方式。

3.6 作为可复用的服务能力

服务端不依赖前端即可独立使用。生成能力通过 REST 与 WebSocket 暴露， 模型调用、知识检索与生成编排全部封装在后端。 其他应用可以直接接入这些能力而不必复用本项目的编辑器前端。 接入方需要遵守三条约定：产物只在完整校验通过后才返回； 返回的蓝图带服务端权威的文件标识，不应自行拼接路径； 就绪探针会读取真实的向量库状态，初始化失败时明确返回异常而非伪装健康。

04建筑成果展示

以下建筑均由系统从自然语言需求生成，经设计审核后编译为参数化蓝图，再由确定性引擎重建渲染。 每一类建筑都对应一份可执行的书写规则，体量关系、立面分格、屋顶形式与构件参数均来自规则约束， 而非逐件指定。

共 7 栋，覆盖传统建筑、塔类地标、传统居住、公共建筑与现代住宅五类。 每栋展示三个视角：正立面与两个不同方位的轴测。

值得说明的是：这些建筑之间共享同一套构件体系与校验规则，差异来自各自的书写规则文件， 而不是为每栋建筑单独开发代码。新增一类建筑形态，原则上只需补规则与必要的几何构建器， 不需要改动生成链路。

四坡屋顶、老虎窗、入口台阶与柱式门廊。与前一栋共享同一套构件， 差异仅来自规则中的屋顶形式与立面分格参数。

08 三层平顶挑檐现代别墅 现代住宅 · 平顶挑檐

平屋顶配出挑檐口，大面积玻璃与横向线脚。挑檐深度来自规则中的出檐参数， 与坡屋顶类建筑共用同一套构件，仅屋面构件的生成方式不同。

05创新点

以下七点并非功能罗列，而是针对「AI 参与三维内容生产」这一命题中若干公认难题的工程解法。 每一点都对应可验证的代码约束，而非设计意图的描述。

创新点 01语义与几何分离：单一实现与纯函数编译器

要解决的问题：模型直接输出几何或渲染代码，产物无法复现、无法比对、无法复用， 同一份设计每次生成都可能得到不同结果。而如果几何逻辑与渲染框架耦合，还会出现第二重问题—— 同一份蓝图在不同环境下被重建出不同结果，且难以独立测试与复用。

解法：引入独立的参数化蓝图语言作为中间层，把设计到蓝图的转换实现为 严格受限的纯函数模块——禁止文件读写、禁止模型调用、禁止全局状态； 同时把几何重建抽为独立的引擎包，不依赖任何前端框架、不依赖任何 npm 运行时依赖， 对外只暴露单一入口，唯一外部输入是包内自带的结构契约文件。

价值：「同一输入必然得到同一输出」从期望变成可验证的性质—— 而这个性质的前提正是全系统只有一份几何实现，前后端不会各自解释蓝图。 蓝图因此成为可信的版本化产物：可做差异比对、可做回滚、可在不同环境复现。 引擎也可脱离浏览器单独测试，修改后即时反映到画布， 并为服务端几何校验或离线出图留下了通路。更重要的是， 问题被重新表述为「编译缺陷是否为空」，这个判定完全交给程序，不再依赖对模型输出的信任。

创新点 02图纸驱动的落地：把「建什么」从模型手里收回

要解决的问题：漏生成、重复生成、构件类型发散。 根源在于「该建哪些构件」原本由模型在生成时顺带决定，每次决策都可能不同。

解法：模型只产出设计文档；批准后，构件条目由程序按图纸标记做差集确定性推导得出， 该步骤完全不调用模型。模型仅负责单个构件的具体实现。

价值：全局布局的一致性由算法保证，而非由模型的稳定性保证。 构件数量、类型与归属在执行前即已确定，可预估、可检查， 出问题时可以直接定位到是「图纸设计问题」还是「单个构件实现问题」， 而不是面对一个混在一起的不可解结果。

创新点 03修复的单调性门禁：给 Agent 的自我纠错设定准入条件

要解决的问题：让模型修 bug 时，修复本身可能引入新错误， 而系统通常无法判断，只能接受结果——于是出现越修越坏。

解法：候选修复必须同时满足「错误数量严格减少」与「未引入任何新的错误码与实体组合」才允许提交， 否则整轮回滚并保留审计记录。模型被限制只能调用白名单内的局部动作， 且只能修改本轮失败的实体，不得改动实体标识与类型。

价值：系统给出了「修复只会让情况变好或保持不变」的机制性保证。 这与「增加重试次数」有本质区别：重试次数无法约束方向，单调性可以。 对于一个自主调用模型的系统，这类不变量是可用性的前提。

创新点 04能力边界显式声明，拒绝静默降级

要解决的问题：模型描述了引擎做不到的形态，系统悄悄省略， 用户直到看到成品才发现缺东西，而问题定位极其困难。

解法：把当前不具备的能力显式声明为结构化配置。需求命中时， 对应条目标记为不可支持并写入交付清单，同时说明本次实际交付什么、如何获得可用结果。 另将「能力缺失」与「交付媒介不一致」严格区分——后者只记提示，不判为失败。

价值：把「系统能力的边界」变成可查询、可版本化的显式契约， 而不是散落在开发认知里的隐性知识。用户预期与系统实际能力之间的偏差被提前消除， 排查问题时也不再需要从缺失的构件反推原因。

创新点 05唯一人工决策点，并带失效保护

要解决的问题：人机协作中最隐蔽的事故类型—— 人审核的是版本 A，系统最终构建的是版本 B。审核动作与构建动作之间存在时间窗口。

解法：全链路只保留一个暂停点，即设计审核，使用框架原生的中断与恢复机制。 恢复执行时比对设计文档的内容指纹与解析器版本， 若图纸在审核期间被改动则拒绝沿用旧结论，强制重新审核。

价值：人的判断被放在唯一真正需要判断的位置——设计意图是否正确， 而不是重复确认程序已经能确定的事。 失效保护则消除了「批的是 A、建的是 B」这一类不会报错、只会产出错误结果的故障。

创新点 06参数化表示带来的存储效率：同等内容，体积相差两个数量级

要解决的问题：网格路线的产物与几何数据绑定。一旦交付，形体就被固化成顶点， 想改一扇窗的位置或高度，只能重新生成或回到建模工具改，无法在文件层面做精确调整。

解法：交付物是参数描述而非几何。构件的类型、尺寸、坐标、依附关系与材质引用 构成一份文本；几何在需要时才由确定性引擎重建，不占用存储，也不进入版本库。

实测：对仓库内 204 个可重建场景做全量统计，共 422 万三角面、1261 万顶点。

同一批内容的存储形式 体积 相对 .wild 可按构件编辑
WILD 蓝图（本项目） 5.1 MB 基准 可以

glTF 顶点量化 54.1 MB 约 11 倍 不可以

价值：换算到平均尺度，一份 422 万三角面的场景用网格表达需要 433 MB， 用 WILD 表达只需 5.1 MB——平均每个三角面 1.26 字节。 单体量看更直观：一栋 686 个构件、退台式玻璃幕墙商业综合体， 蓝图 128 KB，对应网格约 9.7 MB，差 78 倍。

注：上述网格体积按位置 12 + 法线 12 + UV 8 字节每顶点、索引 4 字节估算。 由于几何引擎当前不做顶点焊接，该值是网格方案的上界； 若做焊接，顶点数通常可降到三分之一至六分之一。即便如此，与压缩网格相比仍有约四倍差距。

创新点 07粒度即预算：精细度与算力由同一个参数约束

要解决的问题：让用户选择「更精细」时，真正的成本通常在生成之后才显现—— 模型调用次数、构件条目数、渲染耗时同时上升，用户既无法预估，也无法在生成前取舍。

解法：把四档粒度做成单一开关，由它同时决定设计范围与资源预算： 迭代上限 4 / 6 / 12 / 20 次，模型调用 6 / 10 / 24 / 40 次，最大构件条目 8 / 12 / 24 / 40 条。 用户在发起生成前就能知道大致消耗与预期精细度。

价值：生成质量与生成成本不再互相独立地漂移，而是绑定在用户的一次显式选择上。 更重要的是，预算不是靠提示词里的「请简洁一点」去约束模型， 而是由程序硬性执行——即便模型想多调用几次，条目上限也不允许。

说明：以上创新点均为工程机制层面的设计取舍，其价值需要与同类方案在同一模型、 相近任务和一致验收标准下比较成功率、耗时、Token 消耗、修改准确性与最终渲染效果后才能量化。 创新点 06 的体积数据为仓库内 204 个场景的全量实测，其余为设计描述。 本文档不对尚未量化的部分给出结论。

06能力边界与发展规划

本章把「当前能做到什么」与「接下来要做什么」分开陈述。 已实现的部分标注为已实现或机制已通，尚未实现的部分一律标注为 规划中，两者不混写。

6.1 当前能力边界

系统当前可稳定交付的是低粒度下的完整链路。 中、高、极高三个档位的设计范围与资源预算机制均已实现，但生成稳定性不足， 尚不能作为可交付能力对外承诺。

6.2 显式声明不支持的能力

与「不稳定」不同，以下能力是明确不做的。系统在生成前即会识别并标记， 将对应条目标记为不支持写入交付清单，同时说明本次实际交付什么，而不是硬编一个结果出来。

室内房间平面 不设计房间位置、功能分区与内部隔墙。用户提出时会收到说明，体量、外轮廓、门窗洞口与立面尺寸照常生成
场地语义 不处理车库、后院、花园等室外空间划分；这类需求被判定为能力缺失而非交付媒介差异
二维平面图与剖面图 不产出。体量与立面以图纸 SVG 呈现，此类要求只记提示、不判为失败
有机造型与扫描级细节 参数化引擎不适用于任意曲面、扫描网格与真实复杂人物

规划一光影扩展包规划中

把上表的光影参数面打包为可命名、可版本化、可分发的扩展包。用户调整参数并实时预览后保存为独立文件； 导入世界时载入该包，场景即以对应的光影条件呈现。

落地所需：参数序列化格式、与世界包的合并规则、与当前设置之间的迁移策略。底层参数面已全部就位，主要工作在编辑界面与持久化。

规划二材质扩展包规划中

把材质配方（基色、粗糙度、法线强度、通道组合、程序化参数）抽为独立的可编辑资产， 与现有 PBR 贴图资产并列管理；用户制作材质包后可在材质面板中选用，并在世界导入时随包生效。

落地所需：配方参数与现有材质契约的映射关系、参数合法范围的校验、与蓝图材质引用的对接方式。渲染运行时已支持外部传入，不构成瓶颈。

规划三扩展包制作页面规划中

前两项都以「用户能自己制作」为前提，而当前工作台没有任何创作入口。 计划新增独立的「扩展制作」页面：左侧参数表单，右侧实时预览视口， 支持光影包与材质包的创建、保存、导入、导出与本地库管理， 并在参数越界时给出与后端校验一致的提示，而不是静默接受。

落地所需：参数表单与校验规则的前端实现、预览视口与主视口的隔离、扩展包的版本管理。这是纯工程工作，不涉及模型能力变更。

规划四世界导入与效果预览规划中

光影与材质包的价值必须通过「同一座建筑在不同包下的对比」才能体现。 计划在世界导入环节提供效果预览：载入世界包后列出其携带的扩展包， 允许逐一切换并在同一机位下即时对比，把选择权交还给用户而非自动套用。

落地所需：多包并存时的覆盖顺序定义、切换时的增量重建（避免全量重编译）、对比视图的取景一致性。世界包的解析与持久化链路已通。

为什么需要：当前的直接操作覆盖了「单个构件的调整」， 但真实的设计工作还包括对齐、阵列、批量替换、楼层复制与多选联动—— 这些操作在参数化体系下应当由程序完成，而非逐个手动调整。

计划沿两条线推进：一是补齐建筑场景常用的批量与对齐类操作， 使参数化体系的优势真正传导到编辑阶段； 二是把构件的设计参数（如开间、进深、层高）提升为可整体编辑的层级结构， 让「改一次、整栋生效」成为常态。

落地所需：编辑操作的撤销与事务边界、与 ScenePatch 校验链路的统一， 以及参数层级化后蓝图协议的一次版本升级。

规划六生成稳定性的收敛 规划中

为什么需要：6.1 列出的三处主要不稳定来源（附属构件宿主解析、 复杂体量下的立面分格、室内对象坐标推导）都是确定性问题， 继续依赖模型判断只会越来越贵且越来越不稳。

计划按「先观测、再收编」的顺序推进：先用量化指标确认每个问题域的实际发生率， 再把能被程序判定的部分从模型职责中移出，交给确定性算法。 与之配套的评测集与消融实验会同步建立，使每一次收编都有可对比的数据支撑。

落地所需：固定评测集、通过率指标、逐问题域的失效统计， 以及知识库的分组消融。这部分工作不依赖模型能力，是当前最具确定性的投入方向。

本章内容按项目当前实际状态撰写：6.1 与 6.2 为已核实的现状与限制， 6.3 列出的是已经存在的底层机制及其缺口，6.4 与 6.5 标注为规划，尚未实现。 规划项不构成对当前能力的承诺。
