## 四、本轮踩到的坑（按「谁的问题」分诊）

| # | 现象 | 根因 | 归属 | 修法 |
|---|---|---|---|---|
| 1 | 真实链路直接抛异常 `必须且只能匹配一种结构` | `door.interaction.openAngle = 0`，而 schema 要求 `> 0` | **蓝图 / 数据** | 改 90。⚠️ **11 项数据门禁当时全绿**——只有真实链路才暴露 |
| 2 | 7e 报「1 面墙顶部裸露 2.4m」 | `roof_d` 的 span 边界与 `wall_d_left` 墙中心线**恰好重合**，浮点上判为未覆盖 | **蓝图 / 数据** | span 2.4 → 3.0，让屋顶明显盖过墙 |
| 3 | 渲染构图与照片**左右镜像** | 门廊体量放到了 −X 侧。从正面（−Z）看时屏幕右 = −X，所以 −X 侧的体量出现在画面右，而照片里门廊在画面左 | **设计理解** | B 从 x∈[−4.2,0] 移到 x∈[12,16.2] |
| 4 | 预览图整幅空白，只剩天空 | 自写的软件光栅化器里 `area` 用 NDC 算、重心坐标用屏幕坐标算；NDC→屏幕在 y 轴翻转，两者反号 → 每个像素都被判成在三角形外 | **预览工具自身**（非引擎） | 统一用屏幕坐标算 area |
| 5 | 正立面白墙渲染成中灰 | 预览器照抄了查看器的主光方向（+X +Z），而照片里正立面是**受光过曝**的 | **预览工具自身**（非引擎） | 光向改为 −X −Z |

> 3 与 4/5 的区别很重要：**3 是蓝图错**（几何真的在反侧），**4/5 是我的观察工具错**。
> 如果只看图不看门禁数据，很容易把工具的问题误判成引擎的问题。

## 五、分诊判据（可复用）

渲染出来不对时，按这个顺序判：

1. **先跑数据门禁** `verify_wild_blueprint.py` — 悬空 / 穿透 / 越界 / 宿主不匹配 → **蓝图问题**
2. **再跑真实链路** `check_blueprint_render.mjs` — 数据门禁过了但这里抛异常或 AABB 离谱 → 仍可能是**蓝图问题**（schema 约束比校验器严）
3. **最后看图** — 前两步都过、只是观感不对（材质 / 光影 / 面朝向 / 分格粗细）→ 才轮到**引擎问题**
4. ⚠️ 看图之前先确认为"看图的工具"本身没问题 — 本轮 4、5 两条都是工具错，差点误导结论

### 5.1 离线预览器 `render_preview.mjs` 的能力边界（看图前必读）

这台自写光栅化器**只做 flat shading + 常量环境光**，因此下面这些"看起来不对"都不是引擎的问题：

| 观感现象 | 真实原因 | 判定方法 |
|---|---|---|
| 玻璃像不透明浅色板，一层"看不进去" | 预览器**不做 `transmission` / `opacity`**，玻璃按 `baseColor` 当实体面画 | 见 §3.1：用 `audit_wall_openings.mjs` 量立面面积，确认墙**已开洞** |
| 玻璃栏板是一道浅色实心带 | 同上（`glass_rail` baseColor = [0.72,0.84,0.88]，很浅） | 查 `entity.meshes[i].materialRef` 是否为 `glass_rail` |
| 屋檐平、无阴影缝；凹口无阴影 | **无阴影 / AO**（只有 N·L 朗伯项） | 对比真实浏览器视图（本机无 WebGL，需在有 GPU 的机器上看） |
| 深色细框在 1092px 下几乎看不见 | 分辨率不足 + 无边缘增强 | 加 `--w=2400 --h=1600` |

> ⚠️ **`materialRef` 是字符串（材质名），`materialParams` 是与 `meshes` 等长的平行数组。**
> 取材质要用 `entity.materialParams[meshIndex]`，**不是** `materialParams[mesh.materialRef]`。
> 这条踩过：第一次写探针时按后者取，结果每个网格的材质都是 `null`，差点得出"材质没绑上"的错误结论。

### 5.2 本轮新增的诊断脚本

| 脚本 | 回答的问题 |
|---|---|
| `.workbuddy/diag/audit_wall_openings.mjs <蓝图>` | 宿主墙到底有没有被 `window`/`door` **开洞**？按"立面平面上三角形总面积"与理论洞口面积比对，是**定量判据**不是目测 |
| `.workbuddy/diag/probe_material_binding.mjs <蓝图>` | 每个网格绑的是哪个材质？`mesh.materialRef` ↔ `materialParams` 的平行关系是否成立 |

**`audit_wall_openings.mjs` 本轮实测**（`wall_f_l1`，12×3.3m，3 个开口共 30.68 m²）：
立面平面上三角形总面积 **19.42 m²** —— 理论"开了洞"值 17.84 m²、理论"实心"值 79.20 m² → **墙体确实被开洞**。
→ 结论修正：**一层幕墙的通透性是对的**，"看不进去"纯粹是预览器不做透明。

## 六、待办


**建议进知识库的规则（会影响 agent 生成，需拍板后再动）**

- 🔴 `door` 的 `interaction.openAngle` **必须 > 0**。取值 0 会被 schema 拒绝，而现有 11 项数据校验器**查不出来**，只有真实编译才报错。agent 生成推拉门时很容易写 0。

**渲染侧下一轮（蓝图侧，已自查出的缺口）**

- 🔴 **场地/地形缺失** → 建筑与泳池平台整体**悬空**。正立面下方能透视到平台底面，泳池池壁（`pool_blue`）从平台下缘露出一道蓝带。
  照片里平台与地面平接、周边有围墙与植被。修法：补一圈"回"字形地形板（`floor`，绕开池口）落到设计地坪。
- 🔴 **泳池无水** —— 现只有 `pool_bottom`(-1.7/-1.5) + 4 面池壁（高 1.5），是个**空蓝坑**。
  需补一块接近池沿标高的水面板；水的马赛克分层与折射取决于引擎是否支持半透明/折射材质（**待查**，属 C 类）。
- **C 体量**（主体右侧二层内退 + 阴影凹口）当前用窗近似，未做真实内退。
- **B 门廊落地柱**：照片是 **1 根方柱**，现为 2 根圆柱（`column.style: "modern"`，`bottomRadius/topRadius` → 圆柱）。方柱需查引擎是否支持（**C 类**）。
- **木格栅**：照片门廊顶棚是"有缝的木格栅"，现为一块 0.08 厚的整板（`floor_b_ceiling` + `wood_slat`）。可用多条细板近似（蓝图侧可解）。
- 室内（可见餐桌椅）、植被（椰棕/灌木）、围墙、躺椅。

**预览器侧（工具，不是引擎）**

- 🔴 **补透明**：支持 `transmission` / `opacity`，否则所有玻璃（幕墙、栏板）观感都失真 —— 本轮最大的误判来源。
- **补阴影/AO**：屋檐阴影缝、体量凹口的深度感全靠它。
- 深色细框在 1092px 下丢失 → 提高分辨率或加边缘增强。

**待查（引擎侧，尚未触发）**

- 拖了很久的判断：本机无 WebGL，所有"引擎问题"的判断都只能靠数据与几何间接推。**要判引擎的光照/材质表现，必须换一台有 GPU 的机器开浏览器看。**

### 7.2 出图方式换了（`--screenshot` 会骗人）

新增 `.workbuddy/diag/shot_lantu_viewer_cdp.mjs`：用 CDP 轮询页面就绪标志再截。
旧的 `chrome --screenshot + --virtual-time-budget` 会截到"只有地面、建筑还没重建完"的空帧；
**且此时相机还是写死的初值、与 `?cam=` 无关，不同视角会截出字节完全相同的 PNG**
（本轮 3 张里 `pool` 与 `aerial` 的 md5 一致，差点被误读成"URL 参数没生效"）。

查看器配套改动（都是**观察工具**，不碰引擎）：
- URL 参数：`?cam=pool|front|aerial|iso|back|top`、`?exp=`、`?panel=0`、`?grid=0`、`?bbox=1`
- `window.__wildViewer`：`ready()` / `phase()` / `message()` / `cams()` / `setCam(name)`
  —— 只暴露这几样，**不交出 `renderer`/`scene`/`instance`**，否则"查看器只反映引擎产出"的前提就破了
- 🔴 **取景改为"框建筑本体"**：`focusBoxOf()` 从 `reconstructionReport` 里取结构性类型
  （wall/roof/column/beam/stair 等）的实测包围盒定相机距离与目标点，只有地面/阴影范围仍按整份包围盒。
  原因：加了场地草坪板后（40×30m），整份包围盒被它撑大，相机退到只能看见一片草地、建筑小成一个点。
  **场地理应超出画面，而不是决定画面。**

### 7.3 引擎侧修了一处（详见 `docs/渲染引擎优化/真浏览器出图链路与屋顶覆盖诊断修复.md`）

`RECONSTRUCTION_ROOF_COVERAGE` 判据错误 → 3 块屋顶全报"未完全覆盖墙体范围"（**全是误报**）。
根因：① 拿**每块**屋顶去比**全楼墙并集**（多体量必然触发）；② 墙并集把**泳池矮墙**（高 1.5m）也算进去，
把范围往 −Z 撑到 -7，任何屋顶都盖不住。
修法：只算结构墙（≥1.8m 且 ≥0.1m 厚，与 Python 侧 7e 同口径）+ 比**屋顶并集** + 一次聚合警告。
**修前 3 warning → 修后 0 warning**；回归门禁 `audit_roof_coverage_diagnostic.mjs`（正例 + 反例）。

### 7.6 一个需要拍板的架构缺口

引擎的**光照/look 没有 `src/renderer/` 入口**：`worldLookRuntime.activateProfile()` 只是簿记
（注册的 shader feature 全是裸 `{ id }`，没有 `activate` 实现），真正的 Sky + PMREM 环境 +
灯光 + 曝光 + 雾内联在 `src/components/viewport/CanvasViewport.vue` 里。
⇒ 查看器只能自己硬编码 `HemisphereLight + AmbientLight + DirectionalLight`，
**违反"查看器不自实现引擎行为"的项目原则**（材质/网格有边界，光照没有）。

实测后果：真图里一层幕墙玻璃偏暗到看不出通透 —— ① 没有环境贴图，
`transmission` / `metalness: 0.75` 的窗框拿不到可反射可透射的环境；② 玻璃背后没有室内几何。
**同一份蓝图在两套界面的材质观感不可比。** 三个方案（抽 `viewportLook.ts` 共用 / 给查看器加最小环境贴图 / 不动）
见引擎文档 §三，属架构改动，未擅动。
