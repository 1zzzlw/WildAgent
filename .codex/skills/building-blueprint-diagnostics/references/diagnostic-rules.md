# 诊断规则参考

## 证据最小集

| 关系 | 最小字段 | 计算 |
|---|---|---|
| 直墙顶 | `wall.from`, `wall.to` | `max(from.y, to.y)` |
| 直墙平面范围 | `wall.from`, `wall.to`, `thickness` | 端点范围加半厚度 |
| 平屋顶范围 | `span`, `depth`, `position` | `position.x/z ± span/depth / 2` |
| 坡/曲屋顶 | 生成后的 MeshData | 世界包围盒及檐口/端面最低 Y |
| 楼板层间关系 | `from`, `to`, `thickness` | 同 Y 平面与上下体量覆盖 |
| 门窗宿主 | `parentWall`, `from`, `width`, `height` | 父墙局部沿线范围与垂直范围 |

## 常见通性问题

### 屋顶悬空或墙顶露天

- `position.y` 只表示支承标高；曲面屋顶的檐口可能高于该标高，必须检查实际网格。
- `span/depth` 覆盖墙体平面范围不代表山墙三角区域被填充。
- 对曲面/中式屋顶，墙体矩形顶面与屋面曲线之间出现三角形空白，可能需要通用的山墙封边/填充语义，而不是移动屋顶。
- `chinese_curved` 屋顶应从最高承托的横向墙体推导端部范围；Core 在运行时生成与墙体材质一致的山墙填充。显式提供 `position/span/depth` 只锁定设计边界，不应跳过承托墙识别。
- 允许的墙顶到屋面间隙必须是明确容差；不能用截图主观判断。

### 退台楼层不连续

- 上层墙底应落在下层封顶楼板或明确的梁/柱承托面。
- 退台外露部分应由完整楼板覆盖；不得让上层体量底板单独覆盖同一标高而留下平台缺口。

### 组件重叠与 Z-fighting

- 先区分真实体积交叉和共面闪烁：墙、柱、梁在承节点处相交通常是结构关系；两个可见表面只相差渲染精度则是 Z-fighting。
- 墙附着的阳台、雨棚应从父墙外表面开始计算悬挑深度，不能以墙中心线作为外边界，否则组件会有一半嵌入墙体。
- 水平檐口与阳台/雨棚发生交叉时，按路径切向区间和墙法向实体区间求交，只裁剪重叠路径段；不得按组件 ID、建筑名称或整圈檐口删除。
- 修复后必须验证：悬挑组件不进入墙体、非冲突标高的檐口保留、分段路径仍可编译并映射回原组件。

### 结构骨架越界

- 骨架输出出现 `roof`、`door`、`window`、`balcony` 等后续组件，应在 skeleton 预检阶段拒绝或剥离，并保留诊断。
- 材质可以提前完整定义供后续节点引用；“材质存在”不等于“组件已生成”。

### 世界坐标误用为局部坐标

- 门窗 `from[2]` 通常应为 0 或小的局部法向偏移；明显写入世界 X/Z 时投影回父墙局部坐标。
- 同类规则适用于附着墙的阳台、雨棚和檐口路径，但每种组件需使用自己的协议字段。

## 规则升级标准

只有当规则满足以下条件时才进入代码：

1. 能从 Blueprint 或重建报告确定输入，不依赖某张截图的像素。
2. 对至少两种不同尺寸/屋顶类型成立，或明确限定适用类型。
3. 修复结果可再次被同一校验器验证。
4. 有参数化回归测试；固定建筑文件只作为一个 fixture，不把其 ID 写入逻辑。
5. 不改变批准方案的意图，不用静默几何补丁掩盖上游协议错误。
