## 1. 适用范围

转换建筑类型、立面/屋盖等构件体系、跨构件 recipe 或含大量组件描述的原始资料时使用本规则。目标是让 RAG 能回答“这种建筑由什么组成、按什么关系生成”，而不只是给出一个名称和最少几何列表。

## 2. 来源声明清单

写目标文档前，逐实体记录所有非重复声明：

| 类别 | 需要捕获的内容 |
|---|---|
| `identity` | 一句话定义、关键视觉特征、区分相邻类型的身份组件 |
| `program_space` | 核心功能空间、分区、流线、核心筒、中庭、站台、看台等 |
| `massing` | 层数、层高、长宽高、开间、体量组织、屋顶轮廓 |
| `structure` | 墙/柱/梁/板/屋盖体系及主次关系 |
| `envelope` | 外墙、幕墙、屋面、层间板、内外皮关系 |
| `opening` | 门、窗、洞口、幕墙单元及宿主关系 |
| `circulation` | 楼梯、坡道、连廊、扶梯近似、交通核心 |
| `auxiliary` | 雨棚、阳台、栏杆、凸窗、檐口、烟囱、灯具、设备平台等 |
| `assembly` | 生成顺序、依附对象、对齐、搭接、留缝、碰撞与承托关系 |
| `repetition` | 标准层、模数、阵列、楼层复用、立面节奏 |
| `material` | 材质角色和组合；无效的旧材质字段与材质语义分开记录 |
| `parameter` | 来源给出的范围、比例和条件；工程规范值保留 authority 边界 |
| `unsupported` | 未支持对象、当前降级方式和不得声称的能力 |
| `example` | JSON、表格、公式或案例及其验证状态 |

每条声明使用以下 disposition：

| disposition | 含义 |
|---|---|
| `preserved` | 原意与事实均可保留，写入当前目标实体 |
| `normalized` | 语义保留，字段、枚举、坐标或术语按当前规范改写 |
| `routed` | 不适合当前文件，但写入明确的 component/recipe/详细建筑目标 |
| `downgraded` | 当前引擎无原生能力，保留语义并写出受支持近似 |
| `deferred_conflict` | 来源冲突或证据不足，进入待确认块，不用于正式生成 |
| `rejected` | 精确重复、不可恢复的错误或无关内容；必须记录理由 |

允许内容被压缩，不允许事实类别消失。摘要后的声明必须仍能追踪到目标标题或明确处置原因。

## 3. 实现错误与领域知识分离

按声明粒度判断，不按整段或整份文档判死刑：

- JSON 使用未知字段：拒绝或规范化该字段，不删除同段的空间和组件关系。
- JSON 引用缺失宿主：示例标为错误；“门应依附墙体”之类正确语义仍保留。
- 来源使用未注册业务类型：保留业务名，映射到受支持元素/组件或标为 proposed。
- 参数属于结构、防火或专业规范：保留为 `domain_reference`，不得升级为引擎已验证事实。
- 一个示例同时含正确和错误片段：拆开验证；不要因为局部错误丢弃整类建筑配方。

例：来源写“单元式玻璃幕墙 + 竖梃 + 横挺”，即使不存在 `curtain_wall`/`mullion` 原生类型，也应保留幕墙作为外围护和身份特征，并映射为 `wall + window` 或 `primitive` 组合，而不是只留下“普通墙和窗”。

## 4. 默认完整构成合同

详细建筑实体必须有一个 `topic: composition` 的原子块。推荐格式：

```md
### `<建筑类型>` 默认完整构成合同

- 识别特征：<来源中的关键视觉身份；不得只写抽象风格词>
- 空间与体量：<核心空间、体量、层数/层高/模数；来源未提供则写“来源未提供”>
- 主体骨架：<required elements 及角色>
- 外围护：<required/characteristic elements 及角色>
- 开口组件：<required/characteristic/conditional components 与宿主>
- 交通组件：<required/conditional stair/ramp 等及连接关系>
- 附属组件：<characteristic/conditional/optional 组件及触发条件>
- 重复与模数：<标准层、阵列和复用规则>
- 组装与依附：<构建顺序、parent 引用、标高/边界关系>
- 降级映射：<原始业务对象 → 当前受支持表达；不得直接删除>
```

需要机器更稳定地理解时，增加构件表：

| 系统角色 | 来源构件 | WILD 映射 | 优先级 | 触发条件 | 省略后果 |
|---|---|---|---|---|---|
| 主体骨架 | 核心筒 | `wall` | required | 始终 | 高层失去稳定的空间/结构中心 |
| 外围护 | 玻璃幕墙 | `wall + window` | characteristic | 玻璃办公塔楼 | 立面退化为普通方盒子 |
| 入口 | 通高门厅雨棚 | `door + canopy` | characteristic | 主入口立面 | 入口识别度下降 |
| 无障碍 | 坡道 | `ramp` | conditional | 存在入口高差 | 交通不完整 |

优先级解释：

- `required`：默认必须生成；只有用户明确排除或确定性能力阻止时才可降级，并报告原因。
- `characteristic`：决定类型辨识度；普通/精密生成默认保留，失败回退可简化但必须记录。
- `conditional`：仅在明确条件成立时生成；条件本身进入知识块。
- `optional`：允许基于 seed、风格或性能预算变化。

不得将所有来源构件一律设为 required。结构骨架、身份组件和条件设备的职责不同。

## 5. 最少可行回退

`topic: fallback` 与默认完整构成分开。回退块必须说明：

- 触发条件：低复杂度模式、上下文不足、性能预算或前序确定性失败；
- 保留项：至少保留 required 和一个最关键的 characteristic 系统；
- 可简化项：明确列出，不使用“其余省略”；
- 禁止退化：不能把幕墙塔楼、体育场、航站楼等全部回退为同一普通方盒子；
- 恢复路径：后续详细模式应补回哪些系统。

catalog 中的“最小构件集合”只用于召回入口和 fallback，不是默认生成配方。

## 6. 多实体长文转换

当来源同时包含多个建筑类型：

1. 先按建筑类型建立声明清单，不先写总摘要。
2. 每个建筑类型保留一个默认完整构成合同和一个独立 fallback。
3. 共用构件体系路由到 component；共用跨构件关系路由到 recipe。
4. 建筑实体仍保留该体系的角色、优先级和链接关键词，不能只写“详见其他文档”。
5. 无效 JSON 单独进入示例修复流程，不阻塞其他语义入库。
6. 文档过长时按用途或稳定业务族拆文件，不按字符数随机截断。

不要把每个建筑压缩成一段“视觉特征 + 最小表达”。这种摘要适合 catalog，不足以驱动详细蓝图生成。

## 7. 覆盖验收

交付前逐实体确认：

- 来源中的 identity、空间、骨架、围护、组件、关系、重复和降级信息均有 disposition；
- `preserved/normalized` 内容可在目标标题中定位；
- `routed` 内容有具体目标文件和实体，不是笼统的“另存”；
- `downgraded` 同时保留原业务语义与当前 WILD 映射；
- `deferred_conflict/rejected` 有原因且不会进入正式生成上下文；
- 默认完整构成不是最小回退的同义改写；
- 单独召回 composition chunk 时，模型无需自行猜测主要构件系统；
- 无来源的类别明确缺失，不因模板存在而被补写。
