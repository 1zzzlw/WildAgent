# 尚未实现的跨构件硬规则

本文记录规则缺口，防止把设计建议误写成活动知识后宣称系统已经保证。它不参与 RAG。

## 当前已经有执行点的规则

| 规则 | 执行位置 |
|---|---|
| WILD 字段、枚举和材质结构有效 | `app/utils/blueprint_parser.py` 的 Schema 校验 |
| `materialClass: glass` 必须有正 transmission，opacity 为 1 或省略 | `app/utils/blueprint_parser.py` |
| 门窗、洞口的父墙存在且尺寸落入宿主范围 | `validate_reference_integrity`、`validate_opening_coords`、`validate_opening_fit` |
| 楼梯端点落在相应标高的楼板区域，相邻梯段在平台衔接 | `collect_stair_placement_issues`、`validate_stair_alignment` |
| 墙角、屋顶覆盖、重复骨架和碰撞满足现有几何检查 | `validate_wall_junctions`、`validate_roof_coverage`、`validate_model_quality`、`validate_collision` |

这些规则可以进入活动 capability/relation 文档，因为文档解释的事实有代码负责执行。

## 缺口一：楼梯穿越楼板处保留洞口

当前楼梯校验只验证端点和平台支承。`floor` 只能直接表达矩形或圆形区域，可以用多块矩形楼板围出空域，但流水线不会计算楼梯净空包围体，也不会检查上层楼板是否覆盖梯段。

完成条件：定义楼梯穿越楼板的几何判定；明确平台应保留的支承区和梯段应清空的穿越区；加入失败诊断及确定性修复或拒绝；用直跑、多跑、错层和无楼梯样例验证。完成前，活动知识只能如实说明这一能力边界，不能把“必须留洞”写成已执行保证。

## 缺口二：房间可达性与内隔墙门

“所有内隔墙必须有门”并非普遍规则，因为储物隔断、设备封闭、非房间分隔不一定需要通行。真正需要的是：每个要求使用的空间应通过入口、门和交通空间形成有效可达路径。

当前 `DesignDocument` 没有房间拓扑、邻接边和必达空间集合，Blueprint 也没有可供 validator 使用的房间语义图。因此系统只能校验已有门的宿主和几何，不能判断哪面内隔墙缺门。

完成条件：在设计契约中增加稳定空间 ID、用途、边界和 `required_access`；解析墙体分隔与门连接形成图；从主入口做可达性校验；区分无需通行的封闭空间；同步前端类型、SVG 标注和回归。完成前不建立“内隔墙门”RAG 硬规则。

## 缺口三：菱花窗等复杂窗格

当前 `window` 只有 `verticalMullions` 与 `horizontalMullions`，不能用一个字段表达斜向菱格或任意花纹。直接在知识文档中给一组世界坐标 `primitive` 只会形成不可复用的局部案例，并且无法自动适配父墙方向、窗宽和窗高。

完成条件：先定义参数化窗格组件或受控 `muntinPattern` 契约；编译器根据窗口局部坐标生成杆件；验证杆件落在窗洞内且不产生重影；再把“菱花窗”映射到该组件，并给出只包含单窗与必要宿主的最小 JSON。实现前只能报告不支持或经用户接受后做显式近似。

## 不进入硬规则的内容

幕墙写字楼的地基类型、结构选型、典型玻璃尺寸、设备系统、成本比例和节能数据，需要项目地点、规模、规范版本与可靠来源。它们属于设计输入、工程计算或外部参考，不能因本地模型生成了一段完整说明就直接成为 WILD 生成门禁。
