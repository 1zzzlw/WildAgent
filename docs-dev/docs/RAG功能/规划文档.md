# WildAgent RAG 功能规划文档

> 规划时间：2026-07-29  
> 目标：完成 WildAgent 后端 Agent 的 RAG 检索增强，向量索引数据库使用 Chroma。  
> 适用范围：`wild-server` 后端 Agent 服务、规范文档加载层、知识库索引、Agent Prompt 注入链路。

## 1. 背景

当前 WildAgent 的 Agent 生成链路已经具备：

- FastAPI + WebSocket 对话入口。
- `AgentService.query_structured()` 统一处理生成、修改、聊天三类意图。
- `FileSpecLoader` 从文件系统读取规范文档。
- `build_system_prompt(spec_text)` 将规范注入 System Prompt。
- 18 个空间工具和服务端确定性校验 / 自动修正流水线。
- `storage/knowledge_base/` 已存放蓝图规范和建筑类型参考文档。

但当前规范注入方式仍是固定文件读取：

```python
self.spec_loader = FileSpecLoader([BLUEPRINT-SPEC-MINIMAL.md])
spec_text = self.spec_loader.load()
system_prompt = build_system_prompt(spec_text)
```

这会带来两个问题：

1. 只注入精简规范，Agent 无法充分利用完整规范和建筑类型参考。
2. 如果直接全量注入完整文档，会挤占上下文，影响小模型生成质量和响应稳定性。

因此需要引入 RAG：用 Chroma 对知识库文档建立向量索引，根据用户请求检索最相关片段，再注入本次 Agent 调用。

## 2. 目标

本阶段目标是实现一个可落地、可验证、可扩展的 RAG MVP。

核心目标：

- 使用 Chroma 作为本地持久化向量索引数据库。
- 索引 `wild-server/storage/knowledge_base/` 下的 Markdown 规范文档。
- 新增真实可用的 `RAGSpecLoader`，保持 `SpecLoader.load()` 调用边界基本稳定。
- `AgentService` 根据用户消息动态检索相关规范片段。
- Prompt 注入从“固定精简文档”升级为“固定基础规范 + RAG 相关片段”。
- 不修改 WebSocket 协议，不修改前端协议，不修改 `wild-core`。

非目标：

- 不做多用户权限。
- 不做用户知识库上传 API。
- 不做在线知识库编辑 UI。
- 不做复杂 rerank。
- 不做 LangGraph 重构。
- 不做截图视觉校验。
- 不改变 `.wild` / ScenePatch 协议。

## 3. 当前项目事实

### 3.1 当前代码入口

后端核心文件：

```text
wild-server/app/services/agent_service.py
wild-server/app/spec/loader.py
wild-server/app/agent/prompts.py
wild-server/app/agent/model_client.py
wild-server/config.py
wild-server/storage/knowledge_base/
```

当前 `loader.py` 只有 `SpecLoader` 和 `FileSpecLoader`，`RAGSpecLoader` 还只是注释中的升级方向。

当前 `AgentService` 在初始化阶段创建固定 Agent：

```text
AgentService.__init__()
  -> FileSpecLoader.load()
  -> build_system_prompt(spec_text)
  -> create_agent(...)
```

这意味着 system prompt 目前是启动时固定的，无法按用户请求动态检索不同规范片段。

### 3.2 当前知识库文档

已有知识库：

```text
wild-server/storage/knowledge_base/
├── BLUEPRINT-SPEC-MINIMAL.md
├── BLUEPRINT-SPEC-FULL.md
└── building_types/catalog/
```

建议用途：

- `BLUEPRINT-SPEC-MINIMAL.md`：始终注入，作为 AI 生成的基础铁律。
- `BLUEPRINT-SPEC-FULL.md`：进入 Chroma 检索，用于补充具体构件、坐标、材质、最佳实践。
- `building_types/catalog/`：进入 Chroma 检索，用于“别墅、凉亭、小屋、庭院、塔楼”等模糊建筑类型的默认参考。

说明：`BLUEPRINT-SPECIFICATION.md` 曾是完整规范的历史副本，当前内容与 `BLUEPRINT-SPEC-FULL.md` 完全一致。为避免重复 embedding、重复索引和维护分叉，后端知识库只保留 `BLUEPRINT-SPEC-FULL.md` 作为唯一完整规范。

## 4. 总体设计

### 4.1 目标数据流

```text
用户消息
  -> AgentService.query_structured(message, current_blueprint)
  -> 构造 rag_query
  -> RAGSpecLoader.load(query=rag_query)
       -> Chroma query
       -> 返回相关规范片段
  -> build_system_prompt(spec_text)
  -> create_agent(model, tools, system_prompt)
  -> LLM 生成 Blueprint / ScenePatch / 文本
  -> run_validation_pipeline()
  -> ws_agent.py 原样返回结果
```

### 4.2 Prompt 注入策略

每次 Agent 调用的规范上下文由两部分组成：

```text
固定基础规范
  + RAG 检索片段
```

固定基础规范：

- 使用 `BLUEPRINT-SPEC-MINIMAL.md`。
- 保证顶层结构、10 种构件必填字段、opening 坐标、材质格式等铁律永远在上下文中。

RAG 检索片段：

- 从完整规范和建筑类型参考中按 query 召回。
- 默认取 `top_k = 6`。
- 每个片段保留 source、heading、chunk_index，便于日志和调试。

### 4.3 为什么需要动态创建 Agent

当前 LangChain `create_agent(..., system_prompt=...)` 的 system prompt 是创建时确定的。

RAG 的结果依赖用户消息，例如：

- “生成一个中式凉亭”应召回 `building_types/catalog/pavilions.md` 或更深的凉亭相关片段。
- “门窗位置不对”应召回 opening 坐标和 `parentWall` 规则。
- “屋顶覆盖墙体”应召回 roof span / depth / position 规则。

因此不能继续在 `AgentService.__init__()` 中只创建一个固定 system prompt 的 Agent。建议改为：

- `__init__()` 只创建 `llm`、`tools`、`spec_loader`。
- `query_structured()` 内部每次调用 `spec_loader.load(query=rag_query)`。
- 根据本次检索结果构造 system prompt。
- 用本次 system prompt 创建 Agent 并执行。

这个调整只发生在 `AgentService` 内部，不改变 `query_structured()` 对外接口和 `ws_agent.py`。

## 5. Chroma 设计

### 5.1 依赖

需要在 `wild-server/pyproject.toml` 增加：

```toml
"chromadb>=1.1.0",
"openai>=2.0.0"
```

说明：

- Chroma 负责本地向量索引和查询。
- `openai` 显式声明，供 OpenAI Compatible Embedding API 使用；不要只依赖 `langchain-openai` 的传递依赖。

### 5.2 持久化目录

建议目录：

```text
wild-server/storage/chroma/
```

需要加入 gitignore：

```text
wild-server/storage/chroma/
```

原因：

- Chroma 索引是运行时产物，不应提交。
- Docker Compose 已经挂载 `./wild-server/storage:/app/storage`，容器环境可自然持久化。

### 5.3 Collection

建议默认 collection：

```text
wild_knowledge_base
```

metadata 建议：

```json
{
  "project": "WildAgent",
  "namespace": "wild_spec",
  "version": "1"
}
```

每条 chunk metadata：

```json
{
  "namespace": "wild_spec",
  "source": "BLUEPRINT-SPEC-FULL.md",
  "heading": "2.2.3 开口 (Opening) - 门窗",
  "chunk_index": 12,
  "content_hash": "...",
  "mtime": 1780000000.0
}
```

### 5.4 Embedding

优先使用项目已有 `config.embedding`：

```text
EMBEDDING__NAME
EMBEDDING__API_KEY
EMBEDDING__BASE_URL
```

推荐实现一个 OpenAI Compatible Embedding Function：

```text
OpenAICompatibleEmbeddingFunction
  -> openai.OpenAI(api_key=..., base_url=...)
  -> client.embeddings.create(model=..., input=texts)
```

原因：

- 项目已经使用 OpenAI Compatible Chat 模型配置。
- 不锁定 OpenAI 官方，可接入千问、DeepSeek、GLM 或其他兼容服务。
- 比依赖 Chroma 默认本地 ONNX 模型更可控，避免首次启动下载模型。

可选兜底：

- 如果没有配置 `EMBEDDING__API_KEY`，允许回退到简单本地 hash embedding，仅用于本地 smoke test。
- 生产环境应明确配置真实 embedding 模型，否则检索质量不可保证。

## 6. 分片策略

Markdown 分片建议按标题优先：

1. 按 `#` / `##` / `###` 标题拆成语义 section。
2. 保留当前 heading path。
3. section 超过 `chunk_size` 时再按段落切分。
4. chunk 之间使用 `chunk_overlap` 保留上下文。

默认参数：

```text
chunk_size = 900
chunk_overlap = 150
top_k = 6
```

不同文档的建议：

- `building_types/catalog/`：每个轻量建筑类型文件适合作为默认入口 chunk，深度配方继续放入用途分类目录。
- `BLUEPRINT-SPEC-FULL.md`：按构件类型、坐标系统、最佳实践拆分。
- `BLUEPRINT-SPEC-MINIMAL.md`：不建议只依赖检索，应该始终注入。

## 7. 模块改动计划

### 7.1 `config.py`

新增 RAG 配置：

```python
class RAGConfig(BaseModel):
    enabled: bool = True
    persist_dir: str = "storage/chroma"
    collection_name: str = "wild_knowledge_base"
    chunk_size: int = 900
    chunk_overlap: int = 150
    top_k: int = 6
    allow_hash_fallback: bool = True
```

并在 `Settings` 中增加：

```python
rag: RAGConfig = Field(default_factory=RAGConfig)
```

### 7.2 `app/spec/loader.py`

保留 `SpecLoader` 和 `FileSpecLoader`，新增：

```text
RAGSpecLoader
MarkdownChunker
OpenAICompatibleEmbeddingFunction
HashEmbeddingFunction
```

主要职责：

- 读取知识库 Markdown 文件。
- 分片。
- 初始化 Chroma `PersistentClient`。
- 创建或获取 collection。
- 重建 / upsert 索引。
- `load(query)` 返回固定基础规范 + 检索片段。
- `list_sources()` 返回参与索引和固定注入的文档列表。

建议保持接口：

```python
def load(self, query: str = "") -> str:
    ...
```

`FileSpecLoader.load()` 也同步兼容 `query` 参数，但忽略它，避免调用方关心 loader 类型。

### 7.3 `app/services/agent_service.py`

调整点：

- import `RAGSpecLoader`。
- `SPEC_PATHS` 扩展为基础文档和 RAG 文档。
- `__init__()` 不再固定创建带静态 prompt 的 Agent。
- 将 tools 列表保存到 `self.tools`。
- 新增 `_build_agent(message, current_blueprint)` 或 `_load_spec_context(...)`。
- `query_structured()` 每次根据用户消息和场景摘要检索规范，再创建 Agent。

建议 rag_query：

```text
用户请求
+ 当前场景构件类型列表
+ 当前选中构件类型 / ID
```

首版可只用：

```python
rag_query = message
```

后续再增强。

### 7.4 可选脚本

可以新增：

```text
wild-server/app/rag/build_index.py
```

用途：

- 手动预构建 Chroma 索引。
- 本地检查文档分片数量。
- 打印查询结果。

但 MVP 可先让 `RAGSpecLoader` 在服务启动或首次查询时自动建索引，避免多一个维护入口。

### 7.5 用户知识库导入预留

当前阶段不实现上传功能，但索引层需要给后续扩展留出 metadata 规范，避免未来用户文档和系统规范混在一起：

```json
{

  "doc_scope": "system",
  "doc_type": "blueprint_spec",
  "source": "pavilions.md",

```

后续用户上传文档时：

- `doc_scope` 改为 `user`。
- 文件建议保存到 `wild-server/storage/knowledge_base/user/`。
- 覆盖更新时按 `_source` 删除旧分片，再 upsert 新分片。
- 删除知识文档时同时删除源文件和对应 Chroma 分片。
- 前端只通过新增知识库 API 访问，不改现有 Agent WebSocket 协议。

## 8. 分阶段任务

### Phase R1：RAG Loader MVP

目标：后端可以用 Chroma 建索引并检索知识库。

任务：

- 增加 `chromadb` 和 `openai` 依赖。
- 增加 `RAGConfig`。
- 实现 Markdown 分片。
- 实现 Chroma persistent collection。
- 实现 embedding function。
- 实现 `RAGSpecLoader.load(query)`。
- 本地 smoke test：对“中式凉亭”“opening 坐标”“屋顶覆盖”能召回相关片段。

验收：

- `RAGSpecLoader.load("中式凉亭")` 返回基础规范 + 凉亭相关片段。
- `RAGSpecLoader.load("opening 坐标")` 返回基础规范 + opening 坐标规则。
- Chroma 索引文件写入 `storage/chroma/`。

### Phase R2：AgentService 接入

目标：Agent 真实使用 RAG 上下文。

任务：

- `AgentService` 改为每次 query 动态加载 spec_text。
- 本次检索片段进入 `build_system_prompt(spec_text)`。
- 保留现有 `query_structured()` 返回结构。
- 保留现有校验流水线。
- 日志输出本次 RAG query、命中文档 source / heading / distance。

验收：

- `ws_agent.py` 无需改协议。
- `AgentService.query_structured("生成一个中式凉亭")` 会触发 RAG 检索。
- 生成或修改结果仍走原校验流水线。

### Phase R3：质量增强

目标：让 RAG 检索质量更稳定。

任务：

- rag_query 加入当前场景摘要和选中构件信息。
- 支持文档变更后自动重建索引。
- 支持 top_k、chunk_size、chunk_overlap 环境变量配置。
- 增加检索片段去重和长度上限。
- 增加 query rewrite 或关键词补充，例如“门窗”补充 `opening parentWall from[0]`。

验收：

- 修改门窗、屋顶、楼梯、建筑类型时召回片段明显不同。
- prompt 长度不会随知识库增长失控。

### Phase R4：用户知识库导入扩展（预留）

目标：允许用户手动上传项目相关知识文档，让 Agent 能检索用户补充的建模经验、构件规范、风格参考和项目约束。

任务：

- 新增 `app/api/knowledge.py`。
- 支持 `POST /api/knowledge/upload` 上传 `.md` / `.txt`。
- 保存到 `storage/knowledge_base/user/`。
- 上传完成后自动分片、embedding、upsert 到 Chroma。
- 支持 `GET /api/knowledge/documents` 查看已导入文档。
- 支持 `DELETE /api/knowledge/documents/{document_id}` 删除文件和索引。
- 支持手动 `POST /api/knowledge/reindex` 重建用户知识库索引。
- 前端新增知识库管理面板：上传、列表、删除、重建。

验收：

- 上传一份用户文档后，相关 query 能召回 `doc_scope=user` 的片段。
- 覆盖同名文档不会产生重复分片。
- 删除文档后，检索结果不再出现该文档内容。
- Agent WebSocket 协议不变。

安全边界：

- 首批只支持文本类文档 `.md` / `.txt`。
- 限制单文件大小。
- 文件名必须规范化，禁止路径穿越。
- 用户文档和系统规范必须通过 metadata 区分。

## 10. 风险和处理

### 10.1 Embedding 配置缺失

风险：

- 没有配置 `EMBEDDING__API_KEY` 或 `EMBEDDING__BASE_URL` 时，远程 embedding 不可用。

处理：

- 本地开发允许 hash fallback，保证代码可 smoke test。
- 生产环境必须配置真实 embedding 模型。
- 日志明确提示当前使用的是 fallback 还是真实 embedding。

### 10.2 Chroma 版本 API 变化

风险：

- Chroma 近版本对 embedding function 协议和 collection 配置有变动。

处理：

- 使用官方 Python API：`PersistentClient`、`get_or_create_collection`、`upsert`、`query`。
- 自定义 embedding function 实现 `__call__`、`name()`、`build_from_config()`、`get_config()`。
- 版本先锁定在 `chromadb>=1.1.0`，后续按实际安装结果调整。

### 10.3 动态创建 Agent 带来额外开销

风险：

- 每次 query 都 `create_agent`，可能有少量开销。

处理：

- MVP 优先保证正确性。
- 后续可以按 `spec_text hash` 缓存 Agent。
- 或改为固定 system prompt + user message 注入 RAG 片段，但这会弱化规范约束，暂不优先。

### 10.4 检索片段过长

风险：

- 检索过多会重新挤占上下文。

处理：

- 控制 `top_k`。
- 控制 chunk size。
- 对最终 spec_text 设长度上限。
- 固定基础规范只保留精简版。

### 10.5 用户上传文档质量不可控

风险：

- 用户文档可能格式混乱、内容过长、和系统规范冲突，导致检索片段干扰 Agent。

处理：

- 用户文档单独标记 `doc_scope=user`。
- 后续可按 query 决定是否混入用户文档，或降低用户文档权重。
- UI 上提示用户上传的是“补充知识”，不是覆盖系统规范。
- 必要时引入 rerank 或规则过滤，优先保留系统规范中的硬性格式要求。

## 11. 成功标准

RAG 功能完成后，应满足：

1. 项目依赖中包含 Chroma。
2. `RAGSpecLoader` 可以读取知识库 Markdown，建立 Chroma 持久化索引。
3. `RAGSpecLoader.load(query)` 能返回基础规范和 query 相关片段。
4. `AgentService.query_structured()` 会使用本次 query 的 RAG 结果组装 Prompt。
5. WebSocket 协议和前端调用方式不变。
6. 生成 / 修改结果仍然经过现有校验流水线。
7. 本地至少有 smoke test 证明 Chroma 索引和检索可用。
8. `storage/chroma/` 不进入 Git。
9. 后续用户知识库导入有明确 metadata 和 API 扩展路线。

## 12. 推荐落地顺序

建议下一步按这个顺序实现：

1. 修改 `config.py`，加入 `RAGConfig`。
2. 修改 `pyproject.toml`，加入 `chromadb` / `openai`。
