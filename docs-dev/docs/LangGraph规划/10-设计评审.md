# LangGraph 设计评审

> 日期：2026-08-05
> 评审范围：`wild-server/app/agent/graph.py`、`graph_state.py`、`component_registry.py`、全部 nodes、prompts、ws_agent.py
> 文档版本：基于 2026-08-03 设计文档 + 当前实际代码

---

## 一、总体评价

**架构方向正确，实现中存在若干中等问题需要修复。**

核心思路——**骨架→Send动态派发→gen→val链并行→合并→校验→回调重试**——是正确的工程决策，有效解决了原单体Agent的四大瓶颈（上下文竞争、类型编造、整体重来、调试黑洞）。

设计亮点：
- 注册表驱动（`COMPONENT_REGISTRY`）使新增组件只需配置，符合开闭原则
- 工厂模式（`create_component_generator`/`create_component_validator`）消除了重复代码
- gen→val 两段式设计：gen 调 LLM，val 调工具，职责清晰
- 骨架驱动的动态 Send 派发：未被建议的组件零成本跳过
- 双模式并存（LangGraph 精密 + LangChain 快速）的务实降级策略

## 二、逐维度评估

### 2.1 架构设计：良好（4/5）

**优点：**

| 决策 | 说明 |
|------|------|
| 注册表驱动 | `ComponentConfig` + `get_implemented_components()`，[graph.py](wild-server/app/agent/graph.py) 和 [merge_node.py](wild-server/app/agent/nodes/merge_node.py) 无需为新组件修改 |
| 工厂模式 | `create_component_generator(config)` 和 `create_component_validator(config)` 用闭包生成节点函数 |
| 分层清晰 | Layer 0（骨架）→ Layer 1（并行组件）→ Layer 2（合并+校验）→ Layer 4（回调），每层职责单一 |
| 动态派发 | LangGraph `Send` API 按需派发组件节点，未被骨架建议的组件不消耗 LLM 调用 |
| 并发控制 | `asyncio.Semaphore(3)` 限制 LLM 并发，防止 API 429 |

**问题：**

1. **`on_reasoning_delta` 回调放入 State（[graph_state.py:21](wild-server/app/agent/graph_state.py#L21)）**
   - `Callable[[str, str], Awaitable[None]]` 不可序列化，破坏 LangGraph checkpointing 能力
   - 未来如需中断恢复，此设计成为障碍
   - **建议**：改用 `contextvars` 或外部注册表传递

2. **State 字段冗余**
   - 11 种组件 × 3 个字段（`{ct}_fragments` + `{ct}_gen_diag` + `{ct}_val_diag`）= 33 个静态字段
   - 每次新增组件都需修改 `graph_state.py`
   - **建议**：用 `dict[str, list[dict]]` 映射替代

3. **`_COMPONENT_KEYWORDS` 重复定义**
   - [graph.py:29-41](wild-server/app/agent/graph.py#L29-L41) 和 `ComponentConfig.need_keywords` 各自维护关键词映射
   - 两边不一致的风险
   - **建议**：统一到 ComponentConfig，graph 层从注册表读取

### 2.2 节点划分：良好（4/5）

**优点：**

- gen→val 分离符合单一职责，gen 调 LLM、val 调工具
- 骨架节点只生成 walls/floors/columns/beams，不越界
- 合并节点纯数据操作，不做修复
- 校验节点复用现有 15 步流水线

**问题：**

1. **val 节点使用字符串匹配判断错误（[base_component_node.py:307](wild-server/app/agent/nodes/base_component_node.py#L307)）**
   - `"❌" in validation_result` — 如果校验输出中任何字段值包含 ❌ 字符就会误判
   - **建议**：改为结构化返回（如 `(bool, str)` 或 dataclass）

2. **`Send(gen_name, state)` 传递完整 State 到每个组件节点（[graph.py:74](wild-server/app/agent/graph.py#L74)）**
   - 组件节点只需要骨架数据 + 自己的 RAG 上下文
   - 虽然 LangGraph 做浅拷贝，但仍是反模式
   - **建议**：构建最小化 state 子集传递

3. **骨架节点的 `_components:` 正则过于简单（[skeleton_node.py:215](wild-server/app/agent/nodes/skeleton_node.py#L215)）**
   - `r'_components:\s*(.+)'` 可能误匹配 LLM 回复中其他位置的类似文本
   - **建议**：加锚点约束，如只在 JSON 代码块之前匹配

### 2.3 状态管理：需要改进（3/5）

**优点：**

- `total=False` 的 TypedDict 避免样板代码
- 诊断字段设计完善（每个节点记录 RAG字数、LLM字数、耗时、token用量、thinking内容）
- `retry_count` + `max_retries` 控制重试

**问题：**

1. **无 Reducer 定义**
   - LangGraph Send 模式下，并行节点各自返回 state 更新，默认合并策略是覆盖
   - 如果两个节点意外写入同一字段，后者静默覆盖前者（目前恰好不会发生，因为各节点写不同字段）
   - **建议**：为关键字段显式定义 reducer

2. **回调节点的 `_apply_fixes_to_state` 遍历全部 11 种组件（[callback_node.py:156](wild-server/app/agent/nodes/callback_node.py#L156)）**
   - 对每种组件都执行 `state.get(cfg.output_key)` 然后重新赋值
   - 未修改的组件也被原样写回 state
   - **建议**：只更新真正有变更的组件字段

3. **`status` 字段生命周期混乱**
   - skeleton 失败设 `"failed"`，merge 失败也设 `"failed"`，validate 设 `"complete"/"partial"/"failed"`
   - `_dispatch_components` 用 `state.get("status") == "failed"` 判断 — 语义不够清晰
   - **建议**：增加 `phase` 字段区分错误来源

### 2.4 错误处理：需要改进（3/5）

**优点：**

- 多层 fallback：骨架失败 → 短路；无建议 → 关键词匹配 → 合并空结果
- gen 节点 JSON 提取失败有优雅降级（空列表 + 诊断错误）
- LLM_SEMAPHORE 防止并发爆炸

**问题：**

1. **关键词 fallback 有误判风险（[graph.py:44-53](wild-server/app/agent/graph.py#L44-L53)）**
   - "不要门" 会匹配到 "门" 关键词，触发不必要的 door 生成
   - `ComponentConfig.skip_keywords` 存在但未被 `_keyword_fallback` 使用
   - **建议**：`_keyword_fallback` 从 ComponentConfig 读取 `skip_keywords` 并检查

2. **`_trace_errors_to_components` 用字符串包含判断（[validate_node.py:109](wild-server/app/agent/nodes/validate_node.py#L109)）**
   - `if comp_id and comp_id in output` — ID 为 "door" 时会匹配任何包含 "door" 的文本
   - 不是真正追溯而是启发式匹配
   - **建议**：校验工具返回结构化错误（含 component_id），替代字符串匹配

3. **validate_node 异常处理丢失细节（[validate_node.py:75-79](wild-server/app/agent/nodes/validate_node.py#L75-L79)）**
   - 只返回 `"校验流水线执行失败"`，堆栈信息丢失
   - **建议**：用 `logger.exception` 记录完整堆栈

4. **缺少全局错误边界**
   - 如果图执行中间节点抛出未捕获异常，astream 中断
   - [ws_agent.py:496-501](wild-server/app/api/ws_agent.py#L496-L501) 有外层 try/except，但只能发送错误消息无法恢复

### 2.5 回调与重试机制：设计好，实现有差距（2/5）

这是**设计文档中最核心的创新点**，但实现与设计之间存在明显差距：

| 设计文档承诺 | 实际实现 | 差距严重度 |
|-------------|---------|-----------|
| `ComponentFixRequest` 含 `current_params`、`tool_data`、`suggestion` | callback_node 只从 `failed_components` 取 `error_message` | 🔴 高 |
| 回调时跑 tools + RAG 组合 | 只做了 RAG，没跑 tools | 🔴 高 |
| 每个失败组件独立重试 ≥3 次 | 全局 `retry_count`，所有失败组件一起修正 | 🟡 中 |
| 重试耗尽后降级（移除/简化/标记） | 无降级逻辑，默默返回 `"partial"` | 🟡 中 |
| 回调 prompt 含 `suggestion`、`current_params` | `build_callback_prompt` 只有 `error_message`，`current_params` 始终为 `{}` | 🔴 高 |

**根因分析**：

`_trace_errors_to_components`（[validate_node.py:93-128](wild-server/app/agent/nodes/validate_node.py#L93-L128)）返回的 `failed_components` 从不包含 `current_params` 和 `suggestion` 字段。`

当前 callback prompt 实际发给 LLM 的内容：
```
### door_front (door)
- 错误: [15步校验流水线某步骤的超长文本输出的前200字符]
- 当前参数: {}   ← 永远是空字典
```

LLM 拿到的是校验步骤的文本输出（如 `"Step 4: 检查 opening 坐标... wall_front 上有错误..."`），不是结构化的字段级错误信息。**LLM 基本在"盲修"。**

**这导致设计文档预测的 ~80% 修正成功率在实际中大幅降低。**

## 三、其他发现

### 3.1 死代码

- **`nodes/door_node.py` ~ `chimney_node.py`（11 个文件）**：import 不存在的 `create_component_node`，graph 从不使用它们，但文件仍在磁盘上

### 3.2 空文档

- `docs/LangGraph规划/09-流式思考实施.md` — 空文件
- `docs/LangGraph规划/09-质量优化方案.md` — 空文件

### 3.3 `need_keywords`/`skip_keywords` 未被运行时使用

ComponentConfig 中的 `need_keywords` 和 `skip_keywords` 字段在组件选择阶段未被 graph 使用——组件选择由骨架 `_components:` 行驱动。关键词 fallback 用的是 [graph.py](wild-server/app/agent/graph.py) 中独立维护的 `_COMPONENT_KEYWORDS` 字典。

### 3.4 ws_agent.py 重复 metrics 发送

[session_metrics 被发送两次](wild-server/app/api/ws_agent.py#L551-L608)：第一次从 `final_state` 取 `retry_count` 正确值，第二次用硬编码 `retry_count: 0` 覆盖。第二个发送会覆盖前端的展示。

### 3.5 文档漂移

`IMPLEMENTATION_SUMMARY.md` 描述的 `_should_skip` 函数和 `_suggest_components` 逻辑已被 `_components:` 解析 + Send 派发取代，但文档未更新。

## 五、总结

| 维度 | 评分 | 关键发现 |
|------|------|---------|
| 架构设计 | ★★★★☆ | 骨架→Send派发→gen→val→合并→校验→回调 是正确的方向 |
| 节点划分 | ★★★★☆ | gen/val 分离好，工厂模式消除重复 |
| 状态管理 | ★★★☆☆ | Callable 序列化问题、字段冗余、无 reducer |
| 错误处理 | ★★★☆☆ | Fallback 链完善，但关键词匹配粗糙、追溯逻辑脆弱 |
| 回调重试 | ★★☆☆☆ | 设计文档的创新点在实现中被严重削弱 |
| 可观测性 | ★★★★☆ | 诊断字段完善，前端展示成熟 |

**核心结论**：LangGraph 的架构骨架是正确的，注册表驱动 + Send 动态派发的设计具有良好扩展性。但**回调重试机制——设计文档中最强调的创新——在实现中打了大折扣**：LLM 拿不到精确的当前参数和工具建议数据，基本等同于盲目重试。建议优先修复回调信息传递链路，再逐步解决状态管理和错误追溯问题。
