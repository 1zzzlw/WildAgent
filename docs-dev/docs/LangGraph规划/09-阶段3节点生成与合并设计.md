# Phase 3：节点生成 + 合并 + 严格校验设计

> 目标：让 LangGraph 以“分节点生成建筑组件，再合并校验”的方式工作，减少全量生成失败回退的风险。

## 1. 设计核心

1. 第一个节点 `understand_request` 负责解析用户输入，并调用知识库中的:
   - `building_types/catalog/`
   - `building_types/`
   - `components/`

   目的是：
   - 丰富用户描述语言
   - 确定建筑类型
   - 抽离出可能需要的组件列表，例如门、窗、屋顶、栏杆等

2. LangGraph 生成的本质是“组件子图”，不是“一次性生成完整 Blueprint”。
   每个组件节点只关心自己的知识与输出，不负责其他组件。

3. 组件节点后的校验节点负责局部验证。校验失败时带上结构化错误信息，重新进入同一组件节点或单独修正节点，直到通过或达到重试上限。

4. 所有组件节点完成后，将各节点内存中生成的数据合并到 `merge` 节点，汇总成完整 Blueprint。

5. 合并后的 Blueprint 进入更严格的全局校验节点。该节点也支持多次重试，并将错误信息返回到需要修正的节点。

6. 现有的自动修复代码保留为 LangChain 模式的 fallback，LangGraph 主流程优先使用节点级递归重试，而不是依赖旧的修复函数。

## 2. 建议的节点结构

```text
[user_input]
      │
      ▼
[understand_request]
      │
      ▼
[plan_component_nodes]
      │
      ▼
  ┌──────────┬──────────┬──────────┐
  │          │          │          │
  ▼          ▼          ▼          ▼
[door]    [window]   [roof]   [railing] ...
  │          │          │          │
  ▼          ▼          ▼          ▼
[validate] [validate] [validate] [validate]
  │          │          │          │
  └──────────┴──────────┴──────────┘
             ▼
         [merge_fragments]
             ▼
      [validate_merged_blueprint]
             │
      ┌──────┴──────┐
      │             │
   pass          fail + retry
      │             │
      ▼             ▼
 [final_result]  [feedback_to_failed_nodes]
```

## 3. 组件节点设计

### 3.1 组件节点只处理自己的职责

每个组件节点应满足以下原则：

- 只读 `state` 中全局骨架和当前组件所需上下文
- 只写自己负责的 fragment 数据
- 只检索自己的知识库片段
- 只返回本组件的结构化校验结果

例如 `door` 节点应从 `components/` 中检索门的规范，生成门片段，并返回：

- `door_fragments`
- `door_diagnostics`
- `door_status`

### 3.2 组件知识库路径

- `building_types/catalog/`：用于识别建筑类型与高层组件需求
- `building_types/`：用于补全类型规则、风格、尺寸等
- `components/`：用于获取组件本体的 schema、坐标规则、依赖关系

组件节点只需关心自己这部分知识，不需要把全部建筑语义拉入单次上下文。

### 3.3 校验节点与重试

每个组件节点后面应跟一个校验节点：

- 校验通过：节点结果进入 `merge_fragments`
- 校验失败：生成结构化错误信息，返回当前组件节点重新生成或修正

校验失败信息应包含：

- 具体 failed component id
- 失败的字段与当前值
- 空间约束 / 参考范围
- 已通过组件清单
- 组件父对象引用信息

这种结构化回调比文本化 `fix_*` 更可靠。

## 4. 合并节点与全局校验

### 4.1 合并节点职责

`merge_fragments` 节点负责：

- 从所有组件节点读取 fragment 数据
- 在内存中将 fragment 合并成完整 Blueprint
- 检查 ID 冲突、引用完整性、组件层级关系
- 产生 `merged_blueprint`

这一节点不要做深度修复，只做合并与一致性检查。

### 4.2 全局校验节点职责

合并后的 Blueprint 进入更严格的全局校验节点：

- `validate_merged_blueprint`
- 比组件校验更严格，覆盖跨组件关系和整体空间约束
- 失败时将错误信息返回到责任组件节点或合适的修正路径
- 允许多次重试（建议 `max_retries=3`）

重复重试逻辑应由 LangGraph 状态图本身控制，而不是依赖单体 `fix_*` 函数。

## 5. 与现有自动修复代码的关系

- `wild-server` 现有的自动修复代码仍然保留，不需要删除。
- 但 LangGraph 主流程应优先走“节点级校验 + 回调重试”策略。
- 旧修复代码可作为 LangChain / fallback 路径，在 LangGraph 尚未稳定时保留。
- 一旦 LangGraph 递归循环功能稳定，可将自动修复函数标记为“legacy fallback”，只在回退模式下调用。

## 6. 变更建议

### 6.1 新增

- 新文档：`docs/LangGraph规划/09-阶段3节点生成与合并设计.md`
- 新节点：`plan_component_nodes`
- 新节点：`merge_fragments`
- 新节点：`validate_merged_blueprint`
- 新节点：组件级 `validate` 节点

### 6.2 删除或弱化

- 将“LangGraph 自动修复”表述弱化为“legacy fallback”
- 将“全量存在式生成后再修复”的设计替换为“分片生成后合并再严格校验”

### 6.3 优化

- 让每个组件节点只依赖局部知识，不带入整个建筑上下文
- 把组件校验结果从文本变成结构化错误信息
- 让 `merge_fragments` 只做合并与一致性检查，不做深度修复
- 让全局校验重试逻辑由 LangGraph 节点循环控制

## 7. 关键原则

- 组件优先：`door`、`window`、`roof` 等组件节点只关注自身输出
- 内存优先：组件数据保存在 LangGraph State，合并后再生成完整 Blueprint
- 结构化错误：回调带错误字段、父引用、建议范围，而非自由文本
- 非破坏性：已通过的组件不应在重试中被随意重写
- 递归收敛：失败后重试不等于无限重试，最多 `3` 次，超过后显式报告人工介入
