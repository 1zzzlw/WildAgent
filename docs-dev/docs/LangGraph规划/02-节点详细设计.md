# LangGraph 节点详细设计（基于实际 wild-compiler 与 RAG 实现）

> 每个节点的输入/输出、RAG 策略、工具调用、Prompt 片段、错误处理
> 更新：2026-08-03，基于 `wild-compiler/componentRegistry.ts`（10个注册编译器）与 `RAGSpecLoader.load_many()`

---

## 一、节点设计规范

每个节点遵循统一接口：

```python
async def node_xxx(state: GenerationState) -> dict:
    """
    输入: state（只读需要的字段）
    输出: 部分 state 更新（只写自己负责的字段）
    不修改: 其他节点的输出字段
    
    fragments 格式对齐 wild-compiler 的 ComponentSpec：
    - door/window/canopy/balcony/bay_window: 需要 parentWall
    - railing/cornice: 需要 path（至少2个点）
    - ramp: 需要 from/to
    - chimney/light: 需要 position
    """
    return {
        "door_fragments": [...],   # geometry.components 格式
        "door_diagnostics": [...], # 诊断信息
    }
```

**关键规则**：
- 节点之间**只通过 state 通信**，不直接引用其他节点的局部变量
- fragments 在内存（State）中传递，可选写调试文件
- 每个节点的 RAG 查询带上 `metadata_filter={entity_type: "xxx"}`，避免召回无关 chunk
- 失败时返回空列表 + diagnostic，不抛异常（不阻塞其他并行节点）

## 二、Layer 0: 骨架生成节点

### skeleton_generator

| 属性 | 值 |
|---|---|
| 依赖 | 无（第一个节点） |
| 并行 | 否（顺序） |
| RAG filter | `doc_type=building_type`, `doc_type=recipe`, `entity_type=structural_component`, `entity_type=wall` |
| Tools | `get_wall_bounding_box` |
| 输出 | `skeleton_blueprint`, `skeleton_summary`, `wall_bounding_box` |

**执行流程**：

```
1. RAG 检索: retrieve_many([
     SpecQuery(user_message, {doc_type: "building_type"}),
     SpecQuery(user_message, {doc_type: "recipe"}),
     SpecQuery(user_message, {entity_type: "structural_component"}),
     SpecQuery(user_message, {entity_type: "wall"}),
   ], per_query=2)
   → 不和其他组件竞争 top_k，建筑类型、结构规则各拿 2 个 chunk

2. System Prompt = 骨架专用片段:
   """
   你是建筑骨架生成专家。只生成 walls、floors、columns、beams。
   不要生成门、窗、屋顶或任何组合构件。
   规则:
   - 墙体转角处共享端点坐标
   - floor 覆盖整个建筑底面
   - 输出完整的 Blueprint JSON（geometry.components 为空数组）
   """

3. LLM 生成 → 提取 Blueprint JSON

4. 校验: validate_blueprint_schema + normalize_blueprint_input
   → 通过 → 写入 state.skeleton_blueprint
   → 失败 → 重试 1 次（如果有 building_type 就再精确一次）
         → 仍失败 → state.error = "骨架生成失败"

5. 工具调用: get_wall_bounding_box(skeleton_blueprint)
   → 写入 state.wall_bounding_box = {
        "x_min": 0, "x_max": 6,
        "z_min": 0, "z_max": 5,
        "wall_top": 3.0,
        "walls": [
          {"id": "wall_front", "from": [0,0,0], "to": [6,3,0], "length": 6.0},
          {"id": "wall_left",  "from": [0,0,0], "to": [0,3,5], "length": 5.0},
          ...
        ]
     }

6. 生成 skeleton_summary:
   "可用墙体: wall_front(0→6m, 顶高3m), wall_back(0→6m, 顶高3m),
    wall_left(0→5m, 顶高3m), wall_right(0→5m, 顶高3m)
    可用楼板: floor_ground(6×5m)"
```

## 三、Layer 1: 并行组件节点

### 3.1 通用模板（以 doors 为例）

| 属性 | 值 |
|---|---|
| 依赖 | `skeleton_blueprint`, `skeleton_summary`, `wall_bounding_box` |
| 并行 | 与 windows、roof、furniture 等同时执行 |
| RAG filter | `entity_type=door` |
| Tools | 可选调用 `validate_element_required_fields`（生成后自检） |
| 输出 | `door_fragments`, `door_diagnostics` |
| 实际代码参考 | `wild-web/src/wild-compiler/components/door.ts` - 当前编译器实现 |

**执行流程**：

```
1. RAG 检索: retrieve_many([
     SpecQuery(user_message, {entity_type: "door"}),
   ], per_query=2)
   → 精确过滤 entity_type，只召回门相关 chunk
   → 不与窗户、屋顶片段竞争 top_k

2. System Prompt = 门专用片段:
   """
   你是门组件生成专家。只生成 door 组合构件。
   已知场景骨架:
     {skeleton_summary}
     {wall_bounding_box}

   参考实现: wild-compiler 将 door 编译为:
     - 1 个 opening (墙体洞口)
     - 3 个 primitive.box (门框左/右/上)
     - 1 个 primitive.box (门板)

   规则:
   - door 写入 geometry.components，不是 geometry.elements
   - type 固定为 "door"
   - 必填字段: id, parentWall, from, width, height, interaction
   - from[0]=沿墙距离(0~墙长-门宽), from[1]=底部世界Y, from[2]=法向偏移(通常0)
   - parentWall 必须是骨架中真实存在的 wall id（从上面列出的墙体中选择）
   - interaction 必填: {"mode":"swing","hingeSide":"left"|"right","openAngle":90}
   - 门宽建议 0.9~1.2m, 门高建议 2.0~2.4m
   - 可选字段: frameMaterial, leafMaterial, glassPanel

   只输出你生成的门 components 数组，不要重复骨架内容:
   [
     {"type":"door","id":"door_front","parentWall":"wall_front","from":[4.4,0,0],...},
     {"type":"door","id":"door_back","parentWall":"wall_back","from":[4.4,0,0],...}
   ]
   """

3. LLM 生成 → 提取门 fragments 数组

4. 每个 fragment 快速自检（可选，节省后续校验时间）:
   - parentWall 是否存在于 skeleton 的 wall 列表中?
   - from[0] + width ≤ wall_length?
   - interaction 是否包含必填字段?
   → 不通过 → 记录 diagnostic，保留但标记为 "需回调修正"
   → 通过 → 追加到 door_fragments

5. 返回 state 更新:
   {
     "door_fragments": [...],
     "door_diagnostics": [...]
   }
```

### 3.2 各节点差异表（基于实际wild-compiler注册表）

**实际代码位置**: `wild-web/src/wild-compiler/componentRegistry.ts:48-97`

当前已注册的10种组合构件编译器：

| 节点 | entity_type | 编译为 | 特殊规则 | 代码位置 |
|---|---|---|---|---|
| `door_generator` | `door` | opening + primitive.box×3 | parentWall必须存在，interaction必填 | `components/door.ts` |
| `window_generator` | `window` | opening + primitive.box×N | parentWall必须存在，verticalMullions/horizontalMullions 0~32 | `components/window.ts` |
| `roof_generator` | `roof` | geometry.elements | **不是组件**，直接写入elements，roofType 6个值 | N/A（原生类型） |
| `railing_generator` | `railing` | primitive.cylinder×N + beam×M | path至少2点，可指定parentFloor | `components/railing.ts` |
| `canopy_generator` | `canopy` | primitive.box板 + cylinder支柱 | parentWall必须存在，depth/thickness必填 | `components/canopy.ts` |
| `balcony_generator` | `balcony` | 悬挑板 + 嵌套railing | slabThickness必填，内嵌调用railing编译器 | `components/balcony.ts` |
| `ramp_generator` | `ramp` | primitive.box梁体 + 可选railing | from/to必须有高度差，width/thickness必填 | `components/ramp.ts` |
| `bay_window_generator` | `bay_window` | opening + 窗框 + 投影窗体 | projectionDepth必填，parentWall必须存在 | `components/bayWindow.ts` |
| `cornice_generator` | `cornice` | primitive.profile_sweep | path至少2点，profile必填（截面点数组） | `components/cornice.ts` |
| `chimney_generator` | `chimney` | primitive.cylinder薄壁 + 压顶 | position/width/depth/height必填 | `components/chimney.ts` |
| `light_generator` | `light` | primitive.sphere灯泡 + 行为 | initiallyOn必填，附带behaviors.interactive | `components/light.ts` |

**注意**：
- `furniture` 不使用编译器模式，仍作为原生`geometry.elements`类型（`app/tools/spatial_tools.py:1068` subtype校验）
- `roof` 也不使用编译器，直接作为`geometry.elements`的原生类型
- 组件编译后会自动删除`geometry.components`字段（`wild-compiler/index.ts:104`）

### 3.3 并行执行

```python
# LangGraph 中 fan-out 的实现
import asyncio

async def layer1_parallel(state: GenerationState) -> dict:
    """Layer 1: 所有组件节点并行执行。"""
    results = await asyncio.gather(
        door_generator(state),
        window_generator(state),
        roof_generator(state),
        railing_generator(state),
        furniture_generator(state),
        light_generator(state),
        # 不需要的节点返回空列表
        return_exceptions=True,  # 单个节点失败不影响其他
    )
    # 合并结果...
```

**注意**：不是所有节点每次都执行。如果用户说"生成一个只有墙和门的车库"，window/roof/furniture 节点应该识别出"不需要我"并跳过（返回空列表）。

## 四、Layer 2: 合并与校验节点

### 4.1 merge_fragments

```
输入: skeleton_blueprint + 所有 fragments
输出: merged_blueprint

合并逻辑:
1. 深拷贝 skeleton_blueprint
2. 遍历每个组件的 fragments:
   - ID 冲突检测: door_front 是否已存在? → 自动加后缀 _1
   - parentWall 引用检测: parentWall 是否在 skeleton 的 wall 列表中?
     → 不存在 → 记录 diagnostic，跳过该 fragment
   - 追加到 geometry.components
3. 返回 merged_blueprint
```

### 4.2 validate_and_fix

```
输入: merged_blueprint
输出: validation_results, failed_components, passed_components

直接复用现有的 run_validation_pipeline(merged_blueprint)
→ 15 步校验 + 自动修正
→ 按校验器分组去重（_final_errors）
→ 分类:
   - passed: 无 error 的组件
   - failed: 每个 error 追溯到具体组件 ID
     {
       "component_id": "door_front",
       "component_type": "door",
       "step": 4,
       "check": "validate_opening_coords",
       "error": "from[0]=5.8, 父墙长6m, 门宽1.2m → 右边缘超出",
       "suggestion": "建议 from[0] 改为 ≤4.8"
     }
```

### 4.3 callback_retry（回调重试节点）

这是 LangGraph 中最关键的节点。详细设计见 `03-回调与重试机制.md`。

```
while failed_components 非空 and retry_count < max_retries:
    1. 对每个 failed_component:
       - 精确 RAG: retrieve(f"{component_type} {error_message}")
       - 工具查询: 获取详细的空间数据
       - 组装 callback_payload

    2. LLM 修正:
       - 只输出该组件的修正版本（不是整个 Blueprint）
       - Prompt: "你上次生成的 {component_id} 有错误: {error}。请修正。"

    3. 重新校验修正后的组件

    4. retry_count += 1
```

## 五、Layer 3: 精修节点（后续迭代）

层次低优先级，设计预留。包括：

- `environment_generator`: 地形高度场、环境光、时间
- `detail_generator`: 外部装饰（石狮、影壁、花坛）
- `landscape_generator`: 植被占位、路径

**这些节点的失败不阻塞主流程。**
