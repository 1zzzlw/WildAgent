# 组合构件编译器设计文档

> 版本：2026-08-03
> 范围：`wild-web/src/wild-compiler/` 模块的架构设计、数据流与注册机制。

---

## 一、问题背景

WildAgent 渲染引擎（wild-core）支持 11 种基础几何类型：`wall`、`floor`、`column`、`beam`、`roof`、`opening`、`stair`、`furniture`、`dense_brick`、`body`、`primitive`。每种类型都需要在引擎内部注册一个 builder，由 builder 负责生成实际的三角网格。

问题在于：**建筑领域有大量"复合概念"——门、窗、栏杆、雨棚、阳台、坡道、凸窗、檐口、烟囱、灯具——它们不是单一的基础几何体，而是多个基础元素的组合。**

如果每增加一种复合概念就要在渲染引擎中注册一个新 builder：

- 引擎 `registry.ts` 会不断膨胀；
- 每个新 builder 需要写完整的几何生成代码（数百行）；
- 复合概念之间无法复用（阳台含栏杆，栏杆又要单独实现一遍）；
- LLM 生成时容易混淆 "geometry.elements 的 type" 和 "组合构件的 type"。

## 二、解决方案：编译器模式

**核心思想：组合构件在进入渲染引擎之前，由一个独立的"编译器"展开为基础元素。引擎完全不知道"门"的存在，它只看到 `opening` + `primitive.box`。**

```
Blueprint（含 components）
  │
  ├─ geometry.elements  ← 引擎直接处理（wall, floor, roof, ...）
  │
  └─ geometry.components ← 编译器处理
       │
       ├─ door      → opening + primitive.box×3
       ├─ window    → opening + primitive.box×N
       ├─ railing   → primitive.cylinder×N + beam×M
       ├─ light     → primitive.sphere + primitive.cylinder
       └─ ...
              │
              ▼
         合并到 geometry.elements
              │
              ▼
         wild-core 渲染引擎（无感知）
```

### 核心优势

| 维度 | 无编译器 | 有编译器 |
|---|---|---|
| 新增一个复合概念 | 修改引擎 registry + 写 builder（数百行几何代码） | 写一个 compiler 函数（~50-100 行，组合已有 element） |
| 引擎复杂度 | 随组件类型线性增长 | 保持 11 种 builder 不变 |
| 组件间复用 | 无法复用（阳台不能调用栏杆 builder） | 天然支持（balcony 内部调用 railing 编译逻辑） |
| Blueprint 可编辑性 | 展开后丢失语义（不知道这些 box 是"门"） | 保留语义 + ID 双向映射 |
| LLM 生成 | 容易把组件 type 写入 elements | 明确的 components 入口，类型隔离 |
| 错误隔离 | 一个 builder 崩溃影响全局 | 单个组件编译失败不影响其他组件 |

## 三、模块结构

```
wild-web/src/wild-compiler/
├── index.ts                  # 主入口：compileBlueprintComponents()
├── types.ts                  # 类型定义：编译器接口、上下文、结果、映射
├── componentRegistry.ts      # 组件编译器注册表（10 个内置编译器）
├── componentCache.ts         # LRU 编译缓存（最多 256 条）
├── components/
│   ├── door.ts               # 门 → opening + 3 段门框
│   ├── window.ts             # 窗 → opening + 窗框 + 窗棂
│   ├── railing.ts            # 栏杆 → 立柱 + 横杆
│   ├── canopy.ts             # 雨棚 → 板 + 支柱
│   ├── balcony.ts            # 阳台 → 悬挑板 + 栏杆
│   ├── ramp.ts               # 坡道 → 矩形体 + 栏杆
│   ├── bayWindow.ts          # 凸窗 → 墙洞 + 窗框 + 投影体
│   ├── cornice.ts            # 檐口 → profile_sweep
│   ├── chimney.ts            # 烟囱 → 薄壁筒体 + 压顶
│   └── light.ts              # 灯具 → 灯泡 + 底座 + 光源行为
└── (shared helpers)
    ├── attachedToWall.ts     # 墙体依附：坐标框架、方向、创建 box
    ├── attachedToPath.ts     # 路径依附：采样、偏移
    └── attachedToSurface.ts  # 表面依附：楼板/屋顶高度对齐
```

## 四、编译流程

```
compileBlueprintComponents(source: Blueprint)
│
├─ 1. 深拷贝 source（源 Blueprint 永不修改）
│
├─ 2. 遍历每个 component：
│   │
│   ├─ 校验：id 非空、不重复、不与原生 elements 冲突
│   ├─ 查 registry：getComponentCompiler(component.type)
│   ├─ 如果未注册 → 诊断错误，继续下一个组件
│   │
│   ├─ 查缓存 → 命中则直接返回
│   └─ 调用 compile(component, context) → GeometryElement[]
│       │
│       ├─ 校验：生成的 element.id 不冲突
│       ├─ draggable 标记传递（_draggable）
│       └─ 追加到 elements 数组
│
├─ 3. 记录 ID 双向映射
│   ├─ generatedElementIdsByComponentId: { door_1 → [door_1__opening, door_1__frame_left, ...] }
│   └─ componentIdByGeneratedElementId: { door_1__opening → door_1, ... }
│
├─ 4. delete blueprint.geometry.components（编译后不再需要）
│
└─ 5. 返回 { blueprint, diagnostics, mapping }
```

## 五、在渲染管线中的位置

```

      ▼

      │

      │

  ├─ expandTemplates  （模板实例展开 — 不同的机制）

      │
      ▼

```

## 六、编译器接口

每个组件编译器的签名：

```typescript
type ComponentCompiler<T> = (
  component: T,                      // 组件参数（含 type, id, 及各字段）
  context: ComponentCompileContext,  // 只读的场景 elements（用于查父构件）
) => GeometryElement[]               // 返回基础元素数组
```

- **纯函数**：不修改输入，不产生副作用。
- **context**：只读访问场景中已有的 elements（如 `parentWall` 引用的墙体），用于计算位置和方向。
- **错误处理**：抛出 `ComponentCompileError` 时，上层会捕获并转为诊断，不影响其他组件。

## 七、ID 双向映射与编辑器集成

编译器记录的映射用于前端编辑：

```typescript
interface ComponentCompilationMapping {
  // 组件 → 生成的元素列表
  generatedElementIdsByComponentId: Record<string, string[]>
  // 生成的元素 → 所属组件
  componentIdByGeneratedElementId: Record<string, string>
}
```

**用途**：

- **视口拾取**：用户点击门面上的一个 box → `componentIdByGeneratedElementId` 找到它属于 `front_door` → 高亮整个门组件。
- **组件拖动**：用户拖动门 → `generatedElementIdsByComponentId` 找到所有子元素 → 整体移动。
- **属性面板**：选中组件后显示组件级参数（width/height/material），而非展开后的 box 参数。

## 八、编译缓存

```typescript
// LRU 缓存，最多 256 条
compileComponentCached(component, context, compileFn)
```

**缓存键** = 组件稳定序列化 + 显式引用的父构件快照：
- `parentWall` 引用 → 缓存键包含该墙的 from/to
- `parentFloor` / `parentRoof` 引用 → 缓存键包含对应构件
- roof 无显式 position 时 → 缓存键额外包含所有 wall（自动推算位置依赖）

场景未变化时重复编译命中缓存，避免每帧重新计算。

## 九、注册新组件

三步即可注册一个新的组合构件：

### 1. 定义类型（`wild-core/types.ts`）

```typescript
export interface SpiralStairComponent {
  type: 'spiral_stair'
  id: string
  center: Vec3
  radius: number
  height: number
  turns: number
  width: number
  material?: string
}
```

### 2. 加入联合类型

```typescript
export type ComponentSpec = (
  | DoorComponent
  | WindowComponent
  // ... 现有类型
  | SpiralStairComponent   // ← 新增
) & { draggable?: boolean }
```

### 3. 写编译器（`wild-compiler/components/spiralStair.ts`）

```typescript
export function compileSpiralStair(
  component: SpiralStairComponent,
  context: ComponentCompileContext,
): GeometryElement[] {
  // 用 primitive.cylinder + primitive.box 组合出旋转楼梯
  // ...
  return elements
}
```

### 4. 注册

```typescript
// componentRegistry.ts
registerComponentCompiler({
  type: 'spiral_stair',
  description: '将旋转楼梯编译为分段踏步和中心柱',
  compile: (component, context) =>
    compileSpiralStair(component as Extract<ComponentSpec, { type: 'spiral_stair' }>, context),
})
```

**引擎零改动。** `registry.ts` 和所有 geometry builder 保持不变。

## 十、当前限制与未来方向

### 当前限制

- **只能组合已有基础元素**：如果需要的几何形态无法用现有的 11 种基础元素表达（如 NURBS 曲面、程序化地形），仍需要扩展引擎 builder。
- **无碰撞/物理编译**：编译器只生成几何，不处理物理碰撞体。
- **无自动 LOD**：展开后的元素数量可能较多（如栏杆 2000 根立柱），编译器本身不做 LOD 优化。
- **编译缓存有上限**：256 条 LRU，大规模场景可能需要调整。

### 适合编译器模式的组件特征

| 适合 | 不适合 |
|---|---|
| 多个简单几何体的确定性组装 | 需要全新几何算法的形态 |
| 参数化变体多（不同尺寸的门窗） | 需要物理模拟的形态 |
| 需要编辑器保持高级语义 | 纯视觉效果（用 shader 更高效） |
| 建筑构件的标准化组装 | 自由形态雕塑/有机体 |

### 未来的编译器增强方向

- **组件嵌套**：编译器内调用其他编译器（balcony 已实现内嵌 railing）。
- **编译时参数验证**：在编译阶段就检查参数合法性，而不是等到 builder 阶段报错。
- **增量编译**：只重新编译参数变化的组件。
- **编译器单元测试**：目前无测试覆盖，后续应补上。

## 十一、与知识库/RAG 的关系

编译器注册表中的 10 种组件类型，就是 LLM 在 `geometry.components` 中可以使用的全部类型。知识库文档的职责是：

1. 告知 LLM 哪些 type 属于 `geometry.components`（而非 `geometry.elements`）；
2. 告知 LLM 每种组件的必填字段和合法参数；
3. 禁止 LLM 把组件 type 写入 `geometry.elements`（如 `type: "door"` 在 elements 中是无效的）。

编译器 + 知识库 + Schema 校验构成了三层防线：

```
LLM 生成
  → 知识库（Prompt 层面告知正确类型和字段）
  → Schema 校验（JSON Schema 格式校验）
  → 编译器（未注册的 type → 诊断错误，不崩溃）
  → 引擎 builder（非法 type → ELEMENT_BUILD_FAILED）
```
