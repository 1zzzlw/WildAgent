# LangGraph 模式 RAG 与生成质量深度分析

> 分析对象：
> - `D:/Backup/Downloads/AI 生成 - 现代简约别墅.wild` —— AI 生成的最终蓝图
> - `D:/Backup/桌面/骨架.txt` —— 骨架+门+窗+屋顶+合并节点的完整思考文本
> - `wild-server/storage/knowledge_base/**/*.md` —— RAG 知识库全文
> - `wild-server/app/spec/loader.py` + `app/agent/nodes/skeleton_node.py` + `app/agent/prompts.py` —— RAG 调用逻辑

---

## 一、核心结论

**RAG 知识库本身是好的，但 LangGraph 架构把它的"完整答案"撕成了碎片，导致 LLM 只能拿到最机械的"3 个开口/墙"启发式，最终 24 个窗户。**

更精确地说：

| 阶段 | 应该发生 | 实际发生 |
|------|----------|----------|
| RAG 检索 | 召回 `villas.md` 的"现代别墅最少可行 Blueprint"作为锚点 | ✅ 召回成功（思考文本明确引用"参考 RAG 片段 1（最少可行版本）"） |
| 骨架节点 | 完整给出 8×6m 双层 + 4 角柱 + **2 个水平长窗（win_left + win_right）+ 1 门 + 平屋顶 + 楼梯** | ❌ 给出 4 角柱 + 4 梁 + 双坡屋顶 + **"建议每面墙 3 个开口"** |
| 门窗节点 | 参照 RAG 最小可行模板（2 窗 + 1 门）补足 | ❌ 窗节点按"每面墙 3 个"生成 24 个；门节点正确生成 2 个 |
| 合并节点 | 校验整体设计一致性，主动删减多余额外构件 | ❌ 合并节点只看坐标/碰撞，没能力判断"窗户太多" |

**LangChain 模式之所以工作，是因为它在单次 LLM 调用中看到了 RAG 的"最少可行 Blueprint"完整 JSON 模板，直接照抄/微调，所以得到了"人样"。**

## 二、RAG 知识库本身写得好不好？

**回答：写得好，但有两处问题导致 LangGraph 模式下无法被有效利用。**

### 2.1 写得好的部分（直接抄来当 LLM 参考完全够用）

- **`building_types/residential/villas.md` §1.1 现代别墅** 给出了一个**完整的 10×8m 现代别墅 Blueprint**，包含 1 个门 + 2 个水平长窗（宽 3m）+ 平屋顶 + 楼梯 + 入口雨棚 + 无障碍坡道。这正是"人样"的来源。
- **`recipes/assembly-templates.md` 低层建筑基线** 给出 `floor → column → wall → opening → stair → roof` 的标准组装顺序，是骨架节点的天然参考。
- **`components/windows.md` §X.3.4 现代窗** 列出了**现代别墅的推荐窗型组合 = 条形窗 + 转角窗 + 落地窗**，与 LangChain 模式的产出高度吻合。
- **`components/windows.md` §X.3.6 窗型速配** 表里明确写了"现代别墅 → 条形窗 + 转角窗 + 落地窗"。

### 2.2 RAG 知识库的两处问题

**问题 1：现代窗条款被标为 `status: proposed`，与 `engine-capability-boundaries.md` 冲突**

`components/windows.md` 整体标 `status: proposed`，因为里面写了 `sashType`、`muntinPattern`、`opening` 等当前引擎**不支持**的字段。但这导致：
- 骨架节点的 RAG 检索可能因为 `metadata_filter={"entity_type":"window","status":"supported"}` 等约束把现代窗内容过滤掉
- 即便召回了，提示词里的"参考规范"也会让 LLM 以为不能用，从而降级到最基础的 `window` 字段

**问题 2：`villas.md` 的最小可行 Blueprint 是 `10×8m`，而 LangGraph 生成的别墅是 `8×6m`**

LLM 无法直接复用 10×8m 的模板，必须自己缩放。但缩放过程中，窗户数量是按"数量约束"还是"绝对数量"传递？从思考文本看，骨架节点给出的"RAG 片段 1 窗×6"是绝对数量，到了窗节点就变成了"每面墙 3 个"的启发式规则。**绝对数量被丢失了。**

## 三、为什么 LangGraph 模式生成的窗户是 24 个而不是 6 个？

这是最关键的问题。骨架节点的思考文本写得清清楚楚：

### 3.1 骨架节点的思考过程（行 4-14）

> ```
> 根据知识库，别墅（Villa）默认生成"2层现代别墅"或"欧式/现代简约别墅"。参考RAG片段1（最少可行版本）：
> * 2层现代别墅
> * 占地 8m × 6m
> * 层高 3m
> * 外墙 ×8（一、二层各4面）
> * 地板 ×2
> * 门 ×1（正面底层中央，宽1.0m，高2.2m）
> * 窗 ×6（一层2个 + 二层4个，宽1.2m，高1.1m）
> * 楼梯 ×1
> * 屋顶 ×1（gable，span 9m，depth 7m，height 2m）
> ```

**RAG 提示窗×6**（与 villas.md §1.1 的 2 个窗不完全一致，但是个温和的解读）。骨架节点本应把这个数字传给窗节点。

### 3.2 但骨架节点实际生成的"建议开口方案"是每面墙 3 个

骨架节点的 `_build_skeleton_summary` 函数（prompts.py / skeleton_node.py）生成了"建议开口方案"段，给出每面墙 3 个 from 位置（如 `wall_front_1 (8m): 3 个开口 (2.0, 4.0, 6.0)`），这些 from 坐标被传给窗节点。

**窗节点拿到这个建议后**，思考文本（行 188-194）是这样写的：

> ```
> 重新阅读规则："每面墙的建议开口方案：[wall_front_1] 长8.0m, 建议 3 个开口，位置约 from[0]=2.0m, 4.0m, 6.0m"
> 如果我必须生成窗，我就在这3个位置生成窗。
> 规则："数量克制：严格按骨架中的建议数量生成，不要过度生成。... 窗：每面墙 1~3 个，根据墙长决定"
> 骨架建议每面墙 3 个开口。我就每面墙生成 3 个窗。
> ```

**LLM 严格执行了骨架节点的"每面墙 3 个"指令，丢掉了 RAG 原始的"窗×6"。** 这就是 24 个窗户的来源。

### 3.3 根本问题：骨架节点的"建议开口方案"是机械启发式，不是 RAG 的真实意图

骨架节点 `_build_skeleton_summary()` 中给出的开口方案：

```python
# 推测的骨架 summary 输出（来自 skeleton_node.py 的 _build_skeleton_summary 函数）
"建议开口方案：\n"
"- [wall_front_1] 长8.0m, 建议 3 个开口，位置约 from[0]=2.0m, 4.0m, 6.0m\n"
"- [wall_back_1] 长8.0m, 建议 3 个开口，位置约 from[0]=2.0m, 4.0m, 6.0m\n"
"- [wall_left_1] 长6.0m, 建议 3 个开口，位置约 from[0]=1.5m, 3.0m, 4.5m\n"
"..."
```

这段代码把"墙长 → 几个开口"映射成纯几何规则（每 2~3m 一个开口），与 RAG 最小可行 Blueprint 的"只有 2 个水平长窗"毫无关系。

**这是骨架节点的提示词设计缺陷：把"建议开口"做成了"机械均布"。**

## 四、其他构件的连锁问题

### 4.1 屋顶：骨架节点照搬 RAG 但没考虑缩放

RAG 最小可行的屋顶是 `span=11, depth=9, height=0.3, position=[5,6,4]`，对应 10×8m 建筑 + flat 类型。LLM 缩放到 8×6m 时，**误用了 `roofType: gable`**（错误）+ `span=9, depth=7`（出檐过大）+ `height=2.5`（过高）。

LLM 的推理（行 388-399）：
> ```
> X方向跨度 span = 8.00 + 出檐（比如每边0.5m，总共9.0m，或者就8.0m，一般加出檐，比如 span=9.0）
> Z方向深度 depth = 6.00 + 出檐（比如每边0.5m，总共7.0m）
> ...
> 屋顶类型：gable（双坡）或 hip（四坡）。选 gable。
> 高度 height：2.5m
> ```

LLM 自己拍脑袋决定加 0.5m 出檐 + 选 gable + 高度 2.5m，没有参照任何 RAG 规则。这反映出骨架节点 prompt 里**没有"屋顶类型由建筑类型决定"的强约束**。

### 4.2 柱子：8 根角柱贯穿 6m（撑穿屋顶）

RAG 最小可行中柱子高度 = 6.0m，但 LLM 没有意识到柱子应该"对应每层高度"，反而全高 6m 撑到屋顶下方。LLM 自己写：
> ```
> 现代别墅主要靠墙承重，但加几个柱子丰富结构。或者不加，保持简洁。
> ```

**说明 LLM 对"是否要柱子"犹豫不决，最终 4 角全加、6m 通高。** 这不是 RAG 问题，是 prompt 没明确告诉 LLM "现代别墅可以不需要外露角柱"。

### 4.3 缺少楼梯

LLM 自己在思考中写了：
> ```
> * 楼梯 ×1（室内，宽1.2m）
> ```

但最终没有生成楼梯。说明骨架节点在 `_components:` 行没有把 `stair` 列出。骨架 prompt（`build_skeleton_prompt` 行 73）只提到 light、cornice，没提楼梯。

### 4.4 后门坐标错误

后门 `parentWall=wall_back_1`（z=6），但 `from=[4.44, 0, 0]`（z=0）—— 应该是 z=6。LLM 把"沿墙距离"和"z 坐标"搞混了。这是**门组件 prompt 没强调"from 第 3 个坐标必须与 parentWall 的平面坐标一致"**。

### 4.5 合并节点全部"通过"

合并节点的输出（行 437-457）：
> ```
> 第1轮校验
> 总步骤: 18, 通过: 16, 警告: 2, 错误: 0
> 状态: 全部通过
> ```

校验流水线只检查：结构闭合、字段必填、引用完整、坐标合法、开洞匹配、墙连接、楼梯对齐、屋顶覆盖、尺寸合理、碰撞。**没有任何一条校验"窗户数量是否合理"**。

20 处 beam 碰撞被检测出来，但属于"警告"级别不阻断合并。所以一份 24 窗 + 无楼梯 + 屋顶撑穿 + 后门错位的蓝图就这么通过了。

## 五、RAG 调用逻辑的 4 个具体缺陷

### 缺陷 1：骨架节点只检索"建筑类型"和"recipe"，没检索"窗户/门的款型"
（`skeleton_node.py` 行 36-42）：
```python
queries = [
    SpecQuery(user_message, {"doc_type": "building_type"}),
    SpecQuery(user_message, {"doc_type": "recipe"}),
    SpecQuery("墙体 楼板 柱子 梁", {"entity_type": "structural_component"}),
]
```
骨架节点完全没把"现代别墅应该用什么窗型（条形窗/转角窗/落地窗）"这个关键信息拉进 prompt。

### 缺陷 2：RAG 的"最小可行 Blueprint"在 prompt 里只是"参考"，没有被强制复用

骨架 prompt 的 `build_skeleton_prompt` 让 LLM "基于建筑类型，补充细节描述"，没有要求 LLM "**严格按照 RAG 最小可行的构件清单**生成"。LLM 看到 RAG 只是参考，可以自由发挥，于是发挥出了 24 窗。

### 缺陷 3：组件节点拿到的 RAG 切片太碎

`base_component_node.py` 的窗生成 RAG 查询（修改后）：
```python
queries = [
    SpecQuery(user_message, {"entity_type": config.entity_type}),  # 只查 window
    SpecQuery("现代别墅 窗户 数量克制", None),                    # 模糊补充
]
```
窗节点根本不知道 RAG 里 "现代别墅应该用 2 个水平长窗" 这个事实 —— 它只看到自己的窗规则 + 骨架给的"每面墙 3 个开口"。

### 缺陷 4：metadata_filter 的 status 字段把"proposed"内容屏蔽了

`villas.md` §1.1 是 `status: supported`，但内部多次提到"现代窗款型见 `components/windows.md`"，而 windows.md 整体 `status: proposed`。如果 RAG 检索有 `where={"status":"supported"}` 之类的过滤，现代窗款式就被屏蔽了。

## 六、修复方案（按影响力排序）

### 方案 A：让骨架节点直接输出"完整 Blueprint"而不是骨架（最有效）

**核心思想**：放弃"骨架 + 后续补全"的拆分。骨架节点直接生成完整的最终 Blueprint（包括门窗屋顶），后续节点只做校验和修复。

**优点**：和 LangChain 模式一样，LLM 一次性看到 RAG 完整模板。
**缺点**：失去了"骨架是上游、组件是下游"的解耦，但本来这解耦就带来了不一致。

### 方案 B：在骨架节点加入"开门面 / 开侧面 / 开背面"的分类（次有效）

骨架节点让 LLM 显式标注每面墙的功能：
```json
{
  "facade_plan": {
    "wall_front_1": "主立面，正门 + 大面积水平长窗 2 个",
    "wall_back_1": "背面，仅 1 个后门 + 1 个小窗",
    "wall_left_1": "侧面，留空",
    "wall_right_1": "侧面，留空",
    "wall_front_2": "二层露台/落地窗",
    "wall_back_2": "二层小窗 1 个",
    "wall_left_2": "侧面，留空",
    "wall_right_2": "侧面，留空"
  }
}
```

然后把这个 plan 传给组件节点，窗节点就知道哪些墙不生成窗。

### 方案 C：让 RAG 直接返回"模板 Blueprint 片段"给组件节点

修改 RAG 的 chunk 切分，确保 `villas.md` §1.1 的最小可行 Blueprint 是一个完整的 chunk。在组件节点的 prompt 里强制要求：

> "现代别墅的窗户总数量参考 RAG 召回的最少可行模板（通常 2~4 个），不要在所有墙面均匀分布。"

### 方案 D：合并节点增加"整体设计一致性"校验

校验"窗户总数 / 楼层数 / 墙体面积"的比例。比如 8×6m 别墅，窗户总数应该 ≤ 6（一层 2 个 + 二层 4 个）。超过则触发 fix 或者告警。

### 方案 E（推荐组合）：A + C + D

骨架节点直接生成完整 Blueprint（方案 A），同时把 RAG 最小可行 Blueprint 作为"参考模板"在 prompt 里强制展示（方案 C），合并节点增加"窗墙比"校验（方案 D）。

## 七、结论：用户判断是对的，RAG 知识库写得好但 LangGraph 没用上

**RAG 知识库本身质量不错**，提供了完整的"现代别墅最少可行 Blueprint"作为锚点。但 LangGraph 架构把这个锚点撕碎分发到不同节点后，每个节点都只能看到自己职责相关的切片，没有任何一个节点能看到完整的 RAG Blueprint 模板。

**解决路径**：放弃 LangGraph 的"骨架规划 → 组件补全"拆分（至少对建筑生成这种强结构化任务），让一个 LLM 调用直接产出完整 Blueprint + RAG 模板。这与 LangChain 模式等价，但保留 LangGraph 的校验/修复/流式思考等周边能力。

## 八、补充观察：思考文本本身暴露了 LLM 的"执行偏差"

骨架节点的思考过程显示 LLM 反复在 RAG 模板、机械规则、自身判断之间切换：

| 行号 | LLM 思考 | 偏差 |
|------|----------|------|
| 4 | 参考 RAG 片段 1（最少可行版本） | ✅ 正确引用 |
| 10 | 窗 ×6（一层2个 + 二层4个） | ✅ 数量对齐 RAG |
| 16 | 现代简约别墅，对称布局，大面积玻璃窗预留 | ✅ 风格正确 |
| 19 | 规则明确说"只生成 walls, floors, columns, beams" | ✅ 遵守职责 |
| 41 | 加4个角柱贯穿两层 | ⚠️ 与"现代别墅主要靠墙承重"自相矛盾 |
| 188 | 骨架建议每面墙 3 个开口。我就每面墙生成 3 个窗 | ❌ 抛弃了"窗×6"的数量约束 |
| 287 | 我用 glass 作为 glassMaterial | ✅ 引用 RAG 材质名 |
| 388 | X方向跨度 = 8.00 + 出檐（比如每边0.5m） | ⚠️ 自己拍脑袋加出檐 |

**核心问题在第 188 行**：LLM 在执行层面被"骨架建议每面墙 3 个"覆盖了"窗×6"的 RAG 数量约束。这说明：
1. RAG 的"绝对数量"信息在 prompt 里权重不够
2. 骨架节点的"机械均布建议"权重太高

修复重点：让 RAG 的"构件清单"成为生成时的强约束，而不是参考。

## 九、修复优先级表

| 优先级 | 方案 | 影响 | 工作量 |
|--------|------|------|--------|
| P0 | 方案 A：骨架节点生成完整 Blueprint | 彻底解决碎片化 | 中（重构一个节点） |
| P0 | 方案 C：RAG 模板 Blueprint 作为强参考注入 prompt | 让 LLM 看到完整模板 | 小（改 prompt） |
| P1 | 方案 D：合并节点增加窗墙比校验 | 兜底防止过度生成 | 小（加一个 validator） |
| P1 | 方案 B：骨架输出 facade_plan | 让窗节点知道哪些墙不开窗 | 中（改 summary 函数 + 节点通信） |
| P2 | RAG chunk 切分优化（villas.md §1.1 作为完整 chunk） | 提升召回质量 | 小 |
| P2 | 消除 metadata_filter status 屏蔽 proposed 内容 | 避免误屏蔽 | 小 |

**推荐先做 P0 的两件事**，可以让 LangGraph 模式立刻接近 LangChain 的产出质量。
