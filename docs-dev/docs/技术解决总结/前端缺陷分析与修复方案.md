# WildAgent 前端缺陷分析与修复方案

> 审计基准：对照 `架构设计方案.md`、`项目进展总结.md`、`agent.md`
> 审计日期：2026-08-06
> 范围：`wild-web/src/` 下核心组件、Store、渲染管线、Agent 通信桥接、UI 交互

---

## 1. 概述

前端主链路（Vue 3 + Pinia + Three.js + wild-core + wild-compiler + WebSocket Agent 通信）**整体已接通**。但存在 8 项设计意图与实现之间的偏差，其中 **3 项为高优先级缺陷**（可能导致完整设计承诺在实际运行中落空），**5 项为中低优先级**（影响健壮性、UX 体验、类型安全）。

### 前端核心数据流（当前实现）

```
用户操作 / Agent 建议
  → createPatch() / 直接 loadBlueprint()
  → sceneStore.applyPatch() / loadBlueprint()
  → Blueprint 更新
  → sceneValidator.validateBlueprint()
  → wildCoreAdapter.reconstructWildEntity()
      → compileBlueprintComponents() [wild-compiler 组件展开]
      → coreReconstructEntity()     [wild-core 几何重建]
  → meshDataToGeometry() + materialAdapter() + renderEntity()
  → CanvasViewport 3D 渲染
```

### 关键文件索引

| 文件 | 功能 |
|---|---|
| `src/stores/sceneStore.ts` | 场景状态、Blueprint、revision、重建触发 |
| `src/wild/scenePatch.ts` | ScenePatch 11 种操作的应用逻辑 |
| `src/wild/sceneValidator.ts` | Blueprint 校验 |
| `src/agent/agentBridge.ts` | WebSocket + HTTP 桥接、消息分发 |
| `src/stores/agentStore.ts` | Agent 会话、消息、思考流状态 |
| `src/renderer/renderEntity.ts` | ReconstructedEntity → Three.js Group 转换 |
| `src/renderer/meshDataToGeometry.ts` | MeshData → BufferGeometry |
| `src/renderer/materialAdapter.ts` | MaterialParams → Three.js 材质 |
| `src/components/panels/AIChatPanel.vue` | AI 对话面板（消息、思考、校验流水线） |
| `src/components/viewport/CanvasViewport.vue` | 3D 视口（含 3D 拾取） |
| `src/wild-compiler/index.ts` | 组合构件编译展开 |

## 2. 缺陷 F1：`remove_element` 不级联清理引用（🔴 高优先级）

### 2.1 问题定位

**文件**: `src/wild/scenePatch.ts:47-49`

```typescript
case 'remove_element':
  blueprint.geometry.elements = blueprint.geometry.elements.filter(e => e.id !== op.id)
  break
```

当前实现仅从元素数组过滤掉被删除的元素本身，**不清理任何引用该元素的其他元素**（如 `opening.parentWall`、`roof.parentWall` 等）。

### 2.2 触发路径与影响

1. Agent 或用户执行"删除一面墙"（该墙上挂有门/窗 opening）
2. `applyOperation('remove_element', { id: wall_id })` 删除墙体
3. `sceneValidator.ts:136-147` 对悬空 `opening.parentWall` 报 `level:'error'`
4. `sceneStore.applyPatch()` 对 `level === 'error'` 直接 `return false` → **整个 Patch 被拒**
5. 既无级联删除，也无"先删子再删父"的编排 → **删墙操作直接失败**

### 2.3 修复方案

在 `remove_element` 分支中增加引用级联清理逻辑：

```typescript
case 'remove_element': {
  // 1. 收集所有引用该元素的子节点
  const idsToRemove = new Set<string>([op.id])
  // 遍历查找所有引用目标 id 的元素（递归）
  let foundNew = true
  while (foundNew) {
    foundNew = false
    for (const el of blueprint.geometry.elements) {
      if (idsToRemove.has(el.id)) continue
      const refs = [el.parentWall, el.constraint?.target, el.openingId]
      if (refs.some(r => r && idsToRemove.has(r))) {
        idsToRemove.add(el.id)
        foundNew = true
      }
    }
  }
  // 2. 过滤掉所有待删除元素（自身 + 级联子节点）
  blueprint.geometry.elements = blueprint.geometry.elements.filter(
    e => !idsToRemove.has(e.id)
  )
  break
}
```

**注意**：级联删除应仅在 `source === 'agent'` 且用户已确认时执行；用户手动操作可改为在删除前弹确认框列出受影响子元素。

## 3. 缺陷 F2：重建失败被静默吞掉，不 Gate 提交（🔴 高优先级）

### 3.1 问题定位

**文件**: `src/stores/sceneStore.ts:107-118`

```typescript
// 应用成功
document.value.blueprint = newBlueprint    // ← 行 107: 先提交 Blueprint
document.value.revision++                  // ← 行 108: 先递增 revision

await reconstruct()                         // ← 行 111: 再重建（但结果不检查！）

useHistoryStore().push({                    // ← 行 112: 无论重建结果，都记录历史
  label: patch.summary || '修改场景',
  before, after: deepClone(newBlueprint),
  patch, timestamp: Date.now(),
})
return true                                 // ← 行 119: 永远返回 true
```

而 `reconstruct()` 内部（`sceneStore.ts:141-158`）：

```typescript
async function reconstruct() {
  if (!document.value?.blueprint) return false
  try {
    // ... Worker 中重建 ...
    reconstructed.value = entity
    return true
  } catch (error) {
    console.error('重建失败', error)
    reconstructed.value = null   // 画布变空
    return false                  // 但调用方不检查！
  }
}
```

### 3.2 影响

即使重建抛异常、画布变空（`reconstructed.value = null`），`applyPatch` 仍然：
- 提交了新的 Blueprint 并 `revision++`
- 推入 undo 历史栈
- 返回 `true`（调用方认为成功）

文档称"重建 smoke test 作为成功门槛"，**实际重建结果并未 Gate 提交**。

### 3.3 修复方案

将 Blueprint 提交放在重建成功之后：

```typescript
async function applyPatch(patch: ScenePatch): Promise<boolean> {
  // ... 前置校验不变 ...

  // 先做重建 smoke test
  let reconstructedEntity: ReconstructedEntity | null = null
  try {
    const compilation = compileBlueprintComponents(newBlueprint as any)
    reconstructedEntity = await coreReconstructEntity(compilation.blueprint)
  } catch (e) {
    console.error('重建 smoke test 失败，拒绝 Patch', e)
    return false
  }

  if (!reconstructedEntity) {
    console.error('重建 smoke test 返回空，拒绝 Patch')
    return false
  }

  // 通过后才提交
  document.value.blueprint = newBlueprint
  document.value.revision++
  document.value.dirty = true
  reconstructed.value = reconstructedEntity

  useHistoryStore().push({ /* ... */ })
  return true
}
```

也可以引入临时状态标记 `reconstructPending`，在 `CanvasViewport` 的 `updateScene()` watch 中处理：接口不变但增加"重建失败则回滚"的 guard。

## 4. 缺陷 F3：顶点溢出占位网格材质泄漏（🟡 中优先级）

### 4.1 问题定位

**文件**: `src/renderer/renderEntity.ts:44-47`

```typescript
const placeholder = new THREE.Mesh(
  new THREE.BoxGeometry(1, 1, 1),
  new THREE.MeshStandardMaterial({ color: 0xff4444, wireframe: true, transparent: true, opacity: 0.6 })
)
placeholder.userData.elementId  = meshData.elementId
placeholder.userData.isError    = true
placeholder.userData.errorReason = 'vertex_overflow'
// ❌ 缺失：placeholder.userData.ownsMaterial = true
```

**清理逻辑** (`renderEntity.ts:453-467`)：

```typescript
if (child instanceof THREE.Mesh) {
  child.geometry.dispose()
  if (child.userData.ownsMaterial) {   // ← 只有 ownsMaterial 才 dispose 材质
    materials.forEach(material => material.dispose())
  }
}
```

### 4.2 影响

顶点超限时创建的 `MeshStandardMaterial` 因缺少 `ownsMaterial = true` 标志，在场景重建清理阶段**永远不会被 dispose**。每次带超限网格的重建都泄漏一个 `MeshStandardMaterial`（含 wireframe 着色器状态）。

### 4.3 修复方案

在占位 mesh 创建处增加一行：

```typescript
placeholder.userData.errorReason = 'vertex_overflow'
placeholder.userData.ownsMaterial = true       // ← 补这一行
```

## 5. 缺陷 F4：组合构件编译失败被降级为 Warning（🟡 中优先级）

### 5.1 问题定位

**文件**: `src/wild/sceneValidator.ts:123-133`

```typescript
const compilation = compileBlueprintComponents(blueprint as any)
// 组件编译的诊断全部降级为 warning
for (const diag of compilation.diagnostics) {
  issues.push({
    level: 'warning',           // ← 原始 diag.level 可能是 'error'，但被强制改为 'warning'
    message: `[组件编译] ${diag.message}`,
    sourceElement: diag.source,
  })
}
```

### 5.2 影响

Agent 推送含非法组件的 Patch → 编译诊断报 `error` → 但被降级为 `warning` → `hasErrors = false` → `applyPatch` 正常提交 → 重建时该组件编译失败、生成元素缺失 → 画布"少一块"无任何错误提示。

### 5.3 修复方案

保留原始诊断级别，让 `error` 级别诊断真正阻断 Patch：

```typescript
for (const diag of compilation.diagnostics) {
  issues.push({
    level: diag.level,          // 保留原始级别
    message: `[组件编译] ${diag.message}`,
    sourceElement: diag.source,
  })
}
```

如果某些组件编译错误是可容忍的（如缺少可选功能但不影响几何），则应在 `compileBlueprintComponents` 内部就已经区分 `error` / `warning`，而非在校验层统一降级。

## 6. 缺陷 F5：Patch 确认/拒绝语义缺失（🟡 中优先级）

### 6.1 问题定位

- `types/scenePatch.ts:31` 定义了 `requires_confirmation: boolean`
- `scenePatch.ts:153` 在 `createPatch` 时赋值该字段
- **但全代码库从未读取** `requires_confirmation`

`AIChatPanel.vue:31-37`：对所有带 `message.patch` 的消息一律显示"应用修改"按钮，不区分是否需要确认。

```
应用修改 ── 唯一操作，无"拒绝"按钮
```

`agentStore.ts:309-315`：

```typescript
function confirmPatch() { pendingPatch.value = null }   // ← 无组件调用
function rejectPatch()  { pendingPatch.value = null }   // ← 无组件调用
```

### 6.2 影响

- 需要用户确认的危险操作（批量删除、场景覆盖）与安全操作（单元素添加）UI 无区别
- `pendingPatch` 是孤儿状态（设置了但从不读取、从不清理）
- 用户无法"拒绝" Agent 的修改建议

### 6.3 修复方案

在 `AIChatPanel.vue` 的 patch 区域增加确认/拒绝双按钮：

```html
<div v-if="message.patch" class="message-patch">
  <div class="patch-summary">{{ message.patch.summary }}</div>
  <div class="patch-actions">
    <el-button size="small" @click="handleApplyPatch(message.patch!)">应用修改</el-button>
    <el-button size="small" @click="handleRejectPatch(message)" 
      v-if="message.patch.requires_confirmation">拒绝</el-button>
  </div>
</div>
```

并在 `handleApplyPatch` / `handleRejectPatch` 中调用 `agentStore.confirmPatch()` / `rejectPatch()`，同时给被拒绝的 patch 消息打上 `rejected` 标记。

## 7. 缺陷 F6：不解析 `agent_reply` 内嵌 JSON（⚪ 低优先级）

### 7.1 问题定位

**文件**: `src/agent/agentBridge.ts:425-428`

```typescript
case 'agent_reply':
  agentStore.addAgentMessage(message.content)
  agentStore.setProcessing(false)
  break
```

当前完整 Blueprint 走 `blueprint_generated`（file_url）→ HTTP GET → `loadBlueprint` 路径，功能正常。但 `agent_reply` 内嵌 ```json Blueprint 并未解析和自动应用。

### 7.2 修复方案（可选增强）

在 `agent_reply` 处理中增加 JSON 块提取逻辑（作为快速响应通道）：

```typescript
case 'agent_reply':
  const jsonMatch = message.content.match(/```json\s*([\s\S]*?)```/)
  if (jsonMatch) {
    try {
      const bp = JSON.parse(jsonMatch[1])
      await sceneStore.loadBlueprint(bp, 'AI 生成')
      agentStore.setBlueprintLoaded('inline')
    } catch { /* fall through to normal display */ }
  }
  agentStore.addAgentMessage(message.content)
  agentStore.setProcessing(false)
  break
```

## 8. 改进项 F7：AI 对话框布局与思考面板（已修复 ✅）

> 详见 `.workbuddy/ai-chatpanel-review-2026-08-06.md`

### 8.1 问题描述

精密模式（LangGraph）下：
- 思考面板作为 `flex-shrink:0` 块插在消息列表与输入框之间（最大 40vh），挤占对话区高度
- 消息列表默认 `flex-start`（顶部对齐），内容少时下方留大片空白
- 各节点思考内容未能实时流式展示（依赖模型是否回流 `reasoning_content`）

### 8.2 已实施修复（`AIChatPanel.vue`）

1. **对话底部锚定**：`.messages-container::before { flex: 1 1 auto }` 占位，内容少时对话贴底；溢出正常滚动
2. **思考面板浮动覆盖**：`.thinking-panel { position: absolute; top: 44px; z-index: 5 }`，不占 flex 流高度
3. **思考内容回退兜底**：节点推理块在实时流为空时，回退显示诊断里的 `reasoning_preview`

### 8.3 待确认项

- 浏览器控制台是否出现 `[agentStore] appendThinking node=...` 日志（确认模型是否回流 reasoning_content）
- 若模型不回流 → 需扩展 `model_client.py` 兼容其他字段名，或换用确实支持 `enable_thinking` 的模型

## 10. 改进项 F9：TypeScript 类型安全（⚪ 低优先级）

### 10.1 风险点

| 位置 | 问题 | 影响 |
|---|---|---|
| `renderEntity.ts:35` | `materialParams: any[]` | 材质参数在渲染层全程 `any`，绕过了 `MaterialParams` 类型 |
| `sceneStore.ts:25` | 深路径导入 `../wild-core/src/primitive/parser` | 耦合具体路径，wild-core 重构后可能断链 |
| `agentBridge.ts` 多处 | `(window as any)` / `as any` | 调试钩子污染全局，类型安全边界失效 |

### 10.2 建议

- 渲染层统一使用 `materialAdapter.ts` 导出的 `MaterialParams` 类型
- `sceneStore` 通过 `wild-core/index.ts` 统一入口导入
- 调试钩子改为 `import.meta.env.DEV` 条件编译或统一的 debug API
