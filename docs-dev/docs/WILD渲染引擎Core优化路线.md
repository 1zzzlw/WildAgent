# WILD 渲染引擎 Core 优化路线

> 状态：P0 / P1 已实施；P2 完成本轮可安全前置项，GLB 与深层工程化能力继续保留  
> 编写日期：2026-07-31  
> 范围：`wild-core`、`.wild` 语言、Three.js 展示层及其扩展边界

## 0. 2026-07-31 实施结果

| 优先级 | 本轮结果 |
|---|---|
| P0 | 完成能力清单、完整 Schema 结构校验、重建 diagnostics、类型/校验同步、色彩与环境光、阴影范围、材质缓存、重复混色修复、中式曲面屋顶 |
| P1 | 完成 UV 与内嵌 PBR 通路，补齐柱/梁/开口/家具/body 的主要参数表现，引入静态 builder registry 与 `primitive`，增加篮球和复杂檐口端到端样例 |
| P2 | 完成重复网格 `InstancedMesh` 合批、按需渲染和扩展边界文档；按用户要求未实现 GLB。局部重建、LOD、Worker、独立 package 和第三方插件系统仍保留到有大型场景指标后实施 |

本轮没有把“P2 全部候选项”强行做完。原因是局部重建、Worker 和独立 package 会改变构建、缓存与发布边界，应先由真实大型场景的构建耗时、draw call 和显存数据驱动；这也符合本文原先“不做过深设计”的范围。

具体扩展步骤与项目代码示例见 [WILD渲染引擎扩展开发指南.md](WILD渲染引擎扩展开发指南.md)。

本轮结构回归已固化为 `wild-web/scripts/check-wild-core.mjs`（命令：`npm run check:core`）。当前五份样例均通过，能力清单共 11 项；篮球样例生成 3 个 mesh，复杂屋檐样例生成 18 个 mesh，均无 error diagnostics。

## 1. 结论先行

当前画面不够丰富，**不是 `.wild` 这种参数化文件已经到了极限**，而是下面三层能力还没有对齐：

1. `.wild` 规范写出的能力比 `wild-core` 实际实现的能力多；
2. `wild-core` 输出的数据还缺少 UV、纹理槽、完整材质信息等高质量渲染所需内容；
3. Three.js 展示层目前只有基础灯光、阴影和 `MeshStandardMaterial`，还没有充分发挥 PBR 渲染能力。

因此，现在看到的效果更接近“当前参考实现的上限”，不是 WILD 方案本身的上限。

另外，WILD 和 GLB 不应该被设计成互相替代：

- WILD 适合表达语义、参数、构件关系、可编辑规则和确定性重建；
- GLB 适合承载美术师制作的复杂网格、UV、骨骼和贴图；
- 后续更合理的方向是由 WILD 管理场景和语义，必要时把 GLB 作为一种受控资源引用。

## 2. 本次审阅范围

本次主要查看了：

- `wild-web/wild-lang/` 下的语言规范、原语、材质和版本文档；

## 3. 当前真实能力边界

### 3.1 规范与实现存在明显差距

| 能力 | 规范中的定义 | 当前实现情况 |
|---|---|---|
| 柱子 | 多种柱式、卷杀、侧脚、凹槽 | 当前主要是截锥；`style`、`entasis`、`inclination` 没有真正参与造型，`flutes` 主要改变圆周分段数 |
| 梁 | 矩形、圆形、工字形，可倾斜、可沿曲线 | 工字形按矩形处理；直梁没有完整处理竖向倾角；曲线梁主要是水平分段 |
| 屋顶 | gable、hip、dome、flat、`chinese_curved`、`chinese_pagoda` | `chinese_curved` 当前会退化为普通 gable；飞檐曲线参数未生效；多种屋顶的厚度和细部不完整 |
| 开口 | 矩形、拱形、哥特式、圆形，可生成门窗 | 墙洞和覆盖面主要仍是矩形；`style` 没有生成对应轮廓、窗框、玻璃或门扇结构 |
| 家具 | table、chair、bookshelf、bed、lamp、tile | 除瓦片批处理外，各 subtype 最终基本走同一个简单桌面平面 |
| `dense_brick` | 体素解压和 Marching Cubes / Dual Contouring | 解压和等值面提取仍是占位实现，当前输出空几何 |
| `body` | 体型、头型、四肢、斗篷、兜帽 | 当前主要生成头部和躯干，多个参数尚未参与几何 |
| 模板实例 | 旋转、缩放、材质覆盖、自动唯一 ID | 部分变换只是写入临时字段，许多 builder 不消费；实例 ID 生成与规范描述尚未完全一致 |
| placements | 可在不同构件表面批量排布 | 当前表面查询主要支持 gable 屋顶的左右坡面 |
| 嵌入图片 | 材质可携带 `embeddedImage` | core 会透传，但 Three.js 材质适配层没有使用，几何也没有 UV |

这意味着一些蓝图虽然“字段合法”，但渲染结果会忽略字段、降级成基础形状，甚至得到空几何。当前首先要解决的是“声明了就必须实现，否则明确报不支持”，不能继续静默降级。

### 3.2 材质数据不足以达到常见 GLB 的效果

当前 `MeshData` 主要包含：

- position；
- index；
- normal；
- vertex color；
- transform；
- 单一 `materialRef`。

当前还没有稳定的：

- UV；
- tangent；
- 多材质槽；
- albedo / normal / roughness / metalness / AO 等纹理通道；
- decal；
- 可复用的程序化 shader 参数。

现有风化、苔藓和边缘磨损很多时候是对基础色做整体混合，或者按顶点做简单噪声着色，并不等于真实的裂纹、木纹、砖石法线和边缘磨损。

还存在几个会直接影响观感的问题：

- 顶点颜色已经烘焙了基础色，Three.js 材质又设置一次基础色，存在颜色被重复相乘、整体偏暗的风险；
- 苔藓效果既在材质参数阶段混色，又在顶点颜色阶段再次处理，语义可能重复；
- `albedo`、`lightingCondition` 和 `embeddedImage` 当前没有在展示层真正落地；
- 材质缓存键只包含材质名和是否有顶点色，同名材质参数更新后可能继续复用旧材质。

### 3.3 Three.js 展示层仍处于基础预览阶段

当前视口主要是：

- 环境光；
- 单个方向光；
- PCF 软阴影；
- 深色背景和网格；
- `MeshStandardMaterial`。

代码中还没有完整接入：

- 正确的输出色彩空间和统一色彩管理；
- tone mapping 与曝光控制；
- HDR 环境光照和 PMREM；
- 天空、地面接触感和更合理的阴影范围；
- SSAO、轮廓等按需后处理；
- 渲染质量档位。

所以即使几何不变，仅升级展示层，也能让现有小木屋、别墅、凉亭的效果明显改善。不过展示层只能提升“光影和质感”，不能把一个平面家具变成精细家具，也不能凭空生成飞檐结构。

### 3.4 语言、类型与校验源存在漂移

当前至少有四份相互关联但并非完全一致的定义：

- `wild-lang/schema.json`；
- `wild-core/types.ts`；
- 前端 `src/types/blueprint.ts`；
- 后端 `spatial_tools.py` 中的枚举和必填字段。

已能看到的例子包括：

- core、前端和 schema 的 `InstanceRef` 字段结构不完全一致；
- `furniture.tile` 在部分定义中存在、部分定义中不存在；
- 文档允许曲线数组，但 schema 的对应字段主要按单段对象定义；
- `grain` 已出现在示例和 core 逻辑里，但不在正式 EffectLayer 类型和 schema 中；
- parser 主要检查 JSON、顶层字段和版本，并没有执行完整 JSON Schema；
- 某些已保存场景的 `meta.type` 超出正式枚举。

在扩展新构件之前，应先把“谁是唯一权威定义”统一下来，否则每加一个能力都要在多处手工同步，并容易出现 Agent 认为合法、前端认为合法、core 却无法正确渲染的情况。

### 3.5 现有 Agent 蓝图也没有充分使用已有能力

目前后端保存的多数 AI 场景主要使用基础颜色和基础构件，基本没有使用：

- effects；
- templates；
- instances；
- placements。

因此画面单薄并不全是渲染器问题，也包括 Agent 生成策略没有稳定利用现有能力。不过在优化 Prompt 前，应先确认这些能力在 core 中真正可用，否则只会让 Agent 生成更多“格式正确但效果不生效”的字段。

## 4. WILD 应该如何扩展

### 4.1 不要为每个现实物体增加一个硬编码类型

如果加入篮球，不建议直接增加：

```text
type: "basketball"
```

否则足球、排球、花瓶、路灯、斗拱、吻兽都会继续要求修改 core 的总分支、类型、schema、校验器和 Agent 规范，最终变成无限增长的类型清单。

更合适的是分三档表达：

1. **通用程序化形体**  
   例如 box、sphere、cylinder、profile sweep、lathe、extrude、surface 等少量可组合能力。

2. **语义组件或装配模板**  
   “篮球”“斗拱组”“栏杆组”是带语义和参数的组件，由通用形体、材质和重复规则装配出来。

3. **外部精细资产**  
   对不适合用少量参数描述的雕刻、角色、复杂装饰，使用带内容哈希的 GLB 等资源，由 WILD 保存引用、变换、语义标签和可编辑覆盖项。

这样新增物体时，优先增加“可复用的形体能力”或“组件模板”，只有出现新的数学构造方式时才扩展 core。

### 4.2 篮球的推荐表达

篮球可以作为扩展机制的第一个验收样例：

- 几何：通用 sphere，而不是 basketball 专用 builder；
- 参数：半径、分段或 LOD；
- 材质：橙色 PBR；
- 表面细节：程序化凹凸、接缝 decal/曲线，或受控纹理资源；
- 语义：组件名称或 tag 表示它是篮球；
- 行为：碰撞球、质量、弹性等属于行为/物理层。

如果只需要远景篮球，程序化 sphere 足够；如果需要品牌 Logo、真实颗粒和精细接缝，则应允许纹理或 GLB 资源参与，而不是把全部细节硬塞进几 KB 的参数。

### 4.3 复杂古建筑屋檐的推荐表达

复杂屋檐也不宜做成一个不可拆的 `ancient_eave` 大类型。建议先用一个目标样例反推最少通用能力：

- 屋面主体：可控截面/曲线的 roof surface；
- 檐口：profile sweep 或曲面边界；
- 瓦片：placement / array / instancing；
- 屋脊：独立 sweep 或 ridge 组件；
- 斗拱：可参数化 assembly；
- 吻兽和高细节雕饰：可选 GLB 资源实例。

是否采用这些具体字段，应在完成目标样例后再冻结，避免先设计一套很大但没有真实使用验证的抽象。

### 4.4 `.wild` 不需要每次整体重定义

扩展可以分为三种情况：

| 情况 | 是否需要升级 WILD |
|---|---|
| 规范已有字段，但 core 尚未实现，例如 `chinese_curved` | 不需要改蓝图格式，补齐引擎实现即可 |
| 新增通用构件或材质字段 | 以 v1.1 方式增量增加，v1.0 继续有效 |
| 引入资源清单、GLB 引用等新结构 | 需要小版本升级和迁移/兼容测试 |

建议保留“只增不删”的方向，但在当前规范与实现尚未对齐前，不宜过早宣称 v1.0 已经完成严格网格哈希级冻结。应先建立合规样例，再对外承诺长期兼容。

## 5. 推荐的 Core 形态

近期不需要立刻做完整插件生态，只需要先消除硬编码扩展阻力。

当前核心入口用一个大 `switch (el.type)` 选择 builder。第一步可改为内部注册表：

```text
element type
  -> validator
  -> resolver（可选）
  -> geometry builder
  -> capability metadata
```

近期注册表仍由项目本地静态导入，不允许 `.wild` 动态执行任意代码。这样可以：

- 新增 builder 时少改核心入口；
- 由同一个注册项提供支持类型和能力信息；
- 对未知类型给出明确诊断；
- 后续再决定是否抽成独立插件包。

暂时不建议现在就实现动态 npm 插件下载、运行时脚本加载和第三方权限系统，这些不是当前画面质量的主要阻塞项。

## 6. 分阶段优化路线

### 阶段 0：建立真实基线

目标：先让文档、类型、schema、校验和实现说同一件事。

建议工作：

- 列出每个构件和字段的支持状态：完整、部分、占位、不支持；
- 确定一份可生成 TypeScript 类型和校验器的权威 schema；
- core parser 执行真正的结构校验，未知类型或未实现能力不得静默降级；
- `reconstructEntity` 返回 diagnostics，不能只在控制台警告后跳过构件；
- 修正 core 类型、前端类型、后端校验之间的漂移；
- 建立最小场景、木屋、别墅、凉亭/中式屋顶四组固定测试蓝图；
- 为上述蓝图保存几何统计和截图基线。

验收标准：

- 规范声明支持的字段都有测试；
- 占位能力会明确报错或标记 experimental；
- 同一份蓝图在修改前后有可比较的几何和截图结果。

### 阶段 1：先做不改 WILD 格式的画质提升

目标：最快改善现有场景观感。

建议工作：

- 补齐 Three.js 色彩空间、tone mapping 和曝光；
- 加入 HDR 环境光照、PMREM、天空和地面；
- 调整方向光与阴影相机，使阴影覆盖跟随场景包围盒；
- 修复材质缓存失效策略；
- 修正顶点色与基础色重复相乘、效果层重复混合；
- 保留用户相机视角，避免每次局部修改后自动重新框选整个场景；
- 为低、中、高画质提供简单配置。

这一阶段不修改 `.wild`，风险较低，且最适合先做 A/B 截图确认收益。

验收标准：

- 同一份 `.wild` 在不改变几何的前提下，层次、曝光、阴影和材质辨识度明显改善；
- 修改材质后不会继续显示旧缓存；
- 四组基线场景无明显过曝、死黑、阴影截断。

### 阶段 2：补齐已经写进 v1.0 的几何承诺

目标：先兑现现有规范，再继续增加新类型。

优先顺序建议：

1. `chinese_curved` 屋顶和飞檐参数；
2. 屋顶厚度、屋脊和正确的 hip 轮廓；
3. 柱子的 style、entasis、inclination；
4. opening 的拱形、圆形轮廓，以及门窗框/玻璃的最小表达；
5. 梁的竖向朝向和 i-beam；
6. furniture 与 body 的“真实支持或明确降级”；
7. `dense_brick` 单独评估，避免它拖慢主线。

验收标准：

- 改变对应参数时，几何有稳定、可测的变化；
- 不再出现枚举值不同但画面完全相同的情况；
- 文档示例可以在 core 中得到与描述一致的结果。

### 阶段 3：升级材质数据通路

目标：让 WILD 生成的几何具备接近常规 GLB PBR 资产的材质基础。

建议工作：

- `MeshData` 增加 UV，必要时增加 tangent 和 material slot；
- 明确程序化材质与纹理材质的边界；
- 支持 albedo、normal、roughness、metalness、AO 等通道；
- 将 grain、weathering、moss、edgeWear 的正式 schema 与实现对齐；
- 建立木材、石材、砖、瓦、金属、玻璃等经过验证的材质预设；
- 对资源使用内容哈希，保证同一蓝图依赖的资源可验证。

这一阶段可能需要 WILD v1.1，但应采用增量字段，不能破坏 v1.0。

验收标准：

- 木、石、瓦不再只靠颜色区分；
- 近景能观察到合理的法线和粗糙度变化；
- 缺失资源、哈希不一致时有明确错误。

### 阶段 4：引入可注册 builder 与通用形体

目标：以后新增篮球或新构件时，不再持续扩大核心 `switch`。

建议工作：

- 用 builder registry 替换硬编码分发；
- 能力清单由 registry 自动生成；
- 为每个 builder 绑定参数校验和测试样例；
- 先增加最少的一组通用形体，使用“篮球”和“一段复杂檐口”做验证；
- Agent 只根据当前 capability manifest 生成可用类型。

验收标准：

- 新增一个通用 builder 时不需要修改核心重建流程；
- 不支持的插件/构件在渲染前即可被识别；
- 篮球不用专用硬编码类型即可表达。

### 阶段 5：WILD + GLB 混合资产

目标：允许高细节资产进入场景，同时保留 WILD 的语义和可编辑性。

建议先做最小方案：

- WILD 中保存资源 ID、类型、URI/内嵌方式和内容哈希；
- `asset_instance` 只保存资源引用、transform、语义 tag、可覆盖材质；
- 加载失败时显示明确占位和诊断；
- 参数化建筑主体继续由 core 生成，雕刻、角色、复杂装饰可使用 GLB。

验收标准：

- 同一场景中程序化建筑与 GLB 装饰能共同渲染；
- 资源内容可由哈希验证；
- Agent 能识别资产语义，但不能直接修改 GLB 内部任意三角形。

### 阶段 6：性能与工程化

这部分在画质和扩展路线稳定后再做：

- 按 element ID 局部重建；
- 几何、材质和资源缓存；
- 重复构件使用 `InstancedMesh`；
- LOD 和视锥体剔除；
- 大型构建放入 Worker；
- draw call、顶点数、构建耗时和显存统计；
- 将 `wild-core` 抽成独立 package，并建立独立版本和测试。

## 7. 推荐优先级

### P0：下一轮最值得先做

1. 规范与实现能力盘点；
2. 自动化基线和明确 diagnostics；
3. Three.js 色彩、HDR、阴影与材质缓存修复；
4. 修正顶点色和效果层重复处理；
5. 实现 `chinese_curved`，用中式屋顶作为第一个几何质量样例。

### P1：P0 验证后

1. UV 与正式 PBR 材质通路；
2. 柱、开口、梁等现有规范补齐；
3. builder registry；
4. 通用 sphere / profile sweep 等最小形体集合；
5. 篮球和复杂檐口两个端到端验收样例。

### P2：能力稳定后

1. GLB 混合资产；
2. 局部重建、instancing、LOD、Worker；
3. 独立 `@wild/core` package；
4. 第三方构件包或插件生态。

## 8. 暂不建议做的事情

- 暂不为篮球、花瓶、路灯等每个名词各加一个 builder；
- 暂不直接设计完整动态插件市场；
- 暂不继续扩写大量规范字段而不实现；
- 暂不把后处理当成解决几何单薄的唯一方案；
- 暂不让 Agent 生成 core 未声明支持的新类型；
- 暂不承诺当前 v1.0 已达到跨引擎网格哈希完全一致，除非合规测试套件已经建立。

## 9. 建议的首轮实施包

如果本路线通过，首轮代码优化建议严格控制为一个可验证的小包：

1. 建立四个固定 `.wild` 基线场景和截图；
2. 增加 capability audit 与重建 diagnostics；
3. 修复材质缓存、顶点色混合与基础色重复问题；
4. 完成 Three.js 色彩空间、tone mapping、HDR/环境光照和阴影适配；
5. 输出优化前后截图和性能数据。

首轮先不改蓝图结构、不做 GLB 引用、不做完整插件系统。首轮完成后，再根据截图效果决定优先进入“现有几何补齐”还是“材质数据通路升级”。
