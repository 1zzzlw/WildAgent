# WildAgent 项目阶段路线文档

> 最后更新：2026-08-02
>
> 本文档记录项目六个开发阶段的实际情况：每个阶段解决了什么问题、还存在什么问题、如何解决、实现了什么、用了什么技术、为什么选它。

## Phase 1：前端基础框架 ✅ 已完成

### 解决了什么问题

项目从零起步，需要一个能加载 `.wild` 文件并在浏览器中渲染 3D 建筑的完整前端编辑器。此前只有分散的 `wild-core` 渲染引擎和 `wild-viewer` 查看器参考代码，没有统一的应用框架、状态管理、编辑交互。

### 实现了什么

| 模块         | 产出                         | 说明                                                                         |
| ------------ | ---------------------------- | ---------------------------------------------------------------------------- |
| 状态管理     | 5 个 Pinia Store             | sceneStore / selectionStore / historyStore / agentStore / uiStore            |
| 统一编辑协议 | ScenePatch                   | 11 种操作类型，基于 revision 的版本控制，所有编辑操作（用户/AI）统一走 patch |
| UI 框架      | 9 个 Vue 组件                | 编辑器布局（顶栏 + 左面板 + 3D 视口 + 右面板 + 底部 AI 对话）                |
| 渲染管线     | 4 层适配器                   | wildCoreAdapter → meshDataToGeometry → materialAdapter → renderEntity        |
| 3D 视口      | CanvasViewport               | Three.js 渲染、OrbitControls、PCFSoftShadowMap、响应式布局                   |
| 基础编辑     | 拖拽添加 + 属性面板 + 场景树 | 支持 wall/column/floor/roof 四种基础构件                                     |
| 撤销重做     | historyStore                 | 50 步历史栈，before/after Blueprint 快照                                     |
| 导入导出     | 本地 `.wild` 文件读写        | FileReader 导入 + JSON.stringify 导出下载                                    |
| 前端保护     | 顶点数限制 50,000            | 超限替换为红色线框占位网格，防止浏览器卡死                                   |

### 用了什么 + 为什么

| 技术选择                      | 为什么                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Vue 3 + Composition API**   | 响应式系统天然适合编辑器场景（Blueprint 变更 → 自动触发渲染刷新）；组合式 API 比 Options API 更适合逻辑复用（渲染管线、Agent 通信各自独立可测试） |
| **Pinia**                     | Vue 3 官方推荐状态管理，TypeScript 支持完善，模块化 Store 天然匹配场景/选择/历史/Agent/UI 五个独立状态域                                          |
| **Three.js 0.160**            | 最成熟的 WebGL 库，社区资源丰富，不需要 WebGPU 的尖端特性（项目目标是建筑可视化而非游戏级渲染）                                                   |
| **wild-core 内嵌在 wild-web** | 引擎还在频繁改动期，放在前端项目内调试方便；引擎不依赖任何前端框架，通过单一适配层隔离，后续可随时抽为独立 package                                |
| **ScenePatch 协议**           | 所有编辑操作统一为 patch，用户拖拽和 AI 生成走同一管道，revision 版本号防冲突，undo/redo 只需保存 before/after Blueprint                          |

### 当前存在的问题

Phase 1 的问题已全部解决，无遗留。

## Phase 2：后端 Agent MVP ✅ 已完成

### 解决了什么问题

用户希望通过自然语言描述来生成建筑，但 AI 直接生成 3D 几何不可靠。核心挑战是：

1. **AI 不懂建筑规则**：LLM 不了解 `.wild` 构件格式、空间约束、材质 PBR 规范
2. **小模型 tool use 不可靠**：LLM 不一定会主动调用校验工具，或调用顺序错误，导致带有空间错误的蓝图被输出
3. **生成结果不稳定**：同样 prompt 可能产生结构正确或顶点爆炸两种结果

### 实现了什么

| 模块                   | 产出                                           | 说明                                                                                                         |
| ---------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 通信层                 | FastAPI WebSocket 端点                         | 心跳 ping/pong + 指数退避自动重连 + 页面可见性检测 + 并发锁                                                  |
| 规范注入               | RAGSpecLoader + FileSpecLoader 兜底            | Chroma 检索完整规范和建筑类型参考，固定注入精简铁律；RAG 失败时退回文件读取                                  |
| System Prompt          | 统一三意图 prompt                              | 生成 / 修改 / 聊天三种意图，AI 自行判断，一份 prompt 覆盖                                                    |
| 空间工具               | 18 个纯函数工具                                | 1 查询（get_wall_bounding_box）+ 9 检测（validate_*）+ 8 修正（fix_*）                                       |
| 校验流水线             | 15 步确定性流水线                              | Structure → Schema → Reference → Geometry → Fix → Collision，服务端强制顺序执行                              |
| 自动修正               | 6 类自动修复                                   | opening 坐标/越界、墙体接缝、楼梯对齐、屋顶覆盖、尺寸异常、构件悬空                                          |
| 校验结果展示（基础版） | 前端逐条展示校验结果                           | 当前只展示线性 Python 校验结果（✅/⚠️/❌/🔧），不等同于完整 Agent 流水线                                         |
| 可选思考模式           | `enable_thinking` + `reasoning_content` 实时流 | 开启时请求并展示模型接口实际返回的思考内容；关闭时显式关闭模型思考；接口不支持时明确提示，不使用固定文案冒充 |
| 增量修改               | ScenePatch 生成 + 前端应用                     | AI 识别修改意图 → 生成 patch → 校验 → 前端"应用修改"按钮                                                     |
| Patch 拦截             | 校验失败不发送前端                             | ❌ 级别错误时改为错误提示，不让异常数据进入渲染                                                               |
| 会话管理               | 会话 = 蓝图文件                                | 服务端场景文件作为持久化来源，Pinia 保存当前界面状态，REST API 负责列表、读取、更新和删除                    |
| 蓝图双格式             | Blueprint + ScenePatch 自动识别                | `query_structured()` 按 `"meta" in data` / `"operations" in data` 分流                                       |
| 场景 REST API          | scenes.py                                      | GET 列表 / GET 单个 / PUT 更新 / DELETE 删除                                                                 |
| RAG 检索增强           | Chroma 本地向量索引                            | `storage/knowledge_base/` 规范文档分片、embedding、持久化索引、按 query 动态注入                             |
| RAG 质量基线           | 11 个固定检索用例                              | 使用真实 Loader、metadata 过滤和 358 个 chunk 回归九类组合构件及能力边界                                     |
| 组合构件闭环           | 9 类语义组件 + 编译器                          | 语义组件确定性展开为 Core 基础几何，并打通 Schema、ScenePatch、编辑、知识库和固定评测                        |
| 用户知识库导入         | 预留扩展                                       | 后续支持用户上传 md/txt 等知识文档并增量入库；当前阶段还没有上传 API 和前端入口                              |

### 用了什么 + 为什么

| 技术选择                   | 为什么                                                                                                                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **FastAPI + WebSocket**    | 异步原生支持，WebSocket 天然适合 Agent 流式响应（步骤推送、patch 提案、最终回复），比 SSE 更灵活（支持双向通信）                                                                              |
| **LangChain create_agent** | MVP 阶段最简方案——一行 `create_agent(llm, tools, system_prompt)` 就能拿到可对话的 Agent，不需要手写 tool call 循环。后续升级 LangGraph 时保持 WebSocket 连接入口兼容，并扩展节点/RAG/诊断事件 |
| **OpenAI Compatible API**  | 不锁定供应商，所有兼容接口的大模型（千问/DeepSeek/GLM 等）同一套代码切换，靠 `base_url` 区分                                                                                                  |
| **Pydantic Settings**      | 类型安全的配置管理，`__` 双下划线分隔层级（`CHAT__NAME`），每类模型独立 ModelConfig，新增模型类型只需加一个字段                                                                               |
| **服务端确定性流水线**     | 核心设计决策——不再依赖 LLM "自愿"调用 tools，而是 LLM 只管生成初稿，服务端按固定顺序跑 Python 函数校验。**理由**：小模型 tool use 可靠性差，确定性 Python 代码比 LLM 判断更可靠、更快、可复现 |
| **纯函数 Tool 设计**       | 所有工具 `(blueprint: dict) -> str`，无状态依赖。理由：LangGraph 升级时零改动直接复用为图节点逻辑                                                                                             |
| **Chroma + RAGSpecLoader** | 完整规范和建筑类型参考会持续增长，不能全量塞进 System Prompt。RAG 保留精简基础规范作为铁律，再按用户意图检索相关片段，兼顾上下文长度和生成准确性                                              |

### 移交到后续阶段的已知边界（不阻塞 Phase 2）

1. **校验流水线是线性串行的**：Step 4/5/6/7（opening_coords / wall_junctions / stair_alignment / roof_coverage）互不依赖却必须串行执行，浪费等待时间
2. **修正是一次性的**：fix → recheck 只跑一轮，如果修正后仍有问题（如修正引入新问题），不会自动重试
3. **不能持续迭代修复蓝图**：当前 Phase 2 能“校验 + 局部自动修复”，但不能“持续迭代修复一个蓝图直到稳定”。它已经有检查员和几个维修工，但还没有一个能反复调度检查、维修、复查的流程控制器
4. **条件跳转写死在 if/else 里**：流程逻辑散落在 Python 代码中，不可视化，扩展新节点需要修改流水线函数
5. **RAG 已有固定基线但尚未完成线上排序评估**：当前 11 个固定问题覆盖分片、metadata 和关键词路由；线上 embedding 的语义排序、rerank 与混合检索仍需结合真实请求观察
6. **没有重试机制**：LLM 生成失败或返回非法 JSON 时无自动重试，直接返回错误
7. **没有用户知识库导入**：当前只索引项目内置规范文档，还没有用户上传、删除、重建索引和前端管理入口
8. **运行过程观察不完整**：前端只能看到基础校验结果；RAG 命中知识和 Agent 节点流转尚未形成按请求隔离的实时事件流
9. **复杂建筑仍是单次上下文任务**：一次 RAG 召回和一次整栋生成容易让楼层、构件、组合规则争抢有限上下文，结果可能结构不完整或前后约束不一致
10. **渲染偏差缺少闭环诊断**：后端空间校验通过不代表 `wild-core` 重建后的世界坐标一定正确，目前还不能把渲染侧偏移定位到具体构件和责任模块后局部修复

### 怎么解决

| 问题                         | 解决方案                                                                                          | 对应阶段                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------- |
| 线性串行                     | LangGraph 并行节点（Step 4/5/6/7 同时执行）                                                       | Phase 3                       |
| 一次性修正                   | LangGraph 条件循环边（fix → recheck → 仍有问题 → 再修正，最多 3 轮）                              | Phase 3                       |
| 不能持续修复到稳定           | LangGraph validate → collect issues → route fix → revalidate 循环，直到无致命错误或达到 max_retry | Phase 3                       |
| if/else 不可视化             | LangGraph 声明式状态图（边条件显式定义，流程图可导出）                                            | Phase 3                       |
| RAG 线上排序评估             | 保留现有 11 个固定用例，采集真实查询后再评估 rerank / 混合检索                                    | Phase 3 前置或独立优化        |
| 无重试机制                   | 在 LangGraph 的 generate 节点加校验失败→重试回路                                                  | Phase 3                       |
| 用户知识库导入               | 上传 API + 文件存储 + 增量索引 + 删除重建 + 前端管理面板                                          | Phase 3 后或独立 RAG 扩展阶段 |
| RAG 检索日志与完整流水线展示 | 随显式 LangGraph 改造统一定义节点事件、RAG trace 和前端流水线视图                                 | Phase 3                       |
| 复杂建筑上下文拥挤           | 先生成全局结构计划，再按基础结构、楼层墙体、门窗楼梯、屋顶细部分模块执行节点级 RAG 和生成         | Phase 3                       |
| 渲染后偏移与未对齐           | 统一坐标不变量 + 结构化重建诊断 + 按责任模块生成最小 ScenePatch，再重检与重建                     | Phase 3                       |

## Phase 3：LangGraph 智能编排 ⏳ 待开始

### 解决了什么问题

Phase 2 的校验流水线虽然实现了确定性兜底，但它仍把“检索知识 → 生成整栋建筑 → 校验”视为一次大任务，并用 Python if/else 硬编码流程控制。Phase 3 应该改成“先拆解、再生成、再合并、再严格校验”，让每个组件节点只检索和携带当前模块需要的上下文。

这意味着：

- 第一个节点根据用户输入识别建筑类型并调用知识库中的 `building_types/catalog/`、`building_types/` 和 `components/`。
- 第一个节点同时把用户语言丰富为组件需求清单（例如门、窗、屋顶、栏杆）。
- LangGraph 生成的是组件子图，而不是全量 Blueprint；每个组件节点只关心自己的部分。
- 组件节点自身后面应跟独立校验节点，校验失败时带上结构化错误信息重新生成或修正，直到该组件通过或达到重试上限。
- 所有组件节点运行完成后，合并节点把内存中的片段数据汇总成完整 Blueprint。
- 合并后的 Blueprint 进入更严格的全局校验节点，校验失败时把错误信息返回到责任节点继续重试。

阶段判断必须明确：LangGraph 解决的是编排、状态、循环和可观察性，**不会扩大模型上下文窗口，也不会自动修复坐标或渲染引擎缺陷**。生成完整性依赖合理拆解与节点级 RAG；空间正确性依赖坐标约定、校验器和重建诊断。

### 当前存在的问题（Phase 2 遗留）

- 线性串行：Step 4/5/6/7 互不依赖但串行执行，校验耗时=所有步骤之和
- 单次修正：fix → recheck 后仍有错误也不继续循环
- 条件逻辑散落：跳转规则写在 `run_validation_pipeline()` 的 if/else 里，新增节点需要改动流水线函数本体
- 不可视化：流程逻辑无法导出为图，调试靠打日志
- 检索不可追踪：RAG 命中只写后端日志，前端看不到“哪个节点为何召回了哪条知识”
- 上下文竞争：复杂建筑的一次生成带入多类规范，关键知识可能被挤出或弱化
- 缺少全局不变量：轴网、层高、楼层标高、主体包围盒、朝向等没有在生成前冻结，后续构件各自猜坐标
- 缺少渲染诊断：当前只能看到蓝图级错误，缺乏构件级包围盒、预期位置和实际重建结果对照

### 设计方案

1. `understand_request` 节点
   - 解析用户意图、建筑类型、复杂度和可选组件
   - 调用 `building_types/catalog/`、`building_types/`、`components/`
   - 生成组件任务清单

2. `plan_component_nodes` 节点
   - 根据需求清单生成节点列表
   - 每个节点负责一个组件类型（door、window、roof、railing 等）

3. 各组件节点
   - 只检索本组件相关知识库片段
   - 只生成本组件的 fragment
   - 只输出本组件的结构化校验结果

4. 组件级校验节点
   - 在每个组件节点后进行本地校验
   - 失败时返回结构化错误，带出当前值、约束和建议范围
   - 成功则向合并节点放行

5. `merge_fragments` 节点
   - 把内存中的组件片段合并成完整 Blueprint
   - 进行 ID 冲突、引用完整性、层级关系检查
   - 不做深度修复，仅做一致性检查

6. `validate_merged_blueprint` 节点
   - 对整体 Blueprint 做更严格的跨组件校验
   - 失败时把责任信息返回到合适的组件节点进行重试
   - 允许多次重试，建议 `max_retries=3`

### 关键原则

- 组件优先：每个节点只关注自己的组件输出
- 内存优先：组件数据保存在 LangGraph State，合并后再生成完整 Blueprint
- 结构化错误：回调携带字段、父引用、可修正范围，而不是自由文本
- 非破坏性：已通过组件不应在重试中被随意改写
- 递归收敛：失败多次后显式报告人工介入，而不是无限重试

### 与现有自动修复代码的关系

- 现有自动修复代码保留为 LangChain 模式的 fallback
- LangGraph 主流程优先用“节点级校验 + 回调重试”
- 自动修复代码不是 LangGraph 的首选路径
- LangGraph 稳定后，旧修复函数可标记为“legacy fallback”

### 目标产出

| 模块       | 产出                        | 说明                                                 |
| ---------- | --------------------------- | ---------------------------------------------------- |
| 状态图定义 | `app/agent/graph.py`        | LangGraph StateGraph，定义节点与条件边               |
| AgentState | TypedDict                   | 保存请求、组件片段、校验结果、RAG trace、retry_count |
| 组件拆解   | `plan_component_nodes`      | 从用户语义提取组件需求清单                           |
| 组件节点   | `door/window/roof/...`      | 组件级生成与本地校验                                 |
| 合并节点   | `merge_fragments`           | 内存片段合并为完整 Blueprint                         |
| 全局校验   | `validate_merged_blueprint` | 严格跨组件验证与重试                                 |
| 结构化回调 | Callback Payload            | 失败组件带详细错误、建议范围、父引用                 |
| 重试循环   | LangGraph edges             | 失败后返回责任节点，最多 3 次                        |

### 校验与迭代

1. 先复用现有校验流程，确保与 Phase 2 等价
2. 再把校验流程拆成组件级节点
3. 最后把合并和更严格校验变成独立状态节点

### 后半段扩展：PBR 素材生产与入库编排

渲染能力的扩展不只等于 PBR，至少分成三层：

1. **几何能力**：篮球、复杂屋檐、曲面、雕花和后续外部模型引用；
2. **外观能力**：PBR 材质、纹理图片、UV、HDRI 环境光；
3. **资产生产能力**：素材搜索、下载、AI 生成、Blender 加工、质量检查和入库。

当前浏览器渲染器没有调用外部渲染 API。它读取 `.wild` 的几何与材质参数，由 `wild-core` 生成 `MeshData`，再转换为 Three.js `MeshStandardMaterial` 并在本地 GPU 渲染。现有 WILD v1.1 已能表达 Base Color、Normal、Roughness、Metalness、AO、`uvScale` 和 Base64 内嵌图片，但项目样例仍以数值参数和程序化顶点色为主，尚未形成真实 PBR 素材集的生产、存储和复用链路。

因此，Phase 3 后半段可在蓝图校验状态图稳定后增加一条**独立的资产工作流**。LangGraph 负责长任务编排、重试、费用控制、人工确认和断点恢复；MCP/API 只作为具体工具适配器，不进入浏览器实时渲染循环：

```text
用户/WILD 材质意图
        │
        ▼
[extract_material_intent]  识别材质、视距、质量、授权和预算要求
        │
        ▼
[resolve_asset]            优先查找项目资产目录
        │ 未命中
        ▼
[search_asset]             搜索 Poly Haven 等可信素材源
        │ 未找到合适结果
        ▼
[generate_texture]         可选 AI 纹理生成，返回任务 ID 和产物清单
        │
        ▼
[process_asset]            UV、无缝化、缩放、通道整理、压缩或 Blender 烘焙
        │
        ▼
[validate_asset]           校验尺寸、色彩空间、贴图配套、哈希、来源和授权
        │
        ▼
[register_asset]           存入资产目录/对象存储，登记不可变 assetId
        │
        ▼
[propose_wild_patch]       只向 WILD 写入资产引用和材质参数
        │
        ▼
[render_and_inspect]       本地 Three.js 预览、截图和性能检查
```

这条扩展工作流不替代 Phase 3 的首要目标。实施顺序仍然是：先完成蓝图校验、修正与重试状态图，再以单一材质样例接通最短资产链路，最后才增加 AI 生成和 Blender 加工。

#### 图片与 PBR 通道

| 资源                  | 作用                               | 运行时处理                         |
| --------------------- | ---------------------------------- | ---------------------------------- |
| Base Color            | 表面颜色和花纹                     | 颜色数据，按 sRGB 解释             |
| Normal                | 模拟细小凹凸，不改变物体轮廓       | 非颜色数据；依赖正确 UV            |
| Roughness             | 控制表面光滑或粗糙区域             | 非颜色数据                         |
| Metalness             | 控制金属区域；石材、木材通常接近 0 | 非颜色数据                         |
| AO                    | 加深缝隙和遮挡区域                 | 非颜色数据；需要第二套 UV          |
| Height / Displacement | 推动顶点形成真实高低差             | 后续可选，高细分网格下成本较高     |
| HDRI                  | 提供环境照明和反射                 | 属于场景环境资源，不是物体表面纹理 |

AI 生成一张普通 JPG 并不等于得到可用的 PBR 材质。正式产物应尽量是相互匹配的纹理集，并包含无缝平铺、统一分辨率、真实尺度、正确色彩空间和稳定 UV。UV 不合格时，即使图片质量很高，也会出现拉伸、错位和接缝。

#### MCP/API 候选职责

| 候选工具                                                                        | 适合承担的职责                                        | 路线定位                                                 |
| ------------------------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| [Poly Haven Public API](https://github.com/Poly-Haven/Public-API) 或其 MCP 包装 | 搜索和下载 CC0 PBR、HDRI、模型                        | 优先接入的素材来源；不进入运行时                         |
| [blender-orchestrator](https://github.com/mlolson/blender-orchestrator)         | UV、烘焙、纹理加工、LOD、AI 纹理和模型处理            | 可选的离线/服务端 Worker；先做单工具试点                 |
| [threejs-devtools-mcp](https://github.com/DmitriyGolub/threejs-devtools-mcp)    | 检查 Three.js 材质、贴图、显存、draw call、截图和性能 | 开发与自动验收工具，不是素材来源                         |
| Three.js 代码生成 MCP                                                           | 生成实验代码或辅助调试                                | 不作为 WILD 场景来源，生成代码不得绕过 core              |
| `three-js-textures-uv-mcp`                                                      | 如果能稳定提供 UV/纹理处理，可作为加工节点            | 精确仓库、维护状态和输出协议尚待核实，不作为当前核心依赖 |

初期不同时接入多个职责重叠的 Blender MCP。优先使用一个可控适配器完成端到端试点，并要求所有工具返回结构化产物清单，而不是直接写 WILD 或向项目注入任意 Three.js 代码。Blender 一类可执行脚本的工具必须在隔离 Worker 中运行，API Key 只保存在服务端，并对付费生成设置预算和人工确认。

#### 资产存储与 WILD 边界

Base64 内嵌图片适合小图、Demo 和单文件离线分享，不适合长期保存多张 2K/4K PBR 纹理。正式方案建议使用引用式资产清单：

```json
{
  "materials": {
    "greyRoofTile": {
      "baseColor": "#77736b",
      "textureSet": "grey_tile_01",
      "uvScale": [4, 4]
    }
  },
  "assets": {
    "grey_tile_01": {
      "source": "polyhaven",
      "license": "CC0",
      "maps": {
        "baseColor": "asset://sha256/...",
        "normal": "asset://sha256/...",
        "roughness": "asset://sha256/...",
        "ao": "asset://sha256/..."
      }
    }
  }
}
```

WILD 保存语义、参数、资源 ID、内容哈希和必要的来源信息；图片本体保存在项目资产目录、对象存储或 CDN。AI 素材生成完成后必须固化为不可变资产，同一份 WILD 不应在每次打开时重新生成图片。`embeddedImage` 继续作为小文件和离线兼容方案。

建议按以下顺序推进：

1. `Poly Haven → 资产入库 → WILD assetId → Three.js 本地渲染`；
2. 增加纹理处理、缓存、哈希与授权信息校验；
3. 按需加入 Blender UV/烘焙和 AI PBR 纹理生成；
4. 用 Three.js 调试工具完成截图、材质和性能验收。

GLB 导出仍是独立的后续扩展，不随本阶段的 PBR 资产管线一起实现。Blender 工具即使具备 GLB 能力，本阶段也只把它当作素材加工能力使用。渲染引擎的详细能力边界和扩展原则见 [WILD渲染引擎Core优化路线.md](../docs-dev/docs/WILD渲染引擎Core优化路线.md) 与 [WILD渲染引擎扩展开发指南.md](../docs-dev/docs/WILD渲染引擎扩展开发指南.md)。

## Phase 4：前端交互与渲染升级 ⏳ 待开始

### 解决了什么问题

Phase 1-3 实现了"AI 生成建筑 + 基础编辑"，但前端交互体验离完整编辑器还有差距：无法点击 3D 构件选中、没有变换手柄、环境渲染简陋、缺少丰富的材质/光照/环境效果。Phase 4 让编辑器从"能用"升级到"好用"。

### 已完成的前置能力

- Three.js Raycaster 已能从编译后网格回溯源组件，左键选择并高亮整体组件。
- 九类组合构件已有专用属性区，门窗行为采用右键交互，不占用左键选择。

### 当前存在的问题

- **无法拖拽变换**：没有 Translate/Rotate/Scale Gizmo，修改位置只能通过属性面板输入数字
- **环境渲染简陋**：只有基础的方向光+环境光，没有天空/地面/太阳/HDR 环境贴图
- **材质表现单一**：PBR 材质可用但颜色/纹理缺乏建筑感（木材纹理、石材、瓦片色等）
- **缺少模型扩展类型**：wild-core 目前支持 10 种建筑构件，没有装饰性元素（植被、人物、动物、车辆等）

### 怎么解决

| 问题            | 解决方案                                                                          |
| --------------- | --------------------------------------------------------------------------------- |
| 3D 拾取         | Three.js Raycaster + 鼠标事件 → 根据 `mesh.userData.elementId` 反查元素           |
| 选中高亮        | Outline pass（后处理）或 emissive 叠加 + 包围盒线框                               |
| Transform Gizmo | 集成 `transform-controls` 或自实现 Gizmo（平移/旋转/缩放），修改后生成 ScenePatch |
| 环境渲染        | HDR 环境贴图（RGBELoader）+ Sky shader + Ground plane + 级联阴影 (CSM)            |
| 材质增强        | 消费 Phase 3 资产目录中的 PBR 纹理集，建立木材/石材/砖墙/瓦片/金属/玻璃预设       |
| 扩展模型        | 评估 wild-core `body` 类型扩展能力，必要时增加 `vegetation`/`prop` 构件类型       |

### 实现了什么（目标产出）

| 模块            | 产出                  | 说明                                                   |
| --------------- | --------------------- | ------------------------------------------------------ |
| 3D 拾取         | 已前置完成            | Raycaster → 来源组件 ID → selectionStore 联动          |
| 选中高亮        | 已前置完成            | 选中组件整体显示高亮边框                               |
| Transform Gizmo | 平移/旋转/缩放        | 拖拽手柄直接修改位置/角度/尺寸                         |
| 属性面板增强    | 动态表单控件          | 根据构件类型渲染不同的编辑控件（下拉/颜色选择器/滑块） |
| 环境系统        | 天空 + 地面 + 太阳    | HDR 环境贴图 + 程序化天空 + 地面网格/平面              |
| 光照升级        | CSM 级联阴影 + 软阴影 | 更大范围、更高质量的阴影投射                           |
| 材质库          | PBR 预设 + 资产引用   | 木材/石材/砖/瓦/金属/玻璃，一键切换并复用已入库纹理    |
| 构件库扩展      | 更多预设构件          | beam/opening/stair/furniture 拖拽即用                  |
| 导出增强        | `.wild` + 截图        | 导出纯净 .wild + 高清渲染截图                          |

### 用了什么 + 为什么

| 技术选择                             | 为什么                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **Three.js Raycaster**               | 原生支持，无需额外库。从相机发射射线到鼠标位置，遍历 scene children 检测相交                                     |
| **CSM (Cascaded Shadow Maps)**       | 大场景（建筑尺度）下单张 shadow map 精度不足，CSM 按距离分多层阴影贴图，近处精细远处粗略，是建筑可视化的标配方案 |
| **HDR 环境贴图**                     | PBR 材质需要环境光照才能正确呈现金属/粗糙度效果，HDR 贴图提供真实的环境反射和漫反射                              |
| **TransformControls 或自定义 Gizmo** | Three.js 内置 `TransformControls` 可直接用，但样式固定。如需要更建筑感的 Gizmo（对齐网格、吸附端点），则自实现   |
| **程序化天空**                       | 比静态天空盒更灵活，支持时间变化（白天/黄昏/夜晚），与太阳方向光联动                                             |

### 边界注意

- **人物/动物等扩展类型**受限于 wild-core 引擎能力。`body` 类型目前只支持化身身体网格，要支持通用角色需要扩展引擎几何构建器。Phase 4 先评估可行性，如果引擎改动量大则延后到 Phase 5 或独立阶段
- **运行时不直接调用 MCP 或 AI 图片接口**：Phase 4 只加载已经入库、经过校验的纹理和 HDRI，外部服务不可用时仍应能打开已有 WILD
- **不改动 wild-core 几何核心算法**：环境、色彩和 PBR 贴图消费主要在前端 Three.js 层完成；资产引用如需升级 WILD，则采用向后兼容的小版本字段

## Phase 5：AI 组件模块化 ⏳ 待开始

### 解决了什么问题

Phase 2-3 的 AI 生成是"全量模式"——用户说一句话，AI 生成整个建筑。但实际使用中用户经常只需要 AI 生成**单个组件**（如"一个中式门楣"、"一个旋转楼梯"），然后自己拖到场景中摆放。Phase 5 把 AI 生成能力**模块化**，AI 从"全量生成器"升级为"组件工坊"。

### 当前存在的问题

- AI 只能生成完整建筑或整体 patch，无法生成"可复用的单个构件/构件组"
- 用户无法将 AI 生成的组件保存到构件库供后续复用
- 拖拽放置时缺少智能吸附（对齐墙面、地面、网格）

### 怎么解决

1. **新增 AI 组件生成模式**：用户在聊天中输入 `/component 中式门楣` → AI 生成构件/构件组 → 自动进入构件库的"AI 生成"分类 → 用户拖拽到场景
2. **组件知识库联动**：Phase 2 的 RAG + Phase 5 的组件模式配合——AI 学习过的形状（花瓶、雕像等）自动成为可拖拽组件
3. **智能放置**：拖拽时自动检测鼠标下方表面（地面/墙面/桌面），吸附对齐

### 实现了什么（目标产出）

| 模块              | 产出                            | 说明                                         |
| ----------------- | ------------------------------- | -------------------------------------------- |
| `/component` 命令 | AI 单组件生成                   | 用户指定组件描述，AI 生成构件/构件组 JSON    |
| AI 组件库         | 构件库新增"AI 生成"分类         | 展示已生成的组件缩略图，支持拖拽/点击放置    |
| 组件持久化        | 保存到 knowledge_base/patterns/ | 组件知识条目，跨会话复用                     |
| 智能吸附          | 拖拽时表面检测                  | 自动对齐到地面、墙面、桌面等参考面           |
| 组件参数化        | 放置后弹出参数调节              | 如门楣宽度、柱子高度，拖拽手柄或属性面板调节 |

### 用了什么 + 为什么

| 技术选择                               | 为什么                                                                                                        |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **基于 Phase 3 的 LangGraph 节点扩展** | 新增 `generate_component` 节点，与全量生成共享同一个 LLM + 工具链，只改变输出格式（单构件 vs 完整 Blueprint） |
| **Phase 2 的知识库联动**               | `knowledge_tools.py`（Phase 2 §17.10 预留）的 `/learn` 机制——AI 学习后自动入库 → Phase 5 组件库直接读取展示   |
| **Three.js Raycaster 表面检测**        | Phase 4 已实现 3D 拾取，Phase 5 复用同一套 Raycaster 做拖拽时的吸附面检测                                     |

## Phase 6：测试、部署与稳定化 ⏳ 待开始

### 解决了什么问题

前五个阶段堆叠了大量功能，但没有系统化的测试覆盖和部署方案。Phase 6 建立质量保障体系和交付能力，让项目从"开发中的原型"变成"可部署的产品"。

### 当前存在的问题

- **测试尚未系统化**：已有后端 pytest、Core smoke、组件几何和 RAG 固定评测，但尚未形成统一覆盖率门槛、CI 和浏览器 E2E
- **无部署方案**：没有 Docker 化、CI/CD、环境配置文档
- **错误恢复不完善**：部分异常路径未处理（LLM 超时、文件读写失败、WebSocket 断连恢复后的状态同步）
- **性能未度量**：没有渲染帧率监控、大场景加载时间基准、内存占用分析

### 怎么解决

| 层次     | 方案                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 单元测试 | 18 个 spatial tools（纯函数）是最佳测试起点——给定 Blueprint 输入，断言输出字符串包含预期的 ✅/❌/🔧 标记  |
| 集成测试 | 固定 prompt → LLM 生成 → 校验流水线 → 断言无 ❌ 级错误                                                  |
| E2E 测试 | Playwright/Cypress 控制浏览器：打开编辑器 → 连接 WebSocket → 发送 prompt → 等待 3D 渲染完成 → 截图对比 |
| 部署     | Docker Compose（wild-server + Chroma）+ 前端静态资源 Nginx/CDN 部署                                    |
| 性能     | 大场景（100+ 构件）加载基准测试 + 渲染帧率监控 + 顶点数/draw call 统计面板                             |
| 错误恢复 | 全局异常处理器 + 自动保存 + 崩溃恢复（从 localStorage/后端恢复最后状态）                               |

### 用了什么 + 为什么

| 技术选择            | 为什么                                                              |
| ------------------- | ------------------------------------------------------------------- |
| **pytest + vitest** | Python/TypeScript 各自生态的首选测试框架，async 支持完善            |
| **Playwright**      | 比 Cypress 对 WebGL/Canvas 的支持更好，适合 3D 应用的 E2E 截图对比  |
| **Docker Compose**  | wild-server + Chroma 两个服务有依赖关系，Compose 管理最简单         |
| **Stats.js**        | Three.js 社区标配性能面板，一行引入，不影响生产构建（tree-shaking） |
