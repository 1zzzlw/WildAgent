## 4. 环境变量管理

### 4.1 不提交 .env 到 Git

```bash
# 三步完成
echo ".env" >> .gitignore
git rm --cached wild-server/.env
git commit -m "从仓库移除 .env"
```

> **为什么**：`.gitignore` 只管"还没被追踪的新文件"，对已经被 `git add` 过的文件无效，必须用 `git rm --cached` 移除追踪。

### 4.2 GitLab CI Variables 配置

去 GitLab 项目 → **Settings → CI/CD → Variables**，添加以下变量（勾选 Protected + Masked）：

| Key | 用途 |
|---|---|
| `SSH_PASSWORD` | 服务器 root 密码 |
| `CHAT__NAME` | LLM 模型名 |
| `CHAT__API_KEY` | LLM API Key |
| `CHAT__BASE_URL` | LLM API 地址 |
| `EMBEDDING__NAME` | Embedding 模型名 |
| `EMBEDDING__API_KEY` | Embedding API Key |
| `EMBEDDING__BASE_URL` | Embedding API 地址 |

> `$CI_REGISTRY_USER` 和 `$CI_REGISTRY_PASSWORD` 是 GitLab 内置变量，不需要手动添加。

## 5. 各文件说明

### 5.1 `wild-server/Dockerfile` — 后端镜像

```dockerfile
FROM python:3.12-slim                    # 基础镜像
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv   # 安装 uv
COPY pyproject.toml uv.lock ./           # 先复制依赖文件（利用缓存）
RUN uv sync --frozen --no-dev            # 安装依赖
COPY . .                                 # 复制源码
CMD ["uv", "run", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**与 Java 对比**：Python 不需要"先在本地打包 JAR 再复制到 Docker"。Dockerfile 本身就是一份完整的构建菜谱，所有步骤都在容器内完成。

### 5.2 `wild-web/Dockerfile` — 前端镜像（含 nginx）

```dockerfile
# 阶段一：构建 Vue 项目
FROM node:22-alpine AS builder
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build              # → dist/

# 阶段二：nginx 运行
FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf    # 覆盖默认配置
COPY --from=builder /app/dist /usr/share/nginx/html  # 复制静态文件
EXPOSE 80
```

### 5.3 `wild-web/nginx.conf` — 反向代理规则

| 请求路径 | 处理方式 |
|---|---|
| `/` | 返回 Vue 静态文件（SPA fallback） |
| `/api/*` | 代理到 `wild-server:8000`（HTTP API） |
| `/ws/*` | 代理到 `wild-server:8000`（WebSocket，带 Upgrade 头） |

### 5.4 `.gitlab-ci.yml` — CI/CD 流水线

```
stages: build → deploy

build-server  ┐
              ├─ docker build → docker push（推送镜像到 GitLab Registry）
build-web     ┘

deploy        ── SSH 登录 39.106.183.13 → docker pull → 重启容器
```

#### 关键设计

- **只改前端 = 只构建前端镜像**，反之亦然（`only: changes` 规则）
- **deploy 只在 main 分支触发**，其他分支只构建不部署
- **API Key 不写死在文件里**，通过 `$变量名` 从 GitLab Variables 注入

### 5.5 `docker-compose.yml` — 本地开发

```yaml
services:
  server:
    build: ./wild-server        # 从本地 Dockerfile 构建
    ports: ["8000:8000"]
    env_file: .env              # 读取本地 .env

  web:
    build: ./wild-web
    ports: ["80:80"]
    depends_on: [server]        # 等后端启动完再启动前端
```

## 7. 常见问题

### Q: Python 有没有像 Java JAR 那样的打包命令？

A: 有 `uv build` 打 wheel 包，但那是给**库/模块**用的。Web 服务不需要——Dockerfile 就是打包方式，所有依赖安装和代码构建都在容器里完成。

### Q: nginx 需要手动在服务器上安装吗？

A: 不需要。`wild-web/Dockerfile` 以 `FROM nginx:alpine` 为基础，nginx 已经内嵌在镜像里了。

### Q: .gitignore 写了 .env 为什么还被提交？

A: `.gitignore` 只管"还没追踪的新文件"。已经被 `git add` 过的文件不受影响，必须用 `git rm --cached` 从索引中移除。

### Q: TypeScript 编译报错但运行没问题是怎么回事？

A: 前端类型定义（`src/types/scene.ts`）与 wild-core 实际输出的字段名不一致（如 `positions` vs `geometry`）。运行时 JS 不检查类型，所以能跑；编译时 TS 严格检查，所以报错。修复方式：让类型定义对齐运行时实际数据。

### Q: CI deploy 阶段报 `Permission denied`（SSH 连接失败）

**现象**：
```
Permission denied, please try again.
ERROR: Job failed: exit code 5
```

**根本原因**：GitLab SaaS shared runner 从公网连服务器，必须用密钥认证，密码方式不可靠。

**解决方案：SSH 密钥认证（一次配置永久有效）**

**第一步：在服务器上生成专用部署密钥**

SSH 登录服务器后执行：
```bash
ssh-keygen -t ed25519 -C "gitlab-deploy" -f ~/.ssh/gitlab_deploy -N ""
cat ~/.ssh/gitlab_deploy.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

**第二步：查看私钥内容并复制**

```bash
cat ~/.ssh/gitlab_deploy
```

输出类似：
```
-----BEGIN OPENSSH PRIVATE KEY-----
b3BlbnNzaC1rZXktdjEAAAA...（多行内容）
-----END OPENSSH PRIVATE KEY-----
```

把这整段（包含 BEGIN 和 END 行）全部复制。

**第三步：在 GitLab 添加 Variables**

GitLab → 项目 → Settings → CI/CD → Variables → Add variable：

| 字段 | 填写内容 |
|---|---|
| Type | **File**（重要，不要选 Variable） |
| Key | `SSH_PRIVATE_KEY` |
| Value | 粘贴第二步复制的私钥内容 |

> Type 选 **File** 时，GitLab 会把内容写成临时文件，`$SSH_PRIVATE_KEY` 是文件路径，`-i $SSH_PRIVATE_KEY` 直接可用，不需要处理换行符。

**第四步：`.gitlab-ci.yml` 对应写法**

```yaml
before_script:
  - apk add --no-cache openssh-client

script:
  - ssh -i $SSH_PRIVATE_KEY -o StrictHostKeyChecking=no root@39.106.183.13 "echo 连接成功"
  - scp -i $SSH_PRIVATE_KEY -o StrictHostKeyChecking=no /tmp/deploy.sh root@39.106.183.13:/tmp/deploy.sh
```

## 9. CI/CD 踩坑记录与解决方案

> 在实际配置 `.gitlab-ci.yml` 过程中遇到的 5 个 Bug 及其根因分析和修复方案。

### Bug 1：Runner 标签不匹配 — "no runner with tag 'test'"

**现象**：

```
This job is stuck because there is no active runner online with the tag: test
```

**根因**：

仿照 Java 项目的样例时直接复制了 `tags: - test`，但当前 GitLab 项目没有注册过这个标签的 Runner。GitLab 的标签匹配是**严格相等**的——写了 `test` 就必须有 Runner 恰好打上 `test` 标签，Shared Runner 也不会接这个 job。

**修复**：

删除所有 job 中的 `tags: - test`，让 GitLab SaaS Shared Runner 自动接管。Shared Runner 不需要指定标签即可匹配。

```yaml
# ❌ 错误：指定了不存在的标签
构建后端镜像:
  tags:
    - test

# ✅ 正确：删除 tags，使用 Shared Runner
构建后端镜像:
  # 不需要 tags
```

---

### Bug 2：Docker Hub 基础镜像拉取超时

**现象**：

```
ERROR: failed to do request: Head "https://registry-1.docker.io/v2/library/python/manifests/3.12-slim":
dial tcp 69.63.186.31:443: i/o timeout
```

**根因**：

GitLab SaaS Runner 部署在国内（上海，Artifacts 存在 `cos.ap-shanghai.myqcloud.com`），而 `docker.io`（Docker Hub）在国内被 GFW 屏蔽，直接从 Runner 访问会超时。`python:3.12-slim`、`node:22-alpine`、`nginx:alpine` 这些基础镜像全部托管在 Docker Hub 上，所以 `docker build` 第一步 `load metadata` 就卡死了。

**修复**：

给 `docker:dind` 服务添加 `--registry-mirror` 参数，使用国内 Docker Hub 镜像加速器：

```yaml
# ❌ 错误：直接连 Docker Hub
services:
  - docker:dind

# ✅ 正确：配置国内镜像加速
services:
  - name: docker:dind
    command:
      - "--registry-mirror=https://hub-mirror.c.163.com"
      - "--registry-mirror=https://docker.m.daocloud.io"
```

> **注意**：`ghcr.io`（GitHub Container Registry）不受 `--registry-mirror` 影响，因为它不是 Docker Hub。`wild-server/Dockerfile` 中引用的 `ghcr.io/astral-sh/uv:latest` 走的是 GitHub 的线路，在国内通常可以访问只是较慢。

---

### Bug 3：`pip install uv` 下载极慢

**现象**：

```
Downloading uv-0.11.33-py3-none-manylinux_2_17_x86_64.manylinux2014_x86_64.whl (22.2 MB)
# 下载速度只有几十 KB/s，持续数分钟
```

**根因**：

pip 默认从 `pypi.org` 拉取包，跟 Docker Hub 一样在国内访问慢。`后端语法检查` job 中用 `pip install uv` 安装 uv 包管理器，不走 Docker 镜像加速，直接访问 PyPI 官方源。

**修复**：

给 pip 指定阿里云 PyPI 镜像源：

```yaml
# ❌ 慢：默认 PyPI 官方源
- pip install uv

# ✅ 快：阿里云 PyPI 镜像
- pip install uv -i https://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com
```

### Bug 4：DinD 服务启动失败 — 变量未展开

**现象**：

```
Service container logs:
Status: invalid argument "${REGISTRY_MIRROR}" for "--registry-mirror" flag:
invalid mirror: no scheme specified for "${REGISTRY_MIRROR}":
must use either 'https://' or 'http://'
See 'dockerd --help'., Code: 125

# 后续报错
Cannot connect to the Docker daemon at tcp://docker:2375. Is the docker daemon running?
```

**根因**：

GitLab CI 的 `services:command:` 字段**不支持变量展开**。写法 `${REGISTRY_MIRROR}` 被 `dockerd` 当作字面量字符串接收，而不是变量的值。Docker daemon 解析这个参数时发现它不是一个合法的 URL 格式，直接退出。DinD 服务挂了，后续 `docker build` 也就连不上 daemon 了。

这是一个 GitLab CI 的已知限制——`services:` 块在 job 的 shell 环境初始化之前就被处理了，所以 shell 变量不可用。

**修复**：

不要用变量，直接硬编码镜像地址：

```yaml
# ❌ 无效：变量不会被展开
services:
  - name: docker:dind
    command: ["--registry-mirror=${REGISTRY_MIRROR}"]

# ✅ 正确：直接硬编码 URL
services:
  - name: docker:dind
    command:
      - "--registry-mirror=https://hub-mirror.c.163.com"
      - "--registry-mirror=https://docker.m.daocloud.io"
```

### Bug 5：免费 Docker 镜像加速器速度不稳定

**现象**：

```
#10 sha256:42b50205... 9.44MB / 22.38MB 629.8s
# DaoCloud 镜像拉了 10 分钟才走了一半
```

**根因**：

免费的公共 Docker Hub 镜像加速器（DaoCloud、网易等）在高峰时段会严重降速，带宽可能降到只有几十 KB/s。这些镜像服务本质上是公益性质，没有 SLA 保证。

**修复**：

1. **配置多个镜像互为备份**：dockerd 支持多个 `--registry-mirror` 参数，按顺序尝试
2. **切换更快的源**：网易 `hub-mirror.c.163.com` 实测比 DaoCloud 更快
3. **终极方案（可选）**：把基础镜像手动推送到自己的 GitLab Container Registry，Dockerfile 改用自家仓库地址，彻底不依赖第三方镜像

```yaml
# 双镜像备份：网易（主） + DaoCloud（备）
services:
  - name: docker:dind
    command:
      - "--registry-mirror=https://hub-mirror.c.163.com"
      - "--registry-mirror=https://docker.m.daocloud.io"
```

### Bug 6：`docker build` 中 `uv sync` 下载 Python 依赖极慢

**现象**：

```
#6 [stage-1 5/6] RUN uv sync --frozen --no-dev --no-install-project
#6 0.885 Downloading uvloop (4.2MiB)
#6 0.885 Downloading openai (1.6MiB)
#6 1.168 Downloading tiktoken (1.1MiB)
# 卡住不动，持续数分钟
```

**根因**：

`uv sync` 默认从 `pypi.org` 拉取 Python 包，跟 Bug 2 的 Docker Hub 问题一样，在国内访问缓慢。之前在 `后端语法检查` job 中只修了 `pip install` 的镜像（Bug 3），但 **`docker build` 是一个独立的环境**，里面的 `uv sync` 不受 CI job 的 pip 配置影响。

**修复**：

在 `wild-server/Dockerfile` 中添加 `UV_INDEX_URL` 构建参数，默认指向阿里云 PyPI 镜像：

```dockerfile
# Dockerfile 中新增
ARG UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
ENV UV_INDEX_URL=${UV_INDEX_URL}
```

CI 构建时可以通过 `--build-arg` 覆盖：

```yaml
# .gitlab-ci.yml
- docker build
    --build-arg UV_INDEX_URL=${UV_INDEX_URL:-https://mirrors.aliyun.com/pypi/simple/}
    ...
```

> **关键理解**：`ARG` + `ENV` 的组合让 `UV_INDEX_URL` 在 `RUN uv sync` 执行时自动生效，不需要在 `uv sync` 命令中额外指定 `--index-url`。


### 总结：国内 GitLab CI 配置经验

| 问题类型 | 表现 | 一句话解法 |
|---|---|---|
| Runner 匹配 | job 卡住不跑 | 删掉不存在的 `tags` |
| Docker Hub 被墙 | `i/o timeout` | DinD 配 `--registry-mirror` |
| PyPI 慢（CI pip） | pip 下载 KB/s | `-i https://mirrors.aliyun.com/pypi/simple/` |
| PyPI 慢（Dockerfile uv） | `uv sync` 卡住 | Dockerfile 加 `ARG UV_INDEX_URL` + `ENV UV_INDEX_URL` |
| GitLab 变量不展开 | `${VAR}` 字面量传入 | `services:command:` 硬编码，不用变量 |
| 免费镜像不稳定 | 10 分钟拉不完一层 | 多镜像备份 / 推到自己仓库 |
