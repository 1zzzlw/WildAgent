## RAG 初始化方式评估（用户问「这算正规方式吗，能不能专门写个初始化类在生命周期里调」）

### 结论：一半对、一半不对

**做对的一半**：把网络 I/O 移出导入路径。`RAGSpecLoader(auto_sync=False)` 构造只做本地切分，
再由 `start_background_sync()` 起 daemon 线程做 embedding —— 这个判断是对的，注释也写明了理由
（`loader.py:1061-1063`）。若改成导入期同步，服务启动会被 embedding 超时卡数分钟。

**不对的一半**：构造 + 起线程仍是 **import 副作用**，而且这条链路**只有"起"没有"止"**。

### 证据

| # | 事实 | 位置 |
|---|---|---|
| ① | 全仓**没有** `AgentService.close()`，也没 `RAGSpecLoader.stop()`；`chromadb.PersistentClient` 永不开释，同步线程 daemon 不 join | `grep "def close\|def stop"` 只命中 generation_job_service / ws_heartbeat / ws_agent |
| ② | lifespan 已存在却故意不碰 RAG，`close_connect()` 只是打日志 | `main.py:32-50`、`main.py:63-65` |
| ③ | 唯一被生命周期管理的资源是 generation jobs | `main.py:49` → `shutdown_generation_jobs()` |
| ④ | 测试必须"先导入再打桩" —— 导入期副作用的典型症状 | `tests/agent/test_architecture_node_smoke.py:27+55`、`tests/repair/test_skeleton_blueprint_recovery.py:74`、`tests/repair/test_callback_targeted_repair.py:87` |
| ⑤ | `reload_chat_models()` 是"事后补的重建方法" —— 因为导入期定死、无法重新初始化 | `agent_service.py:1014` ← 症状本身 |
| ⑥ | 手写跨进程文件锁 `.wild_rag_sync.lock` 兜多 worker / dev reload | `loader.py:1186-1234` ← 补偿架构问题 |

### 🔴 顺带发现一个真缺陷（未修）

`_get_collection()`（`loader.py:2155-2198`）是无锁的 check-then-act：
```python
if self._collection is not None: return self._collection
...
self._client = chromadb.PersistentClient(path=...)
```
而它**被两个执行域共享**：daemon 同步线程（`sync_index` → `_get_collection`）与请求线程
（`_retrieve` → `_get_collection`，`loader.py:1650`）。并发首次进入时会各自建一个
`PersistentClient` 指向同一 `storage/chroma`。自启动后首次请求恰好撞上后台同步就会触发。
低概率、非致命（Chroma 内部对同路径 client 有缓存/文件锁），但属真 race。
→ 修法：`_get_collection` 内用已有的 `self._sync_guard`（RLock）包住，或改一次性预建。

### 用户提的"专门写个初始化类 + 生命周期调用"

**方向对，且已经完成 90%**：
- `RAGSpecLoader` **本身就是那个类** —— 它拥有 chunker + embedding + collection + 同步线程 + sync_status + 跨进程锁。
- `AgentService._create_spec_loader()`（`agent_service.py:1034`）**就是那个工厂**。
- 缺的不是"新写一个类"，而是把 `_create_spec_loader()` 从 `AgentService.__init__`
  搬到 lifespan、并补一个 `stop()`（停线程 + 释放 chroma client + 放锁）。

### 三种形态与代价

| 形态 | 说明 | 代价面 |
|---|---|---|
| 现状：import 单例 | 任何 import 都触发构造，无 teardown | — |
| A. lifespan 持有 | `app.state.agent_service` + `finally: stop()` | 所有 `from app.services.agent_service import agent_service` 调用点要改成取 `app.state`（ws_agent / planning.workflow / repair.workflow / config_api / main + 6 个测试文件） |
| B. 独立 `KnowledgeEngine` 类 + `Depends` 注入 | 显式 start/stop/status，AgentService 依赖注入 | 同 A，另加一层接口；收益是测试可完全脱离真实 KB |

⚠️ 纯重构，不解决任何功能缺陷（除 ⑥ 的 race）；与"跑真实链路验收"方向相反。
**用户只问了设计形态，未授权改动** —— 若要做，先定形态。

## 给用户的设计答复：他自己新项目（vibecoding）要的"正规 RAG 加载初始化"最小骨架

### 核心分界（已用双栏图讲）

**WildAgent 那份复杂度的大头不是 RAG，是运行时治理。**
左栏（第一天就写）：lifespan 里建 / finally 里关｜配置是类型化对象注入｜切分本地做完｜索引起不来就让启动失败。
右栏（逼出来了再加）：后台线程+退避重试｜跨进程文件锁｜集合签名保护｜活文件白名单｜查询改写·门控·trace。

### 推荐骨架（回答时给了完整代码）

- 一个 `KnowledgeBase` 类持有全部生命周期：`start()` / `close()` / `sync()` / `search()`
- `main.py` 的 `lifespan` 建它、存 `app.state.kb`、`finally` 调 `close()`
- 路由用 `Depends(get_kb)` 取，**不设模块级全局单例**
- 🔴 最容易踩的坑：**阻塞调用必须 `asyncio.to_thread` 包**（chroma / embedding 都是同步阻塞，
  直接在 async 路由里调会堵死事件循环）
- `sync()` 用"全量算 id → 与集合取差集"的最傻实现（文档几十~几百个毫秒级），
  语义与 WildAgent 的增量三集合完全一样，只是不带重试/锁/白名单
- chunker 起步用 langchain 的 `MarkdownHeaderTextSplitter` + `RecursiveCharacterTextSplitter`（~20 行）
  —— WildAgent 的 `MarkdownChunker` 900 行是它复杂度第二大来源，不必抄

### 推迟触发条件（回答里给了表）

| 能力 | 触发条件 |
|---|---|
| 后台同步线程 | 分片数千以上，或同步一次 > 10s |
| 跨进程文件锁 | 开始 `--workers N` 或多进程重载 |
| 集合签名保护 | 换 embedding 模型 / 改 chunk 参数后旧索引仍在被检索 |
| 活文件白名单 | 删过文档但旧分片仍被召回 |
| 查询改写·门控·trace | 检索质量开始"玄学"，需要证据定位 |

## 二、蓝图坐标语义（引擎会当真，写错就悬空/穿透）

- **墙**：`from[1]`=墙底、`to[1]`=墙顶（另有 `height` 字段则改用它）。转角两面墙**共用完全相同的端点坐标**（容差 0.01m）。
- **楼板**：`from[1]`=板底，`thickness` 向上增厚。**屋顶**：`position[1]` **必须等于承托墙顶**（gap>0.15 判悬空）；
  `span/depth` ≈ 承托墙跨度 + 0~2m 出檐；`roofType` 只有 6 个合法值。
- **门窗/开口**：`from = [沿墙距离, 开口底部世界Y, 法向偏移]`，底部 Y 必须落在宿主墙竖向范围内。
- 🔴 **构件 `from[1]` 语义不统一**：`balcony` 是**板顶**（板向下增厚）；`canopy` 是**板中心** → 用世界包围盒实测，别类推。
- **楼梯**：端点必须命中某层楼板标高（`from[1]+thickness`）或墙顶，且落在**楼板自身标高 ±0.25m** 内
  → 地面板写 `from[1]=-0.2, thickness=0.2`（板顶正好 0.0）。碰撞校验的楼梯 AABB 是**方形**（按 `width/2` 双侧膨胀）
  → 直梯贴外墙会判"穿插"，端点离墙内皮 ≥ 半梯宽 + 0.05。

## S1 + S2 实施（已交付，20:47）

**结论**：S0 之后"不够精细"的主因不是材质/字段/AO，是**曝光**。白天 33.6% 像素 ≥240、

**三个可计算的量**（把"发白/发闷"翻译成数）：`overexposureRatio`（≥240 占比，判"细节还在不在"的
唯一判据）｜`sky.blueBias`=B−R（"天被打白"的客观标志）｜`detailEnergy`（相邻像素亮度梯度均值）。
判据写**区间**不写死等值。工具：`.workbuddy/diag/lib/pngStats.mjs`（零依赖 PNG 解码，无 PIL）。
