## plan 链「分批合并 + 收尾归一」拆分（本轮，13:20–13:30）

按《动态节点设计规划》§3.3 / §4.4 把 merge 从"一条通吃"拆成两种作用域，对应上面那件"待他拍板"的事（`expand_plan` 与 §3.3 不一致）。他拍板语：**"继续吧，按照推荐的思路"**。

| 作用域 | 位置 | 做什么 | 不做什么 |
|---|---|---|---|
| `scope="batch"` | `assembly_workflow._merge_batch` | 用 `fragment_merger.merge_fragment_batch` 把这一组分片并入蓝图 | **不删不改**：无配额强制、无去重、无槽位吸附、无校验修复循环、无归一化 |
| `scope="final"` | `assembly_workflow._finalize_merge` | 配额强制 + 阳台去重 + 槽位吸附 + 校验→修复循环 + 交付归一化 | —— |

- 展开序列（`plan/expand.py`）：`generate_door_01 → merge_door_01 → generate_window_02 → merge_window_02 → merge_all_01 → validate_all_01`（条目数 N+2 → **2N+2**，11 类构件实测 **22 条**）。
- 🔴 **迭代预算必须另给下限**：`budget["iterations"] = max(档位值, len(items)+4)`（standard 档 12 → 26）。档位值是按旧形态标定的，条目翻倍后会**先于队列跑空触发收尾**，表现为"没跑完就交付"。
- `fragment_merger.merge_fragment_batch`：按 **`(id, type)` 先删后插**（§4.4 幂等，重跑不产生重复门窗——配额只查区间不查重复，重复会溜过验收）；只写蓝图副本，**不改 state 里的分片本体**（撞 id 时 `_insert_item` 加后缀，改到本体上下一轮会收集到脏 id）。
- 🔴 **批次合并必须保守**的原因：它跑的时候后面还有分组没到场，此刻按配额剔超额会剔掉还没生成的、按槽位补齐会凭空补缺的。

### 顺带修掉的三个静默缺陷（都是"测试全绿也照样丢产物"那一类）
1. **重试后新分片永远进不了蓝图**：`merge_all` 是 `done`，`refresh_statuses` 只推 `pending/blocked`、不碰终态 → 重跑出的分片被静默丢弃。
   → `store.refresh_statuses` 新增**下游失效**规则：上游未落定 → 已 `done` 的 `merge/validate/fix/repair` 退回 `ready` **并清 `run.state`**（只改 `status` 不改 `run.state` 会被 `poll_runnable` 的 `run.state != "succeeded"` 跳过 → 静默卡死）。
2. **收尾条目的上游口径错了**：全量校验/收尾合并的输入是"全部分片"，不是某几条 `depends_on`；否则 replanner 追加的分组生成完，收尾一直保持 `done`。
   → `store.upstream_ids`：收尾条目（`validate` / `is_final_merge`）的上游 = 全部 `generate` + 全部批次 `merge`（**只算生产条目**，否则收尾之间互相当上游会永远重开）。
3. **`ensure_artifact_consistency` 的重开是假的**：只 `set_status("ready")` 而 `run.state` 仍是 `succeeded` → 条目既跑不动也交付不了，只能等预算耗尽。
   → 改用 `reset_for_retry`（计一次尝试，有上界）。

### 对账口径（`plan/reconcile.py`）：只有收尾合并能判"产物没落地"
`_merge_has_run` 拆成 `_batch_merge_has_run`（该组的批次合并跑过没）与 `_final_merge_has_run`（收尾归一跑过没）。三档证据串：
`（等待合并）` → `（等待收尾归一）` → `（产物未并入蓝图）`（只有最后一档 `consume_attempt=True`）。
拿批次合并当判据会把"还没归一"（槽位吸附还没做）误判成"被删了"，白烧重试额度。

## 修「向上的时候门还会超模」（回应"能不能解决一下"，14:00–14:20）

根因：门扇是**刚体平板**，`setOpeningInteractionProgress` 只有"绕 Y 转"和"沿 `openOffset` 平移"两支，
**既不剪裁也不折卷**。3.6m 墙 + 2.5m 门按洞口高度抬 2.5m → 门顶到 5.0m，高出墙顶 1.4m，没有任何东西能遮，
真图上就是"一块灰板飘在屋面之上"（`docs/renders/lift-real/liftreal_front.png`）。

修法（一处，`wild-core/src/compiler/components/attachedToWall.ts::createOpeningInteraction` 的 `lift` 分支）：

```ts
const wallTop  = Math.max(frame.wall.from[1], frame.wall.to[1])   // ⚠️ WallParams 没有 height 字段，别去找
const headroom = Math.max(0, wallTop - (bottomY + height))
behavior.openOffset = [0, Math.min(interaction.openDistance ?? height, headroom), 0]
```

**关键洞察（这才是"够用"的原因）**：门扇写在**墙中线**（`from[2] = normalOffset = 0`），叶板厚 ~0.06m
≪ 墙厚 0.24m，于是升起后落进"洞口上方那块实心墙"高度带里的部分**被墙自己吃掉**。
所以钳到墙顶不是"牺牲效果"，而是**让墙的遮罩刚好完整** —— 视觉上正是一樘**从下往上收的半开卷帘门**：
洞口下半透空见室内，上半盖着门帘，立面干净。**渲染侧零改动**。

- 实测全仓 `wild-web/lantu/*.wild` **41 樘门 `normalOffset` 全是 0** → 该前提在当前数据里普遍成立。
  但它是**前提**：若给门写非零法向偏移，升起那半截会露在立面上。**别在 KB/提示词里鼓励给门写法向偏移**。
- 三种终态都对，别"修"：净空不足 → `Δy = headroom < height`（半开）；净空充足（矮门配高墙）→ `Δy = height`（整扇让开）；净空 0 → `Δy = 0`（看着仍关着）。
- ⚠️ 与 `overhang` 同型：蓝图里的 `openDistance` **不等于**实际位移，验收只能读编译后的 `openOffset`。
