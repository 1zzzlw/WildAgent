### 检索机制澄清（用户连问两个问题后定的原则）

**① 索引句对向量检索无用，且净效果为负。**
`RAGSpecLoader._retrieve` 是**纯向量检索**（`collection.query`，无 BM25），
切块按 `##`/`###` 标题（`MarkdownChunker`），命中单位是 **chunk 而非文件**；
每个 chunk 正文前会自动拼一行 `> 知识路径：祖先标题 > 当前标题`（`loader.py:561/574`），
所以**碎片自带导航**，不依赖文档结构。

**② 正文里出现文件名不会"顺带召回"那个文件。**
检索器逐 chunk 独立算相似度，**不解析正文里的文件名**，不存在"提到 B 就拉 B 进来"的机制。
唯一自动补齐是 `_expand_parent_neighbors`，只补**同一 `parent_chunk_id`（同文件同章节）**的相邻分片。
反过来：索引句里的"构件类型/参数/PRIMITIVES.md"等 token 会**抬高该空壳 chunk 的相似度**，
让它更容易挤进 `top_k`，**顶掉真正有内容的 chunk**——危害是"挤占"不是"引入"。

**③ 因此不建议把多文档合并成一份**：检索粒度是 chunk（按标题切），
合并后 chunk 数量与内容不变、召回基本不变，反而丢 `source_file` 元数据、
拉深标题层级（`## wall` → `### wall`）。真正影响召回的只有 **chunk 内容本身**。

**已按此删除**：SPEC.md 原 `### 3.2 构件类型定义` 整层（标题 + 索引句
"各构件类型的完整参数在 PRIMITIVES.md 中定义；本节只补充规范层面的特殊约定。"），
原 `#### 3.2.1` 提升为 `### 3.2 门窗组合构件的深度约定`。
（已确认 `3.2.1` 无任何外部引用。）SPEC.md 现 258 行，3.1~3.7 编号连续。

## L 形别墅屋顶缺失 —— 归因：知识库自相矛盾 + 缺反向校验（同日续）

用户给了一份 agent 生成的 L 形别墅蓝图与截图，问"屋顶处理不好，是代码还是知识库的问题"。

### 事实（可复现）
蓝图：主楼 X[0,10]×Z[0,8] + 侧翼 X[10,16]×Z[0,4]，两层（墙顶 6.4），**只有 1 个 roof 元素**
`roof_01 {roofType:gable, span:11, depth:9, height:3, position:[5,6.4,4]}` → footprint X[-0.5,10.5] Z[-0.5,8.5]。
平面是**一个闭合的 L 环（6 段外墙）**，主楼与侧翼之间**没有内墙分隔** → "有几个体量"是**形状分解问题**，不是查表。

新增审计脚本 `.workbuddy/diag/audit_roof_top_coverage.py`（顶层墙按环串起来 → 沿中线采样 → 算屋顶覆盖率）实测：
- 该蓝图：顶层墙 48.0m，屋顶只覆盖 33.3m（**69%**）。
  裸露 = `wall_right_2_2`(100%)、`wall_back_2_1`(88%)、`wall_front_2_1`(34%) —— **侧翼整块无屋顶**。
- 对照 `villa_modern_2f.wild`：42.0m / 42.0m = **100%**。
- 附带：主楼屋顶 +X 侧出檐到 X=10.5，而公共墙在 X=10 → **出檐伸进侧翼上空 0.5m**，
  且 gable 山墙端面（X=10.5）落在侧翼体积内部（截图里那块三角填充板就是它）。

### 归因（两个原因，性质不同）
1. 🔴 **知识库自相矛盾（直接诱因）**：`knowledge/components/capability-boundaries.md` §3.5
   把多体量分段屋顶写进了"**不能做**"：`❌ 复杂组合屋顶（需多个 roof 对象组合）`，
   而它带 `<!-- rag-meta entity_type: roof -->`、`doc_type=component`+`knowledge_role=capability`
   → **正好被"屋顶构件能力"查询命中**。已打印该分片正文确认：模型生成屋顶时拿到的就是这句。
   与之**正面冲突**的是 `knowledge/protocol/generation-redlines.md:31-32`
   「多体量（L 形 / U 形 / 退台）各生成一块屋顶」，而该文件在 `BASE_SPEC_PATHS` 里**每轮全量注入**。
   模型选错了那一份 —— 大概因为 capability 那份 `authority: engine`、且是"能/不能做"表格式，看起来更硬。
2. 🔴 **缺反向校验（漏网原因）**：`validate_roof_coverage` 是**单向 roof→wall**，
   从不问"这些顶层墙上面有没有屋顶"。所以实测 **10 个校验器 + 知识库红线全 PASS**，没有任何环节会拦。

  `generation-redlines.md` 那条从 span/depth 的子句提升为独立条目并给出**体量判定步骤**（否则模型不知道怎么数）。
