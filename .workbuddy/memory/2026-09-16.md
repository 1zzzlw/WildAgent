## 屋顶板厚修复（同日晚，已落地）

用户最终锁定唯一需求：**屋顶要有板厚、要有檐口，其他都不重要**。

**改动**：`wild-web/src/wild-core/src/primitive/geometry/roof.ts` —— 重写 `buildGable` / `buildHip`，新增 `pushSolidTriangle`（跳过退化三角形，防 `computeVertexNormals` 出 NaN）。

**关键设计约定（务必记住）**：板厚必须**向下**增厚。因为编译期 `wild-compiler/components/attachedToSurface.ts:137-143` 的 `roofSurfaceHeight()` 把 gable/hip 的**屋面外表面**定义为「檐口 y=0 → 屋脊 y=height」这条平面（flat 则返回 `thickness`）。檐口(`cornice`)、烟囱(`chimney`) 都靠它定位；若向上增厚，屋面抬高 thickness，附件会相对下沉一个板厚。新几何：屋面(顶面)檐口 y=0→屋脊 y=h；底面檐口 y=-t→屋脊 y=h-t；檐口立板高 t。

**顺带发现并修掉的两个隐藏 bug**（只"补厚度"必踩）：
1. 双坡端面的板厚截面是「雪佛龙带」= **凹多边形**，用单顶点扇形三角化会把缺口外也填上 → 边界边无法成对闭合（30 条边只 18 配对）。必须拆成左右两半四边形 `[A,B,E,F]`+`[B,C,D,E]`。
2. 四坡的坡面归属**随屋脊走向互换**（屋脊沿 Z→山面在 ±Z；沿 X→山面在 ±X）。原先两分支硬合并成一张面表，`hd<hw` 的窄深屋顶体积只有正确值的 1/6。

**验证**：新增 `.workbuddy/diag/verify-roof-solid.mjs` —— 校验水密性（每无向边恰 1 正 1 反）+ 欧拉示性数 `V-E+F=2` + 体积 == `t×span×depth`。13 用例（6 合成 + 7 真实蓝图）全绿，体积全部精确吻合。回归 `check:core` / `check:compiler` / `check:rendering` 三项通过，`vue-tsc` 对 roof.ts 无报错。

**注意**：`check-wild-core.mjs:160 assertRoofMesh` 只硬断言 **flat** 屋顶局部包围盒（`localMax.y=thickness`），gable/hip 无边界快照，故改动不触发既有断言。

**产出**：`docs/前端渲染链路差异诊断报告.md` 新增「〇、修复记录」章节，🔴1/🔴2 标记为已修复，优先级表加「状态」列。

**仍未修（用户明确说"其他都不重要"）**：世界法线着色器 bug（`defaultSurfaceMaterial.ts:88-95`，仅开雪/沙尘时影响明显）、取景算法不统一、白天投影强度 0.17、阴影脏标记竞态。

## 屋顶端面"变空心"回归修复（同日晚）

用户发截图问「为什么变成这样的了」——山墙端头能看到室内。

**根因**：上面那轮把双坡端面从「完整三角面」改成了「板厚窄带（雪佛龙带）」。但旧 `buildGable` 其实是个**实心三棱柱楔**（两个山墙三角面 + 两个坡面 + 底盖 y=0），它的**山墙三角面顺带承担了"封闭建筑端头"的职责**；而蓝图 `simple_villa.wild` 只有 4 面矩形墙、**没有任何山墙墙元素**，端面一收窄，墙顶以上的阁楼三角区就整片敞开。

**量化**（新增三个脚本）：
- 端面覆盖：旧 100% → 中间版 **19.3%** → 修复后 **100%**（`analyze-gable-end.mjs`，在 z=±hd 平面对山墙三角区做网格采样）
- 穿透检测：中间版阁楼区 685 个采样点 **685/685 穿堂而过**（射线沿 Z 平行射入，只会遇到斜面与两端窄带，于是从正面进、背面出，一帧面都不命中）→ 修复后 **685/685 封死**（`detect-hollow.mjs`）

**最终实现**：双坡改成**凸五边形截面沿 Z 拉伸的闭合实体**，截面 `(-hw,-t) → (hw,-t) → (hw,0) → (0,h) → (-hw,0)`。上两边=屋面外表面（契约不变），下边=水平板底 `y=-t`，两竖边=檐口立板，**`z=±hd` 的端面就是这个五边形本身**，山墙天然封死。端面从 p0 扇形剖分成 3 个互不重叠的三角形即可（凸多边形，不再有第一轮那个凹多边形扇形化坑）。

**代价与取舍**：双坡屋面从"薄板壳"变成"实心楔"（阁楼被填实）——这其实是**旧实现的原始形状**，只是底盖从 `y=0` 下移到 `y=-t`，所以观感与旧版一致，只是檐口多出 t 高的可见厚度。四坡（hip）保持薄板不动（它四个坡面本来就自封闭，没有空洞问题）。

**验证全绿**：`verify-roof-solid.mjs` 13 用例（gable 现 16 面 / V-E+F=2 / 水密 24/24 / 体积 = `(span·h/2 + span·t)×depth` 精确吻合）；新增 `check-coplanar.mjs` 未发现共面重叠（屋顶 16 面 vs 其余 1230 面）；`check:core`/`check:compiler`/`check:rendering` + `vue-tsc -b` 全通过。

**工具（`.workbuddy/diag/`）**：`diag-roof.mjs`、`verify-roof-solid.mjs`、`analyze-gable-end.mjs`、`detect-hollow.mjs`、`check-coplanar.mjs`、`depth-ascii.mjs`（ASCII 深度图 + 面归属图，**在没有浏览器、也看不了图片的环境里靠字符画肉眼判读几何**，这条以后很值得复用）、`render-preview.mjs`（软件光栅化出 PNG）。

**经验（重要）**：屋顶几何的职责边界里**包含"封闭建筑端头"**。做"技术正确的最小板厚截面"会破坏建筑封闭性——不要只看单个 mesh 是否水密，还要跑一次"穿透检测"看从外面能不能看进室内。

## 渲染引擎优化方向 + 参数边界分析

用户反馈"效果还是不好"，并担心"渲染引擎优化会不会改动参数 → 后端和知识库也要改"。

**结论：绝大多数渲染引擎优化不动参数。** 用代码证据划清了边界：

**参数边界（关键事实）**
- `.wild` 顶层是**封闭**的：只有 `meta`/`geometry`/`materials`/`behaviors`，规范原文「禁止在根级别出现 elements、bounds 或其他字段」（`wild-server/storage/knowledge_base/BLUEPRINT-SPEC-MINIMAL.md:20-32`）。
- **相机/时间/环境/天气/画质根本不在 `.wild` 里**：世界文档走独立 `wild.world` 且只存 localStorage（`renderer/worldDocumentPersistence.ts:5` 键前缀 `wild_world_document_v1:`）；时间档/画质档/相机预设/环境预设全是前端常量表（`renderer/defaultWorldLook.ts:63-123`）。
- **本次屋顶修复是零参数改动**：`roof.thickness` 早在知识库 `BLUEPRINT-SPEC-MINIMAL.md:94-112` 就有，问题一直是 `wild-core` 没读它。
- 后端校验是**轻量级**的，**不拒绝未知字段**（`wild-server/app/utils/blueprint_parser.py:631-635`）。
- 项目**已有**"渲染层私有数据"通道：下划线前缀字段，如 `_interaction` / `_doorLeafDetail`（`wild-core/types.ts:384-392`，注释明确写"仅供组合编译器和 renderer 使用，不属于可手写的 WILD opening 字段"），以及 `_gableEnds`。

**三类改动波及面**：A 纯渲染实现（不动任何契约）／B 新增下划线私有字段（只加可选类型）／C 改契约参数（才需四处同改：KB 文档 + 生成提示词 + 前端类型 + 后端校验）。渲染引擎优化 90% 是 A 类。

**现状实测（`material-impl-histogram.mjs` 新建）**：simple_villa 62 网格中 **55 个、95.8% 面积走 `surface.default.v1`**（纯程序化 UV 图案，无贴图/法线/粗糙度细节），仅 4.2% 走 `surface.pbr.v1`。剪影阴影实际不透明度约 **0.17**（0.22 × worldLook）。`antialias:false` 只靠 FXAA。地面本体 `receiveShadow=false`，阴影靠透明 `ShadowMaterial` 叠层。

**更正上一份报告的高估**：`defaultSurfaceMaterial.ts:103` 的世界法线 bug 确实存在（`<defaultnormal_vertex>` 后 `transformedNormal` 已是视图空间，再乘 `modelMatrix` 无意义；正解 `inverseTransformDirection(transformedNormal, viewMatrix)`，且漏 `instanceMatrix`），但它**只被天气遮罩使用**（雨丝竖直遮罩 / 积雪积尘朝上遮罩），核心光照用 three.js 自己的 `normal` → 晴天几乎无影响，应从 🔴 降为 🟡。

**优化方向（全部 A 类，零参数改动）**：🔴1 恢复落地感（阴影不透明度或地面 receiveShadow，二选一避免双重变黑）／🔴2 统一取景工具并抬高俯角（编辑器 ×1.55 + corner[1,0.62,1] → 俯角约 24°，偏低偏近易看到屋面底面）／🔴3 材质质感（96% 面积是纯程序化图案，这是"精致度"主战场）／🟡4 抗锯齿／🟡5 SSAO 默认开／🟡6 实体白名单开 FrontSide／🟡7 世界法线／⚪8 阴影脏标记原子化。

**"屋顶还是不好"的两个嫌疑点都不在渲染参数上**：坡比 `2.9/(11.6/2)=0.5` → 约 26.6° 偏扁（属**蓝图数据**）；`roof_tile` 走 `surface.default.v1` 无贴图细节（属**材质实现**）。两者都不需要动知识库。

**产出**：`docs/渲染引擎优化方向.md`（参数边界分析 + 现状盘点 + 分层优化方向 + 落地顺序）；新建 `.workbuddy/diag/material-impl-histogram.mjs`（材质实现面积占比盘点，判断修复收益用）。

## P2 表面凹凸层落地（surface.default.v1，纯 A 类）

用户选定 P2 后开工。**只改 1 个文件**：`wild-web/src/renderer/materialFeatures/defaultSurfaceMaterial.ts`。

**动工前的关键实测（决定了整个设计，务必记住）**
用新建的 `.workbuddy/diag/material-family-report.mjs` 盘点了 `simple_villa.wild`（62 网格 / 809.03 m²）：
- `roof_tile` 282.98 m² / 35.0% → family **masonry**（名字含 tile 被 `descriptor.ts:90` 的正则归到 masonry！）
- `wall_stucco` 232.13 m² / 28.7%、`floor_concrete` 193.02 m² / 23.9% → **mineral**
- `frame_metal` 34.77 m²（38 网格）、`wood_door`+`wood_dark` 18.42 m²、`brick_red` 11.76 m²
- 族面积：mineral 52.8% / masonry 36.4% / metal 4.3% / glass 4.2% / wood 2.3%

**蓝图的 UV 约定是混合的（重大发现）**
- 建筑表面走 `generateArchitecturalSurfaceAttributes`（`mesh-helper.ts:104-153`）→ **按米展开**的逐面投影：`roof_tile` u −5.80..5.80、`wall_stucco` u −5.12..5.12
- 但 `floor_concrete`、`brick_red`、`frame_metal`、`wood_dark`、`stone_cap` 都是 **归一化 0..1**（走 `generatePlanarUVs`，`mesh-helper.ts:77`）
- ⇒ **凡是"物理尺寸敏感"的图案都不能依赖 UV**。砖缝改用世界坐标按主法线轴投影成米制坐标。

**踩坑与设计决策（改这里前必读）**
1. `FAMILY_CODE` 里 `mineral` 与 `masonry` **原本共用 code 1**，着色器无法区分灰泥与砖瓦 → 给 masonry 追加 code 5（不动 0-4 含义）。
2. three 的 `perturbNormalArb` 被 `#ifdef USE_BUMPMAP` 包住（本材质无 bumpMap）→ 必须内联一份。
3. **不能照抄 three 的 `normalize(dFdx(surf_pos))`**：那是为贴图尺度无关设计的；对程序化高度场会让凹凸强度随像素密度漂移。未归一化时扰动角恰等于真实坡度（米/米），与分辨率无关。
4. `normal` 到 `normal_fragment_begin` 才声明，而 `roughnessmap_fragment` 在它之前 → 高度场放在 `map_fragment` 处算，用 `inverseTransformDirection(vNormal, viewMatrix)` 还原世界法线（`viewMatrix` 在 three 片元 prefix 里有声明，已核）。
5. WebGL1 无反导数扩展 → 全段包在 `#if __VERSION__ >= 300 && !defined( FLAT_SHADED )`（three 在 WebGL2 下输出 `#version 300 es`，已核 `three.module.js:20215`）。
6. 复用已算好的 `wildDefaultDetail`（fbm，含 0.15m~4cm 多倍频）当第二尺度，新增开销仅 1 次 valueNoise + 1 次 hash + ~20 ALU。
7. 所有族**共用同一个 GPU program**（`customProgramCacheKey` 是常量），族差异全靠 uniform 分支 → 砖缝分支在源码里始终存在，测试不能断言其"不存在"。
8. 第一版参数（mineral 峰值仅 3.3°）实测等于没做，已调到中位 2.0° / 峰值 7.1°；masonry 块面原本全平，补了沿进深方向的叠压微倾。

**实测数值（medium 档，最终参数）**：masonry 中位 1.2°/95分位 28.2°/峰值 54.4°、淡出 79m；mineral 5.2/11.0/22.0/43m（细级 13m）；wood 6.0/12.7/24.4/32m；metal 3.2/6.8/13.1/26m；neutral 4.5/9.5/17.0/43m。`RELIEF_PRESETS` 最终值：masonry 0.009/6、mineral 0.012/12、wood 0.010/16、metal 0.004/20、neutral 0.010/12。

**迭代两次才成型（第一版是废的）**
- 第一版 mineral relief 0.006 / 单倍频 freq 6 → 峰值仅 3.3°，实测等于没做；且 6 cycles/m 配合 LOD 在 20m 就淡掉。

用户指令："直接全量进行优化吧"。剩余四项全部处理完。

### P3 抗锯齿 —— 先纠正了认知误区
**`antialias: false` 不是"漏开的开关"，改成 `true` 也完全无效**：主光栅化走 `EffectComposer`，
场景渲染到**离屏 RT**，而 `WebGLRenderer.antialias` 只对 canvas 默认帧缓冲生效（那里只贴一张全屏四边形）。
唯一正确位置 = 给合成离屏 RT 开多重采样。

- `CanvasViewport.vue` 新增 `applySceneMsaa(samples)`：对 `composer.renderTarget1/2` 同时设 `samples` 并 `dispose()`。
- **`samples` 是普通属性，已建好的帧缓冲必须 `dispose()` 才会按新采样数重建**（`RenderTarget.js:47/62` 只有裸赋值，无 setter 副作用）。
- **两个 RT 都要开**：`EffectComposer.render()` **不在每帧重置读写缓冲**，靠 `needsSwap` 累积交换。
  本链路 RenderPass(false) → SSAO(true) → Bloom(**false**) → OutputPass(true) → FXAA(true)
  ⇒ **每帧净交换 3 次（奇数）**，RenderPass 落点逐帧在 RT1/RT2 间交替。
- **MSAA 确实有用的证据**：`SSAOPass.js` 的 `OUTPUT.Default` 分支用 `readBuffer.texture` 作底图再乘 AO
  ⇒ RenderPass 写进 RT 的着色结果就是最终画面底图（不是被 SSAO 重渲覆盖）。
  （`SSAOPass` 只自建 `normalRenderTarget`/`ssaoRenderTarget`/`blurRenderTarget`，**0.160 已无 `beautyRenderTarget`**）
- 默认 4x；WebGL1 自动回落 0；帧率降级路径同步降到 2x。FXAA 保留为最后一道（管 MSAA 覆盖不到的高频细节）。
- 安全性核对：`deallocateRenderTarget` 无 `!== undefined` 保护，但 `deleteFramebuffer(undefined)` 经 WebIDL 转 null 是无害 no-op；且未使用过的 RT 上根本没有 dispose 监听器（监听器在 `setupRenderTarget` 里才挂）→ 首次设置 samples 时 dispose 是纯 no-op。

### P6 世界法线 —— 实为"相机相关"的真 bug，不只是"空间混用"
- 旧：`mat3(modelMatrix) * transformedNormal`；新：`inverseTransformDirection(transformedNormal, viewMatrix)`。
- `#include <defaultnormal_vertex>` 结束时 `transformedNormal` **已在视图空间**（且已折入 `instanceMatrix`）。
- **关键**：绝大多数构件 `modelMatrix` 近似单位阵 ⇒ 旧代码拿到的其实是**视图空间法线** ⇒
  `wildVerticalMask = 1 - |n.y|`（雨丝）与 `wildUpward = smoothstep(0.28, 0.82, n.y)`（积雪/积尘）
  **会随相机轨道旋转改变** —— 转视角，屋面的雪忽有忽无。
- 仅影响天气遮罩；核心光照走 `normal` 属性，不受影响。
- 加了 `#ifdef FLAT_SHADED / #else` 守卫（FLAT_SHADED 下 `transformedNormal` 未声明；回退 `normalMatrix * objectNormal`）。
- **回归锁**：`verify-surface-relief.mjs` 新增 `vForbid` 反向断言。
  ⚠️ 踩坑：断言最初直接扫源码，被我自己写的"旧实现是 `mat3(modelMatrix) * transformedNormal`"**注释**误判 →
  改为**先剥掉 `//` 与 `/* */` 注释再查**。

### P7 阴影脏标记 —— 两种真实失效，不是"理论风险"
`markShadowsDirty()` 追加 `markNeedsRender()`。原因：
1. `shadowMap.needsUpdate` 只在**下一次 `renderer.render()`** 消费并清零（`autoUpdate=false`）；
   只置位不请求渲染 ⇒ 队列无可渲染帧时标记**永远悬空**，移动物体后阴影不跟随。
2. 已有帧在排队 ⇒ 可能在本 tick 几何/变换写入落地**之前**执行并清零 ⇒ 按旧姿态烘焙且不再补算。
- **必须同时置 `needsRender`**：只 `scheduleRenderFrame()` 的话 `renderFrame` 会因 `if (needsRender && ...)` 跳过渲染，标记照样悬空。
- rAF 回调在所有同步写与微任务（Vue watcher）之后执行，故"置位 + 请求渲染"即原子。

### P5 面剔除 —— 新建审计工具后被数据彻底证伪（结论：不做）

  （通过的恰好是 window_frame/oak_furniture/glass 这类低面数轻量件）。

## P8 生成结果居中归一化（用户反馈："每次生成蓝图位置不在中心点，有点偏移"）

### 根因：两个坐标系没对齐（不是相机错，也不是参照物错）
- 相机 `frameCameraToBounds()` 的 target 是**包围盒中心**
- 网格 / 地面 / 内置环境钉在**世界原点**（`gridHelper` 只在 y 上跟随包围盒，x/z 恒为 0）
- 生成器产出的是**"角点对齐"坐标**（`x` 0..11.5 而不是 -5.75..5.75）⇒ 两者必然错开

**实测**（新建 `.workbuddy/diag/audit-centering.mjs`，7 份样例蓝图）：
- 足迹中心偏离原点 **5/7**，超 0.5m 的 4/7，平均 **1.939m**，最大 **6.449m**（`generated_modern_villa`）
- `generated_modern_villa` 归一化前 x 跨 **-0.5~11.5**，直接捅出 20×20 网格（±10）—— 与截图里"建筑探出网格"一致

### 修法：纯显示层归一化（A 类，零参数/零契约/零文档改动）
- 编辑器 `CanvasViewport.vue:updateScene()`：`sceneGroup.position.set(-center.x, 0, -center.z)`，
  **紧接着把 `center.x/z` 归零** → 下游所有"以中心为参照"的逻辑自动改正
  （`updateLightingToBounds` 方向光与阴影相机、`sceneBoundsCenter`→内置环境、`frameCameraToBounds`）
- `resetSceneBounds()` 里补 `sceneGroup.position.set(0,0,0)`，避免空场景继承上次偏移
- 查看器 `lantu/viewer/main.ts:frameToBox()` 同样归一化；并把初始 `controls.target` 从
  硬编码 `(5.5, 3, 3)` 改成 `(0, 3, 0)` —— `5.5` 恰是 `generated_modern_villa` 的中心 x，
  那是针对某份蓝图的手工补偿，归一化后反而把默认视角指向了不存在的位置
- **Y 不平移**：`gridHelper.y = bbox.min[1]` 让网格贴建筑自身地面，Y 一并归零会让两者脱开

### 为什么这样最安全（改动边界已核实）
- 拖拽 `handleTransformObjectChange` 改的是对象**局部** `position`（平移不因父级平移失效）
- 保存读的是文档：`createEditorWorldDocument` 里实例 transform 写死 `[0,0,0]` ⇒ 归一化不泄漏进 `.wild`
- `BlueprintRenderInstance.update()` **只**调 `updateSceneGroup`，**不重置 root transform**；
  `ensureInstance` 全项目只在 `CanvasViewport.vue:443` 调一次 ⇒ 每次赋值的归一化不会被冲掉
- 相机每次生成都会重新取景：`loadBlueprint` 建**新** `document.id`（`scene_${Date.now()}`）
  → 触发 watcher 把 `hasFramedScene=false`；且 `reconstruct()` 有 `await`，
  赋值落在后续微任务 ⇒ 顺序上必然"先重置标记、后 updateScene"，不会用旧包围盒取景

### ⚠️ 本机踩坑：`lantu/**` 不在类型检查范围内
`tsconfig.app.json` 的 `include` 只有 `src/**/*`，所以改 `lantu/viewer/main.ts`
**不会被 `vue-tsc -b` 发现**。用 `ts.transpileModule`（TypeScript 编译器 API）单独校验语法；
也可用 vite `transformRequest` 但那要能解析别名（`wild-compiler` 在 vite.config 里配了 alias，
临时起的 server 若没带上 config 会报 resolve 失败）。

### 验证
新建的 `audit-centering.mjs` 第二部分复算归一化后的世界空间，逐蓝图断言：
足迹中心回到原点 / 仍在网格覆盖范围内 / 光照参照中心落在足迹内 / 无 NaN —— 7 份全部通过。
全量回归 9 项全绿（vue-tsc + 3 个 check + verify-roof-solid + verify-surface-relief +
audit-centering + audit-winding + material-family-report）。

1. **L1 夜晚主光在地平线下**：`night.sunPhi=108°` → `sunDirection.y=-0.309`；

   夜晚取 `-sunDirection`，只给主光/阴影相机用，天空与日月实体不动。
2. **L2 阴影正交框/far 不足**：`lightingExtent = max(maxDim*0.68, 4)` 忽略了

3. **L3 滑杆→PMREM 无上限重建**：`el-slider @input` → store → `subscribeWorldEnvironment`

   实测 60 个连续事件 = 59 次 fromScene + 59 次 dispose。
4. **L4 “SSAO 半分辨率”未生效**：`SSAOPass` 构造的 `0.5, 0.5` 是**像素尺寸不是比例**，
   且 `SSAOPass.setSize` 无缩放语义（`SSAOPass.js:313-328`），被 `composer.setSize` 全量覆盖 → 实际全分辨率。
   可安全减半：0.160.1 的 `OUTPUT.Default` 以 `readBuffer.texture` 为底图，只叠加 AO 项。
   修法：包装 `ssaoPass.setSize` 缩放入参（其内部会同步 resolution uniform，自洽）。
5. **L5 `shadow.radius = 4` 是死配置**：`shadowmap_pars_fragment.glsl.js` 里 `shadowRadius`
   只在 `SHADOWMAP_TYPE_PCF` 分支（:122-125）被引用，`PCF_SOFT`（:151+）用固定 9 抽样、不读它。

6. **L6 夜间 Bloom 无输入**：Bloom 在 OutputPass 之前 = 线性 HDR，阈值 1.05；

拖动构件时阴影节流 120ms 有拖尾；`normalBias = extent*0.0015` 等价于“2048 档专用”

初稿对**光方向自身**也套了 12° 高度角下限，但光位置仍用真实 6° ⇒ 落影按 6° 走（104m）而 `far` 按 12° 算（51m），长影照样被切。
正解是**不改光方向**（否则落影与天空里的太阳对不上），只让 `far` 按真实高度角放大。
**教训：任何"值的下限/钳制"落地时，必须逐一检查该值被用在哪几处、是否全都用同一份钳制后的值。**

其他踩坑：
- 落影点求交 `t = -c.y/dir.y`（符号错会让落影点跑到建筑上方，far 需求算成 48 而实际 143）。
- `shadow.bias` 是**归一化深度**偏移，等效世界偏移 = `|bias|×(far-near)`；把 far 从 55 拉到 207 后必须同改，否则 Peter-panning。
- 门槛脚本自己也会撒谎：`configured` 若在脚本里硬编码，就会被"代码改了但脚本没改"糊过去 ⇒ 已升级为对源码做实现契约断言。

**暂缓（有明确理由，不是遗漏）**：L8 空气透视会改所有场景整体观感，应与界面精致化一起定调；
L6(b) Bloom 阈值应先有 G1 的可泛光内容再调，否则只会让受光面发糊。

## 檐口定性：用户问"屋顶没屋檐厚度"是引擎问题还是 .wild 问题

**结论：两者都不是 bug。** 渲染层无责；主要责任在 `.wild` 没用既有 `cornice` 契约，次要责任在 `roof.ts` 的能力缺口。
→ 报告：`docs/渲染引擎优化/屋顶檐口定性报告.md`

**量化事实（`simple_villa.wild` / `roof_main` gable，span 11.6 × depth 9.8 × height 2.9 × thickness 0.2）**

- 檐口立板**存在**：两侧竖直立面世界 Y`[3.00..3.20]`，可见厚度 = `thickness` = **0.20m**

- 屋顶整块 `tri=16`、**只发 1 个 mesh / 1 个 `materialRef=roof_tile`** ⇒ **山墙端面（z=±4.90 五边形，高 3.10m）也是砖红瓦色**，对"简陋"的贡献比檐口更大
- `geometry.components` 里 **`cornice` = 0 个**；`roof_tile` 是纯色 `surface.default.v1`（无瓦面纹理）
- 看不出厚度的真因：**檐口与屋面同色同材质** + 0.2m 太薄 + 平底 + 山墙瓦色

**契约层关键发现**：`cornice`（截面沿路径扫掠）**早就是 WILD 既有契约**，不是缺失能力。
`WILD_BLUEPRINT_SPEC.md` §5 组件表 / §5.4；实现 `wild-compiler/components/cornice.ts`，走 `primitive.profile_sweep`。
⇒ 档 1「只改 .wild 补 cornice」**零代码**可行；但 `profile` 的 u 轴 = **行进方向的右侧**（`primitive.ts:252-259`），绕檐必须统一绕向。

- **可见檐口厚度 0.200 → 0.360**；山墙端面由砖红瓦色 → 墙色（覆盖到屋脊）
- 线脚体积实测 3.3264 m³ == 独立解析值 3.3264

**关键设计（不要退化）**
1. **`_eave` 不存在 ⇒ 完全不生成线脚**，输出与历史一致（"无墙回退"用例双重保护）。
2. **不能把山墙端面从屋面实体拆走** —— 端面是闭合的必要面，拆走会漏水 + 逐分量 χ 失败。正解：保留端面 + 叠加向外偏移 `panelGap`(2mm) 的独立薄板。
3. **博风板 Λ 形带在脊点是凹点，必须耳切**；Δ面积恒等式可验：Λ 带面积 = `span × drop`。
4. 共面即 Z-fighting：封檐板向屋面内侧 `embed`，滴水线塞进封檐板内部，饰面板留间隙。`check-coplanar.mjs` 是这条的守门人。
5. 审计里 `analyzeSolid` 吃**局部坐标**、预览脚本吃**世界坐标**，必须显式传 `toWorld`（否则"檐口最低点"会算成 3.59 而不是 0.39）。

## 中式曲面屋顶三层归因（档 2 的覆盖缺口 + 两个更深的 bug）

用户拿来 `中式意境别墅：L形体量高低错落，曲面屋顶飞檐起翘… .wild`（`roofType = chinese_curved`），
质问三件事：为什么档 2 完全没生效、这种问题不是该屋顶引擎处理吗、有没有违反「不要为特殊功能写专用逻辑」的约定。
结论写成 `docs/渲染引擎优化/中式曲面屋顶三层归因与通用檐口方案.md`。

**L1 直接原因**：`roof.ts:9-10` 两条中式屋顶**早返回**；`roof.ts:37` 与 `resolver.ts:260` 双闸门都只认 `gable || hip`
⇒ `chinese_curved` 从来没被覆盖到。**三处同向闸门。**

**L2 屋顶自身（引擎几何 bug）**
- `chinese_curved` 壳体 **52 条未配对边**，全部落在 `x = ±hw` 的檐口封边（封边与相邻表面**同向**而非反向）
- 两半绕序相反（`quad(..., side === -1)` 把镜像已翻转的手性又翻一次）⇒ 四个面组各自"朝上/朝下"精确对半，
  散度体积 **−12.80（负）**
- 主网格与 `buildPagoda` 都**不产出 `normals`**，落到 `meshDataToGeometry.ts:44` 的 `computeVertexNormals()`；
  恒等索引零顶点共享 ⇒ 只能逐面平面化 ⇒ 举折面折线化、起翘处硬折
- 有起翘（角部抬 0.54m）但**无出檐**、无封檐板/博风板 ⇒ 观感是一块深色薄片
- 当前材质 `DoubleSide` 所以不破洞，但**开背面剔除就会破洞** ⇒ 先修几何

**L3 灰板根因（resolver，最隐蔽）**：`resolveRoofBoundary` 的"结构墙"闸门用
**单段墙高 ≥ 全局最大墙高 × 50%**。该蓝图 16 面外墙各只有 3.2m（按层切段），贯通 1F~3F 的核心筒是单段 9.6m
⇒ 闸门把 16 面外墙**全部滤掉**，结构墙塌缩成 5 面混凝土核心筒墙。后果：
1. `_gableEnds` 只剩核心筒的 2 段（Z=4.5/8.5，X 4~8）⇒ 端部只填中间 4m，
   从正立面看屋脊下露出 4m 宽混凝土板 = 用户截图那块灰弧
2. `dominantMaterialOf` 取到 `concrete` 而非 `wall_finish` ⇒ 檐口饰面上错色
3. `simple_villa.wild` 外墙本身就是整段高墙，闸门不误杀 ⇒ **只拿它当样本会完全绕过此 bug**

**约定自评**：分类纪律守住了（B 类、零契约改动、没另开文件），但 **§八 第 1 条「通用性优先」没守住**：
`buildEaveTrim(roofType, …)` 内部按 hip/else 两套盒子拼装 + 两处 `gable|hip` 闸门
⇒ 把「檐口」这个所有屋顶共有的概念做成 2/6 类型的特权，`roof.ts` 255 → 709 行，454 行只服务两种屋顶。

**提的正确方向**：檐口 = **屋面边界环的扫掠**。有向边配对（`lib/solid-check.mjs` 已有）从任意屋顶的三角面
提边界环 → 沿环扫截面。一个算子覆盖 6/6，`roofType` 分支归零，中式飞檐跟着起翘的环自然成立。
落地顺序：**先修 resolver 闸门 → 再修 chinese_curved 壳体 → 最后把档 2 换成通用算子**（等用户确认）。

**新增工具**：`preview-bp.mjs`（通用预览：4~5 视角 PNG + 逐像素材质分区 ASCII，`--only`/`--mat`/`--views`/`--map`）、
`analyze-curved-roof.mjs`、`verify-curved-roof.mjs`、`probe-curved-winding.mjs`、`png-materials.mjs`。

**两个重要更正/教训**
1. **本环境能直接 `Read` PNG 看图**（实测看到灰色填充板插在屋脊正中）。技能文件里"不能解析图片"的旧结论已修正。
2. **不要按像素颜色反推材质**：着色会把 `wall_finish`(0.84,0.82,0.78) 压成 `floor_finish`(0.52,0.51,0.49) 的基色。
   正解是光栅化时逐像素记录 winning mesh 的 `materialRef`。
3. **ASCII 分辨率不足会造假孔洞**：96×34 下看见"洞"，176×62 下消失。
4. `_eave` / `_gableEnds` 在 `bp.geometry.elements` 上**看不到**（写在 `expandTemplates` 后的副本上），
   要观察必须自己 `compile` 一次再 `reconstructEntity(compiled)`。
