# 从实际作品改进技能

## 当前分工

2026-10-23用户要求：主代理后续创作不使用本技能；由其他Agent测试技能；主代理边独立创作边总结并更新技能。这是本项目当前协作方式，不要求其他使用者放弃技能。

主代理直接依据需求、参考图与当前引擎源码设计。先保留设计输入，再保存完整WILD、必要的作者脚本、实际修改与出图证据；完成后才整理经验。生成中可以记录事实，不把待验证的做法立即升级成其他Agent必须遵守的规则。不给当前作者追加“先照技能做”的前置要求。

## 每栋作品记录什么

- **设计输入与可见事实**：原需求、图片中可确认的体量与构造、未知尺寸和隐蔽面推定。记录最终选择及理由，例如退台为了形成真实可用露台，不编造未保存的思考过程。
- **具体实现**：实际使用的构件、字段、材料、源码入口，关键尺寸/标高与计算方式；明确作者脚本负责哪些布置，哪些能力来自现有引擎。
- **修改依据**：哪张图或哪条诊断暴露了什么问题，修改了什么，最终WILD和图片是否对应同一版本。保留失败稿与原始命令，不用事后描述替代证据。
- **结果与代价**：文件大小、几何/渲染成本、外形/空间/构造表现、尚存缺陷，以及用户反馈。技术可运行、作者看过图、用户认可分别记录。

继续使用用户指定的逐栋目录。技能内只放按需阅读的提炼；完整过程放案例目录，不让所有使用者先读全部历史日志。

## 哪些经验可以写成规则

| 内容 | 写入方式 |
| --- | --- |
| 字段、坐标、支持能力及明确限制 | 核对当前Schema/实现后修正文档，并记录来源；版本语义不能靠案例猜测 |
| 一栋作品中有效的构造计算 | 写清前提、计算与边界，作为可选技法；不能推广成所有建筑的固定尺寸或外形 |
| 配色、立面节奏、屋面、植物等审美选择 | 结合实际图片说明效果和局限；先作为案例经验，保留替代方案 |
| 其他Agent可重复出现的问题 | 先判断是文档歧义、表达缺失、引擎限制还是执行错误，再修最小必要内容 |
| 未执行、未看图或用户认为退步的方案 | 明确标待验证/待深化，保留复盘，不当作高质量默认模板 |

当前13—15例属于待深化案例。可提取沿墙开口、标高、镜像、屋面采样等有依据的方法；不可据此宣称统一作者脚本已能通用地产出精细建筑。

## 保留设计自由

优先传递“如何根据任务作决定”与“如何正确表达这个决定”。不把某栋的平面、柱距、植物阵列、屋顶形式、构件数量或相机角度写成普遍要求。同类型变化应来自场地、空间关系、体量、结构/屋面和材料构造的实际变化。

精细度先看整体比例、轮廓、开口深度、檐口/收边、材料尺度与连接关系，再决定哪些部位值得增加几何。重复大量细杆、窗格或球形植物并不自动提高质量；把真实材料简化成密集黑线也可能降低观感。这些是本轮需要核查的表现问题，不是所有风格都必须采用同一套细部。

保持小文件目标，继续使用参数化构件与材料；不引入GLB/GLTF、内嵌网格或图片资产来绕过表达问题。复用局部计算与材料角色，不默认复用整栋模板。

## 接收其他Agent的测试反馈

用户负责安排其他Agent测试，本次不替用户启动模型测试。收到反馈时尽量保留原提示词、技能版本或包hash、模型/可用工具、原始WILD、实际效果图、操作记录和用户评价；缺少证据就标未知，不补造“已通过”。

先复现反馈所指的表达或理解问题，再改动对应条目；记录“观察到的问题 → 文档改动 → 后续结果”。同一案例修得更好，只说明这次修订有效；需要不同提示词和新方案的结果才能判断是否改善泛化。比较图片时记录视角、光照与引擎版本，避免把换灯光或构图算成建筑设计提升。

没有对照时将原因标为待确认，不能把“加载技能后变差”的相关性直接写成已证明的原因。技能目标是让其他Agent更容易独立作出好设计；是否达到目标以实际作品和反馈为准。
