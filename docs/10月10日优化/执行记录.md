## 1. 当前建筑链

```text
classifier → architecture → material_plan → design_review
                                            ├─ revise → architecture
                                            └─ confirm → plan → execute ↔ replanner
                                                                    ↓
                                                                 compile
                                                                    ↓
                                                             final_validate
                                                                    ↓
                                                            保存并交付 .wild
```

`architecture` 正常情况下请求模型一次，交付完整设计。字段、尺寸、宿主或编译表达检查失败时，带具体证据有界重试，最多三次；失败明确返回原因，不再丢掉失败字段组后用默认建筑替代。模型服务异常立即终止，区别于设计格式错误。

`material_plan` 保留现有材质角色和可信资产解析职责。`design_review` 展示并审核同一 `DesignDocument`；没有另建一个重复设计的 `design` 节点。

建筑 `plan` 从 `resolved_design.component_markers` 确定性展开，不再请求模型重复决定构件种类。按类型分批，任务绑定标记 ID、图纸哈希与宿主依赖。几何投影只供审核与定位，不代表标记已经落实。

`execute` 每批共享一次对应类型的知识检索。已设计的 ID、类型、宿主、位置、尺寸和材料保持只读；只有注册表中尚未声明的可选细节字段可由模型补充。无需生成细节时直接参数化落实；需要时按类型整批请求一次，失败沿现有有界执行状态机处理。

`compile` 在执行结束后装配实际结果。缺失或改变确认字段的标记被列入 `missing_markers`，不会补造实体冒充完成。最终候选门禁重新逐个核对标记与批准实体，失败阻止 `.wild` 保存和加载。

## 3. 接口与几何一致性

门窗显式标记可以写：

```json
{
  "id": "window_second_floor",
  "type": "window",
  "host": "main_L2_front",
  "placement": {"offset": 2.0, "sill_height": 0.85},
  "size": {"width": 1.4, "height": 1.6},
  "form": {}
}
```

`offset` 是沿宿主墙的距离；`sill_height` 相对该墙底部。编译为 WILD 的 `[沿墙距离, 底部世界Y, 局部法向偏移]`，并同步对应设计槽位。没有 `placement` 的历史实例继续使用已有槽位语义。

屋顶显式实例按宿主匹配对应屋面；不再固定取第一块。显式构件改用稳定 ID 后，同场景的宿主引用随之更新。多个显式标记争用同一位置会明确报错。墙宿主采用编译器实际支持的 `<volume_id>_L<楼层>_<方位>`；显式追加门窗和阳台的世界标高由真实宿主墙底确定，移除固定 3.2 米假设。

结果必须只包含图纸字段和允许生成的细节字段。重复 ID、未设计结果、依赖环、图纸哈希或投影版本失效均有明确拒绝路径。审核新版图纸时清空旧版结果，避免几何相似就复用旧细节。

现有协议、材质资源、完整几何校验、批准实体保护和产物指纹证据继续使用。本轮没有重建 Chroma 索引，没有改变环境配置。

## 7. 灯具重复与附属实例编译修复

## 10. 屋顶分体量格式、总体尺寸语义与本地模型日志

## 23. 低档生成耗时与墙宿主交接修复（10 月 11 日）

### 本地记录中的原因

请求 `req_1791715235735_yz5mr8rsf` 的主体阶段耗时 1,118,188ms，约 18.6 分钟；
首次主体模型调用耗时 829,232ms，约 13.8 分钟，返回的思考约 17.3 万字符。
排查初始快照的检索累计约 5.5 秒，保存诊断时累计约 9.1 秒，仍远低于主体模型耗时。
trace 包含多次恢复和并发调用，不能把全部调用时长相加当作一次生成的墙钟耗时。

当前模型为 MiMo。原供应商适配没有 MiMo 分支，思考开关和配置的 4096 预算均未映射到请求。
[MiMo 官方说明](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/text-generation/deep-thinking)
支持通过 `thinking.type=enabled/disabled` 控制思考，并且默认开启；
文档没有列出独立的 `thinking_budget`。`max_completion_tokens` 同时限制思考和最终输出，不能当作纯思考预算。
原流式超时还按每个响应片段重新开始计时，持续收到思考就可能等待十几分钟。

重复修订也有具体交接错误：主体手工按洞口切墙，把 `wall_main_front_L1` 留给仅长 0.9m 的墙段，
后续门窗却仍按图纸的 11m 墙定位。16 个普通窗因此全部越界；反复缩窗无法修复主体宿主。
同一份保存结果有 29 个门窗标记受宿主位置或范围影响。

### 当前实现

- 低档按门、窗、灯的原生族批处理；保留各标记的类型、形态、位置和依赖，检索词也保留各个子类型。
  该图纸从 14 项合并为 6 项：主体、窗、门、屋顶、楼梯、灯，共 36 个标记，附属项仍最多三项并发。
  中、高、极高继续按具体类型展开；自定义设计及特殊依赖不会被删掉。
- architecture 保留用户选择的思考模式。低档 plan 实现和所有局部/装配修订请求关闭深度思考；
  中、高、极高首次实现仍按用户设置。MiMo 接入官方开关，其他供应商沿用已有适配。
  每次构件尝试在已有 trace 中记录请求的 `enable_thinking`；固定思考模型或未知代理是否支持关闭仍由实际接口决定。
- 配置超时覆盖整个流式调用。当前配置 300 秒时，持续输出也不能重置截止时间；
  超时走既有模型服务故障路径，保留部分回复及思考，并关闭流。此上限针对单次调用，不是整栋建筑的完成时限。
- 主体提示明确使用完整逻辑墙宿主，原生门窗负责裁洞。
  主体交接前复用现有门窗安装变换，核对真实宿主、定位点、显式尺寸范围、层高、方向和墙面。
  宿主不兼容时，整段主体回复留在主体阶段修订，避免先采用短墙再让后续所有窗反复失败。
  暴露的局部墙只需承接负责的门窗，不要求覆盖整面体量边界；未给尺寸时只核对已知定位点。
