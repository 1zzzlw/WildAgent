# 图纸标高误判与重复执行修复

日期：2026-10-13。请求：`req_1791871812378_0js4xt5tc`，用户需求“生成一个新中式别墅”，粒度 `minimal`。

## 为什么条目完成后又执行

实际链路是 `execute/replanner → compile → execute/replanner → compile → final_validate`。第一轮条目结束后，compile 会检查整栋建筑；有装配问题时，可将对应标记送回原任务做一次装配修订。这个机制本身正常，但本轮被错误的标高校验触发。

批准图纸明确声明 `floor_layouts` 的两层楼面顶标高为 **0.45m、4.05m**。模型按图纸生成：一层墙底 0.45m、二层墙底 4.05m；两块楼板底分别为 0.27m、3.87m，厚度均为 0.18m，顶面正好对应上述楼面标高。楼梯也已生成。

`validate_design_brief_constraints` 却只读取 massing 的 `floor_height=3.4`，按 `index × floor_height` 检查 **0m、3.4m**，还把楼板底面当成楼面。因此误报缺少墙和楼板。

compile 无法从该全局错误定位具体实体，回到主体修订；主体的依附标记随之重新执行。第二轮仍按错误标高拒绝，已有尝试耗尽，主体及依附结果被清理。最后几何为空，引发用户看到的 `validate_blueprint_schema`、`validate_design_brief`、`implementation_incomplete` 三类错误。它们是前面误判的后果，不能靠补楼梯、跳过校验或扩大容差解决。

## 最小修复

- `app/agent/validation/design_constraints.py`：建筑校验读取批准 DesignDocument 的 massing，并复用已有 `floor_elevations()` 取得逐层世界标高；楼板按 `from.y + thickness` 核对顶面。保留原有容差和缺失结构检查。
- `app/agent/validation/candidate.py`：将批准图纸传给共享校验，装配和最终校验因此使用同一坐标约定。
- `app/agent/validation/diagnostics.py`：按未上线阶段的统一策略固定首版 1.0，校验仍绑定实际图纸和蓝图指纹。

生产代码只修改这三个既有入口，没有修改图路由、增加重试、建筑模板或构件补量规则。旧骨架调用未提供 DesignDocument 时保持原有接口行为。
