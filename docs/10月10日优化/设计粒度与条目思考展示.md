# 设计粒度、条目思考与知识补充

日期：2026-10-10。

## 1. 四档设计范围

粒度影响 architecture 的设计范围与细节表达，不通过增加相同门窗数量或固定构件配额实现。

| 界面选项 | 现有契约值 | 默认设计范围 |
| --- | --- | --- |
| 低 | minimal | 建筑主体、必要门窗、屋顶、多层楼梯与基础照明，简洁构造和材质 |
| 中 | simple | 基础建筑加适量阳台、露台、雨棚、栏杆和入口细节，完善基本立面 |
| 高 | standard | 完整外观、开口分格、檐口、柱饰、屋面节点和分层材质 |
| 极高 | detailed | 完整外观加室内功能分区、通行空间、家具陈设、厨卫和场地细节 |

默认“中”。用户明确提出的构件和家具在任意档位均应设计，不因档位低被删除。具体构件取舍、数量、造型与空间布局仍由模型结合需求决定。极高的家具应落实为有位置、尺寸和造型的图纸标记，不能只出现在说明文字中。

前端选项只显示“低、中、高、极高”；选中后收起下拉列表，保存的档位继续用于后续请求。选择器和传送到 body 的菜单分别设置深色样式；生成中禁止改档位，防止一次请求中途改变设计范围。

`detail_level` 随 WebSocket 输入和持久化任务进入 architecture，选中值优先于模型返回的 complexity.level，并传到 PlanDocument。复用原有枚举，没有增加设计节点、构件数量限制或档位专属执行器。

## 2. 每个条目的模型思考

执行器复用现有 reasoning callback，通过 `plan:<item.id>` 归属到当前条目；执行进度与模型返回的 reasoning 分别显示。自写、知识库、网络与修订阶段的实际模型调用都采用同一流式入口。

条目执行时自动展开“执行过程与模型思考”；结束后收起并保留内容，用户可以再次打开。每个条目的完成或失败事件单独结束自己的运行状态。并发执行使用现有 ContextVar 隔离，不串到其他条目。

首次使用默认开启思考；明确保存过关闭选择的用户仍保留其选择。显示内容来自模型接口实际返回的 reasoning_content，兼容 additional_kwargs 与 response_metadata。供应商没有返回思考时明确显示无返回内容，不把执行进度伪装成模型思考。完整调用记录沿用已有本地 LLM trace。

## 3. 本轮知识补充

使用 [wild-component-example](../../.codex/skills/wild-component-example/SKILL.md) 搜索、查看官方参考图并转换示例，再按 [wild-knowledge-ingest](../../.codex/skills/wild-knowledge-ingest/SKILL.md) 拆来源声明、核验字段、登记文档、同步索引与检查实际召回。

新增两个活动文档、12 个最小样例：

- [家具与桌椅组合](../../wild-server/storage/knowledge_base/knowledge/components/furniture-layout-examples.md)：沙发、茶几、餐桌椅、床、衣柜、书架、床头柜、电视柜、书桌椅。
- [橱柜与厨卫设施](../../wild-server/storage/knowledge_base/knowledge/components/kitchen-sanitary-examples.md)：橱柜、洗手盆、马桶。

已查看并保留 Herman Miller、IKEA、Duravit 的 8 份官方 PDF 对应图纸页。声明和转换范围见 [来源处置清单](../../docs-dev/component-examples/plan-2026-10-10/interior-source-claims.json)。示例保留底部锚点与几何中心的区别、米制尺寸、弧度朝向、材质和各分件关系。产品尺寸与自行设计值分别说明；产品载荷、品牌认证、抽屉/冲水等未实现功能没有变成 WILD 字段或全局设计规则。

家具采用受支持的 furniture 子类型；橱柜和厨卫设施采用多个 primitive 组合，并说明曲面、机械和内部构造的近似。活动示例标为 experimental/schema，尚未做浏览器外观检查或用户认可，不标 verified_example。

原沙发文档的 entity_type 从 component 改为 furniture，与实际输出类型一致。新构件继续复用活动知识里的英文 entity_name、中文正式名称与别名，不另加命名名单。

## 4. 网络检索核查

真实请求证实，当前 Bing RSS 即使返回 HTTP 200，也会给出无关内容：small_window 查询得到 Small 期刊或字典，构造查询得到新闻、系统帮助等。普通搜索页面与更换语言参数也未取得稳定相关结果，因此不能宣称网络搜索已经可靠地获得构件图纸。

本轮修正：

1. 网络查询使用构件正式名称、知识族与去重后的设计说明；不把 Python 字典、snake_case 编号和重复标记名称堆进搜索词。
2. 检查返回标题/摘要是否含构件名称和查询中的构造语境，过滤明显无关条目；英文完整词匹配避免将 window 命中 Windows。
3. 没有相关结果时记录 ok=false，并在条目执行过程显示“网络检索没有相关资料，继续尝试实现”。仍进入本轮实现与修订，不因搜索空结果立即舍弃。

这是一层词面过滤，不能代替来源阅读、图纸识别或专业正确性判断。返回内容仍标为不可信参考数据；RSS 摘要不能冒充已阅读的设计图纸。本轮修改后的真实小窗、建筑主体、沙发查询均过滤为空，诚实保留此结果。见 [修复前结果](../../docs-dev/component-examples/plan-2026-10-10/web-search-before.jsonl) 与 [修复后核查](../../docs-dev/component-examples/plan-2026-10-10/web-search-verification.json)。本轮的官方资料补充使用实际网络搜索和来源核验流程完成。

## 5. 清理误拒绝的字段白名单

服务端轻量校验重复维护的 component_allowed 缺少 Schema 已支持的 slot_id 和 light.body，会让合法示例进入修订甚至舍弃。已删除约 60 行重复白名单，改为复用现有 Schema 字段查询。未知字段仍拒绝，后续 JSON Schema、尺寸、宿主和空间校验继续运行。回归同时验证 Schema 与轻量校验都接受合法的追踪标记和参数化灯体。
