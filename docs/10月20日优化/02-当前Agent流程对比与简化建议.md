# 当前 Agent 流程对比与简化建议

日期：2026-10-20。依据本次“汀院别墅”的完整操作、当前磁盘上的源码、以及 10 月 19 日实施记录。**本次没有修改项目源码，没有重新跑真实 Agent 或 RAG。** 已有未提交修改也包含在扫描中，不能把下面的“源码已存在”当成已经通过生产验收。

最值得迁移的是：让一次建筑判断贯穿到最终几何，用统一标高和真实关系推动局部修订。项目已经有不少支持它的实现，接下来应先稳定和收敛这些入口，减少重复的设计、上下文、执行语言负担与全局反馈噪声。此次我自己新增的抽样检查也漏了窄柱，后来靠项目已有检查找到，说明不能以“Codex 本次用了它”为理由就往项目再加一套。

## 1. 公平比较的前提

| 维度 | 本次 Codex 工作 | 当前 WildAgent | 能得出的结论 |
|---|---|---|---|
| 设计者 | 当前会话模型在连续上下文中做整体设计与修订 | architecture 起草完整图纸，后续模型读取投影与局部上下文 | 上下文连续性与交接内容不同；不能只看节点数认定高下 |
| 程序执行 | 完整本地 Python，可导入 math、定义任意本地辅助函数并读写本次文件 | `generation/program.py` 的受限解释器、只读 ctx、独立进程和资源上限 | 不能把本次脚本原样交给生产解释器，再把语法失败归因于建筑设计 |
| 设计数据 | 自定义的设计事实 JSON，并非完整生产 DesignDocument | 图纸契约、批准版本、投影、markers、implementation records | 本次数据不能直接充当完整生产图纸或逐标记履约证据 |
| 知识获取 | 按问题直接读语言文档、Schema 和少量源码 | 设计阶段多查询，构件阶段按类别检索，必要时查网络 | 本次没有 RAG 召回指标，也没有证明通读知识库更有效 |
| 产物形成 | 一个作者脚本统一生成整栋；两份不同的 WILD，另有哈希重放 | 主体先完成，标记按依赖和类别安排任务，构件片段经装配形成整体 | 关键差异是跨构件事实是否一致，不是“一次输出一定优于分片” |
| 验证 | 引擎、独立回读、复用生产空间检查、真实图像 | evaluate_candidate、关系与空间检查；final_validate 的视觉代理仍标未完成 | 本次补齐了图像查看；不能称生产视觉验收已接通 |
| 成本 | 当前对话无可用精确 token 账单；扫描和写文档也耗费上下文 | 有 token_usage、调用与检索记录 | 不能宣称本次比 Agent 更便宜、更快或更稳定 |

当前建筑主线以 [graph.py](../../wild-server/app/agent/graph.py) 为准：

```text
classifier → architecture → material_plan → design_review
  → plan → execute ⇄ replanner → compile → final_validate
```

本次实际走的是：

```text
有界扫描 → 保存主要设计事实 → Python 统一推导 WILD
  → 引擎与真实渲染 → 独立回读 → 复用项目空间复核
  → 移动一件家具、显式修订一条路线 → 原检查复检 → 图像查看
```

后者仍发生了长椅堵路、抽样漏柱、路线修订又碰到石材脊柱的问题。它的价值在于错误能定位、原稿保留、修订能验证；不是展示一条永不出错的“理想流程”。

| 显式楼面标高、挑空、房间和路径 | `design/coordinates.py:41`；architecture 提示与 floor_layouts | 保留并让所有消费者用同一投影；不要再造另一份独立“设计事实模型” |

## 3. 最优先：先把受限程序契约稳定下来

现有 [10 月 19 日实施记录](../10月19日优化/03-实施与验证记录.md) 第 6、7 节记录了两类实际阻断：`from=`/JSON 换行编码，以及 `import math`/局部辅助函数。后续已经修改说明、错误上下文和解释器；记录同时明确这些最新修正尚未测试或真实回放。

本次完整 Python 中用了 `import math`、自定义函数和普通文件操作；生产程序明确禁止 import、文件与网络，还限制函数表达。即使模型建筑思路相同，也多了一层受限语法和 JSON 源码字符串编码的失败面。单纯再加建筑规则、再加修复轮次都解决不了这个差异。

建议在现有 `generation/program.py` 和调用入口内收敛：

1. 先回放已有失败程序，证明修正后的公共语法确实可用；再完成原 detailed 需求的一次真实生成。不要用更小的 minimal 样例替代同范围验收。
2. 简单单体组件继续允许直接 JSON；复杂重复和标高联动才用 program。现有说明已经这样规定，但 `implementation.py:852` 仍给每次实现附上完整 PROGRAM_GUIDE；可按当前任务选择相关协议，减少每次都学两种输出方式的负担。
3. 复用已有 `slab(top,...)`、`opening(bottom,...)` 等帮助函数，给模型一个与实际解释器一致的小示例。不要把普通 Python 中支持、解释器不支持的写法混进示例。
4. 保留严格解析和失败稿反馈。不要靠自动改写 `from=`、宽松 JSON、吞异常或给程序更多轮次制造通过。

不建议再建一个脚本 Agent、再实现第二门 DSL，或让外部模型获得本次 Codex 的完整文件和进程权限来“对齐能力”。本次作者脚本只适合保留为可检查的参考产物。

## 4. 减少重复设计：材质节点先核对职责

根 README 的流程写“材质方案 → 受控归一化，不新增设计”（第 44 行），但 [material/workflow.py](../../wild-server/app/agent/generation/material/workflow.py) 第 64～75 行会因 regions/keywords 等显式意图进入模型设计，第 96 行附近实际调用模型，第 106 行附近还能进入格式恢复。这不是“每次固定多调一次”；文件也有复用与跳过分支。

本次在同一方案中定住材料角色及参数，后续实体只引用它们。可先查真实 trace：architecture 是否已经给出了足够完整的配色和材料参数？材质模型究竟补齐了缺项，还是重新解释了一次相同意图？

如果已经完整，优先在现有 `needs_material_design`/解析入口收敛为校核与资源匹配；只为尚未决定的材料部分调用模型。保留无贴图时的参数材料与未实现意图诊断，不把缺资产变成删除设计。若当前 architecture 只有材料方向、缺少可用参数，则这次模型调用有职责，不能只因想减少节点就删除。

这是先消除职责重叠、再评估节点是否可合并，不能依据 README 的一句话直接删代码。

## 5. 任务拆分按关系闭合，先用已有组合能力

[expand.py:538](../../wild-server/app/agent/plan/expand.py) 按依赖就绪后再按 kind 分组，`_marker_batches` 按 marker JSON 字符量拆批；[implementation.py:417](../../wild-server/app/agent/plan/implementation.py) 已提供 opening hosts、stair route targets、attachment geometry 等局部上下文。stairs 的输出协议也会包括 floor 和 railing。项目并非没有考虑组合关系。

本次有效的组合是“梯段 + 平台 + 上层板洞 + 到达板 + 防护”共用标高、“屋顶露台 + 门槛 + 外缘栏杆”共用板顶。应优先确认这些事实通过现有 target/context 交接完整，再决定要不要调整任务分组。

可在现有批次逻辑中试验：对共享关键支承关系的小组合共同实现或共同验收；重复独立窗组仍可按类型批量。不要把一整栋的所有内容塞成一个超大程序，也不要把每个踏步、梁条、框边拆成独立模型任务。验收看跨任务关系是否落地，不用“任务多了、构件多了”解释精细度。

预算同样先计量：建筑 marker 路径最终采用的预算由 marker 数和 IMPLEMENTATION_STAGES 推导，不能只引用旧 DETAIL_BUDGET 表来解释真实上限。先记录实际批次与失败原因，不通过扩大 marker 数或调用上限掩盖执行失败。

## 6. 已证实的具体问题：空间待复核标记范围过大

本次用原生产函数做了两轮真实回放，见 [项目空间复核结果](汀院别墅-过程证据/11-项目空间复核结果.json)。最终没有识别到路线阻挡或家具/开口冲突，但所有六条路线都标为 `needs_review`，共同原因是场景里有 28 个未覆盖形态。

源码位置：[spatial_review.py](../../wild-server/app/design/spatial_review.py) 的 `unverified` 在整个场景收集，随后第 133 行附近每条路线都用同一个列表决定状态。圆柱灯绳、球形树冠等可能离某条路线很远，却一起影响它的状态。这是本次可以用具体结果支持的反馈范围问题；不是推测模型水平。

建议在这个现有函数里收敛“未知对象与哪条路径有关”。能用可信保守包络证明远离的对象，不污染该条路线；不能定位或可能接触的对象继续待复核。未知不得无条件转为通过，也不必为每种景观形体建立一套精确碰撞器。共享的有限形态与局部关联足够时，就停止扩展规则。

同时保留“几何净空”和“支承/可达”的区分：当前生产函数的 scope 明确不是完整导航；本次独立脚本补查了声明路线的板面支承，但自己的离散碰撞抽样漏了窄柱。应复用生产多边形相交，按真实需要补到现有边界，别并行维护两个对“通过”含义不同的检查器。

## 7. 模型修复不必响应每个低置信观察

[compile.py:104](../../wild-server/app/agent/design_flow/compile.py) 在 errors **或 observations** 存在且实现完整时，允许一次集中模型修订。`review_spatial_use` 对窗前家具的近窗带观察本来就只表示“结合用途复核”，不是必然错误。代码已有 `review_only`、保留原稿和接受改进的保护，这些应保留。

可优先收敛触发条件：确定性阻挡进入局部修订；可能合理的临窗布置先作为证据展示，只有设计目标明确不允许遮挡或观察足够可信时才花模型调用。这可以减少“本来合理又被改一遍”。必须通过真实观察样本衡量，不能把未证实的碰撞都改成 warning，也不能动批准尺寸来消除提示。

## 8. 先删重复负担，再考虑性能机制

| 收敛对象 | 当前证据 | 优先动作 | 不建议现在加的东西 |
|---|---|---|---|
| 提示词负载 | 实现时拼接 capability brief、相关 Schema、PROGRAM_GUIDE、图纸/宿主/失败稿；已有类型裁剪与上下文筛选 | 先测每块实际注入长度与来源，再去重或按任务选协议 | 新的上下文管理 Agent、另一套知识镜像 |
| 重复设计 | architecture 给材料方向，material 分支仍可能再次设计 | 依据缺项决定是否调用，保持一个批准结果 | 再增加审美评审节点 |
| 全量校验重复 | compile 与 final_validate 都调用 evaluate_candidate | 先测开销；若很小保留。要复用也只能在蓝图、设计、brief、校验版本全部一致时复用既有快照 | 为节省一次检查新建复杂缓存系统 |
| 设计表示 | 当前文档、旧兼容投影、markers 和实际几何并存 | 明确唯一设计源与派生用途，复用现有投影 | 把本次 `01-设计事实.json` 再搬成生产并行 schema |
| 兼容分支 | graph 同时服务建筑、物件、编辑；plan 有旧链逻辑 | 若怀疑无用，先查所有调用和物件/编辑回归，再合并或删除 | 因本次建筑没走到就删除旧入口 |
| 文档中的量化宣传 | README 第 85～87 行写通用 Agent 必须通读约 44 万字符，并据此比较上下文成本 | 改为可复核的实测条件和限定结论。本次是按问题阅读；自动加载全引擎不等于人工通读 | 继续堆没有同条件基线的节省百分比 |

架构查询当前已有多条按主题的查询（`architecture/workflow.py:237` 附近），构件检索则 `per_query=2`、`MAX_RESULT_CHARS=6000`（`plan/knowledge_tool.py:14` 附近）。这些是不同入口，不能用 README 中某个统一 top_k 数字直接推算一整次生成成本。没有测量证据时，不主张砍掉必要示例或随意缩小上下文预算。

## 9. 最小落地顺序与验收

**先完成已有改动的验收。** 回放已保存的程序失败稿；使用修正后的同一详细需求完成一次真实生成，保留首次回复、每次程序输出、错误、采用结果与最终图像。先证明目前这条路能走通，再决定架构改动。本次没有替你执行这些线上模型调用。

**然后只收敛已有入口。** 优先处理任务无关的 PROGRAM_GUIDE 注入、材料是否重复设计、空间未知对象的关联范围、低置信观察是否应触发模型修订；修正文档口径。每次变化都能说明删掉或合并了哪份重复职责。不要把本次文档目录中的生成器和两个检查脚本当成新的生产子系统。

**最后才做同条件对照。** 保持同模型、同需求范围、同粒度、同预算和同验收，比较首次合法图纸率、首次程序执行率、逻辑调用与传输尝试、耗时与 token、失败阶段、关系落实和渲染确认。至少保留多次结果与失败稿，不能只挑最好的一次。对尺寸、翼楼方向和层高做少量变化，验证方法能够迁移；不要求生成同一栋“汀院”。

本次产物适合做“完成效果、源码语义和关系证据”的可观察参照。不要把它的 18 米主楼、两层、L 形、浅水庭或家具数量固化成通用规则。想复制的是整体设计能力、共享参数、局部有效反馈和诚实验收，而不是另一份固定别墅模板。
