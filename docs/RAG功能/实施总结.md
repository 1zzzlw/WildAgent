# WildAgent RAG 功能实施总结

> 总结时间：2026-07-29  
> 当前状态：RAG 后端核心链路已实现并通过本地 smoke test；FastAPI 导入级验证通过。  
> 向量索引数据库：Chroma。

## 1. 本次目标

本次任务目标是为 WildAgent 后端 Agent 增加 RAG 能力，让 Agent 在生成或修改 `.wild` 蓝图时，不再只依赖固定精简规范，而是可以根据用户请求从知识库中检索相关规范片段。

具体目标：

- 使用 Chroma 作为本地持久化向量数据库。
- 索引 `wild-server/storage/knowledge_base/` 下的规范文档。
- 保留现有 WebSocket / REST 协议，不影响前端调用。
- 保留现有 `.wild`、ScenePatch、校验流水线和 `wild-core` 边界。
- 将固定规范注入升级为“基础规范 + RAG 检索片段”。

## 4. RAG Loader 实现

核心文件：

```text
wild-server/app/spec/loader.py
```

保留原有：

- `SpecLoader`
- `FileSpecLoader`

新增：

- `RAGSpecLoader`
- `MarkdownChunker`
- `HashEmbeddingFunction`
- `OpenAICompatibleEmbeddingFunction`
- `create_embedding_function()`

### 4.1 RAGSpecLoader 职责

`RAGSpecLoader` 负责：

- 读取基础规范。
- 读取完整知识库文档。
- 使用 LangChain splitter 分片。
- 使用 Chroma `PersistentClient` 创建本地持久化 collection。
- 首次启动写入完整索引，后续启动按 chunk ID 增量同步。
- 知识库未变化时直接复用持久化索引，不重复调用 Embedding API。
- 新增或变化的片段按每批 10 条写入，已删除文档的旧片段同步清理。
- Embedding 模型或分块参数变化时自动重建 collection，避免向量维度不兼容。
- 根据 query 检索相关片段。
- 拼接最终注入 Prompt 的规范上下文。

最终上下文结构：

```text
基础规范 BLUEPRINT-SPEC-MINIMAL.md

---

RAG 检索到的相关规范片段
```

### 4.2 知识库来源

基础规范：

```text
BLUEPRINT-SPEC-MINIMAL.md
```

进入 Chroma 检索的文档：

```text
BLUEPRINT-SPEC-FULL.md
building_types/catalog/
building_types/*/
components/
recipes/
patterns/
```

这样既保证基础铁律始终在上下文中，又避免完整文档全量挤占 prompt。

说明：`BLUEPRINT-SPECIFICATION.md` 与 `BLUEPRINT-SPEC-FULL.md` 内容完全一致，已从后端知识库和 RAG 索引路径中移除。后续完整蓝图规范只维护 `BLUEPRINT-SPEC-FULL.md`。

## 5. 分片方案优化

最初实现过一个自写 Markdown 分片器，后来参考 `E:\AgentProject\OnCallAgent` 的 RAG 实现后，替换为 LangChain 官方 splitter。

当前分片流程：

```text
MarkdownHeaderTextSplitter
  -> 按 # / ## / ### 标题切分 Markdown

RecursiveCharacterTextSplitter
  -> 对超长片段按 chunk_size / chunk_overlap 二次切分

_merge_small_chunks()
  -> 合并同一标题下过小片段
```

这样做的原因：

- Markdown 标题解析交给 LangChain，减少自维护代码。
- `Document.metadata` 能自然保留标题层级。
- 后续接 LangChain VectorStore、rerank 或检索工具更顺。
- WildAgent 只保留业务相关逻辑：source、heading、chunk_index、content_hash 等 metadata。

当前 metadata 示例：

```json
{
  "namespace": "wild_spec",
  "source": "pavilions.md",
  "path": "...",
  "heading": "轻量建筑分类：凉亭（Pavilion） > 凉亭（Pavilion） > 变体 A：中式四角凉亭",
  "chunk_index": 12,
  "content_hash": "...",
  "mtime": 1780000000.0
}
```

## 6. Embedding 方案

### 6.1 真实运行

真实运行优先使用项目现有 embedding 配置：

```text
EMBEDDING__NAME
EMBEDDING__API_KEY
EMBEDDING__BASE_URL
```

实现类：

```text
OpenAICompatibleEmbeddingFunction
```

它通过 `openai.OpenAI(api_key, base_url)` 调用 OpenAI Compatible embedding 接口。

### 6.2 本地 smoke test

为了不依赖真实 API，也避免测试消耗额度，实现了：

```text
HashEmbeddingFunction
```

它只用于本地 smoke test 或缺少 embedding 配置时的兜底，不代表生产检索质量。

### 6.3 Chroma 接口补齐

Chroma 在 upsert 和 query 时会调用 embedding function 的不同接口。已补齐：

```python
__call__(input: list[str])
embed_documents(input: list[str])
embed_query(input: list[str] | str)
```

这个修复解决了 smoke test 中的：

```text
AttributeError: 'HashEmbeddingFunction' object has no attribute 'embed_query'
```

## 7. AgentService 接入

核心文件：

```text
wild-server/app/services/agent_service.py
```

### 7.1 接入方式

原来：

```text
AgentService.__init__()
  -> FileSpecLoader.load()
  -> build_system_prompt(spec_text)
  -> create_agent(...)
```

现在：

```text
AgentService.__init__()
  -> 创建 RAGSpecLoader
  -> 创建 LLM
  -> 注册 tools

AgentService.query_structured(...)
  -> 根据用户请求构造 rag_query
  -> RAGSpecLoader.load(query=rag_query)
  -> build_system_prompt(spec_text)
  -> create_agent(...)
  -> LLM 生成 Blueprint / ScenePatch / 文本
  -> run_validation_pipeline()
```

### 7.2 保持不变的边界

未改变：

- `query_structured()` 的对外语义。
- `ws_agent.py` WebSocket 协议。
- 前端 `agentBridge.ts`。
- `.wild` Blueprint 格式。
- ScenePatch 协议。
- 服务端 18 个空间工具。
- 服务端校验 / 自动修正流水线。
- `wild-core`。

### 7.3 RAG 失败兜底

如果 RAG 初始化失败，后端会退回：

```text
FileSpecLoader([BLUEPRINT-SPEC-MINIMAL.md])
```

同时日志记录错误类型和摘要，但不再打印完整 traceback，避免本地变量或 API key 泄露到日志里。

## 8. 遇到的问题和处理

### 8.1 依赖下载失败

下载 `chromadb` 依赖时曾卡在 `aiohttp` wheel 下载。

处理方式：

- 临时给终端配置本机代理。
- 也尝试过国内镜像源。
- 最终依赖下载完成后，不把代理相关依赖写入项目。

结论：

- 依赖下载属于环境问题。
- 项目依赖只保留运行真正需要的包。

### 8.2 SOCKS 代理导致 httpx 报错

临时代理环境变量中使用了 SOCKS 代理后，`openai/httpx` 报：

```text
Using SOCKS proxy, but the 'socksio' package is not installed.
```

处理：

- 新开一个不带 SOCKS 代理环境变量的终端即可。
- 不把 `socksio` 作为项目运行依赖。

### 8.3 DashScope embedding 批量限制

启动时 RAG 索引构建报：

```text
batch size is invalid, it should not be larger than 10
```

原因：

- `RAGSpecLoader.sync_index()` 最初每批 upsert 64 个 chunk。
- Chroma 会把这 64 条文本一次发给 embedding 接口。
- DashScope embedding 接口单次 input 最大为 10。

修复：

```python
batch_size = 10
```

### 8.4 Windows 临时目录清理失败

smoke test 使用 `TemporaryDirectory()` 时，Chroma 可能仍短暂持有索引文件句柄，导致：

```text
PermissionError: [WinError 32]
```

修复：

```python
TemporaryDirectory(ignore_cleanup_errors=True)
```

这只影响测试脚本，不影响正式持久化目录。

## 12. OnCallAgent 对照结论

参考项目：

```text
E:\AgentProject\OnCallAgent
```

OnCallAgent 已具备更完整的 RAG 应用骨架：

- `/upload` 上传文件后自动索引。
- `index_directory` 支持批量索引目录。
- `DocumentSplitterService` 使用 LangChain Markdown / Recursive splitter。
- `VectorIndexService` 在重建同一文件索引前按 source 删除旧数据。
- `metadata` 中保留 `_source`、`_extension`、`_file_name`。

但 OnCallAgent 没有做到检索质量最优闭环：

- 没有标准检索评估集。
- 没有 rerank。
- 没有 BM25 / keyword + vector 混合检索。
- chunk 参数是经验值，不是评估驱动调优结果。
- `embed_documents()` 直接批量提交 texts，可能遇到 DashScope 单次 input 不超过 10 的限制。

WildAgent 本次不照搬 OnCallAgent 的 Milvus 架构，继续保持 Chroma。只吸收三点适合当前阶段的做法：

1. 使用 LangChain splitter 承担 Markdown 结构切分。
2. metadata 对齐 `_source` / `_file_name` / `_extension`，方便后续按源文件覆盖更新和删除。
3. 将用户知识库导入作为 RAG R4 扩展阶段写入路线，而不是混入当前 MVP。

## 13. 用户知识库导入预留

当前 RAG 只索引系统内置规范文档：

```text
wild-server/storage/knowledge_base/
```

后续用户手动上传知识库文档建议单独实现为 R4：

- 后端新增 `app/api/knowledge.py`。
- 支持 `POST /api/knowledge/upload` 上传 `.md` / `.txt`。
- 保存到 `wild-server/storage/knowledge_base/user/`。
- 上传后自动调用 RAG 索引服务增量 upsert。
- 覆盖更新时按 `_source` 删除旧分片。
- 删除文档时同步删除源文件和 Chroma 分片。
- 前端新增知识库管理面板。

边界：

- 当前还没有用户导入功能。
- 当前 Agent WebSocket 协议不需要为上传功能提前修改。
- 系统规范和用户文档必须用 `doc_scope=system/user` 区分，系统规范优先级更高。
