## 2. 优先修复验收的误拒与漏检

### 2.1 四个灯具有正确材质，仍被判定缺失

第一次的 `generate_8` 对入口、客厅、厨房、主卧四个灯具进行生成和两轮修复，最终全部放弃。错误均为“未引用设计材质角色 accent”。实际回复把材质放在原生灯具的 `body[].material` 中，值就是 `accent`。

`app/agent/plan/implementation.py::_bind_materials` 已递归处理材质，但 `app/design/relations.py::component_geometry_review` 第 168–183 行仅取实体顶层材质字段。绑定与验收的遍历范围不一致。

用保存的真实输入和输出经过当前生产函数回放：四个灯具均在材质检查处失败。仅在诊断副本中取消该项材质约束后，四个均通过其余验收。这用于隔离误判，不能作为降低生产约束或宣称灯具已恢复的依据。

建议：统一已知材质字段及原生子部件的遍历，保留材质意图校验。验收应覆盖 `light.body` 及同类嵌套结构，不能将任意字符串都视为材质引用。

### 2.2 主沙发偏离图纸 15 米，却被记为已实现

第二次 `generate_10` 的 `sofa_living`：

- 批准位置：`[15, 0.425, 8]`。
- 模型输出：`position: ["=floor_y", 0, 8]`，其中 `floor_y=0`。
- 保存实体位置：`[0, 0, 8]`，X 偏离 15 米；顶视渲染可见沙发位于建筑外。
- 当前生产函数回放仍接受；记录为 `implemented`、`needs_review`，尺寸只记录“未建立原生字段映射”，没有定位错误。

原生家具尺寸实际在 `dimensions.width/height/depth`，现有单实体检查查顶层字段；其定位也未与图纸核对。这里不直接比较 Y：图纸中心与家具底部锚点必须先转换，X 的 15 米漂移则没有这种歧义。

建议：在现有映射和几何验收入口补齐原生家具的尺寸与锚点语义，由代码处理中心到底部的转换，并核对明确的批准位置。遇到没有明确宿主、楼层或空间关系的情况仍应返回冲突，不凭空选择房间。

这两类错误都在当前代码中复现。先解决它们，才能让后续成功率与失败数有可信含义。

## 3. 参数化接口仍把过多编程工作交给模型

现有参数展开减少了重复 JSON，但模型仍需要写公式、选择坐标轴、记住上下文路径和遵守表达式语法。这尚未完全落实“模型决定设计，代码计算几何”。

真实失败包括：

- 第一次入口、第二次餐桌等使用 JavaScript 三元表达式 `i == 0 ? ... : ...`，有限 Python AST 解析器不支持；修复时仍重复相似写法。
- 第二次入口使用 `facts.diagram_hosts[0].from[0]`。`from` 是 Python 关键字，点号访问会语法失败；`facts.wall["from"][0]` 则可解析。对模型暴露的字段访问规则存在容易踩中的边界。
- 三个洗手盆修复时访问 `facts.marker.size.width`，实际设计尺寸在 `facts.marker.design.size.width`。反馈“事实或参数没有字段 size”未给出可直接使用的准确路径。
- 第二次厨房三组构件连续失败：`$repeat.value` 写成多实体数组，展开后 `geometry.elements` 混入嵌套 list。当前验收却统称“没有生成有效实体”，没有指出应使用 `values` 或返回单个对象。真实输出并非空白。
- 书架和花园长凳把 primitive 放进 `components`；吊灯把实体放在行外的 `entities` 或 `lightBody`，约定的 geometry 为空。应定位具体错误字段。书架还存在标高问题，纠正容器本身不证明几何合格。

建议按最小范围收敛：

1. 对已批准且可以明确转换的尺寸、位置、宿主关系直接提供计算结果，避免模型重复查路径、写坐标推导。
2. 在展开入口验证 `$repeat` 的输入形状，错误反馈包含字段路径、实际类型和允许的写法。
3. 对可无损归一的已知实体类型与容器错误由代码处理；存在设计歧义的错误明确退回。
4. 保持有限表达式能力，补清楚语法契约和错误位置；不要为了兼容零散输出引入任意 `eval` 或继续扩成通用编程语言。

第二次 24 次构件修复共使用 261,603 token，占本次约 36.6%。其中有成功修复，不能全部算作浪费；但同样的结构错误反复出现，已足以说明增加重试并非当前首选。

## 4. 屋面几何应由批准参数直接求解

第二次 `generate_5` 的车库屋顶三次均未通过。首次还存在显著标高错误；最后一次已经缩小为上表面投影中心偏移：

- 目标 X/Z：`(-0.4, -0.4, 7.4, 6.4)`。
- 实际 X/Z：`(-0.3844708573, -0.4, 7.4155291427, 6.4)`。
- X 整体偏移约 `0.015529m`，投影宽深已相同；报告缺少 `0.099㎡`。
- 最后候选厚度 `0.12m`、坡角 `-15°`；偏移量正好对应半板厚的旋转投影 `0.12 / 2 × sin(15°)`。

程序已经知道负责体量、出檐、坡角、板厚，却仍要求模型自己求旋转后的表面投影中心，最终整个屋顶被放弃，真实渲染中车库敞口。

建议在现有屋面计算入口按明确参数求板长、中心和支承标高。对这种投影尺寸相同、平移解唯一的候选，可以计算修正量并重新执行覆盖与承托检查。不能扩大容差跳过缺口；修正这一个 X 偏移，也不能据此宣称支承封闭等后续检查全部通过。

## 5. 构造深化：当次没有发挥作用，当前代码已有部分改善

第二次执行了 1 次构造深化，目标 11 项，但原记录为整批 `rejected`。入口采用 `framed_opening` 却携带 `canopy`，不符合该构造系统契约，连同其余门窗与檐口深化一起被丢弃。运行时深化输入 `diagram_hosts=[]`，而保存状态中已有 22 个 drawing hosts。

原建筑设计部分字段写在 `form.system`，也不等于当前确定性执行所需的 `form.construction`。两次批准设计中有效 `form.construction` 均为零，实际 `construct_system` 执行均为零。

当前工作区已有两项改善：深化按提案组独立采纳，以及向深化提供投影宿主。用第二次保存的同一段原始回复回放当前 `refine_construction`：10 项通过设计校验，1 项入口仍拒绝，状态为 `partial`。

这是模拟返回旧回复的离线回放，新增真实模型调用为 0。它只证明当前版本不再因这一入口错误丢掉其他 10 项，并未编译或渲染这 10 项的全部实际几何，也不是重新运行第二栋建筑。原入口还带侧亮窗意图，不能直接改名为另一系统掩盖能力差异。

因此，这两次失败不能直接代表最终版本确定性构造链的收益；同时，当前可复现的材质与定位问题也不能归因于旧运行版本。trace 中有缓存的 `process_first_trace_source_files` 快照，不能仅凭相同源码散列断言整个运行始终使用同一实现。

## 6. “详细”需要落实为建筑表达与可用性

两次图纸均提示一、二层有内墙，却没有附着其上的通行开口。第二次设计还存在深度仅 1.5 米的厨房、卧室；这些需要在设计阶段核对具体空间用途和关系，而不宜交给家具生成阶段补救。

第二次虽然增加了大量家具任务，主体仍较单一，入口被放弃，车库屋顶缺失。提高构件数量并未保证建筑层次。相关失败任务多数已经拿到构件参考，不能简单归为 RAG 没有资料。

建议在现有设计审核、任务依赖和履约流程里优先落实：体量及空间关系 → 屋面和入口完整性 → 檐口、洞口、材质分区等立面表达 → 室内陈设。对于图纸明确承诺的通行关系，应检查开口是否落地；开放空间不能机械强制增加门。家具需求仍保留，只是不应掩盖建筑关键部分的失败。

仅修可靠性不保证达到 10 月 23 日的观感；体量比例、空间组织和立面构图仍需要模型作出好的设计决定，并由实际渲染验收。这次没有进行 10 月 23 日作品对照，也没有宣称达到相同质量。

## 7. 建议实施顺序与验收

| 优先级 | 现有入口中的修改方向 | 验收要求 |
| --- | --- | --- |
| P0 | 嵌套材质检查、原生尺寸与锚点映射 | 合法灯体材质通过；错误材质仍失败；明确位置漂移被拦截；正常底部锚点不误判 |
| P1 | 重复声明输入验证、准确路径反馈、有限无损归一 | 非空错误结构不再被误报空输出；修复信息指出具体结构与可用事实路径 |
| P1 | 屋面与原生构件的确定性定位 | 不同跨度、坡向、板厚、出檐均满足原覆盖及承托约束；不放宽容差 |
| P1 | 核实运行版本并验证构造深化实际落地 | 合法组保留且真实编译；非法组隔离；宿主信息正确；不只统计声明数量 |
| P2 | 图纸可用性、建筑关键部分的履约顺序 | 明确动线有对应开口；入口及屋面完整；经实际渲染检查层次和比例 |
| P2 | 会话指标与 trace 对齐 | UI 不再将有大量调用的运行统计为 0 token；区分执行、等待和并行调用耗时 |

这些修改应复用现有生成、展开、验收与履约入口，并清理被替代的重复映射。当前证据不支持再增加一层 Agent、扩大重试预算或按本次建筑 ID 打补丁。
