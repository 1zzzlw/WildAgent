# WildAgent 项目索引

本文档记录 WildAgent 当前 Agent 生成工作流、结构化中间状态、确定性装配、空间校验与前端重建链路的代码索引，用于后续持续维护和定位问题。

本文档只描述当前代码的位置、职责和接入状态，不把历史设计、待办方案或未接入实现写成已交付能力。

最后核对：2026-09-15。

## 1. 使用方法

索引中的“接入状态”分为：

| 状态 | 含义 |
|---|---|
| 当前主链 | 当前 LangGraph 生成流程会正常执行 |
| 支撑层 | 被主链节点、校验器或前端调用 |
| 兼容保留 | 仍在代码或图中保留，但不是当前新建筑正常主链 |
| 未接入 | 已有实现或测试，但当前主链未调用 |
| 交付后 | Blueprint 通过服务端校验后，在前端编译、重建和显示阶段执行 |

表格中优先记录稳定的函数、类或节点名。行号仅用于当前版本快速定位，代码变更后应重新核对。

## 3. 当前生成主链

当前建筑生成主链为：

```text
classifier
  → planning_research / planner
  → requirement_compiler（planning/requirements.py 内的确定性编译，不是独立节点）
  → plan_validator / plan_review
  → architecture
  → material_plan
  → design_review
  → skeleton (LLM 主体 + 组件建议)
  → Send(component_gen → component_val) × N
  → merge
  → final_validate（固定 Schema 校验 + 逐条业务验收）
  → callback / END
```

LangGraph 图结构是固定节点顺序的唯一事实源。`execution_plan` 只描述本次要完成什么，
`execution_progress` 只展示固定节点运行到哪里，两者都不再参与节点路由。

原始模型 reasoning 不是 `GenerationState` 字段；它通过单次运行时回调向前端传输。

状态职责边界（不要混淆）：

```text
execution_plan          本次需求要完成什么（面向用户与审核的动态任务）
structured_requirements 已批准任务编译出的、节点可消费和可校验的业务约束
acceptance_results      每条验收条件的实际值、证据和状态；业务完成的唯一依据
execution_progress      固定 LangGraph 阶段运行到哪里；只用于展示，不证明业务完成
```

### 复现线上失败：从持久化检查点取真实状态

用户报"某次生成失败了"时，不要靠猜验收文本。每次运行的状态都存在
`wild-server/storage/sessions/langgraph_checkpoints.sqlite3`：

```python
thread_id = f"generation:{request_id}"   # 必须带前缀，裸 request_id 查不到
conn = sqlite3.connect(f"file:{DB}?mode=ro", uri=True, check_same_thread=False)
cv = SqliteSaver(conn).get_tuple(
    {"configurable": {"thread_id": thread_id, "checkpoint_id": ids[-1]}}
).checkpoint["channel_values"]
```

- 失败清单（含 `error` 原文）在 `generation_jobs` 表。
- **必须用 `SqliteSaver` 解码**：venv 里没有 `msgpack`，langgraph 用的是 `ormsgpack`
  且 blob 带 ext 类型。
- 关键判据：`merged_blueprint` 是 dict 而 `final_blueprint` 是 `None`
  → 「蓝图已产出，被验收判死后丢弃」。

范例：`.workbuddy/diag/check_material_kind_2026-09-17.py`。

## 15. 维护约定

以后修改 Agent 工作流时，按以下规则同步更新本文档：

1. 新增、删除或重排 LangGraph 节点时，更新第 3 节主链和对应索引。
2. `GenerationState` 字段变更时，更新第 4 节，并标明字段是临时、可持久化还是可交付。
3. Prompt 输出结构变更时，同步核对对应 normalizer、State 回写和测试。
4. fallback、风格包、组件白名单或确定性装配改变时，更新第 7–9 节。
5. 新增校验器或修复器时，必须记录它的调用入口、执行顺序、复检位置和回归测试，不能只记录函数文件。
6. 代码存在但未接入主链时，必须放在第 12 节，不得写成当前能力。
7. 每次核对后更新文档顶部的“最后核对”日期，并检查相对链接和行号。
8. 问题分析、改造方案和实施记录分别放入对应专题文档或 `docs-dev/`；本文档始终保持为“现行索引”。
