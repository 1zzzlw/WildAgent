# 玫庭庄园创建流程

2026-10-22，Asia/Shanghai。用户追加欧式别墅后，将其排入第二栋；先完成听澜合院，再开始本栋。

## 01 输入与设计

沿用本轮已经扫描并验证的 WILD 1.1、Core 构件能力、项目校验与真实 Chromium 渲染入口。质量参考仍为原始汀院，当前对话 Codex 重新设计法式庄园，不复制旧欧式蓝图。

采用两层对称主楼、石柱门廊、铁艺露台、坡屋面、玻璃花房与喷泉前庭。完整设计见 `01-需求与设计/设计说明.md`。

## 02 实现与记录方式

作者脚本、版本快照、分层映射、命令参数/起止时间/退出码/stdout/stderr、校验报告和图片分别保存；共享本日的只读验收和剖切工具。只修改本轮 docs 产物。

## 03 r1 实测与归因

- r1 Schema、门窗与楼梯关系有效，组件编译无错误；真实 Core 报告花房最左端两根杆件的路径端点重合。原因是取样恰好落在四坡屋顶角点，收点长度为零。r2 将杆件采样移到坡面内部，不删除花房或放宽几何限制。
- 项目碰撞检查指出入口承接小平台与既有门廊地板重叠。实际最后一级已直接接到门廊，r2 删除多余的重复板，不改变台阶或门廊轮廓。
- 完整流水线报告三个老虎窗屋面应覆盖 18×11 米整栋主楼。这与实际承托墙不符：老虎窗各自是 1.56×1.60 米的小墙体，屋面为 2.05×2.12 米，墙顶与屋顶基准均为 9.43 米。
- 源码 `spatial_tools.py:get_roof_support_bounds` 先取最近标高的墙，再调用 `_stepped_support_y`；该函数将被下层大轮廓包围的高层小墙统一解释为退台，因此这里把老虎窗降到主楼 7.55 米墙顶，随后产生尺寸和悬空误报。本次任务不修改应用源码。
- 保留整体失败报告；另外使用同一个原项目屋面检查器，分别传入主屋面、花房和每个老虎窗的真实承托组，并记录带墙厚的独立包络计算。这是明确范围的局部复核，不能冒充完整流水线通过。

## 04 r2 最终复核

- r2 修正花房零长度扫掠与重复地板，保留设计的原屋顶、老虎窗和细部。
- Schema 通过；当前 Core 编译与重建零错误、零警告；真实 Chromium 输出 1,726 个网格，未映射材质为零。
- 完整流水线 17 项无错误，屋面一项保留误判，零警告；同一个屋面检查器对五个实际承托组全部通过，独立墙厚包络与标高差也通过。
- 最终四视外观、两份剖切共 12 张图出图；作者查看了四视外观及两层剖切俯视，确认花房、家具、分区、井口和楼梯确实存在。
- 公共剖切工具补充移除“宿主也被剖切移除”的依附组件，避免剖切副本留下老虎窗组件的悬空引用。剖切仅删除遮挡，保留实体的几何参数原样不动。
- 最终 WILD SHA-256 为 `773bdd857354d9b64a7d9d7388d90e5eef3818b7e4c085942fb5052ae3afbcba`；与汀院及听澜的渲染上下文完全一致。
