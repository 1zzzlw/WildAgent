# 分片文件格式规范

> LangGraph 各节点产出的片段文件格式定义。每个节点产出独立的分片 JSON，最终由 merge 节点组装为完整 Blueprint。

---

## 一、设计目标

1. **独立可校验**：每个分片可以独立跑 Schema 校验
2. **无冲突合并**：各节点输出不互相覆盖
3. **可追溯**：每个 fragment 知道自己来自哪个节点
4. **兼容现格式**：合并后的产物就是标准 Blueprint，无需额外转换
5. **内存优先**：fragments 在 LangGraph State（内存）中传递，可选写文件用于调试
6. **对齐编译器**：components 格式对齐 `wild-compiler/componentRegistry.ts` 的 ComponentSpec 类型

---

## 三、合并规则

```python
def merge_fragments(skeleton: dict, fragments: list[dict]) -> dict:
    """
    1. 深拷贝 skeleton 作为基底
    2. 遍历每个 fragment:
       - elements → 追加到 geometry.elements
       - components → 追加到 geometry.components
       - extra_materials → 合并到 materials（同名材质以 skeleton 为准，防止覆盖）
       - diagnostics → 汇总
    3. ID 冲突检测:
       - 所有 elements/components 的 id 取并集
       - 如有冲突 → 记录 diagnostic，后到的加 _dup 后缀
    4. 引用完整性检测:
       - 所有 parentWall 必须在 wall id 列表中
       - 所有 parentFloor 必须在 floor id 列表中
       - 缺失引用 → 记录 diagnostic
    5. 返回合并后的完整 Blueprint
    """
```

### ID 命名空间规则（基于wild-compiler实际实现）

**代码位置**: `wild-web/src/wild-compiler/index.ts:74-91`

为避免并行节点之间的 ID 冲突：

| 组件类型 | ID 前缀约定 | 编译后子元素ID格式 |
|---|---|---|
| door | `door_`（如`door_front`） | `door_front__opening`, `door_front__frame_left` |
| window | `window_`或`win_` | `window_left__opening`, `window_left__frame_top` |
| railing | `rail_` | `rail_stairs__post_0`, `rail_stairs__beam_0` |
| canopy | `canopy_` | `canopy_entrance__slab`, `canopy_entrance__support_0` |
| balcony | `balcony_` | `balcony_2f__slab`, `balcony_2f__rail__post_0` |
| ramp | `ramp_` | `ramp_access__body`, `ramp_access__rail_left__post_0` |
| bay_window | `bay_win_` | `bay_win_living__opening`, `bay_win_living__frame` |
| cornice | `cornice_` | `cornice_roof__sweep` |
| chimney | `chimney_` | `chimney_kitchen__shaft`, `chimney_kitchen__cap` |
| light | `light_` | `light_chandelier__bulb`, `light_chandelier__base` |

**实际编译器行为**（`wild-compiler/index.ts:74-91`）：
```typescript
const generatedIds = new Set<string>()
for (const element of generated) {
  if (!element.id) throw new Error('编译结果包含空 element.id')
  if (generatedIds.has(element.id) || usedIds.has(element.id)) {
    throw new Error(`编译结果 element.id 冲突: ${element.id}`)
  }
  generatedIds.add(element.id)
}
```

编译器严格检测ID冲突，任何重复ID会导致该组件编译失败（但不影响其他组件）。子元素ID由各编译器内部确定性生成，使用`{componentId}__{subpart}`格式。

## 四、分片的生命周期与存储

### 4.1 运行时（内存）

```
Layer 0: skeleton_fragment   ─┐
Layer 1: door_fragment       ─┤
         window_fragment     ─┤
         roof_fragment       ─┼─→ merge_fragments() → merged_blueprint
         railing_fragment    ─┤       │    (全部在内存 State 中)
         furniture_fragment  ─┤       ▼
         light_fragment      ─┘   validate_and_fix()
                                       │
                              ┌────────▼────────┐
                              │  回调修正        │
                              │  只重写失败分片  │
                              │  不重写已通过分片│
                              └────────┬────────┘
                                       │
                                       ▼
                                 final_blueprint
```

**关键原则：**
- 所有 fragments 存储在 LangGraph State（Python 内存对象）
- 节点间通过内存传递，无序列化开销
- 单次生成 10-30 秒，无需持久化恢复
- 生成失败直接重来，不做断点续传

### 4.2 可选持久化（调试/审计）

```python
# 只在开发模式或审计模式启用
if config.SAVE_GENERATION_FRAGMENTS:
    session_dir = Path(f"storage/sessions/{session_id}/fragments")
    
    # 每个节点完成后写入磁盘镜像
    await save_fragment(session_dir / "1_doors.json", state["door_fragments"])
```

**关键**：回调时只重写失败的 component fragment，不重新跑 Layer 0 和已通过的 Layer 1 节点。

## 五、分片存储方式（重要设计决策）

### 5.1 运行时存储：内存（LangGraph State）

**并行节点生成的各组件片段存储在 LangGraph State 的内存中**，不持久化到磁盘：

```python
class GenerationState(TypedDict):
    # 各节点产出直接写入 state 字段（内存）
    door_fragments: list[dict]        # 内存中的 Python list
    window_fragments: list[dict]
    roof_fragment: dict | None
    # ... 其他组件 fragments
```

**为什么用内存？**

1. **性能**：并行节点同时运行，写内存比写磁盘快 100 倍
2. **简洁**：LangGraph 天然支持 state 在节点间传递
3. **原子性**：整个生成流程要么成功（写入最终 Blueprint），要么失败（内存自动清理）
4. **无锁竞争**：每个节点写自己的 state 字段，不存在文件锁冲突

### 5.2 调试存储：可选持久化（仅开发/调试模式）

在开发阶段，可通过环境变量 `LANGGRAPH_DEBUG=true` 启用分片日志：

```
wild-server/storage/debug/sessions/{session_id}/
├── 0_skeleton.json              ← Layer 0 产出（调试用）
├── 1_doors.json                 ← Layer 1 门节点产出
├── 1_windows.json               ← Layer 1 窗节点产出
├── 1_roof.json                  ← Layer 1 屋顶节点产出
├── 2_merged.json                ← Layer 2 合并后的完整 Blueprint
├── 2_validation_results.json    ← 校验流水线结果
├── 2_retry_1_doors.json         ← 第一次回调修正后的门
└── 3_final.json                 ← 最终产物
```

**存储时机**：每个节点执行完后，异步写入（不阻塞主流程）

**用途**：
- 出现 bug 时精确追踪是哪个节点生成的哪个 fragment 有问题
- 对比重试前后的差异
- 分析 RAG 召回是否精准

**清理策略**：
- 成功的会话：保留 7 天后自动删除
- 失败的会话：保留 30 天（便于排查问题）
- 超过 1000 个会话时，删除最旧的

### 5.3 最终 Blueprint 存储：数据库（生产持久化）

只有完整通过校验的 final_blueprint 才写入数据库：

```
wild-server/storage/scenes/{scene_id}.json   ← 当前实现（文件存储）
或
PostgreSQL scenes 表                         ← 未来可扩展
```

**分片本身不持久化到生产存储**——它们只是生成过程的中间产物。

### 5.4 对比：文件 vs 内存

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **内存 State** | 快、简洁、原子 | 崩溃丢失 | ✅ 生产运行时 |
| **临时文件** | 可追溯、可恢复 | 慢、需清理、锁冲突 | ✅ 调试模式 |
| **数据库** | 持久、可查询 | 写入开销大 | ✅ 最终产物 |

**推荐架构**：
```
运行时 → 内存 State（主路径，性能优先）
       ↓
   (可选) 异步写临时文件（调试模式，不阻塞）
       ↓
    最终 Blueprint → 数据库（生产持久化）
```
