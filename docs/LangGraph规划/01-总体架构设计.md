## 一、当前架构的瓶颈

### 1.1 当前流程（基于实际代码）

```
用户输入
  → RAGSpecLoader.load_many([8个查询], per_query=1) 
     → Chroma 向量检索 + metadata过滤(doc_type/entity_type)
     → 18K字符上下文预算 + body_hash去重
  → FileSpecLoader(BLUEPRINT-SPEC-MINIMAL.md) 兜底
  → 单体 LangChain Agent（build_system_prompt + 18个@tool空间工具）
  → LLM 一次性生成完整 Blueprint（elements + components + materials）
  → wild-compiler展开组合构件(door/window/railing→opening+primitive)
  → 服务端run_validation_pipeline（15步确定性Python函数强制执行）
  → QueryResult(blueprint/patch/text + pipeline_results + error)
```

**当前代码位置**:
- `wild-server/app/services/agent_service.py:578-760` - 完整流水线
- `wild-server/app/spec/loader.py:740-895` - RAGSpecLoader实现  
- `wild-server/app/tools/spatial_tools.py` - 18个空间校验工具
- `wild-web/src/wild-compiler/index.ts:23-102` - 组合构件编译器

### 1.2 四大瓶颈（基于实际RAG/编译器/校验流水线）

| 瓶颈 | 表现 | 根因 | 代码证据 |
|---|---|---|---|
| **上下文竞争** | 建筑类型、door、window、roof chunk 抢 top_k=6，关键组件知识被挤出 | 单次 RAG 或8路per_query=1，18K字符预算紧张 | `agent_service.py:444-470` 八路查询各取1个，`config.py` rag.top_k=6 |
| **类型编造** | LLM发明`door.style`、`roofType:"pitched"`等不存在字段 | metadata过滤命中率低，组件边界文档未进上下文 | `knowledge_base/components/engine-capability-boundaries.md` 存在但可能未被召回，actual schema在`wild-core/types.ts` |
| **整体重来** | 一个opening坐标错→整个Blueprint丢弃重生成 | 无细粒度重试，fix→recheck只执行1轮 | `agent_service.py:154-290` 线性15步流水线，无component级重试 |
| **调试黑洞** | 不知道是door问题还是roof问题 | 单体输出，PipelineStepResult只记录步骤名 | `agent_service.py:56-63` PipelineStepResult结构，无component_id追溯 |

## 二、LangGraph 分片架构

### 2.1 核心思想

**把"一口吞下整个 Blueprint"拆成"骨架→并行填肉→组装校验→精修"。**

每个节点：独立 RAG（按 entity_type 过滤，不互相竞争）+ 独立工具 + 独立 LLM 调用。

### 2.2 图结构总览

```
                              ┌─────────────────┐
                              │   用户输入       │
                              └────────┬────────┘
                                       │
                              ┌────────▼────────┐
                              │  Layer 0: 骨架   │  RAG(建筑类型 + 结构)
                              │  walls + floors  │  + get_wall_bounding_box
                              └────────┬────────┘
                                       │
                    ╔══════════════════╪══════════════════╗
                    ║                  │                  ║
              ┌─────▼─────┐    ┌──────▼──────┐    ┌─────▼─────┐
              │   doors   │    │   windows   │    │   roof    │  ...
              │ RAG(door) │    │RAG(window)  │    │ RAG(roof) │
              └─────┬─────┘    └──────┬──────┘    └─────┬─────┘
                    ║                  │                  ║
                    ╚══════════════════╪══════════════════╝
                                       │
                              ┌────────▼────────┐
```

## 三、每层详解

### 3.1 Layer 0: 骨架生成（顺序，不可并行）

**为什么先跑**：walls 和 floors 是所有其他组件的依赖根。door/window 需要 `parentWall`，roof 需要 wall bounding box，railing 需要 floor。

**输入**：用户自然语言 + 建筑类型

**RAG**：
```
doc_type=building_type  →  确定默认语义、最小构件集合
doc_type=recipe         →  组装顺序、参数关系
entity_type=structural_component → 柱梁楼板规则
entity_type=wall        →  墙体参数
```

**输出**：骨架 Blueprint（仅含 walls + floors + columns + beams）

```
{
  "meta": { "version": "1.1", "type": "building", "name": "中式庭院" },
  "geometry": {
    "elements": [
      { "type": "floor", "id": "ground", ... },
      { "type": "wall", "id": "wall_front", ... },
      { "type": "wall", "id": "wall_back", ... },
      ...
    ],
    "components": []   // 暂时为空
  },
  "materials": { ... }
}
```

**成功后**：运行 `get_wall_bounding_box`，把墙的包围盒写入 state，供后续节点使用。

### 3.2 Layer 1: 并行组件生成（fan-out）

**为什么可以并行**：每种组件只依赖 Layer 0 的骨架 + 自己专属的 RAG。door 不需要等 window 生成完。

**每个节点内部流程**：

```
该组件 RAG（entity_type 精确过滤）
  → 骨架上下文注入（wall 列表、floor 列表、bounding box）
  → LLM 生成该组件的 fragments
  → 输出: [{ type: "door", id: "door_01", parentWall: "wall_front", ... }, ...]
```

**当前支持的 10 种组件及其节点**（基于 `wild-compiler/componentRegistry.ts` 实际注册表）：

| 节点 | RAG entity_type | 编译器函数 | 依赖 | 编译后产出 |
|---|---|---|---|---|
| doors | `door` | `compileDoor` | walls | opening + primitive.box×3 (门框) |
| windows | `window` | `compileWindow` | walls | opening + primitive.box×N (窗框+窗棂) |
| roof | `roof` | N/A | walls (bounding box) | roof element (非compiled) |
| railings | `railing` | `compileRailing` | walls/floors | primitive.cylinder×N + beam×M |
| canopy | `canopy` | `compileCanopy` | walls | primitive.box (板) + primitive.cylinder×4 (柱) |
| balcony | `balcony` | `compileBalcony` | walls/floors | floor (悬挑板) + railing (内嵌) |
| ramp | `ramp` | `compileRamp` | floors | primitive.box (坡面) + railing (可选) |
| bay_window | `bay_window` | `compileBayWindow` | walls | opening + primitive.box×N (投影+窗框) |
| cornice | `cornice` | `compileCornice` | roof | primitive.profile_sweep (飞檐轮廓) |
| chimney | `chimney` | `compileChimney` | roof | primitive.cylinder (筒体) + primitive.box (压顶) |
| lights | `light` | `compileLight` | 无 | primitive.sphere (灯泡) + primitive.cylinder (灯座) + behavior |

**每新增一种编译器类型 → 在图中加一个并行节点 + 一条 edge。** 节点之间完全独立，互不影响。编译器注册机制见 `wild-compiler/componentRegistry.ts:registerComponentCompiler()`。

### 3.3 Layer 2: 合并 + 校验 + 回调

#### 合并策略

```
骨架 Blueprint
  + doors fragments    → 追加到 geometry.components
  + windows fragments  → 追加到 geometry.components
  + roof fragment      → 追加到 geometry.elements
  + ...每个组件的 fragments
  → 完整 Blueprint
```

合并时校验：
- ID 不重复（节点之间使用确定性前缀：`door_`、`win_`、`roof_`）
- 引用完整性（`parentWall` 指向真实存在的 wall id）

#### 校验流水线（复用现有 15 步）

```
validate_blueprint_structure → validate_element_required_fields
  → validate_reference_integrity → validate_opening_coords
  → validate_opening_fit → validate_wall_junctions
  → validate_stair_alignment → validate_roof_coverage
  → validate_element_dimensions → fix_* (自动修正)
  → recheck → validate_collision
```

#### 回调机制（关键创新）

与当前单体 Agent 不同，回调不是把错误信息丢给 LLM 让它猜，而是：

```
回调 payload = {
  // 1. 精确的校验失败信息
  failed_components: [
    {
      "id": "door_front",
      "type": "door",
      "error": "from[0]=5.8, 父墙 wall_front 长6m, 门宽1.2m → 右边缘超出0.6m",
      "tool_suggestion": "建议 from[0] 改为 4.2（居中偏右）或减小 width"
    }
  ],

  // 2. 当前骨架的完整信息（让 LLM 知道可用的墙/地板/柱子）
  skeleton_summary: "wall_front(0→6m), wall_left(0→5m), floor_ground(6×5m)",

  // 3. 出问题组件的 RAG 片段（精确召回，不与其他组件竞争）
  rag_snippet: "door.from[0] 是沿墙距离，范围 0~墙长-门宽。opening 坐标同理。",

  // 4. 已通过校验的组件（LLM 不要重写它们）
  passed_components: ["door_back", "window_left", "window_right"]
}
```

**LLM 拿到这个 payload 后**：不需要猜哪里错了，直接修正 `door_front.from[0]`。修改范围被精确限定在失败组件。

**重试控制**：

```
max_retries = 3
retry_count = 0

while 有未修复的错误 and retry_count < max_retries:
    对每个失败的组件:
        回调 → LLM 修正 → 重新校验
    retry_count += 1

if retry_count >= max_retries and 仍有错误:
    → 标记为 "需要人工介入"
    → 返回部分结果 + 错误详情（而不是静默丢弃）
```

### 3.4 Layer 3: 环境精修（可选，后续迭代）

在核心建筑通过全部校验后，附加非结构性增强：

- 地形（简单高度场或 flat ground）
- 环境光/时间（day/dusk/night）
- 植被占位（简单 primitive 表示，不做粒子系统）
- 外部装饰（飞檐、石狮、影壁等）

**这一层的失败不影响核心建筑**。如果环境生成失败，用户至少可以得到一个通过校验的建筑 Blueprint。

## 四、State 定义

```python
from typing import TypedDict, NotRequired

class GenerationState(TypedDict):
    # ── 输入 ──
    user_message: str
    building_type: str

    # ── Layer 0: 骨架 ──
    skeleton_blueprint: dict              # walls + floors + columns + beams
    skeleton_summary: str                 # 供后续节点注入
    wall_bounding_box: dict               # get_wall_bounding_box 结果

    # ── Layer 1: 分片（并行） ──
    door_fragments: list[dict]            # geometry.components 格式
    window_fragments: list[dict]
    roof_fragment: dict | None
    railing_fragments: list[dict]
    furniture_fragments: list[dict]
    light_fragments: list[dict]
    # ... 其他组件

    # ── Layer 2: 合并 + 校验 ──
    merged_blueprint: dict
    validation_results: list[dict]
    failed_components: list[dict]         # 需要回调修正的
    passed_components: list[str]          # 已通过校验的组件 ID
    retry_count: int
    max_retries: int

    # ── 回调 ──
    callback_context: dict                # RAG + tools 结果

    # ── Layer 3: 精修 ──
    environment_config: dict | None

    # ── 最终输出 ──
    final_blueprint: dict
    error: str | None
    status: str                           # "complete" | "partial" | "failed"
```

## 五、与现有系统的复用

| 现有模块 | 在 LangGraph 中的角色 |
|---|---|
| `agent_service.py` 校验流水线 | Layer 2 直接复用 `run_validation_pipeline()` |
| `spatial_tools.py` 16 个工具 | 每个节点可选调用 + 回调时强制执行 |
| `RAGSpecLoader` + `retrieve_many()` | 每个节点独立 RAG，按 `entity_type` 过滤 |
| `MarkdownChunker` | 不变 |
| `compileBlueprintComponents()` | Layer 2 合并后调用，展开 components |
| `prompts.py` | 拆分为 per-node prompt 片段 |
| `blueprint_parser.py` | 归一化 + Schema 校验在每个节点输出时执行 |

## 六、预期收益

| 指标 | 当前（单体 Agent） | LangGraph 后 |
|---|---|---|
| 组件类型错误 | 偶发，不可控 | 大幅降低（每个节点 RAG 精准，不竞争） |
| 修复效率 | 重新生成整个 Blueprint | 只重试失败的组件 |
| 调试诊断 | 不知道是哪个组件的问题 | 每个节点独立日志 |
| 扩展新组件 | 改 prompt + 改 RAG 查询 | 加一个节点 + 一条 edge |
| 上下文利用率 | 8 路查询竞争一个 top_k | 每路独立 top_k |
| 最大重试 | 无（一次失败 = 整轮失败） | 每个组件最多 3 次回调 |
