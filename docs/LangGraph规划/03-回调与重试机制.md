# 回调与重试机制

> LangGraph 最关键的设计：校验失败后，如何让 LLM 精准修正，而不是盲目重来

---

## 一、当前问题（基于实际agent_service.py实现）

**代码位置**: `wild-server/app/services/agent_service.py:736-760`

现在单体 Agent 校验失败后的处理：

```python
# 实际代码片段
pipeline_results = run_validation_pipeline(json_data)
fatal_steps = _final_errors(pipeline_results)
error_summary = None
if fatal_steps:
    error_summary = "校验流水线存在错误: " + "; ".join(
        f"Step{r.step}({r.name})" for r in fatal_steps
    )
return QueryResult(
    text=reply,
    blueprint=json_data,
    error=error_summary,
    pipeline_results=pipeline_results,
)
```

**当前PipelineStepResult结构**（`agent_service.py:48-53`）：
```python
@dataclass
class PipelineStepResult:
    step: int | str           # 流水线步骤编号
    name: str                 # 校验器名称
    output: str               # 人类可读的校验结果文本
    has_error: bool           # 是否包含❌错误
    has_warning: bool         # 是否包含⚠️警告
```

**问题**：
- `error_summary` 只是步骤名拼接，不含构件级定位
- `output` 是文本而非结构化数据，LLM难以精确解析
- 无法区分是`door_front`还是`door_back`的问题
- 无父墙/父楼板的空间上下文数据
- LLM不知道哪些组件已通过可以不改

## 二、回调 Payload 设计

每次回调传递结构化上下文，而不是一行错误文本：

```python
@dataclass
class CallbackPayload:
    # ── 失败组件的精确信息 ──
    failed: list[ComponentFixRequest]

    # ── 当前场景的骨架信息 ──
    skeleton_summary: str

    # ── 已通过校验的组件（LLM 不要碰它们）──
    passed_component_ids: list[str]

    # ── 专项 RAG 片段 ──
    rag_snippets: list[str]

@dataclass
class ComponentFixRequest:
    component_id: str          # "door_front"
    component_type: str        # "door"
    current_params: dict       # 当前出错的参数
    error: str                 # 人类可读错误
    tool_data: dict            # 工具返回的空间数据
    suggestion: str            # 建议的修正值
```

### 具体实例

LLM 生成了一个门，`from[0]=5.8`，但父墙长 6m，门宽 1.2m：

```python
CallbackPayload(
    failed=[
        ComponentFixRequest(
            component_id="door_front",
            component_type="door",
            current_params={
                "type": "door", "id": "door_front",
                "parentWall": "wall_front",
                "from": [5.8, 0.0, 0],
                "width": 1.2, "height": 2.2,
                "interaction": {"mode": "swing", "hingeSide": "left", "openAngle": 90}
            },
            error="from[0]=5.8 + width=1.2 = 7.0m，但父墙 wall_front 长 6.0m。"
                  "门右边缘超出墙体 1.0m。",
            tool_data={
                "wall_length": 6.0,
                "wall_from": [0, 0, 0],
                "wall_to": [6, 3, 0],
                "valid_range_for_door": "from[0] 应在 [0, 4.8] 范围内",
                "sibling_openings": [
                    {"id": "window_left", "from": [1.0, 0.9, 0], "width": 1.2}
                ],
                "available_space": {
                    "0_to_1.0": "window_left 占据",
                    "2.2_to_4.8": "可用",
                    "4.8_to_6.0": "空间不足（仅 1.2m 但容纳不下 1.2m 宽门 + 余量）"
                }
            },
            suggestion="建议 from[0]=3.0（居中偏右，窗口右侧 0.8m 处）"
        )
    ],
    skeleton_summary=(
        "wall_front: from=[0,0,0] to=[6,3,0], 长度 6.0m, 顶高 3.0m\n"
        "wall_back: from=[0,0,5] to=[6,3,5], 长度 6.0m, 顶高 3.0m\n"
        "wall_left: from=[0,0,0] to=[0,3,5], 长度 5.0m, 顶高 3.0m\n"
        "floor_ground: from=[0,0,0] to=[6,0,5], 6×5m"
    ),
    passed_component_ids=["door_back", "window_left", "window_right"],
    rag_snippets=[
        "opening 和 door 的 from[0] 是沿墙距离（单位米），" 
        "从 parentWall.from 沿墙方向量起。范围: 0 ≤ from[0] ≤ 墙长 - 宽度。",
        "典型门宽 0.9~1.2m，门高 2.0~2.4m。门之间建议间距 ≥0.3m。"
    ]
)
```

### LLM 收到的回调 Prompt

```
以下是你在上一轮生成的 door_front 的校验错误。请修正该组件。

## 错误详情

- 组件: door_front (door)
- 错误: from[0]=5.8 + width=1.2 = 7.0m，但父墙 wall_front 长 6.0m。
  门右边缘超出墙体 1.0m。
- 建议: from[0] 应在 [0, 4.8] 范围内

## 父墙信息

wall_front: from=[0,0,0] to=[6,3,0], 长度 6.0m
可用的沿墙空间: [2.2, 4.8] 区段（约 2.6m）

## 参考知识

opening/door 的 from[0] 是沿墙距离，从 parentWall.from 沿墙方向量起。
范围: 0 ≤ from[0] ≤ 墙长 - 门宽。典型门宽 0.9~1.2m。

## 已通过校验的组件

door_back, window_left, window_right — 这些组件不要修改。

## 请输出修正后的 door_front 组件

只输出一个 JSON 对象，不要输出完整 Blueprint：
{"type":"door","id":"door_front","parentWall":"wall_front","from":[?,0,0],...}
```

## 三、RAG + Tools 在回调中的配合

纯 RAG 和纯 tools 在回调中各有盲区：

| | RAG | Tools |
|---|---|---|
| 能提供 | "正确的做法是什么" | "你具体错在哪里" |
| 盲区 | 不知道当前场景的精确数值 | 不知道该建议什么值 |

**组合使用**（回调时两者都跑）：

```
step 1: 跑 tools → 拿到 wall_length=6.0, valid_range=[0, 4.8]
step 2: RAG 精确查询 "door from 坐标 沿墙距离" → 拿回规则说明
step 3: 组装 callback_payload（tools 数据 + RAG 知识）
step 4: LLM 拿到完整上下文 → 修正
```

## 四、重试控制

```python
class RetryController:
    max_retries: int = 3
    retry_count: int = 0
    failed_history: list[dict] = []  # 追踪每次失败的组件

    def should_retry(self, component_id: str) -> bool:
        """同一组件连续失败 3 次 → 放弃重试，标记为需人工介入。"""
        failures = sum(
            1 for f in self.failed_history
            if f["component_id"] == component_id
        )
        return failures < self.max_retries

    def escalate(self, component_id: str) -> dict:
        """重试耗尽 → 降级处理。"""
        # 选项 A: 移除该组件，返回不完整但可渲染的 Blueprint
        # 选项 B: 用最简版本替换（如把 door 变成简单的 opening）
        # 选项 C: 标记为 needs_human_review，前端展示
        return {
            "action": "remove_or_simplify",
            "component_id": component_id,
            "fallback": {
                "type": "opening",
                "id": f"{component_id}_fallback",
                "parentWall": "...",  # 从 last_attempt 中提取
                "from": [0, 0, 0],
                "width": 1.0,
                "height": 2.0,
                "style": "rectangular"
            }
        }

    def record_failure(self, component_id: str, error: str, attempt: int):
        self.failed_history.append({
            "component_id": component_id,
            "error": error,
            "attempt": attempt,
            "timestamp": time.time()
        })
```

### 重试流程图

```
                    ┌──────────────┐
                    │ 校验失败组件 │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │ retry_count  │
                    │  < max?      │
                    └──────┬───────┘
                      Yes  │  No
                           │
              ┌────────────▼────────────┐
              │  构建 callback_payload  │         ┌──────────────────┐
              │  RAG + tools + skeleton │         │  降级处理        │
              └────────────┬───────────┘         │  移除/替换/标记  │
                           │                     └──────────────────┘
              ┌────────────▼───────────┐
              │  LLM 修正（只输出该   │
              │  组件的修正版本）      │
              └────────────┬──────────┘
                           │
              ┌────────────▼───────────┐
              │  重新校验该组件        │
              └────────────┬──────────┘
                     通过  │  仍失败
                           │
              ┌────────────▼───────────┐
              │  合并修正后的组件     │
              │  继续校验其他失败组件 │
              └───────────────────────┘
```

## 五、回调 Prompt 模板

```python
CALLBACK_PROMPT = """你是 WILD 蓝图修正专家。以下是上一轮生成的组件校验错误，请逐一修正。

## 场景骨架（只读）

{skeleton_summary}

## 需要修正的组件

{formatted_failed_components}

## 相关规范知识（RAG）

{rag_snippets}

## 已通过校验（不要修改）

{passed_component_ids}

## 规则

1. 只修正上面列出的失败组件，不要改动已通过的组件
2. 使用骨架信息中列出的真实 wall/floor id 作为 parentWall/parentFloor
3. 每个组件只输出 JSON 对象，不要输出完整 Blueprint
4. 输出格式:
   [
     {{"type":"door","id":"door_front","parentWall":"wall_front","from":[3.0,0,0],...}},
     {{"type":"window","id":"window_right",...}}
   ]
"""
```

## 六、与当前系统的对比

| | 当前（单体 Agent） | LangGraph 回调 |
|---|---|---|
| 错误信息 | 一行文本: "Step4(validate_opening_coords) error" | 结构化: 组件 + 字段 + 范围 + 建议值 |
| LLM 知道什么 | 只知道"有什么错了" | 知道"哪个组件的哪个字段错了，正确范围是什么" |
| 修正范围 | 重新生成整个 Blueprint | 只修正失败的组件 |
| 兜底 | 返回 error，前端显示"生成失败" | 降级处理：移除问题组件或简化替换 |
| 修正成功率 | ~30%（LLM 猜不中正确值） | 预计 ~80%（LLM 拿到精确范围和当前值） |
