# 实施路线与验收

## 1. 阶段顺序

```text
P0 基线
 → P1 字段与上下文贯通
 → P2 统一解析
 → P2A 设计决策与缺口契约
 → P2B 审核前设计完善循环
 → P3 默认值与归一化边界
 → P4 设计履约验收
 → P5 表达能力（分批）
 → P6 材质与能力查询（分批）
 → P7 视觉反馈及对照
```

2026-10-08：P1、P2、P2A、P2B、P3 代码已完成，P4 代码已完成（见 [执行记录](P4-执行记录.md)），测试交由用户；下一阶段是 P5-A。P3 见 [执行记录](P3-执行记录.md)。P2A/P2B 是新增阶段，其余编号保留。代码完成与运行验收分别记账，未反馈测试不写成通过。

P0 起建立验收样本；P4 是将验收接入产品交付，并非此前不测试。P5、P6 每增加一种能力，都要接入 P4 的验收，不允许先累积一批字段后再找使用者。

## 2. 阶段退出条件

| 阶段 | 退出条件 | 不应做的事情 |
|---|---|---|
| P0 | 当前数据链、问题最小复现、测试与运行限制有记录 | 修改生产生成行为 |
| P1 | 实例完整往返；修订看到原设计；有针对性回归 | 重写整个状态系统 |
| P2 | 同设计同版本下预览与编译共用实体几何语义 | 用另一套近似公式掩盖差异 |
| P2A | 需求/决定可追踪；最小缺口评价有消费者；旧文档兼容 | 只加无人读取的 State 字段 |
| P2B | 审核前有界补全；按证据关缺口；批准后保持执行边界 | 把编译成功当作设计完成 |
| P3 | 显式值与默认值可区分；语义修改不再静默 | 删除所有确定性规则 |
| P4 | 每个已支持要求有实现证据；状态能区分缺失 | 把未知要求全部判成功或全部阻断 |
| P5 | 每个新增自由度均能输入、审核、编译、验收 | 一次引入完整 BIM/室内设计系统 |
| P6 | 无资产材质分支可用；能力查询与实现一致 | 让在线 Agent 每次扫描整个仓库 |
| P7 | 固定视角真渲染；修订有预算；对照数据可复核 | 无界重试、仅凭模型自评宣布提升 |

## 3. 第一阶段必须覆盖的测试矩阵

测试由用户执行，Agent 提供用例和观察点，不自行运行。下表是测试目标，不要求机械地逐行创建一个新文件。优先复用现有夹具和参数化测试。

| 测试 | 输入变化 | 必须观察到的结果 |
|---|---|---|
| 设计往返 | 0/1/多个 components，含 host/size/form/material_role | plan → document → approved plan 不丢语义 |
| 局部修订 | 只修 roof、只修 facade、修 massing | 模型看到实际前置内容；无关字段保留；依赖可失效重算 |
| 槽位一致 | 矩形、L 形、上下层不同轮廓 | 预览与最终宿主、尺寸、位置一致 |
| 默认与显式 | 缺失值、合法显式值、越界值、非法类型 | 分别默认、保留、报具体问题；不以同一 fallback 混处理 |
| 已批准设计 | 尺寸、体量、屋顶在修复前后变化 | 可解释的变更记录；不静默更改批准内容 |
| 确定性 | 同设计、同材质、同解析版本连续执行 | 除明确排除的运行元数据外结果一致 |
| 履约 | 几何合法但缺露台/开口/指定材质 | 履约不能判 fully satisfied |
| 设计补全 | 用户要求存在，但设计缺字段且编译合法 | 创建设计任务，写回当前设计后重新评价 |
| 任务失效 | 任务基于旧版本、宿主因体量修订变化 | 旧补丁不直接覆盖新设计；关联结果失效重算 |
| 有界终止 | 重复缺口、模型故障、不支持能力 | 有明确停止原因与剩余缺口，不伪称完成 |
| 兼容 | 历史文档缺少新增字段 | 明确迁移规则，旧样本可读取，默认被记录 |

## 4. 效果对照任务

建议固定以下 8 类任务，每类先运行 3 次；这是实施目标，不是已完成数据。预算不足时先完成前 3 类，并记录缩减原因。

1. 简单矩形两层住宅：检验基础稳定性与成本。
2. L 形别墅，二层侧翼退台并形成露台：检验设计保真。
3. 主体坡屋顶、侧翼平屋顶：检验逐体量表达。
4. 一段无窗实墙与另一段开敞柱廊：检验围护与开口语义分离。
5. 明确入口宽度与指定立面窗宽：检验显式尺寸。
6. 无 PBR 资产的浅灰矿物墙面、深色金属、暖木入口：检验材质设计。
7. 用户明确不要阳台或烟囱：检验负向要求，不靠数量堆细节。
8. 超出现有引擎支持范围的形态要求：检验能力反馈与降级透明度。

每个任务提前固定：完整提示词、可机器判定要求、可人工评价项、已知引擎能力边界。不能看到结果后再修改答案标准。

## 5. 公平比较方式

主比较采用相同模型/版本、WILD 输出协议、引擎版本、材质资源、最大模型调用数、Token 或金额预算。记录实际消耗，不要求各链路调用结构相同。

比较三组：P0 当前版本、优化版本、通用 Agent。通用 Agent 可以读取同一仓库，但不能通过修改引擎或直接生成 Three.js 绕开 WILD 输出限制。若要比较“允许改引擎”的通用 Agent，单独建立探索组，不与主比较混算。

每次保存：请求、设计文档及版本、归一化变化、解析产物、最终 Blueprint、验收报告、固定视角截图、耗时、调用数、Token、失败原因。大 trace 放测试产物目录并遵守忽略规则，不默认提交到 Git；移除凭据及无关个人信息。

指标分别报告，不先合成一个容易掩盖问题的总分：

- 用户明确要求满足率：满足项 / 可判定要求项；unsupported、needs_review 单独计数，不能从失败样本中隐去。
- 批准设计保真率：已实现决策 / 可验证决策；报告被默认值或修复改写的项。
- 几何有效率：通过实际引擎重建与规定检查的样本比例。
- 视觉质量：匿名、随机顺序的成对人工比较，评估体量层次、入口、立面节奏、材质协调。
- 稳定性与成本：成功次数、失败类型、调用数、Token、耗时中位数；小样本不声称统计显著。

最低交付条件：确定性契约用例全部通过、没有已知无声丢字段问题、批准硬条件不被静默破坏。视觉与性能提升幅度必须由实测填写，不能提前写“提升 50%”。

## 6. 验证命令与限制

以下命令供用户执行，Agent 不自行运行。用户从仓库根目录进入对应目录后执行；先确认环境和依赖已就绪，不自动更新锁文件。

```powershell
# 在 wild-server 目录，按阶段选择相关用例；完整路径集合不是每阶段必跑清单。
uv run --no-sync pytest tests/design tests/compiler tests/agent tests/components tests/plan

# 在 wild-core 目录，仅涉及引擎契约时。
npm run typecheck

# 在 wild-web 目录，涉及前端、编译器或渲染链路时选择对应检查。
npm run check:core
npm run check:compiler
npm run check:rendering
npm run build
```

若 Windows 在导入 asyncio 时出现 WinError 10106，记录为环境阻断。可以继续静态分析、补齐测试和测试说明，但不可把 AST 检查称为业务回归通过，不可在没有既有授权时修改系统网络配置。真实运行在可用环境完成后，才能关闭阶段的运行验收项。

## 8. 新增阶段依赖与优先级

P2 解决同一设计的解释一致性，不承担 SVG 美化。P2A 先对现有协议可表达的层数、体量、屋顶、开口、实例和材质角色建立最小设计缺口判断；P2B 才启用任务循环。能力边界读取现有契约/注册表，不等待 P6 的完整查询工具。

P3 扩展字段级来源及归一化审计时接回 P2A 的决定和缺口，避免另建审计 ID。P4 在相同要求 ID 下检查最终 Blueprint；设计层满足不直接推导成品满足。P5/P6 每批新增能力都要同步设计检查、任务写入和最终验收。P7 才引入真实图像评价。

退台露台是解释闭环的例子，不是要求当前协议立即支持全部露台几何。现有能力无法表达的部分在 P2A/P2B 明确标 unsupported，留到 P5 对应批次，不能通过增加虚构字段假装完成。
