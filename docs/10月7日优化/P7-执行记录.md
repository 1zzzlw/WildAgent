## P7-B：视觉评价（`app/agent/vision/evaluation.py`，43tests 全绿）

### 结论先行：模型没有图像输入能力，所以分两层

`app/llm/` 全库grep `vision|image_url|multimodal` **零命中**；`invoke_llm` 走 LangChain
`ainvoke` 只传纯文本消息。所以：

| 层 | 谁产出 | 能不能自动 |
|---|---|---|
| `proxy_metrics` | 本模块，从蓝图实体字段算 | 能 |
| `human_review` | **只产出待填模板**，`complete=False` | 不能 |

`merge_evaluation` 的`complete` 恒等于 `human.complete` —— proxy 全绿**也不等于**评价完成。

### 四个评价项与实测值（P7-A 真实基线：14×10 两层，8 面外墙，每面 2~3 扇窗）

| 评价项 | 判据（全部从实体字段算） | 实测 | 状态 |
|---|---|---|---|
| `entrance_legibility` | 门是否落在外墙、是否唯一、有无雨棚 | 临街面 1 樘门，唯一入口 | ok |
| `facade_rhythm` | **同一面墙内窗中心间距**的相对离散度 > 0.45 **或** 最小间距 < 0.6m | 长边4.7/4.7、短边 3.4/3.3 | ok |
| `massing_hierarchy` | 屋面数 ≥ 体量数（体量数取自**设计文档** `decisions.volumes`） | 无设计文档时体量数不可知 | **missing** |
| `material_harmony` | 材质引用种类数（≤2 层次过弱 / >8 拼贴） | 6 种材质、0 种带贴图 | ok |

真实基线结果：`ok=3`、`needsReview=[]`、`missing=['massing_hierarchy']`。

### 落地过程中改掉的 4 个真bug（都不是"写错"，是"看起来对"）

1. 🔴 **雨棚判反**：`has_canopy_on_front` 被塞进"问题列表"，`notes` 非空就翻成
   `needs_review` ⇒ **装了雨棚反而被报待复查**。改为雨棚只进 `detail`/`evidence`。
2. 🔴 **体量读错位置**：初版读 `blueprint["volumes"]`，但编译后的蓝图里**没有这个字段**
   （体量在设计文档 `decisions.volumes`）⇒ 这一项恒为 `missing`。改为从设计文档取，
   没有就如实说"体量数不可知"，不拿别的东西凑数。
3. 🔴 **贴图字段是编的**：初版写 `textureSet` ⇒ schema 里根本没这个字段，
   贴图数**恒为 0 且不报错**。查 schema 改成真名 `textures.{baseColor,normal,…}`，
   并加守卫测试 `test_texture_slots_exist_in_schema`。
4. 🔴 **材质漏了一大半**：只读 `material` 字段。但 schema 里门是
   `frameMaterial`/`leafMaterial`、窗是 `frameMaterial`/`glassMaterial`
   ⇒ 真实基线的 6 种材质被算成 3 种。改为覆盖 `_MATERIAL_REF_FIELDS` 全部 10 个引用位，
   守卫测试直接对着 schema核字段名。

### 判据选错的两处（更值得记）

| 初版判据 | 为什么错 | 改成 |
|---|---|---|
| **跨墙开窗密度比**（各墙开口数/墙长的离散度） | 长墙3 洞/ 短墙 3 洞是完全正常的（密度必然 0.214 vs 0.300），会被误判；而真正的问题"开口挤在一端"恰恰是**同墙内**的事，跨墙比值**看不见** | 同墙内**窗中心间距**的离散度 |
| 跨墙密度 + 最短墙长过滤 | 女儿墙是14m 长 × 0.3m 高，水平长度过滤拦不住 | 间距判据天然不需要这个过滤（女儿墙挂不了 2 扇窗） |

补充实测发现：**门不参与窗的节奏统计**。门宽 1.0m 与窗宽 1.5m 不同，中心间距天然
对不齐，混算会把"门+两窗"的正常立面判成间距 0.75/4.0（相对差 0.81）——
这就是初版夹具反复红的真实原因。门的位置另由 `entrance_legibility` 管。

### 一个只有 2 扇窗时才暴露的盲区

`wall_front_1` 在真实基线里只有 2 扇窗 ⇒ 间距列表长度 1 ⇒ `max == min` ⇒
**相对差恒为 0**。把两扇窗挪到 0.2m 间距后判据仍报 `ok`。补了绝对下限
`_RHYTHM_MIN_GAP = 0.6m`，两条判据取或。守卫测试
`test_rhythm_flags_two_windows_clustered_even_with_equal_gaps` 钉住这个盲区。

## P7-C：有界视觉修订（`app/agent/vision/revision.py`，40 tests 全绿）

### 接入方式：不造新链，复用既有受控变更通路

调研结论（`app/agent/generation/architecture/`）：`convergence.py` 与 `completion.py`
已经实现了 P7-C 要的**全部预算机制**（轮数 / 无进展 / 调用预算）与
**证据 → 块 → 写权限白名单 → 接受/拒绝**全流程。所以本模块只做两件既有链路**没有**的事：

1. **视觉证据作为第三种evidence**（前两种是 design gaps + compile defects）；
2. **回退**（`completion.py` 只有"拒绝坏候选"，没有"选历史最优版本"）。

### 五条要求逐条对应

| P7-C 要求 | 落点 |
|---|---|
| 1. 首版 ≤ 2 轮 + 调用/时间预算 | `_MAX_ROUNDS=2`、`_CALL_BUDGET=4`、`_MAX_NO_PROGRESS=2`；`diag.budget` 回报已用调用，`diag.elapsedSeconds` 量耗时 |
| 2. 走既有受控变更接口，不绕过编译器 | 只经 `draft_design_blocks(only_blocks=…)`；产出仍要过 `normalize_architecture_plan` → `compile_document`。**不接触 three.js、不改渲染代码、不直接改蓝图** |
| 3. 能力缺失只标记不阻断 | 没接渲染回调 ⇒ **一次模型都不调**，`stopReason=no_issues`，产物恒可用；模型故障 ⇒ `model_error` + 保留当前版本 |
| 4. 每次候选重跑解析+几何校验+履约 | `candidate_verdict` 三条**合取**：编译零 error ∧ 校验流水线零 error ∧ 履约缺口不增 ∧ 可见问题不增 |
| 5. 变差回退 + 旧证据留痕 | `RevisionLedger` 逐版留`design_hash` / 蓝图引用 / 评价 / verdict / 截图路径；`pick_best` 按**同一套判据**选最优，不是"最后一版" |

### 落地过程中改掉的 3 个真bug

1. 🔴 **`normalize` 越权闸误拒所有候选**（最严重）：越权检查用 `normalized[f] != plan.get(f)`
   判语义相等，但 `normalize_architecture_plan` 走 `exclude_none` 语义
   （`tiers: null` 那个键被整个删掉），而 `architecture_plan_from_document`
   从 pydantic `model_dump` 取值（`null` 键还在）。两者**语义完全相同**但 `!=` 为真
   ⇒ **"归一化越权修改 massing"对每一个候选都触发，包括空补丁**
   ⇒ 修订永远不生效，而诊断只显示"越权修改 massing"，完全看不出真实原因。
   修法：`_same_semantics()` 递归剔 `None` 后比较。
   ⚠️ `completion.py:155` 有**同样一行**（P2B 既有缺陷，不在本轮范围，未改）。
2. 🔴 **候选刚通过校验就崩溃**：`shots[0]` 在渲染回调没给图时 `IndexError`——
   恰好发生在"一次成功的修订即将落地"的那一刻。改为 `shots[0] if shots else None`。
3. 🔴 **`allowed_blocks` 未定义**：删参数时漏改函数体引用 ⇒ `NameError` 被
   `except Exception` 吞成"rejectReason"，看起来像模型问题，实际是代码问题。

另修一处**会静默失效**的闸：把写权限白名单从"本轮授权块"放宽到"全部块"之后，
`semantic_roots - allowed` 恒为空集 ⇒ 那道归一化越权检查**形同虚设**。
已恢复按块收紧（与 `completion.py` 同口径），并在注释里写明这个耦合。

### 诚实边界（写进 docstring，不是口头）

- `missing` **不进**修订队列 —— 数据不足不是设计问题，拿它改设计是在修不存在的问题；
- `confidence == "low"` 只记录不自动改；
- 找不到设计字段映射的意见只记录（`_VISION_FIELD_MAP` 是闭集，映射不到就不猜）；
- 没渲染 ⇒ 不做视觉评价（不是"用几何数据凑一个评价"）。

### 闭环验证到什么程度

- ✅ 代码路径：发现 → 证据 → 候选 → 三条校验 → 采纳/回退，**在真实编译产物上跑通**
  （`tests/vision/test_revision.py` 用 `tests/fixtures/design_trace_baseline.json` 真实编译，
  只有模型调用换桩件）。
- ✅ "发现"这一环确实来自真实引擎渲染（见上节肉眼确认）。
- ⚠️ **未做**：没有真调模型跑完一次完整修订（预算与用户验收范畴）。
  桩件测的是"给定模型返回什么，系统怎么处置"，不是"模型能不能改对"。

## P7-D：对照评测（`app/agent/vision/benchmark.py`，34 tests 全绿）

### 已完成：任务集与判定标准（冻结）

8 类任务全部按路线文档 §4 落地，每类都固定了：完整提示词 / 可机器判定要求 /
人工评价项 / **已知引擎能力边界**（能力边界必填—— 漏了会让"能力不足"被误判成
"生成失败"）。20 条判定函数名集中在 `CHECKS` 注册表，**判定逻辑不许内联**
（内联 = 把答案标准藏进实现，改实现等于改标准且报告里看不出来）。

**防"事后改标准"**：`task_spec_digest()` 给出任务集内容摘要（sha256 前 16 位），
报告里必须带上 ⇒ 前后两份报告能否直接比较，一眼可判。

### 指标按路线文档 §5 分开报告，不合成总分

`ScoreCard` **故意没有 `overall` 字段**（守卫测试 `test_scorecard_has_no_overall_field`
钉住）。独立指标：满足率 / 几何有效率 / `byStatus`（含 `unsupported`、`needs_review`）
/ 失败类型 / 耗时中位数 / 调用数中位数 / Token / 截图索引。

`significance_claim(n)` 把"小样本不声称统计显著"做成规范的一部分：
n<5 时输出"只能给观察，不能声称统计显著"。`coverage_note()` 强制记录缩减了哪几类。

### 🔴 通用 Agent 组：本轮**没有运行条件**，明确标缺

`general_agent` 组的定义是"一个没有 WILD 约束的通用 coding agent 读同一仓库产出结果"。
**本仓库不存在这样的东西**，也不该在框架里伪造一个。守卫测试
`test_framework_provides_no_general_agent_implementation` 直接扫源码，
禁止出现 `run_general_agent` / `GENERAL_AGENT_PROMPT` 之类实现 ——
否则"三方对照"会退化成"同一套东西跑三遍"，对照结论全是假的。

所以本轮对照评测的真实状态：

| 组 | 状态 |
|---|---|
| `p0_baseline` | 框架就绪，**未运行**（需 P0 存档入口） |
| `optimized` | 框架就绪，**未运行**（主模型已配置：API key / base URL / 模型名均已设置） |
| `general_agent` | **缺运行条件** —— 需外部通用 coding agent |

三组都没跑 ⇒ **本轮不产出任何对照结论**。框架能给的是：任务集、判定标准、
指标口径、以及一份"缺哪组、为什么缺"的清单。
