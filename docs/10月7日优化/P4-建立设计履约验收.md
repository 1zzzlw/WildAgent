# P4：建立设计履约验收

状态：未实施。前置：P3。目标：几何正确、设计完成和视觉质量分别有证据。

## 可直接使用的提示词

```text
请实施 WildAgent 建筑生成优化 P4。读取 docs/10月7日优化/03-Agent执行总约束.md，并沿 final_validate → agent_delivery → API/前端实际交付路径核对状态语义。

任务 A：建立最小可判定要求
1. 复用 DesignDocument 的 requirements、constraints、locks；先支持现有协议能表达的明确尺寸、层数、体量、屋顶、开口、实例和材质角色。
2. 区分用户硬要求、已批准的模型设计选择和默认值。不要把“生成别墅”自行扩展成用户要求平屋顶/退台。
3. 要求有稳定 ID、来源和对应设计路径；与最终实体通过 ID/宿主/解析映射连接，不靠对文案做关键词搜索就判满足。
4. 无法可靠解析的自然语言要求标 needs_review，能力不支持标 unsupported；不得默默删掉后再计算高满足率。

任务 B：交付验收
1. 在几何校验之后，对当前最终 Blueprint 验证已支持要求；输入应包含批准设计和共享解析结果，不能只拿最终 Blueprint 自证正确。
2. 每条结果包含 expected、actual、status、evidence(entity IDs/design paths)、相关设计版本；状态可复用现有枚举，避免重复定义。
3. 几何有效性与设计履约分开记录。为旧 complete/partial 的调用方明确兼容方案，不贸然改枚举导致前端不保存，也不能继续让缺失要求显示成“全部满足”。
4. 合法但不完整的产物可按既有政策交付并展示缺口；几何阻断错误仍禁止保存或自动加载。
5. 缓存有效性同时考虑 Blueprint、批准设计/约束和验收器版本。不能只因 Blueprint 指纹没变就复用旧设计的验收。
6. merge/repair 后重验受影响要求；修复不能以删掉要求或降低严重性获得通过。
7. 不在本阶段假装评估“美观”；视觉项明确待人工/后续 P7 评价。

重点入口：app/design/contracts.py、resolver.py，app/agent/validation/design_constraints.py、workflow.py、diagnostics.py，app/services/agent_delivery.py，相关事件契约与前端结果展示。

测试：
- 几何合法但指定屋顶类型错误，履约不通过。
- 组件数量相等但宿主/位置错误，不通过。
- 没有明确要求的装饰缺失，不误判用户要求失败。
- unsupported/needs_review 不变成 satisfied，也不使所有生成无条件失败。
- Blueprint 相同但设计要求改变，旧验收不复用。
- 人工批准后的实例在末端修复被替换，验收可发现。
- 部分交付与几何错误的前端/服务行为符合兼容方案。

交付时提供一份机器可读履约报告和用户能理解的缺口摘要。任何状态语义变化都更新正式 Agent 文档与相关契约测试。
```
