## P6-A：材质设计与资产匹配分离

### 问题

旧实现用 `elif catalog:` 把两件事绑成一个条件：**是否需要材质设计决策** 与
**是否有资产可匹配**。后果：在没有贴图目录的机器上，用户明确提了配色要求
（"外墙用浅灰"）也会整段跳过，材质意图**静默丢失** —— 用户看不到任何提示。

而合法参数材质（`baseColor` / `roughness` / `metallic`）**不依赖贴图**就能承载设计。

### 判据改成三真值

`app/agent/generation/material/plan.py::needs_material_design` 返回 `(需要, 原因)`：

| 条件 | 结果 | 实测输出 |
|---|---|---|
| 无材质要求 + 无资产 | False | `'没有材质要求、也没有可匹配资产，走确定性角色表'` |
| **无资产 + 有材质要求** | **True** | `'用户明确提到材质/配色（facade_primary）'` |
| 有资产 + 无要求 | True | `'有可匹配的 PBR 资产，需要决定资产与角色的对应'` |

判"要不要设计"只看**用户有没有提**，不再看资产数量。函数注释明确写了
"不要在这里判断资产数量来代替判断设计需求"。

### 三张词表各有职责，不可混用（落地时踩到的坑）

| 词表 | 用在哪 | 收什么 | 不收什么 |
|---|---|---|---|
| `_MATERIAL_INTENT_TERMS` | 提需求时 | 含具体材质名（"红砖"、"清水混凝土"） | — |
| `_MATERIAL_FEEDBACK_TERMS` | 给反馈时 | 只收**决策词**（材质/颜色/配色/幕墙…） | 🔴 **不收**"木""金属"这类材质名词做子串匹配 |
| `_MATERIAL_NAMES` + `_SURFACE_ROLE_WORDS` | 反馈第二路判据 | **材质名 + 表面角色词同时出现**才算"在说材质" | 🔴 角色词**刻意不含 structure** |

两轮误判的实测对照：

```
屋顶坐标偏了，往北挪两米  []            ← 纯几何修复不动材质
外墙颜色太深了            ['颜色']
把木梁换成混凝土柱        []            ← 结构变更不换全楼颜色
门改成玻璃的['<材质名+角色词>']  ← 零决策词但明确是材质变更
卧室地板想用木的          ['<材质名+角色词>']
二层栏杆高度不对          []
结构换成钢结构            []
```

第二轮误判的原因：先用纯决策词表漏判"门改成玻璃的"；补第二路后，
`柱` 命中了 `structure` 角色的同义词，而 `structure` 的同义词又含"混凝土"（与
`_MATERIAL_NAMES` 重叠）⇒ "木梁换混凝土柱"被误判。修法是改用独立的
`_SURFACE_ROLE_WORDS`（不含 structure），与角色同义词表解耦。

### 其他改动

- `workflow.py`：`elif catalog:` → `elif needs_design:`，新增 `design_decided` /

  `:352` 包住 `procedural` 写入）。本轮验证继续生效并写了测试钉住，没发现第二个入口。

## P6-B：可机械提取的引擎能力查询面

`app/agent/generation/capability.py`（约 340 行）。

### 纪律：能机械提取的从事实源读，不能机械提取的语义人工维护

事实源唯一：`storage/knowledge_base/schema.json`（必填/类型/枚举/范围）+
`generation/component/registry.py::COMPONENT_REGISTRY`（已实现/写 elements 还是
components/规则文本）。

🔴 **不建第二份字段白名单** —— 那必然与 schema 漂移。
验证方式：测试 `test_surface_follows_schema_without_manual_edit` 用 monkeypatch
往 schema 加字段，断言查询面**自动看到**。

### 四态语义互不相同

| 状态 | 含义 |
|---|---|
| `ok` | 查到且引擎支持 |
| `not_found` | 引擎里没这个类型（带 `available` 列表，"查不到要说有什么，否则模型无从纠正"） |
| `unsupported` | 注册表标 `implemented=False` |
| `query_failed` | 查询面自身不可用（schema 读不到） |

混成一个会让模型去请求实际不存在的能力，或把真不支持的能力当可用。

### 落地时修掉的 2 个真 bug

1. 🔴 **失败结果被缓存**：`capability_surface` 把空字典写进 `_capability_cache`
   ⇒ schema 一时读不到之后，**整个进程的能力面永久为空**。
   正确口径是"没读到就每次重试"；读到但内容为空才缓存。
   修法：`if surface or _capability_cache: _capability_cache = surface`。
   （这个 bug 是被 `test_query_failed_is_distinct_from_empty` 撞出来的 ——
   monkeypatch 后 `_capability_cache` 变 `{}`，导致后续 6 条用例全部报"不存在"。）
2. 🔴 **人工语义表的键必须与 schema 的 type 字面一致**，否则就是**静默失效**
   （表里写好了，查询时永远读不到）。有守卫测试。

### 接入

`design_workflow.py::format_capability_section` 只对**写构件实例的块**
（`target == "components"`）注入能力摘要，且只列**构件类** —— 元素类
（wall/column/primitive…）由骨架确定性派生，不列。长度裁到 2600 字以内。

示例（canopy）：
```
必填：type、id、parentWall、from、width、depth、thickness
坐标语义：from=[沿墙距离, 雨棚板底Y, 法向偏移]
宿主约束：parentWall 必须指向有真实门窗的墙
```

**测试**：`tests/generation/test_capability_surface.py`，14 条全绿。
