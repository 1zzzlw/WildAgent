# editor 对比与 WILD 渲染质量优化建议

日期：2026-10-27。

范围：对比 WildAgent 与 `E:/AgentProject/editor` 的渲染、几何和材质实现，并落实一批 WILD 引擎优化。第 1—7 节保留实施前的分析；第 8 节记录已实现内容、真实验证和未覆盖边界。editor 实现未修改。

实施前的证据等级：源码核对，以及实际安装的 Three.js r160 法线变换数值探针。实施后已增加几何回归、真实 Chromium/WebGL 检查与完整建筑出图，详见第 8 节；未做硬件 GPU 性能基准，未调用模型生成新建筑。

## 1. 结论

WILD 有明确的优化空间，重点是让紧凑蓝图稳定地产生正确、精细的几何与表面，再让现有渲染能力持续生效。

两个项目都用结构化数据描述建筑，并通过程序化几何和 Three.js 呈现。实现存在差别：WILD 使用独立 Core、Worker 和 WebGL 渲染适配；editor 使用场景节点、按脏节点更新的构件系统，以及 WebGPURenderer / TSL。GLB 是 editor 的一种几何来源，不能把其整体观感全部归因于 GLB。

最值得借鉴的顺序：

1. 统一材质与几何之间的物理尺度约定，修复已确认的着色坐标问题。
2. 沿现有构件编译器完善可复用的细节，把设计差异保留在小型参数中。
3. 扩展已有材质预设的覆盖与明确选择，避免不同材料长期共享近似外观。
4. 让交互降画质可恢复，让静止画面使用用户选择的质量档。
5. 复用现有缓存和实例化，逐步更新受影响几何，为细节腾出性能空间。

## 3. editor 中值得借鉴的具体做法

### 3.1 建筑构件拥有可见的构造层次

editor 的 `packages/viewer/src/systems/window/window-system.tsx:1632` 构造窗框、窗扇、玻璃，`:1756` 生成铰链标记，`:1780` 处理窗台。`door/door-system.tsx:1291` 将门把手绑定到独立 hardware 材质槽。

WILD 的 `wild-core/src/compiler/components/window.ts:19` 已支持窗框、玻璃、窗棂和移动窗扇；但当前 `WindowComponent`（`wild-core/types.ts:270`）没有窗台及五金的显式参数。门已有把手几何，但当前公开 `DoorComponent`（`:243`）没有 editor 那样独立的五金材质控制。

建议在现有组件和通用几何中补齐高收益细节：有设计依据的窗台与窗框截面、五金材质槽、收边与必要的接缝。已有 `profile_sweep` 和 `cornice` 应继续复用；小倒角可作为后续通用几何能力评估，不能声称 editor 的所有构件都默认倒角——其窗户 `addShape` 明确使用 `bevelEnabled: false`（`window-system.tsx:281`）。

外观细节必须尊重设计。不能给每扇窗无条件加窗台，也不能用自动装饰改写建筑风格。模型选择构件与设计参数，代码确定性计算细节位置、尺寸和重复构造。

### 3.2 材质按真实尺度使用

editor 的 `packages/viewer/src/lib/box-uv.ts:13` 将 box 的每个面换算为米制 UV；`DECISIONS.md:54` 明确“1 UV 单位 = 1 米”。`packages/core/src/material-library.ts:74` 的材质目录同时组织颜色、法线、粗糙度、AO 贴图以及重复频率。

WILD 已具备相同方向的部分能力，但仍有可定位的缺口：

- `mesh-helper.ts:77` 的回退 UV 按包围盒归一化为 0..1；`beam.ts:31` / `:90` 的网格没有专用 UV，最终会走这一回退。
- `column.ts:54` 的柱身 UV 为归一化参数；`primitive.ts:260` 的截面扫掠沿路径使用总长度归一化，沿截面使用边序号比例。
- `materialAdapter.ts:488` 将 `uvScale` 直接写入 `texture.repeat`。同一材质在不同 UV 约定的几何上，无法自动维持相同物理纹理密度。
- PBR 入库保存 `realWorldSizeMeters`（`PBRAssetPanel.vue:274`、`asset_storage.py:216`），但 Core 材质输出（`primitive/materials/apply.ts:58`）只消费纹理与 `uvScale`，没有直接将该物理尺寸转换为采样频率。
- 默认程序化表面使用世界坐标米制投影（`defaultSurfaceMaterial.ts:205`），已经绕开部分 UV 问题；专用砖材质却直接把 UV 当米（`proceduralMaterials/brickMaterial.ts:118`），所以缺口也影响非贴图材质。

这是可以独立于某一栋建筑解决的通用问题。应明确平面、圆柱、扫掠等几何的尺寸和方向契约，同时处理实例缩放。沿现有版本兼容方式保留旧蓝图外观，不能直接把所有 0..1 UV 改成米而忽略既有 `uvScale`。

### 3.3 稳定的材质配方与部件绑定

editor 的优势之一是材质目录和构件槽位的配合，不只是纹理文件多。

WILD 的 `wild-core/src/materials/descriptor.ts:80` 支持显式 `surfaceFamily`，但也通过材质名推断族；石材、混凝土、抹灰和部分屋面会落入同一个 mineral 族。默认处理适合作为兜底，不能替代明确的材料选择。

建议先完善现有数值型预设：将需要区分的材料映射到明确的图案、方向、尺度、粗糙度和色差；继续使用现有 `surfaceFamily` / `surfacePattern` / 材质注册入口。检查生成与手工编辑最终是否真正绑定这些预设，不能仅凭“预设代码存在”认定建筑已经使用。

保持 WILD 小文件定位：程序化配方优先；若使用 PBR 贴图，沿已有资产引用机制复用共享资源，不将图片或模型大量内嵌到蓝图。共享纹理不等于 GLB 模型，但其外部依赖和资源体积必须单独计量。

### 3.4 后期管线的可控组合

editor 的 `packages/viewer/src/components/viewer/post-processing.tsx:65` 虽命名为 SSGI，但默认 `giIntensity: 0`；`:529` 配置该值，`:552` 对 AO 降噪，`:571` 组合输出。因此不能把它描述成“已经默认开启强全局光照”，也不能据此要求 WILD 先迁移 SSGI。

WILD 精细档已经有 GTAO 和深度/法线引导降噪（`postProcessingRuntime.ts:123`）。应优先检查接触阴影、透明面排除、采样分辨率及实际档位，随后再用具体画面决定是否需要更复杂的光照算法。

### 3.5 细节与更新性能一起设计

editor 的 `WindowSystem`（`window-system.tsx:113`）按脏节点处理，且限制每帧重建数量和耗时（`:141`）。墙的批处理也接入既有脏节点生命周期（`packages/nodes/src/wall/wall-batch-system.tsx:472`）。

WILD 虽已有 Worker、Core 编译缓存、共享材质和实例化，但 `renderEntity.ts:576` 每次更新仍先清理当前组，再重新填充 Three.js 对象。编译缓存命中不代表 GPU 几何对象得以复用。

建议以现有源构件 ID 和编译映射为依据，逐步复用未改变的对象，只重建受影响的几何与实例桶，处理宿主和依赖联动。按需要加入细节等级，避免所有距离都生成不可见的微小几何。该项首先改善编辑成本，并为更精细模型提供容量；不能宣称它单独会改变静态画面的美观。

## 4. 当前源码中确认的优化候选

### 4.1 自适应降级后没有按静止或负载恢复画质

`CanvasViewport.vue:692` 至 `:708`：持续低于 30 FPS 超过两秒，降低像素比、关闭 AO、水面反射与 Bloom，并降低 MSAA。`:1694` 的 `applyQualityPreset()` 才重置降级标记；初始化、手动切质量档或外观 profile 更新会调用该入口。

这不是已复现的“当前场景根因”，但有明确机制风险：短时高负载后，场景静止仍可能维持降级画质。

建议沿现有循环区分交互质量与静止质量，在负载稳定或停止交互后恢复用户档位，使用必要的稳定条件避免反复抖动。已有 `qualityFallback` 诊断字段，应优先复用并核对实际状态。

### 4.2 专用砖 Shader 混用了法线坐标空间

`proceduralMaterials/brickMaterial.ts:74` 当前写法：

```glsl
vWildBrickWorldNormal = normalize(mat3(modelMatrix) * transformedNormal);
```

实际安装的 Three.js `defaultnormal_vertex` 在赋值前已经执行 `normalMatrix * transformedNormal`，此处的 `transformedNormal` 是视图空间法线。再乘模型矩阵不能还原世界法线。WILD 默认表面（`defaultSurfaceMaterial.ts:154`）与 PBR 天气层（`pbrEnvironmentMaterial.ts:63`）已采用从视图空间还原的正确方向。

数值探针使用实际安装的 Three.js r160，以单位模型矩阵、世界法线 `[0, 0, 1]` 为输入：

| 相机绕 X 轴旋转 | 当前砖材质算出的“世界法线” | 正确世界法线 |
| --- | --- | --- |
| 0° | `[0, 0, 1]` | `[0, 0, 1]` |
| 60° | `[0, 0.866025, 0.5]` | `[0, 0, 1]` |

该法线的 Y 分量用于雨、雪、尘的方向判定（`brickMaterial.ts:175` 至 `:184`）。因此相机俯仰可能改变墙面的积雪积尘判断；此结论有坐标计算证据，尚无 GPU 截图验证。它不直接决定砖缝 UV，不能扩大为“所有砖纹都会随相机移动”，也不能认定为普通无天气画面粗糙的主因。

最小修复应统一已有法线空间约定，分别验证普通 Mesh、实例化和非均匀缩放，避免新建一套变换逻辑。

## 5. 建议的实施与验收顺序

| 顺序 | 工作 | 成功标准 |
| --- | --- | --- |
| 先建立可复现基线 | 固定已有 `.wild`、相机、光照、曝光和分辨率；记录实际质量档及降级状态 | 从同一输入稳定重现待改善的区域，无需重新调用模型生成 |
| 第一批：正确性 | 砖法线空间；梁、柱、扫掠等纹理密度；物理尺寸的消费约定 | 相机变化不改变世界方向判断；同材料在不同尺寸与方向上的砖缝/木纹保持预期尺度；旧蓝图兼容 |
| 第二批：外观收益 | 扩展现有材质配方及绑定；在现有窗、门、檐口中补足设计要求的截面和细节 | 正面、斜视及近景可辨材料差异和构造层次；不改变已批准的体量、宿主和开口尺寸 |
| 第三批：稳定画质 | 可恢复的交互降级；核对 AO、反射与抗锯齿的实际生效状态 | 高负载结束后恢复所选质量；无反复闪变；静止截图与指定档位一致 |
| 按容量需要推进 | 复用未改网格、更新受影响实例桶及必要的细节等级 | 修改一个构件不导致无关 GPU 几何反复创建；选取、开合、拖动、撤销及宿主联动仍正确 |

每一批分别报告：静态与几何检查、浏览器真实渲染、视觉查看，以及必要的性能测量。建议保留普通立面、曲面/柱、玻璃/室内三类代表场景，固定条件后检查不同观察角度；不以三角形数量增加、代码通过或一张远景图代替视觉验收。

## 6. 为什么暂不把迁移 WebGPU 排在前面

当前本地 editor 的 viewer 依赖 `three ^0.186`，并使用 WebGPURenderer / TSL；WildAgent 的前端依赖 `three ^0.160`，自定义材质通过 `onBeforeCompile` 注入 GLSL。迁移会涉及材质、后期和兼容性，不能作为一次单纯的参数升级处理。

Three.js 官方文档说明 WebGPURenderer 是一种可选择不同后端的渲染器；它本身不会补出蓝图缺失的窗台、修正纹理密度或替代材质设计。先解决上述已定位的正确性、构造细节和质量状态，再由具体性能或算法需求决定是否迁移。

技术说明参考：[WebGPURenderer](https://threejs.org/docs/pages/WebGPURenderer.html)、[MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html)。官方文档描述当前 API，涉及 WILD r160 的行为以本地安装源码为准。

## 8. 已实现与验证记录

### 8.1 本次实际修改

| 修改 | 实现与作用 |
| --- | --- |
| 默认表面微起伏 | 在固定别墅、相机和光照下关闭 AO / 表面层检查，确认默认表面层仍会产生明显颗粒。将 mineral 默认高度振幅从 16mm 调整到 1.2mm、wood 从 10mm 到 0.5mm、metal 从 4mm 到 0.04mm、neutral 从 10mm 到 0.8mm；保留低频色差和微肌理。砖缝及显式木板、石英石图案的配方独立，不修改蓝图尺寸和用户指定的基础粗糙度。 |
| 统一默认表面的采样尺度 | 默认颜色变化和原有凹凸共用米制世界坐标，避免木纹、拉丝等随构件归一化 UV 被拉伸。移除本次改动造成的未使用 UV varying。 |
| 砖材质法线空间 | 复用默认表面已有的 `inverseTransformDirection(transformedNormal, viewMatrix)`；雨、雪、尘使用正确世界方向。真实 GPU 输出验证相机俯仰前后法线一致。 |
| 尺寸型材质的语义 UV | 在现有 builder 注册入口增加可选运行时参数；程序化砖、具有 `realWorldSizeMeters` 的纹理资产请求米制 UV。梁按表面展开，柱/圆柱按参考圆周与高度展开，扫掠按路径累计长度和截面累计边长展开；无专用 UV 的旧网格逐面展开，避免侧面 UV 被压扁。实例缩放按三角面切向长度修正密度。 |
| 物理纹理尺寸落到采样 | `applyMaterials` 用资产物理宽高换算纹理重复频率：`实际 repeat = uvScale / realWorldSizeMeters`。后端将物理尺寸纳入资产内容 ID，防止相同图片、不同物理尺度被错误去重。 |
| 可恢复的交互降级 | 降级仅在交互过程中触发；停止交互约 600ms 后恢复所选档位的分辨率、AO、反射与抗锯齿。恢复定时器随新交互、手动切档和卸载正确取消。 |
| 增量更新 Three.js 对象 | 复用未改变的网格和相同成员的实例桶，更新实例变换与剔除包围盒；只释放被替换或移除的对象。源几何、材质、交互定义与初始变换未变化时，保留门窗开合和灯具状态。共享材质仍走既有生命周期。文字招牌继续重建，保证其子材质被正确续持和释放。 |

没有新增 WILD 字段，没有改建筑生成链、提示词或原始蓝图，也没有引入 GLB、WebGPU 或第二套生产渲染路径。

### 8.2 兼容性与未实现项

- 直接使用 `textures` / `embeddedImage` 的旧图片材质继续保留原有 UV 和 `uvScale` 含义；本次几何回归覆盖了这一边界。
- 具有物理尺寸的纹理资产现在真正消费该尺寸，因此此前依赖“尺寸被忽略”的画面会改变。既有资产 ID / URL 仍可读取，不改写存量文件；新入库资产的 ID 会包含尺寸。
- 圆柱/柱身周向使用参考圆周，球体使用经纬展开。锥度、柱槽、弯曲扫掠和非均匀曲面仍不能理解为全表面严格等距 UV；本轮验证了常见平面、直扫掠、圆柱/柱、旋转和实例缩放，未宣称完成任意曲面的 UV 展开器。
