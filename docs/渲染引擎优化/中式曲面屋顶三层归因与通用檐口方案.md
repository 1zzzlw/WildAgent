# 中式曲面屋顶三层归因与通用檐口方案

> ✅ **本文的档 A / 档 B / 档 C 已全部实施完毕**（2026-09-16），
> 实施记录、验收证据与顺带发现见 [屋顶檐口通用化实施报告](屋顶檐口通用化实施报告.md)。
> 本文保留为方案原文（§六的落地顺序即实际执行顺序）。
>
> 触发：`中式意境别墅：L形体量高低错落，曲面屋顶飞檐起翘… .wild` 渲染出的屋顶是一块"黑帐篷"，
> 屋脊下方还露出一块浅灰板；此前刚落地的檐口线脚（档 2）在本蓝图**完全没有生效**。
>
> 本文回答三件事：① 为什么没生效；② 这条屋顶本身错在哪；③ 我的档 2 有没有违反
> 《渲染引擎优化指南》的通用性原则，以及正确的通用写法是什么。

蓝图路径：`D:\Backup\Downloads\中式意境别墅：L形体量高低错落，曲面屋顶飞檐起翘，主翼分明营造层次，庭院感空间组织.wild`

## 一、结论先行（三层归因）

| 层 | 现象 | 归属 | 根因 |
|---|---|---|---|
| **L1 直接原因** | 檐口线脚「完全没变化」 | 我的档 2 设计缺陷 | roofType 是 `chinese_curved`，被 `roof.ts:9-10` 早返回 + `roof.ts:37` 的 `gable\|hip` 闸门双重挡下；`resolver.ts:260` 也只为 gable/hip 注入 `_eave` |
| **L2 屋顶自身** | 屋面像一块黑帐篷、起翘处有硬折 | 渲染引擎（几何） | ① 壳体在檐口处**非流形**（52 条未配对边）且体积算出 **−12.8（负）**，两半绕序相反；② 主网格**不产出 `normals`**，靠 `computeVertexNormals()` 兜底把 1920 个不共享顶点的三角形逐面平面化 |
| **L3 那块灰板** | 屋脊下方露出 4m 宽浅灰板 | **resolver 判定塌缩** | `resolveRoofBoundary` 的"结构墙"闸门是 `墙高 ≥ 全局最大墙高×50%`。本蓝图每层外墙各自只有 3.2 m，而贯通 1F~3F 的核心筒是单段 9.6 m → 结构墙集合塌缩成**只剩 5 面混凝土核心筒墙** |

## 二、L1：为什么档 2 在这里完全没有生效

### 2.1 事实

```
【1】屋顶元素 1 个
  roof_main  roofType=chinese_curved  span=13.2 depth=9.7 height=3 thickness=0.3
     position=[6, 9.6, 4.25]  material=roof

【2】buildRoof 分支判定
    早返回分支   = ✅ 命中（roof.ts:9-10，直接 return，不进入线脚段）
    檐口线脚分支 = ❌ 未命中（roof.ts:37 只认 gable|hip）
    线脚实际生成 = 否
```

### 2.2 代码位置

```ts
// roof.ts:9-10 —— 中式两种屋顶在这里就 return 了，根本走不到线脚段
if (roofType === 'chinese_pagoda') return buildPagoda(params, pos);
if (roofType === 'chinese_curved') return buildChineseCurved(params, pos);

// roof.ts:37 —— 即便不早返回，线脚也只认 gable/hip
if (trimSpec && (roofType === 'gable' || roofType === 'hip')) {

// resolver.ts:260 —— 注入端同样只喂 gable/hip
if (roof.roofType === 'gable' || roof.roofType === 'hip') {
  (roof as any)._eave = { material: trimMaterial };
}
```

**三处同向的 `gable|hip` 闸门**，所以 `chinese_curved` / `chinese_pagoda` 必然拿不到线脚。
这不是"没生效"，是**从来没被覆盖到**。

## 三、L2：`buildChineseCurved` 的壳体几何缺陷

`verify-curved-roof.mjs` 输出（span 13.2 × depth 9.7 × h 3 × t 0.3）：

```
[0] materialRef=roof  三角面=1920  顶点=962  边=2880
    水密 = ❌   未配对边 52   退化面 0
    分量 1   逐分量 χ: V962-E2880+F1920=2
    体积 = -12.8040                       ← 负数
    法线朝向: 朝上 864  朝下 864  竖直 192
```

### 3.1 未配对边全部落在檐口

52 条未配对边样例**全部**是 `x = ±6.6 = ±hw`：

```
-6.60000,0.26042,-4.04167|-6.60000,0.54000,-4.85000 ×2
-6.60000,0.24000,-4.85000|-6.60000,-0.03958,-4.04167 ×2
...
```

即 `roof.ts` 的**檐口封边**（`point(side, crossSegments, di, ·)` 那一圈）与它所连的
外/内表面**同向**而不是反向 → 无法成对。

### 3.2 两半绕序相反

`probe-curved-winding.mjs` 按 push 顺序切出四个面组，每组内部都是"朝上/朝下"精确对半：

```
外表面          tri=864  朝上 432  朝下 432
内表面          tri=864  朝上 384  朝下 384  竖直 96
檐口封边        tri=48   朝上  24  朝下  24
前后山面封边    tri=144  朝上  24  朝下  24  竖直 96
```

对半的原因是两个 `side` 分支的 `reverse` 参数（`quad(..., side === -1)` 外 /
`side === 1` 内）把**镜像本来就翻转的手性又翻了一次**，等于没翻。
结果：**约一半三角形法线朝反**，体积散度算出负值。

> 当前材质 `side` 缺省走 `DoubleSide`（`materialAdapter.ts:222`），
> 所以现在还不至于出现空洞；但《优化指南》§4.1 计划"为水密几何开启背面剔除"，
> 一旦开启，这条屋顶会直接破洞。**这是必须先修的地基。**

### 3.3 主网格不产出法线

```ts
// roof.ts:153-159  buildChineseCurved 的返回
const meshes: MeshData[] = [{
  geometry,
  indices: Uint32Array.from({ length: geometry.length / 3 }, (_, index) => index),
  uvs: new Float32Array(uvs),
  transform: { ... },
  materialRef: material || 'default',
}];              // ← 没有 normals
```

对比 gable/hip 主路径（`roof.ts:27`）与山墙填充（`roof.ts:199`）都有
`normals: attributes.normals`。`buildPagoda`（`roof.ts:245-265`）同样缺失。

`meshDataToGeometry.ts:44` 的兜底是 `computeVertexNormals()`。但这条网格用的是
**恒等索引、零顶点共享**（1920 个三角形各自独立顶点），`computeVertexNormals`
只能给出**逐面平面法线** → 举折曲面被折线化，飞檐起翘处出现硬折。
这正是《诊断流程》§七"错误 2：忘记生成法线/UV"的情形。

## 四、L3：那块灰板的根因在 resolver（本蓝图最关键的发现）

### 4.1 复现

```
全局最大墙高 = 9.60   50% 阈值 = 4.80
全部墙 21 面 → 通过高度闸门的「结构墙」 5 面:
    wall_core_front      h=9.60  top=9.60  concrete
    wall_core_right      h=9.60  top=9.60  concrete
    wall_core_back       h=9.60  top=9.60  concrete
    wall_core_left       h=9.60  top=9.60  concrete
    wall_core_partition  h=9.60  top=9.60  concrete
被 50% 闸门误杀的外墙: wall_front_1_1 h=3.20, wall_right_1_1 h=3.20, …, wall_left_3 h=3.20（共 16 面）
→ _gableEnds 命中 2 段: 4.5, 8.5
→ _eave.material = 众数 = concrete
```

`resolveRoofBoundary` 的原意是"滤掉阳台栏杆等矮墙"，但它拿
**单个墙段的自身高度**跟**全局最大墙高**比：

```ts
const maxWallHeight = max(|to[1] - from[1]|)          // = 9.6（核心筒）
const heightThreshold = maxWallHeight * 0.5           // = 4.8
const structuralWalls = walls.filter(
  w => |w.to[1] - w.from[1]| >= heightThreshold       // 每层外墙只有 3.2 → 全灭
)
```

**多楼层建筑的外墙是"按层切段"的，高度天然只有层高；只有贯通全高的核心筒/
电梯井是单段长墙。** 于是这个闸门在多楼层蓝图里必然只留下核心筒。

### 4.2 两个直接后果

1. **`_gableEnds` 只剩核心筒的 2 面墙**（Z=4.5 / 8.5，X 4~8，各 4 m 宽）。
   中式曲面屋顶的坡面在墙顶上方形成三角空腔，需要靠 `_gableEnds` 在**两端**填实。
   两端 12 m 全宽的封堵没生成 → 从正立面看，屋脊下方只露出一块 **4 m 宽的混凝土板**，
   其余敞开。**这就是截图里那块灰弧。**

   `preview-bp.mjs --only=roof_main --mat=roof --views=front` 的输出可直接对照：
   屋面自身在正中留出一个 V 形开口，开口处正好被那块 `concrete` 板填住。

2. **`dominantMaterialOf(effectiveWalls)` 取到 `concrete`**（核心筒材质），
   而不是外墙面 `wall_finish`。也就是说：即使档 2 的闸门放开，檐口饰面依旧会上错色。
   简单双坡别墅（`simple_villa.wild`）之所以看着对，是因为它的外墙本身就是整段高墙，
   闸门没有误杀——**档 2 的验证样本恰好绕过了这个 bug**。

## 五、关于约定：档 2 守住了分类，但没守住通用性

### 5.1 守住的部分 ✅

| 《优化指南》条款 | 档 2 的遵守情况 |
|---|---|
| §二 A/B/C 分类：用 `_` 前缀渲染私有字段 | ✅ 全程只用 `_eave`，没有新增任何 WILD 契约参数 |
| §一 C 类必须事前审批 | ✅ 未触碰 C 类，无需审批 |
| §3.1 修改位置应是 `geometry/roof.ts` | ✅ 改在渲染引擎，没有另开文件另立门路 |
| §七 错误 2：必须产出法线 | ⚠️ 线脚网格产出了，但**没发现同文件里 chinese_curved/pagoda 本来就没产出** |

### 5.2 没守住的部分 ❌

**违反 §八 核心原则第 1 条：「通用性优先：不为单一情况写专用逻辑」。**

具体表现有三处，全部是"按屋顶类型写死"：

1. `buildEaveTrim(roofType: 'gable' | 'hip', ...)` —— 函数签名里就写死了类型，
   内部再分 `if (roofType === 'hip')` / 否则当 gable 两套盒子拼装；
2. `roof.ts:37` 的 `roofType === 'gable' || roofType === 'hip'`；
3. `resolver.ts:260` 同一个闸门。

而"**檐口**"是所有屋顶类型都具备的概念（平屋顶有女儿墙压顶、穹顶有环梁、
中式有飞檐）。把它做成 **2/6 屋顶类型的特权分支**，代价是：

- 覆盖不全（本次现象）；
- `roof.ts` 从 255 行涨到 709 行，其中 **454 行只服务两种屋顶**；
- 每加一种 roofType 都要再补一支 —— 正是担心的"引擎越来越复杂"。

### 5.3 正确的通用写法：檐口 = 屋面边界环的扫掠

关键认识：**任何一个闭合屋面，它的下缘就是一条边界环。** 提取它不需要知道 roofType：

```
任意 roofType 的三角面
      ↓  有向边配对（1 正 1 反成对 → 配对失败的边即边界边）
   边界边集合
      ↓  按共享顶点链成环
   檐口环（gable/hip 是矩形环，dome 是圆环，
          chinese_curved 是带四角起翘的曲线环，pagoda 每层一个环）
      ↓  沿环扫掠一个截面（外挑 outset / 上包 top / 下挂 drop / 滴水线 lip）
   檐口线脚（单一算法，零 roofType 分支）
```

- **复用已有资产**：有向边配对这套机制 `lib/solid-check.mjs` 里已经实现（水密性判定就是它），
  不需要新造轮子。
- **收益**：
  - 覆盖从 2/6 → 6/6，且新 roofType 自动获得；
  - `roofType` 分支数 3 → 0，`buildEaveTrim` 的两套盒子拼装被一次扫掠替代；
  - 中式曲面屋顶的**飞檐起翘**天然成立 —— 线脚跟着起翘的环走，转角自己会翘起来，
    不需要再写"中式专用"的翘角逻辑。

## 六、建议的落地顺序

| 档 | 类型 | 内容 | 为什么排这个顺序 |
|---|---|---|---|
| **档 A** | A 类 | 修 `resolveRoofBoundary` 的承托墙判定：去掉"单段墙高 ≥ 全局最大×50%"的闸门，改为**按墙顶标高**筛（`|墙顶 − 全局最高墙顶| ≤ 0.05`），并保留"承托墙不足 3 面时回退"的兼容分支 | 它是灰板的根因，也污染了 `_eave.material`；不修则后面所有檐口都会上错色/填错位置 |
| **档 B** | A 类 | 修 `buildChineseCurved` 壳体：统一两半绕序、修正檐口封边配对方向、显式产出 `normals`；`buildPagoda` 同步补 `normals` | 屋面"黑帐篷 + 硬折"的直接原因；也是开启背面剔除的前置条件 |
| **档 C** | B 类 | 把檐口改成通用边界扫掠算子，**删除**档 2 的 `gable\|hip` 分支与两处闸门，替换为一次扫掠 | 兑现"通用性优先"，同时把 454 行按类型拼装的代码收掉 |

## 七、本文新增的诊断工具

| 工具 | 作用 |
|---|---|
| `analyze-curved-roof.mjs` | 屋顶元素清单 / 分支判定 / 产物网格 / 檐口线采样 / 承托墙布局 |
| `verify-curved-roof.mjs` | 曲面壳体几何体检：水密、逐分量 χ、体积、法线朝向（6 组参数） |
| `probe-curved-winding.mjs` | 按 push 顺序切面组，逐组统计法线朝向，定位哪一组翻转 |
| `preview-bp.mjs` | 通用蓝图预览：4~5 视角出 PNG + **材质分区 ASCII**；支持 `--only=` / `--mat=` / `--views=` / `--map=` |
| `png-materials.mjs` | PNG 按最近材质色分类成 ASCII（注意：着色会把亮材质压到别的基色，优先用 `preview-bp.mjs` 的精确材质图） |

### 踩坑记录

1. **`bp.geometry.elements` 上看不到 `_eave` / `_gableEnds`。**
   resolver 吃的是 `expandTemplates` **之后**的元素副本
   （`index.ts:236-239`），而 `compileBlueprintComponents` 又保证源 Blueprint 不变。
   要在副本本体上观察，必须自己 `compile` 一次再 `reconstructEntity(compiled)`，
   不能二次 `compile`（那会是另一份没跑过 resolver 的副本）。
2. **不要用颜色反推材质。** 着色会把 `wall_finish`（0.84,0.82,0.78）压成
   `floor_finish`（0.52,0.51,0.49）的基色，分类器直接判错。
   正解：光栅化时逐像素记录 winning mesh 的 `materialRef`，直接输出材质图。
3. **ASCII 分辨率不足会造出"假孔洞"。** 96×34 下轮廓斜边处整格多数是背景，
   看起来像洞；升到 176×62 后消失。判断真假孔洞要看高分辨率，或者直接用水密性门禁。
