## 结论（TL;DR）

| 问题 | 答案 |
|---|---|
| 原计划能省 50% 光栅化吗？ | ❌ **不能**。按三角形口径，只有 **16.5%** 的三角形来自可安全剔除的网格 |
| 直接改 `side` 默认值为 `front` 会怎样？ | ❌ **会大面积破面**。`lantu/tiantan.wild` 可见反面率 **53.65%**（屋面+大理石直接被撕掉） |
| A 类替代方案（渲染侧自动判定）值得做吗？ | ❌ **不划算**。只省约 8%，且能通过检查的恰好是低面数的轻量网格 |
| 应该做什么？ | ✅ 把绕序/水密当**几何引擎的数据质量 bug** 修。修它在 `DoubleSide` 下**观感零变化**，可安全排期 |

**本次决策：不修改 `side` 的任何语义，不动 `materialAdapter.ts`，不碰知识库/提示词/后端校验。**

## 一、原始提案与预期

| 项 | 内容 |
|---|---|
| 目标 | 节省约 50% 光栅化性能 |
| 原计划手法 | 为水密几何体设置 `side: 'front'` 开启背面剔除 |
| 曾归类 | 原文档一度当作 A 类"顺手优化" |
| 第一次纠正 | `side` 是**已文档化的 WILD 契约字段**（`BLUEPRINT-SPEC-MINIMAL.md:377`、`types/blueprint.ts:88`、`wild-core/types.ts:605`、`materialAdapter.ts:86`），改它默认语义属 **C 类**，必须先报告获批 |
| 本次纠正 | 即使获批，**技术上也不该做** —— 下面的实测数据是判决依据 |

代码现状（`renderer/materialAdapter.ts:220-222`）：

```ts
// 8. 兼容既有开放网格与历史构件中不一致的面绕序，默认双面渲染。
// 只有已经验证为封闭实体的材质才通过 side: 'front' 显式开启背面剔除。
material.side = params.side === 'front' ? THREE.FrontSide : THREE.DoubleSide
```

这句注释是**正确的防御性设计**，本次审计证实它防的正是真实存在的问题。

## 二、判据与验证方法

背面剔除安全的前提不是"看起来是实心的"，而是三项拓扑判据**同时**成立。缺任何一项都会出问题：

| # | 判据 | 不满足的后果 |
|---|---|---|
| A | **闭合性**：每条无向边恰好被 2 个三角形共用 | 剔除后露洞（壳体没封口） |
| B | **绕序一致**：同一无向边的两次使用方向相反（1 正 1 反） | 剔除后撕掉半个面（局部翻面） |
| C | **外法线朝外**：有向体积 `Σ a·(b×c)/6 > 0` | 绕序一致但整体朝内 ⇒ 整个物体被剔除掉 |

> 注意：**不能用"面法线是否背离重心"判断绕序**（只对凸体成立）。
> 也必须 A、B **都查** —— 只查 B 会漏掉"绕序一致但没封口"的壳，只查 A 会漏掉"封了口但翻面"。

另加一项直接度量（第四项）：**可见反面率**。从球面 N 个方向向场景打射线，取最近命中的三角形，
若最近命中偏偏是背面，则该像素在开启剔除后会变成洞。这是"到底会不会露洞"的实测，不依赖任何推理。

**工具**：`.workbuddy/diag/audit-winding.mjs`（用 vite `ssrLoadModule` 跑真实重建链路，
`parseWildBlueprint` + `reconstructWildEntity`，与浏览器同一条代码路径）。

## 三、实测数据

**样本**：7 个真实蓝图 / 337 个网格 / 59626 个三角形（`lantu/` 与 `scripts/fixtures/` 全量）

### 3.1 总体

| 指标 | 结果 |
|---|---|
| 可安全剔除（A + B + C 全过） | **193 / 337 网格 = 57.3%** |
| **按三角形口径的可剔除份额** | **9820 / 59626 tri = 16.5%** |
| 非流形边（>2 面共用） | **0** —— 全局没有非流形 |
| 闭合但整体朝内（C 失败） | **0** —— 没有整体翻面的实体 |

两个关键观察：

1. **"57.3% 网格"是个会骗人的数字**。网格数量上过半，但通过检查的全是
   `window_frame`、`oak_furniture`、`glass`、`oak_door` 这类**低面数轻量网格**；
   真正吃面数的 `column_red`(16384 tri)、`granite`(8708)、`wood`(4364) **全在失败名单里**。
   所以真实收益要看三角形口径：**16.5%**。
2. **缺陷只有两类**：开放壳（未封口）+ 绕序冲突（局部翻面）。

## 四、三个候选方案评估

### 方案 A：渲染侧自动判定剔除（A 类，零契约改动）

**做法**：在几何体与材质结合处（`materialAdapter.ts` 附近）对每个 `BufferGeometry`
跑一次 A/B/C 拓扑审计，通过的网格用 `FrontSide`，不通过的落回 `DoubleSide`。
`side` 契约字段语义**完全不变**，只是把"默认值"从写死的 `DoubleSide` 换成"按几何实测决定"。

| 维度 | 评估 |
|---|---|
| 视觉风险 | **零**（只剔除已被证明安全的几何体） |
| 契约影响 | 无（不改知识库/提示词/后端/既有 `.json`） |
| 收益 | **仅 16.5% 的三角形 × 约 50% ≈ 8% 光栅化** |
| 成本 | 每次几何变更要跑拓扑扫描（`Map` 边表，5 万面约几十 ms）；需按 geometry uuid 缓存 |
| 自维护性 | 好（几何修好后自动变为可剔除） |

**结论：不划算。** 8% 的光栅化节省，换来一个横跨"几何 + 材质 + 缓存"三层的运行时扫描机制，
且省下的恰好是窗框/家具/玻璃这些**本来就不费时**的轻量网格。
更重要的是：**它会把一个数据质量问题变成一个静默的渲染决策**，掩盖"屋面根本是反面朝外"这个事实。

### 方案 B：把 `side` 默认语义改成 `front`（C 类）

| 维度 | 评估 |
|---|---|
| 视觉风险 | **灾难性**。`tiantan` 53.65% 的可见面会消失；墙体/楼板/柱/石材全面破面 |
| 契约影响 | 需走 6 步全链：知识库 + 提示词 + 前端类型 + 后端校验 + 几何生成 + 验证；既有 `.wild` 需评估迁移 |
| 收益 | 名义 50%，实际受 3.1 节的 16.5% 上限约束 |
| 回滚 | 需重新发版 |

**结论：否决。** 数据已经证明它会造成大面积破面。

### 方案 C：修几何引擎的绕序/水密（真正的根因）✅ 推荐

| 维度 | 评估 |
|---|---|
| 视觉风险 | **零**（见下方说明） |
| 契约影响 | 无（几何生成实现修正，不是契约参数变更） |
| 收益 | 直接收益是数据质量；**是未来任何剔除方案的前置条件** |
| 成本 | 按材质逐个定位 primitive 生成器，可分批 |

**为什么"零视觉风险"**：本项目的材质光照走 `normal` 属性（由 primitive 生成器显式给出），
**不依赖面绕序**。同时 `DoubleSide` 意味着正反面都渲染。
所以修正绕序在当前的渲染配置下**观感完全不变** —— 可以独立、安全地分批修，不需要一次性做完。

**代价只有"少写了一行补丁的地方"**：修完之后，才能回头谈"是不是可以开剔除了" ——
到那时收益会从 16.5% 接近 100%，剔除去掉的那 ~50% 才真正兑现。

## 七、再评估的触发条件

只有满足**全部**下列条件，才值得重新考虑背面剔除：

1. `audit-winding.mjs` 的**三角形口径可剔除份额 ≥ 95%**；
2. 所有 `lantu/*.wild` 的**可见反面率 = 0.00%**；
3. 判据 C（闭合但朝内）仍为 0，判据 A/B 的残留缺陷<b>有明确归属</b>（不是"反正在容忍"）。

在满足这些之前，`materialAdapter.ts:220-222` 的双面默认值就是**正确实现**，不要动它。
