# 渲染引擎现状评估与照片级路线

> 触发：用户追问"渲染引擎有没有问题，有没有优化空间，我想生成图片中那样精细的图形，后续思路可以是什么"。
> 参照图：热带现代泳池别墅实拍（白墙 + 大挑檐 + 通高玻璃 + 木格栅顶棚 + 泳池 + 躺椅 + 绿植）。
> 对照产物：`wild-web/lantu/docs/renders/standalone_front.png`（当前引擎出图）。
>
> **本轮只读代码，未做任何改动。**

## 一、结论先行

引擎有 **3 个真问题**，其中前两个是**架构性**的（不是调参能解决）：

| 级别 | 问题 | 一句话 | 证据 |
|---|---|---|---|
| 🔴 P0 | **IBL 没有 `src/renderer/` 入口** | 材质层按"存在 `scene.environment`"设计，但生产环境贴图的那段代码被关在 Vue 组件里 → 查看器里所有环境反射失效 | `materialAdapter.ts:139-140,175` vs `CanvasViewport.vue:1363-1390` |
| 🔴 P1 | **AO / 接触阴影同样只活在前端组件** | 建筑与地面、柱脚、楼板下缘全部"贴"在一起，无体积感 | `EffectComposer` 全仓只在 `CanvasViewport.vue` 出现 |
| 🟡 P1 | **材质表达力单一** | 零贴图资产，程序化材质只有 `brick` 一个；表面只有 4~12mm 的"颗粒"，没有抹灰/木纹/石材/瓷砖 | `proceduralMaterials/` 仅 `brickMaterial.ts`；`defaultSurfaceMaterial.ts:62-67`；全仓 `.wild` 带贴图材质 **0 条** |

其余观感差距（挑檐太浅、柱太细、水面是平面）**不是引擎的问题**，见 §六 —— 别上错药。

## 二、P0：IBL 没有引擎入口

### 2.1 现状

材质层（`src/renderer/materialAdapter.ts`）明确按"环境光照存在"来写：

```ts
// materialAdapter.ts:139-140
// IBL 反射基准提高：非金属也有环境反射，金属/光滑面反射更亮；配合 scene.environmentIntensity。
material.envMapIntensity = Math.min(1.8, 1.0 + params.metallic * 0.5)
// :175  半透明物体再抬一次
material.envMapIntensity = Math.max(material.envMapIntensity, 1.05)
```

玻璃也按物理透射配好了：`transmission 0.92 / ior 1.5 / thickness 0.012 / attenuationColor`（`:144-157`）。

**但 `scene.environment` 全仓只有一处赋值**：

```
src/components/viewport/CanvasViewport.vue:1385    scene.environment = nextTarget.texture
```

生产者是一整段内联在组件里的代码：`pmremGenerator` / `environmentScene` / `environmentSky` /
`environmentSunSprite` / `rebuildEnvironment()`（`CanvasViewport.vue:1363-1390`）。
组件里那句注释本身就是证据：

> IBL 强度由 materialAdapter 的 envMapIntensity（非金属 1.0 / 金属 1.0~1.5）承担，
> 太阳亮点已通过 environmentSunSprite 注入环境贴图……

⇒ **材质层（`src/renderer/`）与光照生产者（`.vue`）被拆在两个地方。**
`src/renderer/worldEnvironmentRuntime.ts` 只导出**状态与 uniform**（`getWorldEnvironmentState` /
`subscribeWorldEnvironment` …），**不导出环境贴图**。

### 2.2 后果（这就是"不够精细"的第一主因）

`lantu/viewer/main.ts` 拿不到环境贴图，于是**自己搭了一套简陋光照**：

```ts
scene.add(new THREE.HemisphereLight(0xbfd4ff, 0x46413a, 0.9))   // :80
scene.add(new THREE.AmbientLight(0xffffff, 0.25))                // :81
const sun = new THREE.DirectionalLight(0xfff4e6, 2.2)            // :83
scene.background = new THREE.Color(0x0e1116)                     // 深色背景，不是天空
```

出图上直接能看到：

| 现象 | 原因 |
|---|---|
| 天空是**纯黑** | 查看器把 `scene.background` 设成深灰，引擎的 Sky 进不来 |
| 玻璃是**死蓝色块**，没有反射 | `scene.environment === null` ⇒ `transmission` 没有可折射的内容，`envMapIntensity` 全部失效 |
| 白墙**没有环境明暗过渡** | 只有半球光 + 环境光的粗糙近似，没有 IBL 的方向性 |
| 金属/光滑面**没有反射** | 同上 |

⇒ 这不只是"查看器不好看"。它同时**违反了项目红线**：
「**绝不在 `lantu/viewer/` 自实现材质/网格**，必须走 `src/renderer/` 的 `wildCoreAdapter` + `BlueprintRenderInstance`」。
现在查看器自实现了**光照** —— 性质一样，只是当年这条红线写在材质/网格上。

### 2.3 修法（A 类，纯渲染实现重组，不动 WILD 契约）

把"环境 → PMREM → `scene.environment`"整段从 `CanvasViewport.vue` 抽成
`src/renderer/environmentRuntime.ts`（或补进 `worldEnvironmentRuntime.ts`），对外暴露类似：

```ts
export function activateEnvironment(scene, renderer, preset, atmosphere): { dispose(): void }
```

- `CanvasViewport.vue` 改成调用它（行为不变，先做到零回归）；
- `lantu/viewer/main.ts` 也调用它，**删掉自建的三灯**；
- 顺手统一 `scene.background` 与 `renderer.toneMappingExposure`，别让两套界面各写各的。

这一项**不需要动任何 `._wild` 数据**，却能让玻璃、金属、白墙一次性接近照片观感 —— 性价比最高。

## 三、P1：AO / 接触阴影只活在前端组件

`EffectComposer`（含 AO）全仓**只在 `CanvasViewport.vue` 出现**，查看器完全没有后处理
（`lantu/viewer/main.ts` 只有 `renderer.shadowMap` + `PCFSoftShadowMap`，`:70-71`）。

照片里"檐下暗、柱脚暗、体量交接暗"这些**体积感**主要来自 AO / 接触阴影，不是来自主光。
出图上：左柱柱脚、楼板下缘、建筑与地面交界全是平的。

两条路，可并存：

1. **AO**：把 `CanvasViewport` 的 composer 一并抽成引擎入口（与 §2.3 同一批做，成本叠加最小）；
2. **接触阴影**：给主光加一份近距离 shadow map，或用 SSAO 替代。注意已知坑：
   `shadow.radius` 在 `PCFSoftShadowMap` 下**完全不生效**（已记录在案，别白调）。

⚠️ AO 是"改观感"的项，必须配**批量蓝图回归**（本项目要求：不能只验单样本）。

## 四、P1：材质表达力单一

### 4.1 事实

| 事实 | 位置 |
|---|---|
| 程序化材质**只有砖** | `src/renderer/proceduralMaterials/` = `brickMaterial.ts` + `noise.glsl.ts` |
| 表面族只有"颗粒"，振幅 4~12mm | `materialFeatures/defaultSurfaceMaterial.ts:62-67`：`masonry 0.009 / mineral 0.012 / wood 0.010 / metal 0.004 / neutral 0.010 / glass 0` |
| 图案只有"砌缝 + 颗粒"两种频率 | 同处 `courseCells: [3.3, 6.6]` + `grainFrequency: 6~20` |
| **零贴图资产** | 全仓无 `.png/.jpg/.ktx2/.hdr/.exr` 贴图 |
| **零蓝图用到贴图** | 所有 `.wild` 里带 `textures`/`map`/`normalMap` 的材质条目 = **0** |
| 法线贴图通道是有的 | `materialAdapter.ts:203` `material.normalMap = textureFactory(params.textures.normal, …)` —— **通路在，没数据** |

⇒ 照片里白墙有抹灰微肌理、泳池底是马赛克砖、木格栅有木纹；当前全部是**均匀纯色 + 毫米级噪点**，
所以读起来像"塑料块"。这是"不够精细"的第二主因。

#### 4.1.1 更正上表的措辞（2026-09-21 追补）

"表面族只有颗粒""只有砖"这两句**不够准确**，实测后更正如下：

- `defaultSurfaceMaterial.ts` **实现了 6 个表面族**（`neutral / mineral / masonry / wood / metal / glass`，
  `FAMILY_CODE` 编 0~5），且**图案是有区分的**：masonry/mineral 走"错缝铺装 + 细粒"，
  wood 的 `grainFrequency` 最高（16），metal 最低（4mm 振幅）；采样坐标用的是
  **世界法线选轴 + 米制投影**（`wildSurfaceMetricUv`），所以与 UV 约定无关。
  ⇒ 准确的表述是"**有 6 个族的毫米级微起伏，但没有"看得见的材质特征**"（抹灰抹痕、木纹走向、
  石材纹理、瓷砖缝格、水面波纹与折射），而不是"只有一种表面"。
- 贴图通路**不只在 `materialAdapter` 里**：材质有纹理时 `descriptor.ts:54,63`
  会把 `implementation` 切成 `surface.pbr.v1`，由 `materialFeatures/pbrEnvironmentMaterial.ts`
  真正消费 `map` / `normalMap` / `roughnessMap`。也就是说 **`textures` 字段是端到端通的**，
  缺的是**资产 + 生产者**（169 份蓝图 0 条带纹理材质），不是通路。
  详见《[字段数量不是精细度的瓶颈](字段数量不是精细度的瓶颈：169份蓝图字段使用率实测.md)》。

### 4.2 三条可选路径（按成本排）

1. **扩程序化材质族**（无新资产、无网络依赖，最契合当前仓库形态）：
   给 `proceduralMaterials/` 补 `plaster`（抹灰）/ `woodGrain`（木纹）/ `stone`（石材）/ `tileGrid`（瓷砖/马赛克）/ `water`（水面）。
   **现有 `brickMaterial.ts` 就是模板，套路已经跑通。**
2. **引入贴图资产**：通路已具备（`textures.normal` + `textureLoadMonitor`），但需要
   ① 资产目录与许可；② 蓝图里要能引用；③ UV 约定（见下）。
3. **提高现有 relief 量级**：当前 4~12mm 在照片级特写下偏小 —— 但**不能盲调**，会破坏已有断言。

⚠️ **UV 约定是混合的**（有的面按物理尺寸、有的按归一化）→ 设计任何"物理尺寸敏感"的图案
（砌缝、木纹间距、马赛克格）之前必须先查，否则图案会被拉伸。

## 五、P2：几何细部算子

照片里最像"专业图纸"的几处，靠的是**几何细节**而不是材质：

| 照片细节 | 引擎现状 | 位置 |
|---|---|---|
| 大挑檐（薄板、深挑） | 有 —— 檐口 = 屋面边界环扫掠，`buildEaveTrim` | `primitive/geometry/roof.ts:117,138,598,902` |
| 檐下**木格栅顶棚** | ❌ 无算子（表述上要用 `beam` + `primitive` 手工拼） | `primitive/geometry/` 无 `soffit` |
| 窗洞**侧壁凹进**（reveal，窗框退进墙面） | ❌ 无算子（窗框是独立网格，没有"洞口侧壁"概念） | `opening.ts` 只做洞口 |
| 薄板**边缘倒角/收边** | ❌ 无算子（楼板边缘就是直边） | `floor.ts` |
| 栏杆玻璃**栏板 + 木扶手** | 组件的几何在编译侧拼，但**没有环境反射** → 看起来像细线框 | 受 §2 拖累 |

**红线提醒**：加这些算子时**不得**按构件类型写专属分支（如"只给 balcony 加倒角"），
必须抽成"对所有类型成立的算子"（檐口就是这么做的：屋面边界环扫掠，与 `roofType` 无关）。

## 六、以下不是引擎的问题（别上错药）

| 现象 | 真归因 | 说明 |
|---|---|---|
| 挑檐只有 0.8m | **生成侧**：`facade.py:205` 把 overhang 夹到 0.8m（计划层允许 2m） | 改夹取，不是改渲染 |
| 左侧那根柱太细、像根棍 | **数据 + 引擎已知限制**：`column` 只支持圆截面，无方柱 | 已在 capability 表记为 partial |
| 泳池水面是纯蓝平面 | **引擎缺算子**（如果要波纹/菲涅尔就归 §4.2 的 `water`）；但"它是纯色"本身也是数据 | 当前材质只有 `pool_water` 一个 color |
| 天空纯黑 | **查看器**（§2.3 一并解决） | 不是缺 Sky 实现 |
| 阴影边缘生硬 | **查看器阴影配置** + 无 AO | `PCFSoftShadowMap` 下 `shadow.radius` 无效，要换手段 |

## 七、到照片级的路线

按"收益 / 成本"排序。分级沿用项目约定：**A=纯渲染实现，零参数改动**；
**B=渲染私有 `_` 字段**；**C=WILD 契约参数，须事前获批**。

| 阶段 | 内容 | 级别 | 预期收益 |
|---|---|---|---|
| **S0** | 把"环境 → PMREM → `scene.environment`"与 composer/AO 从 `CanvasViewport.vue` 抽成 `src/renderer/` 引擎入口；查看器改为调用、删掉自建三灯 | **A** | 玻璃/金属/白墙一次性接近照片；同时**消除"查看器自实现引擎行为"的红线违规** |
| **S1** | 统一 `scene.background`（天空）、`toneMappingExposure`、阴影参数到同一入口，两套界面共用 | **A** | 天空不再是黑的；两套界面观感可比 |
| **S2** | 补程序化材质族：`plaster` / `woodGrain` / `stone` / `tileGrid` / `water`（照 `brickMaterial.ts` 的套路） | **A**（若不加新字段） | 去掉"塑料块"感 |
| **S3** | 几何细部算子：檐下顶棚（soffit）、洞口侧壁（reveal）、板边收边 —— 全部按"对所有类型成立"的方式做 | **A**，若需新字段则 **B** | 立面层次与阴影线 |
| **S4** | 相机与构图（长焦、低机位、三分线）+ 后期（轻微暗角/色调） | **A** | 照片感的一半其实在这里 |
| **S5** | 贴图资产通路落地（含 UV 约定核对） | **C**（蓝图要能引用新字段） | 特写级细节 |

**先做 S0**：它一项就同时解决"天空黑 + 玻璃死 + 无反射 + 违反红线"四个问题，且不动任何数据。
S0 完成后再判 S2/S3 哪个优先 —— 有 IBL 之后，很多"看起来缺细节"的地方会自然好转。

### 验收方式（别靠肉眼说"好看了"）

- **S0/S1**：`audit-lighting.mjs` 已有光影链路门禁，须一起过；查看器与编辑器出图做**同机位对比**，
  量化指标建议取「玻璃区域的平均亮度 / 饱和度」与「天顶方向像素与 `scene.background` 的一致性」。
- **S2/S3**：出图 + `verify-surface-relief.mjs`（补丁命中 + 高度场坡度）；新算子须配
  `mutate-*.mjs` 变异测试（照 `mutate_roof_top_coverage.py` 的先例）。
- **全程**：批量蓝图回归，不能只验 `modern_pool_villa` 一个样本。

## 八、一句话

**"不够精细"的主因不是引擎缺几何，而是引擎的"光照与材质后处理"没有对外入口** ——
它被关在编辑器的 Vue 组件里，查看器只能自己拿三盏灯凑。先把这层抽出来（S0），
照片感会立刻到位一大半；之后才是材质族与几何细部的活。
