# "不够精细"的归因：能力口径审计 + 参照照片的精度差距

> 触发：用户提供《WILD 蓝图设计语言》文档（41k 字符 / 1786 行，来自微信）并反馈
> "感觉生成的还是不够精细啊，这个文档可以让你优化一下吗"，附一张热带现代泳池别墅实拍参照图。
>
> 结论先行：**文档本身有用且与 schema 一致；但"不够精细"的主因不在文档，在流水线**
> —— 引擎已实现的能力没有对应的生产者和配额。本轮**未改任何流水线代码**，只做归因与实测取证。

## 一、文档与 schema 的一致性核对

`wild-core/schema.json::$defs` 与文档的构件字典**逐项对得上**，没有野路子：

| 层 | 内容 | 与文档是否一致 |
|---|---|---|
| schema 元素类型（21） | `wall` `floor` `column` `beam` `roof` `opening` `stair` `furniture` `dense_brick` `body` `primitive` + 10 个组合构件 | ✅ 一致 |
| schema 组合构件（10） | `door` `window` `railing` `canopy` `balcony` `bay_window` `cornice` `chimney` `light` `ramp` | ✅ 一致 |
| 文档 §3.11 | `dense_brick / body（当前智能体勿用）` | ✅ 与 schema 存在但无生产者吻合 |

**但这份文档不在 KB 的 19 篇 `required_documents` 里**（`wild-server/storage/knowledge_base/config.yaml:81`），
所以模型目前看不到它。

## 二、主因：引擎已实现、流水线不派发（用脚本查出来的）

新增审计脚本 `.workbuddy/diag/audit_capability_parity.py`，把**四个真实注册点**对起来：

1. `wild-core/schema.json` —— 契约层声明
2. `wild-core/src/primitive/registry.ts` —— 引擎层能不能真建
3. `wild-server/app/agent/generation/components.py::COMPONENT_REGISTRY` + `architecture/skeleton.py` —— 生成侧有没有生产者
4. `wild-server/app/agent/planning/requirements.py::_UNSUPPORTED_COMPONENT_ALIASES` —— 验收侧怎么判

```
① schema 元素类型   21：… furniture …
③ 引擎 primitive    11：beam, body, column, dense_brick, floor, furniture, opening, primitive, roof, stair, wall
④ 生成侧可派发      11：balcony, bay_window, canopy, chimney, cornice, door, light, railing, ramp, roof, window
⑤ 骨架阶段直出       6：beam, building, column, floor, stair, wall
⑥ 声明不支持         1：furniture
⑦ 细部默认配额       8：balcony, bay_window, canopy, chimney, cornice, light, railing, ramp

发现 5 处能力口径不一致：
  [误判缺失] furniture
  [无生产者] body / dense_brick / opening / primitive
```

### 🔴 唯一实质问题：`furniture`

| 层 | 说法 | 位置 |
|---|---|---|
| schema | 合法元素类型，`subtype ∈ {table, chair, bookshelf, bed, lamp, tile}` | `schema.json::$defs.furniture` |
| 引擎 | **已实现**，含六种造型 + `rotation` | `wild-core/src/primitive/geometry/furniture.ts`，注册于 `registry.ts:58` |
| KB | `VALID_ELEMENT_TYPES` 含 `furniture`；能力表写"支持 table/chair/bookshelf/bed/lamp/tile" | `rules/implementation/validation-rules.md:82`、`knowledge/components/capability-boundaries.md:56` |
| KB | 完整参数规范（第八节） | `knowledge/protocol/component-parameters.md:470` |
| **验收侧** | **判为 `unsupported_capability`** | `planning/requirements.py:42-44` |
| **生成侧** | **`COMPONENT_REGISTRY` 里没有它** | `generation/components.py:139-299`（只有 11 个构件） |
| 生成侧 | 骨架阶段只产出 wall/floor/column/beam/stair | `generation/architecture/skeleton.py` |

**判定**：四处说"能用"，只有"真会产出它"和"验收"这两处说"不能用"。
用户说"要家具"，模型再懂也生不出来（无生产者），用户还会拿到一条 warning。

#### 实测取证（不是读代码推测）

往 `lantu/modern_pool_villa.wild` 的**副本**里插 8 个 furniture 元素（餐桌 + 4 椅 + 2 躺椅 + 落地灯，用 `chair` 近似躺椅），
跑真实重建链路：

```
lounger_a        网格 6  X[15.07,16.93]  Y[0.00,0.42]  Z[-4.01,-3.39]
dining_table     网格 5  X[ 7.75, 9.45]  Y[0.00,0.75]  Z[-1.95,-1.05]
dining_chair_*   网格 6  ×4
floor_lamp       网格 3  X[ 4.99, 5.41]  Y[0.00,1.50]  Z[-1.41,-0.99]
  — 结果：PASS
```

出图（`lantu/docs/renders/probe_furn_front.png`）能看到门前餐桌椅、落地灯、泳池边两张躺椅，
**位置、`rotation`、材质全部正确**。⇒ 引擎侧零缺口，缺的只是"没人派发"。

> 探针脚本：`.workbuddy/diag/make_furniture_probe.py`；探针蓝图：`.workbuddy/diag/probe_furniture.wild`。
> 原蓝图未被修改。

### ⚪ 另外 4 个"无生产者"不是问题

`body` / `dense_brick` / `opening` / `primitive` 是**模型可写的逃生口**：
文档 §3.11 明确标"当前智能体勿用"，`opening`/`primitive` 用于模型自行处理特殊洞口与形体。
它们没有专门的生产者属于设计内。脚本会把它们列出来，属于"待确认"而非"待修"。

## 三、第二个堵点：配额表决定了精细度上限

`architecture/profile.py` 的两张表决定了任何一次生成**能长出什么**：

| profile | `base_components` |
|---|---|
| `residential_lowrise`（别墅走这个） | `["door", "window", "roof"]` |
| `ordinary_public` | `["door", "window", "roof"]` |
| `garden_structure` | `["roof", "railing"]` |
| `underground_transport` | `["light"]` |

`_DETAIL_COMPONENT_QUOTAS`（`profile.py:46-55`）只有 8 项：
`canopy / balcony / bay_window / cornice / railing / ramp / light / chimney`。

`planning.py:695-702` 决定"只有进了 `detail_packages` 的细部才会补进配额"。

⇒ **住宅类建筑的精细度上限由这两张表锁定**，与文档写得多细无关。表里没有的东西，
要么靠用户点名，要么永远不会出现。

### 照片里最显质感的做法，逐条对照

| 照片里的做法 | 引擎有对应能力吗 | 计划侧会生成吗 |
|---|---|---|
| 大挑檐（薄板深挑 ~2m） | ⚠️ 见第四节，几何硬夹 0.8m | 有 roof，但挑不出那么深 |
| 檐下木格栅顶棚 | ❌ 无专用构件（需 `beam` + `primitive` 手工拼） | ❌ 无配额 |
| 通高落地推拉门 | ✅ `window` 支持，**当前蓝图正立面已是** `Y[0.15, 3.10]`（2.95m 通高） | ✅ 已生成 |
| 玻璃栏板 + 木扶手 | ⚠️ `railing` 在表里，栏板材质 `glass_rail` 已绑；**木扶手无独立表达** | ✅ 阳台已内嵌栏杆 |
| 躺椅 / 餐桌椅 | ✅ 引擎已实现（见第二节实测） | ❌ **未注册 + 判为不支持** |
| 压顶 / 女儿墙 | ❌ 引擎与 KB 均无此概念 | ❌ |
| 绿植 / 景石 / 铺装 | ❌ 场地语义被判"缺能力"（`requirements.py:52` 含 `花园/后院`） | ❌ 当前蓝图的场地是我手写的 |
| 二层体量挑出 | ✅ 多体量 + 逐体量屋顶（`facade.py:171` `_planned_roof_slots`） | ✅ 已生成 |

## 四、第三个发现：计划值与几何值分叉，验收看不见

照片里最抓眼的"深挑檐"做不出来，根因是一条**两级夹取不一致**：

| 环节 | 位置 | 允许范围 |
|---|---|---|
| 计划字段 | `planning.py:614` | `_clamp_number(..., 0, 2, 0.55)` → **0 ~ 2m** |
| 验收编译 | `requirements.py:332-350` | 用户写"出檐不小于 1.5m" → 编译成 `architecture_roof_overhang`，`expected=1.5` |
| 验收判定 | `requirements.py:862-872` | 读 **`architecture_plan.roof.overhang`**（即计划值） |
| **几何实现** | `facade.py:205` | `max(0.15, min(0.8, ...))` → **实际只挑 0.8m** |

⇒ 用户要求"出檐不小于 1.5m"时：**计划记 1.5 → 验收通过 → 实际屋面只挑 0.8m**。
验收项读的是计划值，几何值它看不到。这与既有方法论里那条一致：
**同一件事被两处解析，就必须有测试钉住一致性**（本例里两处是"计划夹取"与"几何夹取"）。

> 更正记录：排查时我先怀疑 `overhang` 是"无消费者的死字段"（因为 `schema.json::$defs.roof.properties`
> 里确实没有 `overhang`）。**这个怀疑是错的** —— `facade.py:205` 就是它的消费者，它按设计
> 折算成 `span/depth` 膨胀量，所以不进 schema。真正的问题不是"没人读"，而是**读了但夹到 0.8m**。

## 五、这份文档本身需要处理的地方

### 🔴 不能整篇塞进 KB

文档 ≈55~65% 与现有 19 篇重叠（总则/机理 ↔ `behavior-instructions.md`；
骨架与字段 ↔ `blueprint-skeleton.md`；构件字典 ↔ `component-parameters.md`；
生成规则 ↔ `validation-rules.md` + `generation-redlines.md`）。

KB 里已有的教训（已发事故）：**互相矛盾的条目，模型会挑 `authority` 更高 / 更像硬约束的那份**
（2026-09-17：`capability-boundaries.md` 的"复杂组合屋顶不可做"与 `generation-redlines.md` 冲突，
导致 L 形别墅侧翼没屋顶）。整篇入库会立刻制造第二事实源。

### 🟡 §3.2.2「女儿墙（硬性，通用 · 全部建筑）」是空承诺

`女儿墙` / `parapet` 在 `wild-core/src`、`wild-server/storage/knowledge_base` 里**都不存在**，
只在 `app/agent/knowledge/web/knowledge_claims.py` 出现过。一条"硬性 · 全部建筑"的条文
指向一个引擎里没有的概念，会直接误导模型。

### 🟡 第七部分「智能体系统提示（可直接粘贴）」是重复角色定义

与 KB `knowledge/protocol/behavior-instructions.md` 角色重叠，属第二事实源风险。

### ✅ 文档真正的增量价值（KB 目前没有）

- §3.2.1 / §3.2.2 / §3.2.3：楼板轮廓规则、女儿墙、天井拆板法（女儿墙那条要删或改成"暂不支持"）
- §4.13 中式古建（木柱 / 斗栱 / 曲面顶 / 重檐 / 瓦）
- §4.14 欧式古典（柱式 / 拱 / 檐口 / 坡顶）
- §4.16.3 院落朝向面与院墙、§4.16.5 非矩形体块（U/L 形硬性要点）
- §4.17 中式门造型通用规则（隔扇门写法、模数、开樘公式、红线）
- 附录速查表
