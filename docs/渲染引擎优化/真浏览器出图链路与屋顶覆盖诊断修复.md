## 二、修复 ①：屋顶覆盖诊断（`RECONSTRUCTION_ROOF_COVERAGE`）

### 现象

样本蓝图 3 块屋顶（`roof_main` / `roof_b` / `roof_d`，分段覆盖 3 个体量），引擎重建后报 **3 条 warning**：

```
[warning] roof_main :: 屋顶重建范围未完全覆盖墙体范围
[warning] roof_b    :: 屋顶重建范围未完全覆盖墙体范围
[warning] roof_d    :: 屋顶重建范围未完全覆盖墙体范围
```

而同一条蓝图上：流水线 `verify_wild_blueprint.py` 的 **7e 反向屋顶覆盖 PASS**（"所有 15 面墙的顶部均被覆盖"），
真实链路 `check_blueprint_render.mjs` **PASS**，真浏览器渲染也正常 ⇒ 3 条全是误报。

### 根因（两处，都在判据里）

`wild-web/src/renderer/reconstructionDiagnostics.ts`：

1. **逐块屋顶去比全楼墙并集**。原实现先取**所有墙**的并集 `wallBounds`，再对**每一个** roof 单独判定
   「这个 roof 是否盖住 `wallBounds`」→ 要求"每块屋顶都盖住整栋楼"。
   单屋顶时成立，**只要做多体量分段就必然触发**。多体量本来就该"每个体量各盖一块"，每块都不覆盖全楼是**正确**的。
2. **矮墙被算进结构墙并集**。本样本的泳池四壁是 `wall` 类型、高 1.5m、落在 `z∈[-7,-2.6]`，
   会把 `wallBounds` 往 −Z 撑到 -7；而任何屋顶都不可能盖到泳池上 → 再叠一层必然误报。

> 这是"单屋顶前提"在渲染侧的**第二处副本**（生成侧 `facade.py::_planned_roof_slots` 是第一处，已修）。

### 修法

判据改为与 Python 侧 `app/tools/spatial_tools.py::validate_roof_top_coverage`（7e）对齐：

1. **只算结构性墙**：高 ≥ 1.8m 且厚 ≥ 0.1m（与 `_is_structural_wall` 同口径）。矮墙（泳池壁、栏板）本来就不该有屋顶。
2. **比屋顶并集**，不再逐块比；**一次聚合警告**，不再每块各报一条；消息指明缺口方向（如 `X 高侧缺 3.84m`）。
3. 严重度仍是 ⚠️（覆盖不完整按项目政策**只标记、不阻断**）。
4. 明确不重复 7e 的"上层楼板 / 上层墙也能盖住墙顶"那套判定 —— 权威结论仍看流水线 7e，渲染侧这份只做自检。

### 验证

**修前 → 修后**：`diagnostics` 从 `3 warning + 4 info` 变为 **`0 warning + 4 info`**。

回归门禁：`.workbuddy/diag/audit_roof_coverage_diagnostic.mjs`（退出码即结果）

| 用例 | 期望 | 实测 |
|---|---|---|
| 正例：3 块屋顶分段覆盖 3 体量 | 不报 | ✅ 0 条 |
| 正例：泳池矮墙（1.5m）不参与 | 不报 | ✅ 0 条 |
| 反例 1：删掉 `roof_b` | 报 1 条 | ✅ `X 高侧缺 3.84m` |
| 反例 2：`roof_main.span` 12 → 8 | 报 1 条 | ✅ `X 低侧缺 1.94m` |
| 边界：所有墙改成矮墙 | 跳过判定 | ✅ 0 条 |

同时 `check-wild-core` / `check-component-compiler` / `check-rendering-pipeline` 三条既有检查全绿。

## 三、待拍板 ②：光照/look 没有 `src/renderer/` 入口

### 事实

- `src/renderer/worldLookRuntime.ts` 的 `activateProfile()` 只是**簿记**：它注册的 shader feature 全是裸 `{ id }`，
  **没有 `activate` 实现**，所以它并不真正设置天空、环境贴图或灯光。
- 真正的"世界光影"实现在 `src/components/viewport/CanvasViewport.vue` 内部，直接 `new Sky()`、`PMREMGenerator`、
  `HemisphereLight`、`DirectionalLight`、环境 `WebGLRenderTarget`、曝光与雾 —— 内联在 700+ 行的 SFC 里，
  **没有任何渲染器侧的导出**。
- 后果：`lantu/viewer/main.ts` 只能自己硬编码一套 `HemisphereLight + AmbientLight + DirectionalLight`。
  这**违反项目自己的原则**（"查看器绝不自实现引擎行为，必须走 `src/renderer/`"）——
  材质/网格有 `wildCoreAdapter` + `BlueprintRenderInstance` 这道边界，**光照没有**。

### 实测到的观感偏差

真浏览器出的图里，一层幕墙玻璃偏暗、暗到看不出通透。原因至少有两层：
① 场景里没有环境贴图（`scene.background` 是纯色）⇒ `MeshPhysicalMaterial` 的
`transmission`/`metalness`（窗框 `metallic: 0.75`）拿不到可反射/可透射的环境；
② 玻璃背后没有室内几何，透射过去就是暗背face。
编辑器视口因为自带 Sky + PMREM，表现会不一样 —— **同一份蓝图在两套界面的材质观感不可比**。

### 三个选项（需拍板，属架构改动，未擅动）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把 `CanvasViewport.vue` 里的光照/天空/环境抽成 `src/renderer/viewportLook.ts`，导出 `createViewportLook(renderer, scene)`，**编辑器与查看器共用** | 要动 700 行 SFC，需回归编辑器视口 |
| B | 只给查看器加一个"最小环境贴图"（如 `RoomEnvironment`） | 快，但仍是查看器自实现，偏差只是变小 |
| C | 不动，接受查看器光照是"近似替身" | 零成本，但材质类结论不能从查看器图里下 |

> 方案 C 的前提必须在文档与查看器 UI 里写明，否则"看图判引擎"会持续产生误判 —— 本轮已经栽过一次
> （把"我的预览器不做透明"误判成"引擎的幕墙不可透视"）。

### 出图的正确姿势（`--screenshot` 会骗人）

🔴 **`chrome --screenshot + --virtual-time-budget` 不可靠**：它靠猜时长，实测会截到
"只有地面、建筑还没重建完"的空帧。更阴的是 —— 此时相机还是**写死的初值、与 `?cam=` 无关**，
于是**不同视角会截出字节完全相同的 PNG**（本轮 3 张里 `pool` 与 `aerial` 的 md5 一致），
极易被误读成"URL 参数没生效"。

正解：用 CDP 显式轮询页面就绪标志再截。查看器据此暴露了 `window.__wildViewer`
（`ready()` / `phase()` / `message()` / `cams()` / `setCam(name)`）——
**只暴露这几样，不交出 `renderer` / `scene` / `instance`**，否则外部脚本就能自己造网格或材质，
"查看器只反映引擎产出"这个前提就破了。

```bash
# ① 起查看器 dev server（vite 在 wild-web/node_modules，不在仓库根）
cd wild-web/lantu/viewer && node ../../node_modules/vite/bin/vite.js --port 5180 --strictPort &

# ② 多机位出图
cd wild-web && node ../.workbuddy/diag/shot_lantu_viewer_cdp.mjs pool front aerial
#   环境变量：EXP / W / H / DSF / PREFIX / OUT / CDP_PORT
```

取景参数：`?cam=pool|front|aerial|iso|back|top`、`?exp=`、`?panel=0`（出干净图）、`?grid=0`、`?bbox=1`。

| `audit_roof_coverage_diagnostic.mjs` | 屋顶覆盖诊断的正例/反例 | 见 §二 |

### 两个会误导结论的字段事实

🔴 **`mesh.materialRef` 是材质名字符串，`entity.materialParams` 是与 `meshes` 等长的平行数组。**
取材质必须用 `materialParams[meshIndex]`。写成 `materialParams[mesh.materialRef]` 会**全部取到 `null`** ——
本轮第一次写探针就是这么错的，差点得出"材质没绑上"的结论。

🔴 **含洞的墙仍然是 1 个 mesh**（`primitive/geometry/wall.ts` 走 `boxWithHoles`，返回单一缝合几何）。
⇒ 「网格数 = 1」**不能**作为"墙没被开洞"的证据；判开洞只能量面积/覆盖率。

## 六、单文件查看器（双击即看）

### 为什么需要它

`wild-web/lantu/viewer/dist/index.html` **不能双击打开**。它引用的是绝对路径 `/assets/index-*.js`，
在 `file://` 下会解析成 `file:///E:/assets/…` → 浏览器按 CORS 拦截（origin 为 `null`），页面全白。

实测证据（`probe_page_errors.mjs file:///…/dist/index.html`）：

```
控制台错误：
  [error/network] Access to script at 'file:///E:/assets/index-CLPaFPiV.js'
                  from origin 'null' has been blocked by CORS policy
页面状态：{"phase":null,"canvases":0}
```

⇒ 两条路：起 http server，或**把 JS/CSS/蓝图全部内联成单文件**。后者才是"发给别人就能看"的形态。

### 做法：`wild-web/lantu/viewer/vite.config.standalone.mjs`

沿用仓库里原有的 `vite.config.single.mjs` 思路，但**依赖用包名**（`wild-core`），
不再写 `../../src/wild-core/...` —— 那些源码目录已经不存在了（见第四章的包拆分）。

四处关键配置：

| 配置 | 值 | 作用 |
|---|---|---|
| `base` | `'./'` | 产物引用相对路径，`file://` 下不再落到 `E:/assets/` |
| `assetsInlineLimit` | `1e8` | 图片/字体等资源转 base64 |
| `cssCodeSplit` | `false` | CSS 合成一块，方便整体内联 |
| `output.codeSplitting` | `false` | 单块 JS（旧写法 `inlineDynamicImports:true` 已告警） |

插件 `inline-blueprint-and-assets` 做两件事：

1. `transformIndexHtml`（pre）：把蓝图 JSON 塞进 `<script>window.__WILD_INLINE_BLUEPRINT__=…</script>`，
   写进 `</head>` 之前 —— 这样 HTML 里就有蓝图，无需 `fetch`（`file://` 下 `fetch` 本地文件同样被拦）。
2. `closeBundle`：正则把 `<script src="./assets/xxx.js">` 换成 `<script type="module">…</script>`，
   CSS 一并内联，然后 `rmSync(assets/)`。

> ⚠️ 正则必须按 **相对** 路径 `src="\./assets/…"` 匹配。若哪天把 `base` 改成 `'/'`，
> 正则失配 → 资源目录被删但 JS 没内联 → 产出一个 31 kB 的**空壳 HTML**（不易察觉）。
> 构建日志里的 `[standalone] 单文件产物：…` 只有在真正内联后才打印；产物体积 ≈ 700 kB 才正常。

构建：

```bash
cd wild-web/lantu/viewer && node ../../node_modules/vite/bin/vite.js build --config vite.config.standalone.mjs
# 产物：dist-standalone/index.html（蓝图 + JS + CSS 全内联，约 706 kB）
# 换蓝图：BP_FILE=../other.wild BP_LABEL='某某' 再跑一次
```

验证（必须过 `file://`，不是 http）：

```bash
node .workbuddy/diag/probe_page_errors.mjs "file:///E:/AgentProject/WildAgent/wild-web/lantu/viewer/dist-standalone/index.html"
# 期望：加载失败 0 · 控制台错误 0 · phase=ready · canvases=1
```

### 顺带修掉的取景问题

原 `applyCameraPreset` 用 **包围球半径 / sin(fov/2) × 1.4** 定距离。包围球外接整个盒子的**体对角线**，
投影后的真实轮廓远小于它 → 本别墅（41 × 11.7 × 30 m）在 `pool`/`front` 机位只占画面约 1/4，四周大片留白。

改为**逐角投影求最小距离**：把取景盒 8 个角投到相机基（`zAxis` = 视线反方向，`xAxis = up × zAxis`），
对每个角取 `cz + |cx| / tan(hFov/2)` 与 `cz + |cy| / tan(vFov/2)` 的最大值，最后乘 1.06 留白。

```ts
const tanV = Math.tan((camera.fov * Math.PI) / 360)
const tanH = tanV * camera.aspect   // ← 依赖 aspect
// 每个角：dist = max(dist, cz + |corner·xAxis| / tanH, cz + |corner·yAxis| / tanV)
```

🔴 因为是按面投影而不是按球，**距离依赖 `aspect`** → `resize` 时必须重算（已加 `applyCameraPreset(currentCam)`），
否则窗口比例一变建筑就重新贴边。另外正俯视（`top`）时 `worldUp` 与视线共线，`up × zAxis` 退化，
需兜底到 `(1, 0, 0)`。

### 结果

单文件产物在 `file://` 下：`phase=ready`、`canvases=1`、0 网络失败、0 控制台错误，
面板显示 `78 网格 / 38 基础构件 / 11 组合构件 / 12 材质`，四个机位出图正常。
