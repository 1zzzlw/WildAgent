# 渲染引擎优化指南

> 用于指导 AI 优化渲染引擎时的核心原则和边界约束  
> **重要**：所有涉及 WILD 参数扩展的优化必须提前报告并获得批准

---

## 一、WILD 参数扩展的慎重性原则

### 🚨 核心原则（必读）

**只有在迫不得已需要对建筑物进行精细建模控制时，才可以新增 WILD 参数。**

### ⚠️ 参数扩展前置审批流程

**任何涉及 C 类改动（新增或修改 WILD 契约参数）的优化方案，必须遵循以下流程**：

1. **停止实施**：立即停止当前优化工作
2. **方案报告**：详细说明为什么 A 类和 B 类方案无法解决问题
3. **等待审批**：向项目负责人（我）报告方案，说明：
   - 当前问题描述
   - A 类方案尝试及失败原因
   - B 类方案尝试及失败原因
   - 拟新增参数的名称、类型、用途
   - 预计的波及范围（知识库、提示词、后端、前端）
4. **获得批准**：得到明确批准后才能继续
5. **全链路实施**：按照第四节的 6 步流程完整实施

**❌ 禁止行为**：
- 未经批准擅自新增 WILD 参数
- 先实施后报告
- 隐藏在"小优化"中悄悄新增参数

**✅ 正确行为**：
- 优先尝试 A 类和 B 类方案
- 如确需 C 类，提前报告并等待批准
- 批准后完整实施全链路更新

---

### 为什么要慎重？

1. **知识库维护成本**：新增参数需要在 `storage/knowledge_base/BLUEPRINT-SPEC-*.md` 中完整文档化
2. **大模型学习负担**：WILD 参数文档由大模型学习，参数越多，生成质量越难保证
3. **提示词复杂度**：`app/agent/prompts/generation.py` 需要教会大模型何时使用新参数
4. **后端校验逻辑**：`app/utils/blueprint_parser.py` 可能需要新增校验规则
5. **前端类型定义**：`wild-core/types.ts` 需要同步更新
6. **既有文件迁移**：可能需要迁移已有的 `.wild` 文件以兼容新参数

---

## 二、三类改动的波及范围对比

### 分类标准

| 类型 | 改动位置 | 例子 | 何时使用 | 波及面 |
|---|---|---|---|---|
| **A 类：纯渲染实现** | 仅前端渲染器 | 光照、阴影、材质、取景、抗锯齿、后处理、面剔除、几何体形状优化 | **90% 的渲染优化** | **零波及**（不动参数/知识库/后端） |
| **B 类：渲染私有字段** | 前端类型（可选字段，`_` 前缀） | `_roofRidge`、`_eaveProfile`、`_gableEnds` | 渲染器需要额外数据，但不想让大模型学习 | **小波及**（仅前端类型添加可选字段） |
| **C 类：契约参数** | 知识库 + 提示词 + 后端校验 + 前端类型 + 文件迁移 | 新增 `roof.overhang`、修改 `wall.thickness` 语义 | **只有**迫不得已需要让大模型控制一个新的精细建模旋钮时 | **全链路波及**（4-6 处改动）+ **需要批准** |

### 判断标准：何时可以新增参数？

**必须同时满足以下条件**：

1. ✅ **A 类和 B 类方案完全无法实现**所需效果
2. ✅ **用户明确要求**对建筑物某个部位的精细控制
3. ✅ **该参数对建筑设计有实质性价值**（不是纯粹为了视觉效果）
4. ✅ **已提前报告并获得项目负责人批准**
5. ✅ **愿意承担**知识库更新、提示词调整、大模型重新学习的代价

### 优先级排序

```
强制优先 A 类 > 其次 B 类 > 最后 C 类（极少使用，需审批）
```

## 三、渲染引擎 vs 组件渲染引擎

### 3.1 渲染引擎（Rendering Engine）

**位置**：`wild-web/src/wild-core/src/primitive/geometry/`

**职责**：将 WILD 参数转换为 3D 几何体（顶点、面、法线、UV）

**包含的几何类型**：
- `wall.ts` - 墙体（直墙、曲墙、带洞口）
- `floor.ts` - 地板/楼板（矩形、圆形、带孔洞）
- `roof.ts` - 屋顶（双坡、四坡、平顶、穹顶、中式屋顶）
- `column.ts` - 柱子（圆柱、方柱、多边形柱）
- `beam.ts` - 梁（矩形、圆形、工字梁）
- `stair.ts` - 楼梯（直跑、多跑）
- `primitive.ts` - 参数化形体（球、柱、锥、环）
- `opening.ts` - 洞口（矩形、拱形）

**优化方向**：
1. **几何精度**：细分段数、曲面平滑度、UV 连续性
2. **性能优化**：减少顶点数、优化索引、面剔除
3. **视觉质量**：法线生成、边缘处理、共面避免（Z-fighting）
4. **实体完整性**：水密性、欧拉特征、体积计算

**扩展原则**：
- ✅ **优先优化既有几何生成算法**（A 类）
- ✅ **新增下划线私有字段**用于渲染器内部数据传递（B 类）
- ❌ **避免新增可被大模型写入的参数**（C 类，需审批）

---

### 3.2 组件渲染引擎（Component Rendering Engine）

**位置**：`wild-web/src/wild-compiler/components/`

**职责**：编译高级组件（门、窗、阳台等）为基础几何元素

**包含的组件类型**：
- `door.ts` - 门（单开、双开、推拉、旋转）
- `window.ts` - 窗（平窗、弧形窗、百叶窗）
- `balcony.ts` - 阳台（挑板、栏杆、柱子）
- `bayWindow.ts` - 飘窗
- `railing.ts` - 栏杆（扶手、立柱、填充）
- `curtainWall.ts` - 幕墙（玻璃、铝板、石材）

**工作流程**：
```
WILD 组件定义
    ↓
组件编译器（compiler）
    ↓
基础几何元素（wall/floor/primitive）
    ↓
渲染引擎（geometry）
    ↓
3D 网格（vertices/faces/normals）
```

**优化方向**：
1. **组件编译逻辑**：组件如何分解为基础几何
2. **空间定位**：组件在父构件上的位置和朝向
3. **参数映射**：组件参数如何转换为基础几何参数
4. **交互行为**：门窗开合、动画、碰撞检测

**扩展原则**：
- ✅ **优先复用既有基础几何**（用 `primitive` 组合）
- ✅ **新增组件类型时复用既有编译模式**（如 door/window 的洞口处理）
- ⚠️ **新增组件参数需要在知识库文档化**（C 类改动，需审批）
- ❌ **避免为单一组件新增专用基础几何类型**（通用性原则）

---

### 3.3 渲染引擎 vs 组件引擎的边界

| 维度 | 渲染引擎（Geometry） | 组件引擎（Component） |
|---|---|---|
| **输入** | 基础几何参数（span/depth/height/thickness） | 组件语义参数（doorStyle/windowType/balconyWidth） |
| **输出** | 3D 网格（顶点/面/法线/UV） | 基础几何元素数组（wall/floor/primitive） |
| **优化重点** | 几何算法、性能、视觉质量 | 组件编译逻辑、空间定位、参数映射 |
| **扩展场景** | 新的几何生成算法、细节优化 | 新的组件类型、新的组件参数 |
| **参数扩展** | 极少需要（90% 用 A/B 类） | 较常需要（新组件必然有新参数，C 类，需审批） |

## 四、渲染引擎主要优化方向

### 4.1 渲染管线优化（A 类，零参数改动）

**优先级：🔴 高（立竿见影）**

| 项目 | 现状问题 | 优化方向 | 预期效果 |
|---|---|---|---|
| **阴影落地感** | 阴影过淡（0.17-0.34），建筑"悬浮" | 提升阴影不透明度到 0.40-0.46 | 建筑有重量感，"贴"在地面 |
| **取景角度** | 编辑器和查看器不统一，俯角过低 | 统一俯角、抬高视角让屋面为主体 | 视角一致，展示建筑最佳角度 |
| **材质质感** | 95.8% 面积用纯程序化材质，无细节 | 添加法线扰动、粗糙度变化、PBR 材质 | 墙面/屋面有凹凸感，不再"死平" |
| **抗锯齿** | 仅 FXAA，屋顶边缘/窗框有锯齿 | 启用 MSAA 或 SMAA | 边缘平滑，移动时不闪烁 |
| **环境光遮蔽** | 默认档无 SSAO，缺少深度暗示 | 默认档开启轻量级 SSAO | 墙角/檐口有深度感 |
| **面剔除** | 96% 面双面渲染，浪费性能 | 为水密几何开启背面剔除 | 节省 50% 光栅化性能 |

---

### 4.2 几何生成优化（A 类，零参数改动）

**优先级：🟡 中（提升精度和性能）**

| 项目 | 优化方向 | 收益 |
|---|---|---|
| **曲面细分** | 动态调整细分段数（远处少、近处多） | 性能提升 20-40% |
| **法线计算** | 修复世界法线着色 bug（instanceMatrix） | 天气效果正确 |
| **UV 连续性** | 确保贴图在拐角处不撕裂 | 材质映射自然 |
| **共面检测** | 自动检测并微调共面片（避免 Z-fighting） | 消除闪烁 |
| **几何简化** | 对不可见面（地板底面）跳过生成 | 减少顶点数 10-20% |

---

### 4.3 细节增强（B 类，渲染私有字段）

**优先级：⚪ 低（锦上添花，按需添加）**

| 项目 | 实现方式 | 用途 |
|---|---|---|
| **屋脊瓦** | `_ridgeTiles: { spacing, height }` | 屋脊线条细节 |
| **檐口线脚** | `_eaveProfile: { type, depth }` | 檐口装饰线条 |
| **勒脚** | `_baseCourse: { height, material }` | 墙体底部装饰 |
| **窗套** | `_windowTrim: { width, depth }` | 窗框周边装饰 |
| **山墙通风口** | `_ventilation: { size, position }` | 山墙端面通风口 |

**注意**：这些字段以 `_` 开头，**不写入知识库**，仅供渲染器使用，不需要审批。

## 五、优化工作流程

### 5.1 诊断阶段

1. **收集用户反馈**：截图、描述问题（空心/闪烁/颜色不对等）
2. **运行诊断脚本**：
   ```bash
   cd wild-web
   node ../.workbuddy/diag/verify-roof-solid.mjs  # 几何水密性
   node ../.workbuddy/diag/check-coplanar.mjs     # 共面检测
   node ../.workbuddy/diag/material-impl-histogram.mjs  # 材质覆盖统计
   ```
3. **确定问题类型**：
   - 几何生成错误 → 检查 `geometry/*.ts`
   - 渲染效果不佳 → 检查 `renderer/` 和 `CanvasViewport.vue`
   - 组件编译问题 → 检查 `wild-compiler/components/`

---

### 5.2 方案选择（关键决策树）

```
问题能否通过调整光照/阴影/材质/取景解决？
  ├─ 是 → A 类优化（纯渲染实现）✅ 立即实施
  └─ 否 ↓
    
几何生成算法能否优化（不改参数）？
  ├─ 是 → A 类优化（几何算法改进）✅ 立即实施
  └─ 否 ↓
    
是否需要传递额外数据给渲染器（不给大模型）？
  ├─ 是 → B 类优化（下划线私有字段）✅ 立即实施
  └─ 否 ↓
    
是否必须让大模型控制该参数？
  ├─ 是 → C 类改动（契约参数）⚠️ 停止！提交方案报告，等待审批
  └─ 否 → 重新审视需求，可能不需要改动
```

---

### 5.3 实施阶段

#### A 类和 B 类：直接实施

1. 修改代码
2. 运行诊断脚本验证
3. 视觉验证（截图对比）
4. 提交代码

#### C 类：需要审批后全链路实施

**⚠️ 必须先完成第一节的审批流程！**

获得批准后，**必须按顺序完成以下 6 步**：

**步骤 1：更新知识库文档**

位置：`storage/knowledge_base/BLUEPRINT-SPEC-*.md`

```markdown
### roof（屋顶）
- `overhang`: 出檐外挑量（米），默认 0.3
  - 中式建筑通常 0.5-0.8m
  - 现代建筑通常 0.2-0.4m
```

**步骤 2：更新提示词**

位置：`app/agent/prompts/generation.py`

```python
# 教会大模型何时使用 overhang
"屋顶出檐可用 overhang 参数控制，中式建筑通常 0.5-0.8m，现代建筑通常 0.2-0.4m"
```

**步骤 3：更新前端类型**

位置：`wild-core/types.ts`

```typescript
export interface RoofParams {
  // ... 既有字段
  overhang?: number;  // 出檐外挑量（米），默认 0.3
}
```

**步骤 4：更新后端校验**（可选）

位置：`app/utils/blueprint_parser.py`

```python
if 'overhang' in roof and roof['overhang'] < 0:
    errors.append("roof.overhang 不能为负数")
```

**步骤 5：更新几何生成**

位置：`wild-core/src/primitive/geometry/roof.ts`

```typescript
const overhang = params.overhang ?? 0.3;
// 使用 overhang 调整檐口位置
```

**步骤 6：测试和验证**

```bash
# 1. 让大模型生成包含新参数的建筑
# 2. 检查渲染效果
# 3. 运行诊断脚本验证几何正确性
cd wild-web
node ../.workbuddy/diag/verify-roof-solid.mjs
```

**❌ 禁止行为**：只完成部分步骤（会导致系统不一致）

---

### 5.4 验证阶段

**所有改动都必须通过以下验证**：

- ✅ **几何验证**：运行 `verify-roof-solid.mjs` 确认水密、欧拉特征、体积
- ✅ **视觉验证**：多角度截图，确认效果符合预期
- ✅ **性能验证**：FPS 不显著下降（< 10%）
- ✅ **兼容验证**：旧的 `.wild` 文件仍能正常渲染（向后兼容）
- ✅ **大模型验证**（仅 C 类）：大模型能正确理解和使用新参数

## 七、常见错误模式

### ❌ 错误 1：过早新增参数

**症状**：遇到视觉问题就想"加个参数控制"

**正确做法**：
1. 先尝试 A 类优化（调整渲染参数、光照、材质）
2. 再尝试 B 类优化（渲染私有字段）
3. 只有迫不得已且获得批准后才用 C 类

---

### ❌ 错误 2：忘记生成法线/UV

**症状**：几何验证通过，但渲染出来是空心/黑色

**正确做法**：

```typescript
const { geometry: geo, indices } = indexTriList(geometry);
const attributes = generateArchitecturalSurfaceAttributes(geo);  // ← 必须调用

return [{
  geometry: geo,
  indices: new Uint32Array(indices),
  normals: attributes.normals,  // ← 必须添加
  uvs: attributes.uvs,          // ← 必须添加
  // ...
}];
```

**案例参考**：[屋顶檐口修复报告](./屋顶檐口修复报告.md)（2026-09-16 修复）

---

### ❌ 错误 3：C 类改动不全面

**症状**：新增参数后大模型不会用、或者前端报错

**正确做法**：C 类改动必须完成全部 6 步：
1. 知识库文档
2. 提示词
3. 前端类型
4. 后端校验
5. 几何生成
6. 测试验证

**缺一不可！**

---

### ❌ 错误 4：破坏水密性

**症状**：优化后出现穿模、Z-fighting、阴影闪烁

**正确做法**：
- 每次改动后运行 `verify-roof-solid.mjs`
- 确保欧拉特征 χ = 2（闭合实体）
- 确保每条边恰好被 1 正 1 反两个三角形共享（水密）

---

### ❌ 错误 5：未经批准新增参数

**症状**：擅自实施 C 类改动，事后被要求回滚

**正确做法**：
1. **停止当前工作**
2. **提交方案报告**：说明为什么 A/B 类无法解决
3. **等待审批**：获得明确批准后才能继续
4. **全链路实施**：按 6 步流程完整实施

**这是最严重的错误，必须避免！**

---

## 八、总结

### 核心原则（优先级排序）

1. **通用性优先**：不为单一情况写专用逻辑
2. **A 类优先**：90% 问题可以通过纯渲染实现解决
3. **B 类其次**：需要传递数据时用下划线私有字段
4. **C 类慎用**：只有迫不得已且获得批准才新增契约参数

---

### 记住这句话

**"如果一个渲染问题需要新增参数才能解决，那很可能是你还没找到正确的渲染方法。"**

---

### 快速决策参考

```
渲染效果不好？
  ├─ 光照/阴影/材质/取景 → A 类（零参数）✅ 立即实施
  ├─ 几何算法优化 → A 类（零参数）✅ 立即实施
  ├─ 需要传递内部数据 → B 类（下划线字段）✅ 立即实施
  └─ 必须让大模型控制 → C 类（契约参数）⚠️ 停止！报告并等待批准
```

---

### 审批提醒（重要！）

**任何 C 类改动（新增或修改 WILD 契约参数）必须遵循以下流程**：

1. ⚠️ **停止实施**
2. 📝 **提交方案报告**（说明为什么 A/B 类不行）
3. ⏸️ **等待审批**（向项目负责人报告）
4. ✅ **获得批准**（得到明确批准）
5. 🔧 **全链路实施**（完成 6 步流程）

**未经批准的 C 类改动将被要求回滚！**
