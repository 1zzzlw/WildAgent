### 第二阶段：质感升级（3-5 天）🔴 ✅ 已完成（P2 方案 1）

#### ✅ 任务 3：表面凹凸层（P2）
- **完成时间**：2026-09-16
- **改动**：`wild-web/src/renderer/materialFeatures/defaultSurfaceMaterial.ts`（唯一一个文件）
- **说明**：`surface.default.v1` 原本只做法线"变平"（润湿），没有任何凹凸；
  本轮补上程序化高度场 + 凹凸扰动，**纯 A 类，零参数改动**。
- **关键技术决策（踩坑记录，改这里前务必读）**：
  1. **砖缝尺寸不能用 UV 定义**。实测同一份蓝图里 UV 约定是混合的：
     屋面/外墙按米展开（`roof_tile` u −5.8..5.8），而楼板/门窗构件是归一化 0..1
     （`floor_concrete`、`brick_red`、`frame_metal`）。因此砖缝/瓦垄改用
     **世界坐标按主法线轴投影**得到米制平面坐标，与 UV 约定解耦。
  2. **`masonry` 与 `mineral` 原本共用 family code = 1**，着色器无法区分"砖瓦"与"灰泥"。
     已给 `masonry` 独立编码 5（不改动 0-4 的既有含义），砖缝只对 masonry 生效。
  3. **不能复用 three 的 `perturbNormalArb`**：它被 `#ifdef USE_BUMPMAP` 包住，
     而本材质没有 bumpMap。已在文件内内联一份。
  4. **内联时不能照抄 three 的 `normalize(dFdx(surf_pos))`**。three 归一化屏幕空间导数
     是为了贴图尺度无关；对程序化高度场会导致凹凸强度随像素密度漂移。
     未归一化时扰动角恰好等于真实坡度（米/米），与分辨率无关。
  5. **`normal` 在片元着色器里到 `normal_fragment_begin` 才声明**，而
     `roughnessmap_fragment` 在它之前。所以高度场在 `map_fragment` 处计算，
     用 `inverseTransformDirection(vNormal, viewMatrix)` 还原世界法线（此时还没有 `normal`）。
  6. **WebGL1 没有反导数扩展**：全段包在 `#if __VERSION__ >= 300 && !defined( FLAT_SHADED )`
     内（three 在 WebGL2 下输出 `#version 300 es`）。WebGL1 或 flatShading 下自动降级为
     原行为，不会编译失败。
  7. **非 masonry 族复用已算好的 `wildDefaultDetail`**（fbm，含 0.15m~4cm 多倍频），
     不额外增加 fbm 采样开销。
  8. **细粒必须是两级倍频**。单倍频两头不讨好：频率低→近看是"团块"不是颗粒；
     频率高→远处被 LOD 淡掉。现在 `grainFrequency` 与 `grainFrequency × 3.2` 两级，
     **各自按频率淡出**（否则细粒会把粗颗粒一起提前淡掉）。
  9. 砖缝宽度取单侧的 5%（`smoothstep(0.0, 0.05, edge)`）。第一版用 7.5%，
     近距离看缝占层高的 30%，像宽倒角瓷砖而不是砖瓦。
- **参数（`RELIEF_PRESETS`，改这里即可调强度）**：

  | family | 高度振幅(mm，medium 档实测) | 图案 | 中位倾角 | 95分位 | 峰值 | 主特征淡出视距 |
  |---|---|---|---|---|---|---|
  | masonry | 7.0 | 0.30m×0.15m 错缝铺装（缝宽 5%，带叠压微倾） | 1.2° | 28.2° | 54.4° | 79m |
  | mineral | 9.4 | 0.083m 两级细粒糙面 | 5.2° | 11.0° | 22.0° | 43m（细级 13m） |
  | wood | 7.8 | 0.063m 细粒 | 6.0° | 12.7° | 24.4° | 32m |
  | metal | 3.1 | 0.050m 细粒 | 3.2° | 6.8° | 13.1° | 26m |
  | neutral | 7.8 | 0.083m 细粒 | 4.5° | 9.5° | 17.0° | 43m |

  > 面积占比：mineral 52.8%（灰泥+混凝土）、masonry 36.4%（瓦+砖）、metal 4.3%、wood 2.3%、玻璃 4.2%（本就不参与）
  >
  > 倾角是"法线被扰动的角度"，等于该处表面真实坡度 `arctan|dh/dx|`，与像素密度无关。
- **附带效果**：粗糙度也会跟随高度场变化（缝里更粗糙），缝的粗糙度增量
  `wildSurfaceReliefRoughness` = 0.14~0.30，用于削弱"塑料感"。
- **顺带修正**：连带的旧断言 `check-rendering-pipeline.mjs` 的 shader 版本号断言已同步
  （`wild-surface:default-surface-v1` → `-v2`），并补了 9 条新断言（含两级细粒与 `#if` 守卫）。
- **验证**：
  - `node ../.workbuddy/diag/verify-surface-relief.mjs`（新增）——用真实 three ShaderLib 源码
    跑补丁命中检查 + JS 复刻高度场换算坡度与 ASCII 图案
  - `node ../.workbuddy/diag/material-family-report.mjs`（新增）——材质名×family×实现 的面积盘点
  - `node ../.workbuddy/diag/relief-preview.mjs`（新增）——**离线着色预览出 PNG**
    （法线扰动 + 朗伯 + 掠射高光），2 行（3m / 20m 视距）× 3 列（对照 / masonry / mineral），
    肉眼判断"是否像砖瓦"和"远处会不会闪"
  - `vue-tsc -b`、`check:core`、`check:compiler`、`check:rendering` 全通过
  - 屋顶几何回归 `verify-roof-solid.mjs` 13 用例全绿
- **视觉确认**：`relief-preview.png` 已确认——20m 看到清晰的错缝砖瓦与细颗粒灰泥糙面；
  3m 砖缝宽度合理、灰泥为沙粒质感而非团块。
  ⚠️ 但这是**离线着色近似**，真实页面的 PBR/SSAO/环境光会改变观感，仍需人眼过一遍。

### 第三阶段：性能与精度（1-2 天）🔴 ✅ P3/P8 已完成 / P5 已否决（P4 经核实无需改动）

#### ✅ 任务 4：抗锯齿（P3）
- **完成时间**：2026-09-16
- **目标**：消除屋顶边缘/窗框锯齿
- **关键判断（先纠正一处认知误区）**：`antialias: false` 并不是"漏开了一个开关"。
  整个主光栅化走 `EffectComposer`，场景渲染到**离屏 RT**（不是 canvas 默认帧缓冲），
  而 `WebGLRenderer` 的 `antialias` 只对默认帧缓冲生效 —— **改成 `true` 也完全无效，还会白占显存**。
  唯一正确的位置是给合成的离屏 RT 开多重采样。
- **改动**：`wild-web/src/components/viewport/CanvasViewport.vue`
  - 新增 `applySceneMsaa(samples)`：对 `composer.renderTarget1/2` 同时设 `samples` 并 `dispose()`
    （`samples` 是普通属性，已建好的帧缓冲必须 dispose 才会按新采样数重建）
  - 默认 `DEFAULT_MSAA_SAMPLES = 4`；WebGL1 不支持 RT 多重采样 → 自动回落为 0
  - 帧率降级路径同步降到 `DEGRADED_MSAA_SAMPLES = 2`
  - FXAA 保留为最后一道，负责 MSAA 覆盖不到的着色器高频细节（高光闪烁、程序化纹理边缘）
- **为什么两个 RT 都要开**：`EffectComposer` 不在每帧重置读写缓冲，靠 `needsSwap` 累积交换。
  本链路 RenderPass(no-swap) → SSAO(swap) → Bloom(no-swap) → OutputPass(swap) → FXAA(swap)
  **每帧净交换 3 次（奇数）**，RenderPass 落点逐帧在 RT1/RT2 间交替。
- **为什么 MSAA 真的有用**：`SSAOPass` 默认输出会 `readBuffer.texture` 作底图再乘 AO
  （`SSAOPass.js` 的 `OUTPUT.Default` 分支），所以 RenderPass 写进 RT 的着色结果确实是最终画面底图。
- **波及面**：A 类（零参数改动）

#### ❌ 任务 6：面剔除（P5）—— 已被数据证伪，不建议推进
- **结论**：**不做**。原计划"节省约 50% 光栅化"在真实蓝图数据上不成立，且默认切成 FrontSide
  会造成大面积破面。完整证据与替代方案见 [P5-面剔除评估报告.md](./P5-面剔除评估报告.md)
- **实测数据**（`.workbuddy/diag/audit-winding.mjs`，7 个真实蓝图 / 337 网格 / 59626 tri）
  | 判据 | 结果 |
  |---|---|
  | 可安全剔除（闭合 + 绕序一致 + 外法线朝外） | **193 / 337 网格（57.3%）** |
  | 按三角形口径的可剔除份额 | **9820 / 59626 tri（16.5%）** |
  | 可见反面率（射线实测） | `tiantan` **53.65%**、`cabin_v1` 27.96%、`eave_extension` 16.41% |
- **最该修绕序的材质**（按不可剔除三角形数）：`column_red`(16384)、`granite`(8708)、
  `wood`(4364)、`wood_red`(4096/5144)、`broken_tile`(3664)
- **为什么不能"就切成 FrontSide"**：`mat_wall_white` / `wall_ext` / `floor_concrete` / `mat_wood_floor`
  这些**墙体楼板**全是绕序冲突；`tiantan` 的 `roof_blue` + `marble` 反法线占比过半 —— 剔除会把屋面和大理石直接撕掉。
- **A 类替代方案也被否掉**：在渲染侧对每个几何体跑拓扑审计、只对通过的网格开 FrontSide，
  视觉上零风险，但**省下的只有 16.5% × 约 50% ≈ 8% 光栅化**，而通过检查的恰好是窗框/家具/玻璃这类
  低面数轻量网格；真正费面的 `column_red`/`granite` 全在失败名单里 —— 性价比不成立。
- **正确的下一步**：把它当**几何引擎的数据质量 bug** 修（`diagnosis flow` 里"绕序/水密异常 → 几何引擎"），
  按材质逐个修 primitive 生成器。修绕序在 `DoubleSide` 下**视觉上完全无变化**（光照用 `normal` 属性、
  不依赖绕序），所以可以零风险地慢慢修，修好后再回头谈剔除。

#### ✅ 任务 7：生成结果居中归一化（P8）
- **完成时间**：2026-09-16
- **现象**：用户反馈"每次生成蓝图时，建筑的位置不是中心点，有点偏移"
- **根因（已量化）**：生成器产出的是**"角点对齐"坐标**（如 `x` 从 0 到 11.5，而不是 -5.75 到 5.75）。
  而取景与参照物分属两套坐标系：
  - 相机 `frameCameraToBounds()` 的 target 是**包围盒中心**
  - 网格 / 地面 / 内置环境却钉在**世界原点**（`gridHelper` 只在 y 上跟随包围盒，x/z 恒为 0）
  ⇒ 只要足迹中心不在原点，建筑与网格就一定错开。**相机没错，参照物没错，两者没对齐。**
- **实测**（`.workbuddy/diag/audit-centering.mjs`，7 份样例蓝图）
  | 指标 | 结果 |
  |---|---|
  | 足迹中心偏离原点的蓝图 | **5 / 7** |
  | 偏移 > 0.5m 的蓝图 | 4 / 7 |
  | 平均 / 最大偏移 | 1.939m / **6.449m**（`generated_modern_villa`） |
  | 还会捅出 20×20 网格的 | `generated_modern_villa` 归一化前 x 跨 **-0.5~11.5**（网格只到 ±10） |
- **修法**：**纯显示层归一化**，不碰文档/几何/契约
  - 编辑器 `CanvasViewport.vue:updateScene()`：`sceneGroup.position.set(-center.x, 0, -center.z)`，
    随后把 `center.x/z` 归零，让下游所有"以中心为参照"的逻辑（方向光与阴影相机、内置环境、
    网格与地面）自动改用归一化后的中心
  - 查看器 `lantu/viewer/main.ts:frameToBox()`：同样归一化 `sceneGroup.position`，
    并把初始 `controls.target` 从硬编码的 `(5.5, 3, 3)` 改为 `(0, 3, 0)`
    （`5.5` 恰是 `generated_modern_villa` 的中心 x —— 那是为某份蓝图做的手工补偿，归一化后反而错了）
- **为什么 Y 不动**：`gridHelper.y = bbox.min[1]` 让网格贴建筑自身地面；Y 一并归零会让网格与建筑脱开。
- **为什么不改文档坐标**：拖拽改的是对象**局部** `position`，保存读的是文档
  （`createEditorWorldDocument` 里实例 transform 写死 `[0,0,0]`），两者都不受影响。
  归一化只发生在渲染实例根节点的 `position` 上，且 `BlueprintRenderInstance.update()` **不会重置**它。
- **离线校验**：`audit-centering.mjs` 第二部分复算归一化后的世界空间，断言
  "足迹中心回到原点 / 模型仍在网格覆盖范围内 / 光照参照中心落在足迹内 / 无 NaN"，全部通过
- **波及面**：A 类（零参数、零契约、零文档改动）

### 第四阶段：长期规划（按需）🔴 ✅ P6/P7 已完成

#### ✅ 小 Bug 修复
- **P6：世界法线着色修正**（2026-09-16 完成）
  - **改动**：`wild-web/src/renderer/materialFeatures/defaultSurfaceMaterial.ts` 顶点补丁
    - 旧：`vWildDefaultWorldNormal = normalize(mat3(modelMatrix) * transformedNormal)`
    - 新：`vWildDefaultWorldNormal = inverseTransformDirection(transformedNormal, viewMatrix)`
  - **为什么是 bug 而不只是"精度问题"**：`#include <defaultnormal_vertex>` 结束时 `transformedNormal`
    **已在视图空间**（且已折入 `instanceMatrix`）。再乘模型矩阵属于空间混用。
    更关键的是：绝大多数构件 `modelMatrix` 近似单位阵 ⇒ 旧代码拿到的其实是**视图空间法线**，
    于是 `wildVerticalMask = 1 - |n.y|`（雨丝，只刷竖直面）和
    `wildUpward = smoothstep(0.28, 0.82, n.y)`（积雪/积尘，只刷朝上面）
    **会随着相机轨道旋转而改变** —— 转个视角，屋面的雪就会忽有忽无。
  - **影响面**：仅天气遮罩（雨丝方向 / 积雪 / 积尘），不影响核心光照（光照走 `normal` 属性）
  - **回归锁**：`verify-surface-relief.mjs` 新增正/反向断言，禁止 `mat3(modelMatrix) * transformedNormal`
    再次出现（断言只查剥掉注释后的代码，避免注释里引用旧写法造成误判）

- **P7：阴影脏标记原子化**（2026-09-16 完成）
  - **改动**：`wild-web/src/components/viewport/CanvasViewport.vue` 的 `markShadowsDirty()`
    追加 `markNeedsRender()`
  - **两种真实失效模式**（不是"理论时序风险"）：
    1. `shadowMap.needsUpdate` 只在**下一次 `renderer.render()`** 里被消费并清零
       （`autoUpdate=false`），而该函数只置位不请求渲染 ⇒ 若此刻队列中没有待渲染帧
       （相机静止、无动画），标记**永远悬空**，移动物体后阴影不跟随；
    2. 若已有帧在排队，该帧可能在本 tick 的几何/变换写入落地**之前**执行并清零标记
       ⇒ 阴影按旧姿态烘焙，且之后不再补算。
  - **为什么加 `markNeedsRender()` 就够**：`requestAnimationFrame` 回调在所有同步写与
    微任务（Vue watcher）之后执行，保证重算阴影时场景图已是最终状态。
    （若只 `scheduleRenderFrame()` 而不置 `needsRender`，`renderFrame` 会因
    `if (needsRender && ...)` 直接跳过渲染，标记照样悬空 —— 所以两者都要。）

## 三、关键原则（重要！）

### 参数边界
- **A 类优化**（90% 场景）：纯渲染实现，零参数改动
- **B 类优化**（10% 场景）：渲染私有字段（`_xxx`），不让 LLM 学
- **C 类改动**（慎用！）：契约参数，影响知识库/提示词/后端校验/既有文件

### 新增参数的判断标准
**只有在"迫不得已需要对建筑物精细控制"时才新增 C 类参数**

理由：
1. 增加知识库维护成本
2. 增加大模型输出内容复杂度
3. 需要调整提示词工程
4. 可能需要迁移既有 `.wild` 文件

**优先级**：A 类 > B 类 > C 类

- 用的是既有 `roof.thickness` 参数（知识库早已定义）

### 8.2 本次踩坑（都值得记住）

1. **审计脚本先报了"实现公式"的错，而不是实现的错**
   初稿对**光方向本身**也套了 12° 高度角下限，但光位置仍用真实的 6°
   ⇒ 落影实际按 6° 走（104m），而 `far` 是按 12° 算的（51m），长影照样被切。
   正确做法是**不改光方向**（否则落影与天空里的太阳对不上），只把 `far` 按真实高度角放大。
   **教训：凡是引入"值的下限/钳制"，必须检查该值被用在了几处、是否全都用同一份钳制后的值。**
2. **落影点求交的符号**：`t = -c.y / dir.y`。写成 `+` 会把落影点算到建筑上方，
   `far` 需求被严重低估（本项目：算成 48，实际 143），黄昏 far 差 2.6~3.9× 的问题被完全掩盖。
3. **`shadow.bias` 是归一化深度偏移**，等效世界偏移 = `|bias| × (far − near)`。
   只在调 `far` 时才会暴露问题 —— 把 `far` 从 55 拉到 207 后，原来的 `-0.0002`
   等效世界偏移翻了近 4 倍，会出现 Peter-panning。两者必须同改。
4. **审计脚本本身就是回归门禁**：升级为对源码做实现契约断言后，
   "改了公式没同步脚本"或"注释说做了但没做"都会被抓出来。以后改光影参数，
   同步更新 `audit-lighting.mjs` 的断言是必须动作，不是可选项。

- **L8（空气透视下限）与 L6(b)（Bloom 阈值随时段）暂缓**：前者会改所有场景的整体观感，

| **E3** | 尺寸随尺度缩放 | `drop = max(1.5×板厚, clamp(0.04×短边, 0.10, 0.34))`；`outset = clamp(0.4×drop, 0.05, 0.16)`。避免小体量屋顶被巨型线脚压垮 |

### 9.3 本次踩坑

1. **"看不见檐口"是材质问题，不是几何问题**
   先量了四件事才定案：出檐量 0.68/0.78m（正常）、檐口立板 0.20m（存在）、
   板底是 113.7㎡ 水平平底、**整块屋顶只有 1 个材质**。最后一条才是根因 ——
   0.2m 的檐口立板与屋面同为 `#9e472e`，视觉上糊成一片。
2. **山墙端面比檐口更伤观感**（本次意外收获）
   `buildGable` 用五边形截面封死 `z=±hd`，且整块屋顶共用一个 `materialRef`，
   于是正面/背面看到的是**一大块 3.10m 高的砖红三角**。修材质归属的收益大于加线脚本身。
3. **不能把山墙端面从屋面实体里拆出去**
   端面是双坡实体闭合的必要面。拆走 ⇒ 屋顶漏水 + 逐分量 χ 校验失败。
   正解是保留端面（屋面材质）+ 叠加一层向外偏移 `panelGap` 的**独立薄板**（墙材质）。
   偏移量必须 > 0 且足够大（本项目 2mm），否则与端面共面 → Z-fighting。
4. **Λ 形带必须用耳切，扇形剖分会出界**
   博风板截面是 6 边形且**在脊点处是凹点**（`V-E+F` 校验会立刻暴露自交）。
   多边形面积恒等式可验算：Λ 带面积 = `span × drop`（垂直落差恒定）。
5. **门禁改成"逐分量"后比原来更严**
   线脚天然是多分量网格，整体 `χ = 2×分量数`。改法不是放宽到"挑一个分量看"，
   而是**逐分量都要求 χ=2**，于是"线脚某一块悄悄开了口"也能被抓到。
6. **坐标系混用**：`analyzeSolid` 吃的是**局部坐标**几何，而预览脚本会加
   `transform.position`。审计里必须显式传 `toWorld`，否则"檐口最低点"这类
   断言会算成 `3.59` 而不是 `0.39`（差了一个 origin）。
7. **离线预览一度忽略 `transform.rotation`**：本蓝图 62 个网格里 36 个带旋转，
   旧预览图里左右后墙/门窗位置全错。已修，并加 `check-rot.mjs` 做落位核查。

### 9.4 待办（同一 B 类清单的剩余项）
