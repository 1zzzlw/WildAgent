# 字段数量不是精细度的瓶颈：169 份蓝图的字段使用率实测

> 触发：问"生成的建筑模型不够精细，是不是渲染引擎的字段类型太少了？如果给 WILD 蓝图补更多字段会不会好一点？"
> 结论：**不是字段太少**。WILD 的元素层/构件层/材质层已经有大量"细节字段"，其中相当一部分**从未被任何蓝图使用**（包含专门为曲面屋顶、柱收分、踏步加的字段）。
> 本文件是**只读统计**，未改任何代码 / schema / 知识库。
>
> 统计口径：仓库内全部 `.wild` 蓝图 **169 份**（排除 `node_modules` / `dist`），逐份统计 `geometry.elements` / `geometry.components` / `materials.*` 的键使用情况。

## 一、先看结论表：哪些"细节字段"已经存在但没人写

| 字段 | 所在类型 | 出现总次数 | 覆盖蓝图数 | 引擎是否消费 |
|---|---|---|---|---|
| `roof.tiers`（重檐层数） | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `roof.tierHeight` | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `roof.eaveCurveHeight`（曲檐起翘） | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `roof.curveProfile` | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `roof.eaveOutset`（出檐） | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `roof.shrinkFactor` | 元素 roof | **0** | **0 / 169** | ✅ 有 |
| `column.entasis`（柱收分） | 元素 column | **0** | **0 / 169** | ✅ 有 |
| `column.flutes`（凹槽） | 元素 column | **0** | **0 / 169** | ✅ 有 |
| `wall.curve` / `beam.curve`（曲线构件） | 元素 wall/beam | **0** | **0 / 169** | ✅ 有 |
| `stair.stepCount` / `stepDepth` / `stepHeight` | 元素 stair | 1 | 1 / 169 | ✅ 有 |
| `materials.*.textures` | 材质定义 | **0** | **0 / 169** | ✅ 有（`surface.pbr.v1` 走 map/normalMap/roughnessMap） |

| `materials.*.procedural` | 材质定义 | **0** | **0 / 169** | ✅ 有（brick 专用实现） |
| `materials.*.environmentResponse` | 材质定义 | **0** | **0 / 169** | ✅ 有（湿/雨/雪/尘响应） |

**这张表就是答案**：`roof` 的 15 个字段里有 6 个是专门为"重檐 / 曲檐 / 起翘"加的，`column` 的 11 个字段里有 3 个是为"收分 / 凹槽 / 倾斜"加的 —— 引擎也都读了（每个字段至少 1 个 `wild-core` 文件引用）—— 但 169 份蓝图用完的次数是 **0**。

## 二、字段本身不少：三层字段量

| 层 | 类型数 | 单类型字段数 | 细节字段示例 |
|---|---|---|---|
| 元素 `geometryElement` | 11 类 | 7 ~ 17 | `roof`(15)：`tiers` / `tierHeight` / `eaveCurveHeight` / `curveProfile` / `eaveOutset` / `shrinkFactor` |
| 构件 `componentSpec` | 10 类 | 8 ~ 19 | `window`(15)：`frameWidth` / `frameDepth` / `glassDepth` / `verticalMullions` / `horizontalMullions` / `frameMaterial` / `glassMaterial` |
| 材质 `materialDef` | 1 类 | 12 | `textures` / `normalScale` / `uvScale` / `procedural` / `environmentResponse` / `surfaceFamily` |

抽样一份真实蓝图的材质段（`modern_pool_villa.wild`，12 个材质）——**每个材质只用了 5~8 个字段**：

```
wood_slat  : baseColor [0.30,0.22,0.14], roughness 0.65, metallic 0   ← 木格栅 = 一块棕色平面
deck_stone : baseColor [0.74,0.72,0.67], roughness 0.88, metallic 0   ← 石材铺装 = 一块浅灰平面
pool_water : baseColor [0.13,0.47,0.60], roughness 0.05, metallic 0   ← 水面 = 光滑蓝面，无法线/波纹
glass      : baseColor [0.62,0.78,0.86], roughness 0.05, transmission  ← 只有玻璃多写了 3 个字段
```

**"看起来像纸板"的直接原因在这里**：不是字段不够写，是写进去的从来只有"颜色 + 粗糙度 + 金属度"。`textures` / `normalScale` / `uvScale` / `surfaceFamily` / `procedural` 这 5 个能让表面"有东西"的字段，全库使用率 **0%**。

## 三、构件层是反例：字段有人写，但关键进深字段没人写

| 字段 | 出现次数 | 覆盖蓝图数 | 说明 |
|---|---|---|---|
| `window.verticalMullions` | 4378 | 135 / 169 | 竖梃分格：**写得很勤** |
| `window.horizontalMullions` | 4373 | 134 / 169 | 横梃分格：**写得很勤** |
| `window.frameWidth` | 295 | 82 / 169 | 框料宽度：还行 |
| `window.frameDepth` | 28 | **10 / 169** | 框料**进深**：几乎没人写 ⇒ 窗框没有厚度 |
| `window.glassDepth` | 18 | **2 / 169** | 玻璃**厚度**：几乎没人写 ⇒ 玻璃是零厚度贴片 |
| `cornice.profile` / `closedProfile` | 48 | 27 / 169 | 檐口线脚轮廓：有 48 次（唯一被用起来的"细节构件"） |

构件层证明了"只要有人写、引擎就能出细节"（4378 次竖梃是真的在渲染）。同一个 `window` 里，**分格写了、进深没写** —— 所以窗看起来是"贴在墙上的格子"，而不是"有框、有玻璃、有洞口的窗"。这是**生产者问题**，不是字段问题。

## 四、为什么"补字段"这条路已经试过一次且失败（三层归因）

以 `roof.tiers` 为例，一个字段要真正影响出图，必须同时具备三样：

1. **引擎有实现**：✅ 有（`wild-core` 读了这些字段，`buildRoof` 支持多檐/曲檐）；
2. **知识库教了模型**：⚠️ 极弱 —— `tiers` 只出现在 2 个 KB 文档、`flutes` 1 个、`eaveCurveHeight` 2 个；而 `surfaceFamily` / `procedural` 在 KB 里 **0 次**（模型根本不知道"材质可以声明表面族"）；
3. **有人写**：❌ 0 次。

即：**字段 → 引擎** 这一段早就通了，断在 **知识库 → 模型 → 蓝图** 这一段。这就是"能力已实现却无人派发"这一类缺陷的另一个实例（对照 `.workbuddy/diag/audit_capability_parity.py` 的四个注册点口径）。

## 五、真正缺字段的地方只有一类（而且未必该用"加字段"解）

元素层的 `material` 是**单个字符串**：一面墙只能有一个材质，没有面槽位、没有勒脚/压顶/抹灰的分层。真实建筑外立面至少三层（抹灰 + 勒脚 + 压顶），这是"照片感"里最显眼的差异之一。

但按项目红线（🔴 禁止按构件类型写专属分支加能力），正确形态不是"给 wall 加 `baseTrim`、给 roof 加 `fascia`、给 column 加 `capital`"（那是每类构件一套装饰字段，字段数量暴涨、模型写不对），而是：

> **一个对所有元素类型成立的"边缘收口算子"** + 元素级**面槽位**（`surfaces: { top/bottom/side }` 之类），由算子统一消费。

这属于 **C 类**（改 WILD 契约参数）→ 必须事前报批，且要同步：schema 两副本（字节一致）+ 归一化器 + 4 个注册点 + 校验器 + KB + 提示词 + 验收。

## 六、还有一条容易被忽略的代价：字段越多，模型漏写越多

一次生成要在一段有限的输出里写完整栋楼。字段膨胀的边际收益是递减的，边际错误是递增的：模型更容易漏字段、写错枚举值、把"必填"漏掉。所以正确的方向是 **"缺省即精细"**——把"好看"做成引擎的默认行为（算子 + 材质资产 + 光照标定），而不是把"要不要好看"变成模型的一道选择题。

## 七、建议顺序（与《渲染引擎现状评估与照片级路线》一致）

| 优先级 | 做什么 | 为什么不是"加字段" |
|---|---|---|
| 1（已做） | S0 光照/环境/后期链路收进引擎 | 已交付，见 [S0 实施报告](S0实施报告：光照与环境链路收进引擎.md) |
| 2 | **S1 曝光/环境标定** | IBL 挂上后白天接近过曝，这是"照片感"的第一道门槛 |
| 3 | **S2 程序化材质族**（灰泥抹痕 / 木纹方向 / 石材纹理 / 瓷砖缝格 / 水面波纹） | 这些**不需要新字段**——`surfaceFamily` 已存在，缺的是实现 |
| 4 | **S5 纹理资产 + 生产者** | `textures` 通道已通（`surface.pbr.v1`），缺资产与"谁写" |
| 5 | 元素级面槽位 + 边缘收口算子 | 唯一值得加字段的方向，**C 类须报批** |

**顺手可以立刻做、零 schema 改动的一件事**：把 `glassDepth` / `frameDepth` 在知识库与提示词里写成"窗框必填项"，让窗有框、有玻璃厚度 —— 字段和引擎都就位了，只差有人写。
