# 光影优化方案（L1 ~ L10 · 内容侧 G1 ~ G4）

> 范围：**只讨论光照与阴影链路**，外加建筑组件（几何 / 材质 / 内容）中与光影直接相关的部分。
> 全部结论均由 `.workbuddy/diag/audit-lighting.mjs` 在无浏览器环境下用真实蓝图复算得出，输出存于 `.workbuddy/diag/audit-lighting-output.txt`。
> 改动分级沿用 [渲染引擎优化指南](渲染引擎优化指南.md) 的 **A / B / C** 口径：本方案 **无 C 类改动**，不动 WILD 契约。
>
> **落地状态（2026-09-16）**：L1 ~ L5、L7、L9、L10 已实施并通过全量回归；L6(b) 与 L8 暂缓（原因见 [§六](#六建议落地顺序)）。

## 一、结论摘要

审计共 21 个「蓝图 × 时段」组合 + 3 条渲染链路事实核查，**原始 6 项断言未通过**：

|---|---|---|---|---|---|
| L1 | 夜晚主光被放在地平线下方 | A | 🔴 | ✅ 已修 | `night` 的 `sunPhi=108°` 使主光从地面下方往上打光，且与月亮实体方向相反 |

### 1.1 实施要点（与方案的差异）

- **L2 的落影区入框公式**：方案初稿写的是 `horizontalRadius + shadowTravel × 0.35`，实施时改成几何上更准确的形式 ——
  正交框 U 轴水平、V 轴在太阳所在竖直面内，因此
  `U ≤ 足迹半对角线`、`V ≤ 足迹半对角线 × sin(高度角) + 半高 × cos(高度角)`。
  与全量蓝图复算完全吻合（tiantan 白天需 U 11.31 / V 13.44，公式给出同一组数），且不再需要拍系数。
- **关键光高度角下限从 12° 降到 5°（仅作数值护栏）**：初稿打算把光方向本身抬到 12°，
  但那样"天空里可见的太阳位置"与"主光方向"会不一致（落影与太阳对不上）。
  最终选择**不改光方向**，改为把 `far` 按真实高度角放大到能容纳落影行程
  （tiantan 黄昏 `far` 192.7 → 实现取 206.7，正交投影深度是线性的，精度足够）。
- **`bias` 同步换算**：`shadow.bias` 是归一化深度偏移，等效世界偏移 = `|bias| × (far − near)`。
  `far` 从 55 涨到 207 后原来的固定 `-0.0002` 等效偏移会明显变大（Peter-panning），
  所以改为按世界空间目标偏移反推：`bias = clamp(-0.01 / (far - near), -5e-4, -2e-5)`。
- **`shadowExtent` 与 `lightingExtent` 拆开**：`lightingExtent`（内置环境半径 / 日月 / 天气层 / 雾的尺度参照）
  **刻意不随太阳角度变化**，否则切换时段时山体与远树会整体跳位；只有阴影正交框用新引入的 `shadowExtent`。
- **半球光 `groundColor` 也补上了天气色调 lerp**（原先只有 `color` 跟着变色），
  否则沙尘/雨天时天空半球偏暖而地面反射半球仍是冷色。

## 三、逐项方案

### L1 夜晚主光被放在地平线下方 · 🔴 A 类

**现象**：夜晚档建筑发平，几乎没有方向性感；夜晚阴影贴花无意义。

**机理**
- `CanvasViewport.vue:1156-1160`：`sunDirection.setFromSphericalCoords(1, preset.sunPhi, preset.sunTheta + azimuthOffset)`。
- `defaultWorldLook.ts:72`：`night.sunPhi = 108°` > 90° ⇒ `sunDirection.y < 0`。
- `CanvasViewport.vue:1461`：`directionalLight.position = center + sunDirection × lightDistance` ⇒ **主光跑到地面之下**。
- `CanvasViewport.vue:1341`：`moonBody.position = center − sunDirection × radius` ⇒ 月亮在天上。**两者方向相反。**

**影响**：夜晚主光与建筑上半部法线相背，实际贡献趋近 0，夜间画面基本只剩半球光（0.163）；`timeShadowScale = 0.36`（line 1191）是在补偿一个本不该出现的问题。

**修法**：引入 `keyLightDirection`，只用于主光与阴影相机；天空、太阳/月亮实体继续用 `sunDirection`。

```ts
// applyTimePreset() 内，计算 sunDirection 之后
// 夜晚 sunPhi > 90° 使太阳落到地平线下；主光应取月亮方向（与 moonBody 同向）。
const keyLightDirection = timeOfDay.value === 'night'
  ? sunDirection.clone().negate()
  : sunDirection.clone()
```
随后 `updateLightingToBounds()` 的 `directionalLight.position` 改用 `keyLightDirection`（`sky.material.uniforms.sunPosition` 与 `environmentSunSprite.position` 保持不变 —— 它们在夜晚本就隐藏）。

**风险**：低。夜间亮度分布会明显改变，需配合 L6/夜间曝光一起目视一次。

---

### L2 阴影正交框与远裁剪面不足 · 🔴 A 类

**现象**
- 白天：投影边缘出现一条**笔直的裁切线**（正交框外 `inFrustum=false` → GLSL 返回 `shadow = 1`，即"无阴影"）。
- 黄昏：长影在离建筑约 `2 × lightingExtent` 处被硬切（`far` 不足 → `frustumTest=false` → 同样返回无阴影）。

**机理**：`CanvasViewport.vue:1454-1478`

```ts
lightingExtent = Math.max(maxDim * 0.68, 4)     // 只含模型水平尺寸
const lightDistance = lightingExtent * 2.5      // line 1459
shadowCamera.far = lightDistance + lightingExtent * 2   // line 1470 —— 不含落影行程
```

缺两个量：① 正交框必须同时罩住**投影体**与**落影区**；② `far` 必须覆盖落影行程 `shadowTravel = maxY / tan(elevation)`。

**修法**

```ts
const elevation = Math.asin(THREE.MathUtils.clamp(sunDirection.y, 0.05, 1))  // 用 keyLightDirection
const MAX_SHADOW_TAN = Math.tan(THREE.MathUtils.degToRad(12))   // 高度角下限，避免 150m 长影
const shadowTravel = Math.max(0, size.y) / Math.max(Math.tan(elevation), MAX_SHADOW_TAN)
const horizontalRadius = 0.5 * Math.hypot(size.x, size.z)

lightingExtent = Math.max(horizontalRadius + shadowTravel * 0.35 + 1, 4)
shadowCamera.far = lightDistance + shadowTravel + lightingExtent * 1.5
```

同时把**黄昏的关键光高度角下限提到约 12°**（仅用于主光与阴影，天空与太阳实体仍保持 6° 的视觉位置）。

**代价核算**：extent 变大 ⇒ 纹素变粗。tiantan 白天 10.88 → 13.5，2048 图下纹素 `10.6mm → 13.2mm`，肉眼无感。`high` 档 4096 图保持不变。

**风险**：低-中。`far` 从 ~49 拉到 ~190 会放大固定 `shadow.bias = -0.0002`（line 384）在世界空间的等效偏移（归一化深度 × (far−near)），可能出现 Peter-panning。**这与 L10 是同一组参数，建议 L2 与 L10 一起改、一起目视。**

### L3 天气滑杆触发无上限 PMREM 重建 · 🔴 A 类（性能）

**现象**：拖动天气面板任意滑杆时明显掉帧。

**机理（完整触发链，无任何去重）**

```
WorldPackagePanel.vue:64-69   el-slider @input="setWeather(key, $event)"   ← 7 条连续滑杆
  → worldPackageStore.setEnvironment()
  → worldEnvironmentRuntime.ts:82  listeners.forEach(...)
  → CanvasViewport.vue:237-241     applyTimePreset()
  → CanvasViewport.vue:1166        rebuildEnvironment(preset, atmosphere)
  → CanvasViewport.vue:1236-1247   pmremGenerator.fromScene(...) + previousTarget.dispose()
```

**证据**：60 个滑杆事件 → 59 次 `fromScene()` + 59 次 `dispose()`。每次 `fromScene` 是一遍立方图 6 面渲染 + PMREM 卷积 + GPU 纹理创建/销毁。

**修法**：在 `applyTimePreset` 内对 PMREM 重建加「签名去重 + 尾沿节流」。

```ts
// 把影响环境贴图的输入量化成签名；只有签名变化才重建 PMREM。
function environmentSignature(preset: TimePreset, atmo: WorldAtmosphereAppearance): string {
  const q = (v: number) => Math.round(v * 32) / 32   // 1/32 量化，肉眼不可辨
  return [preset.label, q(atmo.cloud), q(atmo.rain), q(atmo.snow), q(atmo.dust),
          q(atmo.fog), q(atmo.tintStrength), q(atmo.backgroundTint)].join('|')
}
```
签名不变则跳过 `rebuildEnvironment()`，其余（灯光强度、天空 uniform、阴影不透明度）照常更新 —— 这些是纯 uniform 写入，成本可忽略。

离散切换（时段 / 环境档 / 画质档 / WILD profile）必须**绕过去重立即重建**：给 `applyTimePreset(forceEnvironment = false)` 加一个强制参数，由 `cycleTimeOfDay` / `cycleEnvironmentPreset` / `applyQualityPreset` / `worldLookRuntime.subscribe` 传 `true`。

**风险**：低。注意签名必须包含所有影响 `syncSkyPreset` 的输入，否则会出现「改了天气但环境贴图没跟上」。

### L4 SSAO「半分辨率」实际未生效 · 🔴 A 类（性能）

**现象**：`CanvasViewport.vue:318` 注释声称「SSAO 半分辨率 + 更细核：开销减半」，实测跑全分辨率。

**机理**
- `SSAOPass(scene, camera, width, height)` 的 `width/height` 是**目标像素尺寸**，默认 512；传 `0.5, 0.5` 只是把初始 RT 建成 0.5×0.5 纹素。
- three `examples/jsm/postprocessing/SSAOPass.js:313-328` 的 `setSize(width, height)` 把 `ssaoRenderTarget / normalRenderTarget / blurRenderTarget` **直接设为传入值，没有任何缩放语义**。
- `EffectComposer.setSize()` 对每个 pass 下发 `width × pixelRatio`；`CanvasViewport.vue:480` 在 `initThreeJS()` 末尾就调用了 ⇒ 构造参数被全量覆盖。

**为什么可以安全地减半**：0.160.1 的 `SSAOPass.OUTPUT.Default`（`SSAOPass.js:236-249`）以 **`readBuffer.texture`（合成器全分辨率缓冲）** 为底图，只用 `blurRenderTarget` 走 `CustomBlending` 叠加 AO 项。因此缩小内部 RT **不会降低底图清晰度**，只会让 AO 项被上采样 —— 这正是「半分辨率 SSAO」的正确形态。

**修法**

```ts
const SSAO_SCALE = 0.5
const baseSsaoSetSize = ssaoPass.setSize.bind(ssaoPass)
// SSAOPass.setSize 内部会一并刷新 ssao/blur 的 resolution uniform 与投影矩阵 uniform，
// 所以只需在入口处缩放入参，内部即自洽。
ssaoPass.setSize = (width: number, height: number) =>
  baseSsaoSetSize(Math.max(1, Math.round(width * SSAO_SCALE)), Math.max(1, Math.round(height * SSAO_SCALE)))
```

**风险**：低。AO 边缘略软（本就是低频项，且后接 blur）。缩分辨率后建议把 `kernelRadius` 从 4 提到 6~8 补偿采样密度（`CanvasViewport.vue:320`）。

### L5 `shadow.radius = 4` 是死配置 · 🟡 A 类

**机理**：three 0.160.1 `shadowmap_pars_fragment.glsl.js`

```glsl
#if defined( SHADOWMAP_TYPE_PCF )
  float dx0 = - texelSize.x * shadowRadius;   // ← 只有这一支引用 shadowRadius
  ...
#elif defined( SHADOWMAP_TYPE_PCF_SOFT )
  vec2 texelSize = vec2( 1.0 ) / shadowMapSize;
  float dx = texelSize.x;                      // ← 固定 9 抽样 bilinear kernel，不读 radius
```
项目用 `PCFSoftShadowMap`（`CanvasViewport.vue:298`）⇒ 编译出 `SHADOWMAP_TYPE_PCF_SOFT` ⇒ `shadow.radius = 4`（line 386）不产生任何效果。

**修法（二选一）**
- (a) **推荐**：删掉该行并注明「PCF_SOFT 不读 radius，柔化靠降 mapSize / 提高 SSAO」。零视觉变化。
- (b) 想真正拿到可控柔化：改用 `VSMShadowMap`（读 `radius` + `blurSamples`），但需处理漏光并重调 bias —— 属 B 类以上，建议单独立项。

### L6 夜间 Bloom 档位没有可泛光的内容 · 🟡 A 类 + 内容侧

**机理**：Bloom 位于 `OutputPass(ACES)` **之前**，作用于**线性 HDR** 值，阈值 `1.05`（`CanvasViewport.vue:324`）。

夜晚光照预算（`audit-lighting §6`）：主光 0.334 + 半球光 0.163 ⇒ 漫反射线性亮度上限 **0.397**（按 albedo 0.8 估），**远低于阈值**。能突破阈值的只有自发光与灯光构件，而两者在现有蓝图中**均为 0**。

⇒ `bloomPass.enabled = QUALITY_PRESETS[quality].bloom && timeOfDay === 'night'`（line 1188）在当前内容下等于白开，只有开销没有画面收益。

**修法（两条腿，建议先 a 后 b）**
- (a) **内容侧**：让生成器产出窗洞自发光与灯光构件（见 §四 **G1**）。这是让夜间档真正有意义的根本。
- (b) **渲染器侧**：Bloom 阈值随时段变化 —— 白天维持 1.05（避免大量受光面泛光：白天上限 2.641），夜晚降到 0.6~0.8。需在 `applyTimePreset` 内写 `bloomPass.threshold`。

---

### L7 阴影贴花颜色不随环境变化 · ⚪ A 类

**机理**：`CanvasViewport.vue:398` 阴影色恒为 `0x26352d`；只有 `opacity` 随环境与时段变化（line 1190-1196）。

**证据**：沙漠环境地面色 `#b9844f` 与阴影色色相偏差 **118°**、亮度比 0.353；秋林偏差 102.6°。⇒ 沙漠/秋林的投影呈"冷绿黑"，与暖色地面脱节。

**修法**：让阴影色跟随环境地面色做暗化

```ts
shadowGround.material.color
  .copy(new THREE.Color(environmentPreset.groundColor))
  .multiplyScalar(0.32)
  .lerp(new THREE.Color(atmosphere.groundTint), atmosphere.tintStrength * 0.5)
```
`opacity` 保持现有链路。**风险**：低。极简环境下会从 `#26352d` 变为 `#747b73 × 0.32 ≈ #252724` —— 几乎等价，不会破坏已验收的 P0 阴影落地感。

### L8 晴天 / 黄昏无空气透视 · 🟡 A 类（观感）

**机理**：`CanvasViewport.vue:1370-1393`

```ts
if (presenting || atmosphere.fog > 0.025) { /* 设 Fog / FogExp2 */ }
else { scene.fog = null }
```
`WORLD_WEATHER_PRESETS.clear.fog = 0.02`（`worldWeatherRuntime.ts:26`）⇒ 0.02 不大于 0.025 ⇒ **编辑器视图无 fog**。

**影响**
- 内置环境（山体 / 远树，半径 `Math.max(30, lightingExtent × 3.6)`，line 1109）与天空背景之间没有过渡，远景"贴"在天空上。
- L2 的长影硬切失去了天然的远端淡出（`ShadowMaterial` 的 `fog` 默认为 true，有 fog 时会自动向雾色过渡）。

**修法**：引入「空气透视下限」——只要天空可见（`preset.skyVisible` 或非 presentation 之外仍希望有纵深），就保持一个极轻的 `THREE.Fog`：`near` 由相机距离推，`far` 取 `lightingExtent × 40` 量级；天气档只在其上叠加。

**风险**：低-中。会改变**所有**场景的整体观感，建议与界面精致化一起定调，不要单独悄悄改。

---

### L9 拖动构件时阴影滞后 · ⚪ A 类

**机理**：`SHADOW_DIRTY_THROTTLE_MS = 120`（line 230）；`handleTransformObjectChange`（line 910-916）只在距上次 ≥120ms 时置脏。

另有一处边界：`handleTransformMouseUp`（line 923）在 `delta.lengthSq() < 1e-10` 时提前 `return`，这条路径不补阴影刷新。正常拖拽会走 `applyPatch → updateScene → markShadowsDirty`，所以只在「拖出去又拖回原位」这类零净位移场景下遗留脏阴影。

**修法**：加一次尾沿定时器（拖动停止后 ~120ms 补一次 `markShadowsDirty()`）；或把节流降到 50ms。更优雅的做法：拖动中把 `shadowMapSize` 临时降到 1024，松手恢复。**风险**：低。

---

### L10 `normalBias` 与阴影图分辨率不自洽 · 🟡 A 类

**机理**：`CanvasViewport.vue:1472`

```ts
directionalLight.shadow.normalBias = Math.max(0.008, lightingExtent * 0.0015)
```
它只跟 `lightingExtent` 挂钩。当 `mapSize = 2048` 时，纹素尺寸 `= 2 × extent / 2048`，故 `extent × 0.0015 ≈ 1.54 × texel` —— 恰好等于「1.5 纹素」这个合理取值。**换个阴影图分辨率就错位**：

| mapSize（画质档） | texelSize | normalBias | 折合纹素 | 后果 |
|---|---|---|---|---|
| 1024（流畅） | `extent × 0.00195` | `extent × 0.0015` | **0.77×** | 欠 bias → 自阴影痤疮 / 摩尔纹 |
| 2048（均衡） | `extent × 0.00098` | `extent × 0.0015` | 1.54× | 合理 |
| 4096（精细） | `extent × 0.00049` | `extent × 0.0015` | **3.07×** | 过 bias → 接触阴影变淡、薄构件漏影 |

**修法**：改为按纹素尺寸表达，与 `mapSize` / `extent` 自动自洽

```ts
const shadowTexel = (2 * lightingExtent) / directionalLight.shadow.mapSize.width
directionalLight.shadow.normalBias = NORMAL_BIAS_TEXELS * shadowTexel   // NORMAL_BIAS_TEXELS ≈ 1.5
```

**风险**：低，但会改变低/高画质档的阴影观感（这正是目的）。**与 L2 同组，建议一起改。**

## 四、建筑组件（内容 / 几何 / 材质侧）的光影空间

### G1 生成器不产出任何灯光 / 自发光 · 🔴 内容侧

**事实**
- 后端 schema 已就绪：`wild-server/app/agent/generation/components.py` 定义了 `lightType` / `initiallyOn` / `lowIntensity` / `highIntensity` / `distance` / `angle` / `color`。
- 前端渲染已就绪：`renderEntity.ts:210-233` 完整实现了 `PointLight` / `SpotLight` 挂载、亮度档位（`lightIntensityAt`）与开关过渡动画。
- **但 `0/7` 现有蓝图含灯光构件，`0/7` 含 `emissive`。**

**影响**：夜间档（L6）、灯光交互、Bloom 三者全部空转。夜间就是"曝光 0.68 的黑色建筑 + 深蓝天空"。

**建议**：生成阶段为规则建筑产出「窗洞自发光 + 每层一个 PointLight（`initiallyOn: false`，交给交互点亮）」。一次点亮三条能力，是投入产出最高的一步。属跨前后端改造，**需单独立项走能力评估**。

### G2 法线来源与硬边表现 · 🟡 几何侧

**机理**：`meshDataToGeometry.ts:44-48`

```ts
if (meshData.normals) geometry.setAttribute('normal', ...)
else geometry.computeVertexNormals()
```
对**带索引**的网格，`computeVertexNormals()` 会跨面平均 → 盒体 / 墙体边缘被"磨圆"，硬边光影消失。

**建议**：先统计现有蓝图 `normals` 缺失比例（可加一条诊断）；对缺失项按折痕角（如 40°）重算法线，而非无条件平均。

### G3 AO 通道已铺好但无内容 · ⚪ 几何侧

**机理**：`meshDataToGeometry.ts:74-79` 把同一份 UV 同时挂到 `uv` / `uv1` / `uv2`，`materialAdapter.ts:213-215` 已支持 `textures.ambientOcclusion → aoMap`；但没有任何材质产出 AO 贴图。

**建议**：若希望 `low` 档关掉 SSAO（`QUALITY_PRESETS.low.ssao = false`）后仍保留角落暗部，最稳的是在**生成侧**烘焙一份廉价 AO（顶角 / 檐下 / 凹角），走已有的 aoMap 通道 —— 零渲染器改动，且能被 IBL 与 fog 正确调制。

### G4 半透明构件投出实心阴影 · ⚪ 几何侧

**机理**：`renderEntity.ts:86`

```ts
mesh.castShadow = !(material instanceof THREE.MeshPhysicalMaterial && material.transmission > 0)
```
玻璃（`transmission > 0`）已正确关闭投影。但 `materialAdapter.ts:167-175` 走 `opacity < 0.99 → transparent = true` 这条路的材质，**`transmission === 0` 时仍会投出全不透明阴影** —— shadow depth 材质不读 `opacity`。

**建议**：对这类材质加 `alphaTest`（如 0.5）或同样关闭 `castShadow`。需先确认现有蓝图是否存在该类材质（可加诊断）。

| 顺序 | 项目 | 理由 | 状态 |
|---|---|---|---|
| 1 | **L3** | 纯性能、零画面风险、可独立验证（滑杆拖动帧率） | ✅ 已实施 |

**L8 与 L6(b) 为什么暂缓**

- **L8（空气透视下限）** 会给**所有**场景叠加一层雾，直接改变整体观感调性。
  它和"界面精致化"是同一个决策（雾的浓度/色温要和新的视觉基调一起定），
  单独先改会多一轮返工，所以留到那批一起做。
- **L6(b)（Bloom 阈值随时段变化）** 的正确做法是"先有可泛光的内容，再调阈值"。
  在 G1 之前，把夜间阈值从 1.05 降到 0.65 只能让受光的墙面与地面开始发糊，
  画面收益为负。等 G1 产出窗洞自发光/灯光构件后再一起调，才是对的顺序。
