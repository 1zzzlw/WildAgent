## 〇、修复记录（本次已落地）

### 设计约定（重要）

板厚的增厚方向**必须向下**，因为编译期的 `roofSurfaceHeight()` 已把 gable/hip 的**屋面外表面**定义为"檐口 `y=0` → 屋脊 `y=height`"这条平面（`wild-compiler/components/attachedToSurface.ts:137-143`）：

```ts
if (roof.roofType === 'flat') return roof.thickness   // flat: 顶面 = thickness（向上增厚）
const widthRatio = Math.min(1, Math.abs(localX) / (roof.span / 2))
if (roof.roofType === 'gable') return roof.height * (1 - widthRatio)  // gable: 顶面 = 参考面
```

檐口（`cornice`）、烟囱（`chimney`）都靠它定位。若把板厚**向上**增厚，屋面会整体抬高 `thickness`，导致檐口/烟囱相对屋面下沉一个板厚。所以采用：

| 面 | 双坡（gable） | 四坡（hip） |
|---|---|---|
| 屋面（顶面，法线朝上） | 檐口 `y=0` → 屋脊 `y=h` | 同 |
| 底面（法线朝下） | **水平面 `y=-t`** | 斜面：檐口 `y=-t` → 屋脊 `y=h-t` |
| 檐口立板 | `x=±hw` 两块（高 `t`） | 矩形周圈四条（高 `t`） |
| 端面封边 | `z=±hd` 的**完整五边形截面**（见下） | 无（四坡四周都是檐口，四坡自封闭） |

双坡的截面是**凸五边形** `(-hw,-t) → (hw,-t) → (hw,0) → (0,h) → (-hw,0)`，沿 Z 轴拉伸成闭合实体：上两条边就是屋面外表面（檐口 `y=0` → 屋脊 `y=h`，契约不变），下边是水平板底 `y=-t`，两个竖直短边是 `t` 高的檐口立板，**而 `z=±hd` 的末端面就是这个五边形本身**——山墙端头因此天然封死。

对照 `buildFlat`（`roof.ts`）：flat 向上增厚，因为它的可见顶面若留在 `y=0` 会与墙顶共面；gable/hip 的屋面是斜面，只在檐口线擦边，不存在共面问题。

### 第二轮：修「屋顶端面变空心」的回归（同日晚）

第一轮把端面从"完整三角面"改成了"板厚窄带"，结果建筑山墙端头被打开，从正面可以**直接看穿进室内**（用户截图反馈："为什么变成这样的了"）。

**根因**：旧 `buildGable` 其实是一个**实心三棱柱楔**（两个山墙三角面 + 两个坡面 + 底盖 `y=0`），它的山墙三角面顺带承担了"封闭建筑端头"的职责；而蓝图 `simple_villa.wild` 只有 4 面矩形墙、**没有任何山墙墙元素**，所以一旦端面只剩板厚窄带，墙顶以上的阁楼三角区就彻底敞开。

量化证据（`.workbuddy/diag/analyze-gable-end.mjs`，在 `z=±hd` 平面上做网格采样）：

| 中间版本（只留板厚窄带） | 4 | 2.3200 | **19.3%** ❌ |
| 本次修复（完整五边形） | 3 | 19.1400 | **100.0%** ✅ |

穿透检测（`.workbuddy/diag/detect-hollow.mjs`，在阁楼区铺 685 个采样点、从建筑外侧沿轴向打入射线，统计第一个命中面相对端面的深度）：

|---|---|---|

### 顺带修掉的隐藏 bug

这三个是在写校验脚本时才暴露出来的，**若只"补个厚度"会留下更严重的坑**：

1. **端面扇形三角化不能用在凹多边形上（已不再适用）。** 第一轮的端面是"雪佛龙带"（凹多边形），单顶点扇出会把缺口外的区域也填进去 → 边界边无法成对闭合（实测 30 条边只有 18 条配对）。**第二轮的凸五边形截面改成整面填充后，该问题连同端面空洞一起消失**——现在从 `p0` 扇形剖分成 3 个互不重叠的三角形即可。
2. **四坡的坡面归属随屋脊走向互换。** 屋脊沿 Z 时山面在 ±Z、坡面在 ±X；屋脊沿 X 时正好相反。原先把两个分支硬合并成一张面表，`hd < hw` 的窄深屋顶会算错（`hip 8×6` 体积只有正确值的 1/6）。
3. **端面必须是"整面"而不是"板厚截面"。** 这条是最贵的教训：只做"技术正确"的板厚截面，会破坏建筑端头的封闭性。屋顶几何的职责边界里包含"封闭建筑端头"。

同时新增 `pushSolidTriangle` 跳过零面积三角形，避免 `ridgeHalf = 0`（四角锥）时 `computeVertexNormals` 归一化零向量得到 NaN 而整块屋面变黑。

### 🔴 2. 屋顶底面与墙顶严格共面 → Z-fighting —— ✅ 已修复

> 板底下移到 `y = -thickness` 后，屋顶只在檐口线（一条线）与墙顶擦边，不再存在共面**面片**。详见「〇、修复记录」。

### 🔴 3. 自定义表面着色器的"世界法线"算错

`src/renderer/materialFeatures/defaultSurfaceMaterial.ts:88-95`

```glsl
.replace('#include <defaultnormal_vertex>',
  '#include <defaultnormal_vertex>\nvWildDefaultWorldNormal = normalize(mat3(modelMatrix) * transformedNormal);')
```

three.js 的 `<defaultnormal_vertex>` 执行完毕后，`transformedNormal` **已经是视图空间向量**（已乘 `normalMatrix`，见 three r160 `ShaderChunk/defaultnormal_vertex.glsl.js`）。再乘 `mat3(modelMatrix)` 得到的是一个既不属物体空间也不属世界空间的无意义向量。

同时：对 `InstancedMesh` 完全没有乘 `instanceMatrix`。同文件里世界坐标的注入是**有**处理实例矩阵的（defaultSurfaceMaterial.ts:104-110），说明本意是要支持实例化渲染，只是法线这一处漏了。

该 varying 被用于 `color_fragment` 阶段的朝上掩码（:178-196）：雨痕、积雪、积尘的贴附方向全部依赖它。默认 `snow = 0 / dust = 0` 时看不出来，一旦开雪或沙尘，效果会**随相机旋转而漂移**。

修法：改用未乘 `normalMatrix` 的 `objectNormal`，并补实例矩阵分支：

```glsl
vec3 wildObjectNormal = objectNormal;
#ifdef USE_INSTANCING
  wildObjectNormal = mat3(instanceMatrix) * wildObjectNormal;
#endif
vWildDefaultWorldNormal = normalize(mat3(modelMatrix) * wildObjectNormal);
```

### 🟡 4. 阴影是"按需重算"的，存在标志位被提前消费的竞态

`CanvasViewport.vue:290-294` 关闭了 `renderer.shadowMap.autoUpdate` 与 `directionalLight.shadow.autoUpdate`，意图是省掉拖动视角时的阴影重渲。

但 `markShadowsDirty()`（`CanvasViewport.vue:1481-1485`）**只置位不触发渲染**；真正出帧由 `scheduleRenderFrame()` 驱动。如果在这之间另有 `markNeedsRender()`（OrbitControls 的 `change`、resize、纹理加载回调等）先跑了一帧，`needsUpdate` 会被那一帧消费掉，结果是**阴影停留在旧状态或整帧无阴影**。

→ 建议把 `markNeedsRender()` 收进 `markShadowsDirty()`，或把"脏标记 + 渲染"绑定成一次原子调度。

### 🟡 5. 材质默认全部 `DoubleSide`

`materialAdapter.ts:220-222`

```ts

material.side = params.side === 'front' ? THREE.FrontSide : THREE.DoubleSide
```

实测本样本 **62 个材质 100% 都是 `DoubleSide`**（含墙壁、地面、屋顶等封闭实体）。代价：

- 阴影 pass 需渲染双倍面，acne 风险上升（目前靠 `shadow.normalBias = 0.025` 压住）
- 面绕序错误被掩盖，长期不暴露

→ 建议按构件类型白名单开启 `FrontSide`（墙 / 楼板 / 地面 / 屋顶这类封闭实体）。

| `renderEntity.ts:40-59` | `MAX_VERTICES` 超限时整构件被换成红色线框盒，仅 `console.warn`，用户在界面上看不到原因。本样本最大构件仅 154 三角面，暂无触发 |
| `materialAdapter.ts:168-180` | 透射材质走 `transparent = false` + `depthWrite = true`；而查看器对玻璃显式设了 `transparent = true`。两者渲染列表归属一致，但深度写入策略不同 |

另外玻璃在两套里走的是**不同材质实现**：编辑器走 `surface.pbr.v1` 自定义着色器（`materialFeatures/registry.ts:77-86` → `pbrEnvironmentMaterial.ts`）并叠加 `scene.environment` IBL；查看器是裸 `MeshPhysicalMaterial`。这是窗户玻璃一亮一暗的来源。

## 三、修复优先级建议

**先分清层次再动手**——这 6 项里只有 4 项属于"前端渲染代码"，第 1 项根本不在前端。

| 优先级 | 动作 | 所在层 | 涉及文件 | 状态 |
|---|---|---|---|---|
| 1 | 给 `gable` / `hip` 补板厚与檐口（顺带消掉共面） | **几何引擎**（不是前端） | `wild-core/src/primitive/geometry/roof.ts:240,259` | ✅ **已完成** |
| 2 | 修表面着色器的世界法线（含实例矩阵） | 前端渲染 | `renderer/materialFeatures/defaultSurfaceMaterial.ts:88-95` | 待办 |
| 3 | 抽出共享的"取景"工具，两套界面共用 | 前端渲染 | `CanvasViewport.vue:1453` + `lantu/viewer/main.ts:111` | 待办 |
| 4 | 提高白天投影强度，或让地面参与 `receiveShadow` | 前端渲染 | `renderer/defaultWorldLook.ts:101`、`CanvasViewport.vue:413` | 待办 |
| 5 | 阴影脏标记与渲染调度原子化 | 前端渲染 | `CanvasViewport.vue:1481-1485` | 待办 |
| 6 | 封闭实体材质白名单开启 `FrontSide`；按能力给 MSAA | 前端渲染 | `renderer/materialAdapter.ts:222`、`CanvasViewport.vue:287` | 待办 |

### 如果目标只是"让前端看起来和图 1 一致"

那么**真正的前端改动只有三项**，且顺序应该反过来：

1. **取景算法（第 3 项）** —— 这是图 1 / 图 2 观感差异的第一大来源，改动小、收益立竿见影。
2. **投影强度（第 4 项）** —— 让建筑有落地感，是"精致度"差距的主要来源。
3. **世界天气状态** —— 图 2 是雨天预设，本身不是 bug；把默认档恢复成晴天即可。

**"屋顶没有宽度"这一条不属于前端**，改前端渲染代码无论怎么改都不会出现板厚与檐口，必须回到 `wild-core` 的 `roof.ts`。
