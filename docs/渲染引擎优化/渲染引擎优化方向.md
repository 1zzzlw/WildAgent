# 渲染引擎优化方向（含参数边界分析）

> 结论先行：**渲染引擎优化在绝大多数情况下不需要改动参数，也就不需要动后端和知识库。**
> 本文用代码证据划清「参数边界」，再给出按层分级的优化方向。

---

## 一、为什么"改渲染引擎"通常碰不到参数

### 1.1 `.wild` 参数面其实很窄

蓝图的顶层结构是**封闭**的，规范文档明确禁止扩展：

```json
{
  "meta": { "version": "1.1", "type": "building", "name": "建筑名称" },
  "geometry": { "elements": [], "components": [] },
  "materials": {},
  "behaviors": {}
}
```

出处：`wild-server/storage/knowledge_base/BLUEPRINT-SPEC-MINIMAL.md:20-32`，原文写的是
「**禁止在根级别出现 elements、bounds 或其他字段**」。

也就是说，`.wild` 只描述**几何与材质引用的数值**（`span` / `depth` / `height` / `thickness` / `position` / `roofType` …），
不描述任何"怎么画"的东西。

### 1.2 相机、时间、环境、天气、画质**根本不在 `.wild` 里**

它们走的是另一份文档 `wild.world`，而且只存在浏览器本地：

| 状态 | 存放位置 | 证据 |
|---|---|---|
| 世界文档（instances / chunks / materialLibraries / environment） | `localStorage`，键前缀 `wild_world_document_v1:` | `renderer/worldDocumentPersistence.ts:5,12-37` |
| 时间档（白天/黄昏/夜晚） | 前端常量表 | `renderer/defaultWorldLook.ts:63-86` |
| 画质档（流畅/均衡/精细：pixelRatio、shadowMapSize、ssao、bloom） | 前端常量表 | `renderer/defaultWorldLook.ts:89-95` |
| 相机预设（corner/human/bird/front 的方向向量） | 前端常量表 | `renderer/defaultWorldLook.ts:97-104` |
| 环境预设（极简/草地/雪山/沙漠/秋林：地面色、雾色、直射光倍数、**剪影阴影不透明度**） | 前端常量表 | `renderer/defaultWorldLook.ts:106-123` |

→ **这一整层怎么调都不会触达后端与知识库。**

### 1.3 一个现成的反例：本次屋顶修复是**零参数改动**

用户要的"板厚 + 檐口"，用的就是既有的 `roof.thickness` —— 它早就写在知识库里了：

```
wild-server/storage/knowledge_base/BLUEPRINT-SPEC-MINIMAL.md:94-112
### roof（屋顶）
{ "type": "roof", "id": "main_roof", "roofType": "gable",
  "span": 7.0, "depth": 6.0, "height": 2.5,
  "thickness": 0.3, "material": "tile", "position": [3, 3, 2.5] }
```

问题从来不在"参数里没有厚度"，而在 **`wild-core` 的几何引擎没去读它**。
修复只改了 `buildGable` 怎么消费这个已有数值，知识库、提示词、后端一行没动。

### 1.4 后端校验是"轻量级"的，而且项目已有渲染层私有通道

- 后端 `validate_blueprint_schema` 的注释写得很清楚（`wild-server/app/utils/blueprint_parser.py:631-635`）：
  「**只检查基本结构完整性**（meta/geometry/elements 存在性、ID 唯一性），不做空间关系校验」——
  **它不拒绝未知字段**。
- 更关键的是，项目**已经有**传递"仅供编译器和 renderer 使用、不属于可手写 WILD 字段"的既有约定：下划线前缀字段。

```ts
// wild-web/src/wild-core/types.ts:384-392
/** 仅供组合编译器和 renderer 使用，不属于可手写的 WILD opening 字段。 */
_interaction?: InteractiveElementBehavior;
/** 仅供 door 编译器使用；把门板细节合并进同一可交互网格。 */
_doorLeafDetail?: { rows: 2 | 3; columns: 1 | 2; hingeSide: 'left' | 'right'; doubleDoor: boolean };
```

同类还有 `_gableEnds`（`chinese_curved` 屋顶的运行时山墙数据）。
**渲染层若要新数据，走这条通道即可，不必碰 `.wild` 契约。**

### 1.5 三类改动的波及面

| 类型 | 例子 | 前端解析器 | 后端校验 | 知识库文档 | 生成提示词 | 既有 `.wild` 文件 |
|---|---|---|---|---|---|---|
| **A 纯渲染实现** | 光照、取景、材质着色、抗锯齿、后处理、面剔除、几何体形状 | 不动 | 不动 | 不动 | 不动 | 不动 |
| **B 新增渲染私有字段** | `_roofRidge`、`_eaveProfile` 等下划线字段 | 加可选字段 | 不动（不校验未知字段） | 不动 | 不动 | 不动（旧文件缺字段走默认值） |
| **C 修改契约参数** | 改 `roof.thickness` 语义、新增可被 LLM 书写的 `roof.overhang` | 改类型 | 可能改校验 | **必须改** | **必须改** | **可能需迁移** |

**渲染引擎优化的 90% 属于 A 类；剩下 10% 属于 B 类。C 类只在"想给 LLM 增加一个新旋钮"时才需要。**

## 二、当前渲染引擎的现状盘点（实测）

在 `wild-web` 用真实重建链路跑 `simple_villa.wild`：

| 指标 | 实测值 |
|---|---|
| 网格数 / 材质参数数 | 62 / 62 |
| 走 `surface.default.v1` 的面 | **55 个网格、774.75 m²、占总面积 95.8%** |
| 走 `surface.pbr.v1` 的面 | 7 个网格、34.28 m²、占 4.2% |
| 抗锯齿 | `antialias: false`，仅靠后处理 FXAA（`CanvasViewport.vue:287、320`） |
| 色调映射 | `ACESFilmic`，曝光 1.05（`:296-297`） |
| 阴影 | `PCFSoftShadowMap` + `autoUpdate = false`（`:290-294`） |
| 地面 | 地面本体只受光不接收阴影（`presentationGround.receiveShadow = false`，`:413`）；阴影靠一块透明 `ShadowMaterial` 叠层模拟（`:388-395`） |
| 剪影阴影不透明度 | 极简档 **0.22**（`defaultWorldLook.ts:101`）再乘 `worldLook.shadowOpacity`（`CanvasViewport.vue:1124,1165-1167`）→ 实际约 **0.17** |
| 面剔除 | 默认全 `DoubleSide`（`materialAdapter.ts:222`），只有显式 `side:'front'` 才开剔除 |

### 关于"世界法线"着色 bug 的更正

之前诊断报告把它列为 🔴，**实测影响被高估了**。虽然计算确实是错的：

```glsl
// renderer/materialFeatures/defaultSurfaceMaterial.ts:103
'#include <defaultnormal_vertex>\nvWildDefaultWorldNormal = normalize(mat3(modelMatrix) * transformedNormal);'
```

`<defaultnormal_vertex>` 之后 `transformedNormal` 已经是**视图空间**法线，再乘 `modelMatrix` 无意义
（正确写法是 `inverseTransformDirection(transformedNormal, viewMatrix)`；而且它漏了 `instanceMatrix`）。

但它在片元着色器里**只被天气遮罩使用**（`:178-196`）：

```glsl
vec3 wildDefaultNormal = normalize(vWildDefaultWorldNormal);
float wildVerticalMask = 1.0 - abs(wildDefaultNormal.y);  // 雨丝竖直遮罩
float wildUpward = smoothstep(0.28, 0.82, wildDefaultNormal.y);  // 积雪 / 积尘朝上遮罩
```

**核心光照用的是 three.js 自己的 `normal`，不受影响。** 晴天（雪/雨/尘均为 0）时几乎无影响。
→ 优先级应降为 🟡。

## 三、优化方向（按层 + 波及面）

### 3.1 渲染管线层 —— 零参数改动，收益最大

| 优先级 | 动作 | 现状 → 目标 | 涉及位置 | 波及面 |
|---|---|---|---|---|
| 🔴 1 | **恢复落地感**：建筑"浮"在地面上 | 剪影阴影 0.17 → 0.35~0.45；或让地面本体 `receiveShadow = true` 并撤掉叠层（二选一，避免双重变黑） | `defaultWorldLook.ts:101-123`、`CanvasViewport.vue:388-415` | A 类，无 |
| 🔴 2 | **统一取景工具** | 编辑器 `×1.55` / corner `[1,0.62,1]`（俯角约 24°，偏低偏近，容易看到屋面底面）→ 抽公共函数并略抬高俯角，让屋面成为主体 | `CanvasViewport.vue:1453-1474` + `lantu/viewer/main.ts:111-124` | A 类，无 |
| 🔴 3 | **材质质感**：96% 面积是纯程序化 UV 图案 | 给 `surface.default.v1` 补法线/粗糙度扰动，或扩大 `surface.pbr.v1` 覆盖面（玻璃已在用 PBR，一亮一暗的根源） | `materialFeatures/defaultSurfaceMaterial.ts`、`materialAdapter.ts` | A 类，无 |
| 🟡 4 | **抗锯齿** | `antialias:false` + FXAA → 按 `capabilities` 给 MSAA，或换 SMAA | `CanvasViewport.vue:287,320` | A 类，无 |
| 🟡 5 | **接触阴影 / SSAO 默认开** | 仅 medium 档开 SSAO → 默认档开启，或加一层廉价接触阴影 | `defaultWorldLook.ts:89-95` | A 类，无 |
| 🟡 6 | **面剔除** | 96% 面 `DoubleSide` → 已闭合实体白名单开 `FrontSide`（本次屋顶已确认水密，可入白名单） | `materialAdapter.ts:222` | A 类，无 |
| 🟡 7 | **世界法线着色** | 视图空间法线误乘 `modelMatrix` → `inverseTransformDirection(...)`，并补 `instanceMatrix` | `defaultSurfaceMaterial.ts:103` | A 类，无 |
| ⚪ 8 | **阴影脏标记原子化** | `autoUpdate=false` + `needsUpdate` 存在中间帧消费的时序风险 | `CanvasViewport.vue:1483` | A 类，无 |

### 3.2 编译层 / 几何层 —— 零参数改动

- 屋面细节：屋脊瓦、檐口线脚、烟囱（`chimney` 组件已存在）、山墙通风口
- 墙体细节：勒脚、窗套、阳台（`balcony` / `bayWindow` 组件已存在）
- 几何精度：曲面细分段数、UV 连续性、共面检测（已有 `check-coplanar.mjs`）

### 3.3 参数契约层 —— **建议暂时不动**

只有在需要"让 LLM 能写出一个新的可控数值"时才涉及，届时必须**四处同改**：

1. 知识库文档 `storage/knowledge_base/BLUEPRINT-SPEC-*.md`
2. 生成提示词 `app/agent/prompts/generation.py`
3. 前端类型 `wild-core/types.ts`
4. （可选）后端校验与空间工具

### ⚠️ 屋顶檐口状态说明

**代码分析结果**：
1. `buildGable` 函数**已正确实现**板厚和檐口逻辑
2. 蓝图参数 `thickness: 0.2` **已存在且会被读取**
3. 几何引擎会生成闭合五边形截面实体（含檐口立板）

**可能的视觉问题原因**：
1. **材质遮挡**：檐口立板可能与屋面使用相同材质，颜色过于相近导致难以区分
2. **光照角度**：某些光照条件下檐口立板的厚度不明显
3. **取景角度**：之前的俯角可能正好看不到檐口厚度
4. **需要重新构建**：代码修改后需要重新编译前端

**建议验证步骤**：
1. 重新构建前端项目（`npm run build` 或 `npm run dev`）
2. 用新的取景角度查看（现在俯角已提高）
3. 检查屋面和檐口是否使用了不同材质/颜色
4. 用浏览器开发工具检查渲染的几何体数量和顶点数

如果重新构建后仍看不到檐口，可能需要：
- 增加檐口与屋面的材质对比度
- 添加檐口独立材质定义
- 调整光照角度突出厚度

## 五、如果"效果还是不好"指的是屋顶本身

那两个嫌疑点**都不在渲染引擎的参数上**：

| 嫌疑点 | 实测 | 归属 |
|---|---|---|
| 屋面坡度过缓 | `height 2.9 / (span 11.6 ÷ 2) = 0.5` → **约 26.6°**，视觉上偏"扁" | **蓝图数据**（`simple_villa.wild` 的 `roof.height`） |
| 屋面材质是纯色程序化图案 | `roof_tile` 走 `surface.default.v1`，无贴图、无法线细节 | **材质实现**（见 3.1 第 3 项） |

前者改数据（或让生成侧给更合理的默认坡比），后者改材质实现。**两者都不需要动知识库。**

## 六、未来渲染引擎优化重点方向（按优先级）

### 6.1 高优先级（立竿见影的视觉改善）

#### 🔴 P0：阴影落地感（最容易被用户察觉）

**现状**：建筑物看起来"浮"在地面上，缺少真实感
- 剪影阴影不透明度 = 极简档 0.22 × worldLook.shadowOpacity ≈ **0.17**（过淡）
- 地面本体 `receiveShadow = false`，阴影靠一块透明 `ShadowMaterial` 叠层模拟

**改进方案（二选一）**：
1. **方案A（快）**：提升阴影不透明度 0.17 → 0.35~0.45
   - 修改位置：`defaultWorldLook.ts:101-123`、`CanvasViewport.vue:388-415`
   - 波及面：A 类（纯渲染参数）
2. **方案B（彻底）**：让地面本体 `receiveShadow = true` 并撤掉叠层
   - 好处：消除双重变黑，更真实
   - 代价：需调整地面材质接收阴影的方式

**建议**：先做方案A验证效果，如不满意再上方案B

#### 🔴 P1：统一取景工具（决定第一印象）

**现状**：编辑器和查看器的取景参数不一致
- 编辑器：`×1.55` / corner `[1, 0.62, 1]`（俯角约 24°，偏低偏近）
- 查看器：`lantu/viewer/main.ts:111-124` 另有一套
- 问题：俯角过低容易看到屋面底部（即使已修复檐口，仍不是最佳视角）

**改进方案**：
- 抽公共函数统一取景逻辑
- 略微抬高俯角（建议 30°~35°），让屋面成为视觉主体
- 修改位置：`CanvasViewport.vue:1453-1474` + `lantu/viewer/main.ts:111-124`
- 波及面：A 类

#### 🔴 P2：材质质感提升（占总面积 95.8%）

**现状**：
- 55 个网格（774.75 m²，占总面积 95.8%）走 `surface.default.v1`
- `surface.default.v1` 是纯程序化 UV 图案，无贴图、无法线扰动、无粗糙度变化
- 只有 7 个网格（34.28 m²，占 4.2%）走 `surface.pbr.v1`（主要是玻璃）
- 结果：看起来像"扁平的卡通"而非真实建筑

**改进方案（按工作量递增）**：
1. **快速改善**：给 `surface.default.v1` 补法线/粗糙度扰动
   - 修改：`materialFeatures/defaultSurfaceMaterial.ts`
   - 效果：墙面/屋面有细微凹凸感，不再"死平"
2. **中等改善**：扩大 `surface.pbr.v1` 覆盖面
   - 让墙体/屋面材质支持 PBR 流程（baseColorMap + normalMap + roughnessMap）
   - 修改：`materialAdapter.ts` 中材质映射逻辑
3. **深度改善**：建立材质库 + 预设
   - 为常见材质（砖墙/瓦片/混凝土/木材）提供 PBR 纹理集
   - 位置：前端材质预设 + `wild.world` 材质库

**建议**：先做方案1验证效果，工作量小（1-2天），收益明显

### 6.2 中优先级（优化性能和精度）

#### 🟡 P3：抗锯齿

**现状**：`antialias: false` + 仅 FXAA 后处理
- 屋顶边缘/窗框等锐利几何出现锯齿（尤其在移动时）

**改进方案**：
- 根据 `renderer.capabilities` 给 MSAA（硬件支持时）
- 或换用 SMAA（质量更好的后处理抗锯齿）
- 修改位置：`CanvasViewport.vue:287,320`
- 波及面：A 类

#### 🟡 P4：接触阴影 / SSAO 默认开启

**现状**：只有 medium 画质档开 SSAO，默认档（流畅）无环境光遮蔽
- 结果：墙角/檐口等接触处缺少深度暗示

**改进方案**：
- 默认档开启轻量级 SSAO（或廉价接触阴影）
- 修改位置：`defaultWorldLook.ts:89-95`
- 波及面：A 类

#### 🟡 P5：面剔除优化

**现状**：96% 面 `DoubleSide`（双面渲染）
- 问题：浪费约 50% 光栅化性能（背面也在画）
- 原因：历史保守策略，担心法线翻转

**改进方案**：
- 为已确认水密的几何体开白名单（屋顶/墙体/地板）
- 设置 `side: 'front'` 启用背面剔除
- 修改位置：`materialAdapter.ts:222`
- 波及面：A 类
- **注意**：本次屋顶修复后，gable/hip/flat 已确认水密，可入白名单

### 6.3 低优先级（修复小 bug）

#### ⚪ P6：世界法线着色修正

**现状**（已在 § 二 说明）：
```glsl
'#include <defaultnormal_vertex>\nvWildDefaultWorldNormal = normalize(mat3(modelMatrix) * transformedNormal);'
```
- `<defaultnormal_vertex>` 后 `transformedNormal` 已是视图空间法线
- 再乘 `modelMatrix` 无意义（应该用 `inverseTransformDirection(transformedNormal, viewMatrix)`）
- 漏了 `instanceMatrix`

**影响评估**：
- 只影响天气遮罩（雨丝竖直遮罩、积雪/积尘朝上遮罩）
- 核心光照用 three.js 自带 `normal`，不受影响
- 晴天下几乎无影响

**改进方案**：
- 修正世界法线计算
- 修改位置：`defaultSurfaceMaterial.ts:103`
- 波及面：A 类
- **优先级**：🟡 → ⚪（降级，非关键路径）

#### ⚪ P7：阴影脏标记原子化

**现状**：`autoUpdate = false` + 手动 `needsUpdate` 存在时序风险
- 中间帧消费的竞态条件

**改进方案**：
- 引入原子化的脏标记机制
- 修改位置：`CanvasViewport.vue:1483`
- 波及面：A 类
- **优先级**：⚪（理论问题，实际未遇到）

- 屋面细节：屋脊瓦（`_ridgeTiles`）、檐口线脚（`_eaveProfile`）

- 既有组件完善：烟囱（`chimney` 已存在）、阳台（`balcony` / `bayWindow` 已存在）
- 几何精度：曲面细分段数、UV 连续性

**波及面**：B 类（前端类型添加可选字段，后端不动）

## 九、参数边界总结（给未来开发者的备忘）

| 改动类型 | 波及范围 | 例子 | 何时使用 |
|---|---|---|---|
| **A 类：纯渲染实现** | 仅前端渲染器 | 光照/取景/材质着色/抗锯齿/后处理/面剔除/几何形状 | 90% 的渲染优化 |
| **B 类：渲染私有字段** | 前端类型（可选字段）| `_roofRidge`、`_eaveProfile` | 渲染器需要额外数据，但不想让 LLM 学 |
| **C 类：契约参数** | 知识库 + 提示词 + 后端校验 + 前端类型 + 既有文件迁移 | 新增 `roof.overhang` | 只在需要"让 LLM 能控制一个新旋钮"时 |

**本次屋顶檐口修复**：A 类，用的是既有 `roof.thickness`，知识库早已定义，只是之前几何引擎没读。

**慎重新增 C 类参数的原因**（你已明确的原则）：
1. 影响知识库维护成本
2. 影响大模型输出内容复杂度
3. 影响提示词工程
4. 可能需要迁移既有 `.wild` 文件

**原则**：只有"迫不得已需要对建筑物精细控制"时才上 C 类；优先用 A 类/B 类解决。
