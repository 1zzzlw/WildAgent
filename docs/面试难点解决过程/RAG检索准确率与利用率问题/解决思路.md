# 解决思路：建立可评测的查询增强、索引增强与知识利用闭环

> 实现状态：评测与增强目标方案，尚未完成生产增强和对照验证。最后整理：2026-09-05。  
> 共享契约、成本口径和全局 P0–P4 见[统一实施路线与验收](../统一实施路线与验收.md)。

## 1. 方案结论

“利用 LLM 改写查询”和“利用 LLM 改进索引”是待验证的候选手段，不是必选路线。先恢复可用的检索链并修正阶段上下文；检索请求本身报错时，引入增强不能替代错误定位。

WildAgent 更适合采用以下顺序：

1. 先定位真实请求中的检索异常，再冻结评测集、索引快照和当前主链，得到可信基线；
2. 优先利用 Agent 已有结构化状态和 metadata 做确定性查询规划；
3. 只对模糊、口语化或检索置信度低的查询调用 LLM 改写；
4. 保留原始查询，与改写查询并行召回后融合，避免语义漂移；
5. 只有确定性 metadata 提取仍不能覆盖难例时，才离线使用 LLM 提议索引字段，经 Schema 和来源审核后进入候选索引；
6. 扩大候选集后再重排，最后按节点预算注入上下文；
7. 同时评估检索指标、延迟成本和最终 Blueprint 的知识采用情况。

核心原则是：**先证明问题，再逐项增加复杂度；先利用已有结构化状态，再为真正不确定的部分付出 LLM 成本。**

## 2. 目标架构

```text
用户请求 + Agent 结构化状态
→ QueryPlan（意图、实体、主题、约束、过滤条件）
→ 判断是否需要 LLM 改写
→ 原始查询 + 安全改写查询 + 节点专属查询
→ metadata 过滤下的向量/BM25 候选召回
→ 候选合并、去重和统一重排
→ 节点级上下文选择与预算控制
→ KnowledgeEvidence 写入结构化中间状态
→ LLM / 确定性装配消费证据
→ Blueprint 校验与结果评估
→ Trace、检索指标、采用指标、成本指标
```

## 3. 第一阶段：先建立可信基线

### 3.1 固定实验条件

每次实验必须记录：

- 评测集版本；
- 知识库 commit 或内容签名；
- embedding 模型和版本；
- chunk size、overlap 和 chunker 版本；
- Top-K、候选数量和 metadata filter；
- 查询策略、重排策略和配置；
- 是否使用临时索引。

真实 embedding 实验优先使用临时索引，避免为了调参修改正式 `storage/chroma`。

### 3.2 扩展评测集

在现有60题基础上，为每个重要意图补充以下变体：

| 分组 | 示例目的 |
| --- | --- |
| 标准查询 | 验证基础召回能力 |
| 口语化改写 | 验证自然表达鲁棒性 |
| 中英文混合与别名 | 验证术语映射 |
| 错别字与噪声 | 验证非标准输入处理 |
| 长需求与多约束 | 验证查询分解能力 |
| 近邻实体干扰 | 验证错误硬过滤风险 |
| 无 metadata filter | 模拟真实用户原始输入 |
| 节点结构化状态 | 验证是否仍需要 LLM 改写 |
| 领域外负样本 | 验证拒绝和检索门禁 |

正样本除 `expectedSources` 外，应逐步加入：

- `expectedChunkIds` 或稳定父块标识；
- `requiredTerms`；
- `forbiddenSources`；
- 查询所属 Agent 节点；
- 预期的 `doc_type`、`entity_type`、`topic` 或约束标签。

### 3.3 建立实验矩阵

| 方案 | 查询 | 索引 | 召回/重排 | 目的 |
| --- | --- | --- | --- | --- |
| A：基线 | 原始查询 | 当前索引 | 当前向量召回 | 得到未经增强的基线 |
| B：当前主链 | `SpecQuery` + 确定性过滤 | 当前索引 | 当前规则排序 | 衡量现有代码真实收益 |
| C：查询增强 | 原始查询 + 选择性 LLM 改写 | 当前索引 | 多查询融合 | 单独衡量查询改写收益 |
| D：索引增强 | 与 B 相同 | 增强 metadata/index text | 与 B 相同 | 单独衡量索引增强收益 |
| E：组合候选 | 选择性改写 | 增强索引 | 混合召回 + 二阶段重排 | 单项验证后再测试组合，不作为默认最终架构 |

每次只改变一个主要变量，否则无法归因。C 组应与相同过滤和融合规则的无改写对照比较；混合召回、候选扩展和重排分别消融后再进入 E 组。知识迁移后的索引内容可以变化，但评测集、embedding、预算等控制条件保持一致，并分别记录索引快照。

现有 28 个正样本都预填过滤条件，必须增加无过滤和真实节点状态样例；精细答案优先采用稳定规则/父块标识，避免 chunk 重切后答案 ID 失效。调参集与最终验收集分开，生成实验重复运行并记录样本数与波动。

### 3.4 同时记录三类指标

**检索质量：**

- Hit@K；
- Recall@K；
- MRR；
- Precision@K 或 nDCG；
- 负样本错误接受率；
- metadata filter 导致的零召回率。

**运行成本：**

- 查询规划、改写、召回和重排的 P50/P95 延迟；
- LLM 改写 Token 和单次成本；
- 超时、异常和回退率；
- 查询缓存命中率；
- 最终注入字符数和 Prompt Token。

**知识利用：**

- 命中、注入、模型采用声明与产物验证分别统计，不能合并成一个“已使用”指标；
- 必需约束在 Blueprint 中的兑现率；
- 引用或证据与实际决策的一致性；
- 在同一阶段基础契约下，开启/关闭可选检索的结果差异；
- 最终 Schema、空间和几何校验通过率。

## 4. 第二阶段：实现选择性查询改写

### 4.1 先用已有结构化状态

Agent 节点已经知道当前任务是建筑类型规划、墙体、门窗、屋顶还是装配规则时，应直接形成确定性 `QueryPlan`，不需要让 LLM 再猜一次。

例如门窗节点可直接提供：

```json
{
  "intent": "component_constraints",
  "entity_type": "window",
  "topics": ["parameters", "assembly", "constraints"],
  "constraints": ["host", "opening_fit"],
  "filters": {
    "doc_type": "component",
    "entity_type": "window"
  }
}
```

LLM 只处理结构化状态无法覆盖的部分，例如模糊建筑俗称、长文本中的多重意图、跨语言表达或连续检索低置信度。

### 4.2 QueryPlan 建议字段

```json
{
  "raw_query": "用户原始文本",
  "intent": "knowledge_retrieval",
  "entities": [],
  "topics": [],
  "required_terms": [],
  "optional_terms": [],
  "constraints": [],
  "filters": {},
  "subqueries": [],
  "rewrite_source": "deterministic|llm+deterministic",
  "confidence": 0.0
}
```

其中 `filters` 必须经过服务端白名单和枚举校验。LLM 不应获得生成权限、知识写入权限或任意 Chroma `where` 表达式能力。

### 4.3 不替换原句，使用多查询融合

不要只搜索 LLM 输出的关键词。至少保留：

1. 原始用户查询；
2. 规范术语改写查询；
3. 必要时按独立意图拆出的子查询。

然后在同一 metadata 范围内召回候选并使用 RRF 或统一相关性得分融合。这样即使 LLM 改写发生语义漂移，原始查询仍能提供回退通道。

### 4.4 选择性触发条件

满足任一条件时才考虑调用 LLM：

- 确定性 planner 无法识别实体和主题；
- 首次正常召回为空或经过校准的相关性指标不足；基础设施异常先进入错误处理，不作为改写触发理由；
- 查询包含多个混合意图，需要拆分；
- 查询明显包含跨语言、别名或噪声；
- 当前节点没有足够的结构化任务信息。

其他情况继续使用确定性 QueryPlan，避免每次请求都增加一次模型调用。

### 4.5 运行保护

- 使用小模型或低成本模型；
- 设置严格超时；
- 对规范化后的查询计划做缓存，缓存键包含索引/策略版本和访问范围；
- 失败时回退到原始查询；
- 记录改写前后文本、原因、耗时、Token 和命中差异；
- 低置信度的 LLM 字段只能作为软检索词，不能直接变成硬过滤。

## 5. 第三阶段：离线索引增强

### 5.1 确定性提取优先

WildAgent 知识库本身是结构化 Markdown，标题路径、frontmatter、`rag-meta` 和目录结构已经能提供大量可靠字段。应先确定性提取：

- `doc_type`；
- `entity_name`；
- `entity_type`；
- `topic`；
- `status`；
- `authority`；
- `primary_terms`；
- `synonyms`；
- `constraint_tags`。

只有字段缺失、术语覆盖不足或文档结构复杂时，才让 LLM生成候选值。

### 5.2 LLM 只生成候选，不直接写正式索引

建议输出一个可审计的候选清单：

```json
{
  "entity_name": "window",
  "primary_terms": ["window", "opening", "parentWall"],
  "synonyms": ["窗", "窗户", "外窗"],
  "constraint_tags": ["host", "opening_fit"],
  "index_summary": "窗构件参数、宿主墙引用与洞口适配规则",
  "source_chunk_id": "...",
  "enrichment_model": "...",
  "enrichment_prompt_version": "...",
  "confidence": 0.0
}
```

候选结果必须经过：

1. metadata Schema 校验；
2. 枚举和术语白名单校验；
3. 与原文的可追踪性检查；
4. 重复和冲突检查；
5. 人工审核或高置信度审批规则；
6. 临时索引 A/B 评测。

### 5.3 区分检索文本与注入正文

可以为每个 chunk 保存两类内容：

- **原始正文**：最终注入 Prompt 的事实内容；
- **index_text**：标题路径、标准术语、同义词、约束标签和简短索引摘要，用于 embedding 或 BM25。

检索命中后仍返回原始正文，避免 LLM 生成的索引摘要覆盖或歪曲真实 Blueprint 规则。

### 5.4 增量更新与可复现性

索引增强结果至少记录：

- 原始内容哈希；
- metadata 版本；
- enrichment Prompt 版本；
- 模型名称；
- 生成时间；
- 审核状态。

只有原文、Schema 或增强版本变化时才重新处理，降低大规模索引构建成本。

## 6. 第四阶段：扩大候选后统一重排

当前规则重排只能调整已选结果顺序。建议改为：

```text
多查询分别召回较大的候选集
→ 统一 metadata 安全过滤
→ 按 parent/body hash 去重
→ 向量与 BM25 排名融合
→ 对 Top-N 候选做相关性重排
→ 多样性与来源覆盖控制
→ 截取最终 Top-K
```

重排可以分级：

1. 先使用低成本规则或轻量 Cross-Encoder；
2. 只有难例再使用 LLM reranker；
3. LLM reranker 只看少量候选，并输出可校验的 chunk 排名；
4. authority 和 status 作为可信度约束，不应无条件压过相关性。

如果启用 BM25，需要先解决当前原型的数据接口、metadata filter 和中文分词问题，再用评测判断它是否真的优于纯向量召回。

## 7. 第五阶段：让知识进入结构化执行状态

只把 RAG 文本拼进 Prompt，无法可靠证明知识被使用。复用统一 RequirementSpec 和决策/验收记录，以关联记录表达 `KnowledgeEvidence`，不另建独立状态机：

```json
{
  "decision_id": "roof_support_rule",
  "claim": "屋顶覆盖范围必须覆盖支承墙外包围盒",
  "chunk_ids": ["chunk_xxx"],
  "applied_to": ["main_roof", "upper_wall_group"],
  "status": "planned|applied|validated|rejected"
}
```

后续规划、装配和校验节点都消费同一份证据状态，并记录：

- 哪条知识支持哪个设计决策；
- 该决策是否进入 Blueprint；
- 校验是否证明它被正确执行；
- 如果未采用，原因是冲突、能力不支持还是上下文预算不足。

这些记录可以追踪规则声明与产物兑现，但不能独立证明因果贡献：模型可能引用了未真正使用的片段，也可能在无检索时满足同一规则。需要同条件开关或内容消融实验才能判断检索增量收益；UI 对注入阶段使用“已注入知识片段”，不直接显示“已采用”。

确定性 assembler 消费已批准设计与固定规则，不在装配时重新检索或相信模型自由文本声明的规则。

## 9. 验收标准

不要预先承诺一个脱离基线的绝对数字。建议先跑 A 方案确定基线，再设置以下相对门禁：

- 全部方案使用相同评测集与真实 embedding；查询/重排实验固定索引快照，索引增强实验只改变声明的索引因素；
- 正样本 Hit@K、Recall@K 和 MRR 不低于基线；
- 口语化、别名、噪声和长查询分组得到可重复的明显提升；
- 领域外负样本错误接受率不高于基线；
- metadata 硬过滤造成的零召回率下降；
- LLM 改写失败时能够无损回退到原始查询；
- P95 延迟和单请求成本不超过产品预算；
- 注入上下文字符数或 Token 不因候选扩大而失控；
- 候选检索配置应在质量不回退的前提下带来可重复的质量或成本收益；相同基础契约下若关闭可选检索已同样有效，可以保留更简单配置；
- 同一配置连续运行得到稳定结果，并能通过 Trace 解释差异来源。

可以把“难例 Recall@5 至少提升10个百分点且整体指标不回退”作为第一轮候选目标，但最终阈值应以真实基线和业务容忍度校准。

## 10. 对齐统一实施阶段

按[统一路线](../统一实施路线与验收.md)开展以下工作包，不预设所有增强都要上线：

| 全局阶段 | RAG 专项任务 |
| --- | --- |
| P0 | 定位检索错误；补真实无过滤/节点查询；真实 embedding 与临时索引基线；错误、召回和注入可观测 |
| P1 | 配合平面专用契约，校准阶段上下文和内容预算；先利用已有结构化状态 |
| P2–P3 | 在平面求解及编辑实验中记录知识声明、需求与产物验收关系；保持检索配置稳定便于归因 |
| P4 | 根据难例分布选择候选扩展/重排、选择性改写、索引增强或混合召回，逐项对照后再组合 |

单项低风险修正可以依据基线提前试验，但不让 LLM 改写、索引增强和混合检索阻塞近期平面闭环。正式索引评测默认只读；候选重建使用临时索引，验证后再发布。

## 11. 面试中的解决方案表达

> 我审计后发现，查询改写和混合检索原型没有进入生产主链，现有评测也不足以证明真实召回与利用效果。因此我提出先定位检索异常、冻结真实 embedding 基线，并把查询规划、召回、重排、注入和产物兑现分开评估。后续优先利用节点已有结构化状态，只对证据支持的难例试验选择性改写或离线索引增强。增强是否上线由相同条件下的质量与成本收益决定；目前完成的是审计和方案设计，不能宣称已经提升 Recall 或 Blueprint 质量。
