# 当前遇到的问题：RAG 检索准确率、知识利用率与评测闭环不足

> 本文记录原审计与当前源码边界；实施优先级见[统一实施路线与验收](../统一实施路线与验收.md)。最后补充整理：2026-09-05。

## 1. 问题结论

WildAgent 并不是完全没有做 RAG 优化。当前项目已经具备语义分片、Chroma 向量召回、节点级 metadata 过滤、确定性查询规划、候选去重、规则重排、Trace 和检索评测脚本。

核心问题是：**缺少可用检索、阶段上下文、检索质量和产物效果之间的可信验证闭环。** 查询增强和索引增强只是候选优化手段，并非必需能力。

另一个已观察问题是：2026-09-03 的生成 Trace 记录 `BadRequestError`，但 Loader 降级为基础规范后节点仍可能显示无 `rag_error`。这个现象应先定位实际请求错误并分层暴露；不能将异常零召回归因于查询语义差，或用 LLM 改写替代基础检索修复。

项目中虽然存在 LLM 查询改写和 BM25 混合检索的独立实现，但它们没有接入当前 `RAGSpecLoader` 主链；索引阶段也没有发现使用 LLM 自动提取结构化字段的正式流程。与此同时，现有评测没有对“原始查询、当前确定性规划、LLM 改写、索引增强”等方案做同一数据集上的对照实验，因此暂时无法证明任何增强方案提升了检索质量。

此外，“检索准确率”和“知识利用率”是两个不同问题：

- **检索准确率**：需要的知识是否出现在 Top-K，以及排序是否足够靠前；
- **知识利用率**：召回并注入 Prompt 的知识是否真正影响了 Agent 的设计决策和最终 Blueprint。

当前项目对第一项已经有部分基础设施，对第二项仍缺少直接的量化证据。

## 2. Agent 领域分类

- **一级领域**：Knowledge & RAG
- **二级领域**：Query Transformation、Indexing、Retrieval & Reranking、Context Engineering、Evaluation & Observability、Performance & Cost
- **问题类型**：Retrieval Quality and Knowledge Utilization Gap
- **关键术语**：Query Rewriting、Index Enrichment、Hybrid Retrieval、Reranking、Hit@K、Recall@K、MRR、Context Utilization、Groundedness、A/B Evaluation
- **当前状态**：已定位并形成解决思路，尚未完成生产接入和对照验证

## 3. 当前真实 RAG 链路

当前主链可以概括为：

```text
用户请求 / Agent 节点状态
→ 节点手工构造 SpecQuery 与 metadata_filter
→ query_planner 根据索引 metadata 识别别名并补全粗粒度过滤
→ Chroma 向量召回候选
→ 按语义距离、status、authority 调整候选优先级
→ 内容哈希去重
→ 对已经截断的结果做规则重排
→ 补充同一父块的相邻分片
→ 按字符预算注入 Prompt
→ LLM 生成设计状态或 Blueprint
```

主要代码位置：

- [`loader.py`](../../../wild-server/app/spec/loader.py)：分片、索引、向量召回、去重、重排和上下文拼接；
- [`query_planner.py`](../../../wild-server/app/spec/query_planner.py)：别名目录、确定性查询计划和 LLM 候选改写接口；
- [`agent_service.py`](../../../wild-server/app/services/agent_service.py)：RAG Loader 创建、查询过滤和 Prompt 注入；
- [`app/agent/nodes`](../../../wild-server/app/agent/nodes/)：各设计节点构造自己的检索查询；
- [`rag_trace.py`](../../../wild-server/app/agent/rag_trace.py)：记录查询、命中、上下文、耗时和 Token；
- [`eval_retrieval.py`](../../../wild-server/scripts/rag/eval_retrieval.py)：检索评测与报告生成。

## 4. 当前已经实现的能力

| 能力 | 当前实现 | 实际边界 |
| --- | --- | --- |
| 语义分片 | Markdown 标题、实体 metadata、代码块和表格保护 | 能改善索引单元质量，但不能自动保证语义相关性 |
| 向量检索 | `RAGSpecLoader` 使用 Chroma 与配置的 embedding | 质量取决于真实 embedding、知识内容和查询表达 |
| 节点检索路由 | 多个节点使用 `SpecQuery` 指定 `doc_type`、`entity_type` | 过滤条件和查询扩展大量由代码手工维护 |
| 确定性查询规划 | 从 `primary_terms`、`synonyms` 等 metadata 建立别名目录 | 当前生产检索仍保留原始查询文本，主要收益是补全过滤条件 |
| 候选治理 | 多取候选、内容去重、status/authority 优先级、相邻分片补全 | 当前规则重排发生在每个查询结果截断之后，不能找回未进入候选集的正确片段 |
| 检索 Trace | 记录 query、filter、命中 chunk、距离、耗时和上下文字符数 | 能证明“召回和注入”，不能独立证明“模型采用” |
| 离线评测 | 支持 `expectedSources`、`requiredTerms`、Hit@K、Recall@K、MRR | 尚未支持多方案 A/B 对照和端到端知识采用评估 |

## 5. 对原有两个解决方向的核查

### 5.1 利用 LLM 改写用户查询

项目中已经存在 [`query_rewriter.py`](../../../wild-server/app/agent/rag/query_rewriter.py)，能够让 LLM 输出：

- `entity_type`；
- `attributes`；
- `features`；
- `constraints`；
- `keywords`。

同时存在 `EnhancedRAGRetriever`，它会把关键词拼成新的检索文本，并尝试把 `entity_type` 加入 metadata 过滤。

但全项目调用关系显示，这些类只在模块导出、示例和测试中使用，没有接入 `AgentService → RAGSpecLoader` 的生产路径。当前 Loader 使用的是 [`query_planner.py`](../../../wild-server/app/spec/query_planner.py) 中的确定性规划；其中 `apply_llm_rewrite()` 也只有测试覆盖，没有生产调用。

因此，准确结论是：

> LLM 查询改写已经有原型代码，但尚未完成生产集成，更没有通过对照实验证明收益。

现有原型还存在以下风险：

1. LLM 输出没有经过完整的字段白名单、枚举和置信度校验；
2. 直接使用模型生成的 `entity_type` 做硬过滤，判断错误时会造成零召回或漏召回；
3. 改写后只搜索关键词拼接文本，没有同时保留原始查询作为独立召回通道；
4. 没有记录改写耗时、Token、失败率和改写前后命中差异；
5. 每次请求都改写会放大高并发下的延迟和费用。

### 5.2 利用 LLM 改进索引

当前 Loader 已经能够把文档中的 `entity_name`、`doc_type`、`entity_type`、`topic`、`primary_terms`、`synonyms` 和 `constraint_tags` 等 metadata 写入索引，也支持按内容哈希增量同步。

但这些字段主要来自人工维护的 Markdown frontmatter、`rag-meta` 和路径配置。当前代码中没有发现一个正式的离线流程，使用 LLM 从知识正文中自动提取、校验并落盘这些字段。

因此，准确结论是：

> 当前具备“结构化索引字段的承载能力”，但尚未具备“LLM 索引增强流水线”。

直接让 LLM 自动生成索引字段还会引入：

- 字段幻觉和错误分类；
- 同一文档多次处理结果不一致；
- 模型或 Prompt 升级后索引不可复现；
- 自动摘要丢失 Blueprint 约束；
- 索引字段与原文事实无法追踪；
- 知识更新后增量重建和版本管理困难。

## 6. 当前项目仍然存在的核心问题

### 6.1 缺少冻结基线和同条件 A/B 对照

现有评测脚本能评估一次检索结果，但没有把以下方案作为可切换的实验变量：

1. 原始查询 + 向量召回；
2. 当前 `SpecQuery` + 确定性过滤；
3. 原始查询 + LLM 改写的多查询召回；
4. 增强 metadata 或索引文本后的召回；
5. 混合检索与更强重排。

没有统一数据、统一 embedding、统一索引快照和统一 Top-K 的对比，就无法把指标变化归因到某一项优化。

### 6.2 历史报告不能证明当前真实语义检索质量

仓库中现有的 [`eval_retrieval_20260824_195838.md`](../../../wild-server/scripts/reports/eval_retrieval_20260824_195838.md) 使用 `HashEmbeddingFunction`，只执行了5个问题。报告虽然得到 `Hit@5=100%`、`Recall@5=100%`、`MRR@5=1.0`，但脚本本身已经明确说明 Hash embedding 只能用于流程 Smoke Test，不能代表生产语义召回质量。

当前 [`rag_retrieval_cases.json`](../../../wild-server/evals/rag_retrieval_cases.json) 已扩展为60题，其中28个正样本、32个负样本，但仓库中没有发现使用当前完整评测集和真实 embedding 生成的最新对照报告。

### 6.3 评测样本仍不足以验证查询改写

当前正样本大多是“一个主题对应一条标准查询”，并且28个正样本全部携带预先写好的 metadata filter。这更接近验证“已知路由下能否找到文件”，不能充分检验 LLM 查询改写是否有价值。

还缺少：

- 同一意图的口语化、缩写、错别字和中英文混合改写；
- 长需求中夹杂多个建筑约束的复杂查询；
- 无 metadata filter 的真实用户原始输入；
- 容易混淆的近邻实体与错误硬过滤样本；
- 节点状态已经结构化和完全非结构化输入之间的分组对比；
- 以 `expectedChunkIds` 或具体规则为答案的细粒度评测。

### 6.4 查询规划存在“有计划但未完全用于召回”的情况

`build_query_plan()` 能生成 `rewritten_query`、aliases、topics 和 constraints，但当前 `RAGSpecLoader.retrieve()` 与 `retrieve_many()` 仍然把原始文本传给 Chroma，只采纳部分粗粒度过滤补全。

这使查询计划中的同义词、主题和约束没有完整参与向量召回。另一方面，如果未来直接把全部别名拼入查询，又可能稀释原始语义。因此需要通过多查询融合验证，而不是简单替换原句。

### 6.5 重排只能改善顺序，不能弥补召回缺失

当前规则重排以 authority、词语重叠和距离为依据，但它作用于已经选出的少量结果。正确片段如果没有进入初始候选集，后续重排无法找回。

真正的两阶段检索应先扩大候选集合，再使用统一的相关性评分重排，最后截取 Top-K。

### 6.6 BM25 混合检索仍是未接入原型

[`hybrid_retriever.py`](../../../wild-server/app/agent/rag/hybrid_retriever.py) 没有接入 `RAGSpecLoader`。其当前实现使用另一套 LangChain 文档接口，metadata filter 在向量分支中只写入了局部 `search_kwargs`，并没有传给实际调用；BM25 分支也没有执行等价过滤。

因此不能直接把该模块打开作为生产方案，需要先统一数据模型、过滤语义、中文分词和融合策略，再进行对照实验。

### 6.7 召回命中不等于知识被 Agent 使用

当前 Trace 可以记录注入了哪些 `chunk_id`，引用校验也能限制伪造引用，但 Blueprint 生成链路没有稳定记录：

- 哪个设计决策使用了哪个知识片段；
- 召回规则是否进入结构化中间状态；
- 知识约束是否在最终 Blueprint 中兑现；
- 关闭 RAG 后结果是否真的变差。

因此“RAG 利用率”目前不能只用上下文字符数、命中数或引用数量衡量。

### 6.8 性能与成本缺少独立预算

引入 LLM 查询改写后会增加一次模型调用。如果再加入多查询、混合召回或 LLM 重排，还会继续增加延迟与 Token。当前没有针对查询增强记录独立的：

- P50/P95 改写延迟；
- 改写 Token 与成本；
- 超时、失败和回退比例；
- 缓存命中率；
- 单次增强带来的 Recall/MRR 增益。

没有这些指标，就无法判断推理成本是否换来了足够收益。

## 8. 面试中的问题描述

> 我发现项目虽然已经有 LLM 查询改写、混合检索和结构化 metadata 的原型，但生产主链实际仍以节点手工查询、确定性过滤和向量召回为主。更关键的是，项目没有在同一评测集上比较原始查询、查询改写和索引增强，也没有区分“召回到知识”和“最终采用知识”。所以我把问题归类为 RAG 检索质量与知识利用率闭环不足，计划先建立可复现的基线和端到端指标，再决定哪些查询值得调用 LLM、哪些索引字段适合离线增强。
