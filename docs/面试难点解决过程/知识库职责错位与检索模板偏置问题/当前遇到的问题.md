# 当前遇到的问题：知识库职责错位与检索模板偏置

> 实现状态：问题来自当前工作树只读审计，尚未完成知识库重构与效果验证。
>
> 最后核对：2026-09-05。

全局阶段与证据口径见[统一实施路线与验收](../统一实施路线与验收.md)。

## 1. 问题结论

WildAgent 当前知识库同时保存两类性质不同的内容：

1. 通用建筑类型、组件百科、固定尺寸和建筑构成配方；
2. `.wild` Blueprint 契约、空间关系、组件宿主、坐标语义、引擎能力边界和几何约束。

第一类与基础模型的通用知识可能重叠，第二类包含模型无法自行得知的 WildAgent 项目事实。源码确认两类知识具有进入同一生成上下文的路径，因此存在固定配方锚定、参考值被硬化和上下文竞争风险；实际注入比例及对模板化的因果贡献仍待 Trace 与对照实验验证。

2026-09-03 已审计请求的 RAG 实际报错且零命中，不能将该次坏结果归因于召回了建筑模板。判断知识是否保留，应看阶段必要性、可靠来源和增量收益，不能只依据“模型可能已经知道”。

因此，这不是单纯的“知识库内容质量不好”，而是知识库职责、检索路由和上下文工程共同发生了错位。

## 2. Agent 领域分类

- **一级领域**：Knowledge & RAG
- **二级领域**：Knowledge Governance、Retrieval Routing、Context Engineering、Retrieval-Induced Bias、Evaluation & Observability
- **问题类型**：Knowledge–Task Misalignment and Retrieval-Induced Template Bias

## 3. 问题背景

最初引入建筑类型和组件知识，是希望通过 RAG 补充模型的建筑知识，让模型在生成别墅、办公、商业、教育、医疗和交通建筑时拥有更具体的参考。

随着知识不断增加，知识库开始同时承担两个职责：

- 告诉模型“某种建筑通常由什么组成”；
- 告诉模型“如何使用当前 WildAgent 能力正确表达和验证 Blueprint”。

模型对前者通常已有较强基础，但无法自行知道后者。如果二者以相似权重进入生成上下文，领域参考就可能被误解为默认配方或隐性硬约束。

## 4. 当前知识库规模

知识库位于 [`wild-server/storage/knowledge_base`](../../../wild-server/storage/knowledge_base/)。

本次只读统计结果：

| 类别 | Markdown 文件数 | 大小 | 行数 | 主要内容占比 |
| --- | ---: | ---: | ---: | ---: |
| `building_types` | 16 | 约 242 KB | 4753 | 约 54% |
| `components` | 15 | 约 112 KB | 2786 | 约 25% |
| `recipes` | 9 | 约 45 KB | 1023 | 约 10% |
| Blueprint 规范 | 2 | 约 45 KB | 1122 | 约 10% |
| `patterns` | 2 | 约 5 KB | 120 | 约 1% |

`building_types + components` 占主要 Markdown 内容约 79%。

其中当时的 [`public-building-subtypes.md`](../../../docs-dev/retired-knowledge/building_types-rules-v2/public/public-building-subtypes.md) 单文件约 119 KB、2481 行，包含 38 类公共建筑的：

- 默认完整构成；
- `required/characteristic/conditional/optional` 组件；
- 固定尺寸和柱网参考；
- 关键组装关系；
- 最少可行 fallback。

这些内容包含成套参考配方，具备锚定设计的风险；文档体积和占比本身不能证明生产注入比例或效果。

## 5. 当前真实 RAG 链路

```text
Markdown
→ MarkdownChunker
→ Chroma / Embedding
→ retrieve / retrieve_many
→ 拼接 BLUEPRINT-SPEC-MINIMAL
→ 节点 Prompt
→ 模型输出
```

主要入口：

- [`agent_service.py`](../../../wild-server/app/services/agent_service.py)：知识库扫描和 Loader 初始化；
- [`loader.py`](../../../wild-server/app/spec/loader.py)：Markdown 分片、索引、过滤、召回和上下文拼接；
- [`prompts.py`](../../../wild-server/app/agent/prompts.py)：将上下文注入节点 Prompt。

[`BLUEPRINT-SPEC-MINIMAL.md`](../../../wild-server/storage/knowledge_base/BLUEPRINT-SPEC-MINIMAL.md) 始终完整注入，其他 Markdown 通过 RAG 按需召回。Loader 默认上下文上限为 18000 字符。

## 6. 建筑构成知识怎样进入设计节点

### 6.1 总体建筑方案

[`architecture_node.py`](../../../wild-server/app/agent/nodes/architecture_node.py) 会同时检索：

- `building_type`；
- `recipe`；
- `pattern`。

固定构成、尺寸和配方有进入体量、屋顶、立面轴网和细部设计上下文的路径；是否命中并产生实际影响需逐次追踪。

### 6.2 平面空间分析

[`floor_space_analysis_node.py`](../../../wild-server/app/agent/nodes/floor_space_analysis_node.py) 会检索：

- 建筑类型；
- 平面功能分区；
- 空间清单和面积；
- 邻接、门窗、流线和楼梯配方。

召回内容还会写入 `floor_plan_rag_context`，继续被以下节点复用：

- [`floor_layout_node.py`](../../../wild-server/app/agent/nodes/floor_layout_node.py)；
- [`floor_openings_node.py`](../../../wild-server/app/agent/nodes/floor_openings_node.py)。

因此，一份建筑模板可能连续影响：

```text
总体体量
→ 空间清单
→ 平面布局
→ 墙、门窗和交通
```

### 6.3 执行计划

[`execution_plan_node.py`](../../../wild-server/app/agent/nodes/execution_plan_node.py) 在计划研究阶段也会检索 `building_type` 和 `recipe`，模板偏置可能在真正设计开始前就进入执行计划和阶段指导。

## 7. Metadata 没有完全隔离领域参考

大量建筑构成文档标记为：

```yaml
status: experimental
authority: domain_reference
```

但当前 [`loader.py`](../../../wild-server/app/spec/loader.py) 的生成过滤主要排除：

- `status: proposed`；
- `authority: inferred`；
- `doc_scope: index`。

`experimental/domain_reference` 仍可进入正式生成召回，只在排序时受到较小惩罚。

模型实际获得完整文本后，不一定稳定地区分：

- 必须遵守的 Blueprint 契约；
- 仅供参考的建筑惯例；
- 可自由变化的设计示例；
- 只应在失败阶段使用的 fallback。

## 8. 当前主要问题

### 8.1 知识库职责错位

知识库主体正在从“项目专属执行知识”变成“建筑百科和构件目录”。通用内容与大模型已有知识高度重叠，而项目真正稀缺的 Blueprint 设计知识占比相对不足。

### 8.2 固定组件构成存在模板偏置风险

旧版 `component-building-matrix.md` 使用强弱矩阵描述不同建筑应该使用哪些组件。它现已由通用的 [`component-selection-relations.md`](../../../wild-server/storage/knowledge_base/recipes/component-selection-relations.md) 取代。旧矩阵召回后，模型容易把“常见构成”理解成“推荐配方”甚至“必须构成”，造成：

- 不同输入选择相似组件；
- 建筑体量和空间方案趋同；
- 组件数量和类型被提前锁定；
- 模型更倾向复述模板，而不是根据用户需求重新设计。

### 8.3 固定尺寸伪装成设计约束

建筑文档中存在柱网、墙厚、层高、门窗尺寸、跨度和搭接数值。即使正文标记为领域参考，模型仍可能直接采用这些数字，导致：

- 用户没有要求的尺寸被自动固定；
- 不同规模建筑共享同一参数；
- 参考值与当前引擎能力或实际几何冲突；
- 数值看起来专业，但没有经过专业校核。

### 8.4 fallback 与正常设计知识混在同一检索空间

最少可行 fallback 本应只在模型失败、低复杂度或性能受限时使用。它与正常设计知识一起召回时，模型可能主动选择更简单、更安全的表达，使普通或精密模式也退化成相似盒子。

### 8.5 检索粒度过粗

当前节点常按 `doc_type=building_type/recipe/component` 检索，只能区分文档类别，不能准确区分：

- 总体设计策略；
- 空间拓扑规则；
- Blueprint 字段契约；
- 组装关系；
- 校验与修复规则；
- 通用领域参考；
- fallback。

因此容易召回“主题相关但执行职责不匹配”的内容。

### 8.6 上下文竞争

建筑类型和组件文档体积较大时，会挤占真正需要的内容：

- 坐标与宿主关系；
- 屋顶覆盖规则；
- 楼层连续性；
- 洞口局部坐标；
- 当前支持的类型和枚举；
- 已知错误和修复条件。

## 9. 哪些内容没有必要默认注入

- 住宅、办公楼、学校通常包含哪些通用构件；
- 大量建筑子类型百科；
- 固定建筑—组件强弱矩阵；
- 通用门窗和风格历史介绍；
- 未经当前引擎验证的工程尺寸；
- 每种建筑的完整固定组件配方；
- 默认柱网、层高、墙厚和门窗尺寸；
- 将 characteristic 组件写成每次必用组件的规则；
- 与 Blueprint 表达无关的建筑领域描述。

这些内容可以保留为可选领域参考，但不应默认进入生成 Prompt。

## 10. 哪些组件知识必须保留

不能简单删除所有组件文档。大模型通常知道“建筑有门窗和楼梯”，但不知道 WildAgent 当前版本的项目事实：

- `door/window` 应写入 `geometry.components`；
- `parentWall` 如何引用；
- `opening.from[0]` 是沿墙路径距离，而不是世界坐标；
- 当前支持哪些 `roofType`；
- 幕墙不是原生 `curtain_wall` 类型；
- 幕墙怎样降级为 `wall + window`；
- `wild-compiler` 如何编译组合组件；
- `wild-core` 如何解释局部坐标和父子关系；
- 哪些搭接是允许接触，哪些属于碰撞；
- 哪些字段会导致重建失败。

这类项目专属事实不仅要保留，还应成为未来知识库的主体。

## 11. 当前审计状态与证据边界

原审计记录运行知识库 linter 后得到以下结果；本轮文档修订未重新运行，不能视为当前重新验证：

- 扫描 45 个文件；
- 当前规则报告 41 个 error、88 个 warning；
- 很多 error 是“建筑实体缺少默认完整构成合同”。

这说明现有维护规则仍将详细建筑组件构成视为知识库核心。如果转向 Blueprint 设计知识，还要同步修改知识分类规则、ingest 约定、linter、metadata 过滤、Agent 查询策略和评测集，否则会出现一边精简构成知识、另一边检查工具又要求补回的冲突。

真实分片预览在原审计轮次被宿主机 `OSError: [WinError 10106]` 阻断，因此完整知识库的实际 chunk 数量尚未重新验证。该错误属于宿主机 Python/asyncio 环境问题，不能作为知识库业务测试结论。

还需要注意：目前已经确认模板知识具备进入设计节点的路径，但尚未通过受控对照实验量化它对结果趋同的实际贡献，不能把所有相似结果都归因于知识库。

## 12. 面试表达

> 我遇到的是 Agent 的知识治理与上下文工程问题。知识库包含与基础模型知识可能重叠的领域参考，但各阶段所需的项目契约、空间语义和能力边界没有得到充分隔离和匹配。这些内容存在进入多个节点的路径，可能稀释上下文或形成固定配方偏置，但需要逐次追踪和实验验证。我通过源码和知识内容审计确认了它们进入生产 Prompt 的路径，并提出将知识库职责划分为项目专属事实、可执行规则、领域参考和已验证经验。目前完成了问题定位与方案设计，模板偏置的实际影响仍需通过对照实验验证。
