# 解决思路：将知识库重构为 Blueprint 可执行设计知识库

> 实现状态：知识治理目标方案，尚未完成重构与量化验收。最后整理：2026-09-05。  
> 本文工作包遵循[统一实施路线与验收](../统一实施路线与验收.md)，不单独安排一套全局阶段。

## 1. 方案结论

WildAgent 不应继续把知识库建设成建筑百科，而应优先保存基础模型无法自行知道的项目事实：

- 设计意图怎样映射为 `.wild`；
- 当前引擎支持和不支持什么；
- 不支持的业务对象怎样降级；
- 构件怎样依附、对齐和组装；
- 哪些空间和几何关系必须满足；
- 哪些错误可以确定性修复；
- 什么条件下必须阻止交付。

通用建筑知识按阶段需要检索：空间功能、容量和邻接参考可能对 Program/Topology 有增益；固定整栋配方、无关百科和 fallback 不应无差别注入普通生成。是否退出某阶段由对照实验决定，不能按目录整批排除。

## 2. 重构原则

判断一条知识是否应进入当前节点，依次检查：

1. 当前节点是否需要这项信息才能完成任务？
2. 它是否来自可靠且适用的项目或领域来源？
3. 它属于硬规则、软建议、示例还是 fallback？
4. 在相同需求和模型配置下，加入它是否改善约束、质量或成本？

项目独有知识应优先保障，但“模型可能已经知道”不是排除通用知识的充分条件。

同时遵守以下原则：

1. 先建立基线和对照实验，再移动或归档内容；
2. 按知识声明的职责治理，不按目录整批删除；
3. 系统硬约束、领域建议、示例和 fallback 必须显式区分；
4. 默认检索围绕当前节点任务，而不是只按文档大类；
5. 知识采用效果必须落实到结构化状态和最终 Blueprint；
6. Schema、compiler、core 和真实重建结果优先于未经验证的说明；
7. 不为每种建筑维护独立的校验和修复逻辑。

## 3. 目标知识分层

### 3.1 系统铁律层

对需要生成 Blueprint 字段的模型阶段注入，并保持小而稳定；空间规划阶段使用 FloorPlanIR 专用契约，确定性 assembler 不必接收模型上下文：

- `.wild` 顶层结构；
- element/component 类型边界；
- 坐标系和局部坐标；
- 引用关系；
- 材质基本规则；
- 不允许发明的字段和枚举。

当前 [`BLUEPRINT-SPEC-MINIMAL.md`](../../../wild-server/storage/knowledge_base/BLUEPRINT-SPEC-MINIMAL.md) 应进一步精简为这一层，而不是承担所有阶段的通用说明书。

### 3.2 Blueprint 设计层

这是未来默认 RAG 的主体：

- 体量怎样表达为 floor/wall/roof；
- L、U、庭院、退台怎样形成闭合轮廓；
- 空间邻接怎样转换为内墙和门；
- 门窗如何映射到合法宿主槽位；
- 屋顶如何覆盖多体量和退台；
- 楼梯如何连接楼层和楼板洞口；
- 阳台、雨棚和栏杆如何依附宿主；
- 幕墙、天窗等业务概念如何降级；
- 生成顺序与跨构件依赖；
- Blueprint 设计不变量。

它回答的不是“办公楼通常有什么”，而是：

> 当设计意图包含中庭、退台、幕墙或坡屋顶时，如何用当前 `.wild` 能力正确表达？

### 3.3 领域参考层

保存通用建筑类型、空间经验和领域参数，按当前阶段和来源选择；领域参考不能自动升级成硬约束：

- 用户明确查询建筑知识时使用；
- 用户明确要求参考某个建筑原型时使用；
- 专业类型需要补充领域背景时使用；
- 知识覆盖不足时按需使用；
- 未来接入权威规范或用户私有资料时使用。

### 3.4 项目模式层

保存经过项目验证的经验：

- 用户确认过的偏好；
- 通过 `.wild` 校验和真实重建的案例；
- 可复用但不能普遍化的项目模式；
- 已知失败案例和通用修复规则。

## 4. 内容迁移策略

| 当前内容 | 处理方式 |
| --- | --- |
| WILD Schema、字段、枚举、坐标 | 保留并提高优先级 |
| `parentWall`、局部坐标、宿主关系 | 保留 |
| 屋顶覆盖、楼层连续、楼梯连接 | 保留并补充 |
| 非原生业务对象的降级映射 | 保留 |
| compiler/core 能力边界 | 保留 |
| 校验器错误和确定性修复规则 | 保留并结构化 |
| 已验证 `.wild` 示例 | 保留 |
| 通用建筑组件构成 | 按声明拆分；功能需求参考可进入 Program，固定整栋配方退出无差别注入 |
| 38 类公共建筑固定构成合同 | 保留来源与适用关系，压缩重复配方；功能知识和项目映射分别评测 |
| 固定柱网、墙厚、门宽 | 移入领域参考 |
| 构件—建筑类型强弱矩阵 | 退出默认生成 |
| 门窗百科和传统形式长篇介绍 | 移入领域参考 |
| 最少可行组件组合 | 只允许 fallback 阶段读取 |
| 用户确认且重建通过的模式 | 保留在项目模式层 |

迁移时要拆开通用知识和项目事实。例如：

```text
“办公楼通常有核心筒、幕墙和雨棚”
→ 通用领域参考，退出默认生成

“幕墙在当前 WILD 中使用 wall + window，window 引用 parentWall”
→ 项目专属 Blueprint 设计知识，保留并提高优先级
```

## 5. Metadata 重构

复用或扩展现有 metadata，明确三个维度。

### 5.1 知识职责

```yaml
knowledge_layer:
  - wild_schema
  - blueprint_design
  - domain_reference
  - project_pattern
```

### 5.2 生成阶段

```yaml
generation_stage:
  - request
  - architecture
  - spatial
  - assembly
  - validation
  - repair
  - reconstruction
```

### 5.3 约束强度

```yaml
constraint_mode:
  - hard
  - guidance
  - example
  - fallback
```

Loader 和 Prompt 必须明确区分：

- 必须执行的项目规则；
- 只供设计参考的建议；
- 不应复制的示例；
- 只在失败阶段使用的回退。

## 6. 按生成阶段检索

节点不再主要按 `doc_type` 粗粒度检索，而是按知识职责、生成阶段和约束强度检索。

| 阶段 | 应检索内容 | 不应默认检索 |
| --- | --- | --- |
| Architecture | 体量表达、楼层连续、屋顶策略、能力边界 | 完整建筑组件模板 |
| Floor space | 建筑用途、容量、空间需求、核心预留和功能约束 | 无关门窗百科和固定整栋尺寸配方 |
| Floor layout | 轮廓覆盖、分区、挖空、跨层对齐 | 建筑类型完整构成 |
| Floor openings | 宿主、局部坐标、连通性、采光和碰撞 | 通用门窗风格历史 |
| Assembler | 不使用 RAG，直接消费已批准设计 | 所有领域参考 |
| Validation | 使用确定性校验器 | 通用建筑知识 |
| Callback repair | 按错误代码检索有限修复规则 | 建筑类型配方 |
| Chat | 根据用户问题按需读取领域参考 | 无关生成规则 |

主要改造位置：

- [`architecture_node.py`](../../../wild-server/app/agent/nodes/architecture_node.py)；
- [`floor_space_analysis_node.py`](../../../wild-server/app/agent/nodes/floor_space_analysis_node.py)；
- [`floor_layout_node.py`](../../../wild-server/app/agent/nodes/floor_layout_node.py)；
- [`floor_openings_node.py`](../../../wild-server/app/agent/nodes/floor_openings_node.py)；
- [`execution_plan_node.py`](../../../wild-server/app/agent/nodes/execution_plan_node.py)；
- [`callback_node.py`](../../../wild-server/app/agent/nodes/callback_node.py)；
- [`loader.py`](../../../wild-server/app/spec/loader.py)。

## 7. 实施顺序

全局依赖见[统一路线](../统一实施路线与验收.md)：基线属于 P0，阶段基础契约属于 P1，较大规模知识迁移和增强属于 P4。以下是按需展开的知识治理工作包。

### 工作包 A：建立只读基线

不改生产知识库，先记录：

- 每个节点召回的文件和 chunk；
- 各知识层占 Prompt 的字符比例；
- 各节点 RAG 字符数和模型 Token；
- fallback 触发率；
- 组件、体量和空间拓扑重复度；
- 首轮 Blueprint 校验率；
- `wild-core` 重建通过率。

### 工作包 B：增加知识职责 metadata

先在候选索引中为已有声明标记；同步对齐 Loader、过滤字段、ingest 规则与 linter，避免迁移后的内容又被要求补回完整配方。Markdown 示例中的多值字段如何编码到当前索引及如何过滤，需要先做兼容验证。

先为现有声明标记：

- `wild_schema`；
- `blueprint_design`；
- `domain_reference`；
- `project_pattern`。

在不删除文档的情况下，先实现可过滤的职责边界。

### 工作包 C：调整节点检索

让总体、空间需求、拓扑、开洞和修复节点选择本阶段规则与必要领域参考，不再只靠 `doc_type` 决定整包注入。先排除无关配方与 fallback，再以实验验证具体内容的取舍。

### 工作包 D：迁移有价值内容

从建筑类型和组件文档中提取：

- 宿主关系；
- 坐标语义；
- 跨构件依赖；
- 当前支持映射；
- 降级规则；
- 几何约束；
- 已验证错误和修复规则。

其余通用建筑内容进入领域参考层。

### 工作包 E：精简或归档旧配方

确认新检索和评测稳定后，再压缩大型建筑类型构成、固定组件矩阵、重复百科和普通生成不需要的 fallback 配方。先保留迁移清单和 disposition，不直接删除原始资料。

### 工作包 F：验证索引并发布

- 运行知识库 linter；
- 使用真实 MarkdownChunker 预览分片；
- 使用临时 Chroma 做检索评测；
- 验证通过后同步正式索引；
- 持续观察生产 RAG Trace 和生成指标。

## 8. 对照实验

在删除或归档知识前，使用同一组生成案例比较：

| 组别 | 检索内容 |
| --- | --- |
| A | 当前完整知识库 |
| B | 排除通用 `building_types` 和组件百科，作为消融对照，不预设为上线配置 |
| C | 各阶段基础契约 + 项目规则 + 经筛选的必要领域参考，隔离整栋配方和 fallback |

统一评估：

- Prompt/RAG 字符数；
- 模型 Token 和响应时间；
- 用户硬约束实现率；
- Blueprint JSON 合法率；
- 首轮几何通过率；
- fallback 触发率；
- `wild-core` 重建通过率；
- 相同输入与模型配置重复运行时，有效候选的体量和空间拓扑差异；
- 检索来源分布；
- 每个失败是否能定位到具体 Blueprint 规则。

只有候选配置在相同基础契约、需求集和模型配置下获得可重复收益，且约束与质量不回退，才选择迁移或归档。每次先改变一个主要因素；减少上下文和改变知识类型若同时发生，不能把收益全部归因于内容类型。

## 9. 检索评测

评测用例应使用答案键：

```json
{
  "query": "退台建筑的屋顶应该如何覆盖",
  "expectedSources": [
    "blueprint-design/roof-coverage.md"
  ],
  "requiredTerms": [
    "support_y",
    "coverage",
    "level"
  ],
  "metadataFilter": {
    "knowledge_layer": "blueprint_design",
    "generation_stage": "assembly"
  }
}
```

主要指标：

- Hit@K；
- Recall@K；
- MRR；
- 错误知识层命中率；
- 不适用阶段知识命中率，以及领域建议被误当硬约束的比例；
- chunk 来源分布；
- 空召回率和距离分布。

Hash embedding 只用于验证分片、索引和过滤流程，不能证明生产语义召回质量。正式对照实验需要使用真实 embedding 和临时索引。

## 10. 验收指标与门禁

持续记录：

- 默认 Prompt 中 Blueprint 专属知识占比；
- 各阶段 `domain_reference` 命中分布及不适用内容命中率；
- RAG 字符数和模型 Token；
- 用户约束实现率；
- 首轮 Blueprint 校验率；
- `wild-core` 重建通过率；
- fallback 触发率；
- 同类建筑体量和空间拓扑重复率；
- 仅在满足约束的有效候选中统计设计差异率；
- Hit@K、Recall@K 和 MRR；
- 每条规则的源码、规范或验证样例来源覆盖率。

建议设置以下门禁：

1. 系统规则必须来自当前源码、Schema 或经过验证的 `.wild` 样例；
2. `domain_reference` 不得默认作为硬约束；
3. fallback 知识只能在明确 fallback 阶段召回；
4. assembler 和 validator 不依赖通用建筑百科；
5. 未支持能力必须提供显式降级或明确拒绝；
6. 正式索引变更必须经过真实 embedding 的检索评测。

## 11. 不采用的做法

- 不直接删除全部组件知识；
- 不认为大模型自行知道当前 `.wild` Schema 和 `wild-core` 行为；
- 不把通用建筑参数写成系统硬规则；
- 不继续扩充每种建筑的固定组件合同；
- 不用增大 `top_k` 或上下文长度掩盖知识职责混乱；
- 不把最少可行 fallback 当成普通生成配方；
- 不在未做对照实验前清空正式 Chroma；
- 不因某段 JSON 无效就删除其中仍成立的宿主和装配语义；
- 不为每种建筑维护独立的校验与修复逻辑。

## 12. 面试表达

> 我审计了建筑类型和组件知识进入生成上下文的路径，确认存在职责混用风险，但模板偏置的实际贡献还没有量化。因此我提出按知识职责、阶段和约束强度治理：平面使用专用契约，项目规则优先保障，必要领域参考按任务选择，fallback 单独隔离。后续计划先使用相同需求集和真实 embedding 建立基线，再比较检索、约束、成本与有效设计差异；只有实验支持才迁移或归档内容。目前完成的是审计和方案设计，不能宣称已减少模板偏置。
