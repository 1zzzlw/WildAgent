# 当前遇到的问题：Agent 分层自检与自我纠错闭环不完整

> 本文区分现有局部实现与待补能力；实施阶段见[统一实施路线与验收](../统一实施路线与验收.md)。最后补充核对：2026-09-05。

## 1. 问题结论

“结构自检、事实自检、工具行为自检、推理逻辑自检”是一套合理的检查维度，但它还不能单独构成 Agent 的自我纠错能力。

完整的自我纠错至少需要形成以下闭环：

```text
发现问题
→ 结构化分类
→ 选择允许的修复层级
→ 在候选副本上执行修复
→ 使用同一组校验器复检
→ 只提交安全改善的结果
→ 无改善则回滚
→ 达到预算后停止或转人工处理
```

WildAgent 当前已经实现了其中相当一部分，尤其是 Blueprint 的确定性校验、局部修复、复检、回滚和保存门禁。但项目中以四类自检命名的通用 Validator，与当前生产工作流并没有完整连接：

- `StructureValidator` 存在，但生产主链使用的是另一套 Blueprint、FloorPlanIR 和 Gate 校验；
- `FactualValidator` 只以有限方式接入最终流水线，主要检查少量数值范围和枚举；
- `ToolValidator` 没有接入生产链，实际工具安全由 `repair_tools.py` 的白名单机制承担；
- `ReasoningValidator` 没有接入生产链，而且以自然语言推理文本为检查对象，失败时默认通过。

因此，这个问题不能描述成“项目没有自我纠错”，也不能描述成“四层自检已经完成”。准确说法是：

> WildAgent 已具备 Blueprint 层的局部校验—修复—复检闭环，但分层自检协议、事实一致性、决策一致性和最终重建结果反馈仍未统一，四个通用 Validator 也没有真正成为生产纠错链的组成部分。

## 2. Agent 领域分类

- **一级领域**：Reliability & Recovery
- **二级领域**：Self-Reflection & Self-Correction、Validation、Tool Use & Execution、State & Memory、Evaluation & Observability
- **问题类型**：Layered Self-Check and Closed-Loop Recovery Gap
- **关键术语**：Self-Correction Loop、Structured Validation Issue、Bounded Repair、Revalidation、Rollback、Fail-Closed、Decision Consistency、Outcome Verification
- **当前状态**：局部闭环已实现，统一自检与端到端纠错尚未完成

## 3. 四类自检在当前项目中的真实状态

| 自检类型 | 对应代码 | 当前生产状态 | 核心问题 |
| --- | --- | --- | --- |
| 结构自检 | [`structure_validator.py`](../../../wild-server/app/agent/validators/structure_validator.py) | 通用类未接入；生产链另有结构和 Schema 校验 | 存在重复体系，缺少覆盖所有中间状态的统一契约 |
| 事实自检 | [`factual_validator.py`](../../../wild-server/app/agent/validators/factual_validator.py) | 部分接入最终校验 | 主要检查数值范围和枚举，不能代表完整事实正确性 |
| 工具行为自检 | [`tool_validator.py`](../../../wild-server/app/agent/validators/tool_validator.py) | 通用类未接入 | 只让 LLM 给出诊断和修复文字，不等于工具执行安全 |
| 推理逻辑自检 | [`reasoning_validator.py`](../../../wild-server/app/agent/validators/reasoning_validator.py) | 未接入 | 依赖自然语言推理文本，失败时默认通过，规则检查尚未完成 |

## 4. 当前已经具备的纠错能力

### 4.1 确定性 Blueprint 校验流水线

[`run_validation_pipeline()`](../../../wild-server/app/services/agent_service.py) 已按固定顺序执行：

- Blueprint 顶层结构；
- 必填字段；
- 引用完整性；
- 门窗局部坐标和宿主范围；
- 墙体连接；
- 楼梯对齐；
- 屋顶覆盖；
- 构件尺寸；
- 重复骨架质量；
- 碰撞和竖向高程；
- 组件专用放置规则；
- 领域参数范围与枚举。

对于材质引用、门窗坐标、开口越界、楼梯对齐、构件尺寸、屋顶覆盖、墙体连接和部分碰撞问题，流水线会执行确定性修复并立即复检。

这部分是真正可靠的“检查—修复—复检”，因为修复结果仍由程序规则判定，而不是由 LLM 自己声明成功。

### 4.2 结构化问题协议

[`validation_issues.py`](../../../wild-server/app/agent/validation_issues.py) 会把文本校验输出转换成稳定的 `ValidationIssue` 字典，包括：

- 错误代码；
- 根因分类；
- 校验器名称；
- 严重程度；
- 实体和关联实体；
- 建议修复层级；
- 建议工具；
- 可选修复目标。

这使后续修复节点不必只读取一段模糊的自然语言错误。

### 4.3 受限工具修复

[`repair_tools.py`](../../../wild-server/app/agent/repair_tools.py) 定义了白名单动作，例如：

- 新增明确缺失的实体；
- 删除明确列出的超额实体；
- 移动、缩放或重新挂载门窗；
- 修正材质引用；
- 修改少量允许的几何字段。

模型不能任意覆盖 Blueprint，只能选择工具和参数；程序还会检查允许修改的实体、字段、引用和数值。

### 4.4 候选副本、全量复检和回滚

[`callback_node.py`](../../../wild-server/app/agent/nodes/callback_node.py) 的修复流程已经具备较强的安全性：

1. 只处理本轮结构化错误对应的实体；
2. 在 Blueprint 副本上执行动作；
3. 对候选结果重新运行完整校验；
4. 比较修复前后的问题集合；
5. 只有错误严格减少且没有引入新问题时才提交；
6. 未改善时丢弃候选结果，相当于回滚；
7. 每个失败目标都有独立重试上限。

复检还调用 `_validate_design_brief_constraints()`，覆盖部分楼层、构件配额和立面开口约束。因此当前已有有限设计一致性检查，缺少的是完整用户需求的结构化映射与验收覆盖。

### 4.5 最终保存门禁

[`agent_delivery.py`](../../../wild-server/app/services/agent_delivery.py) 只允许 `status=complete` 且没有错误的 Blueprint 保存。警告过多时也会拒绝交付。

这保证了“修复失败后不能把结果伪装成成功产物”。

### 4.6 人工审核与运行中反馈

项目还具备执行计划审核、平面审核、风格审核和运行中用户意见重规划。这属于 Human-in-the-loop，不是 Agent 自主纠错，但能处理需要用户取舍的设计问题。

## 5. 当前仍然存在的核心问题

### 5.1 四个 Validator 是并列原型，不是统一生产链

全项目调用关系显示：

- `StructureValidator.validate_and_fix()` 没有生产调用；
- `ToolValidator.diagnose_tool_error()` 没有生产调用；
- `ReasoningValidator.validate_reasoning()` 没有生产调用；
- `FactualValidator` 只在最终流水线中被实例化，并直接调用其私有范围和枚举检查方法。

四个类主要由 Mock LLM 的独立测试覆盖，不能证明它们已经参与真实生成、修复和复检。

### 5.2 结构自检没有统一覆盖所有中间状态

生产链已经分别校验 ArchitecturePlan、FloorPlanIR、Blueprint、Plan2Build Gate 和最终交付状态，但这些检查分布在多个模块中，没有统一说明：

- 每个状态的权威 Schema 是什么；
- 哪些错误能自动修复；
- 修复后从哪个节点重新执行；
- 哪些错误必须阻断；
- 哪些状态变化会使已有校验快照失效。

通用 `StructureValidator` 只关注一个 JSON Schema，不能覆盖跨阶段状态契约。其 `JsonSchemaValidator` 在缺少 `jsonschema` 依赖时还会返回空错误，属于 Fail-Open。

### 5.3 “事实自检”目前只是有限的参数范围检查

[`domain_schema.yaml`](../../../wild-server/config/domain_schema.yaml) 当前只为门、窗、墙、楼板、柱和楼梯配置了少量尺寸范围。最终流水线直接检查范围和枚举，没有使用：

- 配置中的父子关系；
- `FactualValidator.validate_entity()` 的完整父对象逻辑；
- 批量覆盖率统计；
- 设计方案与 Blueprint 的语义一致性；
- RAG 证据与项目事实来源；
- 当前 Schema、compiler 和 core 能力边界。

未配置约束的实体会直接通过；事实校验内部发生异常时，最终流水线还会返回“校验跳过”的成功标记。因此“通过事实自检”并不等于建筑事实完整正确。

### 5.4 通用 ToolValidator 不等于工具行为校验

`ToolValidator` 的核心行为是让另一个 LLM 阅读错误并生成：

- 根因文字；
- 修复步骤文字；
- 预防建议。

其 `execute_fix()` 会让 LLM 重新生成完整输出，得到可解析 JSON 后立即返回，没有自行证明：

- 工具参数是否在白名单；
- 工具前置条件是否成立；
- 修改是否只影响允许实体；
- 是否引入新错误；
- 真实执行结果是否符合预期。

生产链中的 `repair_tools.py + callback_node.py` 实际上比该通用类更安全，后续应该统一到现有受限执行机制，而不是再接入一条“LLM 重写完整 JSON”的旁路。

### 5.5 推理自检关注了不稳定的检查对象

`ReasoningValidator` 让一个 LLM 判断另一个 LLM 的自然语言 reasoning 是否矛盾，存在以下问题：

- 推理文本可能为空、被截断或不对外提供；
- 自评模型也可能犯同类错误；
- 同样的结论可以由不同推理文字得到；
- 解析失败和模型异常时默认返回“通过”；
- 规则检查只识别少量英文关键词；
- 数值一致性部分仍是未实现的 `pass`。

对 WildAgent 而言，更可靠的对象不是隐藏的思考过程，而是：

```text
用户约束 → ArchitecturePlan → FloorPlanIR → DesignBrief → Blueprint → 校验结果
```

应该检查这些可执行状态之间的决策一致性，而不是试图证明自然语言思维链正确。

### 5.6 最终 Mesh 结果没有自动回到后端纠错链

后端最终校验主要基于 `.wild` Blueprint 字段和程序计算。真正的 `wild-compiler → wild-core → MeshData` 重建发生在前端 Worker 中，重建诊断显示在 [`ValidationPanel.vue`](../../../wild-web/src/components/panels/ValidationPanel.vue)。

当前没有发现前端把结构化 `reconstructionReport` 自动提交给正在运行的生成任务并触发对应修复。现有 `execution_feedback` 是用户输入的运行中意见，不是 Core 自动反馈。

因此仍可能出现：服务端 Blueprint 校验通过并保存，但组合构件展开或真实 Mesh 包围盒仍存在问题。

### 5.7 局部修复无法覆盖所有全局错误

Callback 主要按 `entity_id` 聚合问题。没有实体归属、没有 `repair_target` 的全局错误不会进入模型局部修复，只能阻断或人工处理。

这对安全是合理的，但当前缺少一套明确的升级策略，将全局问题路由到：

- 重新规划；
- 重建 FloorPlanIR；
- 确定性全局修复；
- compiler/core 修复；
- 用户确认。

### 5.8 修复验收还没有覆盖全部质量维度

当前 Callback 主要依据“错误数量严格下降且没有引入新错误”决定是否提交。该规则已经比只看错误总数可靠，但仍需要补充：

- 严重程度是否降低；
- 警告是否显著增加；
- 已有 DesignBrief 检查之外，用户需求和批准关系是否被破坏；
- Blueprint 指标改善是否对应真实 Mesh 改善；
- 修复是否造成设计质量退化或结果趋同。

未来增加问题级预算时，还必须保留任务总预算，防止自动重规划后新 ID 或新错误重置局部额度。该项是扩展恢复路由的设计要求，不能据此断言当前流程已经出现无限循环。

### 5.9 缺少系统级纠错评测

当前测试大量验证单个 Validator、工具或修复案例，但还缺少统一指标回答：

- 人工注入某类错误后，能否被正确发现；
- 根因分类是否正确；
- 是否选择了正确修复层级；
- 修复成功率和误修率是多少；
- 平均需要多少轮；
- 回滚是否真正保护了原结果；
- 达到重试预算后是否正确停止；
- 是否在不同建筑尺寸和形态上都成立。

## 6. 对初步四层方案的正式补充

建议保留原有四层，但重新定义边界，并补充两个不可缺少的层面：

| 层级 | 正式名称 | 检查对象 |
| --- | --- | --- |
| 1 | Structure & Contract Check | JSON、Schema、阶段状态、必填字段、引用和状态转换 |
| 2 | Factual & Semantic Check | 用户约束、项目事实、能力边界、数值和实体关系 |
| 3 | Tool Action Check | 工具选择、参数、权限、前置条件、执行差异和副作用 |
| 4 | Decision Consistency Check | 用户意图、计划、中间状态与最终输出是否一致 |
| 5 | Execution Outcome Check | compiler/core 真实重建、Mesh 几何和运行时结果 |
| 6 | Recovery Policy & Budget | 修复层级、回滚、重试预算、停止条件和人工升级 |

第4层建议用“决策一致性”替代“自然语言推理逻辑”，第5、6层则负责把检查结果真正变成安全、可终止的纠错循环。

- 四类通用 Validator；

- `ValidationIssue` 协议；
- Callback 修复节点；
- 白名单修复工具；
- LangGraph 重试路由；
- 最终保存门禁；

本轮只整理问题与方案，没有修改自检或修复代码，也没有把现有单元测试定义表述为当前环境已通过的运行结果。

## 8. 面试中的问题描述

> 我最初把 Agent 自检分为结构、事实、工具和推理四层。审计项目后发现，四个 Validator 类虽然都存在，但并没有组成生产闭环；真正可靠的部分反而是 Blueprint 校验流水线和 Callback 的白名单修复、全量复检与回滚。我因此把问题重新定义为 Agent Reliability & Recovery：方案上保留结构、事实和工具检查，计划把自然语言推理检查改为可执行状态之间的决策一致性检查，再补充真实执行结果验证和有限恢复策略。这样衡量的不是 Agent 会不会反思，而是它能否发现错误、受控修复、证明改善，并在无法改善时安全停止。
