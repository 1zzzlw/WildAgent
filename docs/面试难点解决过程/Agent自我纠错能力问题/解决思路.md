# 解决思路：建立分层验证、受限修复与结果反馈闭环

> 实现状态：复用已有局部闭环的目标方案，新增协议与反馈尚待实现验证。最后整理：2026-09-05。  
> 全局阶段与共享契约见[统一实施路线与验收](../统一实施路线与验收.md)。

## 1. 方案结论

WildAgent 不需要再并列接入四个通用 Validator，然后让 LLM 多做四次判断。更合适的方案是复用当前已经可靠的 Blueprint 校验和 Callback 修复机制，把它升级成覆盖全部中间状态和真实重建结果的统一纠错协议。

目标不是让 Agent 输出更多“反思”，而是让每次纠错满足：

```text
可检测
→ 可分类
→ 可执行
→ 可复检
→ 可回滚
→ 有预算
→ 可观测
```

## 2. 目标闭环

```text
生成结构化状态
→ 按状态类型执行 ValidatorSet
→ 产出统一 ValidationIssue
→ 选择 repair_level
→ 优先执行确定性修复
→ 仍未解决时由 LLM 选择白名单动作
→ 在候选副本上执行
→ 重跑受影响校验 + 最终全量校验
→ 比较问题集合、意图约束和真实结果
→ 改善则提交，否则回滚
→ 达到单问题预算后重规划、询问用户或终止
```

## 3. 第一阶段：统一自检协议

### 3.1 不按 Validator 类组织状态，按问题协议组织

建议所有检查输出统一结构：

```json
{
  "issue_id": "stable-id",
  "stage": "floor_plan|blueprint|compiler|core",
  "category": "schema_contract|host_relation|coverage_geometry",
  "code": "ROOF_COVERAGE",
  "severity": "error|warning|info",
  "entity_ids": ["main_roof"],
  "related_entity_ids": ["upper_wall_1"],
  "observed": {},
  "expected": {},
  "message": "",
  "repair_level": "deterministic_fix|model_tool|replan|compiler|core|manual",
  "suggested_actions": [],
  "retryable": true,
  "source": "validator-name",
  "validator_version": "1.0"
}
```

当前 [`validation_issues.py`](../../../wild-server/app/agent/validation_issues.py) 已经具备雏形，应在它上面扩展，而不是再创建互相独立的错误格式。

### 3.2 每种中间状态声明 ValidatorSet

| 状态 | 必需检查 |
| --- | --- |
| Intent / ExecutionPlan | 用户意图、能力白名单、依赖、终止条件 |
| ArchitecturePlan | 体量、楼层、功能和设计约束 |
| FloorPlanIR | 轮廓、空间拓扑、流线、开口和竖向交通 |
| DesignBrief | 组件配额、风格、材质和立面约束 |
| Blueprint | Schema、引用、坐标、宿主、覆盖、碰撞和尺寸 |
| Compiled Blueprint | 组合构件展开、映射和生成数量 |
| Mesh / Scene | 世界包围盒、可见间隙、穿插、空 Mesh 和材质结果 |

每个状态都应明确：权威 Schema、ValidatorSet、允许修复方式、复检入口和失败后的路由。

### 3.3 必需校验不能 Fail-Open

对 Schema、引用、保存门禁和真实重建等必需检查：

- 依赖缺失应返回 `validator_unavailable` 错误；
- 执行异常应返回 `validator_failed`，不能伪装成通过；
- 只有明确标为可选的检查才能 `skipped`；
- Trace 必须区分 `passed`、`failed`、`skipped` 和 `unavailable`。

这意味着需要修正当前 `JsonSchemaValidator` 和领域事实检查中的默认放行语义。

## 4. 第二阶段：重新定义四类自检

### 4.1 Structure & Contract Check

结构自检不应只检查最终 JSON，而要检查每个阶段的契约：

- 字段和类型；
- 必填项；
- 枚举；
- 引用闭合；
- 状态版本；
- 节点输入输出边界；
- 非法阶段越权，例如骨架提前生成后续组件；
- 修改后校验快照是否按 Blueprint 指纹失效。

确定性可修复的格式问题可以归一化；无法证明安全的缺失信息应回到上游节点重新生成，不能由修复器猜值。

### 4.2 Factual & Semantic Check

事实检查需要分为三类：

1. **项目事实**：当前 `.wild` Schema、compiler/core 能力和坐标语义；
2. **领域约束**：尺寸范围、宿主、装配、标高和覆盖关系；
3. **任务事实**：用户明确要求、批准方案、DesignBrief 和风格确认结果。

规则来源应记录 authority 和版本。未配置规则不能自动等价于“验证通过”，而应在覆盖率中标记为 `not_checked`。

`domain_schema.yaml` 的范围检查可以保留，但应：

- 对齐当前真实字段名，例如检查 `stepHeight` 而不是失效的旧字段；
- 接入父子关系和自定义几何检查；
- 统计实体类型和字段覆盖率；
- 与 Schema、知识库和 Core 能力来源保持一致；
- 对异常采取明确失败或降级策略。

### 4.3 Tool Action Check

工具行为自检应围绕工具执行生命周期，而不是只生成诊断文字：

**执行前：**

- 工具是否在白名单；
- 当前问题是否允许使用该工具；
- 参数是否符合 Schema；
- 目标实体和引用是否存在；
- 权限、修改范围和重试预算是否满足。

**执行中：**

- 在候选副本或事务中执行；
- 记录修改前后差异；
- 单动作失败不污染其他状态；
- 对外部副作用使用幂等键。

**执行后：**

- 检查动作是否真的产生预期差异；
- 重跑直接相关的 Validator；
- 再运行最终全量校验；
- 发现新错误时回滚；
- 保存工具调用、结果和失败原因。

当前 [`repair_tools.py`](../../../wild-server/app/agent/repair_tools.py) 和 [`callback_node.py`](../../../wild-server/app/agent/nodes/callback_node.py) 已经覆盖多数基础，应继续扩展，不建议把 `ToolValidator.execute_fix()` 的整份 JSON 重生成方式接入生产。

### 4.4 Decision Consistency Check

将原来的 Reasoning Check 改成可观测的决策一致性检查：

```text
用户明确约束
↕
ArchitecturePlan 决策
↕
FloorPlanIR 空间关系
↕
DesignBrief / StylePackage
↕
Blueprint 实体与参数
↕
最终校验和重建结果
```

复用统一 `RequirementSpec`，以关联记录表达决策和证据，不再建设独立需求表或决策状态机。建议记录：

```json
{
  "decision_id": "main_entrance",
  "requirement_ids": ["user.entry.south"],
  "source_state": "FloorPlanIR",
  "target_entities": ["door_main", "wall_south_1"],
  "expected": {
    "facade": "south",
    "count_min": 1
  },
  "status": "planned|applied|validated|rejected",
  "evidence": []
}
```

Validator 检查的是决策是否从计划落到输出，以及是否被验证，不需要读取或保存完整自然语言思维链。

## 5. 第三阶段：补齐执行结果检查

### 5.1 为什么必须检查真实重建

Blueprint 字段合法只证明输入协议成立。组合组件经 `wild-compiler` 展开并由 `wild-core` 生成 Mesh 后，仍可能发生：

- 编译映射缺失；
- 输出 Mesh 为空；
- 世界坐标变换错误；
- 屋面最低点与墙顶不连续；
- 组件实际包围盒与宿主分离；
- 材质或透明度在渲染阶段失效。

这些问题不能靠自然语言反思发现。

### 5.2 推荐方案 A：服务端或共享 Worker 预重建

在保存正式 `.wild` 前，使用与前端一致的 compiler/core 版本执行无渲染重建，输出结构化 `ReconstructionReport`。

```text
Blueprint 校验通过
→ compiler/core 预重建
→ Mesh 关系校验
→ 失败则进入对应 repair_level
→ 全部通过后保存和发送
```

该方案需先解决 TypeScript Core 的运行方式、版本一致性和检查覆盖。首批只接入可稳定判断的编译失败、缺失网格与无效顶点，再通过正反例逐步覆盖分区屋顶、宿主、真实洞口和楼梯连接。

当前重建诊断主要使用包围盒；单个屋顶还与汇总墙体范围比较，不能直接作为多体量分区覆盖的完备门禁。报告必须携带已执行、跳过、不支持的检查和版本。零 error 仅代表已运行检查未发现错误；材质视觉和审美问题仍需单独验收。

### 5.3 推荐方案 B：两阶段交付握手

如果暂时不能服务端重建，可以采用：

```text
后端发送 candidate_blueprint
→ 前端 Worker 重建
→ 前端返回结构化 reconstruction_report
→ 后端决定提交、修复或拒绝
→ 通过后再发送 blueprint_committed
```

报告必须携带 Blueprint 指纹、compiler/core 版本和 request ID，避免把旧重建结果应用到新候选。还需处理重建失败、客户端断开、报告超时与重复回传；未收到有效报告保持未提交状态。客户端报告的可信边界需明确；若交付要求独立可信验证，应以服务端同版本重建结果为准。

普通用户文字反馈继续走现有 `execution_feedback`，不要与机器重建报告混用。

## 6. 第四阶段：建立分层修复策略

### 6.1 修复优先级

1. **确定性修复**：能由结构或几何关系唯一推导；
2. **受限模型工具**：存在多个候选值，但修改范围可白名单化；
3. **重新规划**：错误来自总体方案或空间拓扑；
4. **用户确认**：修复会改变设计意图；
5. **compiler/core 修复**：Blueprint 正确但重建算法错误；
6. **阻断交付**：无法安全修复或已耗尽预算。

### 6.2 单调改善条件

先检查不可接受的条件，再比较改善，不把意图违反放在质量向量末尾：

1. 候选越过允许范围、破坏已批准硬约束、引入新 blocker/更严重错误或必需检查不可用时直接拒绝。
2. 对余下候选比较目标问题的严重程度和问题集合，至少有一个目标改善。
3. 完成同一校验集的全量复检；已接入的必需重建检查也要重跑。
4. 无改善或出现禁止条件则回滚，不能用减少低级错误抵消设计意图破坏。

当前 Callback 已复检 DesignBrief 的构件配额、楼层与立面开口等有限约束；下一步扩展的是完整 RequirementSpec 追踪和覆盖，不是从零增加所有设计一致性校验。

### 6.3 重试预算按问题指纹管理

当前按组件计数已经比全局重试安全，但同一实体可能同时出现不同错误。建议使用：

```text
(issue_code, entity_id, validator_version)
```

作为预算键，并记录：

- 尝试次数；
- 使用的修复层级；
- 每次动作和结果；
- 是否发生循环；
- 最后一次失败原因。

同一问题连续两次无改善时可以提前停止，避免把全部预算浪费在等价动作上。

同时设置 request/job 级总预算，覆盖自动修复、重规划轮数、LLM 调用和累计耗时或 Token。问题指纹用于定位与局部限额，不能替代总预算；新实体 ID、新错误码和自动重规划不得重置任务总预算。记录状态指纹与已尝试动作，识别循环；预算耗尽时保留最后有效结果和停止原因。用户明确发起的新任务可创建新预算。

### 6.4 全局错误升级路由

没有实体 ID 的问题不能交给局部 `patch_entity`。需要根据 `repair_level` 路由：

- `replan` → ArchitecturePlan 或 FloorPlanIR 节点；
- `deterministic_fix` → 对应共享修复器；
- `compiler` / `core` → 阻断并生成工程诊断；
- `manual` → 用户确认；
- 不可恢复 → 终止并保留报告。

## 7. 第五阶段：可观测性与评测

### 7.1 每轮纠错 Trace

至少记录：

- 输入 Blueprint 或状态指纹；
- ValidatorSet 和版本；
- 发现的问题；
- 修复策略与工具动作；
- 变更字段；
- 修复前后问题集合；
- 是否提交或回滚；
- 重试次数；
- LLM Token、延迟和错误；
- 最终停止原因。

### 7.2 故障注入评测集

为每个根因类别建立参数化故障样本：

| 类别 | 示例 |
| --- | --- |
| schema_contract | 缺字段、错枚举、阶段输出越界 |
| coordinate_frame | 世界坐标误写为父墙局部坐标 |
| host_relation | 门窗引用不存在的墙 |
| level_continuity | 上层墙、楼板或屋顶标高断开 |
| coverage_geometry | 屋顶未覆盖最高承托墙 |
| compiler_geometry | 组件展开数量或映射错误 |
| core_geometry | Mesh 为空或世界包围盒异常 |
| model_instruction | 用户要求与 Blueprint 不一致 |
| tool_action | 非白名单字段、越权实体和无效参数 |

同一规则至少覆盖多种尺寸、形态和建筑类型，不使用建筑 ID 或固定截图坐标建立特判。

### 7.3 核心指标

- Detection Recall：已注入错误中被发现的比例；
- Classification Accuracy：根因和修复层级正确率；
- Repair Success Rate：修复并复检通过的比例；
- False Repair Rate：原本正确但被错误修改的比例；
- Regression Rate：修复引入新问题的比例；
- Rollback Correctness：无改善候选被正确拒绝的比例；
- Average Repair Rounds：平均修复轮数；
- Budget Exhaustion Rate：达到预算仍未解决的比例；
- End-to-End Validation Rate：最终 Blueprint 和重建共同通过率；
- Cost per Successful Repair：每次成功修复的 Token、延迟和费用。

## 9. 对齐统一实施阶段

以[统一路线](../统一实施路线与验收.md)安排工作；每一层是检查职责，不要求各自新增 Agent 节点或模型调用。

| 全局阶段 | 纠错专项任务 |
| --- | --- |
| P0 | 梳理生产检查覆盖和已有修复行为；记录候选、问题、动作、回滚与成本 |
| P1 | 修复必需检查异常放行；适配统一 ValidationIssue；有限需求校验；禁止条件与任务总预算 |
| P2 | 衔接有限求解的局部修复、无解/不支持/预算耗尽和全局升级路由 |
| P3 | 检查批准版本、Patch 范围与产物映射；使过期校验失效 |
| P4 | 分阶段接入真实重建，扩展参数化故障与误修评测 |

优先复用现有 Callback 与白名单工具。已确认的安全放行缺陷可提前修复，不等待完整契约；覆盖扩展则跟随支持能力逐项验收。

## 10. 验收标准

- 每个生产状态都有明确 ValidatorSet；
- 必需校验异常不会被记录为成功；
- 每条错误都能追踪到根因、修复层级和停止条件；
- 确定性问题优先由共享修复器处理；
- 模型只能选择白名单动作，不能直接覆盖完整 Blueprint；
- 所有修复都在候选副本执行，并由同一组校验器复检；
- 无改善或引入更严重问题时能够回滚；
- 问题级预算能区分不同故障，任务总预算不会因新实体、新错误或自动重规划而重置；
- 用户批准的设计意图不会被静默修改；
- 适用且必需的 compiler/core 检查已执行，发现错误时阻断或进入明确修复层；未检查项和覆盖范围单列；
- 参数化故障集能够输出 Detection、Classification、Repair、Regression 和 Cost 指标；
- 真实建筑回归中，纠错成功率提升且平均重试、Token 和延迟处于可接受范围。

## 11. 面试中的解决方案表达

> 我没有把自我纠错简单理解为让模型再反思一次，而是把它设计成一个可验证的恢复状态机。项目原有的 Blueprint 校验、白名单修复、候选副本、全量复检和回滚已经构成了局部闭环，我提出在此基础上扩展统一 ValidationIssue，按结构、事实、工具、决策一致性和真实执行结果分层检查。能唯一推导的问题走确定性修复，模型只能选择受限工具；修复结果必须在不破坏用户意图、不引入更严重问题的前提下单调改善，否则回滚。后续计划通过问题级与任务级双重预算、分阶段 compiler/core 重建反馈限制恢复过程。目前完成的是审计和方案设计，新增能力与效果仍需实现和故障注入验证。
