# 五个难点的统一实施路线与验收

> 文档性质：跨专题实施规划，不代表业务改造已经完成。  
> 最后整理：2026-09-05。  
> 阅读入口：[难点索引](难点.md)。各专题保留问题证据和技术细节；全局优先级、共享契约及验收口径以本文为准。

## 1. 近期目标与专题分工

近期目标是：让有限复杂度建筑稳定走通“生成平面 → 局部修订 → 用户确认 → 确定性装配”，保住有效设计，并得到同条件前后对照数据。

五个问题可以独立归类，但实施时共享状态、错误协议和评测基础，不分别建设五套流程。

| 专题 | 在统一路线中的职责 |
| --- | --- |
| 工作流与中间状态 | 定义需求、批准版本、阶段输入输出和失效关系 |
| 知识职责与模板偏置 | 区分项目硬规则、领域建议、示例和 fallback，按阶段选择上下文 |
| RAG 准确率与利用率 | 验证召回、注入、采用声明和产物兑现，按增量收益选择增强手段 |
| 自我纠错 | 复用现有校验、受限修复、复检和回滚，补齐预算与恢复边界 |
| 平面规划与用户审核 | 承担近期主线：面积语义、拓扑、有限求解、Patch 和批准平面装配 |

首期先覆盖矩形轮廓、直墙、普通门窗的单层/双层住宅；双层必须提前预留同位交通核心。先使单层通过，再加入双层。L/U 形、中庭、退台、曲墙和高层作为后续能力扩展及显式不支持样例，不承诺首期自动求解。

新规划器只在声明支持的范围内试验；能力外请求保留可用旧路径或返回明确不支持，不静默降成矩形，也不把基础设施替换作为首期前置条件。

## 2. 证据与完成状态

每项结论区分三类证据：

- **源码确认**：某个机制存在，并注明是否接入当前生成路径。
- **样本观察**：某次请求确实发生，注明请求、时间和版本范围。
- **待验证假设**：机制对质量、成本或多样性的因果贡献，需要对照实验。

例如，[2026-09-03 请求 Trace](../../wild-server/storage/sessions/rag_traces/session_1788435875430/req_1788435876883_xvjfu98kp.json) 记录两次 `BadRequestError`、零命中、4 次 LLM 调用、65674 Token 和约 441 秒请求耗时。它支持“该次请求检索出错且成本高”，不能代表平均生成成本，也不能证明知识库模板导致了该次失败。Trace 的 `GenerationPaused` 还应与检索异常、无效平面和正常人工审核暂停分别解释。

先定位 `BadRequestError` 的实际请求与响应原因，不预设是 embedding、过滤条件或供应商参数问题。记录错误时去除密钥和敏感请求头。

现有文档中的旧 linter、Hash embedding 和宿主环境错误记录保留为历史证据。后续运行必须记录新的环境、工作树内容签名与结果，不把历史失败当成当前环境结论。

## 3. 共享契约与事实源

### 3.1 最小对象集

| 对象 | 权威内容 | 更新规则 |
| --- | --- | --- |
| `RequirementSpec` | 用户需求、hard/soft/default、来源、验收方式 | 保留稳定 requirement ID 和修订记录；统一替代方案中的 `RequestSpec` 命名 |
| `FloorPlanIR` | 平面空间、边界、墙、洞口和交通关系 | 保存稳定实体 ID、revision、父版本；SVG 是其派生视图 |
| `ApprovedDesignContract` | 已批准需求、体量、平面和材质版本的清单 | 引用持久化的不可变 revision/内容哈希，不复制第二套可写设计数据 |
| `Blueprint` | 确定性装配后的三维产物与交付内容 | 关联批准版本、装配版本和产物哈希；交付后的编辑仍遵守 `.wild`/ScenePatch 边界 |

`DecisionRecord` 和 `KnowledgeEvidence` 起初只是通过 requirement ID、实体 ID、规则 ID 关联的记录，不引入新的独立状态机。约束账本属于 `RequirementSpec` 及其验收记录，不另建重复可写需求表。

“唯一事实源”按阶段和职责理解：需求、二维设计和三维产物各有明确权威对象；不得由 SVG、模型摘要或装配默认值反向静默改写已批准事实。

### 3.2 批准、修改和失效

批准清单必须引用可重新读取的完整快照，不能只保存一个无法恢复内容的哈希。需求、体量或平面变化后，建立新 revision，并使依赖的批准状态、装配结果和校验报告失效；材质等局部变化至少使对应装配、材质和重建检查失效。

Patch 必须带 `base_revision`。旧版本 Patch 和旧 Blueprint 的重建报告不能提交到新版本。旧产物可保留供查看，但应明确标记为旧版本，不能继续显示为当前已验证结果。

### 3.3 来源不等于质量

目标状态应分开表达：

- 来源：模型、程序求解器、用户编辑、模板；
- 质量：待校验、有效、无效、诊断预览；
- 审核：未批准、已批准、已失效。

当前 [`is_confirmable_spatial_plan()`](../../wild-server/app/agent/spatial_plan.py) 允许 `model` 和 `deterministic_template`；[新链合并逻辑](../../wild-server/app/agent/nodes/floor_validate_node.py) 还依赖子结果是否都来自模型。引入程序布局时必须同步迁移这些判断及旧检查点，合法求解结果不能被当成故障 fallback。迁移前新旧来源规则仍是现状，不代表目标状态已实现。

### 3.4 验收证据与错误协议

沿用现有 `ValidationIssue`，统一采用 `observed`、`expected`、`entity_ids`、`constraint_ids` 和 `repair_level` 等字段，旧字段通过适配迁移。阶段 Schema 可各自独立，但问题输出和修复审计应可互通。

约束证据既可以指向实体，也可以指向关系、集合或全局计算。“禁止阳台”“总面积上限”不能强制要求存在对应正向实体。需求覆盖率与已实现检查的通过率分开统计；`not_checked` 不得计为通过。

## 4. 统一实施阶段

| 阶段 | 必做交付 | 验收与进入下一阶段的条件 |
| --- | --- | --- |
| P0 可信基线 | 定位检索异常；区分基础上下文、召回和错误；保存原始候选、归一化候选、最终 IR；建立 10～20 个需求样例 | 能定位设计在哪一步丢失；生成失败、人工暂停、检索异常分类明确；获得成功率和包含失败的成本基线 |
| P1 保住设计 | 平面专用契约；关键需求 ID；面积与核心预留语义；明确候选来源和质量；在现有修复器能力内保留和局部修复候选 | 局部失败不静默清空有效设计；无法修复时保留候选并明确失败；诊断预览不可批准；批准约束的适用检查不回退 |
| P2 有限求解 | LLM 生成空间程序和拓扑；程序在声明范围内生成几何与洞口候选；受控可行性反馈；按证据简化模型调用 | 在相同需求集上比较可确认率、约束满足率、模型设计保留率与成本；区分无解、不支持和预算耗尽 |
| P3 局部编辑与装配一致性 | 先实现移动共享边界、移动洞口及锁定实体；自然语言和 SVG 操作共用 Patch；版本检查与装配映射 | 修改影响范围可解释；非受影响实体保持稳定；图、批准 IR 和 Blueprint 来自同一批准清单 |
| P4 扩展验证与按需优化 | 分阶段重建门禁；扩展几何与恢复覆盖；知识分层对照；按失败分布选择检索增强 | 检查覆盖明确、误报受控；真实 embedding 和端到端实验有可重复增益；再推广到复杂形态 |

已确认的必需校验异常放行问题可以提前做小修复并验证，不必等待完整契约。恢复操作涉及已批准设计变化时应重新审核；能力不足和引擎缺陷不能通过静默改坐标掩盖。

各专题实施章节只是上述阶段内的工作包，不再各自定义 P0/P1。查询改写、LLM 索引增强、混合检索、完整 CAD 编辑和全能布局求解器均不是首期必选项。

## 5. 三个专项边界

### 5.1 平面面积与求解

先定义 FloorPlanIR 空间多边形表示的面积口径，以及它与房间净使用面积、墙厚的换算关系。可用区域按轮廓并集扣除该层明确 void 计算；交通核心作为有归属的空间预留，不能同时扣除又要求重复覆盖。

Program 阶段就预留楼梯/电梯位置和面积，跨层开洞在哪些标高扣除必须明确。Geometry 再在剩余区域分配房间，不能分完全部面积后才插入核心。

每次求解配置有限候选数和时间预算，并记录：`feasible`、`proven_infeasible`、`unsupported`、`budget_exhausted`。只有面积下界冲突等可证明情况才报告无解；启发式没找到解不等于需求无解。

### 5.2 修复预算与提交条件

保留问题级预算，同时设置 request/job 级总预算，包括自动修复/重规划轮数、模型调用和累计耗时或 Token。新实体 ID、新错误码和自动重规划不能重置任务总预算；用户明确发起的新任务可新建预算。

先检查禁止条件：破坏已批准硬约束、越过允许范围、引入新严重错误、必需校验不可用。候选满足禁止条件之外的要求后，再比较目标问题是否改善，并全量复检。无改善回滚，耗尽预算时保留最后有效状态及停止原因。

### 5.3 重建验证范围

优先复用同版本 compiler/core，先验证可稳定判定的编译失败、缺失网格和无效顶点；有正反例验证后再增加宿主分离、分区屋顶、真实洞口和楼梯连接检查。最终门禁附检查集版本、Blueprint 哈希、已执行/跳过/不支持项目。

当前 [`reconstructionDiagnostics.ts`](../../wild-web/src/renderer/reconstructionDiagnostics.ts) 主要使用包围盒，单个屋顶还与汇总墙体范围比较。这不能直接作为多体量分区屋顶、坡面贴合和真实开洞的完整证明。`error=0` 仅表示已运行检查没有发现错误；必需检查未执行时不得宣称完整通过。材质视觉和审美效果需单独验收。

## 6. 共同评测口径

### 6.1 基线与对照

需求集同时包含详细要求、信息不足输入、约束冲突、不支持能力和两到三轮局部修改。冻结评测集、模型配置、知识内容签名、索引/chunker、装配和校验版本；工作树未提交时记录内容签名，不能只记 commit。

确定性装配用固定批准快照复跑；模型链使用相同输入和配置重复运行并报告样本数、波动与失败数。调参样例和最终验收样例分开，避免只对看过的案例有效。10～20 例用于首期发现问题，不据此宣称所有建筑类型都可靠。

### 6.2 必须分开的指标

| 指标 | 统计口径 |
| --- | --- |
| 首轮可确认率 | 范围内有效需求的首次有效平面数 / 对应请求数；诊断 fallback 不算成功 |
| 最终成功率 | 在任务总预算内完成规定交付的请求数 / 对应请求数；同时单列冲突和不支持输入的正确处理率 |
| 硬约束满足率 | 通过适用验收的硬约束数 / 全部适用硬约束数；未检查项不计通过 |
| 模型设计保留率 | 模型提出且应保留的需求/拓扑决策在有效 IR 中的落实比例；程序正常推导坐标不算信息丢失 |
| 局部修改保留率 | 受影响依赖范围之外的实体和关系保持比例；修改前声明影响范围，避免把必要联动算成漂移 |
| 每次成功的成本 | 同批全部尝试的模型 Token/耗时/费用合计除以成功数，另报单请求延迟；成功数为零时标为不可计算并保留总成本 |
| 检查覆盖与通过 | 已检查的规则/能力范围和通过情况分别报告，不以零 error 代替完整覆盖 |

RAG 的 `retrieved → injected → cited/planned → validated` 分开记录。注入只能证明片段进入 Prompt；采用引用是声明，产物满足规则也不能单独证明 RAG 因果贡献。用相同基础契约下开启/关闭可选检索的对照验证增量收益。

先用真实 embedding 建立可用检索基线，再比较阶段化上下文；查询改写、索引增强、BM25 和重排分别改变一个主要变量。正式索引评测默认只读，重建实验使用临时索引；Hash embedding 仅用于流程烟雾测试。

通用领域知识按任务必要性、来源可靠性和实验增益选择，不能只因“模型可能知道”就排除。多样性只在有效且满足约束的候选中比较。确定性复现基于固定批准契约与实现版本；模型 seed 若可用，应记录但不承诺端到端逐字一致。

## 7. 每次实施的记录与面试表达

每次完成一个工作包，补充以下证据后再更新状态：

1. 触发需求、原始失败、请求 ID 与对应代码/内容版本。
2. 比较的方案、选择原因、实际修改范围和未处理边界。
3. 同条件前后结果：样本数、成功/失败、约束、成本和回归情况。
4. 一个仍失败或不支持的反例，以及下一步是否值得继续。

面试表述使用与状态一致的动词：“源码审计确认了……”用于现状，“我提出/计划……”用于方案，“实现并在 N 个样例中验证……”必须有真实记录。不要把文档中的目标收益写成已经取得的效果。
