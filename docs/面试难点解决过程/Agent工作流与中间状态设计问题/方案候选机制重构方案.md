# 方案候选机制重构方案

> ## ⚠️ 本文已废弃（2026-09-17）
>
> 本文是"引入用户选方案、替代自动评分"的第一版设计，**结论已被推翻**：
>
> 1. 文中 §二/§三 设计的 `architecture_proposal` + `proposal_review` 节点曾按本文落地，但
>    `interrupt` 的中断事件与 resume 通道**从未接通**（后端只识别 `plan_review` / `design_review`，
>    前端只处理 `execution_plan_review_required` / `design_review_required`），
>    导致计划模式下生成请求必然报"未返回结果"。
> 2. 删除候选选择时**没有同步修改 `architecture` 提示词**——提示词仍索要 `candidates` 数组，
>    而归一化只读顶层 `massing/volumes/...`，于是 LLM 输出被整体丢弃、实际使用确定性兜底方案。
> 3. 本文 §六 声称的三项收益只兑现了一项（见下方对照）。
>
> **最终处置**：候选机制（含本文新增的两个节点）**整体删除**，用户参与能力交还给已连通的
> `design_review` 链路。请以同目录
> 《[候选机制清理与proposal节点处置方案.md](候选机制清理与proposal节点处置方案.md)》为准。
>

## 一、问题分析

### 1.1 当前机制的问题

**核心问题**：`select_architecture_plan()` 自动评分选择候选方案

```python
# 当前流程
用户："生成一个别墅"
    ↓
LLM 生成 3-4 个候选
    ↓
代码自动评分（score_architecture_plan）
    ↓
代码检查违规（architecture_requirement_violations）
    ↓
代码选择最优（max by score）
    ↓
用户看到结果（可能不是想要的）
```

**具体问题**：

1. **复杂且容易出错**
   - `select_architecture_plan()` 逻辑复杂（300+ 行）
   - 评分标准难以调优
   - 违规检查经常误判
   - 频繁出现"所有候选均违反已批准业务要求"错误

2. **用户无法参与**
   - 用户需求模糊时（"生成一个别墅"），系统自动决策
   - 可能选了用户不喜欢的方案
   - 用户想要其他候选时，只能重新生成

3. **调试困难**
   - 评分逻辑分散在多个函数
   - 违规检查和约束应用逻辑不一致
   - 日志不够详细，难以定位问题

---

### 1.2 新方案的优势

**核心思路**：让用户选择方案，而不是代码自动选择

```python
# 新流程
用户："生成一个别墅"
    ↓
LLM 生成 3-4 个方案概要
    ↓
【展示给用户，等待选择】
    ↓
用户选择："我要第 2 个"
    ↓
针对选中方案生成详细设计
```

**优势**：

✅ **删除复杂代码**
- 删除 `select_architecture_plan()` 的评分逻辑
- 删除 `score_architecture_plan()`
- 删除 `architecture_requirement_violations()` 的自动检查
- 删除 `apply_structured_architecture_requirements()` 的强制应用

✅ **提升用户体验**
- 用户看到多个方案，自己选择
- 更符合实际设计流程（先看概念，再深化）
- 降低"不满意就重新生成"的频率

✅ **降低出错概率**
- 不再有"所有候选均违规"的错误
- 不再需要复杂的约束检查
- 生成失败的可能性降低

✅ **代码更清晰**
- 职责分离：proposal 节点生成概要，architecture 节点生成详细设计
- 逻辑简单：不需要评分、排序、选择

---

## 二、重构方案

### 2.1 新增节点：architecture_proposal

**位置**：在 `planner` 和 `architecture` 之间插入

**职责**：
- 生成 3-5 个建筑方案概要（不生成完整 Blueprint）
- 展示给用户选择
- 等待用户确认或反馈

**新流程**：

```
classifier → planner → plan_review → architecture_proposal → proposal_review → architecture
```

---

### 2.2 节点详细设计

#### Node 1: `architecture_proposal`

**输入**：
- `user_message`：用户需求
- `complexity_profile`：复杂度配置
- `structured_requirements`：已批准约束（参考）

**输出**：
- `architecture_proposals`：3-5 个方案概要
- `proposal_review_status`：`"pending"`

**方案概要格式**：

```python
{
    "id": "proposal_0",
    "concept": "三层欧式别墅",
    "description": "采用对称布局，坡屋顶，石材外墙，适合郊区环境",
    "preview": {
        "floors": 3,
        "width": 12.0,
        "depth": 10.0,
        "volumes": 1,
        "roof_type": "gable",
        "style": "欧式",
        "facade_bays": 5,
    },
    "rationale": [
        "对称布局适合欧式风格",
        "3 层高度符合郊区别墅标准",
        "单体量简洁大气",
    ]
}
```

**关键点**：
- ❌ 不生成完整的 volumes、facades、component_quota
- ❌ 不生成完整的 Blueprint
- ✅ 只生成方案概要（concept + preview）
- ✅ 快速生成（减少 LLM 调用时间）

---

#### Node 2: `proposal_review`

**职责**：等待用户选择方案

**使用 LangGraph interrupt**：

```python
from langgraph.types import interrupt

async def proposal_review(state):
    proposals = state["architecture_proposals"]
    
    choice = interrupt({
        "type": "proposal_selection",
        "proposals": [
            {
                "id": p["id"],
                "title": p["concept"],
                "description": p["description"],
                "preview": p["preview"],
            }
            for p in proposals
        ],
        "resume_examples": {
            "select": {
                "action": "select",
                "proposal_id": "proposal_0"
            },
            "regenerate": {
                "action": "regenerate",
                "feedback": "我想要现代风格"
            },
        }
    })
    
    if choice["action"] == "select":
        selected = next(p for p in proposals if p["id"] == choice["proposal_id"])
        return {
            "selected_proposal": selected,
            "proposal_review_status": "approved",
        }
    
    elif choice["action"] == "regenerate":
        return {
            "proposal_feedback": choice.get("feedback", ""),
            "proposal_review_status": "rejected",
        }
```

**路由逻辑**：

```python
def _after_proposal_review(state):
    status = state.get("proposal_review_status")
    
    if status == "approved":
        return "architecture"
    
    elif status == "rejected":
        return "architecture_proposal"  # 重新生成方案
    
    else:
        return "__end__"
```

---

#### Node 3: 简化后的 `architecture`

**输入**：
- `selected_proposal`：用户选择的方案概要

**输出**：
- `architecture_plan`：详细方案
- `design_document`：设计文档

**关键变化**：

❌ **删除**：
- 不再调用 `select_architecture_plan()`
- 不再生成多个候选
- 不再评分选择
- 不再检查违规

✅ **简化**：
- 直接基于 `selected_proposal` 生成详细方案
- 只调用一次 LLM
- 只生成一个完整方案

**伪代码**：

```python
async def architecture_planner(state):
    selected_proposal = state["selected_proposal"]
    
    # 基于选中的方案概要，生成详细设计
    prompt = build_detailed_architecture_prompt(
        proposal=selected_proposal,
        structured_requirements=state["structured_requirements"],
        spec_text=...,
    )
    
    llm_result = await invoke_llm(llm, messages)
    raw_plan = extract_json_object(llm_result.content)
    
    # 规范化（不再需要 select）
    plan = normalize_architecture_plan(
        raw_plan,
        user_message=selected_proposal["concept"],
        complexity_profile=state["complexity_profile"],
        profile=...,
    )
    
    # 直接构建设计文档
    design_document = build_design_document_or_error(plan, ...)
    
    return {
        "architecture_plan": plan,
        "design_document": design_document,
        ...
    }
```

## 五、风险和注意事项

### 5.1 风险

1. **破坏现有功能**
   - 修改了核心流程，可能影响其他节点
   - 测试覆盖不全，可能漏掉边缘 case

2. **前端需要配套修改**
   - 需要支持方案选择界面
   - WebSocket 消息格式可能需要调整

3. **用户体验变化**
   - 增加了一次用户交互（选择方案）
   - 可能被认为"多了一步"

---

### 5.2 降低风险的措施

1. **渐进式重构**
   - 先新增节点，不删除旧代码
   - 测试通过后再删除
   - 保留回退方案（Feature Flag）

2. **充分测试**
   - 单元测试（proposal 生成）
   - 集成测试（完整流程）
   - 手动测试（真实场景）

3. **Feature Flag 控制**
   ```python
   # 配置项
   ENABLE_PROPOSAL_SELECTION = os.getenv("ENABLE_PROPOSAL_SELECTION", "false") == "true"
   
   # 路由逻辑
   if ENABLE_PROPOSAL_SELECTION:
       return "architecture_proposal"
   else:
       return "architecture"  # 旧流程
   ```

## 八、总结

### 核心改动
