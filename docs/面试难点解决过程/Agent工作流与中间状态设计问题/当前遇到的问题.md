# Agent 工作流与中间状态设计：当前遇到的问题

> 文档性质：现状、证据与问题边界。
>
> 实现状态：本文只描述当前代码，不表示后续优化已经实施。
>
> 最后核对：2026-09-14。

## 1. 当前真正要解决的问题

WildAgent 当前存在一个明确的规划—执行对齐问题：

> 已批准 ExecutionPlan 中的建筑要求虽然进入了 `architecture` 节点的模型提示词，但没有继续成为候选归一化、评分和选择阶段可执行的结构化约束。

这不是简单的“下一个节点没有收到 State”，也不是“模型完全没看懂提示词”。问题实际发生在同一个 `architecture` 节点内部：

~~~text
已批准 ExecutionPlan
→ 转换成 Prompt 文本
→ 模型 reasoning 能够识别要求
→ 模型最终 JSON 候选可能偏离要求
→ 归一化和评分代码不知道这些批准要求
→ 偏离要求的候选仍可能胜出
→ 被选中的 architecture_plan 才进入 LangGraph State
→ 后续节点收到的已经是偏离后的方案
~~~

因此，本难点的核心不是保存模型原始思维过程，而是：

> 如何把上游已经批准的重要决定，转换成后续程序能够消费、校验和追踪的结构化业务状态。

## 2. 当前 LangGraph 主链

当前主图位于 [`graph.py`](../../../wild-server/app/agent/graph.py)，共享状态位于 [`graph_state.py`](../../../wild-server/app/agent/state.py)。

普通生成模式可以简化为：

~~~text
classifier
→ architecture
→ material_plan
→ design_review
→ skeleton
→ 动态组件 gen → val
→ merge
→ final_validate
→ callback / END
~~~

启用 `plan_mode` 后，会先经过可审核计划层：

~~~text
classifier
→ planning_research / web_research
→ planner
→ plan_validator
→ plan_review
→ plan_executor
→ 按批准计划调度 architecture、material_plan、skeleton 等业务节点
~~~

图中没有名为 `execution_plan` 的节点，因为：

- `execution_plan` 是 `GenerationState` 中的一个字段；
- `planner`、`plan_validator`、`plan_review`、`plan_executor` 才是 LangGraph 节点名称；
- 它们分别绑定 `execution_planner`、`execution_plan_validator`、`execution_plan_review`、`execution_plan_executor`。

## 3. 实测问题：批准约束在候选选择前失效

### 3.1 实际观察到的现象

一次“生成一个别墅”的 Plan Mode 测试中，已批准执行计划在总体方案阶段明确包含：

- 两层，首层和二层层高均为 `3.0m`；
- 主体平面外包尺寸约 `12m × 8m`；
- `gable` 双坡屋顶；
- 出檐不小于 `0.5m`。

流式 reasoning 曾主动复述这些条件，并形成过 `12m × 8m`、`gable`、出檐 `0.6m` 的中间设想。但是，最终进入程序处理的候选变成了：

| 阶段               |          尺寸 | 屋顶    | 结果                      |
| ------------------ | ------------: | ------- | ------------------------- |
| 已批准计划         | 约 `12m × 8m` | `gable` | 以阶段指导文本进入 Prompt |
| reasoning 中间设想 |    `12m × 8m` | `gable` | 只存在于流式思考文本      |
| 候选 1             |    `14m × 9m` | `flat`  | 评分 118，最终被选择      |
| 候选 2             |   `15m × 10m` | `gable` | 评分 118，未被选择        |

这个现象说明：

> 模型在思考过程中理解过约束，不等于这些约束已经进入最终 JSON，更不等于后面的确定性程序会继续执行这些约束。

### 3.2 `architecture_planner` 是一个节点内工作流

[`architecture_planner`](../../../wild-server/app/agent/nodes/architecture_node.py) 在 LangGraph 中整体只对应一个 `architecture` 节点，但函数内部包含一条线性工作流：

~~~text
读取 GenerationState
→ 解析修订意见和复杂度
→ RAG 检索
→ 识别 Architecture Profile
→ 提取 ExecutionPlan 阶段指导
→ 构建 Prompt
→ 调用 LLM
→ 解析 JSON，必要时格式恢复
→ 归一化并评分候选
→ 选择 architecture_plan
→ 构建 DesignDocument
→ 返回 State 增量
~~~

这些步骤不会作为独立节点显示在 LangGraph 图中。因此，本次信息断点首先属于“节点内部的数据交接”，而不是两个 LangGraph 节点之间的 State 传递失败。

## 4. 当前代码中的完整断点

### 4.1 批准计划只被转换成提示词

[`execution_plan_phase_guidance`](../../../wild-server/app/agent/planning/execution.py) 会从 `execution_plan.dynamic_tasks` 中找到当前 `architecture` 阶段的任务，并把标题、目标和验收条件拼成文本：

~~~python
phase_guidance = execution_plan_phase_guidance(
    execution_plan,
    "architecture",
)

if phase_guidance:
    prompt += phase_guidance
~~~

这证明批准计划到达了总体方案模型调用，但此时它只是 Prompt 的一部分。

### 4.2 reasoning 与最终 JSON 是两条数据通道

[`llm_invocation.py`](../../../wild-server/app/llm/invocation.py) 分别处理模型的 `reasoning` 和 `content`：

- `reasoning` 通过运行时回调发送给前端，用于展示思考过程；
- `content` 被解析为 JSON，进入候选归一化和选择；
- 原始 reasoning 不进入 `GenerationState`，后续业务逻辑也不会解析 reasoning 来恢复设计要求。

不持久化原始 Chain-of-Thought 是合理边界。真正需要保存的是经过明确提取、可以验证的业务决定，而不是模型完整思考文本。

### 4.3 候选选择函数没有接收批准约束

当前调用为：

~~~python
plan, selection_diag = select_architecture_plan(
    raw_plan,
    normalization_request,
    complexity_profile,
    profile,
)
~~~

四个输入分别是：

- `raw_plan`：模型最终 `content` 解析出的对象；
- `normalization_request`：修订意见或原始用户消息；
- `complexity_profile`：复杂度要求；
- `profile`：建筑类型能力配置。

这里没有 `execution_plan`，也没有从已批准计划提取出的尺寸、层数、屋顶和出檐等结构化约束。

### 4.4 评分器只能检查自己收到的信息

[`score_architecture_plan`](../../../wild-server/app/agent/generation/architecture/) 当前主要根据以下信息评分：

- `user_message` 中显式出现的层数、尺寸、对称性和屋顶要求；
- `architecture_profile` 中的建议宽深范围、入口要求和基础构件；
- 候选自身的复杂度、体量、结构网格和设计说明。

本次原始用户消息只有“生成一个别墅”。`12m × 8m`、双层、`gable` 等条件只存在于批准计划时，评分器就无法检查这些条件。

### 4.5 同分选择放大了信息缺口

候选选择使用：

~~~python
selected_index = max(
    range(len(candidates)),
    key=lambda index: scores[index],
)
~~~

Python 的 `max` 在多个候选同为最高分时返回第一个。因此两个候选都是 118 分时，候选 1 被稳定选中。

“同分取第一个”是错误候选胜出的直接机制，但不是根因。根因是评分体系没有批准约束，导致本应拉开差距或直接淘汰候选的条件没有参与选择。

## 5. 三种信息不能混为一谈

| 信息           | 当前载体                            | 当前作用                 |
| -------------- | ----------------------------------- | ------------------------ |
| 模型 reasoning | 运行时流式事件                      | 给用户观察，不是业务状态 |
| 模型最终候选   | `content` 解析后的 `raw_plan`       | 供归一化、评分和选择     |
| 已选总体方案   | `GenerationState.architecture_plan` | 供后续节点继续执行       |

本次不是“reasoning 没有完整传给下一个节点”。更准确的说法是：

> reasoning 中理解过的批准要求没有稳定落实到最终候选；批准要求本身也没有以独立的结构化约束进入归一化和选择代码。最终，已经偏离的 `architecture_plan` 才被写入 State 并传给后续节点。

## 6. 与已删除旧平面工作流的区别

旧平面设计链曾经出现过：

1. 校验反馈已经存在于 State，但 `floor_*` 节点构建 Prompt 时没有读取，导致 revise 盲跑；
2. 局部墙体或洞口错误触发 `spatial_plan` 整包 fallback。

它与当前问题具有相同的抽象模式：

~~~text
上游已经产生重要信息
→ 后续处理步骤没有把它作为明确输入使用
→ 最终结果偏离上游决定
~~~

但二者不是同一个代码问题：

| 对比项       | 已删除的旧平面链           | 当前总体方案链                   |
| ------------ | -------------------------- | -------------------------------- |
| 重要信息     | 上一轮平面审核反馈         | 已批准 ExecutionPlan 约束        |
| 信息所在位置 | LangGraph State            | ExecutionPlan，并被渲染进 Prompt |
| 未消费位置   | 后续 `floor_*` 节点 Prompt | 候选归一化、评分与选择           |
| 当时解决方式 | 读取反馈并注入旧平面节点   | 当前尚未实施                     |
| 当前状态     | 相关生产代码已删除         | 问题仍存在                       |

因此，旧平面链的修复不能作为当前批准约束问题已经解决的证据。

## 7. 当前问题的根因分层

### 7.1 表示层

批准要求只有面向模型的自然语言表示，缺少供程序执行的结构化表示。例如当前没有一个明确对象稳定表达：

~~~yaml
width:
  target: 12
  tolerance: 0.5
depth:
  target: 8
  tolerance: 0.5
floors:
  exact: 2
roof_type:
  allowed: [gable]
eave_overhang:
  minimum: 0.5
~~~

上面只是说明缺失的数据形态，不代表当前已经实现该结构。

### 7.2 传递层

`execution_plan_phase_guidance()` 的返回值只拼入 Prompt，没有作为独立参数继续传给：

~~~text
normalize_architecture_plan
score_architecture_plan
select_architecture_plan
~~~

### 7.3 执行层

当前缺少确定性机制来区分：

- 必须满足的硬约束；
- 可以用于比较的软偏好；
- 建筑能力边界；
- 模型自行提出的设计选择。

因此，即使模型输出偏离批准计划，程序也无法决定应该淘汰、扣分、修复还是要求重新生成。

### 7.4 追踪层

`architecture_diag` 记录候选摘要、评分和选中序号，但还不能回答：

- 每个批准约束由哪个候选满足或违反；
- 哪项约束导致候选被淘汰；
- 约束在归一化前后是否发生变化；
- 最终 `architecture_plan` 如何证明与批准计划一致。

## 8. 已确认事实与证据边界

### 8.1 当前可以确认

- 批准计划通过阶段指导文本到达了 `architecture` 模型 Prompt；
- reasoning 中曾出现符合批准条件的中间设想；
- 最终展示的候选与批准计划存在直接矛盾；
- `select_architecture_plan()` 没有接收 ExecutionPlan 批准约束；
- `score_architecture_plan()` 无法检查只存在于批准计划中的要求；
- 两个候选同分时，第一个候选会被确定性选中；
- 当前问题发生在 `architecture` 节点内部，后续节点接收的是已经选定的方案。

### 8.2 当前不能直接断言

- 所有生成请求都会发生同样的约束漂移；
- reasoning 越长，最终方案就一定越差；
- RAG 上下文长度是本次漂移的直接原因；
- 偏差一定完全来自模型原始 JSON，因为本次记录没有保留该原文，尚不能排除归一化阶段参与改写；
- 只修改 Prompt 就能稳定解决问题；
- 将原始 reasoning 写入 State 就能解决问题。

## 9. 后续解决必须满足的验收条件

本文件不提前确定最终实现，但后续方案至少要能够证明：

1. 已批准要求拥有独立、可序列化的结构化表示；
2. 归一化、评分和选择阶段能够明确访问这些要求；
3. 硬约束违反不能仅靠普通加减分后仍然胜出；
4. 软偏好可以参与可解释评分，但不能覆盖硬约束；
5. 诊断结果能够展示每个候选满足和违反了哪些约束；
6. 约束必须随相关计划版本更新，不能继续使用已经失效的旧批准结果；
7. 至少使用本次 `12m × 8m + 两层 + gable + 出檐` 案例建立回归测试；
8. 增加一个仅有泛化用户需求、没有额外批准约束的反例，证明普通生成行为没有被破坏。

## 10. 当前阶段的一句话总结

面试或学习时，可以先这样概括当前问题：

> 我在 LangGraph 建筑生成流程中发现，已批准计划虽然通过 Prompt 影响了模型推理，但没有被编译为候选选择器能够执行的结构化约束，导致模型最终 JSON 偏离后，程序仍可能把错误候选写入 State。问题不在于保存 Chain-of-Thought，而在于建立从“批准决定”到“确定性校验与选择”的可靠状态契约。
