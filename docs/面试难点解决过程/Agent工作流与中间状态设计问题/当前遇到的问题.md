# Agent 工作流与中间状态设计：当前遇到的问题

> 文档性质：现状与问题边界。  
> 实现状态：本文只描述当前代码，不表示后续优化已经实施。  
> 最后核对：2026-09-08。

共享契约和实施阶段见[统一实施路线与验收](../统一实施路线与验收.md)。以下源码机制与质量影响假设分开解读。

## 1. 背景

WildAgent 使用 LangGraph 组织建筑生成流程。模型参与意图识别、执行计划、总体方案、平面设计、材料规划和失败修复，程序再把中间结果确定性装配为 `.wild` Blueprint。

当前主链可以简化为：

~~~text
classifier
  → planning_research / planner / plan_validator / plan_review / plan_executor
  → architecture
  → floor_space_analysis
  → floor_layout
  → floor_openings
  → floor_validate
  → floor_plan_review
  → material_plan
  → approved_plan_assembler
  → style_review
  → decor_assembly
  → merge
  → final_validate
  → callback / END
~~~

主图位于 [`graph.py`](../../../wild-server/app/agent/graph.py)，中间状态位于 [`graph_state.py`](../../../wild-server/app/agent/graph_state.py)。更完整的文件和函数位置见 [项目索引](../../项目索引.md)。

## 2. 核心矛盾

当前需要解决的规划—执行问题是：

> 用户要求和已批准计划中的设计决定，没有被编译为后续节点共同消费、持续校验的结构化约束；已有样本分别出现了候选方案改写批准约束，以及归一化失败后整份设计回退。

这存在推理成本与最终建筑质量不匹配的风险，影响幅度需基线验证：前面虽然进行了大量分析，后面的候选选择、归一化、fallback 和确定性装配却可能只拿到不完整的设计信息。

## 3. 2026-09-08 总体方案实测：批准约束在候选选择前失效

### 3.1 测试中实际观察到的现象

本次“生成一个别墅”的测试中，进入总体方案阶段的已批准执行计划明确包含：

- 两层，首层和二层层高均为 `3.0m`；
- 主体平面外包尺寸约 `12m × 8m`；
- `gable` 双坡屋顶；
- 出檐不小于 `0.5m`。

流式 reasoning 曾主动复述这些条件，并形成过符合条件的中间设想，例如 `12m × 8m`、`gable`、出檐 `0.6m`。但最终用于程序处理的两个候选摘要变为：

| 阶段 | 尺寸 | 屋顶 | 结果 |
|---|---:|---|---|
| 已批准计划 | 约 `12m × 8m` | `gable` | 作为总体方案阶段任务进入提示词 |
| reasoning 中间设想 | `12m × 8m` | `gable` | 只出现在流式思考文本中 |
| 候选 1 | `14m × 9m` | `flat` | 评分 118，最终被选择 |
| 候选 2 | `15m × 10m` | `gable` | 评分 118，未被选择 |

因此，这个样本的关键问题不是“模型完全没有看到约束”，而是：

> 模型已经识别并讨论了批准约束，但这些决定没有稳定进入最终供选择的候选结构化状态，也没有在候选归一化和评分选择阶段被再次约束。

### 3.2 当前代码能够确认的链路原因

[`architecture_node.py`](../../../wild-server/app/agent/nodes/architecture_node.py) 会通过 `execution_plan_phase_guidance(...)` 把总体方案阶段的任务目标和验收条件追加到模型提示词，因此批准计划确实到达了总体方案模型调用。

但是，模型返回候选后，`select_architecture_plan(...)` 当前只接收：

- 模型输出的 `raw_plan`；
- 原始 `user_message`；
- `complexity_profile`。

它没有接收 `execution_plan` 或本阶段已经批准的尺寸、屋顶、出檐约束。随后 [`score_architecture_plan`](../../../wild-server/app/agent/architecture_plan.py) 也只从原始用户消息提取显式要求进行评分。本次原始用户消息只是“生成一个别墅”，所以只存在于批准计划中的 `12m × 8m` 和 `gable` 等条件没有进入候选评分。两个候选同为 118 分时，当前确定性选择逻辑取第一个候选，最终选中了与批准屋顶不一致的平屋顶方案。

这条链路可以概括为：

~~~text
用户原始消息（泛化需求）
→ ExecutionPlan 补充了具体批准约束
→ 约束以提示词文本形式到达总体方案模型
→ reasoning 中识别了约束
→ 最终候选结构化结果偏离了部分约束
→ 候选评分重新只看原始用户消息
→ 约束漂移未被发现，首个同分候选被选中
~~~

这正是规划—执行对齐失效，而不只是提示词写得不够严格：同一项决定没有成为跨状态、跨节点持续有效的业务数据。

### 3.3 “反复否定、重新生成”的准确边界

测试记录中大量出现“等等”“让我重新考虑”“让我简化”。它说明模型在一次复杂输出中反复修改局部方案，造成明显的推理绕行和前后不稳定，但不能仅凭这些文本断言 LangGraph 多次重跑了总体方案节点。

当前实现中，总体方案在精密模式下先执行一次流式模型调用；只有最终 `content` 无法解析出 JSON 时，才会额外触发一次定向格式恢复，并向界面输出“总体方案结构化输出缺失或格式无效”的提示。本次记录范围内没有出现该提示。因此，现有证据更支持“单次模型调用内部反复推演”，而不是“服务端不断重试总体方案”。

界面上的反复思考是可见症状；对生成结果真正产生影响的是 reasoning、最终 JSON、批准计划和候选评分之间缺少一致的结构化决策载体。

### 3.4 证据强度与结论边界

本次可以确认：

- 批准计划中的明确约束与最终选中候选存在直接矛盾；
- 批准计划到达了模型提示词，但没有进入候选选择函数；
- 候选评分无法检查仅存在于批准计划中的尺寸和屋顶要求；
- 同分时选择第一个候选，是本次矛盾方案最终胜出的直接机制。

本次不能直接断言：

- 16168 字 RAG 上下文就是模型反复修改方案的根因；
- 所有总体方案请求都会发生同样的约束漂移；
- reasoning 越长必然导致最终方案越差；
- 本次发生了整体 fallback 或多轮总体方案重试。
- 偏差一定直接产生于模型原始 JSON；当前展示记录没有保留该原文，尚不能排除归一化阶段参与改写。

## 4. Reasoning 与业务状态分离

模型的 `content` 和 `reasoning` 由 [`llm_invocation.py`](../../../wild-server/app/agent/llm_invocation.py) 分别收集。原始 reasoning 通过 [`runtime_context.py`](../../../wild-server/app/agent/runtime_context.py) 的运行时回调发送到 WebSocket，再由前端展示。

当前边界是：

- `GenerationState` 没有原始 reasoning 字段；
- reasoning 回调被定义为“不进入 LangGraph State”的运行时资源；
- [`generation_job_service.py`](../../../wild-server/app/services/generation_job_service.py) 只持久化公开 progress，不持久化原始模型 reasoning；
- 后续节点通常只能消费解析后的 JSON `content`；
- reasoning 中没有进入 JSON 的设计决定无法被后续节点可靠使用。

不持久化原始 Chain-of-Thought 本身是合理的。真正缺失的是等价、精简、可执行的“结构化决策记录”。

- 供应商 reasoning 兼容：[`model_client.py`](../../../wild-server/app/agent/model_client.py)
- 运行时回调：[`runtime_context.py`](../../../wild-server/app/agent/runtime_context.py)
- WebSocket `thinking_delta`：[`ws_agent.py`](../../../wild-server/app/api/ws_agent.py)

## 5. ExecutionPlan 管理步骤，但没有完整承载设计

[`execution_plan.py`](../../../wild-server/app/agent/execution_plan.py) 中的 ExecutionPlan 主要记录：

- 任务标题和目标；
- 所属执行阶段；
- 验收条件；
- 任务依赖；
- 执行状态和结果引用。

它能回答“系统下一步执行什么”，但不能完整回答：

- 用户哪些要求是不可违背的硬约束；
- 为什么选择某种体量、平面或屋顶策略；
- 哪些备选方案被否决；
- 设计决策最终由哪些 Blueprint 实体实现；
- 哪个校验器证明了设计要求已经实现。

动态计划最终仍要归一化到有限的能力和阶段白名单。因此当流程本身已经固定时，让模型额外生成执行计划可能增加 Token 和延迟，却没有增加对设计结果的实际控制力。

本次测试进一步暴露了一个更具体的断点：ExecutionPlan 中的本阶段目标和验收条件虽然被转换为提示词文本，但没有继续作为结构化输入传给候选归一化与评分逻辑。也就是说，它当前可以影响模型生成，却不能在模型输出偏离后作为确定性选择依据。

相关代码：

- 计划能力和任务归一化：[`execution_plan.py`](../../../wild-server/app/agent/execution_plan.py)
- 研究、规划、校验、审核和执行节点：[`execution_plan_node.py`](../../../wild-server/app/agent/nodes/execution_plan_node.py)
- Plan Mode 路由：[`graph.py`](../../../wild-server/app/agent/graph.py)

## 6. 设计信息分散，权威归属与版本关系不清晰

当前设计信息分布在以下对象中。不同阶段使用不同表示本身合理，问题是缺少清晰的权威归属、版本引用和失效规则：

- `architecture_plan`
- `floor_space_analysis`
- `floor_layout`
- `floor_openings`
- `spatial_plan`
- `material_plan`
- `design_brief`
- `execution_plan`
- 各节点 diagnostics 和前端 reasoning

这些字段的职责并不完全重复，但缺少一个统一约束账本将下面的过程串起来：

~~~text
用户原始要求
→ 总体方案决策
→ 平面、立面和屋顶决策
→ Blueprint 实体
→ 校验结果
~~~

当某项要求没有实现时，当前通常只能看到最终几何错误，难以直接判断问题来自需求提取、方案归一化、fallback、装配还是重建。

## 7. Normalizer 和 fallback 可能造成规划信息损失

总体方案和平面方案都存在归一化、自动修复和 fallback：

- [`normalize_architecture_plan`](../../../wild-server/app/agent/architecture_plan.py)
- [`_fallback_plan`](../../../wild-server/app/agent/architecture_plan.py)
- [`normalize_spatial_plan`](../../../wild-server/app/agent/spatial_plan.py)
- [`fallback_spatial_plan`](../../../wild-server/app/agent/spatial_plan.py)
- [`deterministic_baseline_spatial_plan`](../../../wild-server/app/agent/spatial_plan.py)

这些机制提高了可用性，但存在以下风险：

1. 缺少统一报告说明哪些字段被保留、默认、修复或删除；
2. 局部格式问题可能最终触发整体方案替换；
3. fallback 可以继续进入后续链路，但原始设计意图可能已经丢失；
4. 前端不一定能明确区分模型方案、程序修复和安全模板。

最终就会出现“前面思考很多，后面却编译成安全模板”的现象。

## 8. 确定性装配承担了过多设计选择

当前主链的 `skeleton` 已指向 [`approved_plan_assembler`](../../../wild-server/app/agent/nodes/approved_plan_assembler_node.py)，而不是旧 LLM skeleton。

主体、屋顶、门窗槽位、阳台、入口附件和栏杆包含大量确定性规则：

- [`architecture_plan.py`](../../../wild-server/app/agent/architecture_plan.py)
- [`plan2build/assembler.py`](../../../wild-server/app/agent/plan2build/assembler.py)
- [`plan2build/decor_assembler.py`](../../../wild-server/app/agent/plan2build/decor_assembler.py)
- [`component_registry.py`](../../../wild-server/app/agent/component_registry.py)
- [`plan2build/style_registry.py`](../../../wild-server/app/agent/plan2build/style_registry.py)

确定性装配是保证几何稳定和可复现的必要手段。问题是上游设计变量表达不充分时，装配器只能依赖固定 profile、默认细节包、固定平面分割、固定风格包和有限组件白名单。

不同输入因此可能逐渐收敛为相似的体量、平面和立面结果。

## 9. 服务端校验与真实重建几何之间仍有边界

服务端已经具有多轮校验和修复：

- [`run_validation_pipeline`](../../../wild-server/app/services/agent_service.py)
- [`spatial_tools.py`](../../../wild-server/app/tools/spatial_tools.py)
- [`plan2build/gates.py`](../../../wild-server/app/agent/plan2build/gates.py)
- [`merge_node.py`](../../../wild-server/app/agent/nodes/merge_node.py)
- [`validate_node.py`](../../../wild-server/app/agent/nodes/validate_node.py)
- [`callback_node.py`](../../../wild-server/app/agent/nodes/callback_node.py)

但 `.wild` 的最终几何由前端 `wild-compiler` 和 `wild-core` 重建：

- [`wild-compiler/index.ts`](../../../wild-web/src/wild-compiler/index.ts)
- [`wild-core/src/primitive/resolver.ts`](../../../wild-web/src/wild-core/src/primitive/resolver.ts)
- [`wild-core/src/primitive/index.ts`](../../../wild-web/src/wild-core/src/primitive/index.ts)
- [`reconstructionDiagnostics.ts`](../../../wild-web/src/renderer/reconstructionDiagnostics.ts)

因此，“Blueprint 字段通过服务端校验”不必然等价于“重建后的 Mesh 几何正确”。屋顶覆盖、父子分离、真实开洞、退台支承等问题可能到前端重建阶段才完整暴露。

## 10. 修复闭环仍不能完整表示设计正确性

[`merge_node.py`](../../../wild-server/app/agent/nodes/merge_node.py) 最多执行三轮校验—修复；[`callback_node.py`](../../../wild-server/app/agent/nodes/callback_node.py) 只接受错误减少且没有引入新问题的修复候选。

现有闭环的局限是：

1. 错误数量减少不代表高优先级错误已经解决；
2. Callback 已复检部分 DesignBrief 楼层、配额与立面开口约束，但尚未覆盖完整用户需求，因此仍有未覆盖意图被修改的风险；
3. 服务端校验改善不等价于前端重建结果改善；
4. 当前问题结构对“实际值、期望值、设计约束、修复证据”的表达还不统一。

## 12. 已观察现象与待量化影响

已有请求分别支持高成本生成后整体 fallback，以及批准约束在候选生成和选择之间漂移的现象。以下影响仍需通过多样例和同条件实验分别量化，不能仅由源码结构推断全部因果关系：

- 精密模式的 Token 和时间成本增加，但结果质量没有同比提升；
- reasoning 中已经出现的设计意图在 JSON 解析、归一化或 fallback 后丢失；
- 已批准计划中的约束到达模型提示词后，没有继续进入候选评分和确定性选择；
- 不同需求最终收敛到相似的体量、平面、风格和组件组合；
- 问题追溯只能停留在“最后哪个几何错了”，难以定位设计意图在哪一阶段被改写；
- 修复能让某个校验器通过，却不能保证真实重建几何和用户设计要求同时正确。

## 13. 问题边界

当前可以确认：

- reasoning 与业务 State 之间存在明确边界；
- ExecutionPlan 主要是执行计划，不是完整设计契约；
- ExecutionPlan 阶段指导当前以提示词文本影响总体方案生成，但未成为候选评分的结构化输入；
- 方案、fallback、装配、校验和重建分布在多个模块；
- 服务端 Blueprint 校验与前端真实重建属于两个阶段。

当前不能直接断言：

- 所有几何错误都是 reasoning 丢失造成的；
- 确定性装配本身就是错误设计；
- 单纯增加推理 Token 就能提高几何质量；
- 把 `ReasoningValidator` 接入主链就能解决问题。

这个难点需要同时处理“设计信息表达”“模型与程序职责边界”和“真实几何交付门禁”三个层面。
