# Agent 工作流与中间状态设计：当前遇到的问题

> 文档性质：记录当前代码、LangSmith Trace 证据和问题边界。
>
> 实现状态：本文只描述尚未优化时的现状，不表示后续方案已经实施。
>
> 最后核对：2026-09-15。

## 1. 当前真正要解决的问题

WildAgent 当前的问题不是简单的“模型没有思考”，也不是 Planner 输出没有写入 `GenerationState`。

通过对一次“生成一个别墅”的完整 LangSmith Trace 进行逐节点对照，可以确认：

1. Planner 已经生成了本次需求对应的详细任务和验收条件；
2. 这些内容确实进入了 `execution_plan.dynamic_tasks`；
3. LangGraph 节点之间也能看到这些累积状态；
4. 但自然语言任务没有被稳定转换成下游节点可直接消费的结构化业务约束；
5. `execution_plan.steps` 调度的是固定节点，而不是逐条执行 `dynamic_tasks`；
6. 一个节点运行结束后，同一 phase 的多个动态任务可能被一起标记为 `completed`；
7. `acceptance` 只是自然语言文本，没有与确定性校验器建立对应关系；
8. 最终 Blueprint 通过固定 Schema 校验，不代表本次计划中的业务验收条件全部通过。

因此，当前难点可以更准确地概括为：

> 如何把上游已经批准的自然语言任务，转换成后续节点能够消费、程序能够逐条校验、整个流程能够持续追踪的结构化业务状态。

当前缺失的不是更多思考文本，而是下面这条业务链路：

~~~text
dynamic_tasks
→ 可执行的结构化业务约束
→ 明确的消费节点
→ 实际生成结果
→ 逐条验收结果与证据
~~~

## 2. 最初的判断为什么不够准确

### 2.1 最初的理解

最开始观察到的现象是：Planner 能够理解并讨论用户要求，但最终生成结果没有完整落实这些要求。

当时把问题理解为：

~~~text
Planner 已经想到了
→ 没有完整按照 State 结构传给下游
→ 下游节点能够使用的信息很少
→ Planner 的价值被削弱
~~~

这个判断描述出了“上游决定没有稳定落实”的现象，但还没有区分以下三种情况：

1. Planner 根本没有输出对应内容；
2. Planner 输出了，但节点没有写入 State；
3. 内容已经进入 State，但下游节点没有按业务含义消费和校验。

### 2.2 LangSmith 中为什么从头到尾都是 `GenerationState`

LangGraph 使用共享 State 工作。LangSmith 节点界面中看到的大对象通常是节点执行时的完整状态快照，并不表示每个节点都重新生成了全部字段。

实际关系可以理解为：

~~~text
下一节点输入
= 上一份完整 GenerationState
+ 上一节点返回的局部更新
~~~

因此，阅读 Trace 时必须分清：

- 节点输入：节点执行前已经累积的完整 State；
- 节点输出：当前节点本次新增或修改的字段；
- 下游输入：合并后的新 State；
- 字段存在：只能证明字段被携带，不能证明当前节点真正使用了它。

这一步修正了最初的观察方式：

> 在下游节点输入中看到 `dynamic_tasks`，只能证明它还在 State 中，不能证明节点已经消费了其中每条要求。

## 3. 当前开启 Plan Mode 后的实际主链

当前主图位于 [`graph.py`](../../../wild-server/app/agent/graph.py)，共享状态定义位于 [`state.py`](../../../wild-server/app/agent/state.py)。

对于“生成一个别墅”请求，开启 `plan_mode` 后的主流程可以简化为：

~~~text
classifier
→ planning_research / web_research
→ planner
→ plan_validator
→ plan_review
→ plan_executor
→ architecture
→ plan_executor
→ material_plan
→ design_review
→ plan_executor
→ skeleton
→ 动态组件 gen → val
→ merge
→ plan_executor
→ final_validate
→ plan_executor
→ END
~~~

其中：

- `execution_plan` 是 `GenerationState` 中的字段，不是节点；
- `planner` 生成计划；
- `plan_validator` 校验计划结构和能力引用；
- `plan_review` 等待用户批准或修改计划；
- `plan_executor` 从 `execution_plan.steps` 中选择下一条就绪步骤；
- 真实建筑结果仍由 architecture、material_plan、skeleton 等业务节点产生。

这条流程也是后续区分 `steps` 和 `dynamic_tasks` 的基础。

## 4. Trace 第一步：Planner 的内容有没有进入 State

### 4.1 Planner 模型实际输出

本次 Planner 模型最终 `content` 的顶层结构为：

~~~yaml
summary: 功能定义—骨架生成—细节填充—规范校验
tasks:
  - title: 功能布局与主体结构设计
    phase: architecture
    objective: 设计两层主体、车库和后院的功能布局
    acceptance:
      - 完成包含两层主体、车库及后院的整体功能分区
      - 确定主要墙体轴线和关键高度
      - 形成包含前廊、屋顶和车库顶的体量轮廓

  - title: 材料规划与内部配置
    phase: material_plan
    objective: 规划材料、家具和照明
    acceptance:
      - 为主要建筑元素指定材质
      - 在至少两个房间内布置家具
      - 在室内外关键位置添加照明

  - title: 门窗与建筑细部添加
    phase: skeleton
    acceptance:
      - 正确生成门窗
      - 至少添加一个 balcony 或 canopy
~~~

Planner 还提出了“必要的承重柱和联系梁”等骨架验收要求。

这些内容中，一部分是用户“生成一个别墅”没有明确指定、由 Planner 补充的设计假设，例如两层、车库、后院、前廊、家具和照明。

### 4.2 Planner 节点写入的 State

在 Planner 节点输出的 `execution_plan.dynamic_tasks` 中，可以继续找到：

- 任务标题；
- 任务目标；
- 所属 phase；
- 每条 acceptance；
- 任务 basis；
- 后端补充的任务 ID、依赖和状态。

例如：

~~~yaml
dynamic_tasks:
  - id: task_3
    title: 材料规划与内部配置
    phase: material_plan
    status: pending
    objective: 系统规划材料，并添加家具和照明组件
    acceptance:
      - 为所有墙体、楼板、屋顶和门窗指定材质
      - 在至少两个房间内布置家具
      - 在室内外关键位置添加照明
~~~

因此可以排除一个最初假设：

> 本次 Planner 的任务内容并没有在“模型输出 → Planner 节点 State”这个边界整体丢失。

更准确的调查方向应当变成：

> 这些已经进入 State 的内容，后续究竟由谁读取、怎样执行、怎样证明完成？

## 5. Trace 第二步：`steps` 和 `dynamic_tasks` 分别是什么

### 5.1 `execution_plan.steps` 描述固定节点

本次 Trace 中的 `steps` 类似：

~~~yaml
steps:
  - type: planning_research
    node: planning_research
  - type: architecture
    node: architecture
  - type: material_plan
    node: material_plan
  - type: skeleton
    node: skeleton
  - type: merge
    node: merge
  - type: final_validate
    node: final_validate
~~~

这些步骤与 `graph.py` 中已经存在的固定业务节点高度重合。

### 5.2 `execution_plan.dynamic_tasks` 描述本次需求

`dynamic_tasks` 描述的是这次“别墅”具体要做什么，例如：

- 功能布局与主体结构设计；
- 屋顶与竖向交通设计；
- 材料规划与内部配置；
- 建筑骨架生成；
- 门窗与建筑细部添加；
- 全面规范性校验与修正。

两者的语义区别是：

| 字段 | 回答的问题 | 当前是否被执行器调度 |
| --- | --- | --- |
| `steps` | 固定工作流运行到哪个节点 | 是 |
| `dynamic_tasks` | 本次用户需求具体要完成什么 | 否，不是逐条调度 |

### 5.3 执行器真正读取的是 `steps`

[`execution_plan_executor`](../../../wild-server/app/agent/planning/workflow.py) 的主要逻辑是：

~~~text
检查执行期间的新反馈
→ 判断 steps 中是否存在失败步骤
→ 判断 steps 是否全部完成
→ next_ready_step(plan)
→ 从 CAPABILITY_REGISTRY 校验 type 和 node
→ 把对应 step 标记为 in_progress
→ 通过 plan_next_node 返回下一节点
~~~

它不会逐条取出 `dynamic_tasks` 并执行其 objective 或 acceptance。

所以当前存在两套固定流程描述：

~~~text
graph.py 中的 LangGraph 节点和条件边
execution_plan.steps 中的节点、依赖与状态
~~~

`steps` 当前并非完全无作用，它承担调度、失败判断和完成判断；但它重复表达了 LangGraph 已经固化的节点顺序，形成了第二个流程事实源。

## 6. Trace 第三步：`dynamic_tasks` 是否被下游真正消费

### 6.1 architecture 和 material_plan 主要接收文本指导

[`execution_plan_phase_guidance`](../../../wild-server/app/agent/planning/execution.py) 会从 `dynamic_tasks` 中筛选相应 phase，然后把任务标题、目标和验收条件拼接成自然语言指导。

当前确认：

- architecture 会读取 architecture 阶段的 guidance；
- material_plan 会读取 material_plan 阶段的 guidance；
- guidance 主要作为 Prompt 内容影响模型。

这说明任务不是完全没有被使用，但目前主要是一种“软提示”：

~~~text
dynamic_tasks 中的自然语言
→ 拼接进 Prompt
→ 模型尝试遵循
~~~

它还不是程序能够直接校验的约束对象。

### 6.2 skeleton 没有直接读取对应 phase guidance

当前 skeleton 主要消费已经形成的 `architecture_plan` 和 `material_plan`，没有像 architecture、material_plan 一样直接调用 `execution_plan_phase_guidance()` 获取 skeleton 阶段任务。

这意味着 skeleton 阶段的“柱、梁、门窗、阳台或雨篷”等要求是否继续存在，依赖上游是否把它们完整转换进其他中间对象，而不是直接依据原始动态任务执行。

### 6.3 动态组件分发不以 `dynamic_tasks` 为权威输入

skeleton 完成后，组件分发主要读取：

- `suggested_components`；
- `design_brief.component_quota`；
- `user_message`；
- 已注册组件能力。

因此，“Planner 在动态任务中要求家具、照明或阳台”并不自动等于相应组件生成链一定会运行。

### 6.4 字段仍在 State 中不等于业务已经执行

这是本次 Trace 阅读得到的关键认识：

~~~text
下游输入仍包含 dynamic_tasks
≠ 下游代码读取了 dynamic_tasks
≠ 节点落实了其中的要求
≠ 最终结果通过了 acceptance
~~~

判断一个字段是否真正有价值，必须继续检查：

1. 节点代码是否读取；
2. 读取后是否转成明确决策；
3. 决策是否影响生成、归一化、筛选或组件派发；
4. 最终是否存在对应校验结果。

## 7. Trace 第四步：为什么任务会被标记为完成

### 7.1 当前按 phase 回写动态任务状态

业务节点由 `_planned_node()` 包装。节点返回后，`complete_execution_step()` 会把业务结果映射回计划状态，再由计划更新逻辑修改 `steps` 和 `dynamic_tasks`。

当前动态任务的状态更新主要按 phase 匹配，而不是逐条执行 acceptance。

例如本次计划中：

~~~yaml
task_1:
  phase: architecture
  title: 功能布局与主体结构设计

task_2:
  phase: architecture
  title: 屋顶与竖向交通设计
~~~

architecture 节点成功后，两条 architecture 任务都可能随 phase 一起被标记为完成。

同样：

~~~yaml
task_4:
  phase: skeleton
  title: 建筑骨架生成

task_5:
  phase: skeleton
  title: 门窗与建筑细部添加
~~~

skeleton 节点返回成功后，两条 skeleton 任务都可能被标记为完成，即使门窗、阳台或雨篷还需要后续组件链才能生成。

### 7.2 `completed` 当前更接近节点进度

在这种设计下，动态任务的 `completed` 实际更接近：

> 与该 phase 对应的固定业务节点已经运行完成。

它不能严格证明：

> 该任务下的每条 acceptance 都已在最终 Blueprint 中实现并通过检查。

当前把两种不同状态混在了一起：

| 状态 | 正确含义 |
| --- | --- |
| 节点运行状态 | architecture、skeleton 等代码是否执行完成 |
| 业务验收状态 | 家具数量、屋顶类型、组件存在性等要求是否满足 |

这也是为什么 Trace 中看起来计划顺利执行，但仍无法从状态直接证明具体业务要求已经完成。

## 8. Trace 第五步：对照最终结果验证状态含义

### 8.1 计划中明确存在的验收要求

本次 `dynamic_tasks` 中包含：

- 在至少两个房间内布置 table、chair 等家具；
- 在室内外关键位置添加 light；
- 至少添加一个 balcony 或 canopy；
- 生成必要的承重柱和联系梁；
- 门窗满足相应位置和局部坐标规则。

### 8.2 最终 Blueprint 能证明什么

本次 Trace 的最终 Blueprint 中可以看到：

- wall、floor、stair、roof 等主体元素；
- door、window 等组件；
- 最终固定校验错误数和警告数均为 0。

但没有找到足够证据证明以下计划要求已经落实：

- furniture；
- light；
- balcony 或 canopy；
- 计划中要求的柱和梁。

### 8.3 最终校验通过不等于计划验收通过

当前 `final_validate` 主要验证 Blueprint Schema、引用关系以及已实现的固定业务规则。

它没有逐条读取自然语言 `acceptance`，也没有形成类似下面的结果：

~~~yaml
acceptance: 至少两个房间包含家具
status: failed
expected: 2
observed: 0
validator: furniture_room_count
~~~

因此，本次结果中的“校验错误为 0”只能证明：

> 最终 Blueprint 通过了当前已经注册的固定校验规则。

不能进一步证明：

> Planner 提出的所有动态任务和验收条件均已完成。

## 9. 这次 Trace 是否执行失败或发生重试

本次提供的三个 Trace 文件属于同一个 Thread 的连续执行过程，中间停止在 `plan_review`、`design_review` 等位置主要是人工审核中断，而不是任务异常失败。

完整流程最终显示：

~~~yaml
status: complete
execution_plan_status: completed
plan_next_node: __end__
retry_count: 0
validation_errors: 0
validation_warnings: 0
~~~

其中 skeleton 出现过 `deterministic_fallback`，表示该节点使用了确定性降级结果，不等同于 callback 重试。

所以本次 Trace 暴露的问题不是“流程没有走到 END”，而是：

> 流程能够正常结束，计划也显示 completed，但当前状态和校验体系不能逐条证明动态任务已经实现。

这个现象比单纯执行失败更值得关注，因为它属于“表面成功但业务验收不完整”。

## 10. 具体子问题：批准约束没有进入 architecture 候选选择

最新 Trace 证明的是整个计划消费与验收链存在缺口。此前发现的 architecture 候选评分问题，是这个更大问题在单个节点内部的具体表现。

### 10.1 旧实测案例

一次 Plan Mode 测试中，已批准总体方案任务明确提出：

- 两层，层高均为 `3.0m`；
- 主体尺寸约 `12m × 8m`；
- `gable` 双坡屋顶；
- 出檐不小于 `0.5m`。

模型 reasoning 曾讨论这些要求，但最终候选为：

| 阶段 | 尺寸 | 屋顶 | 结果 |
| --- | ---: | --- | --- |
| 已批准计划 | 约 `12m × 8m` | `gable` | 作为文本进入 Prompt |
| reasoning 中间设想 | `12m × 8m` | `gable` | 只存在于思考流 |
| 候选 1 | `14m × 9m` | `flat` | 评分 118，最终被选择 |
| 候选 2 | `15m × 10m` | `gable` | 评分 118，未被选择 |

### 10.2 同一 architecture 节点内部的断点

[`architecture_planner`](../../../wild-server/app/agent/generation/architecture/workflow.py) 在 LangGraph 中只是一个节点，但内部还包含：

~~~text
读取 State
→ RAG 检索
→ 获取 architecture phase guidance
→ 构建 Prompt
→ 调用 LLM
→ 解析候选 JSON
→ 归一化候选
→ 候选评分与选择
→ 写入 architecture_plan
~~~

当前批准要求进入了模型 Prompt，但 `select_architecture_plan()` 的输入没有独立的批准约束对象。评分器主要能看到：

- 原始 `user_message`；
- `complexity_profile`；
- `architecture_profile`；
- 模型最终候选。

原始用户消息只有“生成一个别墅”时，只存在于批准计划中的尺寸和屋顶要求就无法稳定参与确定性评分。

两个候选同为 118 分时，Python `max()` 会选择第一个最高分候选。“同分取第一个”是错误候选胜出的直接机制，但根因仍是批准要求没有进入评分和选择契约。

### 10.3 它与最新问题的关系

二者不是两个无关问题，而是整体与局部的关系：

~~~text
整体问题
dynamic_tasks 没有被编译成全流程可消费、可验收的结构化要求

architecture 节点内的具体表现
批准要求只进入 Prompt，没有进入候选归一化、评分和选择
~~~

所以不能只修复“同分选择”，也不能只继续强化 Prompt。否则其他节点和最终验收仍然存在相同的信息断点。

## 11. 三种信息不能混为一谈

| 信息 | 当前载体 | 当前作用 |
| --- | --- | --- |
| 模型 reasoning | 运行时流式事件 | 帮助观察模型思考，不是业务状态 |
| 模型最终 content | 解析后的结构化对象 | 进入节点内部归一化和业务处理 |
| LangGraph State | `GenerationState` | 在节点之间传递已保存的业务数据 |

不需要把原始 Chain-of-Thought 写入 State。真正需要保存和传递的是经过明确提取、可以由程序消费和验证的业务决定。

因此，本次问题不能再表述为：

> 大模型的思考总结没有完整传给下一个节点。

更准确的表述是：

> Planner 的任务已经写入 State，但仍停留在自然语言计划层，没有形成贯穿生成、选择和校验阶段的结构化业务契约。

## 12. 当前问题的根因分层

### 12.1 流程职责层

LangGraph 已经定义固定节点和安全边界，`execution_plan.steps` 又保存并调度一次相同流程。

结果是：

- 图结构与计划步骤成为两个流程事实源；
- 阅读时难以快速区分真实节点、计划数据和工具函数；
- 固定节点进度与本次动态业务任务混在同一个计划对象中。

### 12.2 业务表示层

`dynamic_tasks` 中的 objective、acceptance 和 basis 仍是自然语言，缺少统一结构来表达：

- 目标业务对象；
- 期望值和允许范围；
- 硬约束还是软偏好；
- 由哪个节点消费；
- 由哪个校验器检查；
- 当前系统是否支持。

### 12.3 节点消费层

不同节点消费计划的方式不一致：

- 有的节点把 phase guidance 拼入 Prompt；
- 有的节点间接依赖上游结果；
- 组件分发依赖 `suggested_components` 和 `design_brief`；
- 候选评分和归一化未必接收已批准任务。

因此，无法从 `dynamic_tasks` 稳定追踪到实际负责落实要求的代码位置。

### 12.4 状态语义层

动态任务按 phase 更新状态，使“节点执行完成”和“业务验收完成”混为一谈。

当前 `completed` 缠绕了两种含义：

~~~text
固定工作流节点运行完成
本次动态任务验收通过
~~~

二者必须通过不同证据判断，但当前没有分离。

### 12.5 验收层

自然语言 acceptance 没有稳定 ID、检查函数、expected、observed 和证据引用。固定 Blueprint 校验也无法自动覆盖 Planner 临时提出的所有任务。

最终只能知道：

~~~text
工作流执行结束
Blueprint 通过现有固定校验
~~~

却不能回答：

~~~text
每条动态任务是否实现
每条验收条件为什么通过或失败
未检查和不支持的要求有哪些
~~~

### 12.6 追踪层

虽然 LangSmith 能展示完整 State，但当前字段还不能直接串起：

~~~text
原始任务
→ 结构化要求
→ 消费节点
→ 生成结果
→ 验收证据
~~~

因此 Trace 可以帮助人工发现问题，却还不能让程序自动证明任务完成。

## 13. 与已删除旧平面工作流的区别

旧平面设计链曾出现过：

1. 校验反馈已经存在于 State，但旧 `floor_*` 节点构建 Prompt 时没有读取；
2. 局部墙体或洞口错误触发整个 `spatial_plan` fallback。

它和当前问题拥有相似的抽象模式：

~~~text
上游已经产生重要信息
→ 后续步骤没有把它作为明确输入使用
→ 最终结果偏离上游决定
~~~

但旧平面节点已经从当前生产主链删除，不能再用旧修复证明当前问题已经解决。

当前问题发生在仍然存在的：

- ExecutionPlan；
- architecture；
- material_plan；
- skeleton；
- 动态组件分发；
- final_validate；
- 计划状态回写。

## 14. 已确认事实与证据边界

### 14.1 当前可以确认

- Planner 的 `summary + tasks` 已被写入 `execution_plan.dynamic_tasks`；
- 本次问题不是 Planner 到 State 的整体写入失败；
- LangSmith 中的节点输入主要展示累积后的完整 `GenerationState`；
- 字段存在于节点输入不等于节点实际消费；
- `execution_plan_executor` 调度的是 `steps`，不是逐条调度 `dynamic_tasks`；
- `steps` 与 LangGraph 的固定业务顺序存在重复；
- architecture 和 material_plan 会把部分 phase guidance 放入 Prompt；
- skeleton 没有直接消费 skeleton phase guidance；
- 组件分发不以原始 `dynamic_tasks` 为直接权威输入；
- 动态任务当前会按 phase 批量更新状态；
- 自然语言 acceptance 没有被逐条编译成确定性验收；
- 本次 Trace 最终正常结束，`retry_count=0`；
- 最终固定校验通过，但不能证明所有动态业务要求均已满足；
- architecture 候选评分未稳定接收只存在于批准计划中的约束。

### 14.2 当前不能直接断言

- 所有生成请求都会遗漏动态任务；
- Planner 提出的每条任务都应无条件执行；
- 模型自行补充但未经用户确认的设计假设等同于用户硬约束；
- reasoning 越长，最终结果就越差；
- 把 reasoning 保存进 State 就能解决问题；
- 只修改 Prompt 就能形成可靠业务闭环；
- 只删除 `steps` 就能解决动态任务消费和验收问题；
- 当前所有 acceptance 都能直接转成确定性校验；
- `deterministic_fallback` 就等同于执行重试或流程失败。

## 15. 后续解决必须能够证明什么

本文件不提前限定具体代码方案，但后续优化至少需要通过测试证明：

1. LangGraph 与计划数据不再维护两套可能冲突的固定节点顺序；
2. 每条已批准动态任务都能获得明确的处理结果；
3. 可支持的要求能被转换成节点可消费的结构化形式；
4. 无法理解、未支持或无需执行的要求会显式标记，而不是静默丢失；
5. architecture、material_plan、skeleton 和组件生成能读取属于自己的业务要求；
6. 归一化、候选评分和选择仍然受到已批准硬约束限制；
7. 固定节点运行进度与动态业务验收状态能够区分；
8. 任务不能仅因为相同 phase 的节点运行完成就被判定为完成；
9. 每条必需 acceptance 都有通过、失败、未检查或不支持等明确结果；
10. 最终 Blueprint Schema 合法但业务要求失败时，系统不会宣告全部任务成功；
11. LangSmith 能从动态任务追踪到消费节点、结果对象和验收证据；
12. 使用本次家具、照明、阳台或雨篷、柱和梁等要求建立回归样例；
13. 使用旧 `12m × 8m + 两层 + gable + 出檐` 案例验证批准约束参与候选选择；
14. 增加不带额外批准约束的普通生成反例，证明优化没有破坏原流程。

## 16. 当前阶段的一句话总结

学习和面试时，可以先这样概括当前问题：

> 我通过 LangSmith 对照 Planner 原始输出、LangGraph State、节点消费代码和最终 Blueprint，发现问题并不是模型计划没有写入 State，而是自然语言动态任务没有被编译成下游可执行、可验收的业务约束。当前 `execution_plan.steps` 重复调度 LangGraph 已固定的节点顺序，动态任务又会按 phase 随节点运行被批量标记完成，导致系统可能出现“工作流正常结束、固定校验通过，但计划中的具体业务要求没有得到逐条证明”的规划—执行失配。
