# 能力闸门：从"硬阻断"改为"只标记不阻断"

> 文档性质：记录"计划校验直接终止整轮生成"的根因定位，以及阻断政策的两次收紧。
>
> 触发（第一次）：`生成一份明确的建筑平面草图，标注出主楼的宽度、进深尺寸（例如：宽约12米，深约10米）`
> 在 `plan_validator` 被判定为"当前 Agent 能力无法执行"，整轮生成以 `__end__` 结束。
>
> 触发（第二次）：`建筑主体为两层矩形体量（约10x12米），附带一个一层矩形车库体量（约6x6米）`
> 等四条验收条件因句中含"车库"被整体阻断。
>
> 日期：2026-09-17。状态：已落地。
>
> **最终政策（§7）**：能力缺失一律只标记不阻断；只有**计划对象本身不合法**和
> **模型服务终态错误**才允许终止一次生成。

---

## 1. 现象与最初误判

Agent 模式下的报错是：

```text
执行计划校验失败：当前 Agent 能力无法执行：生成一份明确的建筑平面草图，标注出主楼的宽度、进深尺寸（例如：宽约12米，深约10米）
```

报错文本由 [`execution_plan_validator`](../../../wild-server/app/agent/planning/workflow.py) 拼出：

```python
"error": (
    "执行计划校验失败：" + "；".join(issue["message"] for issue in issues[:6])
    if issues
    else None
),
```

这个函数只是**上报点**，不是判定点。真正的判定在上游
[`_compile_acceptance`](../../../wild-server/app/agent/planning/requirements.py)：
它把这条 acceptance 编译成 `support_status="unsupported"`，
再由 [`validate_structured_requirements`](../../../wild-server/app/agent/planning/requirements.py)
输出 `unsupported_plan_requirement`。

**结论：凡是"能力边界"类报错，先看 `requirements.py` 的编译分支，不要从 validator 往下查。**

---

## 2. 原实现的两个缺陷

### 2.1 把一个关键词表当成两种完全不同的语义

原代码只有一处判定：

```python
if _contains_any(text, ("房间位置", "房间布局", "功能分区平面", "平面草图", "内部隔墙")):
    ... support_status="unsupported"
```

它把两类语义混成了一个"不可执行"：

| 语义 | 例子 | 系统真实能力 | 正确处置 |
| --- | --- | --- | --- |
| **能力真缺失** | 房间位置、房间布局、功能分区平面、内部隔墙 | 主链不设计内部空间，无房间坐标、无隔墙 | 硬阻断：模型写进计划也没人能实现 |
| **能力真缺失（场地语义）** | 车库、后院、花园 | 不作场地/环境语义处理 | 当时判硬阻断，**§7 已改为不阻断** |
| **交付媒介不一致** | 平面草图、平面图、二维平面 | 不产出 2D 平面图，但体量/立面/尺寸由 `design_review` 的 SVG 预览与 `DesignDocument` 呈现 | **降级为人工确认**，不终止整轮 |

"出个平面草图"只是顺口描述交付形式，把它等同于"要求系统做内部空间设计"，
代价是整轮生成被杀掉——收益（提醒用户）远小于损失（无法交付）。

> 注：本节的"能力真缺失 → 硬阻断"只维持了半天。第二次触发后（§7）连这一类也不再阻断。

### 2.2 尺寸只认 `a×b` 一种写法

原抽取逻辑是一条正则：

```python
re.search(r"(\d+(?:\.\d+)?)\s*(?:m|米)?\s*[×xX*]\s*(\d+(?:\.\d+)?)", text)
```

`宽约12米，深约10米` 这种自然语言表述落不进 `architecture_dimensions`，
于是句子里明明给了尺寸，却没有任何可判定的量化要求。

## 3. 分级设计：severity 决定能否终止整轮

引入两级语义（`RequirementSeverity` 已存在于 `contracts.py`）：

| 级别 | 典型来源 | 含义 | 去向 |
| --- | --- | --- | --- |
| `error` | 计划结构问题、模型服务终态错误 | 这份数据本身不合法，放过去下游必然崩 | `plan["status"]="failed"` → `__end__` |
| `warning` | 能力缺失、交付媒介不一致、纯主观验收 | 照常生成，把差异写进验收结果供人看 | `plan["status"]="reviewing"` → `plan_review` 中断 |

本节最初把"能力缺失"放在 `error` 一侧，**§7 已改到 `warning` 一侧**；
`severity` 作为唯一阻断杠杆的设计保持不变。

关键点：**`needs_review` 不通过 `validate_structured_requirements` 重复上报**。
它已经由 [`initialize_acceptance_results`](../../../wild-server/app/agent/planning/requirements.py)
转成 `status="not_checked"`，出现在计划审核面板的 `acceptance_results` 里。
同一信号两个来源只会让审核者困惑——所以校验器只报结构问题与 `unsupported`
（后者是"事实声明"，用户需要知道哪条要求没被满足）。

## 4. 落地改动

### 4.1 `app/agent/planning/contracts.py`

`PlanValidationIssue` 增加可选字段：

```python
severity: NotRequired[RequirementSeverity]  # error 终止本轮；warning 仅展示并交人工
```

省略时按 `error` 处理，既有调用方语义不变。

### 4.2 `app/agent/planning/requirements.py`

1. 关键词表按语义拆分：

   ```python
   _UNSUPPORTED_INTERIOR_TERMS = ("房间位置", "房间布局", "功能分区平面", "内部隔墙")
   _UNSUPPORTED_SITE_TERMS = ("车库", "后院", "花园", "garage", "backyard", "garden")
   _PRESENTATION_MEDIUM_TERMS = ("平面草图", "平面图", "二维平面", "2d 平面", "2d平面")
   ```

2. 尺寸抽取升级为 `_extract_plan_dimensions(text)`，支持两种写法：

   | 正则 | 匹配样例 |
   | --- | --- |
   | `_PLAN_DIMENSION_PAIR` | `12×10`、`12x10`、`12*10` |
   | `_PLAN_WIDTH_DEPTH_PAIR` | `宽12米，深10米`、`宽度约12米、进深约10米` |

   并加**示例值豁免**：紧邻尺寸前的文本以 `_ILLUSTRATIVE_LEADS`
   （`例如` / `比如` / `示例` / `如` / `（如` 等）结尾时跳过该组数字。
   `例如：宽约12米，深约10米` 只是说明量级，不能变成 `near` 硬判定——
   否则模型按示例写 12×10、归一化算出 14×9，验收会判失败并阻断交付。

3. **判定顺序**：媒介降级分支放在**所有量化抽取分支之后**。
   句子里只要给出了层数、尺寸、屋顶或构件等可执行指标，就按指标编译，
   不再按媒介判级。这样 `绘制建筑平面图，主楼宽12米，深10米` 得到的是
   `architecture_dimensions`（可判定），而不是一句"要平面图"的警告。

### 4.3 `app/agent/planning/workflow.py`

`execution_plan_validator` 只把 error 计入失败：

```python
blocking = [issue for issue in issues if str(issue.get("severity") or "error") != "warning"]
plan["valid"] = not blocking
plan["status"] = "reviewing" if not blocking else "failed"
```

`execution_plan_validation` 仍然返回**全部** issues（含 warning），
供审核面板展示；`error` 文本只拼接 blocking 项。

### 4.4 `app/api/ws_agent.py`

`plan_validator` 的步骤状态同步分档，避免一条提示就把步骤标红：

```python
if blocking:          summary = f"{len(blocking)} 个阻断问题"        # 步骤 error
elif issues:          summary = f"校验通过，{len(issues)} 条提示待人工确认"  # 步骤 done
else:                 summary = "任务、要求与能力边界校验通过"
```

## 7. 最终政策：能力缺失一律不阻断（2026-09-17 第二次调整）

第一次调整（降级"媒介不一致"）落地后，用户在 Agent 模式立刻撞到第二次：

```text
执行计划校验失败：当前 Agent 能力无法执行：建筑主体为两层矩形体量（约10x12米），
附带一个一层矩形车库体量（约6x6米）；……车库位于主楼侧翼；……
```

四条验收条件**全部只因为句中含"车库"**被判 `unsupported`。

### 7.1 用户给出的产品原则（原文）

> "就让他正常生成就行，只要他能生成出蓝图文件就可以……就算他没有能力生成车库也没关系……
> 为什么要有阻断呢？这个阻断会导致他无法生成……只要他能正常生成的话，他能够生成出蓝图文件就可以。"

这条原则是对的，理由是**失败模式的代价不对称**：

| 处置 | 结果 |
| --- | --- |
| 阻断 | 用户**一张图都拿不到**，而且要在报错里读一段能力声明 |
| 不阻断 | 用户拿到一栋楼；缺的能力写在验收结果里，人工审核时看得见 |

原来那套设计的**初衷**没错——"不能把模型写的计划静默显示为 completed"。
问题是它把**诚实**实现成了**终止**：要求被标记出来了，代价是整轮归零。
诚实与终止本来就是两件事，不该用同一个杠杆。

### 7.2 落地

`severity` 保持不变仍是唯一杠杆，只是把"能力缺失"挪到 `warning` 一侧：

| 改动点 | 内容 |
| --- | --- |
| `_compile_acceptance` | 三条 `unsupported_capability` 分支补 `severity="warning"` |
| `validate_structured_requirements` | `unsupported` 的 issue 沿用要求自身的 severity，不再写死 `error` |
| `prompts/planning.py` 第 6 条 | 补一句"服务端会标记但不会因此终止本轮"，避免 Planner 为了绕开它而改写或重复表述用户要求 |
| `app/agent/README.md` | 同步"两者都只标记不阻断" |

**保留阻断的两类**（都不属于"能力"问题）：

1. **计划对象本身不合法**——缺字段、ID 重复、节点被篡改、动态任务引用不存在的依赖。
   放过去下游必然崩，这是数据损坏而不是能力不足。
2. **模型服务终态错误**——没有任何东西可以生成。

### 7.3 验证

`.workbuddy/diag/check_no_block_2026-09-17.py` 用用户原话四条验收条件跑完整链路：

```text
四条 → 全部 [warning] unsupported_capability / target=architecture.semantic_space
计划校验 → issues=4  blocking=0
交付阶段 → 来自"缺能力"的阻断项：无
真实节点 → execution_plan_status = reviewing
          error                 = None
          路由                  = plan_review
```

即：报错消失了，四条要求以提示形式进入人工审核，生成继续。

新增回归 `tests/agent/test_execution_plan.py::test_unsupported_capability_never_blocks_delivery`
钉住"不卡校验、不卡任务完成、不卡交付"三件事。

## 8. 遗留：`车库` 该不该留在"缺能力"表里

实证脚本 `.workbuddy/diag/check_garage_volume_2026-09-17.py` 给出一份
`主体 10x12（两层）+ 车库 6x6（一层）+ L 形相连 + hip 屋顶` 的方案，
让引擎真实跑确定性骨架，结果：

```text
floor_1_main / floor_1_garage          ← 车库体量有自己的楼板
wall_right_1_1 / wall_right_1_2        ← 一层墙按 L 形缺口分段
wall_back_1_1  / wall_back_1_2
二层只剩 wall_front_2 / right / back / left ← 车库只有一层，二层收窄，正是要的形状
stair_1_2                              ← 主楼竖向交通
```

**结论：引擎能建出车库体量**，`volumes` 的 `role=secondary` + `x/z` 偏移 +
`start_floor/end_floor` 完整支持"两层主楼 + 一层附属体量"。
把"车库"整体标成缺能力，是**不准确的**（缺的只是车库语义：车库门、坡道、地面坡度）。

> 判据修正（2026-09-17）：该脚本原先用"墙 id 里含 `garage`"作为判据，
> 因此一直误判为"建不出"——骨架其实是用**墙环开缺口**表达附属体量的。
> 现已改为三条证据：`floor_1_garage` 存在、一层墙环被切分（>4 段）、
> 二层墙环不切（4 段）。修正后变体 A/B 均判定可建，脚本退出码 0。

**但暂时不能直接从关键字表里删掉**，因为会踩一个更深的坑：

```python
# requirements.py::_check_requirement
if validator == "architecture_dimensions":
    massing = architecture_plan.get("massing", {})
    observed = {"width": massing.get("width"), "depth": massing.get("depth")}
```

`architecture_dimensions` 比对的是 `massing.width/depth`，即**总轮廓**，
而用户嘴里说的是**主体尺寸**。"主体 10x12 + 车库 6x6" 的正确 L 形方案
总轮廓是 16x12；一旦这条被编译成 `architecture_dimensions = 10×12`，
验收必然不通过 → **把"事前阻断"变成"事后阻断"，比现在更糟**（白跑一轮仍拿不到蓝图）。

**前置条件**：先在结构化要求里把"主体尺寸"和"总轮廓尺寸"分开表达
（例如 `architecture.massing.floors` 之外再引入主体/附属体量的区分），
才可以把"车库"从缺能力表里移出。在那之前，它保持"标记但不阻断"，代价可接受。

## 9. 可复用的判断准则

> 判断一次生成该不该被终止时，问的是：
> **是这份数据本身坏了（下游会崩），还是只是能力不足 / 表述不一致？**
> 只有前者配终止。后者一律标记 + 继续。

这条准则的两面教训：

1. **不要用"终止"来表达"诚实"。** 想让用户知道某条要求没被满足，
   正确做法是把它写进验收结果，不是让整轮生成归零。
   失败的代价是不对称的：标记错了用户还能用产物，终止错了用户什么都没有。
2. **关键词判定表要按语义分表。** 本项目先后把三类不同语义
   （缺能力 / 交付媒介不一致 / 主观验收）堆进同一个 `_contains_any`，
   结果每次都得靠用户撞报错才发现分类错了。

## 10. 连带缺陷：验收编译的"量词盲区"（2026-09-17 16:41，已修）

第 7 节把"能力缺失"放开了，但同类事故换了个入口又发生了一次：
**引擎真做得到的事情，被验收编译读错意思后判死。**

### 10.1 现象

任务 `req_1789634516108_eu82yreb4`（用户只输入"生成一个别墅"）报：

```text
错误: 业务验收未通过：实际数量：{'door': 1, 'window': 13, 'roof': 1}
[1] ~ [10.2] 全部 20 个结构校验器【全部通过】
```

合并也是成功的。从持久化检查点取真实状态：

```text
merged_blueprint      = dict（23 个元素）      ← 蓝图早就合并出来了
final_blueprint       = None                  ← 被丢弃
execution_plan_status = failed
material_plan.roles   = 9 个
```

### 10.2 死因链

计划里 task_4 的验收原文是：

> 材质方案包含墙体、屋顶、门窗**至少3种**材质

语义是"材质至少 3 **种**"。但 `_compile_acceptance` 的**构件分支**先命中，
把它编译成：

```json
{"types": ["door", "window", "roof"], "minimum": 3}
```

即"门、窗、屋顶**每种至少 3 个**"。实际 `door=1`、`roof=1` → `failed`
（`severity=error`）→ `blocking_acceptance_failures` 命中 →
`workflow.py` 把 `final_blueprint` 置 `None`，23 个元素随判决一起消失。

根因在 `_minimum_count`：**它只认「至少N」，不区分量词。**

| 输入 | 修复前 | 应为 |
| --- | --- | --- |
| 至少3**种**材质 | 3（种类数被当成实例下限） | 不构成实例下限 |
| 至少3**个**窗户 | 3 | 3 ✓ |
| 不**少于**6个 | 1（完全不认） | 6（本轮未改，见 10.5） |

### 10.3 三个相互叠加的子缺陷

| 级别 | 子缺陷 | 说明 |
| --- | --- | --- |
| 🔴 | **量词盲区** | 「种/类/款/类型」数与「个/扇/面」数不是一回事 |
| 🔴 | **材质没有编译分支** | `validator="material_plan_exists"` 在全仓**无任何分支产出**，是死代码；且它只判 `roles>0`，不读 `expected.minimum`。所以"材质要求"只能被构件分支抢走 |
| 🟡 | **数量词不绑定名词** | 全句抓「至少N」后统一套到所有匹配类型，而不是只约束它修饰的那个名词（本轮未改） |

### 10.4 落地改动

`app/agent/planning/requirements.py`：

1. **量词感知**：`_quantified_minimum` → `(数量, 是否种类量词)`；
   `_minimum_count` 遇到种类量词退回 1（不设实例下限）；
   新增 `_minimum_kind_count` 取种类下限。长量词必须排在短量词前
   （`类型` 要先于 `类`，否则被 `类` 吃掉）。
2. **材质分支前置**：新增 `_MATERIAL_TERMS`，在**构件分支之前**判定
   「材质词 + 种类量词」→ `kind="material_role_count"`、
   `validator="material_plan_exists"`、`expected={"minimum": N}`。
3. **`material_plan_exists` 支持下限**：`observed >= expected["minimum"]`，
   缺省 1（与旧行为 `roles > 0` 完全等价）。
4. 顺带把两处与新政策矛盾的文案（"当前系统不支持该要求"）改成
   "当前 Agent 不具备该能力，将按可达范围生成并在交付结果中标记"。

**分支优先级是这里的核心教训**：更具体的语义（材质）必须排在更泛的分支
（构件）之前。这与第 2 节「媒介降级分支必须放在量化抽取之后」是同一个规律的
两个方向——都是"谁先命中谁定义语义"，而命中顺序是被写死的。

### 10.6 仍然遗留（需要产品决策，未动手）

1. **「不少于/不低于N」不认**，整条要求会掉进 `phase_outcome` 兜底，
   退化成"检查某产物存在"，**永远通过**。事故那次计划里的
   「窗户数量不少于6个」「墙体数量不少于8面」都是这个下场。
   之所以本轮不改：补上它会把"永远通过"变成"可能失败"，
   **新增阻断点**，与第 7 节政策方向相反，需要先确认口径。
2. **数量词不绑定名词**：`至少3个` 会同时约束句子里所有匹配到的类型。
3. **验收失败仍会丢弃 `final_blueprint`**（`workflow.py` 的
   `payload["final_blueprint"] = None`）。这是第 7 节政策只覆盖了
   "编译期阻断"、没覆盖"交付期判死"的缺口——蓝图已经产出，
   却因为一条验收判定被扔掉，与"拿到不完整的结果好过什么都拿不到"冲突。

### 10.7 事故暴露的方法论缺口

**第 7 节的四道验证全绿，这次事故依然发生。** 原因不是验证不够多，
而是验证的**输入**选错了：四道验证用的都是我们**自己构造的**验收文本，
而线上崩的是 **LLM 自己写的**验收文本。

> 教训：验收编译器的回归输入必须来自**真实运行的计划**，
> 不能只喂手写的样例。持久化检查点里躺着每一次真实运行的
> `structured_requirements` 与 `acceptance_results`，
> 那才是回归集的正确来源。
