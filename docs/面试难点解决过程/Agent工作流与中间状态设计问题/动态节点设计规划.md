## 〇、v1 为什么失败，v2 换掉了什么问题

### 0.1 v1 的死结

v1 问的是"**怎么在运行时创建节点**"。LangGraph 的硬约束是节点集必须在 `compile()` 之前确定，运行时只能动态选路由目标。于是 v1 退回到预注册白名单 `NODE_REGISTRY`：11 类构件的 `generate` / `merge` 展开后是二十多个图节点，全部提前写死。**"动态创建节点"最后变成了"事前列举所有节点"**——和现状 `graph.py:308-318` 那句 `for cfg in implemented: add_node(f"{ct}_gen")` 是同一个东西，只是把固定边换成了条件边。

后果是加一个新构件仍然要改代码：v1 的"新增构件六步清单"里第二步就是"注册节点"。它把分支从 `if component_type ==` 搬到了注册表，没有消灭分支。

### 0.2 v2 换掉的提问

v2 不再问"运行时有哪些**节点**"，改问"运行时有哪些**工作项**"。

工作项是数据，不是拓扑。图（谁按什么顺序调用谁）固定不变；变的是 `plan` 这一串条目。这就像解释器与程序的关系：**解释器是固定的一小段代码，程序是无限的数据。** 要支持新的构件类型，是写一段新"程序"（数据），不是给解释器加指令。

| | v1 | v2 |
| --- | --- | --- |
| 动态对象 | 节点（拓扑） | plan 条目（数据） |
| 图规模 | 11 类构件 × 2 角色 ≈ 25+ 节点，随构件增长 | 固定 5 个业务节点，不随构件增长 |
| 加新构件 | 加注册项 + 加图节点 | 加数据（知识 + 策略），不改图 |
| LangGraph 约束 | 直接冲突，只能退回白名单 | 不受影响（节点集从不变化） |
| 分支位置 | 从 `if` 搬进注册表 | 从 `if` 搬进数据 |

### 0.3 代价，先说清楚

把动态性放进数据，代价是 **`execute` 必须变成一个通用执行器**：它要按条目里的 `op` 分派到固定的一小撮处理器。这带来一条新的纪律——**`op` 是闭集（新增 `op` 属于架构变更），`kind` 是开集（新增 `kind` 只是数据变更）**。整份文档的可实现性就压在这条分工上。

## 一、目标流程

### 1.1 拓扑

```
classifier ─┬─ chat   → END
            ├─ edit   → patch → END
            └─ generate
                 → architecture        （方案设计：DesignDocument）
                 → design_review       （★ 唯一人工中断点：审设计图纸）
                 → skeleton            （骨架设计：主体蓝图 + 设计清单）
                 → plan                （产出 plan 条目列表）
                 → ┌───────────────────────────┐
                   │  execute ──→ replanner ──┐│
                   │     ↑                    ││
                   │     └── 还有待办条目 ─────┘│
                   └───────────── 没有待办 ─────┘
                 → final_validate → END
```

- 循环体只有 `execute` 和 `replanner` 两个节点，靠条件边回边。
- `execute` 每轮执行**一条**条目；`replanner` 每轮判断"还有没有下一条"。
- 循环里**没有**动态节点创建，只有固定节点 + 数据驱动的处理器。

### 1.2 五个业务节点的职责

| 节点 | 职责 | 调模型 | 产出 | 现状对照 |
| --- | --- | --- | --- | --- |
| `architecture` | 方案设计：体量、层数、立面、构件配额、材质角色、槽位 | ✅ | `design_document` / `resolved_design` / `design_brief` 前身 | `architecture` + `material_plan`（见 §1.3） |
| `skeleton` | 骨架设计：主体蓝图（墙 / 楼板 / 屋顶 / 楼梯）+ 设计清单（`facade_plan` / `component_quota` / `opening_slots`） | ✅ | `skeleton_blueprint` / `design_brief` / `skeleton_summary` | `skeleton` 节点，基本不动 |
| `plan` | 把"还差什么"展开成条目列表，并做结构校验 | ✅（定策略）+ 程序（定条目） | `plan` | 取代旧 `planner` + `structured_requirements` 编译链 |
| `execute` | 取一条待办条目，按 `op` 分派执行 | 视 `op` 而定 | 片段 / 蓝图改动 / 条目结果 | 取代 `{ct}_gen` / `{ct}_val` / `merge` |
| `replanner` | 对账、判定是否继续、必要时追加条目 | 默认不调（异常时才调） | `plan` 的状态更新 / 追加 | 取代 `callback` + `merge` 的收尾判定 |

**保留不动的**：`classifier`（意图分类）、`chat`、`patch`（编辑路径）、`final_validate`（确定性全量校验）。这四处与新链无关，改造时不要顺手重构。

### 1.3 `material_plan` 的归并（唯一的可回退点）

`DesignDocument.decisions.materials` 已经带 `resolved_plan` 字段，`review_outcome.py` 的 `_resolved_material_plan` 也是优先读它。因此**材质解析不再需要独立节点**，降级为 `architecture` 内部的一次确定性调用（`resolve_material_plan` 算子原样保留）。

若实测发现资产匹配需要独立的检索轮次，允许把 `material_plan` 保留为第 6 个节点——这是本次节点收敛中**唯一**的可回退点，其余四个节点不可拆。

### 1.4 一条请求的完整时序（例子：两层小别墅，前后立面开窗，带阳台）

1. `classifier` → `generate`
2. `architecture` → `DesignDocument`（体量 12×9、两层、gable 屋顶、配额：window 6~8、balcony 1~2、railing 0~1……）
3. `design_review` → **中断**，前端出 SVG 图纸；用户点批准
4. `skeleton` → 主体蓝图（`wall_n_1` / `wall_s_1` / `floor_1` / `roof_1` / `stair_1`）+ `design_brief`（`facade_plan`、`component_quota`、`opening_slots`）
5. `plan` → 程序按清单展开 12 条条目（见 §2.2 示例）
6. 循环：
   - `execute` 取 `it_001 generate window（host=wall_s_1）` → 一个模型调用产出该墙全部窗片段
   - `replanner` 对账 → `it_001` done，还有待办 → 回 `execute`
   - `execute` 取 `it_002 merge window` → 确定性并入蓝图
   - ……如此反复，直到条目耗尽
   - 中途某条 `generate balcony` 失败 → `replanner` 调一次模型，追加一条 `repair` 条目（`origin=emergent`）
7. `final_validate` → 13 件套校验 + 引擎重建 → 交付（清单里逐条列出未支持项）

## 二、plan 与 state：新的核心数据契约

### 2.1 为什么叫"条目"而不是"节点"

条目是**数据**，因此可以自由增删改；节点是**拓扑**，因此必须提前确定。整份方案的目的就是把"想知道下一步做什么"这件事，从拓扑层面挪到数据层面。

### 2.2 PlanItem 字段契约

```jsonc
{
  "id": "it_003",                       // 确定性生成：{op}_{kind}_{序号}
  "op": "generate",                     // 闭集，见 §2.3
  "kind": "window",                     // 开集，来自能力清单，见 §2.4
  "target": {                           // 作用对象：程序可解析的引用
    "host_wall": "wall_s_1",
    "source_slots": ["slot_win_1", "slot_win_2"]
  },
  "params": { "subtype": "casement" },  // 算子特有参数，由程序校验
  "depends_on": ["it_001", "it_002"],   // 依赖的条目 id
  "origin": "plan",                     // plan（计划内）| emergent（replanner 追加）

  // ── 两个状态字段，语义不混（见 §2.6、§2.8）──
  "status": "pending",                  // 计划态：pending|ready|blocked|done|skipped|unsupported
  "run": {                              // 执行态：本轮执行的事实记录
    "state": "idle",                    // idle|running|succeeded|failed|aborted
    "attempts": 0,
    "artifacts": [],                    // 产物引用（片段 id / 蓝图元素 id）
    "evidence": ""                      // 程序写的证据，模型不得写
  }
}
```

`PlanDocument`（存进 `state.plan`）：

```jsonc
{
  "schema_version": "plan/1.0",
  "revision": 1,              // replanner 每次追加/失效条目时递增
  "budget": { "llm_calls": 12, "iterations": 5 },
  "items": [ /* PlanItem */ ],
  "history": []               // 每轮的 status diff 摘要，用于前端与审计
}
```

### 2.3 `op` 闭集（五个动词，不多不少）

| op | 语义 | 执行者 | 调模型 | 输入数据 | 产出 |
| --- | --- | --- | --- | --- | --- |
| `generate` | 产出一个 WILD 片段（构件） | 生成处理器 | ✅ | `kind` + 宿主几何 + 槽位/配额 + 知识 | 片段（state 的 `component_fragments`） |
| `merge` | 把片段确定性并入蓝图 | 合并处理器 | ❌ | 片段引用 + 目标宿主 | 更新后的蓝图（幂等） |
| `validate` | 跑指定的一组校验器 | 工具 | ❌ | 校验器名列表 | 问题列表（写回条目状态） |
| `fix` | 跑指定的确定性修复算子 | 工具 | ❌ | 算子名 | 蓝图改动 + 审计记录 |
| `repair` | 模型出白名单修复动作，程序执行 | 修复处理器 | ✅ | 失败切片 + 已通过 id 黑名单 | 蓝图改动（受白名单约束） |

三条纪律：

1. **不要新增第六个 `op`**。"这件事不知道该归哪个 op"的时候，先判断它属于哪一类：能一次模型调用产出的 → `generate`；纯几何并入 → `merge`；能判定的 → `validate`；能机械改的 → `fix`；要模型判断怎么改 → `repair`。现有 `_PLANNED` 式的"资源解析""样式选择"等需求一律折进 `generate` 或前移到 `architecture`。
2. **`op` 的处理器数量恒定**。图节点数 = 5 + classifier/chat/patch/final_validate，与构件类型数量完全解耦。
3. **需要模型判断但不产出几何的场合**（例如"这些墙里哪面适合开门"）**不要新造 op**：它是 `architecture` 或 `plan` 阶段的职责，硬塞进循环只会让每轮成本不可控。
4. **每个 op 的处理器形态与可用工具集是固定的**：`generate` / `repair` 走工具型处理器（模型 + 有界工具循环），`merge` / `validate` / `fix` 纯确定性。展开见 §4.7–§4.12。

### 2.4 `kind` 是开集：数据从哪来

`kind` 的取值来自**知识库的能力清单**（`doc_type=component` + `knowledge_role=capability` 分片），当前对应 11 类已实现构件（door / window / roof / railing / canopy / balcony / light / ramp / bay_window / cornice / chimney）。

- 程序侧不维护 `kind` 白名单常量：判断"某 kind 能不能做"的依据是知识库里有没有这个分片。
- **当前代码里的 per-type 静态规则必须下沉进知识库**：`components.py` 的 `_COMPONENT_RULES`（11 段）与 `ComponentConfig.extra_rules`、`prompts/generation.py` 的 `_COMPONENT_LABELS`。否则 `execute` 的通用提示词里没有字段约束，生成质量会掉——这是 P2 的关键任务，不是可选项。

### 2.5 条目粒度：`(kind, host_wall)` 分组，不是一槽位一条

门窗按槽位逐条会变成几十次模型调用。**一组的粒度是 `(op, kind, host_wall)`：一次调用产出该组全部槽位的片段。** 组内只剩一个槽位时自然退化为单元素批。

对账仍到槽位级：`target.source_slots` 记录该组覆盖哪些槽位，条目的 `evidence` 里列出实际落地的槽位 id，未落地的槽位进交付清单。

### 2.6 两个状态机：计划态与执行态分开，"谁写状态"一节定死

一个字段同时表达"这件事要不要做"和"这次跑成没跑成"，就会出现"状态说不清"的老问题。因此拆成两个：

**计划态 `status`（replanner 与 `plan` 阶段写，表达"这事怎么处置"）**

| status | 含义 | 谁写入 |
| --- | --- | --- |
| `pending` | 待办 | `plan` 展开 / `replanner` 追加 |
| `ready` | 依赖已满足，下一轮可执行 | `replanner` |
| `blocked` | 依赖未完成或已失败 | `replanner` |
| `abandoned` | 重试耗尽 / replanner 判定无法完成（进交付清单） | `replanner` |
| `done` | 产物已产出**且**已并入蓝图并对账通过 | `replanner` 的 `reconcile` |
| `skipped` | 被 replanner 判定不再需要（记入交付清单） | `replanner` |
| `unsupported` | 能力缺失（无知识分片 / 无执行路径） | `plan` 阶段判定，或 `replanner` 兜底 |

**执行态 `run.state`（`execute` 写，表达"这一次跑的结果"）**

| run.state | 含义 | 谁写入 |
| --- | --- | --- |
| `idle` | 尚未执行过 | `plan` 展开 |
| `running` | 本轮正在执行（含模型重试） | `execute` |
| `succeeded` | 本轮产出了产物 | `execute` |
| `failed` | 本轮失败，`attempts` 已 +1 | `execute` |
| `aborted` | 因模型服务故障等终止，不再重试 | `execute` |

**两条硬规定**：

1. **模型不得写任何一个状态字段**。计划态只由 `reconcile` 与 `plan` 阶段的结构判定写入，执行态只由 `execute` 写入。这条直接承接《当前遇到的问题.md》§7 的老问题——"节点跑完 ≠ 业务要求完成"：`execute` 说 `succeeded` 不算数，产物不存在、或存在但没并进蓝图，计划态都不会变成 `done`。
2. **`run.state=failed` 不是终态**：它只表示"这一轮失败"，`status` 仍可能是 `ready`（还有重试额度）。终态只由 `reconcile` 判定：`done` / `abandoned` / `skipped` / `unsupported`。这条区分是 §5.4"无进展检测"能工作的基础。

> 这个拆法不是自创。Claude Code 的任务系统里 `TaskState`（后台进程监管：`pending|running|completed|failed|killed`）与 TodoV2（模型自己的待办看板：`pending|in_progress|completed|deleted`，带 `blocks/blockedBy/owner`）是两套字面量不共享的体系，混淆它们是读源码的第一道坑（《深入 Claude Code 源码》第 16 章 §1.2 / §三点五）。

### 2.7 plan 的类型化校验

`plan` 节点产出的条目列表必须过 Pydantic 模型 + 五项结构校验，不通过不许进入循环：

1. `op` ∈ 闭集；2. `kind`（若该 `op` 需要）在知识库有分片；3. `target` 里的引用（`host_wall` / 宿主 id / 槽位 id）在 `skeleton_blueprint` / `design_brief` 里真实存在；4. `depends_on` 无环、无悬空引用；5. 条目总数与预算在上限内（§3.5）。

校验失败 → **不阻断交付**：把无法校验的条目降级为 `unsupported` 并记入清单，可校验的部分照常执行（沿用"能力缺失只标记不阻断"的政策）。只有"整个 plan 为空且没有任何条目"才算异常，此时终止并报错。

### 2.8 state 契约：三层划分（对齐 Claude Code 的状态分层）

`GenerationState` 现在同时住着三类性质完全不同的东西，这才是"state 太乱"的真正来源——只删字段治不了，因为新链还会长出同类字段。所以先定分层，再定字段。

| 层 | 内容 | 例子 | 住址 |
| --- | --- | --- | --- |
| **① 图 state** | 跨节点、跨循环、断点恢复必须活下去的**权威事实** | `plan`、`design_document`、`design_brief`、`skeleton_blueprint`、`merged_blueprint`、`status` | LangGraph `GenerationState` |
| **② 执行上下文** | 单次执行需要的输入与临时对象，用完就丢 | 本批槽位切片、宿主几何、检索命中的 chunk、拼好的提示词、模型原始回复 | 作为**函数参数**传给处理器，不写 state |
| **③ 旁路观测** | 诊断、耗时、token、每个校验器的原始输出 | 节点耗时、`node_starts`、原始 reply、`component_diagnostics` 明细 | 日志 / LangSmith / RAGTrace / 事件流 |

Claude Code 的三层是 `bootstrap/state`（进程级单例）→ `Store<AppState>`（单一状态树）→ `ToolUseContext`（**每次工具执行的参数容器，工具用完即丢，不进 Store**）（第 33 章 §四）。我们的 ①②③ 就是它的同构：**关键动作是把 ② 从 state 里挪出去**——v2 的 `execute` 每次只处理一条条目，它的输入本来就该是参数，而不是 state 字段。

**准入判据（四条测试，全过才能进 state）**：

| # | 测试 | 不过怎么办 |
| --- | --- | --- |
| T1 | **恢复测试**：进程崩了从 checkpoint 恢复，缺了它能否继续？ | 能 → 不进 |
| T2 | **消费测试**：除写它的节点外，还有别的节点读它吗？ | 没有 → 不进（它是执行上下文的局部变量） |
| T3 | **重算测试**：能否由其它 state 字段或磁盘产物重算？ | 能 → 不进 |
| T4 | **单写者测试**：只有一个节点写它？ | 是 → 不进，且**不要加 reducer** |

**三条配套纪律**：

1. **只有一个写者就不要 reducer**。`Annotated[..., merge_state_mapping]`（`state.py` 的 `component_fragments` / `component_diagnostics`）是并行 gen 节点的遗留解法；新链里 `plan` 只有 `replanner` 写、产物只有 `execute` 写，**单写字段一律直接覆盖**，reducer 只在真正并行 fan-out 时才引入。
2. **不可序列化的东西不进 state**：模型客户端、回调、轮询器一律走 `ContextVar`（现状 `ws_agent` 绑定反馈轮询器已是这个做法），否则 checkpoint 会炸。
3. **state.py 文件头加守则注释**（照抄 Claude Code `bootstrap/state.ts` 那两条注释的精神）：

```python
# app/agent/state.py
# ⚠️ 不要在这里继续加字段。加字段前先过《动态节点设计规划》§2.8 的四条准入测试。
# ⚠️ 每个新字段必须在 §2.9 的表里有对应行：谁读、谁写、为什么不能重算。
```

### 2.9 字段最终形态（保留 / 新增 / 删除）

现有 `GenerationState` 有 100+ 个字段（`app/agent/state.py`），目标是 **≤ 45**。

**新增（3 个）**

### 2.10 最小可恢复集合（checkpoint 只写必要字段）

Claude Code 的崩溃恢复指针只写三个字段（`sessionId` / `environmentId` / `source`），理由写得很直白：**写得越少，崩溃前完整写下去的概率越高**（第 33 章 §7.1）。LangGraph 的 checkpoint 是同一类东西。

- **可恢复集合**：`request_id`、`session_id`、`intent`、`plan`、`design_document`、`design_brief`、`skeleton_blueprint`、`merged_blueprint`、`status`、`error`。其余字段按 T1/T3 逐个判：能重跑的（校验结果）与能重建的（提示词、切片、摘要）都不进恢复路径。
- **不追求"恢复后与崩溃前逐字节相同"**，只追求"能从中断点继续跑完"。恢复后由 `reconcile` 重新对账，缺失的中间态自然被补齐。
- **收益是三重的**：写盘更快、恢复更可靠、旧 checkpoint 的兼容负担更小（字段少了，反序列化失败的组合也少了）。

## 三、plan 怎么生成

### 3.1 输入

| 来源 | 内容 |
| --- | --- |
| `design_document` / `design_brief` | 体量、立面方案（`facade_plan`）、构件配额（`component_quota`）、精确槽位（`opening_slots`）、材质角色 |
| `skeleton_summary` | 墙体 id 与几何、楼板标高、可用材质 id 清单（`build_skeleton_summary`，`generation/skeleton_output.py`） |
| 知识库 | 能力清单（哪些 `kind` 可做、需要什么宿主） |
| 请求参数 | 生成档位（§8.3）、预算上限 |

### 3.2 分工：模型定策略，程序定条目

这是本方案可复现性的关键。

- **模型负责**：本次要覆盖哪些 `kind`、每个 `kind` 的策略（`subtype`、朝向偏好、风格倾向）、以及特殊的额外工作（例如"用户点名要门廊雨棚"）。
- **程序负责**：把策略展开成确定的条目列表（`expand_plan(strategy, design_brief, skeleton_summary) -> items`）。展开是纯函数，同样的输入必须得到同样的条目序列。

模型不写条目 id、不写坐标、不决定循环顺序。这沿用了门窗链上已经跑通的先例：`build_component_prompt`（`prompts/generation.py`）把"程序解析的精确开口槽位（最高优先级）"直接塞给模型，要求逐字复制坐标——**程序负责给位置，模型只负责给形状**。

### 3.3 展开规则（确定性）

| 条目来源 | 展开规则 | 依赖 |
| --- | --- | --- |
| 门窗槽位 | 按 `(kind, host_wall)` 分组，每组一条 `generate` + 一条 `merge` | `merge` 依赖对应 `generate` |
| 配额构件（阳台 / 雨棚 / 栏杆 / 灯光 / 檐口 / 烟囱 / 坡道 / 凸窗 / 屋顶 / 门） | 每个 `kind` 一条 `generate` + 一条 `merge`，数量与参数来自 `component_quota` 与档位套餐 | 同上 |
| 主体（墙 / 楼板 / 屋顶 / 楼梯） | **不展开条目**：已由 `skeleton` 节点产出 | — |
| 材质 | 若 `DesignDocument` 已解析出 `resolved_plan` 则不展开；否则一条 `generate(material)` | — |
| 收尾 | 一条 `merge`（配额强制 + 全局归一化）+ 一条 `validate`（13 件套全量） | 依赖全部 `merge` |

展开失败的条目（找不到宿主、宿主已无可用长度）**不报错**：标 `unsupported`，进交付清单。

### 3.4 plan 校验复用旧资产

`plan_validator` 的位置和角色保留：它以前校验 `ExecutionPlan.steps`，现在校验 `PlanItem[]`。判定逻辑（能力白名单、依赖合法性、安全门禁）迁移，数据结构换掉。

### 3.5 档位（低 / 中 / 高 / 最高）的接入点

档位不再是"另一条流程分支"，而是 **`expand_plan` 的一个参数**：

| 界面档位 | `level` | 体量 | 展开的 `kind` | 迭代上限 M | 模型调用上限 |
| --- | --- | --- | --- | --- | --- |
| 低 | `minimal` | 1 | 只展开用户点名的 `kind` | 2 | 4 |
| 中 | `simple` | 1 | 用户点名 + 门窗 | 3 | 6 |
| 高 | `standard` | 1 | 按配额补全套餐 | 5 | 12 |
| 最高 | `detailed` | ≥2 | 套餐 + 立面节奏细分 | 8 | 20 |

- 档位由**界面给定**（协议字段），写入 `design_document.decisions.complexity.level`；`plan`、`execute` 只读不推断。现状 `resolve_complexity_profile`（`generation/architecture/profile.py`）靠关键词猜测档位的逻辑保留为兜底，并撤掉 `min_detail_packages = 0`、`min_volumes = 1` 两处硬削弱。
- 档位调高**不等于能力变强**：高/最高档要求但无知识分片的 `kind` 一律 `unsupported`，并在交付清单里显式列出"本次档位要求但未支持的项"，不许静默降级。
- 上表数值是初值，P2 用双跑对照实测后修正，调整时保持单调。

## 四、execute：通用执行器

### 4.1 取哪一条：确定性选择

```
取 items 中第一个满足「status == pending 且 depends_on 全部 done」的条目
列表顺序 = plan 里的声明顺序（不排序、不依赖字典遍历顺序）
没有可选条目 → 交回 replanner（由它决定继续、终止还是补条目）
```

不做优先级队列、不做并行调度。**顺序确定性优先于吞吐**：同一份输入两次运行必须产出同一份蓝图，否则回归样例钉不住、双跑对照也没有意义。（并行 fan-out 是后续可选项，前提是先证明 merge 的 fan-in 顺序确定。）

### 4.2 `op` → 处理器分派表

| op | 处理器 | 实现位置 |
| --- | --- | --- |
| `generate` | 知识按需检索 → 五段提示词 → 模型 → 解析片段 → 该 kind 的校验器 | 复用 `generation/component_workflow.py` 的检索与解析 |
| `merge` | 幂等 patch（追加 / 替换）+ 开口登记 | 复用 `generation/assembly.py` 与 `patch_workflow.py` |
| `validate` | 调 `app/tools/spatial_tools.py` 的校验器 | 原样复用 |
| `fix` | 按 `_FIX_MAP`（`assembly.py:9`）派发确定性修复算子 | 原样复用 |
| `repair` | `extract_repair_actions` → `execute_repair_actions`（`repair/tools.py`） | 原样复用 |

分派表是**唯一**允许出现 `op` 判断的地方。表中前两行（`generate` / `repair`）是**工具型处理器**——模型 + 有界工具循环；后三行是**确定性处理器**——纯代码。边界与工具集见 §4.7–§4.12。除此之外任何地方出现 `if kind == "window"` 这类分支，都说明该逻辑应该变成知识或数据。

### 4.3 `generate` 处理器：提示词由程序拼装

五段固定结构（顺序不得调换）：

| 段 | 内容 | 来源 |
| --- | --- | --- |
| A 角色定义 | 跨类型共用的一段文本 | 代码常量，**全类型同一份** |
| B 任务切片 | 本条目的槽位 + 宿主几何 | 程序从 `design_brief` / `skeleton_blueprint` 截取 |
| C 知识 | 字段、取值范围、单位、宿主关系、编译后产出 | RAG（`doc_type=component` + `capability` / `parameters`） |
| D 全局约束 | 材质 id 白名单、配额、立面上限、档位 | 程序从 `design_brief` 与蓝图推导 |
| E 输出格式 | JSON 骨架 | 代码常量 |

四条硬规定：

1. **禁止 per-type 静态提示词常量**。字段级约束只能来自 C 段。现存 `_COMPONENT_RULES`、`extra_rules`、`_COMPONENT_LABELS` 在 P2 之前下沉进知识库。
2. **禁止在提示词里写死数量与位置**（"生成 2 个门""对称布置 4 扇窗"）。数量与位置唯一来自 B 段。
3. **只发本条目相关的切片**，不发全量蓝图。现状门窗已经这么做了（`slot_section` 只给本类型槽位），本方案把它推广到全部 `kind`。
4. **B 段必须包含"逐字复制坐标，不得自行计算"**的措辞，沿用门窗先例。

自检方法：新增一个 `kind` 时，如果 A 段或 E 段需要改动，说明组装契约已被破坏。

### 4.4 `merge` 处理器：幂等

```
merge(item, fragment):
  1. fragment 的 source_item_id 必须等于 item.id；不等则丢弃并记缺口
  2. 蓝图里已存在 item.id 产出的元素 → 替换（不是追加）；否则追加并写入来源标记
  3. 在宿主上登记开口/引用时先按键去重
```

- **元素 id 必须确定性生成**（`{item_id}` 或 `{item_id}_{n}`），不许用随机数、时间戳、uuid。
- 没有幂等这一条，重试会产生重复门窗——而重复元素恰好可能绕过配额检查（配额只查区间，不查重复）。
- 条目 id 提升为蓝图元素的**正式溯源字段**，`validate_reference_integrity` 增加"带来源标记的元素其条目必须存在"的检查。没有溯源，"对账"就还是关键词匹配换了个马甲：对不上时你分不清是"没生成"还是"生成了但对不上"。

### 4.5 失败与 per-item 预算

| 情况 | 处理 |
| --- | --- |
| 模型调用抛异常（额度、鉴权） | 立即终止整轮，不进循环（沿用现有模型故障分类） |
| 片段解析失败 | `run.state=failed`、`run.attempts += 1`；计划态不动，下轮 `replanner` 置回 `ready` 重试 |
| 该 kind 的校验器报错 | 写入 `run.evidence`，交给 `replanner` 决定是否追加 `repair` 条目 |
| `run.attempts ≥ max_attempts`（默认 3） | 终态：计划态置 `abandoned`，进交付清单，不再重试 |

`attempts` 是 **per-item** 的，不是全局轮数：新出现的失败条目不应该被别的条目耗尽的预算连坐（现状 `component_retry_counts` 已是这个语义，继续沿用）。

### 4.6 与 v1"校验不进循环"红线的差异

v1 禁止校验进入循环，理由是"边跑边修会振荡、错误数闸门失效"。v2 **允许 `validate` 与 `fix` 作为条目出现在循环里**，因为它们现在是显式工作项：

- 结果写回**条目状态**，不写全局 `status`，不会污染交付判定；
- 有 per-item 预算，不会无限重试；
- 顺序确定（条目顺序固定），所以不会出现"修完又被后续批次推翻"的振荡——被后面条目推翻的情况由 `replanner` 的 `reconcile` 发现，并作为新的缺口显式追加。

**但 `final_validate` 仍然只跑一次、在循环之外**，它是对外交付的唯一闸门：13 件套校验器 + 引擎侧真实编译重建（`wild-web/scripts/validate-generated.mjs`：解析 → 重建 → 编译组件；必要时再加 `check-rendering-pipeline.mjs` 的渲染级检查）。循环内的 `validate` 条目只是为了少跑冤枉路，不是交付依据。

### 4.7 两种处理器：确定性处理器与工具型处理器

> 本节回答一个问题：plan 的条目能不能「把 RAG 检索、校验工具、网络搜索都当 tool 交给模型」？
> 答案是：**方向对，但只给 `generate` / `repair` 两类条目**，其余三类绝不经过模型。

| op | 处理器形态 | 给工具吗 | 理由 |
| --- | --- | --- | --- |
| `generate` | **工具型**：模型 + 有界工具循环 | ✅ | 字段约束可能超出程序预取的知识，允许模型自己补检索；允许它自查 |
| `repair` | **工具型**（现在就是这个形状） | ✅ | `REPAIR_TOOL_SPECS` 本身就是白名单工具，模型选动作、程序执行 |
| `merge` | 确定性 | ❌ | 幂等数据操作，模型参与只引入不确定性 |
| `validate` | 确定性 | ❌ | 校验必须可复现、结果可对账 |
| `fix` | 确定性 | ❌ | `_FIX_MAP` 已完全覆盖，不需要判断 |

**为什么 `validate` / `fix` 不给模型**：项目已经在这个坑里踩过一次。用 `create_agent` 把 19 个工具（`agent_service.py:982-1002`）全交给模型之后，结论记录在 `docs-dev/wild-server/扩展方向.md`：「create_agent 对流程控制力弱——LLM 可能忘记调用校验工具」，这正是后来把生成与校验拆成确定性节点的原因。**所以：关键校验由 plan 里的 `validate` 条目保证（模型无法跳过），模型自愿调工具只是加分项，不是保证。**

这一条同时解释了「每条条目的提示词不同」应该怎么实现：**不是每条写一份模板**（那是 `_COMPONENT_RULES` 的老路），而是 A/C 段共用、B/D 段按条目数据变化，工具集也按条目裁剪（§4.8）。

### 4.8 工具层：注册表 + 按条目裁剪

不要把 19 个工具一次性塞给每次调用：工具 schema 本身占 token，无关校验器会浪费调用次数、稀释注意力。**工具集按条目裁剪**（数据表，不是分支）：

| 工具类别 | 内容 | 现有位置 |
| --- | --- | --- |
| knowledge_search | 按 metadata 过滤的 RAG 检索 | `RAGSpecLoader.load_many` + `SpecQuery`（`app/spec/loader.py:154,1253`） |
| validate | 校验器 | `app/tools/spatial_tools.py` |
| fix | 确定性修复算子 | 同上（**只给 `repair` 条目**） |
| mutate | 定点改蓝图的白名单动作 | `REPAIR_TOOL_SPECS`（`app/agent/repair/tools.py`） |
| web_search | 外部检索 | 见 §4.12（默认关闭） |

```python
# app/agent/planning/tool_registry.py（新增）
@dataclass(frozen=True)
class ToolSpec:
    name: str                          # 唯一名，写进 tool_trace
    tool: Any                          # @tool 装饰后的函数对象
    category: str                      # knowledge_search | validate | fix | mutate | web_search
    max_calls: int = 2                 # 单条目内该工具的调用上限
    applies_to: tuple[str, ...] = ()   # 形如 ("generate:window", "repair")；空元组 = 全部条目

TOOL_REGISTRY: tuple[ToolSpec, ...] = (
    ToolSpec("search_knowledge", search_knowledge, "knowledge_search", max_calls=2),
    ToolSpec("validate_opening_coords", validate_opening_coords, "validate",
             applies_to=("generate:door", "generate:window", "generate:bay_window", "repair")),
    # ...
)

def tools_for(item) -> list[ToolSpec]:
    """按 (op, kind) 裁剪工具集；顺序固定，同样的条目必然拿到同样的工具集。"""
```

两条纪律：**`tools_for(item)` 是纯函数**（可单测、顺序确定）；**新增 `kind` 不需要改 `tools_for` 的逻辑**，只在 `TOOL_REGISTRY` 里加一条声明。

### 4.9 工具型处理器的执行循环（有界）

`generate` 处理器分三段，只有中间一段是模型自主的：

```
1. prepare   （确定性）拼检索 query → RAG 预取 → 切片（宿主几何 + 槽位）→ 五段提示词
2. act       （模型 + 工具，有界）create_agent(裁剪后的工具) → ainvoke → 至多 MAX_TOOL_CALLS 次工具调用
3. finalize  （确定性）解析 JSON → 过滤 → 该 kind 的校验器 → 写入片段
```

```python
# app/agent/planning/executors.py（新增）
async def run_generate(item, *, blueprint, design_brief, thinking_mode, llm):
    prompt, _slice_ids = build_item_prompt(item, blueprint, design_brief)   # 1. prepare
    tools = tools_for(item)
    agent = create_agent(model=llm, tools=[t.tool for t in tools],
                         system_prompt=TOOL_AGENT_SYSTEM)                  # A 段（全类型共用）
    result = await agent.ainvoke(
        {"messages": [{"role": "user", "content": prompt}]},
        config={"recursion_limit": 2 * MAX_TOOL_CALLS + 1,                 # 有界
                "callbacks": [reasoning_callback]},                        # thinking 流式复用
    )
    fragments, tool_trace = extract_fragments(result, item)                # 3. finalize
    return fragments, tool_trace
```

`create_agent` 的用法与 `ainvoke` 的调用形状照抄 `agent_service._create_agent` / `query_structured`（含 `thinking_mode` 的推理流式回调与 token 记账），**不新写一个模型客户端**。

四条规定：

1. **有界**：`MAX_TOOL_CALLS` 默认 3，配 `recursion_limit = 2 × MAX_TOOL_CALLS + 1`。超限即停，把已拿到的交给 `finalize`；拿不到片段就是本轮 `run.state=failed`（不是终态，还能重试）。
2. **记录**：每次工具调用写 `state.tool_trace[item_id] = [{tool, args_digest, ok, chars}]`，同时进 LangSmith metadata，交付清单的审计区引用它。**没有这条，出问题时无法区分「模型没查」和「查了但知识里没有」。**
3. **工具异常不等于节点失败**：工具抛异常 → 把错误文本作为工具结果返回给模型让它继续；**模型服务故障（额度、鉴权）→ 立即终止整轮**（复用现有 `terminal_model_error` 分类，不重试）。
4. **不把工具循环暴露成主图节点**：主图的粒度是「条目」，工具调用明细在 LangSmith 上是嵌套 run。理由：工具循环若变成主图节点，条目数 × 工具调用数会一起放大图步数，`recursion_limit` 立刻失去意义，而它带来的可见性并不比嵌套 run 多。

**与 §6.1 的关系**：主图每轮仍是两个真实图步（`execute` + `replanner`），checkpoint / interrupt / 逐条目 trace 都不变；工具层是 `execute` 内部的实现细节。

### 4.10 RAG 作为工具的两种用法（主力是预取）

| 用法 | 谁触发 | 可复现 | 定位 |
| --- | --- | --- | --- |
| 预取（主力） | 程序按 `(op, kind, 宿主)` 拼 query，命中直接进 C 段 | ✅ | 现有 `component_workflow` 就是这么做的，继续沿用 |
| 按需（补充） | 模型判断还缺某类字段知识，调 `search_knowledge` | ⚠️ 记 chunk id 后可归因 | 上限 2 次，补程序没预料到的字段问题 |

**检索工具必须带过滤**，不能给模型一个能查全库的口子：

```python
# 只允许这两类过滤对，来自 knowledge/policy.py 的既有配方
SpecQuery(text=query, metadata_filter={"doc_type": "component", "knowledge_role": "capability"})
SpecQuery(text=query, metadata_filter={"doc_type": "recipe", "knowledge_role": "relation"})
```

- 过滤统一走既有安全层（`app/rag/security.py` 的 `split_business_and_access_filters`），**新工具不得绕过**；
- 命中结果必须记 chunk id（进 `evidence` 与 `tool_trace`），否则「模型说知识里没有」无法证伪。

### 4.11 工具的实现契约（三族机制不要混）

| 族 | 形态 | 谁决定改哪里 | 用途 |
| --- | --- | --- | --- |
| A `@tool` 纯函数 | `(blueprint: dict) -> str` | 函数自己全量扫描 | 校验器 / 确定性修复算子 |
| B `REPAIR_TOOL_SPECS` | 声明式 spec + 参数，程序执行 | 模型指定 `entity_id` 与参数 | 定点改蓝图（走白名单） |
| C 检索 | `SpecQuery` + `load_many` | 程序或模型给 query | 知识拉取 |

新增工具按这三族归类：能纯函数化的一律 A；改蓝图的一律 B；**不允许给模型开放任意字段写入，也不接受白名单外的新动作名**。

两条沿用现有实现的规定：校验器输出沿用 `✅ / ⚠️ / ❌` 标记约定，严重度判定集中在 `_severity_from_text`（`app/services/agent_service.py:212`），不许散到各工具里；修复算子的「已修改」路径**故意不带 `✅`**（靠「不含 `❌` 且蓝图确实变了」判定），不要为了好看统一。

### 4.12 网络搜索作为工具：三条限制（或者干脆不给）

现有政策是「不在生成请求内做在线检索」（不可复现、成本不可控）。要把它做成工具，必须同时满足三条：

1. **默认关闭**，由配置开关与前端开关同时放行；未配置 API key 时该工具根本不出现在 `tools_for(item)` 里（不是调用了才失败）；
2. **只允许出现在**「显式能力缺口」或「用户点名要外部资料」的条目上，`generate` 条目默认不给；
3. **命中必须记 URL 与 chunk id 进 `evidence`**，并给本次请求打上「含外部检索、结果不可复现」标记，交付清单里体现。

**更推荐的做法仍然是离线补课**：把外部知识通过既有 `web_research` 入库，变成下一次生成可用的一等知识。这样在线路径保持纯净，知识缺口也真的被填上（§9.3 已定此路线）。

## 五、replanner：唯一的循环控制点

### 5.1 每轮做三件事（快路径不调模型）

```
1. reconcile(plan, blueprint, artifacts)   # 确定性，唯一的状态写入口
2. 若有可执行条目 → goto execute
   否则 → goto final_validate
3. 只在出现异常时调模型：有条目 failed / 发现计划外缺口 → 追加条目（§5.3）
```

**快路径必须是纯确定性的**：绝大多数请求（顺利生成）全程不该出现第二次模型调用。这条是成本可控的前提——循环里每次调模型都乘以迭代数，而迭代数可达十余次（每个 `generate` 条目一轮，每个 `merge` 条目一轮）。

### 5.2 `reconcile`：状态只在这里改

```
reconcile(plan, blueprint, fragments) -> plan'
  只读 run.state / run.artifacts，只写 status（两类字段的写者不重叠，见 §2.6）
  对每条 run.state ∈ {succeeded, failed} 的条目:
    产物存在且已并入蓝图            → status = done（run.evidence = 落地元素 id 列表）
    产物存在但尚未并入              → status = ready（等对应的 merge 条目）
    无产物且 run.attempts < 上限    → status = ready（下轮重试）
    无产物且 run.attempts ≥ 上限    → status = abandoned
    依赖里有 abandoned/skipped      → status = blocked
  几何比对沿用 design_constraints.py 的 _opening_values_match（容差 0.01）
```

**每次改动蓝图的操作之后都必须重跑 `reconcile`**。蓝图不是只读的：`enforce_component_quota` 会增删构件、`deduplicate_balcony_representations` 会删掉与阳台重叠的手写 floor、`remove_ground_level_railings` 会删落地栏杆、`fix_*` 会改写坐标。这些删改会让此前写入的状态失效，而漂移是**静默**的——`done` 的统计基于条目状态而非蓝图内容，所以不会报错，只会让交付清单说谎。因此收尾 `merge` 之后、出交付清单之前，必须再对账一次。

### 5.3 异常时才调模型：允许的动作闭集

| 动作 | 语义 |
| --- | --- |
| `add_items` | 追加条目（必须是已有的 `op` + 已有的 `kind`） |
| `replace_item` | 替换某条失败条目（换宿主、降数量、换 subtype） |
| `drop_item` | 放弃某条条目（记入交付清单的未完成项） |
| `mark_unsupported` | 标注为能力缺失（只标记不阻断） |
| `give_up` | 主动终止本轮，带 warning 交付 |

程序校验后写回 plan，条目 `origin = emergent`，`revision += 1`，并向 `history` 追加一条 diff 摘要（前端据此更新进度面板）。

**涌现缺口是"从放置后果推导出来的需求"，不是校验发现的问题。** 以"阳台放进某面墙 → 该墙需要栏杆；但 balcony 已内嵌 U 形栏杆，禁止再加独立 railing"为例：这类判断需要看"刚放下什么 + 它的宿主"，模型看切片就能做，程序也能做。实现时优先写成确定性派生（**新增**算子 `derive_items(item, blueprint) -> items[]`：给定刚放下的元素与它的宿主，输出必须确定），只有无法几何推导的场合才交给模型。

### 5.4 终止条件（五重，必须全部有界）

| 条件 | 判定 | 处置 |
| --- | --- | --- |
| 无可执行条目（无 `pending` / `ready`） | 队列空 | 进 `final_validate` |
| 迭代数 > M（档位相关，§3.5） | 计数 | 终止，带 warning 交付 |
| **无进展**：连续 K=2 轮无任何条目状态变化 | 状态快照比对 | 终止，带 warning 交付 |
| `revision > 2` | replanner 追加次数 | 不再追加，终止 |
| 模型调用 / token 超预算 | 计数器 | 终止，带 warning 交付 |

**"无进展检测"是本方案防死循环的主力**：只靠迭代上限，遇到"追加了条目但永远不 done"的情况会白烧满 M 轮预算。

### 5.5 有界性论证（面试可直接讲）

1. 条目数有界：`plan` 展开受档位套餐与预算上限约束，`replanner` 追加受 `revision ≤ 2` 约束；
2. 每轮至少消费一条条目（`execute` 必然写一条的 `run`，或 `replanner` 把它判成终态）；
3. 连续两轮没有状态变化即终止；
4. 因此循环步数 ≤ 条目总数 × (1 + 追加上限)，与 `recursion_limit` 的关系见 §6.2。

## 六、可观测性与前端进度

### 6.1 一个条目 = 两个真实图步

`execute → replanner` 每轮都是真实的 LangGraph 步骤，因此 **checkpoint、`interrupt`、逐节点 trace 三样全部保住**——这正是 v1 反复强调、也是最不能丢的东西（这个项目的调试几乎全靠 trace）。

代价要说清楚：**LangGraph 的节点名是静态的**，所以 trace 里不能出现"这次执行的是 door 条目"这种节点名。条目级可见性靠两条替代通道：

1. `state.current_item_id` + 条目快照写进每次 `execute` 的输入，trace 的 input 里能看到"这一轮在处理哪条"；
2. 前端事件流按条目推送进度（§6.3）。

不要为了好看而伪造动态节点名——那会变成 v1 那种"看起来动态、实际写死"的翻版。

### 6.2 `recursion_limit` 公式

现状 `generation_recursion_limit(component_count, max_retries, plan_mode)`（`graph.py:209-217`）按组件链数量算（当前取值 48 / 50 / 68，被 `tests/agent/test_agent_graph_routing.py` 钉住）。v2 把入参换成条目数：

```
limit = max(48, 16 + plan_item_count * 2 + retry_budget * 4)
        （plan_item_count 计入 replanner 追加的条目；*2 是因为一条条目 = execute + replanner 两步）
```

条目**内部**的工具调用不占主图步数（§4.9），它们的上界在 `execute` 内部单独约束（`MAX_TOOL_CALLS`）。这正是「工具层不暴露为主图节点」的收益：条目数 × 工具调用数不会一起放大图步数。

改公式必须同步改上面那条测试。**上限是安全余量，不是停止条件**——真正的停止条件是 §5.4 的五重判定（现有文档 `docs/agent/AGENT_AND_CHAT.md` 已明确这个立场：靠调大 `recursion_limit` 解决不了循环问题）。

### 6.3 事件协议（前端 plan 面板）

| 事件 | 时机 | 载荷 |
| --- | --- | --- |
| `plan_ready` | `plan` 节点产出入 plan | 完整条目列表 + 档位 + 预算 |
| `plan_item_started` | `execute` 取到条目 | `item_id` / `op` / `kind` / 可读描述 |
| `plan_item_finished` | `replanner` 更新状态 | 状态 + `evidence` + 耗时 |
| `plan_updated` | `replanner` 追加/失效条目 | 新增条目 + `revision` + 原因 |
| `plan_completed` | 循环结束 | 统计（总数 / done / abandoned / skipped / unsupported） |

- `plan_ready` 直接替换现有 `execution_plan_ready`（`ws_agent.py:1056` 附近），因为旧计划数据结构被删除。
- 事件要加进 `generation_job_service.py` 的 `_PERSISTED_EVENT_TYPES`，否则断线重连后进度面板会空掉。
- **进度面板是只读展示，不是批准闸门**：用户可以看、可以中断，但 plan 不需要批准（§7.3）。
- 配套清理：`ws_agent.py:588-596` 的 `_node_label` 里按构件类型生成 `{ct}_gen / {ct}_val` 标签的循环、`wild-web/src/stores/agentStore.ts` 的 `_COMP_LABELS` / `_NODE_LABELS` 循环，全部删除——新链不再有 per-type 节点。

### 6.4 交付清单

沿用固定结构，逐条列出未完成项（不许合并成一句话），并保证 `done + abandoned + skipped + unsupported == total` 可校验：

```jsonc
{
  "detail_level": "standard",
  "plan_revision": 2,
  "items": { "total": 12, "done": 9, "abandoned": 1, "skipped": 0, "unsupported": 2 },
  "unsupported_items": [
    { "item_id": "it_007", "kind": "bay_window", "reason": "无可用宿主墙长度" }
  ],
  "detail_level_gaps": ["入口台阶", "门廊装饰柱", "老虎窗", "窗套线脚", "分层材质"]
}
```

`detail_level_gaps` 专门承载"本次档位要求但能力缺失"的项，与普通 `unsupported` 分开——这是 §3.5 那条红线的落地位置。

## 七、人工审核

### 7.1 审核对象与位置

**审核对象是 `architecture` 产出的设计图纸**（`DesignDocument` + `resolved_design` + SVG 预览），沿用现有中断：`build_design_review_interrupt`（`app/design/review_outcome.py`）的载荷形状不动，`preview.svg` 链不动。

位置保持在现状那一格：`architecture → design_review → skeleton`。理由：

1. 用户批准的是"方案图纸"，此时还没有骨架产物，审核载荷的形状与现状**完全一致**，改造面最小；
2. 若把中断挪到 `skeleton` 之后，载荷就要带骨架蓝图与"重建后的外观预览"，而这条链现在不存在，等于给本轮凭空加一项能力；
3. 审核通过后 `skeleton → plan → 循环` 全自动跑完，用户只在图纸上介入一次。

### 7.2 恢复输入

| 动作 | 载荷 | 行为 |
| --- | --- | --- |
| 批准 | `{"action": "confirm"}` | `revision` 不变，进入 `skeleton` |
| 提意见 | `{"action": "revise", "feedback": "..."}` | 回 `architecture`，`revision += 1`，原来已跑的骨架与 plan 作废重建 |
| 直接改图 | `{"action": "revise", "document": {...}}` | 用提交的文档覆盖，**仍须过 `DesignDocument` 校验** |

**重规划（§5.3 的 `add_items`）不需要重新审核**：它只改 plan、不改图纸。只有 `architecture` 被重新调用导致图纸变化时，才需要重新审核——否则等于用户批准了一张已经改过的图。

### 7.3 plan 不审批，但可见

计划模式（`plan_mode`）的语义在本方案里消失了：以前它是"先批准一份任务列表再执行"，现在 plan 是内部数据驱动的执行队列，用户通过进度面板**看**它，而不是批准它。

**`plan_mode` 开关的删除时机**：等 §6.3 的 plan 面板与新链一起上线后再删（P3），连带删除 `wild-web/src/stores/agentStore.ts` 的 `STORAGE_KEY_PLAN_MODE`、`src/agent/protocol.ts` 与 `types/agent.ts` 的 `plan_mode` 字段、`agentBridge.ts` 对 `turn.plan_mode` 的判断。反过来做（先删开关）会让用户看到"按钮没了、但后端的链还是旧的"。

### 7.4 外围契约同步改造（红线）

任何中断点或节点名的增删，必须四处同步，缺一不算改完：

| 位置 | 现状 | 改造 |
| --- | --- | --- |
| `app/api/ws_agent.py` `_NODE_LABELS` | 按节点名写死中文标签 | 增删节点名；删掉 `{ct}_gen / {ct}_val` 循环 |
| `app/api/ws_agent.py` `_OUR_NODES` | 硬编码节点名集合（含 per-type 循环） | 换成新 5 节点 + classifier/chat/patch/final_validate，**删掉 per-type 循环** |

历史上已经因此出过一次事故（见 `docs-dev/2026-09-17-candidate-mechanism-cleanup.md`：`proposal_review` 的 `interrupt()` 没有消费方，走到那里必然报"未返回结果"）。删 `plan_review` 会制造同一个形状的坑，必须三处同步（后端 + 前端 + 一条端到端恢复用例）。

## 八、能力边界与档位

### 8.1 能力缺失只标记不阻断

继承既定政策：无知识分片、无执行路径、宿主不可用的要求 → `unsupported`，不派发、不阻断、进交付清单。**不要把能力缺失当 bug 修**，也不要把"发散需求"（调度层面的自由）和"能力缺失"（"先做地基"这类做不了的事）混为一谈。

### 8.2 新增一个构件类型要做什么（v2 的三步）

1. **知识入库**：`doc_type=component` + `knowledge_role=capability` 分片（字段、取值范围、单位、宿主关系、编译后产出）+ `recipe` + `relation` 装配关系分片；
2. **在能力清单里声明**（数据，不是代码常量）；
3. **加回归样例**：一个正向、一个负向。

**不需要做的**：新增图节点、新增 `op`、新增 state 字段、新增 `if kind ==` 分支、改 `ws_agent` 的节点集合。

对照 v1 的六步清单，省掉的正是"注册节点"这一步——这也是 v2 存在的全部理由。

### 8.3 档位与成本的对应

见 §3.5 的表。补充两条：

- **档位决定条目集合与预算，不决定"能力"**：高档位不会让系统支持它本来不支持的构件，只会让它把支持的构件做得更细（更多 `kind`、更多细节套餐）。
- **与其它的"精度开关"是两条轴，不要合并**：`thinking_mode`（前端的深度思考）只影响**实现质量**（是否思考、检索是否更严），档位影响**输出细节**。一条请求同时带这两个字段。

## 十一、红线

每条都带理由，不带理由的禁止项不写。

1. 🔴 **模型不得写条目 `status`**。状态只由 `reconcile` 与结构判定写入——否则退回"节点自称完成"的老问题。
2. 🔴 **`op` 是闭集，`kind` 是开集**。新增 `op` 是架构变更（要加处理器 + 测试）；新增 `kind` 只是数据变更。想加第六个 `op` 时先回到 §2.3 的三条纪律。
3. 🔴 **禁止 per-type 代码分支**。`if kind == "window"` 这类判断只允许出现在 §4.2 的分派表里，其余位置都应该是知识或数据。
4. 🔴 **每轮 `execute` 只做一条，且顺序确定**。不许改成一个 while 循环的大节点——那会丢 checkpoint、`interrupt` 和逐节点 trace。
5. 🔴 **`replanner` 的快路径不调模型**。只有出现 failed 条目或计划外缺口时才调一次。
6. 🔴 **所有终止条件必须有界**，且"无进展检测"不可省（§5.4）。
7. 🔴 **能力缺失只标记不阻断**，并在交付清单里逐条列出。
8. 🔴 **`op` 层幂等 + 元素 id 确定性**（`{item_id}`），不许用随机数、时间戳、uuid。
9. 🔴 **每次改蓝图之后重新对账**（配额强制、去重、`fix_*`、`repair` 之后）——否则交付清单会说谎且不报错。
10. 🔴 **`final_validate` 只在循环之外跑一次**，它是唯一交付闸门；循环内的 `validate` 条目不承担交付判定。
11. 🔴 **中断点与节点名的增删必须四处同步**（后端标签表 / 节点集合 / resume 分支 / 前端事件），并带一条端到端恢复用例。
12. 🔴 **档位调高不等于能力变强**：要求但未支持的项必须显式列出，不许静默降级。
13. 🔴 **关键校验不能只靠模型自愿调用工具**。可以给模型校验工具自检，但计划里必须有显式的 `validate` 条目兜底——项目上次把生成与校验都交给 `create_agent` 的结果就是「模型忘记校验」。
14. 🔴 **工具集按条目裁剪，不许把全部工具塞给每次调用**。`tools_for(item)` 是纯函数；新增 `kind` 只改 `TOOL_REGISTRY` 声明，不改逻辑。
15. 🔴 **工具调用必须有上界并留痕**（`MAX_TOOL_CALLS` + `tool_trace`），检索类工具必须带 metadata 过滤且不绕安全层。没有留痕，就无法区分「模型没查」与「知识里没有」。
16. 🔴 **新字段必须过四条准入测试**（§2.8）。"先加上去再说"就是 state 退回一百个字段的起点；只有一个写者的字段不配 reducer，也不配进 state。
17. 🔴 **计划态只由 `reconcile` 写，执行态只由 `execute` 写，模型一个都不能写**。终态是 `done` / `abandoned` / `skipped` / `unsupported` 四个，`run.state=failed` 不是终态（§2.6）——把它当终态的代码会提前放弃还能重试的条目。

## 附 B：一句话总结（面试版）

> 我把"动态节点"重新定义了一遍：动态的不是图，是工作项。图固定为 architecture → skeleton → plan → execute ⇄ replanner 五个节点，运行时动态生成的是一份 plan 条目列表——每条是"一个算子 + 一份数据"。算子是闭集只有五个（生成 / 合并 / 校验 / 修复 / 模型修复），数据是开集（构件类型来自知识库）。这样加一个新构件只加数据，不改图也不加代码分支；`execute` 每轮执行一条、`replanner` 决定还有没有下一条，每轮都是真实图步，所以 checkpoint、人工审核中断和逐条目 trace 一个都没丢。对账由程序做，模型不能自己宣布完成；循环有五重有界终止条件，其中"连续两轮无进展"是防死循环的主力。
>
> 执行层分了两种处理器：`merge` / `validate` / `fix` 是纯代码，`generate` / `repair` 走「模型 + 有界工具循环」——RAG 检索、校验器、白名单修改动作都作为工具给模型，但工具集按条目裁剪、调用次数有上界、每次调用留痕；而关键校验仍然由计划里的 `validate` 条目兜底，不指望模型自己记得调工具。
>
> 上一版方案把动态性放在拓扑上，结果被 LangGraph "节点集必须在 compile 前确定"这条约束逼回白名单预注册——所谓动态最后变成了事前列举所有节点。这一版换掉了这个问题本身。
