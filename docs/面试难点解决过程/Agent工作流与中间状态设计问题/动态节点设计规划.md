## 一、能力边界裁定：房间层是新增能力

### 1.1 现状（改造前的事实）

| 事实 | 证据 |
| --- | --- |
| 主链不设计内部空间，无房间坐标、无隔墙 | `app/agent/planning/requirements.py:46-51`：`_UNSUPPORTED_INTERIOR_TERMS = ("房间位置", "房间布局", "功能分区平面", "内部隔墙")` |
| 计划节点明确声明不做房间坐标与内墙 | `app/agent/prompts/planning.py:193` |
| `DesignDocument` 里没有房间概念 | `app/design/contracts.py:221`：字段为 `requirements` / `decisions`（massing、volumes、facades、structural_grid、circulation、component_quota）/ `constraints` / `locks` / `rule_trace` |
| 全仓没有房间建模 | `grep -rn "room" wild-server/app/` 零命中 |
| 现有平面视图画的是体量，不是房间 | `app/design/resolver.py:309` 渲染"体量平面 + 主立面 + 侧立面"三面板，平面面板用的是 `volumes` 的矩形 |

也就是说：现在系统能表达的"平面"是体量块，不是房间划分；房间层是从零开始的新能力。

### 1.2 能力声明

| 项 | 内容 |
| --- | --- |
| **主张** | 把用户的空间需求表达为房间拓扑（房间名、所属楼层、功能类型、正交多边形边界、相邻关系、挑空标记），并把房间作为**槽位宿主**与**内墙生成**的几何真值 |
| **不主张** | 曲线 / 斜交 / 自由曲面房间；坡屋顶下的空间划分；施工图级开间标注与轴网出图；家具布置语义；日照、疏散、无障碍等合规审查 |
| **交付媒介** | 房间层渲染进 SVG 的平面面板（替换现有"体量平面"面板），供人工审核。不承诺导出 DWG / CAD |
| **失败处置** | 房间层生成失败或校验不过时，回退到"只有 massing + 立面槽位"的图纸（即现状能力），并在交付里显式列出"本次未提供房间划分" |

最后一行很重要：房间层是**叠加能力**，不是主链的前置依赖。它失败时必须能退回现状能力，而不是把整轮生成打死。

### 1.3 范围边界（支持 / 不支持）

| 支持 | 不支持 |
| --- | --- |
| 正交（轴对齐）多边形房间 | 非正交 / 斜墙 / 曲面房间 |
| 同层多房间 + 相邻关系 | 跨层挑空以外的复杂竖向空间关系 |
| 内墙由相邻房间的共享边确定性生成 | 弧形墙、异形隔断、家具级隔断 |
| 房间功能类型作为枚举标签（`living` / `bedroom` / `kitchen` / `bathroom` / `circulation` / `storage` / `garage` / `service`，闭集见 §13.2.1） | 对房间功能做语义推理（如"按朝向分配卧室"） |
| 房间级门洞可达性 | 疏散路径、防火分区、无障碍合规 |
| 房间层 → SVG 平面面板 | DWG / IFC / 施工图导出 |

边界之外的需求走既有政策：只标记、不阻断（《能力闸门分级》§7）。

### 1.4 房间层验收标准（确定性、可测）

房间层必须能被程序逐条判定，不许用"看起来对"当验收。以下八条进入最终校验：

1. 每个房间 `polygon` 是简单正交多边形，面积 > 0，无自交；
2. 同层房间两两不重叠（交面积为零，容差 `1e-3`）；
3. 同层房间并集 ⊆ 该层 modeled 轮廓，覆盖率 ≥ 95%（余量留给核心筒与公共区域）；
4. `adjacent` 关系对称（A 声明相邻 B，则 B 也必须声明相邻 A）；
5. 相邻房间共享边长度 ≥ 0.9m，不足者视为噪声邻接并剔除；
6. 内墙数量 = 去重后的共享边数量（内墙是房间边界的确定性投影，不是模型自由发挥的产物）；
7. 每个房间至少一个门洞，且门洞落在属于该房间的边界上（房间级可达性）；
8. 房间边界与内墙 / 外墙几何一致（墙中心线落在边界上，容差 0.05）。

第 4、6、7 条是这套设计能不能成立的关键：它们把"房间"从模型的说辞变成了程序可对账的对象。

### 1.4.1 多楼层竖向规则（三条，同样进校验）

房间层的楼层语义必须有明确约束，否则多层建筑的上下层关系无从校验：

9. **楼梯间竖向对位**：`type=circulation` 的房间，在相邻楼层必须**平面投影重叠 ≥ 60%**（用面积比判定）。楼梯要上下贯通，错位会导致楼梯悬空。
10. **挑空不得被压**：`double_height=true` 的房间，其上方楼层在该房间投影内**不得有房间**（重叠面积必须为 0）；否则挑空被楼板压住，`shell` 无法正确开洞。
11. **上下层墙体不强制对齐**：外墙由 massing 逐层生成、天然对齐；内墙允许上下层错位（结构上由楼板承担）。**不要**额外增加"内墙必须对位"的约束——那会无谓地限制户型。

这三条与第 1 至 8 条一起，构成房间层的完整校验集合。第 9、10 条是结构类判定，不需要蓝图，与第 1 至 5 条一样在设计节点内就能跑（§13.11）。

### 1.5 对既有闸门的影响（顺序红线）

- 本能力落地前，`_UNSUPPORTED_INTERIOR_TERMS` 里那四个词条**必须继续标 unsupported**，不得提前放行。
- 只有在 P2 的房间层通过 §1.4 全部八条之后，才允许把对应词条从 unsupported 表移除。
- **不得先改闸门再补能力**——那会造成"闸门放行、但没有任何节点能实现"，正是《能力闸门分级》§2 记录过的那类事故（先放宽判定，再发现没人能实现）。
- `prompts/planning.py:193` 那句"本节点不设计房间坐标和内部隔墙"要随能力落地同步改写，否则提示词与真实能力再次不一致。

### 1.6 房间层带出的三个连带问题

1. **主体结构生成者缺失**：节点库只有 `design` / `generate:<type>` / `merge:<rule>` / `validate`，没有墙、楼板、屋顶、内墙的生成者。房间一旦权威，"从房间推出主体几何"这件事没有归属。因此新增 `shell` 节点角色（§5.1）。
2. **改房间要改内墙**：房间边界改了，内墙必须跟着改。内墙不能走 `merge` 的增量 patch（会残留旧墙），必须由 `shell` 节点整层幂等重建（§5.1、§6.6.1）。
3. **闸门与能力的先后**：见 §1.5。

## 二、新流程总览

```
意图分类（classifier）
  → 复杂度分流
      ├─ 单构件 / 简单请求 → 直接创建专项生成节点（跳过图纸）
      └─ 完整建筑 → 方案设计（设计节点：massing + rooms + slots）
                          ↓
           主体结构生成（shell 节点：确定性，rooms + massing → 墙/楼板/屋顶/内墙）
                          ↓
           动态执行调度器（缺口循环）
              ├─ 读缺口 missing
              ├─ 派发「生成节点」→ 按需拉构件知识 → 生成 WILD 片段
              ├─ 派发「合并节点」→ 增量 patch 进蓝图（确定性，见 §6.6）
              ├─ 确定性对账：回写 filled / missing
              └─ 循环直到缺口清空或只剩不阻断项
                          ↓
           最终校验（确定性校验器全量跑 + 房间层八条）→ 交付
```

与现状的关系：`classifier`、`final_validate` 保留；中间的 `planner → plan_review → architecture → material_plan → design_review → skeleton → 组件 gen→val → merge` 这条固定链整体被"设计节点 + shell 节点 + 调度器循环"取代。

**关于跳过图纸的分支**：单构件 / 简单请求不走图纸，也就**没有槽位、没有缺口对账**。这条支路的验收必须显式定义，不能默认它"天然没问题"：

- 验收退化为：`final_validate` 全量固定校验；
- 交付里必须标注"本次未经图纸审核"；
- 它产生的涌现缺口（例如合并暴露的宿主缺失）没有槽位可回写，因此该支路只能交付 warning 级差异，不允许宣告"图纸要求全部满足"。

### 2.1 意图分类保留，复杂度分流弱化

"意图分类"与"动态创建节点"不是同一层的事，不能因为后者就取消前者：

| 分类 | 是否保留 | 理由 |
| --- | --- | --- |
| `generate` / `edit` / `chat` 三分类（`routing.py:19`） | ✅ 保留 | 这是**输入语义**的区分，不是执行拓扑的区分：generate 从零建建筑，edit 对现有 `current_blueprint` 做 ScenePatch，chat 不产模型。三者产出的东西不同，"正确"的定义也不同；而且 edit 需要读整份现有蓝图（§7.4），generate 不需要。取消它等于让生成节点去猜"用户是要新建还是改当前这栋"，猜错的代价是覆盖用户已有的建筑 |
| `edit` 但无当前场景时降级 `chat`（`routing.py:229`） | ✅ 保留 | 这类边界判断本身就依赖显式识别修改意图 |
| generate 内部的"复杂度分流"（简单请求跳图纸） | ⚠️ 弱化 | 槽位机制天然能表达"只有一个门"：槽位少，图纸自然退化成一张近乎空的表。不需要再靠分类器判断"简单"，也不需要为此单独留一条分支 |

**结论**：意图分类该留，generate 内部的复杂度分流逐步退出——让槽位数量自己决定要不要出图，而不是让分类器替用户判定"这个需求简单所以不用设计"。

### 2.2 生成粒度由用户控制（低 / 中 / 高 / 最高）

**先说清楚它不是什么**：粒度指的是**建筑的精细程度**，不是构件的数量，也不是 §2.1 里那个"要不要出图纸"的分流。分流决定**做不做**，粒度决定**做多细**。

同一个别墅：
- **低粒度** = 体量 + 屋顶 + 必要的门窗洞口。就是当前的默认输出，看起来像个模型。
- **高粒度** = 在此基础上加门廊与柱、入口台阶、老虎窗、栏杆立柱、窗套与线脚、材质分层、檐口阴影。看起来像一栋真建筑。

两者构件数量差不到一倍，但"是不是一个真实建筑"差一个量级。所以粒度控制的不是"做多少个"，而是"做多细"，并且它同时决定生成时间与成本。

#### 2.2.1 现状：档位写死在代码里，用户无法控制

| 事实 | 位置 |
| --- | --- |
| **已经有四级**：`minimal` / `simple` / `standard` / `detailed`，每级带 `min_volumes`、`min_detail_packages`、`target_structural_elements`、`grid_bays` 四个参数 | `app/agent/generation/architecture/profile.py:19` 的 `_COMPLEXITY_PROFILES` |
| 档位是**从用户消息的关键词猜出来的**：三组关键词（"简单/简洁"→ simple，"复杂/豪华/精致/层次感"→ detailed），无命中一律 `standard` | `profile.py:287` 的 `resolve_complexity_profile` |
| **有两处把档位主动削弱**：`min_detail_packages` 被硬设为 0（等于关掉"按复杂度自动补细节"的开关）；除非用户明说"多体量/退台/错落"，`min_volumes` 被强制为 1 | `profile.py:320-322` |
| 细节构件**完全靠用户点名**：只返回用户明确说出的构件，注释写明"类型和风格不能触发固定构件套餐" | `profile.py:330` 的 `_default_detail_packages` |
| 八类细节构件的配额其实已经定义好了 | `planning.py:46` 的 `_DETAIL_COMPONENT_QUOTAS`：canopy / balcony / bay_window / cornice / railing / ramp / light / chimney |

**结论**：现在输出是"盒子"，不是能力不够，而是**默认没有任何细节套餐**——不说"要阳台"就不加阳台，不说"要烟囱"就不加烟囱。开关从来没被打开过。

#### 2.2.2 新设计：档位由用户在界面上选

复用既有的四级枚举，**不新造词**（前端展示 low / medium / high / max，后端仍是这四级）：

| 界面档位 | `level` | 体量数 | 细节套餐 | 结构构件量级 | 轴网 |
| --- | --- | --- | --- | --- | --- |
| 低 | `minimal` | 1 | 无 | ~1 | 1×1 |
| 中 | `simple` | 1 | 只加用户点名的 | ~6 | 1×1 |
| 高 | `standard` | 1 | 按档位补全 `_DETAIL_COMPONENT_QUOTAS` | ~10 | 2×2 |
| 最高 | `detailed` | ≥2 | 按档位补全 + 立面节奏细分 | ~18 | 3×2 |

改动要点：

1. **`resolve_complexity_profile` 增加 `level` 入参**：界面档位优先，关键词只作为兜底（用户没选时使用）。同时撤掉 `min_detail_packages = 0` 与 `min_volumes = 1` 这两处硬削弱——它们原本是为了防止关键词误判，用户显式选择之后这个顾虑不再成立。
2. **档位随请求一路传到设计节点，写进 schema**（`decisions.complexity.level`）；生成节点只读 schema 里的档位，不各自推断。
3. **档位同时是成本开关**：§6.3 的调用次数与迭代上限按档位给不同值。低档位走最省路径，最高档位允许更多调用与迭代——用户选高就应该接受更长的生成时间。
4. **与"精密模式"不是一回事，两条轴不要合并**：代码里另有一条 `precision_mode`（前端的 `thinking_mode` / `precision_mode`，`ws_agent.py:556`），它只影响**实现与验证质量**（是否开启思考、检索是否更严），不影响输出细节。**粒度决定"做多细"，精密模式决定"做多准"。**

#### 2.2.3 粒度调高会撞上能力缺口，必须显式列出

对照"低粒度 / 高粒度"两张参考图，高粒度想表达的东西里有一部分**当前没有对应构件类型**：

| 参考图里的细节 | 当前是否有对应 |
| --- | --- |
| 檐口与水平线脚 | ✅ `cornice` |
| 栏杆（含立柱） | ✅ `railing`（有 `postSpacing`、`railLevels`） |
| 门廊 / 雨棚 | ✅ `canopy` |
| 阳台 / 凸窗 / 灯光 / 烟囱 | ✅ `balcony` / `bay_window` / `light` / `chimney` |
| **入口台阶（室外踏步）** | ❌ 没有。`stair` 是室内竖向交通，`ramp` 是坡道，都不是入口台阶 |
| **门廊装饰柱** | ❌ 没有。`column` 是结构柱，不是门廊柱 |
| **老虎窗（dormer）** | ❌ 没有 |
| **窗套 / 窗台线脚** | ❌ 没有 |
| **材质分层（砖基座 + 白墙）** | ❌ 没有"分层材质"的概念 |
| 室外环境（树木、铺地、人物） | ❌ 不在范围内，见 §1.2 的不主张 |

**红线**：档位调高不等于能力变强。高 / 最高档位要求、而当前不支持的项，一律标 `unsupported` 只标记不阻断（§十一），并且**必须在交付里显式列出"本次高粒度要求但未支持的项"**。不允许为了让档位"看起来生效"而静默降级——那会让用户以为选了最高档就什么都有了。

这份缺口清单同时也是一份**能力扩展的优先级依据**：要让最高档位真正兑现，需要补的构件类型按此顺序推进（台阶 → 门廊柱 → 老虎窗 → 窗套线脚 → 分层材质）。

**补课的完整闭环（定死，不要留给人猜）**：

1. **触发者是人**：交付清单（§13.9）里的 `unsupported_items` 逐条列出"缺什么 kind"；前端在结果页提供"补课"入口，由人决定是否发起。
2. **产出进知识库**：`web_research` 的结果按既有入库流程写成两类分片——`doc_type=component` + `knowledge_role=capability`（字段、取值范围、宿主关系）与 `doc_type=recipe` + `knowledge_role=relation`（装配关系）。
3. **生效方式**：入库后**下一次生成**该 kind 才可用；**已经在跑的请求不受影响**（不热更新）。
4. **还不是终点**：知识入库只让生成节点知道怎么生成，**还必须在 `NODE_REGISTRY` 里注册 `generate:<kind>` 并按 §13.7 的六步清单走完**，否则槽位仍标 `unsupported`。**补课 = 知识入库 + 注册节点 + 补回归样例，三件都做完才算完。**
5. **不做在线研究**：生成请求内不发起外部检索，避免把网络的不确定性引进生成链路。

## 四、设计图纸 schema（新核心资产）

### 4.1 双投影原则

图纸 = 一份结构化 schema，两个投影：

| 投影 | 给谁 | 形态 |
| --- | --- | --- |
| JSON 文本 | 大模型 | LLM 只读写 JSON，从不看图 |
| SVG 渲染 | 用户 | 程序从 schema 确定性生成，用于审核 |

流程：LLM 生成/改 schema(JSON) → 程序渲染 SVG → 用户审图 → 反馈文字 → LLM 改 schema。

**现状补充**：`render_design_svg` 现在渲染三个面板——体量平面、主立面、侧立面，且体量矩形上已带 `data-design-path="/decisions/volumes/{index}"`。房间层落地后，平面面板的内容从"体量块"换成"房间色块 + 内墙 + 门窗图元"，立面面板不变（立面槽位本来就有）。这两个面板的数据源不同，渲染函数要拆成两个数据源而不是共用 `result.volumes`。

### 4.2 三层结构

用户确认：**分层**。房间拓扑、构件槽位分属不同节点，混一层会让缺口无法精确指向。这里补上 massing 层的明确地位。

```jsonc
{
  "schema_version": "3.0",          // 房间层是破坏性变更，故从 2.0 升到 3.0
  "massing": { "shape": "rectangle", "width": 12.0, "depth": 9.0,
               "floors": 2, "modeled_floors": 2, "floor_height": 3.0 },
  "rooms": [                          // 层一：房间拓扑层（设计节点产出）★新增能力
    { "id": "room_1", "name": "客厅", "floor": 1, "type": "living",
      "polygon": [[0,0],[6,0],[6,5],[0,5]], "double_height": true,
      "adjacent": ["room_2", "room_3"] },
    { "id": "room_2", "name": "楼梯间", "floor": 1, "type": "circulation",
      "polygon": [[6,0],[9,0],[9,5],[6,5]], "adjacent": ["room_1"] }
  ],
  "slots": [                          // 层二：构件槽位层（设计节点产出，专项节点消费）
    { "id": "slot_door_1", "kind": "door", "host": "room_1", "host_wall": "wall_x",
      "subtype": "double", "status": "missing" },
    { "id": "slot_win_1", "kind": "window", "host": "room_1", "host_wall": "wall_y",
      "subtype": "floor_to_ceiling", "status": "missing" },
    { "id": "slot_stair_1", "kind": "stair", "host": "room_2", "status": "filled" }
  ],
  "revision": 3                       // 重规划时递增，见 §6.4
}
```

- **massing 层**：体量真值（形状、宽深、层数、建模层数、层高）。房间层必须落在它之内（§1.4 第 3 条）。
- **房间拓扑层**：谁挨着谁、哪堵墙、挑空、功能类型。回答"空间关系"。**这是新增能力，验收见 §1.4。**
- **构件槽位层**：墙/楼板上的构件槽位，每个槽位带 `kind`、`subtype`、`host`、`status`。`kind` 的完整取值见 §13.4，字段契约见 §13.2。

**host 的双重语义**：`host` 现在既可以是房间（`room_1`），也可以是墙面（`wall_x`）。房间层落地前 `host` 只能指向立面推导出的墙；落地后优先指向房间，`host_wall` 由 `shell` 节点在生成内墙/外墙后回填。这个回填动作必须在设计节点之后、生成节点之前完成，否则门洞槽位找不到宿主。

### 4.3 槽位与缺口

- 单一 `slots[]` + `status` 字段，`filled`/`missing` 作为派生的调度视图，而非两份会互相漂移的数组（两个数组一旦不同步就是新 bug）。
- **词表统一**：槽位状态和 severity 只能有一套名字，这里直接沿用《能力闸门分级》已落地的 `RequirementSeverity = error | warning` 与 `needs_review` / `not_checked`，不另起 `blocking` / `pending` 之类的叫法——迁移期一件事两个名字必然出错。统一如下：

| 槽位 `status` | 含义 | 对应的旧词 |
| --- | --- | --- |
| `missing` | 图纸要求、尚未落地 | 旧 `pending` / `not_checked` |
| `generating` | 已派发，执行中 | 旧 `in_progress` |
| `filled` | 已落地且通过对账 | 旧 `completed`（但语义从"节点跑完"改成"元素存在"） |
| `unsupported` | 能力缺失，只标记不阻断 | 沿用 |
| `needs_review` | 交付媒介不一致等需人工裁决 | 沿用《能力闸门分级》 |

`severity` 只保留两级并沿用已落地的名字：**`error`（计划对象本身不合法，终止本轮）** 与 **`warning`（照常生成，差异进交付清单）**。"能力缺失降级为 warning"的含义不变。**LLM 不产出 severity，severity 由确定性规则判定。**

### 4.4 从 schema 到 SVG

沿用现有 `DesignDocument → resolve_design → render_design_svg` 链，但要拆成两个数据源（§4.1）。审核对象从"任务列表"变为"这张图"，反而更直观。

## 五、节点库（白名单）

### 5.1 节点类型

"动态"的只是：**选哪个节点、什么参数、拉什么知识、什么时机**。节点本身来自预定义白名单（安全边界），不许自由创建（《后续设想.md》§3.1 的死循环/越权顾虑由此化解）。

| 节点角色 | 职责 | 声明拉取的知识 | 输出 | 类型 |
| --- | --- | --- | --- | --- |
| `design` | 生成/修改三层 schema | `protocol`（协议）+ 能力边界 | massing + rooms + slots | LLM |
| **`shell`** | **rooms + massing → 墙 / 楼板 / 屋顶 / 内墙，整层幂等重建** | 无（确定性） | 蓝图主体骨架 | 确定性 |
| `generate:<type>` | 按构件类型生成 WILD 片段 | `capability` + `parameters` | WILD 片段 | LLM |
| `merge:<rule>` | **按批次增量** patch 进蓝图（不是最后一次性合并，见 §6.6） | 无——合并只读写结构，不消费知识 | 更新后的蓝图 | **确定性（无 LLM）** |
| `validate` | 确定性校验 + 修复 | 无（纯代码） | 缺口状态更新 | 确定性（图节点 id 为 **`final_validate`**，见 §13.4 的命名说明） |

**`shell` 为什么必须是独立节点**：房间是几何真值，内墙是房间边界的投影。房间一改，内墙必须整体重建，不能靠 merge 增量补。同时它是确定性的（无 LLM 调用），所以它能作为"对账基准"存在——蓝图主体由它产出，槽位对账只需要看构件有没有落上去。把它塞进 `merge` 会让"改房间"和"补构件"两件事耦合在一个节点里，重规划时无法区分该重建什么。

**`merge` 为什么是确定性的**：槽位已经把 `host` / `host_wall` / 坐标给全，生成节点又是逐字复制槽位坐标（§7.5 的门窗先例），所以"把片段贴进蓝图"是一次数据操作——追加元素 + 在宿主上登记开口——不需要模型做判断。真正需要判断的场合（片段贴不进去、约束冲突、涌现缺口）分别归给 `repair`（修正）角色和 `design` 角色，不归 merge（§6.6、§7.4）。

### 5.2 节点职责声明

每个节点在注册时显式声明自己的检索 query，调度器据此拼装（不再硬编码在节点内部）：

```python
NODE_REGISTRY = {
    "design": {
        "role": "design",
        "knowledge": ["doc_type=blueprint_spec+role=protocol",
                      "doc_type=component+layer=wild_schema"],
        "output": "design_schema",
    },
    "shell": {
        "role": "shell",
        "knowledge": [],                       # 纯确定性，不检索
        "inputs": ["design_schema.massing", "design_schema.rooms"],
        "projection": "full_schema",           # 它是几何真值的生产者，需要全量
        "idempotent": True,
    },
    "generate:window": {
        "role": "generate",
        "component_type": "window",
        "knowledge": ["doc_type=component+entity_type=window",
                      "doc_type=component+topic=parameters"],
        "projection": "slot_slice",            # 只拿本组槽位 + 宿主几何，见 §7.4
        "validator": "validate_opening_coords",
        "batch_by": ["subtype", "host_wall"],  # 见 §6.2
    },
    "merge:opening_into_wall": {
        "role": "merge",
        "knowledge": [],                       # 合并确定性执行、不消费知识，见 §6.6
        "projection": "host_subtree",          # 只拿被 patch 的宿主子树
        "patch_op": "DesignPatchOperation",
        "idempotency_key": "slot_id",          # 见 §6.5
    },
}
```

### 5.3 白名单与安全边界

- 调度器只能从 `NODE_REGISTRY` 派发；模型只能选节点 + 填参数，不能发明节点。
- 能力缺失（如"生成地基"）→ 槽位标 `unsupported`，不派发，不阻断。

## 六、调度器循环

### 6.1 LangGraph 落地形态

"动态创建节点"这个说法在 LangGraph 里做不到，必须说清边界在哪里，否则实施时会走成错的架构。

**硬约束**：LangGraph 的节点集在 `compile()` 之前就必须确定，运行时只能动态**选择路由目标**（`Command(goto=...)` 或条件边），不能运行时 `add_node`。所以：

- 白名单节点必须预先注册。11 类已实现构件（door、window、roof、railing、canopy、balcony、light、ramp、bay_window、cornice、chimney）的 `generate` / `merge` 角色展开后是二十多个图节点，这是可接受的（`graph.py` 现在就在为每类构件注册 `{type}_gen` / `{type}_val` 两个节点）。
- 因此"动态"的准确含义是：**静态拓扑 + 动态路由**。文档里不要再写"动态创建节点"。

**推荐形态：调度节点 + 回边，而不是一个内部 while 循环的大节点。**

```
scheduler ──(选目标)──> generate:<type> ─┐
    ^                                     │
    └────────── 对账后回边 ────────────────┘
```

**这一条是硬要求，理由是它会一次性丢掉三样东西**：

| 若写成单个 while 节点 | 后果 |
| --- | --- |
| 丢 checkpoint | 循环中途失败无法从断点恢复，只能整轮重跑 |
| 丢 interrupt | `design_review` 的人工审核无法在循环内挂起等待（`ws_agent` 的 resume 依赖 `snapshot.next` 判断中断点） |
| 丢 LangSmith 逐节点 trace | 这个项目的调试几乎全靠 trace，《当前遇到的问题.md》整篇就是 trace 对照的产物；循环内部只看得到一个巨型节点，可观测性直接归零 |

**可选优化**：同一批次内互相独立的槽位（同 `kind`、不同 `host`）可用 LangGraph 的 `Send` 做并行 fan-out，但必须先验证 `merge` 的 fan-in 顺序确定性；顺序不确定就不能并行，否则回归样例钉不住。

### 6.2 调度粒度

调度循环如果读成"每个缺口派发一个节点"，粒度就是槽位级的（`slot_win_1`）。按这个粒度，一栋别墅几十个门窗槽位就是几十次 LLM 调用加几十次 RAG 检索；现状是 skeleton 一次加每类构件一次。这个成本差异必须在设计阶段就定死。

**规定**：调度粒度是 `(kind, subtype, host_wall)` 分组，**一组一次调用，产出该组内全部槽位的片段**。节点内部允许处理 N 个槽位（输入是槽位列表，输出是片段列表）。单槽位派发只在"该组只剩一个槽位"时自然退化为单元素批。

### 6.3 预算

**预算按档位给值**（§2.2.2 承诺"档位同时是成本开关"，这里落地）：

| 预算项 | 低 `minimal` | 中 `simple` | 高 `standard` | 最高 `detailed` |
| --- | --- | --- | --- | --- |
| 单次生成的 LLM 调用次数（不含重试） | ≤ 4 | ≤ 6 | ≤ 12 | ≤ 20 |
| 调度迭代上限 `M` | 2 | 3 | 5 | 8 |
| token 预算（相对基线） | ≤ 1.0× | ≤ 1.2× | ≤ 1.5× | ≤ 2.5× |
| `repair` 触发 | 不允许 | 允许 | 允许 | 允许 |

三条规定：

1. **数值随档位单调递增**，且**每档都必须有上限**——高档位是"允许更贵"，不是"不设限"。超限一律终止并带 warning 交付（§6.8）。
2. 上表是**建议值**，必须在 P0.5 用双跑对照实测后修正（基线取 `standard`）。调整时保持单调性，不要只调某一档。
3. **低档位不触发 `repair`**：低档位的语义是"快速出一版体量"，与其花 LLM 调用去修，不如直接带 warning 交付并列出问题。这也让低档位的成本上限真正可控。

### 6.4 重规划语义

只写"重规划：回设计节点改 schema"是不够的，回退时已有产物的去向必须定义：

| 问 | 答 |
| --- | --- |
| 已 `filled` 的槽位保留吗 | 保留。重规划只针对缺口，不推翻已对账通过的产物 |
| schema 改了，已生成的片段还留吗 | 分情况：房间/massing 改动 → `shell` 整层重建，构件全部重生成；仅槽位增删 → 只处理受影响槽位 |
| 怎么表达"这轮改了什么" | `revision` 递增（§4.2），并把每轮的 slots diff 写进交付清单 |
| 用户已批准的 `design_review` 决策能复用吗 | 仅当 rooms / massing 未变时可复用；一变则必须重新审核，否则等于用户批准了一张已经改过的图 |
| 重规划算不算一次迭代 | 算，计入 M（§6.3） |

### 6.5 幂等与顺序确定性

循环里每补一个缺口就 patch 一次，`merge` 会被反复调用。两条要求：

1. **patch 按 `slot_id` 幂等**：patch 前先查该槽位是否已 `filled`；重复 patch 是覆盖不是追加。没有这一条，重试会产生重复门窗——而重复元素恰好可能绕过数量配额检查（配额只查区间，不查重复）。
2. **顺序确定性**：槽位迭代顺序必须稳定（按 `slots[]` 声明顺序，或按 `(kind, host_wall, id)` 稳定排序）；元素 id 必须确定性生成（`{slot_id}` 或 `{slot_id}_{n}`），不许用随机数、时间戳、uuid。顺序不定则同一输入两次生成结果不同，回归样例无法钉住，双跑对照也失去意义。

### 6.6 主循环与增量合并

```
读 missing → 按 (kind, subtype, host_wall) 分组选节点（白名单）→ 节点按声明拉知识
  → 执行 → 产出片段 → merge 节点幂等 patch 进蓝图（确定性，不消费知识）
  → merge 派生本次放置带来的新需求（确定性，写进 gaps，见 §6.6.5）
  → 确定性对账回写 filled/missing → 循环
  → 缺口清空后做一次收尾合并（全局约束 + 跨宿主校验）
```

#### 6.6.1 合并的时机：按批次增量，不是最后一次性合并

这是本方案与现状最大的一处结构差异：

| | 现状（项目里的 merge） | 本方案（文档里的 merge） |
| --- | --- | --- |
| 时机 | 所有构件节点跑完后一次性合并全部片段 | 每生成一批（§6.2 的分组）就合并一次，在调度循环内反复发生 |
| 触发 | 全部 `val` 节点 fan-in 到 merge | 调度器每轮迭代结束时调用 |
| 失败暴露 | 最后才知道"这个窗贴不进这面墙" | 该批次合并时立刻暴露，后续批次还能据此调整 |
| 工作集 | 一次面对全部构件 | 每次只面对一个宿主子树 |

这正是"动态合并节点"应有的形态：不是一个又大又靠后的收尾步骤，而是随生成节奏反复发生的编辑操作。现状那种"攒到最后一起合"等于把动态节点又退回成了批处理。

#### 6.6.2 增量合并管不了的两类东西，必须留一次收尾合并

1. **全局约束的强制**：`enforce_component_quota` 这类"总数必须在 min~max 之间"的判定与调整，只有等该类构件全部生成完才有意义，只能在收尾做。它**会改动蓝图**，所以属于合并的一部分，不归校验。
2. **需要全局视野的检查**：屋顶对整体的覆盖（`validate_roof_coverage`）、楼层之间的叠放包含（`validate_stacked_member_containment`）。这些**不放进收尾合并**，统一交给紧随其后的 `final_validate`（§6.6.5 的单点校验）——校验只在一个地方发生，避免"哪里算校验"含糊。

所以主循环的收尾是：**缺口清空 → 收尾合并（只做会改动蓝图的全局约束强制）→ 最终校验（全量 13 件套跑一次）**。收尾合并同样幂等（§6.5），重复执行不产生副作用。

#### 6.6.3 合并要不要调用大模型：规则知识的消费者是谁

"合并是修改蓝图的过程，所以需要检索规则知识"——这个判断对，但真正的设计问题是**这些规则由谁消费**：

| 方案 | 规则载体 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 规则在代码里，合并确定性执行** | `spatial_tools.py` 校验器 + `assembly.py` 修复算子 | 可靠、可幂等、零额外 LLM 调用、可单测 | 新增一条装配规则要改代码加测试 |
| **B. 规则在知识库，合并由 LLM 执行** | `recipe` + `relation` 检索片段进 Prompt | 加规则只需入库，不用改代码 | 每批次多一次 LLM 调用；LLM 可能改坏无关元素；patch 不天然幂等，违反 §6.5 |

**本方案选 A**，理由是它和本方案自己定的红线直接相关：§十一 的"确定性对账优先，LLM 不得自报完成"、§6.5 的幂等要求、§6.3 的调用次数预算。让 LLM 去改蓝图，等于把"谁把文件改坏了"重新变成不可归因的问题。

**规则知识仍然要检索，只是消费者换人**：`recipe` + `relation` 的片段供 **`repair`（修正）角色**在片段贴不进去、或校验报冲突时使用（§7.4 的 `repair` 行，那是唯一需要模型判断的环节），以及供 `design` / `generate` 角色了解装配约束。**合并本身只读写结构、不做判断，因而不消费知识。**

> **结论：走方案 A。** 本方案不留待确认的架构取舍。若日后目标变成"新增装配规则不必改代码"，需回到方案 B，并同步放宽上述三条红线——届时按 §十 的流程先跑一轮双跑对照再切换，不直接换。

#### 6.6.4 增量阶段跑什么校验、报错怎么处置

现状的 `run_validation_pipeline`（`app/services/agent_service.py:221`）是**全量流水线**：对整份蓝图按固定顺序跑 13 个校验器，并在 Step 1 / Step 2 失败时把后续步骤全部标记为"跳过"并提前返回。这套语义**不能直接用在增量阶段**，原因很直接——**建造中途的蓝图本来就是不完整的**，全量结构校验会把"还没建完"报成错误。

规定：

1. **增量阶段默认不跑校验**——校验是收尾之后的单点（§6.6.5）。唯一的例外是 §6.6.5 结尾那条：某类涌现缺口确实无法用几何推导表达时，允许跑该缺口对应的**单个**校验器，且结果只写 `gaps`。**任何情况下都不要在增量阶段跑全量流水线**，也不要用它的提前返回 / 跳过传播——那会把"这一批窗没贴好"放大成"整个校验停摆"。
2. **增量阶段的 `❌` 一律只记录、不触发修复**——不要在增量阶段区分"缺失"和"非法"。这个区分**不可实现**，已实测：13 个校验器里有 **4 个会在同一次输出里同时报这两类**（`validate_blueprint_structure` 11 条缺失 / 1 条非法、`validate_opening_coords` 2/2、`validate_roof_coverage` 2/1、`validate_element_required_fields` 8/2），按文案关键词分类不可靠；另有 2 个（`validate_wall_junctions`、`validate_stair_alignment`）的文案不含可判定的关键词，连启发式分类都做不到。既然分类本身不可靠，就不要把处置建在它上面。
3. **把判断推迟到蓝图完整之后**：收尾合并结束时蓝图已完整，这时任何 `❌` 都是真问题，直接进修复路径，不需要再分"缺失 / 非法"。而"槽位还没落地"这件事本来就由 `status=missing` 表达（§13.6.3），不依赖校验器的文案。
4. **增量阶段只做两件事**：对账更新 `filled/missing`（§13.6.3）、把涌现缺口写进 `gaps`（§6.7）。
5. **`fix_*` / `repair` 的主触发点是收尾合并之后的最终校验失败**，不是增量阶段。中途对"还没盖完的房子"跑修复循环，只会去修一个本来就还不该完整的东西。
6. 结构类校验（`validate_blueprint_structure`、`validate_element_required_fields`）在增量阶段失败时**不得中止调度循环**；只有在收尾合并之后失败才算 `error`，才走修复路径。

#### 6.6.5 校验节点的位置：单点在最末，不进循环

**结论：校验是一个节点，位置固定在收尾合并之后（`final_validate`），不放进调度循环。** 循环里需要的是另外两件事，不是校验。

三层职责，各有各的位置，**不要互相替代**：

| 职责 | 在哪 | 形态 | 频率 |
| --- | --- | --- | --- |
| **对账**：槽位是否落地 | 循环内 | 纯代码 diff（§13.6.3） | 每轮 |
| **派生**：刚放下的东西带来什么新需求 | 合并节点内 | 确定性几何推导，产出新槽位或新缺口 | 每次 patch |
| **校验**：整体是否合法 | 收尾合并之后的单节点 | 13 件套全量流水线 | 一次 |

**为什么校验不进循环**（四条，按危害排序）：

1. **会让 `repair` 的安全闸门失效。** 现有 `callback_node` 的提交判据是"执行修复动作后**全量复检、错误数下降才提交**"（`repair/workflow.py` 步骤 6-7）。中途蓝图一直在大，错误数本来就会变，这个判据在循环内失去意义——错误数下降可能只是"这一批没新增错误"，而不是"修好了"。
2. **振荡风险。** `repair` 改的是既有元素（`move_opening` / `resize_opening` / `reparent_opening`）。中途修完，后续批次的合并可能推翻它；反过来它也破坏后续合并依赖的宿主关系，两边互相覆盖。
3. **成本。** `repair` 是 LLM 调用，受 per-target × 3 约束（§13.4 规定 5）；放进循环等于再乘以迭代数（最多 `M` 轮，而批次可达十余个）。
4. **中途报错大多是假阳性。** 见 §6.6.4 第 2 条：4 个校验器把"缺失"与"非法"混在同一次输出里，无法在增量阶段干净过滤。

**涌现缺口不由校验发现，由合并节点算出来。**

这是本节的要点。以"楼梯嵌入 → 楼板必须开口"为例：它**不是**校验发现的问题，而是**几何后果**——合并节点放下楼梯时，同时掌握楼梯的底面投影与楼板的范围，两者的交集就是要开的洞，可以精确算出，既不需要校验器也不需要模型。

用校验去发现它，等于用"发现问题"的机制去干"推导需求"的活；而且为了让它生效，就被迫在循环里跑校验，把上面四个问题全部引进来。因此：

- **合并节点的职责包含"派生"**：每次 patch 之后，确定性推导本次放置带来的新需求（新的开口、新的宿主约束、新的附属槽位），写进 `gaps`（§6.7）。
- **派生的结果只作为新槽位 / 新缺口**，不直接触发修复；由后续批次或收尾合并处理。
- **派生必须是确定性的**：同样的输入得到同样的新槽位集合，可单测，不依赖模型判断。

**唯一例外**：如果某类涌现缺口确实无法用几何推导表达，才允许在增量阶段跑**该缺口对应的单个校验器**（不是全量流水线），且结果只写 `gaps`、不触发修复。

**必须实现的派生规则（初始四条，实现时按此写，不要自行增删）**：

| 触发（merge 刚放下什么） | 派生结果 | 产出 |
| --- | --- | --- |
| 楼梯放进某个房间 | 该层楼板在楼梯投影处需要开口 | 新槽位 `kind=floor_opening`，`host_wall` 留空，`host` 指向该楼板 |
| 阳台放进某面墙 | 阳台自带悬挑板与 U 形栏杆（现有 `deduplicate_balcony_representations` 的语义即此） | 新槽位 `kind=railing`，`host_wall` 继承阳台的宿主墙；同时**禁止骨架再写一份手绘 floor**，否则会与阳台重叠 |
| 门 / 窗 / 凸窗放进某面墙 | 宿主墙需要登记该开口，且**同一面墙上的开口不得重叠** | 不产生新槽位；写入宿主的开口登记表，冲突时产出 `error` 级缺口 |
| 雨篷 / 门廊放进某面墙 | 檐下净空要求 | 不产生新槽位；净空不足时产出 `warning` 级缺口 |

三条实现要求：

1. **派生只产出槽位或缺口，不直接改蓝图**——改蓝图是 `merge` 自己的职责（`patch`），派生只是"记账"。
2. **派生必须可单测**：给定「已放下的元素 + 宿主几何」，输出必须是确定的槽位集合。测试样例至少覆盖上表四行。
3. **新增派生前先确认它不是校验的活**：判据是"这件事能不能只看刚放下的东西和它的宿主算出来"。能，就是派生；不能（需要全局视野），就属于收尾之后的全量校验（§6.6.2）。

### 6.7 缺口契约 gaps[]

每个节点输出强制带结构化缺口，缺口既驱动下一个节点选择，也驱动检索 query 拼装：

```jsonc
{
  "slot_id": "slot_win_1",
  "kind": "window",
  "subtype": "floor_to_ceiling",
  "severity": "error",               // error | warning（§4.3 词表）
  "source": "plan",                  // plan（图纸计划内）| emergent（执行中涌现）
  "evidence": "图纸槽位未落地到蓝图"
}
```

**两种缺口（关键，来自讨论）**：
1. **计划内缺口**：图纸画完就有的 missing（缺窗、缺门）→ 驱动主循环；
2. **涌现缺口**：**由合并节点在放置时确定性推导出来的新需求**（楼梯嵌入 → 楼板必须开口 → 开口本身是新槽位），不是校验发现的。推导规则见 §6.6.5，写回见 §13.6.2。若不回写，合并失败会被静默吞掉——正是"校验全绿但引擎重建失败"类事故的动态版。

两类缺口都必须进 `gaps`，且 `source` 字段区分（`plan` / `emergent`）。**校验器不是涌现缺口的发现者**：校验只在收尾合并之后跑一次，那时发现的问题已经属于"要修"，不属于"要补缺"。

### 6.8 终止 / 重规划 / 降级

| 场景 | 决策 |
| --- | --- |
| missing 空且无 emergent gap | 进入最终校验 |
| error 级缺口有关联节点 | 派发补缺 |
| error 级缺口无节点能补（能力缺失） | 转 `unsupported`，继续（沿用"能力缺失只标记不阻断"） |
| 补缺后对账仍失败 N 次 | 重规划：回设计节点改 schema（§6.4） |
| 迭代超上限 M 次 / token 超预算 / 重规划超 1 次 | 终止，带 warning 交付（防死循环） |

### 6.9 filled/missing 的确定性对账

`filled/missing` 的更新者是**确定性对账**（图纸槽位 vs 蓝图实际元素做 diff），LLM 只负责发现涌现缺口，**不许自报"我做完了"**。这取代了《当前遇到的问题.md》§7 里"节点完成≠业务验收完成"的老问题——槽位 diff 天然区分两者。

## 七、节点输入按需组装（知识 + 蓝图）

### 7.1 节点声明 query → 调度器拼装

- 生成节点（准备生成窗户）→ 只拉窗户的 `capability + parameters`；
- 合并节点（窗户嵌入墙）→ **不拉知识**（确定性执行，见 §6.6.3）。规则只在校验报冲突、需要判断怎么处置时，由 `repair`（修正）角色按失败类型检索；
- 设计节点 → 拉 `protocol`（整体协议/坐标系）+ `wild_schema`（能力边界，房间层落地前必须拉到，否则设计节点会画出系统实现不了的房间）。

### 7.2 与现有过滤对的映射

现有检索契约天然按此分好，直接复用（**位置已按 v2 订正**）：

| 过滤对 | 现有位置 | 消费节点 |
| --- | --- | --- |
| `blueprint_spec` + `protocol` | `policy.py:61-69`、`services/agent_service.py:1192-1196`、`planning/workflow.py:59-62` | design / patch |
| `component` + `capability` | `policy.py:61-69`、`services/agent_service.py:1196-1200` | generate |
| `component` + `topic=parameters` | `planning/workflow.py:55` | generate |
| `component` + `entity_type=<类型>` | `component_workflow.py:92`、`skeleton_workflow.py:71-72`、`services/agent_service.py:1230-1250` | generate（按构件类型细分） |
| `recipe` + `knowledge_role=relation` | `skeleton_workflow.py:70`、`policy.py:61-69` | **`repair`**（片段贴不进去时的判断依据，见 §6.6.3）；merge 不消费 |
| `recipe` + `entity_name` | `planning/workflow.py:54`、`architecture/workflow.py:132` | **`repair` / `design`**（装配关系点名）；merge 不消费 |

**一条新增要求**：设计节点必须拉到 `wild_schema`（`architecture/workflow.py:133` 已在用这一对），因为房间层是否在能力范围内、槽位 `kind` 是否有对应实现，都只能靠这份知识判断。否则设计节点会自由发挥出系统根本没有的构件类型，最后全部落到 `unsupported`。

### 7.3 蓝图按需投影（不是把蓝图文件发给模型）

一个常见直觉是"把蓝图文件作为提示词发给每个节点，模型才能生成得更准"。方向是对的，实现必须收窄：**发给节点的是程序从图纸和蓝图里截取的、该节点需要的那部分片段，不是整份文件。**

| 维度 | 发整份蓝图 | 发切片 |
| --- | --- | --- |
| 精确性 | 生成一个窗户，却要读几十面无关的墙 | 只给它要开口的那面墙与其他相关宿主 |
| 成本 | 随建筑规模线性膨胀，且每轮迭代重发 | 只随该节点负责的槽位数增长 |
| 注意力 | 大量无关内容稀释真正的约束（配额、宿主 id） | 关键约束不被淹没 |
| 可归因 | 模型自行在全文里找宿主，错了无法定位 | 切片由程序给出，错了能归因到投影逻辑 |

**关键原则：投影由程序（确定性代码）完成，不让模型自己在全量内容里找宿主。** 模型只做"填空"，不做"检索宿主"——这正是《后续设想.md》里"Agentic Workflow 而非完全 Agent"的边界所在。

三个投影层级，按节点角色分配：

| 投影 | 内容 | 消费者 |
| --- | --- | --- |
| 整份 JSON | 完整 schema / 蓝图 | `patch`（ScenePatch 必须知道当前文件）、最终校验、审计 |
| 按宿主切片 | 该节点负责的槽位 + 槽位宿主的几何（一面墙的坐标、一个房间的边界）+ 与这些宿主直接相关的约束 | `generate:<type>`（构件生成） |
| 全局摘要 | 结构化摘要 + 全局约束（材质 ID 白名单、构件配额、立面上限）+ 确定性空间不变量 | `generate` 的全局部分；`repair`（**它同时拿全局摘要 + 失败切片**，见 §7.4） |

### 7.4 节点输入契约

每个节点在 §5.2 的 `NODE_REGISTRY` 里声明自己需要哪些投影，调度器按声明组装：

| 节点角色 | 蓝图投影 | 知识投影 | 改造前的现状对照 |
| --- | --- | --- | --- |
| `design` | 无（还没有蓝图，正在造） | protocol + wild_schema | architecture 节点 |
| `shell` | rooms + massing（全量，它自己就是生产者） | 无 | skeleton 节点 |
| `generate:<type>` | **按宿主切片**：本批槽位 + 宿主几何 | capability + parameters | 组件生成节点：全量 `skeleton_summary` + facade_plan + `opening_slots` 切片 + 配额 |
| `merge:<rule>` | 增量 patch 的宿主子树 | **无**（不消费知识，见 §6.6.3） | 现状 merge 节点一次性合并全部片段，**不调用模型**；本方案保留"无 LLM"，但改为按批次增量合并 |
| `validate` | 无（纯代码） | 无 | validate 节点 |
| `patch` | **整份 JSON** | protocol + capability + relation | patch 节点：`current_blueprint` |
| `repair`（修正） | 失败切片（出错元素 + 当前参数 + 允许修改的关联实体 + 已通过元素 ID 黑名单） | 按失败类型精准检索 | callback 节点：`build_callback_prompt` |

一句话原则：**能定位到"某一个槽位 + 它的宿主"的节点，就不要给它整份蓝图。**

### 7.5 已有先例：开口槽位切片已经在跑

这条路线不是新发明，门窗上已经跑通了。`build_component_prompt`（`app/agent/prompts/generation.py:104`）里的 `slot_section` 做的就是 §7.3 的规则：

- 从 `design_brief.opening_slots` 筛出属于本构件类型的槽位，序列化成结构化片段；
- 标注"程序解析的精确开口槽位（最高优先级）"；
- 要求"每个输出必须选择一个不同槽位，并逐字复制该槽位的 `wall_id`→`parentWall`、`from`、`width`、`height`。**不要自行计算或微调坐标**；合并阶段会再次吸附"。

这就是"程序截取片段 + 模型只填空 + 确定性对账"的完整闭环，只是目前**只覆盖 `window` / `door`**（`generation.py:146` 的类型判断），其余构件仍只有全量摘要加配额。

所以本节的实施动作是把这个模式推广到全部构件类型：每个槽位带 `host` / `host_wall`，生成节点按 §6.2 的分组只拿本组槽位与宿主几何，而不是全量 `skeleton_summary`。同时保留摘要里的全局约束（材质白名单、配额、立面上限）——那些是全局性的，切不开。

**一个已知缺口**：生成节点之间目前并行且互不可见，同一面墙上门和窗的洞口冲突只能等 merge 之后的校验加修复兜底。§6.2 的 `batch_by: [subtype, host_wall]` 把同宿主槽位收进同一批，让冲突在生成阶段就被看见，是这条的正确解法。

## 八、对账与验收

### 8.1 槽位 diff 即验收

程序拿图纸槽位和蓝图元素做 diff，每个槽位有 `filled` / `unsupported` / `needs_review` 明确结果，替代原来的"自然语言 acceptance 编译 + 关键词匹配"。

**这已有原型**：`validation/design_constraints.py:117-148` 的 `validate_design_brief_constraints` 已经实现了"槽位 → 元素"的匹配（比对 `parentWall` / `from` / `width` / `height`）并上报 `missing_slot_ids`。本节的实施起点是这个函数，不是从零写：

1. 摘掉它的窄口径限制（现在只覆盖 `door` / `window` / `bay_window`，且只在配额要求"全量实现"时才启用）；
2. 把匹配对象从 `design_brief.opening_slots` 换成图纸 `slots[]`；
3. 输出从 `errors: list[str]` 换成结构化的 `{slot_id, status, evidence}`；
4. 保留它的容差逻辑（`_opening_values_match`，0.01）。

### 8.2 溯源字段（对账的地基）

要对账，蓝图元素就必须能回答"我是由哪个槽位生成的"。现状是部分具备：

- `facade.py:372` 已经往开口上写 `opening_slot_id`；
- 但这是立面链内部的字段，不是 blueprint 契约的正式字段，merge / patch 之后是否保留没有保证。

**要求**：`slot_id` 提升为蓝图元素的正式溯源字段，由 merge 节点在 patch 时写入，`validate_reference_integrity` 增加"带 `slot_id` 的元素其槽位必须存在"的检查。没有这一步，"确定性对账"就还是关键词匹配换了个马甲——匹配不上的时候你分不清是"没生成"还是"生成了但对不上"。

### 8.3 severity 分级沿用

`error` 才阻断，`unsupported` / `needs_review` 只标记——迁移 `evaluate_acceptance_results` / `blocking_acceptance_failures` 的判定逻辑，不重写（词表见 §4.3）。

### 8.4 最终校验

最终校验仍跑 13 件套确定性校验器（附 A）+ `check_blueprint_render.mjs` 真实编译重建，作为最后一道闸。**房间层落地后追加 §1.4 的八条 + §1.4.1 的三条竖向规则**（实现为一个新增工具模块，签名遵守 §13.10，数据来源见 §13.10.1）。

### 8.5 图纸审核的交互契约（唯一的人工环节）

审核是流程里唯一需要人参与的地方，必须定死，不能留给实现者猜。沿用现有 `build_design_review_interrupt`（`app/design/review_outcome.py:14`）的既有形状，只把载荷从 `DesignDocument` 换成三层 schema：

**中断载荷**（程序 → 前端）：

```jsonc
{
  "type": "design_review",
  "question": "请审核设计图纸，然后批准或提出修改意见。",
  "schema": { /* 完整三层 schema：massing + rooms + slots */ },
  "preview_url": "/api/designs/{session_id}/preview.svg?revision={revision}",
  "slots_summary": { "total": 24, "unsupported": 2 },   // 让用户一眼看到哪些做不了
  "resume_examples": {
    "confirm": { "action": "confirm" },
    "revise":  { "action": "revise", "feedback": "请填写需要修改的地方" }
  }
}
```

**恢复输入**（前端 → 程序）：

| 动作 | 载荷 | 程序行为 |
| --- | --- | --- |
| 批准 | `{"action": "confirm"}` | schema 冻结，`revision` 不变，进入 `shell` |
| 提意见 | `{"action": "revise", "feedback": "..."}` | 回 `design` 节点，反馈作为 B 段输入（§13.11），`revision` 递增 |
| 直接改图 | `{"action": "revise", "schema": {...}}` | 用提交的 schema 覆盖，**仍须过 §13.11 的设计节点校验** |

四条硬规定：

1. **审核对象是图纸（schema + SVG），不是任务列表**——任务列表审核（`plan_review`）已删除（§3.1）。
2. **用户直接改 schema 时不能绕过校验**：提交的 schema 必须重跑 §13.11 的五项检查，不过就打回并说明原因。
3. **`unsupported` 槽位要在审核时可见**：用户必须在批准之前看到"哪些要求当前做不了"（`slots_summary`），而不是生成完才发现。
4. **重规划后必须重新审核**：`rooms` 或 `massing` 一变，之前那次批准作废（§6.4 已定）。

## 十、分阶段实施与出口判据

> 落地顺序采用**绞杀者模式（strangler fig）**：新流程先跑通、再切换、最后清理，避免一次性推倒导致全绿门禁全红。

### 10.1 为什么保留双跑对照

《后续设想.md》§四原本主张"模式切换 + 收集数据再决定推广"（成功率 / token / 时长 / 满意度四个维度对照）。直接跳到绞杀者替换等于放弃对照实验，也等于放弃了那条"数据说话"的路线。

对照组放在 P0.5：不是为了永久保留两套流程，而是为了在 P4 删除之前，有数据证明新链路没倒退。**没有基线的删除是不可逆的**——删完才发现质量下降，恢复成本远高于当初测一趟。

### 10.2 关键回归样例（必须钉住）

家具/照明/阳台或雨篷/柱梁（《当前遇到的问题.md》§15.12）、旧 `12m×8m + 两层 + gable + 出檐`（§15.13）、幕墙建筑 door 配额（`test_architecture_quota_consistency.py`）、普通生成反例（§15.14）。

**追加**：房间层需要自己的样例——单层三室、两层带楼梯间、含挑空、以及一个"房间合计超出体量"的负例（必须被 §1.4 第 3 条拦住）。

## 十一、红线与风险

- 🔴 **能力缺失只标记、不阻断**（用户既定原则）：缺能力 → `unsupported`，绝不因发散需求把能力缺失当 bug 修。
- 🔴 **发散 ≠ 什么都支持**："先外墙后内墙"是调度粒度（✅ 放开）；"先做地基"是能力边界（❌ 标 unsupported）。二者必须区分。
- 🔴 **节点库白名单是安全边界**：模型只能选节点 + 填参数，不能发明节点，杜绝死循环/越权。
- 🔴 **校验节点不进调度循环**：校验固定在收尾合并之后的 `final_validate` 单点执行；循环内只有"对账"与"合并派生"两件事（§6.6.5）。把校验放进循环会让 `repair` 的"错误数下降才提交"闸门失效并引发振荡。
- 🔴 **档位调高不等于能力变强**：高 / 最高粒度要求但不支持的项标 `unsupported` 只标记不阻断，且必须在交付里显式列出"本次高粒度要求但未支持的项"；不得为了让档位看起来生效而静默降级（§2.2.3）。
- 🔴 **确定性对账优先**：filled/missing 由程序 diff 决定，LLM 不得自报完成。
- 🔴 **闸门不得先于能力放宽**：房间层落地前，`_UNSUPPORTED_INTERIOR_TERMS` 继续生效；落地并通过 §1.4 后才移除对应词条（§1.5）。
- 🔴 **调度器不得写成单个 while 节点**：会丢 checkpoint / interrupt / 逐节点 trace（§6.1）。
- 🔴 **中断点改动必须三处同步**：`ws_agent.py` + `agentBridge.ts` + 端到端恢复用例（§3.6）。
- 🟡 **两套事实源清零**：steps 与 dynamic_tasks 编译链删除后，调度器是唯一事实源。
- 🟡 **能力缺失项在最终交付要显式列出**，不能静默丢（继承《当前遇到的问题.md》§15.4）。
- 🟡 **房间层可回退**：房间层失败时退回"massing + 立面槽位"的现状能力，并在交付里显式声明（§1.2）。
- 🔴 **节点不接收整份蓝图，除非角色需要全局一致性**：能定位到"槽位 + 宿主"的节点就给切片，投影契约见 §7.4。
- 🔴 **投影由程序完成**：不让模型自己在全量内容里找宿主。模型只填空，不检索——这是"Agentic Workflow 而非完全 Agent"的边界。
- 🔴 **合并确定性执行**：merge 只读写结构、不做判断，不调用 LLM（§6.6.3）。需要判断的场合走 `repair`（修正）角色，涌现缺口走 `design` 角色。

### 13.2 槽位契约（最核心的数据结构）

```jsonc
{
  "id": "slot_door_3",        // 必填。格式 slot_<kind>_<序号>，序号在同一 kind 内从 1 递增
  "kind": "door",             // 必填。取值必须是 NODE_REGISTRY 里已注册的 kind
  "subtype": "double",        // 选填。自由文本，同 kind 内细分用（示例：落地窗、双开门）。
                              // 取值不设闭集，但同一 kind 内同类槽位必须用同一种写法（否则分组会碎）。
                              // 生成节点按 (subtype, host_wall) 分组（§6.2）
  "host": "room_1",           // 必填。宿主：房间 id 或元素 id（§4.2 的 host 双重语义）
  "host_wall": "wall_x",      // 条件必填。附着在墙面/开口上的构件必须有，即 door / window / bay_window
                              // （对齐 spatial_tools.py:43 的 WALL_OPENING_COMPONENT_TYPES）。
                              // 其余 kind 不强制，按各自的知识分片规定。
                              // 由 shell 节点在生成墙之后回填，设计节点可以先留空
  "status": "missing",        // 必填。missing | generating | filled | unsupported | needs_review（§4.3）
  "params": {},               // 选填。槽位级参数（如 stair 的踏步数、window 的分格数）
  "severity": "error"         // 选填，默认 error。判定规则见 §13.3
}
```

五条规定：

1. **`id` 必须确定性生成**：不许随机数、时间戳、uuid；同一份输入两次生成必须得到相同的 id 集合。
2. **数组顺序稳定**：同一 `kind` 的槽位按 `id` 排序，保证迭代顺序确定（§6.5）。
3. **`host_wall` 由 `shell` 节点回填，不由设计节点猜**：设计节点只声明"这个房间需要一扇窗"，落在哪面墙由 `shell` 生成墙之后按 §13.6.4 分配。
4. **`unsupported` 槽位不派发**，直接进交付清单。
5. **槽位是唯一事实源**：生成什么、生成几个、放在哪里全部由槽位决定；生成节点不得增删槽位。

#### 13.2.1 房间契约（rooms[]）

```jsonc
{
  "id": "room_1",                          // 必填。格式 room_<序号>，同层内从 1 递增
  "name": "客厅",                          // 必填。展示用中文名，可重复
  "floor": 1,                              // 必填。楼层，1 起，不得超过 massing.modeled_floors
  "type": "living",                        // 必填。闭集，见下表
  "polygon": [[0,0],[6,0],[6,5],[0,5]],    // 必填。轴对齐矩形四角，逆时针
  "double_height": false,                  // 选填，默认 false。挑空房间为 true
  "adjacent": ["room_2"]                   // 选填，默认 []。必须对称（§1.4 第 4 条）
}
```

`type` 是**闭集，不得自行扩展**。要扩集必须同时改 §1.3 的能力声明与 SVG 配色，不能只在代码里加一个枚举值：

| `type` | 含义 |
| --- | --- |
| `living` | 起居、客厅、家庭厅 |
| `bedroom` | 卧室、书房 |
| `kitchen` | 厨房、餐厅 |
| `bathroom` | 卫生间、盥洗 |
| `circulation` | 楼梯间、门厅、走廊 |
| `storage` | 储藏、设备间 |
| `garage` | 车库 |
| `service` | 其他辅助空间 |

**`polygon` 只接受轴对齐矩形**（4 个点、对边平行于 X/Z 轴）。不是任意多边形——曲线、斜边、L 形房间必须拆成多个矩形。这就是 §1.3 里"支持正交房间"在数据层的确切含义。

### 13.3 缺口契约

```jsonc
{
  "slot_id": "slot_win_1",     // 计划内缺口必有；涌现缺口可为 null
  "kind": "window",
  "subtype": "floor_to_ceiling",
  "severity": "error",          // error | warning（§4.3 词表）
  "source": "plan",             // plan（图纸计划内）| emergent（执行中涌现）
  "evidence": "图纸槽位未落地到蓝图",
  "related_ids": []             // 涌现缺口的相关元素 id（如"楼板必须开口"涉及哪块楼板）
}
```

`severity` 的判定规则（**由程序判定，LLM 不产出 severity**）：

| 情形 | severity |
| --- | --- |
| 槽位对应的 `kind` 在 `NODE_REGISTRY` 里有注册节点 | `error`（要补） |
| 槽位对应的 `kind` 没有注册节点 | 转 `status=unsupported`，降为 `warning`，不阻断 |
| 校验器报出结构性问题（引用缺失、几何非法） | `error` |
| 交付媒介不一致、纯主观要求 | `warning`（沿用《能力闸门分级》的 `needs_review` 处置） |

### 13.4 节点注册表（完整）

`NODE_REGISTRY` 是唯一派发来源，字段含义如下：`role`（角色）/ `knowledge`（声明的检索 query）/ `projection`（需要的蓝图投影）/ `inputs`（读取的 state 字段）/ `outputs`（写入的 state 字段）/ `validator`（关联的确定性校验器）/ `batch_by`（§6.2 分组键）/ `idempotency_key`（§6.5）。

| 节点 | role | projection | validator | 备注 |
| --- | --- | --- | --- | --- |
| `design` | design | 无 | — | 产出 massing + rooms + slots；必须拉 `wild_schema` |
| `shell` | shell | full_schema | `validate_wall_junctions`、`validate_reference_integrity` | 确定性；幂等重建；负责回填 `host_wall` |
| `generate:<kind>` | generate | slot_slice | 见下 | 每个需要 LLM 生成的 kind 一条，当前 11 条；`batch_by=["subtype","host_wall"]` |
| `merge:<kind>` | merge | host_subtree | `validate_opening_coords` 等 | 确定性；`idempotency_key="slot_id"` |
| `validate` | validate | 无 | 13 件套全跑 | 纯代码。**命名说明：`role` 叫 `validate`，图节点 id 叫 `final_validate`**（沿用现有 `graph.py:325` 的注册名）。文档里两处指同一个节点，不要理解成两个 |
| `patch` | patch | 整份 JSON | 既有 ScenePatch 校验 | 编辑路径，允许用 LLM 产出 patch 操作 |
| `repair`（修正） | repair | 失败切片 | 按失败类型 | **唯一允许对蓝图做判断性修改的角色**（§6.6.3）；承接现有 `repair/` 模块与 callback 节点。**它不直接改蓝图，只产出修复工具动作由程序执行**（§13.10）。命名见下方"名称防混" |

**注意 `patch` 与 `merge` 的区别**：`patch` 是编辑路径，由 LLM 产出 ScenePatch 操作（复用 `agent_service.query_structured(..., expected_output="patch")`）；`merge` 是生成路径，确定性执行，不调用模型。两者共用 `DesignPatchOperation` 这个数据结构，但**不要合并成一个节点**。

**名称防混：三个都带"修/改"字的东西，是三层不同机制，不要混用名称**

| 名字 | 是什么 | 调模型吗 | 谁触发 |
| --- | --- | --- | --- |
| **`merge` 的 patch** | 把生成好的片段贴进蓝图（追加元素、在宿主上登记开口） | ❌ | 调度器每批次（§6.6.1）、收尾（§6.6.2） |
| **`fix_*`（确定性修复算子）** | 机械修复：坐标换算、材质引用补齐、屋顶覆盖补全、尺寸纠正等 | ❌ | 校验流水线内按 `_FIX_MAP` 自动派发（附 A.2） |
| **`repair`（修正角色）** | 前两层都解决不了时，由模型做判断性修改 | ✅ | 校验报出无确定性修复方案的错误，或涌现缺口需改动既有元素 |

把 `fix_*` 说成"合并的修复"、或让 `repair` 接手本来 `fix_*` 能处理的错误，都会让"谁把文件改坏了"变得不可归因。因此规定：

1. 校验报错后**先查 `_FIX_MAP`**：有对应 `fix_*` 就确定性修复，**不许直接把错误丢给 `repair`**。
2. `fix_*` 修复失败（返回 ❌ 或未产生有效变化）时，才升级到 `repair`。
3. `repair` 的改动范围限制在失败切片内：出错元素 + 允许修改的关联实体。**已通过对账的槽位元素是黑名单，不得改动**（沿用 `build_callback_prompt` 的 `passed_component_ids` 机制）。
4. `repair` 之后必须重新对账（§13.6.3），它的修改不能绕过对账。
5. **`repair` 的预算是 per-target 的，不是全局轮数**：沿用现有机制——`max_retries`（默认 3）配 `component_retry_counts`，**每个失败目标最多修 3 次**；`retry_count` 只作遥测记录，**明确不作为截断门禁**（`graph.py:231` 的现有注释即此意）。只有"仍存在还有剩余重试次数的失败目标"时才允许再次进入 `repair`（`_final_validate_dispatch` 的现有判定，`graph.py:226-266`）。因此修复预算是 O(失败目标数 × 3)，而不是一个固定轮数——**不要改成全局轮数上限**，那会让一个新出现的失败目标被别的目标耗尽的预算连坐。
6. **`repair` 与调度循环是两套独立的上限，不要合并计数**：§6.3 的迭代上限 M 管的是缺口循环（`design → generate → merge → 对账`），`repair` 管的是校验后的修复路径。两者各有上限，互不占用对方的额度。

**需要 `generate` / `merge` 节点的 kind（当前 11 类）**：`door`、`window`、`roof`、`railing`、`canopy`、`balcony`、`light`、`ramp`、`bay_window`、`cornice`、`chimney`。

**另外两类不走 `generate` 节点，不要混进来**：

- `stair`：房间层带来的槽位 kind（§4.2 的 `slot_stair_1`）。楼梯几何是确定性展开（§3.3），由 `shell` 承担，**不注册 `generate:stair`、不调 LLM**。
- `wall` / `floor`：结构主体，由 `shell` 从 rooms + massing 确定性产出，**不派发**。

**新增 kind 一律按 §13.7 的清单走。**

### 13.5 提示词组装契约 ★★★

生成节点的 system prompt 由**程序**按固定五段拼装，顺序不得调换：

| 段 | 内容 | 来源 | 是否含具体构件字段 |
| --- | --- | --- | --- |
| **A 角色定义** | 一段跨类型共用的通用文本 | 代码常量，**全类型共用同一份** | ❌ 不含 |
| **B 槽位切片** | 本批槽位的 JSON + 宿主几何 | 程序从 schema / 蓝图截取（§7.3） | 由槽位数据决定 |
| **C 知识** | capability + parameters | RAG 检索（§7.1） | ✅ 字段约束只在这里 |
| **D 全局约束** | 材质 ID 白名单、配额、立面上限、档位 | 程序从 schema 与 shell 产物推导 | 不含 |
| **E 输出格式** | JSON 数组骨架 | 代码常量 | 不含 |

**五条硬规定**：

1. **禁止 per-type 静态提示词常量。** 字段级约束（必填项、取值范围、单位约定）必须来自 C 段的 RAG `capability` 知识，不许写成代码里的字符串。现存的 `_COMPONENT_RULES`（`components.py:49`，11 段）必须在 P4 之前**下沉进知识库**（`doc_type=component` + `knowledge_role=capability` 分片），代码侧只保留 A 段这类跨类型共用文本。
2. **A 段必须是全类型共用的同一份文本。** 如果实现时发现"门和窗的 A 段不一样"，说明你正在把字段清单往 A 段里塞——那属于 C 段。
3. **禁止在提示词里写死数量与位置**：不许出现"生成 2 个门""对称布置 4 扇窗"这类文本。数量与位置唯一来自 B 段的槽位数据。
4. **B 段只放本批槽位与宿主几何**，不放全量蓝图（§7.3）。
5. **B 段必须包含"逐字复制坐标，不得计算"的措辞**，与门窗先例一致——`generation.py:104` 的 `slot_section` 已有可用措辞，直接沿用。

**自检方法**：新增一个构件类型时，如果 A 段或 E 段需要改动，说明组装契约已被破坏。

### 13.6 确定性算法

#### 13.6.1 批次分组

```
输入: schema.slots[]
1. 过滤掉 status ∈ {filled, unsupported, needs_review} 的槽位
2. 按 kind 分组
3. 每组内按 (subtype, host_wall) 再分组
4. 输出批次列表；批次顺序 = kind 的注册顺序，组内按 (subtype, host_wall) 字典序
   不得依赖 dict 插入顺序或集合遍历顺序
```

#### 13.6.2 幂等 patch

```
merge(slot, fragment):
  1. 校验 fragment.slot_id == slot.id；不等则丢弃并记缺口
  2. 若蓝图已存在 element.slot_id == slot.id 的元素：
       替换该元素（不是追加）
     否则：
       追加元素，并写入 slot_id
  3. 在宿主上登记开口/引用关系时，先按键去重
  4. 返回 patch 摘要 {slot_id, action: added|replaced}
```

**★ 强制重新对账规则（否则交付清单会说谎）**

蓝图**不是只读**的。以下操作都会增删改 `geometry.elements` / `geometry.components`，从而让此前写入的槽位状态失效：

| 操作 | 位置 | 会做什么 |
| --- | --- | --- |
| `enforce_component_quota` | `assembly.py:223` | 增删构件以符合配额 |
| `deduplicate_balcony_representations` | `assembly.py:20` | 删掉与 balcony 重叠的手写 floor 及其独立 railing |
| `remove_ground_level_railings` | `assembly.py:162` | 删掉落地的栏杆 |
| `apply_fixes` → `fix_*` 家族 | `assembly.py:283` → `spatial_tools.py` | 8 个修复算子，含删除与改写 |
| `execute_repair_actions` | `repair/tools.py:230` | 模型修复动作，含 `remove_entity` |
| `shell` 幂等重建 | §13.12 | 整层删除后重建 |

**规定**：上述每一个操作**之后**都必须重新跑一次 `reconcile`（§13.6.3），再继续下一步。不重新对账的后果是静默的——一个已经标 `filled` 的槽位，其元素可能刚被删掉，而交付清单仍把它算作已完成，`filled + unsupported + needs_review == total` 这个等式**依然成立**（因为它统计的是槽位状态，不是蓝图实际内容），所以**不会报错**。

**交付前的断言**：出交付清单之前，必须重新对账一次并断言槽位状态是最新的；断言失败（数量对不上）属 `error`，不得静默交付。这是 §13.9 第 4 条的强制点。

#### 13.6.3 对账

```
reconcile(schema, blueprint):
  filled = { e.slot_id for e in blueprint 元素 if e.slot_id } ∩ { s.id for s in schema.slots }
  对每个 slot:
    slot.id ∈ filled          -> status = filled
    slot 已标 unsupported      -> status = unsupported
    slot 有 needs_review 标记  -> status = needs_review
    否则                       -> status = missing
几何比对沿用 §8.1 的容差 0.01（`_opening_values_match`）
```

#### 13.6.4 host_wall 分配（`shell` 节点内）

```
输入: schema.rooms[]、schema.massing、需要宿主墙的槽位集合
1. 由相邻房间共享边生成内墙，由 massing 轮廓生成外墙
2. 对每个需要宿主的槽位，在其 host 房间的边界墙里选一面：
   - 优先选朝向与该 kind 默认朝向一致的外墙
   - 同一面墙上的槽位按 id 排序依次分配，累计宽度不得超过墙长
3. 结果写回 slot.host_wall，并保证确定性（同样输入必须得到同样分配）
4. 分配不下（墙长不够）-> 该槽位标 needs_review，不阻断，进交付清单
```

#### 13.6.5 调度循环

```
iteration = 0
while iteration < M:
    pending = [s for s in schema.slots if s.status == 'missing']
    if not pending and not emergent_gaps: break
    for batch in group_batches(pending):            # 13.6.1
        node = registry.lookup(batch.kind)          # 白名单
        if node is None:
            mark_unsupported(batch); continue
        mark_generating(batch)
        fragments = run(node, projection(batch))    # §7.4
        for slot, frag in zip(batch.slots, fragments):
            if frag is None: continue               # 该槽位保持 missing
            merge(slot, frag)                       # 13.6.2
            emergent += derive_consequences(slot, blueprint)   # §6.6.5 派生，确定性，非校验
    reconcile(schema, blueprint)                    # 13.6.3
    if emergent: 写入 gaps；必要时回 design（计入重规划次数）
    iteration += 1
final_merge()                                       # §6.6.2 收尾合并（会删改元素：配额强制、阳台去重）
reconcile(schema, blueprint)                        # ★ 必须重新对账：见下
validate(blueprint)                                 # §6.6.5 全量校验：单点，在循环之外
```

**注意最后三行的顺序与必要性**：

1. `validate` 在 `final_merge` 之后、循环之外。**不要在循环内调用 `validate`**（§6.6.5 的四条理由）。循环内发现涌现缺口靠的是 `derive_consequences` 这个确定性派生，不是校验。
2. **`final_merge` 之后必须重新对账一次**。收尾合并不是只读操作——`enforce_component_quota` 会增删构件，`deduplicate_balcony_representations` 会删掉与 balcony 重叠的手写 floor，`remove_ground_level_railings` 会删栏杆。这些删改会让循环末期写入的槽位状态失效：一个已经 `filled` 的槽位，其元素可能刚被去重删掉。**不重新对账，交付清单就会说谎**（§13.9 要求 `filled + unsupported + needs_review == total`，而这里的漂移是静默的）。
3. `repair` 若被触发，它之后同样要重新对账再复检（§13.4 规定 4 已定）。

### 13.9 交付清单契约

本文档多处要求"在交付里显式列出未支持项"，这里给出它确切的结构。**不要各自设计一个格式**：

```jsonc
{
  "request_id": "req_xxx",
  "detail_level": "detailed",          // 本次档位
  "design_revision": 3,
  "slots": { "total": 24, "filled": 20, "unsupported": 3, "needs_review": 1 },
  "unsupported_items": [               // 逐条列出，不许合并成一句话
    { "slot_id": "slot_canopy_1", "kind": "canopy", "reason": "kind 未注册生成节点" },
    { "slot_id": null, "kind": "entrance_step",
      "reason": "档位 detailed 要求入口台阶，当前无此构件类型（§2.2.3）" }
  ],
  "needs_review_items": [
    { "slot_id": "slot_win_7",
      "reason": "宿主墙可分配长度不足，未能落在槽位声明的房间边界上" }
  ],
  "warnings": [],
  "detail_level_gaps": ["入口台阶", "门廊装饰柱", "老虎窗", "窗套线脚", "分层材质"]
}
```

四条硬规定：

1. `unsupported_items` **逐条列出**，一条一个对象。不许写成"部分要求未支持"这样的一句话。
2. `detail_level_gaps` 专门承载"本次档位要求但能力缺失"的项，与普通 unsupported 分开——这是 §2.2.3 那条红线的落地位置。
3. 清单**同时进 state（供前端展示）与日志**，两者结构一致。
4. `slots.filled + unsupported + needs_review == slots.total` 必须可校验；不相等说明有槽位被漏掉，属 `error` 级问题。

### 13.10 工具契约：校验与修复全部是 tool

**校验和修复都是 `@tool` 装饰的纯函数**，这不是可选项，是新架构的前提。`app/tools/spatial_tools.py` 现有 22 个：

| 类别 | 数量 | 函数 |
| --- | --- | --- |
| 校验 | 13 | `validate_blueprint_structure` / `validate_element_required_fields` / `validate_element_dimensions` / `validate_reference_integrity` / `validate_wall_junctions` / `validate_opening_coords` / `validate_opening_fit` / `validate_collision` / `validate_roof_coverage` / `validate_roof_top_coverage` / `validate_stair_alignment` / `validate_stacked_member_containment` / `validate_model_quality` |
| 确定性修复 | 8 | `fix_opening_coords` / `fix_opening_fit` / `fix_wall_junctions` / `fix_stair_alignment` / `fix_element_dimensions` / `fix_element_elevations` / `fix_roof_coverage` / `fix_material_references` |
| 辅助 | 1 | `get_wall_bounding_box` |

**统一契约**（`spatial_tools.py` 文件头即此意）：

1. **签名**：`(blueprint: dict) -> str`。纯函数，不读外部状态、不写文件。
2. **返回人类可读文本，用标记表达严重度**。三类工具的返回形态**不一样**，照现状对齐，不要自己统一成一种：

| 类别 | 无需处理 | 发现问题 | 已做修改 |
| --- | --- | --- | --- |
| 校验器 | `✅ ...` | 若干行 `❌` / `⚠️` | — |
| 修复算子 | `✅ ... 无需修正。` | 返回 `❌` 表示修不了 | `已自动修正 ...：` + 明细（**无标记**） |

修复算子的"已修改"路径**故意不带 `✅`**——它靠"不含 `❌` 且蓝图确实变了"来判定成功（`assembly.py:283` 的 `apply_fixes`：`success = "❌" not in fix_output and blueprint != before_fix`）。**不要为了好看给这条路径加 `✅`**，也不要反过来把"无需修正"和"已修改"合并成同一个返回——那样就没法区分"改成功了"和"本来就没问题"。

任何工具在通过路径上**都不得返回空串**（现有 22 个没有一个是这么做的）。
3. **严重度判定集中在 `_severity_from_text`**（`app/services/agent_service.py:212`）：`("❌" in output, "⚠️" in output)`。无标记的返回被当作"无错误无警告"。不要把这套判定散到各个工具里——需要把某类警告升级为错误时只改这一处。
4. **新增校验器必须遵守标记约定**。返回空串、或不带标记的文本，流水线无法分类它，等于这个校验器不存在。
5. 每个工具都要能**在给定 blueprint 上独立跑通**（不依赖运行时上下文），这样它才能既被流水线强制执行、又能被注册给模型可选调用。

#### 13.10.1 校验器怎么拿到房间数据（签名保持不变）

房间层的校验（§1.4、§1.4.1）需要 `rooms`，而工具签名是 `(blueprint: dict) -> str`。**不要为此给校验器加第二个参数**——那会破坏 §13.10 的统一契约，也会让所有既有工具失去可互换性。

**做法：把设计图纸挂在蓝图的 `meta` 上。** 这是延续现有约定——`merge` 现在就已经往 `blueprint.meta` 写 `designRevision` / `designHash` / `designSchemaVersion`（`assembly_workflow.py` 第 4 节）。新增一个：

```
blueprint.meta.designSchema = {   // 完整三层 schema（massing + rooms + slots）
    "schema_version": "3.0",
    "revision": 3,
    "massing": {...},
    "rooms": [...],
    "slots": [...]
}
```

于是：

- 房间校验器从 `blueprint["meta"]["designSchema"]["rooms"]` 取数据，签名保持 `(blueprint) -> str`；
- 没有房间层时（回退模式或简单请求），该键缺失，校验器返回 `✅ 无房间层，跳过检查。`——与现有"没有 X，构件，跳过检查"的写法完全一致；
- 槽位对账（`reconcile`）**不依赖这个键**，它是程序内部的 `(schema, blueprint)` 双入参函数，不是工具。

**硬规定**：`meta.designSchema` 是**只读副本**，由 `shell` 在重建时写入一次。任何节点不得就地修改它——要改 schema 只能回 `design` 节点改并递增 `revision`（§6.4）。

**两族修复工具，分工不同，不要混用：**

| | `fix_*`（`spatial_tools.py`） | `REPAIR_TOOL_SPECS`（`app/agent/repair/tools.py:11`） |
| --- | --- | --- |
| 形态 | 无参数纯函数，**全量扫描 + 全量修复** | **声明式 spec + 参数**，定点操作 |
| 谁决定改哪里 | 函数自己找问题 | 模型指定 `entity_id` 与参数 |
| 谁执行 | 流水线 / `_FIX_MAP` 自动派发 | `extract_repair_actions(text)`（`repair/tools.py:89`）解析模型输出 → `execute_repair_actions`（`repair/tools.py:230`）执行 |
| 例子 | `fix_opening_coords(blueprint)`：把世界坐标换算成沿墙距离 | `move_opening(entity_id, along, elevation)`：只动指定的那扇门窗 |

因此 `repair` 角色的真实运行方式是：**模型不直接改蓝图，只输出一组"修复工具动作"，由程序按白名单执行**。这与 §7.3 的"模型只填空、程序执行"是同一条原则，也正是"把修复封装成 tool"的完成态——**不要为了实现 `repair` 而让模型直接改蓝图 JSON**。

现有可用动作：`add_entity` / `remove_entity` / `move_opening` / `resize_opening` / `reparent_opening` / `set_material_reference` / `patch_entity`（共 7 个，完整清单与执行契约见 §13.13）。扩展时按同样格式加一条 spec，并在 `execute_repair_actions` 里加对应分支，**不要给模型开放任意字段写入**。

### 13.11 设计节点的输入输出契约（源头节点，必须最严）

设计节点是整条链的源头，它输出错了后面全错。因此它的约束比生成节点更严。

**输入**：仍按 §13.5 的五段式组装（A / E 段与生成节点共用同一份文本），但 B / C / D 段的内容不同：

| 段 | 设计节点的内容 |
| --- | --- |
| B 用户需求 | 原始 `user_message` + 档位 `detail_level` + 上轮审核反馈（重规划时） |
| C 知识 | `blueprint_spec` + `protocol`（坐标系与字段协议）；`component` + `wild_schema`（**能力边界：哪些 kind 已注册**） |
| D 全局约束 | 档位对应的体量 / 细节要求（§2.2.2 的表）、构件 kind 白名单、材质角色可用集合 |

**输出**：一个 schema 对象，字段严格按 §4.2 + §13.2 + §13.2.1。程序侧用 Pydantic 模型校验，**不通过不许进入下一步**。

**设计节点自己的一关**（与最终校验无关，只保证"图纸本身合法"）：

1. 结构合法性：Pydantic 模型通过；
2. **kind 白名单**：每个 `slot.kind` 必须在 `NODE_REGISTRY` 里已注册；未注册的**就地改成 `unsupported`**，不是报错（§1.5 的能力缺失政策）；
3. 房间校验 §1.4 的第 1、2、3、4、5 条（结构类，不需要蓝图即可判定）；
4. 竖向规则 §1.4.1；
5. id 的确定性与唯一性（§13.2 规定 1、2）。

**失败与重试**：最多重试 2 次（同一份输入让模型重出）。两次都不过，**按 §1.2 的失败处置回退**：

- 丢弃 `rooms`，只保留 `massing` + 由立面推导的 `slots`（即现状能力）；
- 在交付清单里写进"本次未提供房间划分"（§13.9 的 `unsupported_items`）；
- **不阻断整轮生成**。

**禁止**：不要为了"让它通过"而放宽校验；不要让它输出蓝图元素——它只产出 schema，蓝图由 `shell` 生产。

### 13.12 `shell` 节点的生成算法（rooms + massing → 主体几何）

`shell` 是**新建**节点，不是搬迁 `skeleton.py`（§3.3）。它把房间层翻译成主体几何，算法必须确定性：

**输入**：`design_schema`（massing + rooms）、`detail_level`、资产目录。
**输出**：`blueprint.geometry.elements` 里的墙 / 楼板 / 屋顶 / 楼梯，以及 `blueprint.materials`。

按顺序执行：

1. **楼板**：每个建模层生成一块楼板，范围 = massing 轮廓。`double_height=true` 的房间，其上方楼层在该房间投影内**不生成楼板**（挑空）。
2. **外墙**：每层按 massing 轮廓生成外围墙（矩形体量即 4 面）。相邻层的同位置外墙**各自成段、不合并**，便于后续按层校验。
3. **内墙**：由相邻房间的共享边生成；**每条共享边只生成一面墙**（去重）；长度小于 §1.4 第 5 条阈值（0.9m）的共享边不生成。
4. **屋顶**：按 massing 顶部生成，形式沿用既有 `_SUPPORTED_ROOF_TYPES` 的受支持集合。
5. **竖向交通**：`type=circulation` 的房间生成楼梯，踏步按确定性展开（沿用现有竖向核心筒算法的思路，但由**房间边界**驱动，不再按体量比例推导）。
6. **材质**：读资产目录（`asset_storage.list_manifests()` → `compact_asset_catalog`），把设计节点给出的材质角色意图用 `resolve_material_plan` 落到真实 `assetId`，写入 `blueprint.materials`。**材质 ID 白名单的唯一来源就是这里**（§13.5 的 D 段从 `blueprint.materials` 的键读）。

**幂等重建**：`shell` 每次执行先删除自己上次产出的元素再全量重建，识别方式是 id 前缀——`shell` 产出的元素使用 `wall_` / `floor_` / `roof_` / `stair_` 前缀，**生成节点产出的组件一律不得使用这些前缀**（§13.2 已规定 id 格式）。

**与旧 `skeleton.py` 的关系**：几何真值从"体量比例"换成"房间边界"。旧的 massing 驱动部分改为房间驱动；`core_runs` 那类**硬编码比例的核心筒逻辑删除**，核心筒改由 `type=circulation` 的房间表达。

### 13.13 `repair` 的输出契约与白名单执行

**输入**（失败切片，§7.4）：出错元素 + 其当前参数、校验器给出的结构化问题、组件工具数据（说明"具体错在哪"）、允许修改的关联实体 id、**已通过对账的元素 id 黑名单**、按失败类型检索的 `recipe` / `relation` 知识。

**输出**：一个 JSON 数组，每项是一个修复动作：

```jsonc
[{"tool": "move_opening", "arguments": {"entity_id": "win_3", "along": 2.4, "elevation": 1.1}}]
```

**可用的七个动作**（`REPAIR_TOOL_SPECS`，`repair/tools.py:11`）：

| 动作 | 作用 |
| --- | --- |
| `add_entity` | 只在配额明确缺少某类构件时新增一个完整实体 |
| `remove_entity` | 只删除结构化问题明确列出的超额实体 |
| `move_opening` | 移动门窗，只改沿墙距离与高程 |
| `resize_opening` | 调整门窗宽高 |
| `reparent_opening` | 把门窗改挂到真实 wall，可同时指定新的局部位置 |
| `set_material_reference` | 把材质字段改成 `blueprint.materials` 里已存在的 ID |
| `patch_entity` | 局部字段替换 |

**执行**（`execute_repair_actions`，`repair/tools.py:230`）：

- 在**蓝图副本**上执行；逐个动作应用，**单个动作失败只回滚该动作**（不影响其他动作）；
- 受三个白名单约束：`allowed_entity_ids`（能改谁）、`allowed_add_types`（能加什么类型）、`allowed_remove_ids`（能删谁）；
- 执行完在副本上**跑全量复检，只有错误数下降才提交**；
- 提交后必须重新对账（§13.4 规定 4）。

**禁止**：不接受白名单外的新动作名；不接受直接写 `geometry` 的原始操作；模型不得输出蓝图 JSON。

## 附 C：一句话总结（面试版）

> 我把"固定节点 + 动态提示词"重构为"意图分类 → 方案设计 → 主体结构生成 → 动态执行调度器 → 最终校验"：设计图纸（结构化 schema）是唯一事实源，既喂模型（JSON）也喂用户（SVG）；调度器按缺口分组循环，派发白名单内的生成/合并节点：生成节点按需拉取知识，合并节点确定性地幂等增量 patch（不调用模型），对账由程序做 diff，直到缺口清空；节点来自白名单保证安全，能力缺失只标记不阻断。
>
> 其中房间层（内部空间设计）是本轮新引入的能力，我按新增能力做了单独的能力声明、范围边界和八条确定性验收标准，并且把闸门放宽排在能力落地之后——先把能做的做出来，再放开判定，而不是先放开判定再补能力。
>
> 每个节点拿到的是程序从图纸和蓝图里截取的切片（本组槽位 + 宿主几何）加按需检索的知识，而不是全量文件；模型只负责填空，不负责在全文里找宿主。这条规则在门窗上已经跑通（精确开口槽位），本轮是把它推广到全部构件类型。
