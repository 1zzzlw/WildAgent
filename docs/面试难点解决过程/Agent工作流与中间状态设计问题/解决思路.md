# Agent 工作流与中间状态设计问题：解决思路

> 文档性质：根据实际代码与 LangSmith Trace 梳理并落地的改造方案。
>
> 当前状态：代码改造已于 2026-09-15 完成，并在同日完成接手复验与一轮运行时缺陷修复。

> plan 模式端到端图集成测试已覆盖“节点运行成功但业务验收失败必须阻断交付”的路径（见 §12）。
> 仍未完成的只有需要模型额度与网络的真机 LangSmith Trace 复验，不应在此之前宣称线上验证完成。
>
> **后续结论（2026-09-17，部分方案已回退）**：本文中「候选违规检查 → 候选评分选择」这条链路已被整体删除。

> 《候选机制清理与proposal节点处置方案.md》。本文其余内容保留为 2026-09-15 的问题现场记录。
>
> 核心问题：如何把上游已经批准的重要决定，转换成后续程序能够消费、校验和追踪的结构化业务状态。

## 1. 这次是怎样一步步定位问题的

### 1.1 最初判断：上游思考没有完整传给下游

最开始看到的现象是：Planner 能理解用户要求，也能生成很详细的计划，但后续生成结果没有稳定落实这些要求。

因此最初怀疑：

```text
Planner 已经想到了
→ 但没有按照 GenerationState 的字段传递
→ 下游节点收到的信息太少
→ Planner 的作用被削弱
```

这个判断抓住了“上游决定没有落实到下游”的现象，但对原因的描述还不准确。

### 1.2 使用 LangSmith 观察完整 State

通过 LangSmith 逐个查看节点输入和输出后发现，界面中大部分字段一直存在，是因为 LangGraph 展示的是不断累积的完整 `GenerationState`，而不是每个节点只返回的局部增量。

阅读时必须区分：

- 节点输入：该节点执行前的完整 State；
- 节点输出：节点本次写入或更新的字段；
- 下一节点输入：上一份完整 State 与节点输出合并后的新 State。

这一步说明：仅凭“后续结果没采用要求”，不能直接断定发生了节点间状态丢失。

### 1.3 对照 Planner 原始输出和 `execution_plan`

Planner 的模型输出中包含：

```text
summary
tasks[].title
tasks[].objective
tasks[].phase
tasks[].acceptance
tasks[].basis
```

这些内容经过后端归一化后，确实进入了：

```text
execution_plan.dynamic_tasks
```

例如本次 Trace 中的“两层主体、车库、后院、前廊、家具、照明、阳台或雨篷、柱和梁”等要求，都能在 `dynamic_tasks` 的目标或验收条件中找到。

所以这次问题不是：

> Planner 的输出没有进入 State。

而是：

> Planner 的自然语言计划虽然进入了 State，却没有被转换成下游节点必须执行和最终校验的业务约束。

### 1.4 区分 `steps` 和 `dynamic_tasks`

继续查看 `execution_plan` 后发现其中存在两套看起来像“步骤”的数据。

`steps` 描述固定节点流程：

```text
planning_research
→ architecture
→ material_plan
→ skeleton
→ merge
→ final_validate
```

`dynamic_tasks` 描述本次用户需求，例如：

```text
完成两层带车库别墅的功能布局
添加门窗和阳台或雨篷
布置家具和照明
执行规范校验
```

但 LangGraph 本身已经写死了安全的节点和连线顺序。于是 `steps` 又保存了一份相同的流程，并由 `execution_plan_executor` 读取、判断依赖、标记状态，再返回下一个节点名称。

这形成了两个流程事实源：

```text
LangGraph 图结构：规定节点怎样运行
execution_plan.steps：再次描述并调度相同节点
```

两者表达的是同一件事，增加了阅读和维护成本，也容易产生不一致。

### 1.5 检查 `dynamic_tasks` 是否真的被执行

`dynamic_tasks` 虽然包含本次需求，但当前没有执行器逐条调度它们：

- `execution_plan_executor` 实际选择的是 `steps`；
- `architecture` 和 `material_plan` 只把对应阶段任务拼成提示词；
- `skeleton` 没有直接消费 skeleton 阶段的计划指导；
- 后续组件生成主要依赖 `design_brief`，不会逐条读取原始动态任务；
- `final_validate` 校验 Blueprint 固定规则，不会逐条验证自然语言 `acceptance`。

更关键的是，当前进度更新以 `phase` 为粒度。一个节点完成后，同一 phase 的多个动态任务可能一起被标记为 `completed`，并不代表每条验收条件都已经实现。

本次 Trace 中就出现了这种情况：

- 两条 `architecture` 任务由一次 architecture 执行统一标记；
- 两条 `skeleton` 任务由一次 skeleton 执行统一标记；
- 计划要求家具、照明、阳台或雨篷、必要的柱和梁；
- 最终产物没有证明这些要求全部实现；
- 相关任务仍可能显示为 `completed`。

### 1.6 最终结论

当前问题不是简单的 State 字段太少，也不主要是节点之间丢失了 State。

真正的问题是中间缺少一个“计划编译与验收闭环”：

```text
Planner 生成自然语言任务
→ dynamic_tasks 成功保存任务
→ 部分内容只作为软提示传给节点
→ 没有编译成节点可直接消费的结构化业务约束
→ 没有为每条验收条件绑定确定的检查方式
→ 节点运行结束便按 phase 更新完成状态
```

因此难点可以更准确地表述为：

> 如何将上游已批准的自然语言任务，编译为下游节点可消费的结构化要求，并用可追踪的验收结果证明这些要求是否真正完成。

## 2. 旧设计的主要问题

### 2.1 固定流程被重复描述

LangGraph 已经负责固定、安全的执行顺序，`execution_plan.steps` 又保存并调度同一顺序。

问题包括：

- 图结构和 `steps` 可能不一致；
- 阅读代码时无法立刻判断谁才是流程权威；
- 每增加或删除节点，需要同时维护图和计划模板；
- `plan_executor` 看似动态调度，实际上只能从固定能力白名单中选择已有节点。

### 2.2 动态任务只是自然语言描述

`dynamic_tasks` 能说明本次要做什么，但其中的 `objective`、`acceptance` 和 `basis` 仍是文本。

文本可以帮助模型理解，却无法直接回答：

- 哪个节点必须消费这条要求；
- 要写入哪个业务对象和字段；
- 当前系统是否支持；
- 使用哪个校验器检查；
- 未实现时是否允许继续交付。

### 2.3 `acceptance` 不是可执行验收

当前 `acceptance` 是一句句验收描述，不等同于程序已经实现的断言。

例如：

```text
“在至少两个房间内布置家具”
```

要成为真正的验收条件，至少还需要明确：

```text
检查对象：Blueprint 组件
组件类型：furniture
空间范围：不同房间
比较方式：房间数 >= 2
校验器：哪个函数负责检查
检查结果：实际发现几个房间
```

否则只能展示这句话，不能证明它通过。

### 2.4 运行完成和业务完成被混为一谈

节点运行成功只能说明代码没有在该节点失败，不代表该阶段的所有动态要求均已实现。

当前按 phase 批量完成任务，会把：

```text
节点执行完成
```

误当成：

```text
任务全部满足验收条件
```

这正是状态看起来完整、最终结果却可能遗漏要求的原因。

## 3. 新设计的职责划分

首要优化目标是让五类对象各自只负责一件事。

### 3.1 LangGraph：固定、安全的执行顺序

LangGraph 是唯一的流程事实源，负责：

- 有哪些真实节点；
- 节点之间的固定顺序；
- 条件分支和循环边界；
- 哪些操作可以执行；
- 异常时进入重试、重规划还是结束。

模型和计划数据都不能自由生成节点名称，也不能越过服务端图结构和能力白名单。

### 3.2 `dynamic_tasks`：本次需求真正要完成什么

它保留面向用户和计划审核的任务描述，例如：

```yaml
- id: task_3
  title: 材料规划与内部配置
  phase: material_plan
  objective: 为建筑配置材料、家具和照明
  acceptance:
    - id: acc_3_1
      description: 所有主要建筑元素具有有效材质
    - id: acc_3_2
      description: 至少两个房间包含家具
    - id: acc_3_3
      description: 室内外关键位置包含照明
  basis: 用户未提供细节，由规划阶段提出并等待审核
```

它回答的是“本次要做什么”，不负责决定 LangGraph 下一步运行哪个节点。

### 3.3 `structured_requirements`：节点可以消费的业务约束

这是旧设计真正缺失的一层。它由已批准的 `dynamic_tasks` 经过确定性归一化和白名单编译得到。

最小结构示例：

```yaml
structured_requirements:
  - id: req_furniture_room_count
    source_task_id: task_3
    source_acceptance_id: acc_3_2
    phase: component_generation
    target: blueprint.components.furniture.room_count
    operator: gte
    expected: 2
    consumers:
      - furniture_generator
      - final_validate
    validator: furniture_room_count
    severity: error
    support_status: supported
```

它回答：

- 这条要求来自哪个任务和验收条件；
- 哪些节点需要消费；
- 目标字段或业务对象是什么；
- 怎样比较实际值与期望值；
- 哪个校验器负责给出证据；
- 当前能力是否支持。

无法编译的自然语言要求不能静默丢弃，必须标记为：

```text
unsupported：当前系统明确不支持
needs_review：需要用户或程序进一步明确
```

### 3.4 `acceptance_results`：记录每条验收条件是否通过

它保存业务完成情况，而不是节点运行情况：

```yaml
acceptance_results:
  acc_3_2:
    task_id: task_3
    requirement_id: req_furniture_room_count
    status: failed
    expected: 2
    observed: 0
    validator: furniture_room_count
    evidence_refs: []
    message: 未检测到分属不同房间的家具组件
```

建议状态只保留有限枚举：

```text
pending
passed
failed
not_checked
not_applicable
unsupported
```

其中 `not_checked` 和 `unsupported` 不能被当成通过。

动态任务只有在其所有必需验收项均为 `passed`，或经过明确审核后为 `not_applicable` 时，才能标记为完成。

### 3.5 `execution_progress`：只展示固定节点运行进度

它代替 `execution_plan.steps` 的进度展示职责，但不参与路由：

```yaml
execution_progress:
  architecture:
    status: completed
    result_ref: architecture_plan
  material_plan:
    status: in_progress
    result_ref: null
  skeleton:
    status: pending
    result_ref: null
```

可按需要补充 `started_at`、`completed_at` 和 `error`，但不要重新加入 `depends_on`、`node` 或“下一节点”等调度字段，否则会再次形成第二套工作流。

它只回答：

> 固定节点运行到哪里了？

不能回答：

> 用户要求是否已经实现？

后一个问题只能由 `acceptance_results` 回答。

## 4. 建议的目标 State

为避免同一数据保存多份，建议采用以下边界：

```python
class GenerationState(TypedDict, total=False):
    # 已批准计划：保存目标、审核状态和本次动态任务，不保存固定节点步骤。
    execution_plan: ExecutionPlan

    # 由动态任务编译出的机器可消费约束。
    structured_requirements: list[StructuredRequirement]

    # 每条验收条件的检查结果。
    acceptance_results: dict[str, AcceptanceResult]

    # 固定 LangGraph 节点的运行进度，仅用于观测和展示。
    execution_progress: dict[str, ExecutionProgressItem]
```

精简后的 `ExecutionPlan` 可以保留：

```yaml
execution_plan:
  plan_id: plan_xxx
  version: 1
  intent: generate
  goal: 生成一个别墅
  status: approved
  review_status: approved
  planner_source: llm
  planner_summary: ...
  assumptions: []
  constraints: []
  dynamic_tasks: []
  feedback: ""
  change_summary: []
```

应该删除：

```text
execution_plan.steps
current_plan_step_id
plan_next_node
依赖 steps 才能成立的状态更新逻辑
```

但这些字段不能在改造第一步直接删除，必须等新路由、反馈处理和进度记录完成迁移后再移除。

## 5. 目标执行流程

```text
用户输入
→ classifier
→ planning_research
    ├─ 本地知识充分 → planner
    ├─ 需要联网补充 → web_research → planner
    └─ 失败 → END
→ planner：生成 dynamic_tasks
→ requirement_compiler：编译 structured_requirements
→ plan_validator：检查任务是否可编译、能力是否支持、验收器是否存在
→ plan_review：展示动态任务、结构化要求和不支持项
    ├─ 要求修改 → planner
    ├─ 终止 → END
    └─ 用户批准
         → architecture：消费总体方案要求
         → material_plan：消费材质要求
         → design_review
              ├─ 修改方案 → architecture
              ├─ 终止 → END
              └─ 审核通过
                   → skeleton：消费主体结构要求并生成组件建议
                   → 根据 structured_requirements 和组件建议动态派发能力
                   → 各组件 gen → val
                   → merge
                   → final_validate：执行固定校验和逐条业务验收
                        ├─ 存在可修复问题 → callback → final_validate
                        ├─ 阻断性验收失败 → 失败或进入受控修订
                        └─ 所有阻断性验收通过 → END
```

`requirement_compiler` 表示一个明确职责，不一定必须增加为新的 LangGraph 节点。首期可以是 Planner 后由 `plan_validator` 调用的确定性函数，避免为了分层而增加无必要节点。

目标流程中，LangGraph 继续负责固定、安全的主链、人工审核、组件分支和有限修复回路；
`dynamic_tasks` 不直接生成节点顺序，而是先编译为 `structured_requirements`，再影响已有节点的
输入、组件能力选择和最终验收。这样既保留现有业务节点的生成、检索与校验能力，又不再依赖
自然语言 Prompt 偶然落实计划内容。

### 5.1 反馈和重规划怎样保留

删除 `plan_executor` 后仍需保留当前的用户反馈与重规划能力，但不再依赖 `steps` 选择下一个固定节点。

可以在关键节点边界使用统一的反馈检查函数：

```text
没有新反馈 → 继续沿 LangGraph 固定边执行
收到反馈 → 更新 plan_feedback → 返回 planner 重规划
超过最大次数 → 结束并报告错误
```

它只决定“继续还是重规划”，不决定完整业务节点顺序。

## 6. 新设计怎样解决旧问题

| 旧问题 | 新设计 |
| --- | --- |
| LangGraph 与 `steps` 重复描述流程 | LangGraph 成为唯一执行顺序来源 |
| `dynamic_tasks` 只有文本，节点无法稳定取值 | 编译成 `structured_requirements` |
| 部分节点只收到软提示，部分节点完全不读取任务 | 每条要求声明明确的 `consumers` |
| `acceptance` 只是展示文本 | 为验收项分配 ID、比较方式和 validator |
| 一个 phase 执行完，多个任务一起完成 | 按 `acceptance_results` 逐条判断任务状态 |
| 节点成功与业务完成混为一谈 | `execution_progress` 和 `acceptance_results` 分离 |
| 不支持的要求可能被忽略 | 编译阶段显式标记 `unsupported` 或 `needs_review` |
| 模型可能影响执行节点 | 模型只描述业务目标，节点和路由仍由代码控制 |

## 7. 已执行的完整实施路线

本次按照以下顺序完成改造，并在删除 `steps` 后补齐对应契约、消费和验收闭环。

### 阶段 0：固定问题样例和预期结果

把本次 Trace 中的计划与最终 Blueprint 保存为回归样例，至少覆盖：

- 两层、车库、后院和前廊；
- 家具覆盖至少两个房间；
- 室内外照明；
- 阳台或雨篷；
- 必要的柱和梁。

先记录当前结果，让测试能够证明“任务被标记完成，但验收没有证据”。

本次落地采用精简的纯逻辑回归数据复现 Trace 中的关键条件，没有把整份大型 Trace 复制进测试目录；测试覆盖两层、gable、出檐下限、必需组件以及“Schema 通过但业务验收失败”的情况。

### 阶段 1：只增加新契约，不改变原执行流程

1. 在 planning contracts 中定义 `StructuredRequirement`、`AcceptanceResult` 和 `ExecutionProgressItem`。
2. 在 `GenerationState` 增加三个字段及清晰注释。
3. 初始化验收状态和节点进度。
4. 保留旧 `steps`，确保此阶段行为不变。

验证目标：新结构可以序列化、进入 Trace，原流程测试仍然通过。

### 阶段 2：把动态任务编译成结构化要求

1. 为 `dynamic_tasks.acceptance` 增加稳定 ID。
2. 建立受控的 requirement 类型、目标字段、操作符、消费者和 validator 白名单。
3. 编译已知要求。
4. 无法理解或当前不支持的要求显式记录，禁止静默忽略。
5. `plan_validator` 检查每条必需验收是否能映射到消费者和校验器。

验证目标：Planner 不能通过自然语言生成任意节点或任意校验函数；每个验收项都有编译结果。

### 阶段 3：让真实节点消费结构化要求

按业务阶段逐个接入：

1. architecture 消费体量、层数、空间和屋顶约束；
2. material_plan 消费材料与风格约束；
3. skeleton 消费墙、板、柱、梁、楼梯和洞口要求；
4. 组件分发根据结构化要求决定家具、灯光、阳台、雨篷等能力是否需要运行；
5. candidate 归一化、评分和选择阶段再次检查硬约束，不能只在提示词中讨论一次。

验证目标：从要求 ID 能追踪到消费节点和结果对象；故意让节点忽略约束时测试会失败。

### 阶段 4：建立逐条验收闭环

1. 为支持的 requirement 注册确定性 validator。
2. validator 写入 `acceptance_results` 的 expected、observed 和证据引用。
3. 动态任务状态由验收结果计算，不再按 phase 批量更新。
4. 阻断性要求存在 `failed`、`not_checked` 或 `unsupported` 时不得宣告计划完成。
5. 固定 Blueprint Schema 校验与本次业务验收分别记录，避免“Schema 合法”被误认为“用户要求全部满足”。

验证目标：家具为 0 时，“至少两个房间有家具”必须失败，相关动态任务不能显示完成。

### 阶段 5：迁移进度并删除 `steps`

1. 节点开始、完成或失败时更新 `execution_progress`。
2. 把反馈检查和重规划分支移到统一节点边界逻辑。
3. LangGraph 条件边直接决定固定节点流转。
4. 删除 `execution_plan.steps`、`next_ready_step()`、基于 step 的 `update_plan_step()` 和相关 executor 调度逻辑。
5. 删除已失去用途的 State 字段、UI 展示和测试代码。

验证目标：代码中只有 LangGraph 图定义执行顺序；删除 `steps` 后正常、反馈重规划和失败流程全部可运行。

### 阶段 6：LangSmith 与回归验收

在 LangSmith 中重点核对四条链：

```text
dynamic_task
→ structured_requirement
→ consumer node output
→ acceptance_result
```

同时检查：

- `execution_progress` 是否准确反映节点状态；
- 未运行节点不会显示完成；
- 未检查的验收不会显示通过；
- 不支持项会在 Plan Review 阶段暴露；
- Trace 结束时每条必需要求都有最终状态和证据。

## 9. 最终验收标准

完成这次改造至少要满足：

1. `execution_plan` 中不再存在静态 `steps`；
2. LangGraph 是固定节点顺序的唯一事实源；
3. 每条动态任务验收条件都有稳定 ID；
4. 每条验收条件都有结构化编译结果；
5. 支持的要求能定位消费者和 validator；
6. 不支持或含糊的要求不能静默进入执行；
7. 节点完成只更新 `execution_progress`，不会直接证明业务任务完成；
8. 动态任务只有在必需验收全部通过后才显示完成；
9. 最终 Schema 校验通过但业务要求未通过时，不得宣告完整成功；
10. 反馈、重规划、失败终止和最大重规划次数在删除 `steps` 后仍然有效；
11. LangSmith 能从任务一路追踪到约束、消费结果和验收证据；
12. 模型不能通过输出内容调用未注册节点或校验器。

## 10. 当前最准确的总结

本次分析不是要让 `GenerationState` 保存更多模型思考文本，而是要把自然语言决定变成程序契约。

最终职责应当是：

```text
LangGraph
负责固定、安全的执行顺序

dynamic_tasks
负责描述本次需求真正要完成什么

structured_requirements
负责把已批准的动态任务转换成节点可以消费的业务约束

acceptance_results
负责记录每条验收条件是否真正通过以及证据是什么

execution_progress
只负责展示固定节点运行到了哪里
```

目标链路是：

```text
用户需求
→ 动态任务
→ 结构化要求
→ 节点消费
→ 验收结果
→ 可追踪的最终结论
```

这才真正解决“上游已经批准的重要决定，如何稳定进入后续生成、校验和追踪过程”的问题。

## 11. 面试时怎样表达

代码改造已完成后，可以描述为“通过 Trace 定位问题，并完成了计划—约束—执行—验收链路改造”；但在补做真实端到端 Trace 前，不应宣称线上验证已经完成。

可以这样表达：

> 我通过 LangSmith 对照 Planner 原始输出、LangGraph State 和最终 Blueprint，发现问题并不是模型计划没有写入 State，而是自然语言动态任务没有被编译成下游可执行、可验收的业务约束。同时，原方案使用 `execution_plan.steps` 重复描述 LangGraph 已经固定的节点顺序，运行进度和业务完成状态也没有分开。我随后让 LangGraph 成为唯一流程事实源，删除 `steps` 和二次调度；保留 `dynamic_tasks` 表达本次目标，新增 `structured_requirements` 作为节点消费契约，用 `acceptance_results` 逐条记录实际值和证据，并用 `execution_progress` 单独展示固定节点进度。architecture 候选选择会重新检查层数、尺寸、屋顶和组件等批准约束，最终 Schema 通过但业务验收失败时也会阻断交付，从而避免节点运行完成却错误地把业务任务标记为完成。

同时修正了两处设计一致性问题：

- **`needs_review` 从未产出**：`RequirementSupportStatus` 定义了该值但编译器从不使用，所有无法确定化的验收都被判成硬阻断。现在区分为两级——纯主观验收（如“体量合理且外观协调”）标为 `needs_review`（`severity=warning`，`not_checked`，不阻断交付）；当前能力明确不支持的请求（家具、平面布局、车库/后院）仍标为 `unsupported` 并在计划校验阶段硬阻断。
- **英文别名子串误判**：`chair` 会命中 `armchair`、`table` 会命中 `comfortable`，把普通验收判成“不支持”。现在英文别名按词边界匹配，中文别名仍按子串匹配。

### 12.4 追加修复：要求注入破坏了立面槽位与配额的一致性

上一节复验后，实际运行中出现大量生成中断，报错为：

```text
1 validation error for DesignDocument
Value error, door 立面槽位数量 1 不在配额 2~2 内
```

**根因（已确定性复现）**：`normalize_architecture_plan` 会把 `door`/`window` 的配额
**派生**成立面 pattern 的实际槽位数量（`min == max == count`，见该函数内
`_facade_opening_counts` 分支），这是 `DesignDocument` 校验所依赖的不变量。
而 `apply_structured_architecture_requirements` 在该归一化**之后**运行，会把结构化要求
的最少数量直接写进这两个开口的配额：

```text
立面实际门槽位 = 1        → normalize 派生 door 配额 = 1~1
要求"至少 2 个门"        → 注入后 door 配额 = 2~2
立面 pattern 没变，仍只有 1 个门槽位
→ DesignDocument 校验失败 → 未捕获的 Pydantic 异常 → 整轮生成终止
```

同一处还有第二个问题：候选违规检查原本只看 `required_components` 是否包含该类型，
而注入本身就会把这些类型写进 `required_components`，检查因此**恒为真**。
少给门窗的候选不会被拒绝，问题被推迟到契约层才炸掉。

**修复**：

1. `door`/`window` 被显式标记为**派生配额**（`_PATTERN_GOVERNED_OPENINGS`）。要求注入
   只用它们做违规检查，**不再改写配额**，不变量得以保持。
2. 违规检查改为按**立面实际槽位数量**判定（复用与 `DesignDocument` 相同的计数实现，
   避免"检查认为达标、契约却拒绝"的分歧），并消除了 `required_components` 的循环判定。
   少给门窗的候选现在会在**方案选择阶段**被识别，优先选用达标候选；全部候选都不达标时
   给出明确的业务失败，而不是崩溃。
3. `architecture` 节点新增受控失败路径：`DesignDocument` 业务不变量失败统一转成
   `DesignContractError`，节点返回可读原因。任何其它契约不一致也不会再把未捕获异常
   抛穿整轮生成。
4. 修正一处英文别名回归：`"/"` 是纯符号，不能按英文词边界匹配。否则 `door/window`
   里的斜杠两侧是字母会被判定不成立，把"任一"要求错判成"全部"，进一步加重配额收紧。

**修复前后对比（确定性复现，fallback 方案）**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 基线（无结构化要求） | 通过 | 通过 |
| 要求"至少 2 个门"（实际 1 个） | **DesignDocument 失败，整轮终止** | 通过，且该候选被标记为违规 |
| 要求"至少 3 个门" | **失败，整轮终止** | 通过，且该候选被标记为违规 |
| 要求"至少 20 个窗"（实际 13 个） | **失败，整轮终止** | 通过，且该候选被标记为违规 |
| 要求"至少 2 个阳台" | 通过 | 通过 |

其中"通过"指不再产生契约冲突；槽位确实不足时仍会在候选选择阶段如实报告违规，
不会静默放行。

**新增回归测试**：`tests/agent/test_architecture_quota_consistency.py`（13 个用例），
覆盖配额不被改写、注入后契约仍合法、少给构件被判违规、达标方案不被误判、
非开口构件仍走 `required_components` 承诺、斜杠"任一"语义、契约错误被包装成可读业务错误。
已验证这些用例确实能捕获回归：恢复旧的配额改写逻辑会让其中 6 个变红（含契约崩溃用例），
恢复旧的斜杠判定会让 1 个变红。
