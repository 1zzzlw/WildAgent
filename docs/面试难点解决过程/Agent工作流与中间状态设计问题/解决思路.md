# Agent 工作流与中间状态设计：解决思路

> 文档性质：目标方案与实施路径。  
> 实现状态：本文是解决方案，不表示相关改造已经完成。  
> 最后整理：2026-09-05。

> 共享对象、全局 P0–P4 和验收口径见[统一实施路线与验收](../统一实施路线与验收.md)。本文提供工作流专项设计，新增契约与节点调整仍属待实施方案。

## 1. 总体结论

本次优化的核心不是继续增加 Agent 节点，也不是让模型输出更长的 reasoning，而是重新划分模型与程序的职责：

> 把 ExecutionPlan 降级为流程进度表，把“已批准设计契约”升级为生成事实核心；模型负责不可替代的设计决策，程序负责确定性实现、验证和修复。

现状和代码证据见 [当前遇到的问题](当前遇到的问题.md)，完整代码位置见 [项目索引](../../项目索引.md)。

## 2. 设计目标

新工作流需要同时满足：

1. 用户硬约束从输入到 Blueprint 都可追踪；
2. 关键设计决策以结构化状态保留，不依赖原始 Chain-of-Thought；
3. 同一份已批准设计能稳定编译成同一 Blueprint；
4. 设计多样性来自上游设计策略，不来自几何坐标随机抖动；
5. fallback 不能静默覆盖有效设计；
6. 修复必须复检，且不能破坏已批准约束；
7. 最终交付门禁逐步纳入 `wild-core` 实际重建检查，并记录检查覆盖范围与未检查项。

## 3. 目标工作流

~~~text
用户需求
  ↓
RequirementSpec：硬约束、软偏好、未决问题
  ↓
ArchitectureDesign ↔ SpatialDesign：先核对面积、核心预留与体量可行性
  ↓ 形成可行候选；改变已锁定要求时需用户取舍
ArchitectureDesign：体量、楼层、屋顶、立面策略
  ↓ 用户确认
SpatialDesign：功能分区、邻接、交通、开洞意图
  ↓ 用户确认
ApprovedDesignContract：冻结已批准设计
  ↓
实现映射：程序从批准设计派生要求与实体映射
  ↓
Deterministic Assembler：确定性编译 Blueprint
  ↓
Validator → Deterministic Repair → Recheck
  ↓
必要时执行一次受限模型修复
  ↓
wild-compiler / wild-core 无头重建验证
  ↓
Delivery Gate
~~~

这个流程保留现有的方案审核、确定性装配、有限修复和最终交付门禁，但不再让自然语言执行计划承载建筑设计信息。

## 4. 建立唯一的 ApprovedDesignContract

将已批准设计收敛为不可变版本清单；设计内容仍由各自权威对象保存：

~~~json
{
  "schema_version": "1.0",
  "contract_id": "design_01",
  "revision": 1,
  "requirement_ref": {"revision": 2, "content_hash": "..."},
  "architecture_ref": {"revision": 2, "content_hash": "..."},
  "floor_plan_ref": {"revision": 4, "content_hash": "..."},
  "material_ref": {"revision": 1, "content_hash": "..."},
  "unresolved_items": []
}
~~~

这是 Blueprint 生成前的批准依据，不是第二套可写设计内容。被引用的快照必须持久化且可重新读取；`RequirementSpec` 保存需求事实，`FloorPlanIR` 保存二维设计事实，`.wild` Blueprint 保存装配产物。`architecture_plan`、`material_plan` 等已有对象先保持权威内容，迁移时通过版本引用和只读适配收敛，不要求一次替换全部 Graph State。

修改需求、体量或平面后产生新 revision，并使依赖的批准状态、装配结果及校验报告失效。装配输出记录批准清单、assembler/compiler/core 版本和 Blueprint 哈希；交付后的编辑继续遵守 ScenePatch 边界，不能静默反写已批准平面。

- [`architecture_node.py`](../../../wild-server/app/agent/nodes/architecture_node.py)

## 5. 建立约束账本

优先把用户明确需求和当前阶段适用的系统硬规则转换成统一约束；领域建议与示例保留来源及软约束性质，不能自动升级为用户硬要求：

~~~json
{
  "id": "constraint_roof_01",
  "source": "user",
  "importance": "hard",
  "target": "roof.type",
  "expected": "gable",
  "status": "approved",
  "realized_by": ["roof_main"],
  "validation": "passed"
}
~~~

约束状态使用同一个生命周期：

~~~text
extracted → proposed → approved → realized → validated
                                      ↘ violated
~~~

约束账本属于 `RequirementSpec` 及其验收记录。`realized_by` 适用于实体型约束；禁止某类构件、面积上限、邻接和连通等要求允许引用关系、集合或全局检查结果。未配置验收器的要求标记 `not_checked`，不能计入已验证。

通过约束账本，可以直接查询：

- 用户哪条要求还没有进入方案；
- 哪条设计约束没有对应 Blueprint 实体；
- 哪个校验器证明了约束已经实现；
- 修复是否破坏了用户批准的硬约束。

## 6. 用结构化决策记录承接 reasoning

不将原始 Chain-of-Thought 写入业务 State。每个真正需要模型设计判断的节点必须输出精简的结构化决策：

~~~json
{
  "data": {},
  "decisions": [
    {
      "id": "decision_massing_01",
      "topic": "massing",
      "selected": "podium_tower",
      "alternatives_rejected": ["single_block"],
      "basis": [
        "constraint_floor_count",
        "constraint_public_lobby"
      ]
    }
  ],
  "assumptions": [],
  "unresolved": [],
  "provenance": {
    "source": "model",
    "fallback_used": false
  }
}
~~~

这些决策与知识证据起初作为关联记录保存，不建立独立状态机。后续节点消费 `data`、`decisions`、`assumptions` 和 `unresolved`。前端默认展示这些可解释结果，原始 reasoning 只作为临时调试流。

现有 [`ReasoningValidator`](../../../wild-server/app/agent/validators/reasoning_validator.py) 不直接接入主链评价 Chain-of-Thought。可以将其职责调整为 `DesignContractValidator`，校验：

- 硬约束是否进入设计契约；
- 决策是否引用真实约束；
- 是否仍有未解决冲突；
- 关键字段是否在归一化过程中丢失。

## 7. 精简 ExecutionPlan 和模型调用

当前 ExecutionPlan 最终仍会映射到有限能力白名单，因此建议：

- ExecutionPlan 根据意图和已完成状态确定性生成；
- 只在知识不足时执行 `planning_research`；
- 用户编辑设计目标和约束，而不是内部节点名称；
- Plan UI 由 ApprovedDesignContract 和阶段状态派生；
- ExecutionPlan 只记录阶段、进度、依赖和审核状态。

模型调用边界调整为：

| 环节 | 目标方式 |
|---|---|
| 意图分类 | 规则优先，模糊输入才调用小模型 |
| ExecutionPlan | 确定性生成 |
| 总体建筑方案 | 保留模型设计 |
| 空间功能和拓扑 | 保留模型设计；精确布局按有限求解实验逐步迁移 |
| 墙线推导 | 确定性 |
| 门洞宿主和局部坐标 | 确定性 |
| 外窗布置 | 模型给出立面意图，程序映射合法槽位 |
| 材料 | 用户明确时确定性，模糊时一次结构化调用 |
| 硬契约与几何校验 | 可执行规则确定性检查；审美与开放式语义评审单列，不伪装成硬验证 |
| 修复 | 确定性优先，剩余问题才调用受限模型 |

## 8. 让 normalizer 和 fallback 可观察

每个 normalizer 返回统一报告：

~~~json
{
  "preserved": [],
  "defaulted": [],
  "repaired": [],
  "dropped": [],
  "critical_information_lost": false
}
~~~

fallback 必须携带来源和信息损失记录：

~~~json
{
  "provenance": "fallback",
  "fallback_reason": "model_schema_invalid",
  "replaced_stage": "floor_layout",
  "preserved_constraints": [],
  "lost_decisions": [],
  "requires_review": true
}
~~~

执行规则：

1. 局部字段可修复时只修复局部，不整体替换方案。
2. 关键设计字段被删除时不允许静默继续。
3. 第一次格式错误只执行一次定向结构修复。
4. 只有模型服务失败、重复格式失败或方案无法通过基础校验时才进入 fallback。
5. 诊断 fallback 不可确认；完整且校验有效的基础模板只有在用户明确选择模板模式后才能审核，不伪装成原模型方案。
6. fallback 触发率、整体替换率和关键字段损失率进入运行指标。

主要改造位置：

- [`architecture_plan.py`](../../../wild-server/app/agent/architecture_plan.py)
- [`spatial_plan.py`](../../../wild-server/app/agent/spatial_plan.py)
- [`floor_space_analysis_node.py`](../../../wild-server/app/agent/nodes/floor_space_analysis_node.py)
- [`floor_layout_node.py`](../../../wild-server/app/agent/nodes/floor_layout_node.py)
- [`floor_openings_node.py`](../../../wild-server/app/agent/nodes/floor_openings_node.py)

## 9. 把多样性放在设计层

确定性装配器应保持可复现，不通过随机坐标制造多样性。多样性来自 ApprovedDesignContract 中明确的设计维度：

- `massing_strategy`：单体、错动、退台、庭院、裙房塔楼；
- `circulation_strategy`：中央核心、侧向核心、双核心、环形；
- `spatial_zoning_strategy`：线性、核心式、组团式、环廊式；
- `facade_rhythm`：规则、渐变、分段、错位；
- `roof_strategy`：整体、分区、退台平台、坡顶组合；
- `void_strategy`：中庭、天井、露台、架空；
- `entrance_strategy`：居中、偏置、转角、多入口。

可复现与多样性的边界：

- 同一批准契约、同一装配及依赖版本，应产生相同规范化 Blueprint（排除时间戳等运行字段）；
- seed 若受模型支持，只作为批准前候选实验的配置，不能保证模型端到端逐字复现；
- 新候选策略不能改变已批准设计；策略变化需要新 revision 和对应审核；
- 诊断 fallback 与用户主动选择的基础模板模式分开；
- 不使用建筑 ID、截图坐标或单一案例名称分支。

### 10.2 wild-core 真实重建

最终保存前执行与前端一致的无头重建：

~~~text
Blueprint
→ wild-compiler
→ wild-core
→ reconstruction diagnostics
→ Delivery Gate
~~~

优先直接复用 TypeScript compiler/core，不在 Python 中重新实现一套近似几何。

以下是逐步建设的阻断检查目标，需先确定适用范围、容差与正反例测试；不能直接把现有包围盒诊断全部升级成全局门禁：

- Mesh 缺失；
- 非有限顶点或退化几何；
- 屋顶与承托墙分离；
- 父子组件明显脱离；
- 屋顶覆盖不足；
- 洞口没有形成真实开洞；
- 楼梯没有连接目标楼层。

## 11. 统一 ValidationIssue 和修复收敛规则

所有校验器输出同一种问题结构：

~~~json
{
  "code": "roof_support_gap",
  "severity": "error",
  "stage": "reconstruction",
  "entity_ids": ["roof_main", "wall_upper_01"],
  "observed": {"roof_base_y": 6.0},
  "expected": {"support_y": 6.4},
  "repairability": "deterministic",
  "repair_target": "roof_main",
  "constraint_ids": ["constraint_roof_01"]
}
~~~

统一修复顺序：

~~~text
确定性修复
→ 受影响校验器复检
→ 全量复检
→ 必要时受限模型修复
→ 全量复检
→ wild-core 重建复检
~~~

修复先检查禁止条件：破坏已批准硬约束、越过允许修改范围、引入新 blocker/更严重错误、必需校验不可用，均拒绝候选。通过这些条件后，再判断目标问题是否改善并完成全量复检。警告和设计偏好可辅助比较，不得抵消硬约束违反。

同时保留问题级预算和整个 request/job 的自动修复、重规划、调用次数与成本总预算。新错误码或新实体 ID 不得重置任务总预算。

## 12. 对齐统一实施阶段

全局顺序以[统一实施路线](../统一实施路线与验收.md)为准，本专题不再独立安排一套 P0–P6。

| 全局阶段 | 工作流专项任务 |
| --- | --- |
| P0 | 保存模型、normalizer、fallback 和 repair 证据，得到成本与信息损失基线 |
| P1 | 最小 RequirementSpec、平面契约和来源/质量分离；保留失败前候选；修复已确认的必需校验异常放行 |
| P2 | 有限布局求解试验；根据调用收益简化 ExecutionPlan 和固定模型步骤 |
| P3 | 批准版本清单、Patch 失效传播和装配映射；已有状态先通过适配复用 |
| P4 | 真实重建门禁、复杂形态与有效候选多样性评测 |

不要把完整 ApprovedDesignContract 建成首期观测和局部修复的前置条件。先围绕关键需求与平面完成小闭环，再按实际跨阶段一致性问题扩展契约。

## 13. 回归和评估

首期只验收统一路线声明的矩形单层/双层范围。下面的完整矩阵是后续覆盖目标，不是首期全部交付要求：

- 建筑类型：住宅、办公、商业、公共建筑；
- 楼层：单层、多层、高层示意；
- 体量：矩形、L 形、U 形、庭院、退台、裙房塔楼；
- 屋顶：平顶、坡顶、分区屋顶；
- 平面：不同功能分区和交通策略；
- 特殊几何：挖空、退台、曲线墙、幕墙、多楼梯和电梯。

每个样例同时断言：

- 硬约束全部进入 ApprovedDesignContract；
- 每条适用硬约束都有实体、关系、集合或全局计算的验收证据，未检查项单列；
- normalizer 没有静默删除关键字段；
- fallback 不会伪装成模型方案；
- 确定性修复后重新执行全量校验；
- 模型修复只能修改失败实体的允许字段；
- 适用且必需的 `wild-core` 检查均已执行，无 error，报告附覆盖范围；
- 同一批准契约和实现版本的规范化装配输出稳定；
- 多样性只在满足约束的有效候选之间比较，模型链重复运行并报告波动。

## 14. 验收指标

持续记录：

- 硬约束结构化覆盖率；
- 硬约束最终实现率；
- 各节点输入、输出字段保留率；
- fallback 触发率和整体替换率；
- 每个成功 Blueprint 的模型调用次数和 Token；
- 首轮几何通过率；
- 确定性修复后通过率；
- 模型修复后通过率；
- `wild-core` 重建通过率；
- 修复引入新错误率；
- 固定批准契约与实现版本的装配可复现率；
- 有效候选的体量、空间拓扑和立面策略差异率。

三条硬门禁：

1. 所有适用的已批准硬约束必须有通过的验收证据；未检查、能力不支持或需用户取舍的项必须显式处理，不能从分母中隐藏；
2. 交付时适用的必需重建检查必须已执行且 error 为 0，检查覆盖率另外报告；
3. 修复不得引入新 blocker 或破坏已批准约束。

## 15. 不采用的做法

- 不把原始 Chain-of-Thought 写入业务状态。
- 不简单接入 `ReasoningValidator` 再增加一次模型自检。
- 不继续叠加 planner、reviewer 和 critic 等自然语言节点。
- 不为每个建筑或 Bug 增加专属坐标修复。
- 不使用随机坐标制造多样性。
- 不让 fallback 静默覆盖有效模型设计。
- 不把前端 reconstruction error 当成普通提示。
- 不同时维护多个可写的设计事实源。

## 16. 面试表达摘要

这个问题可以按照下面的逻辑说明：

1. **定位矛盾**：系统不是没有推理，而是推理结果没有充分转换为可执行中间状态。
2. **划分边界**：模型负责总体方案和空间设计等不可替代判断，装配、校验和可确定修复交给程序。
3. **建立设计契约**：用约束账本和 ApprovedDesignContract 连通用户需求、设计决策、Blueprint 实体和校验证据。
4. **限制 fallback**：所有默认、删除、修复和整体替换都必须可观察，关键信息丢失时不能静默继续。
5. **闭合几何交付**：服务端校验后执行 `wild-core` 真实重建验证，逐步覆盖最终几何，并明确自动检查与视觉验收的边界。
6. **用数据验收**：同时评估约束实现率、Token 成本、fallback 比例、几何通过率、修复收敛率和结果多样性。

第一个应当落地的改造是：**建立可信基线，保存模型候选与归一化差异，定位检索异常和整体 fallback；随后以最小需求契约保住有效平面。** 上述面试要点属于拟实施方案，完成代码改造和同条件验证后才能描述为已取得效果。
