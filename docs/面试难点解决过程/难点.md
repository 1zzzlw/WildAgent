# WildAgent Agent 项目问题清单与领域分类

本文档用于持续记录 WildAgent 开发过程中真实遇到的 Agent 工程问题，并将每个问题归类到对应的 Agent 技术领域。

它不是只围绕某几个问题展开的专题总结，也不默认不同问题之间存在因果关系。后续发现的新问题应作为独立条目继续追加，用于：

- 梳理项目中解决过的工程问题；
- 明确每次实践对应的 Agent 知识领域；
- 沉淀面试时可讲述的问题、分析、方案与验证过程；
- 识别已经接触和尚未形成实践的问题方向。

## 一、维护规则

跨专题的实施顺序、共享契约、首期范围和评测口径统一见[统一实施路线与验收](统一实施路线与验收.md)。本索引用于分类和问题追踪，各专题的技术方案不是五套独立重构任务。最近文档优化：2026-09-05；本次仅修订文档，未实施所列业务方案。

每个问题至少记录以下信息：

- **问题名称**：使用能够反映本质的工程名称，而不是只描述表面现象；
- **一级领域**：该问题在 Agent 工程中的主要归属；
- **二级领域**：问题涉及的具体技术方向，可以有多个；
- **关键术语**：便于学习、检索和组织面试表达的中英文术语；
- **当前状态**：区分发现问题、形成方案、完成实现和验证闭环；
- **问题摘要**：说明现象、原因和影响；
- **面试表达**：用简洁语言说明问题本质和个人实践；
- **详细记录**：链接到完整的问题分析、解决方案和验证材料。

证据分别标为“源码确认”“样本观察”“待验证假设”。单次请求成本不代表均值；源码存在检索路径不等于已证明模板偏置。面试中的完成时表述必须有实际代码与运行结果支持。

状态统一使用：`已发现`、`已定位`、`已形成方案`、`实施中`、`已验证`、`已归档`。

> “已形成方案”不等于“已解决”。只有完成代码实现，并通过测试、评估或真实运行结果证明有效，才能标记为“已验证”。

## 二、Agent 领域分类参考

这张表是后续新增问题时的分类参考。一个问题只选择一个最主要的一级领域，相关能力放入二级领域，避免重复创建相似条目。

| 一级领域 | 典型二级领域 | 主要关注点 |
| --- | --- | --- |
| Agent Architecture & Orchestration | 工作流编排、状态机、节点路由、并发、终止条件 | Agent 如何组织和推进任务 |
| Planning & Reasoning | 任务分解、计划生成、Reasoning-to-Action、反思与重规划 | Agent 如何形成并修正行动计划 |
| State & Memory | 结构化中间状态、短期记忆、长期记忆、Checkpoint、状态压缩 | 信息如何在执行过程中保存和传递 |
| Tool Use & Execution | 工具选择、参数生成、Schema、幂等性、副作用管理 | Agent 如何可靠调用外部能力 |
| Knowledge & RAG | 知识治理、索引、召回、重排、检索路由、Context Engineering | 外部知识如何进入决策上下文 |
| Reliability & Recovery | 校验、重试、Fallback、故障恢复、确定性修复 | Agent 如何处理不确定输出和执行失败 |
| Evaluation & Observability | Trace、日志、离线评估、在线指标、回归测试、成本分析 | 如何判断 Agent 是否真正有效 |
| Human-in-the-loop & Interaction | 人工确认、可中断执行、进度反馈、可解释性 | 用户如何参与和控制 Agent |
| Safety & Governance | 权限控制、输入输出边界、数据隔离、风险操作审批 | Agent 如何安全、合规地行动 |
| Multi-Agent Systems | 任务委派、角色协作、共享状态、冲突处理 | 多个 Agent 如何协同完成任务 |
| Runtime & Deployment | 会话生命周期、WebSocket、持久化、任务恢复、扩缩容 | Agent 如何稳定运行和部署 |
| Performance & Cost | Token、延迟、缓存、并行、模型路由 | 如何控制运行成本并提高效率 |

## 四、问题记录

### 1. Agent 编排、结构化中间状态与执行闭环失配

- **英文分类**：Agent Orchestration, Structured Intermediate State, and Execution-Loop Misalignment
- **一级领域**：Agent Architecture & Orchestration
- **二级领域**：Planning & Reasoning、State & Memory、Reliability & Recovery、Evaluation & Observability
- **关键术语**：Planning–Execution Alignment、Reasoning-to-Action Gap、Structured Intermediate Representation、Lossy Planning Compilation、Verification and Recovery Loop
- **当前状态**：已形成方案，尚未完成实现与效果验证

#### 问题摘要

WildAgent 当前存在推理成本与实际收益不匹配的问题。Agent 生成了大量自然语言 reasoning，但关键设计意图缺少贯穿中间状态的完整追踪；已有样本中模型设计在归一化失败后被整体回退，暴露了规划—执行对齐问题。

模型的设计信息还会在 JSON 解析、normalizer、fallback 和确定性装配过程中继续被压缩或覆盖，可以进一步归类为 Lossy Planning Compilation，即规划信息从自然语言推理编译为可执行 Blueprint 时发生有损转换。

同时，固定工作流、确定性兜底和受限组件能力可能限制设计搜索空间；不同详细输入是否因此收敛为相似体量、平面和立面，仍需多样性评测。现有空间校验、修复、复检与 `wild-core` 真实重建之间也没有完全闭合，因此某个 Blueprint 通过服务端字段校验，并不必然代表最终 Mesh 几何正确。

#### 面试分类

这不是单纯的 Prompt 问题，而是以 **Agent 工作流编排** 为主，横跨以下方向的系统问题：

- 规划结果能否转化为执行节点真正使用的状态；
- 结构化中间状态能否保留关键设计意图；
- Fallback 和确定性规则是否过度覆盖模型决策；
- 校验、修复、复检与最终执行结果能否形成闭环；
- 推理 Token 和执行质量之间是否存在可度量的收益。

#### 面试表达

> 我遇到的是 Agent 的规划—执行对齐问题。模型虽然生成了较多推理内容，但关键设计决策没有完整编译为可执行的结构化状态，后续又受到 normalizer、fallback 和确定性装配的二次压缩。我将问题从 Prompt 层提升到工作流、状态表示、能力约束和验证闭环层进行分析，并形成了相应的结构化状态与几何验证改造方案。目前应准确描述为已完成定位和方案设计，尚待实现与量化验证。

### 2. RAG 知识治理、检索路由与上下文模板偏置

- **英文分类**：RAG Knowledge Governance, Retrieval Routing, and Context Template Bias
- **一级领域**：Knowledge & RAG
- **二级领域**：Knowledge Governance、Retrieval Orchestration、Context Engineering、Evaluation & Observability
- **关键术语**：External Semantic Memory、Knowledge–Task Misalignment、Retrieval-Induced Bias、Retrieval Routing、Context Dilution
- **当前状态**：已形成方案，尚未完成知识库重构与检索效果验证

#### 问题摘要

当前知识库职责错位：通用建筑类型、组件百科、固定尺寸、组件构成合同和 fallback 配方具有进入生成上下文的路径，但缺少充分的阶段与职责隔离，存在挤占项目契约、空间关系和能力边界的风险。实际注入比例和影响需要 Trace 与对照实验验证。

这些通用知识与大模型已有建筑知识可能重叠，却会通过 RAG 连续进入总体方案、平面分析、空间布局和门窗设计等节点。模型可能把原本只应作为参考的建筑惯例理解成默认配方或隐性硬约束，形成 Knowledge–Task Misalignment 和 Retrieval-Induced Design Bias，可能增加 Token 成本、压缩设计自由度并造成结果趋同；这些因果贡献尚未量化，通用领域参考也可能对空间功能和拓扑提供增益。

知识库更应该重点提供大模型自身无法可靠知道的 WildAgent 项目事实：

- 当前 `.wild` Schema、字段和枚举；
- Blueprint 坐标系、局部坐标和宿主引用；
- 设计意图到 WILD 元素/组件的映射；
- `wild-compiler` 和 `wild-core` 的能力边界；
- 非原生业务对象的受支持降级表达；
- 跨构件组装、依附、覆盖和连续性约束；
- 已验证的错误、校验和确定性修复规则。

#### 面试分类

这不是单纯的“知识库内容质量差”，而是以 **Agent 知识架构与 RAG** 为主，横跨以下方向的系统问题：

- 哪些知识应由基础模型提供，哪些知识必须由项目知识库提供；
- 不同任务节点应检索什么知识，以及是否需要分域路由；
- 检索结果如何组织为有效上下文，而不是堆叠文档片段；
- 固定配方如何通过检索形成隐性模板偏置；
- 如何使用召回指标和生成结果对知识库改造进行验证。

#### 面试表达

> 我遇到的是 Agent 的知识治理与上下文工程问题。知识库包含与基础模型知识可能重叠的领域参考，但各阶段的项目契约、空间语义和组件能力边界缺少充分隔离。源码确认了混合检索路径，模板偏置的实际贡献仍待实验。我提出按项目规则、必要领域参考、示例和 fallback 治理知识，并计划通过检索评估与生成回归验证取舍。目前应准确描述为已完成问题定位和方案设计，尚未完成整体重构与量化验收。

### 3. RAG 检索准确率、知识利用率与评测闭环不足

- **英文分类**：RAG Retrieval Quality, Knowledge Utilization, and Evaluation-Loop Gap
- **一级领域**：Knowledge & RAG
- **二级领域**：Query Transformation、Indexing、Retrieval & Reranking、Context Engineering、Evaluation & Observability、Performance & Cost
- **关键术语**：Query Rewriting、Index Enrichment、Hybrid Retrieval、Reranking、Hit@K、Recall@K、MRR、Context Utilization、Groundedness、A/B Evaluation
- **当前状态**：已形成方案，尚未完成生产接入和对照实验

#### 问题摘要

WildAgent 已经具备语义分片、Chroma 向量召回、`SpecQuery` 过滤、确定性别名规划、规则重排、Trace 和检索评测脚本，但这些能力尚未形成能够证明效果的完整闭环。

项目中虽然存在 LLM 查询改写和 BM25 混合检索的原型代码，但没有接入当前 `AgentService → RAGSpecLoader` 生产主链；索引阶段也没有发现使用 LLM 自动提取、校验和版本化结构化字段的正式流程。现有历史报告使用 Hash embedding 且只执行了少量问题，不能代表当前生产语义检索质量。

更重要的是，当前指标主要回答“是否召回并注入了知识”，还不能回答“Agent 是否实际采用这些知识并改善了最终 Blueprint”。因此需要把检索准确率、上下文利用率、端到端生成质量和运行成本分开评估。

#### 面试分类

这是一个以 **RAG 检索优化** 为主、同时涉及 **Agent Evaluation** 的系统问题，包含：

- 自然语言查询到可执行 QueryPlan 的转换；
- 索引 metadata、检索文本和原始知识的分层管理；
- 向量召回、关键词召回、候选融合和二阶段重排；
- 检索片段到结构化设计决策的知识采用追踪；
- Recall、MRR、延迟、Token 和最终 Blueprint 质量的联合评估。

#### 面试表达

> 我发现项目已经有查询改写和混合检索原型，但生产链仍以手工查询、确定性过滤和向量召回为主，而且缺少同一索引和评测集上的 A/B 对照。更关键的是，命中知识不代表 Agent 真正使用了知识。因此我计划先定位检索异常，建立原始查询与当前主链基线，再按难例证据试验选择性 LLM 改写和索引增强；索引增强放到离线入库阶段并保留来源和版本。最终除了 Recall 和 MRR，还追踪知识是否进入结构化决策，以及是否提高 Blueprint 的校验通过率。目前完成的是代码审计和方案设计，尚不能宣称检索效果已经提升。

### 4. Agent 分层自检与自我纠错闭环不完整

- **英文分类**：Layered Agent Self-Check and Closed-Loop Recovery Gap
- **一级领域**：Reliability & Recovery
- **二级领域**：Self-Reflection & Self-Correction、Validation、Tool Use & Execution、State & Memory、Evaluation & Observability、Safety & Governance
- **关键术语**：Structured Validation Issue、Bounded Repair、Revalidation、Rollback、Fail-Closed、Decision Consistency、Outcome Verification
- **当前状态**：局部校验—修复闭环已实现，统一自检与端到端纠错尚未完成

#### 问题摘要

WildAgent 已存在 Structure、Factual、Tool 和 Reasoning 四类通用 Validator，但它们没有共同接入生产工作流：Structure、Tool 和 Reasoning Validator 主要停留在独立模块和 Mock 测试，Factual Validator 也只通过私有范围、枚举检查部分接入最终流水线。

生产链实际接入的自我纠错能力分布在另一套实现中：Blueprint 确定性校验、结构化 `ValidationIssue`、白名单修复工具、候选副本、全量复检、无改善回滚、单组件重试预算和最终保存门禁。Callback 还复检部分 DesignBrief 的楼层、配额和开口约束。这说明项目已有局部纠错和有限设计一致性检查，缺少的是完整需求覆盖与统一协议。

此外，当前事实检查覆盖有限，自然语言推理检查不稳定，没有实体归属的全局问题缺少明确升级路由，前端 `wild-compiler / wild-core` 的真实重建诊断也没有自动回到后端纠错链。因此服务端 Blueprint 通过校验，仍不等于最终 Mesh 结果正确。

#### 面试分类

这是一个以 **Agent Reliability & Recovery** 为主的系统问题，包含：

- 不同中间状态的结构与契约检查；
- 用户约束、项目事实和输出之间的语义一致性；
- 工具动作的白名单、权限、前置条件和副作用控制；
- 计划、中间状态与最终结果的决策一致性；
- 修复后的复检、回滚、重试预算和停止条件；
- compiler/core 真实执行结果反馈；
- 故障注入、修复成功率和误修率评估。

#### 面试表达

> 我最初把 Agent 自检分为结构、事实、工具和推理四层。审计后发现，四个 Validator 类并没有组成生产闭环，真正可靠的是 Blueprint 校验与 Callback 的受限工具修复、全量复检和回滚。因此我提出把“推理自检”改为可执行状态之间的决策一致性检查，并计划补充真实执行结果检查和任务总预算。能确定的问题由程序修复，模型只能选择白名单动作；候选只有在不引入新问题并通过复检后才能提交，否则回滚并在预算耗尽后停止或转人工。目前项目已有局部闭环，本轮完成的是统一方案设计，尚未完成端到端改造和量化验收。

- [解决思路](Agent自我纠错能力问题/解决思路.md)

### 5. 平面规划、中间表示与用户审核链路失配

- **英文分类**：Floor-Plan Planning Representation and Human-in-the-loop Misalignment
- **一级领域**：Planning & Reasoning
- **二级领域**：Structured Intermediate Representation、Constraint Satisfaction、State & Memory、Human-in-the-loop、Knowledge & RAG、Reliability & Recovery、Evaluation & Observability、Performance & Cost
- **关键术语**：FloorPlanIR、Representation Alignment、Topology-first Planning、Constraint Ledger、Plan Repair、Multi-view Consistency、Human-in-the-loop Editing、Plan-to-Blueprint Fidelity
- **当前状态**：已完成源码和真实会话审计，已形成方案；尚未完成整体改造和对照评测

#### 问题摘要

WildAgent 已经采用了正确的两阶段目标：FloorPlanIR 保存二维设计事实，程序从同一份 IR 绘制 SVG，用户确认后再由 `ApprovedPlanAssembler` 生成 Blueprint。实际体验差不是因为保留了 SVG，而是因为 FloorPlanIR 之前的规划链和用户修改链仍不稳定。

当前总体体量会在空间需求之前被锁定，平面阶段再用多个串行 LLM 节点直接生成空间清单、精确坐标、墙体和洞口。平面规范主要以 Prompt 文本存在，缺少带来源、优先级和验收状态的结构化约束账本；空间需求与体量之间也没有可行性反馈循环。一个覆盖、重叠或宿主问题仍可能让整份模型设计被替换成确定性故障预览。

源码中确实存在按建筑关键词选择空间清单、按面积生成条带布局和两区/三区/四区基础平面的固定 fallback，但真实 Trace 不支持“坏结果是知识库直接套模板”这一单一结论。2026-09-03 已审计请求中 RAG 实际零命中并记录 `BadRequestError`，三个平面节点只拿到了完整注入的 Blueprint 基础规范；该次请求记录 4 次 LLM 调用共消耗 65674 Token、LLM 耗时约 440 秒，模型生成的多空间和 21 面内墙最终仍因覆盖问题退化成 2 个空间、0 面内墙的不可确认预览。

前端 SVG 当前通过 `<img>` 展示，用户只能确认或提交自然语言意见；修改会让平面链从空间分析重新运行，并不是针对 FloorPlanIR 的局部 Patch。因此系统还没有实现真正的“用户在平面图上修改，同一份参数状态同步更新”。

#### 面试分类

这是一个以 **Agent Planning Representation** 为主的系统问题，包含：

- 自然语言需求到 RequirementSpec 的结构化转换；
- 空间程序、邻接拓扑和精确几何的职责分离；
- 总体体量与平面可行性的双向规划；
- FloorPlanIR、SVG 和 Blueprint 的多视图一致性；
- 阶段化知识检索和上下文职责；
- 校验失败后的局部修复、回退和信息保留；
- 用户可视化审核、局部编辑和版本控制；
- 平面质量、多样性、成本和 IR-to-Blueprint 保真度评测。

#### 面试表达

> 我最初怀疑平面效果差是因为模型不理解 SVG 或知识库套用了固定模板。源码和真实 Trace 表明，SVG 本身是由 FloorPlanIR 确定性渲染的；该次请求中 RAG 零命中却注入了与二维规划不匹配的 Blueprint 规范，模型又串行手算空间、坐标和洞口，最终一个几何错误会让整份设计退化成 fallback。我的方案是保留两阶段架构，新增 RequirementSpec 和拓扑优先规划，让程序求解可计算的几何；用户的鼠标或自然语言修改统一转换成 FloorPlanPatch，校验后更新同一份 IR，最终由同一个批准 revision 驱动 SVG 和 Blueprint。目前完成了问题定位和方案设计，尚未完成代码改造与量化验收。
