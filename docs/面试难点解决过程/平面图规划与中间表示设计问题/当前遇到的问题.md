# 当前遇到的问题：平面规划、中间表示与用户审核链路失配

> 本文记录源码机制与历史请求观察；跨专题优先级和证据口径见[统一实施路线与验收](../统一实施路线与验收.md)。最后补充核对：2026-09-05。

## 1. 问题结论

WildAgent 把新建筑生成拆成“平面规划”和“Blueprint 构建”两个阶段，这个方向本身是正确的。当前代码也已经确立了合理的目标边界：`FloorPlanIR` 保存二维设计事实，SVG 由程序从同一份 IR 绘制，用户确认后再由 `ApprovedPlanAssembler` 生成三维主体。

实际体验差并不是因为“保留了 SVG 平面图”，而是因为这条链路目前还没有真正做到设计信息稳定流动：

- 平面设计以前置总体体量为不可修改边界，空间需求与体量缺少可行性反馈循环；
- 平面规范主要散落在 Prompt 和 Python 校验器中，没有形成版本化、可逐项追踪的约束账本；
- 平面节点复用了与阶段不匹配的 RAG 上下文，真实 Trace 中甚至没有召回任何知识；
- 模型一次性生成精确坐标，任一严重几何问题都可能让整份设计退化为确定性故障预览；
- Prompt 示例、Architecture Profile 和硬编码 fallback 共同形成模板锚定；
- 用户当前只能看 SVG、提交文字意见，不能直接编辑平面实体；
- 修改意见会重新运行整条平面链，未被要求修改的设计也可能漂移。

因此，该问题更准确的定义是：

> WildAgent 已经有 FloorPlanIR、确定性 SVG 和人工确认的正确骨架，但空间需求、体量、拓扑、几何、知识上下文和用户修改之间尚未形成统一的可执行规划协议，导致模型生成成本很高、有效设计容易在校验与 fallback 中丢失，最终预览呈现模板化和不稳定。

## 2. Agent 领域分类

- **一级领域**：Planning & Reasoning
- **二级领域**：Structured Intermediate Representation、Constraint Satisfaction、State & Memory、Human-in-the-loop、Knowledge & RAG、Reliability & Recovery、Evaluation & Observability、Performance & Cost
- **问题类型**：规划表示与人机协同链路设计问题
- **关键术语**：FloorPlanIR、Representation Alignment、Topology-first Planning、Constraint Ledger、Plan Repair、Multi-view Consistency、Human-in-the-loop Editing、Plan-to-Blueprint Fidelity
- **当前状态**：已完成源码和真实会话审计，已形成方案；尚未完成整体改造和对照评测

## 3. 当前设计实际上是怎样的

当前工作区的新建筑链路是：

```text
用户需求
  ↓
execution_plan
  ↓
architecture
  - LLM 生成多个总体方案候选
  - 程序按 Architecture Profile 和固定评分选择一个
  - 锁定 massing / volumes / facades / roof / component_quota
  ↓
floor_space_analysis
  - LLM 生成逐层空间清单
  - 首次检索 building_type + recipe
  ↓
floor_layout
  - LLM 在已锁定体量中生成空间坐标或多边形
  - 复用上一节点的 RAG 上下文
  ↓
floor_openings
  - LLM 生成内墙、门窗和垂直交通
  - 再次复用同一 RAG 上下文
  ↓
floor_validate
  - Python 合并三份输出
  - 归一化、有限修复、工程预审
  - 从 FloorPlanIR 确定性生成 SVG
  ↓
floor_plan_review
  - 用户确认或提交文字修改意见
  - 修改时回到 floor_space_analysis
  ↓
material_plan / ApprovedPlanAssembler / G1-G6
  ↓
Blueprint / G7 / final_validate / 保存
```

主要入口如下：

| 环节 | 当前实现 |
| --- | --- |
| 工作流路由 | [`graph.py`](../../../wild-server/app/agent/graph.py) |
| 总体方案 | [`architecture_node.py`](../../../wild-server/app/agent/nodes/architecture_node.py) |
| 空间清单 | [`floor_space_analysis_node.py`](../../../wild-server/app/agent/nodes/floor_space_analysis_node.py) |
| 空间布局 | [`floor_layout_node.py`](../../../wild-server/app/agent/nodes/floor_layout_node.py) |
| 内墙、门窗与流线 | [`floor_openings_node.py`](../../../wild-server/app/agent/nodes/floor_openings_node.py) |
| 合并、校验与 SVG | [`floor_validate_node.py`](../../../wild-server/app/agent/nodes/floor_validate_node.py) |
| FloorPlanIR、fallback 与 SVG Renderer | [`spatial_plan.py`](../../../wild-server/app/agent/spatial_plan.py) |
| 用户确认与修订路由 | [`floor_plan_review_node.py`](../../../wild-server/app/agent/nodes/floor_plan_review_node.py) |
| 前端审核界面 | [`AgentExecutionPanel.vue`](../../../wild-web/src/components/panels/AgentExecutionPanel.vue) |
| 已确认平面到主体 | [`assembler.py`](../../../wild-server/app/agent/plan2build/assembler.py) |

仓库中还保留了 [`floor_plan_design_node.py`](../../../wild-server/app/agent/nodes/floor_plan_design_node.py)，用于旧检查点兼容。当前新计划能力已经改成四个平面子步骤，但旧节点仍在 Graph 路由表中，迁移完成前需要警惕新旧链路语义不一致。

## 4. 对三个猜测的核查结果

### 4.1 “大模型没有利用平面图规范”——部分成立

不能说模型完全没有收到规范，因为 [`prompts.py`](../../../wild-server/app/agent/prompts.py) 已经明确写入了坐标系、空间覆盖、邻接、采光、湿区、门窗宿主和连通性等规则。

但这些规则主要以自然语言 Prompt 和 JSON 示例存在，不等于模型真正吸收并满足了规范：

- 平面节点没有使用独立、版本化的 FloorPlanIR JSON Schema 约束模型输出；
- 用户硬约束没有被拆成带 ID、来源和验收状态的 `RequirementSpec`；
- `extract_json_object()` 只能证明取到了 JSON，不能证明空间设计可行；
- 真正的几何问题要到 `floor_validate` 合并之后才集中暴露；
- 当前知识库没有一份专门面向“空间规划阶段”的权威平面设计约束包，现有内容更多是 Blueprint Schema、建筑类型和组装配方。

所以更准确的说法是：

> 平面规范进入了 Prompt，但没有完整进入模型必须遵守、程序可以逐项验收的结构化规划协议。

### 4.2 “平面图是固定设计”——确实存在固定化来源

当前项目中存在明确的确定性模板代码：

- [`floor_space_analysis_node.py`](../../../wild-server/app/agent/nodes/floor_space_analysis_node.py) 的 `_fallback_space_analysis()` 按别墅、公寓、商业、办公、民宿等关键词选择固定空间清单；
- [`floor_layout_node.py`](../../../wild-server/app/agent/nodes/floor_layout_node.py) 的 `_layout_spaces()` 会把多个空间按面积比例排成贯穿进深的竖向条带；
- [`floor_openings_node.py`](../../../wild-server/app/agent/nodes/floor_openings_node.py) 的 `_derive_walls_and_doors()` 会从公共边界派生墙，并在每面墙中间放一扇门；
- [`spatial_plan.py`](../../../wild-server/app/agent/spatial_plan.py) 还保留两区、三区和四区的 `deterministic_baseline_spatial_plan()`。

当前拆分链已经把这些 fallback 标成 `deterministic_fallback`，并禁止它冒充模型方案直接确认，这是正确的安全边界。但是它仍然会被绘制给用户；当模型结果频繁无效时，用户实际看到的自然就是相似的模板平面。

此外，Prompt 中重复出现固定矩形分区示例，总体方案又受到 Architecture Profile、默认尺寸、复杂度目标和规则评分限制。真实 Trace 中两个总体方案都得到 `118` 分，选择逻辑在同分时固定选择第一个候选。这些机制都会进一步降低结果差异。

### 4.3 “是不是直接从知识库套出一套固定模板”——当前证据不支持这个结论

最新真实 Trace [`req_1788435876883_xvjfu98kp.json`](../../../wild-server/storage/sessions/rag_traces/session_1788435875430/req_1788435876883_xvjfu98kp.json) 显示：

- 两次 `retrieve_many` 都出现 `BadRequestError`；
- `hit_count` 都是 `0`；
- 没有任何 `injected_chunk_ids`；
- 每次上下文仍包含 `13710` 个字符，这是始终完整注入的 `BLUEPRINT-SPEC-MINIMAL.md`，不是召回到的平面设计模板。

因此，这一次坏结果并不是知识库召回了固定别墅模板。更接近事实的是：

> RAG 没有召回平面知识，但系统仍把一份偏 Blueprint 构件协议的长基础规范送进了平面节点；模型输出无效后，程序 fallback 又产生了模板化预览。

当时的知识库确实存在模板偏置风险。例如现已归档的 [`villas.md`](../../../docs-dev/retired-knowledge/building_types-rules-v2/residential/villas.md) 包含固定尺寸的完整 Blueprint。rules-v3 已将全部 `building_type` 文档移出活动索引，并通过 Loader 过滤和回归测试阻止它们重新进入生成上下文。

## 5. 已确认的核心问题

### 5.1 空间需求在总体体量之后生成，阶段之间只有单向约束

`architecture` 先锁定 `massing` 和 `volumes`，后续平面 Prompt 又明确禁止修改总体层数、体量和立面。空间分析如果提出的房间面积与已锁定体量不兼容，布局节点只能强行塞入现有边界。

当前用户修订平面时，[`route_floor_plan_review()`](../../../wild-server/app/agent/nodes/floor_plan_review_node.py) 只返回 `floor_space_analysis`，不会把“体量本身不可行”的问题升级回 `architecture`。

这会形成：

```text
总体体量先锁死
  ↓
空间清单无法放入
  ↓
布局坐标违规
  ↓
整份回退
  ↓
用户继续要求修改，但体量仍不能变
```

### 5.2 缺少结构化约束账本

当前 Graph State 保存了 `architecture_plan`、三个平面子结果和 `floor_plan`，但没有独立保存：

- 用户硬约束；
- 用户偏好；
- 约束来源；
- 适用楼层或实体；
- 检查方式；
- 当前满足状态；
- 哪一次修订改变了该约束。

执行计划中的 `acceptance` 只能提供阶段级概述，无法代替实体级 `RequirementSpec`。因此模型下一轮重画时，很难稳定保留用户已经确认的关系。

### 5.3 平面 RAG 的知识路由和上下文职责错位

`floor_space_analysis` 检索 `building_type + recipe`，随后 `floor_layout` 和 `floor_openings` 复用同一个 `floor_plan_rag_context`。三个阶段需要的知识实际上不同：

| 阶段 | 真正需要的知识 |
| --- | --- |
| 空间清单 | 建筑功能、容量、空间类型和用户要求 |
| 空间拓扑 | 邻接、分区、采光、湿区、动线和核心位置 |
| 门窗与竖向交通 | 宿主、通行、疏散、洞口净距和跨层关系 |
| Blueprint 装配 | WILD 构件字段、局部坐标和编译器能力 |

当前却把 `BLUEPRINT-SPEC-MINIMAL.md` 作为 13710 字符的基础上下文完整注入前三个阶段。大量三维构件字段对二维空间规划没有直接帮助，却增加了输入 Token、注意力竞争和延迟。

更隐蔽的问题是：真实 Trace 中底层检索已经记录 `BadRequestError`，但节点诊断里的 `rag_error` 仍为 `null`，页面只显示“已完成知识检索”。这会让开发者误以为知识已经被使用。

### 5.4 模型承担了过多精确坐标工作

当前 `floor_layout` 要求 LLM 直接给出每个空间的 `bounds/polygon`，`floor_openings` 又要求 LLM 给出墙线、宿主、offset 和连通关系。

LLM 擅长判断“客厅靠近入口、厨餐相邻、卧室远离公共区”，但不擅长一次性保证：

- 多个多边形无重叠；
- 面积总和精确覆盖不规则轮廓；
- 所有内墙都落在公共边界；
- 门洞 offset 在墙长范围内；
- 所有空间从入口连通；
- 跨层核心在每层保持同位。

这些可计算约束全部交给模型时，存在输出字段丰富但几何无效的风险。已有失败样本支持这种风险，整体通过率仍需完整基线。

此外，`prompts.py` 的空间分析要求空间面积之和接近单层面积，却将楼梯/电梯推迟到后续阶段，存在先分完面积再插入核心的冲突风险。当前需要明确分区面积、净面积、墙厚、核心预留和跨层 void 的语义；不能仅更换求解方式而保留互相冲突的阶段约束。

### 5.5 校验失败时发生整份规划信息清零

[`normalize_spatial_plan()`](../../../wild-server/app/agent/spatial_plan.py) 会先尝试墙体吸附、补墙和修复宿主；如果仍有问题，则返回 `fallback_spatial_plan()`。空间重叠或覆盖缺失等问题因此会让整份模型设计被替换。

最新会话 [`session_1788435875430.json`](../../../wild-server/storage/sessions/session_1788435875430.json) 是直接证据：

- `floor_space_analysis` 产生了逐层空间清单；
- `floor_layout` 标记为 `source=model`；
- `floor_openings` 报告 21 面内墙、26 个洞口；
- `floor_validate` 最终只剩 2 个空间、0 面内墙、0 个洞口；
- `fallback_reason` 是空间未完整覆盖组合轮廓。

这说明高成本模型设计并不是逐项修复后落入 FloorPlanIR，而是在一个几何问题出现后整体丢失。

### 5.6 固定三次串行模型调用放大了成本，但没有提高最终有效率

同一 Trace 显示：

- 4 次 LLM 调用（总体方案 + 3 个平面节点）；
- 合计 `65674` Token；
- LLM 总耗时约 `440455ms`；
- 整个请求约 `441540ms`；
- 最终仍是不可确认的 fallback 平面。

这些是 2026-09-03 该次请求的计量，不代表平均成本或整段会话总成本。Trace 顶层的 `GenerationPaused` 应与检索 `BadRequestError`、无效平面和正常人工审核暂停分别统计。该样本说明高成本调用没有产出可确认平面；减少模型节点能否改善质量，仍需对照验证。

### 5.7 修改不是对 FloorPlanIR 的局部编辑，而是整链重生成

用户提交修改意见后，流程从 `floor_space_analysis` 重新开始。当前没有稳定的平面编辑操作协议，例如：

```json
{
  "op": "resize_space",
  "target": "space_1_kitchen",
  "preserve": ["main_entrance", "stair_core", "wet_zone"]
}
```

因此，“把厨房扩大 1 米”可能同时改变卧室数量、空间 ID、门的位置和二层布局，用户难以逐步收敛方案。

### 5.8 SVG 目前是只读预览，不是平面编辑器

[`AgentExecutionPanel.vue`](../../../wild-web/src/components/panels/AgentExecutionPanel.vue) 把 SVG 编码成 Data URL 后放入 `<img>`。用户可以切换楼层、确认方案或提交文字意见，但没有空间选择、墙线拖动、门窗移动或尺寸编辑事件。

所以当前产品实际上是：

> 用户看图 + 用文字要求模型整份重画。

还不是：

> 用户直接修改 SVG 视图，系统把操作同步回 FloorPlanIR。

### 5.9 缺少平面设计质量和多样性评测

现有测试主要验证：

- normalizer 接受或拒绝某种结构；
- fallback 对不同建筑关键词返回不同空间名称；
- SVG 能否生成；
- warning 是否阻断确认；
- 节点状态是否正确传递。

这些测试不能回答：

- 不同详细需求是否得到不同拓扑；
- 相同需求多候选是否具有真实差异；
- 模型方案保留率是多少；
- fallback 触发率是多少；
- 用户修改是否只影响目标实体；
- FloorPlanIR 到 Blueprint 的几何是否一致；
- RAG 命中是否真的改善平面质量。

## 6. 已经正确、应该保留的设计

以下部分不是问题，不应因为体验差而推翻：

- 使用 `FloorPlanIR` 作为二维规划事实源；
- SVG 由程序从 IR 确定性渲染，不让模型手写 SVG；
- 用户确认前不生成和保存三维 Blueprint；
- `floor_validate` 不调用 LLM 给自己判通过；
- Blueprint 主体由 `ApprovedPlanAssembler` 消费已确认 IR；
- fallback 明确标记来源，不能冒充模型方案；
- 修复后重新运行同一校验器。

确认门禁仍有迁移边界：`is_confirmable_spatial_plan()` 接受 `model` 和 `deterministic_template`，新链合并又要求子结果均为 `model` 才标记模型来源。后续程序求解几何时应区分来源、质量和审核状态，保留诊断 fallback 不可确认的限制。

真正需要改变的是 FloorPlanIR 之前的规划方式、失败后的修复粒度和用户修改协议。

## 7. 证据边界

本次结论来自当前源码、已保存会话和 RAG Trace 的静态审计，需要明确以下边界：

- 当前工作区正在从单个 `floor_plan_design` 节点迁移到三个模型子步骤和一个确定性校验步骤，部分文件尚处于未提交状态；
- 保存的会话包含旧版本产生的 `deterministic_template`，不能把所有历史行为都当作当前最终代码行为；
- 现有真实样本大量使用“生成一个别墅”这类信息不足的请求，本身就会触发默认设计；
- 已确认模板和整体 fallback 会造成趋同，但“不同详细需求也必然趋同”仍需要正式多样性测试；
- 本轮只完成问题定位和方案文档，没有修改平面生成业务代码，也没有宣称质量已经提升。

## 8. 面试中的问题描述

> 项目最初已经采用 FloorPlanIR 和 SVG 审核，但实际效果仍然很差。我通过源码和真实 RAG Trace 发现，问题并不是 SVG 本身，也不能简单归因于知识库套模板。平面阶段的检索实际零命中，却反复注入与二维规划不匹配的 Blueprint 基础规范；模型串行生成空间清单、坐标和洞口，最终一个覆盖错误又会让整份设计退化成确定性模板。与此同时，体量先被锁定、用户修改只能整链重画、SVG 也只是只读图片。这个问题属于 Agent Planning Representation：需要让需求、拓扑、几何和用户编辑共同围绕可验证的 FloorPlanIR 演进，而不是依赖更多 Prompt 和更多模型调用。
