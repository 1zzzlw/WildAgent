# 解决思路：让 FloorPlanIR 成为可规划、可编辑、可验证的二维设计事实源

> 实现状态：目标方案，尚未完成整体改造和对照验证。最后整理：2026-09-05。  
> 共享契约、首期能力范围和 P0–P4 以[统一实施路线与验收](../统一实施路线与验收.md)为准。

## 1. 方案结论

保留“平面设计 → 用户确认 → Blueprint 构建”的两阶段架构，也保留 SVG 审核图。需要重构的不是 SVG，而是 FloorPlanIR 的生成和修改方式。

推荐目标是：

> 大模型负责需求理解、空间功能、拓扑意图和候选取舍；程序负责几何求解、硬约束校验、SVG 渲染和 Blueprint 编译；用户通过 SVG 操作或自然语言修改同一份 FloorPlanIR。

不要再让大模型独立编写 SVG，也不要让它在固定三次调用中反复手算全部坐标。平面阶段应围绕一个版本化状态逐步演进，任何修改都必须能够说明“改了什么、保留了什么、通过了哪些约束”。

## 2. 目标链路

```text
用户需求
  ↓
RequirementSpec
  - hard_constraints
  - preferences
  - capacities
  - source / priority / acceptance
  ↓
SpaceProgram + AdjacencyGraph
  - 每层功能空间
  - 邻接、分区、动线和跨层核心
  ↓
Massing / Layout 协同候选
  - 先验证面积和拓扑可行性
  - 不可行时允许回到总体体量
  ↓
LayoutEngine 生成几何候选
  - bounds / polygons
  - 共享边、墙线、门洞候选
  ↓
FloorPlanIR Candidate
  ↓
ValidatorSet
  ├─ 通过 → 确定性 SVG → 用户确认或编辑
  └─ 失败 → 局部修复 / 定向重规划 / 体量升级
  ↓
Approved FloorPlanIR
  ↓
ApprovedPlanAssembler
  ↓
Blueprint + G1-G6 + Core 重建检查
```

核心变化是：平面设计不再是一次性文本生成，而是一个有限状态机。

## 3. 统一三个事实层

### 3.1 RequirementSpec：用户到底要求了什么

首先把用户需求从 Prompt 文本中提取为结构化约束：

```json
{
  "requirements": [
    {
      "id": "req_main_entrance_south",
      "kind": "orientation",
      "target": "main_entrance",
      "operator": "faces",
      "value": "south",
      "priority": "hard",
      "source": "user",
      "status": "pending"
    },
    {
      "id": "req_kitchen_adjacent_dining",
      "kind": "adjacency",
      "target": "kitchen",
      "operator": "adjacent_to",
      "value": "dining",
      "priority": "hard",
      "source": "user",
      "status": "pending"
    }
  ]
}
```

每条约束至少保存：

- 稳定 ID；
- 来源：用户、项目规则、知识库或默认值；
- 优先级：hard、soft、default；
- 目标楼层或实体；
- 可执行验收方式；
- 当前满足状态和证据。

这样后续模型和程序不需要从整段历史对话重新猜需求。

### 3.2 FloorPlanIR：二维建筑设计事实

FloorPlanIR 保存：

- 楼层与有效轮廓；
- 空间程序和稳定空间 ID；
- 空间多边形；
- 邻接与可达关系；
- 共享边和墙体；
- 门窗宿主与局部位置；
- 竖向空间和交通核心；
- Requirement 满足证据的关联引用；
- 版本、来源和父版本。

它是二维设计的权威事实源；需求由 `RequirementSpec` 保存，批准依据由 `ApprovedDesignContract` 引用不可变版本，三维交付内容由 `.wild` Blueprint 保存。不能再维护一套可写的 SVG 设计事实。

### 3.3 SVG：FloorPlanIR 的 View

SVG 只承担：

- 给用户展示空间、尺寸、墙、门窗和校验结果；
- 接收用户的选择、拖动和修改操作；
- 把操作转换成 FloorPlanIR Patch；
- 在 Patch 通过校验后重新渲染。

禁止出现：

```text
LLM 独立生成 SVG
LLM 独立生成 FloorPlanIR
```

正确关系是：

```text
FloorPlanIR → SVG Renderer → SVG
SVG Interaction → FloorPlanPatch → FloorPlanIR
```

## 4. 平面阶段上下文

### 4.1 建立专用 FloorPlanIR Contract

新增一份版本化、短小的平面协议，内容只包括：

- FloorPlanIR Schema；
- X/Z 坐标系；
- 空间、墙、开口和跨层核心字段；
- 阶段输入输出边界；
- 稳定错误码；
- 可由程序检查的硬不变量。

它应该是平面节点的固定基础上下文。`BLUEPRINT-SPEC-MINIMAL.md` 只在 Blueprint 装配或最终生成阶段使用，不应完整注入空间分析和空间布局节点。

### 4.2 RAG 按阶段检索，而不是共享整包文本

推荐按阶段建立 QueryPlan：

| 阶段 | 固定上下文 | 检索内容 | 禁止注入 |
| --- | --- | --- | --- |
| Requirement / Program | RequirementSpec Schema | 建筑用途、容量、空间需求 | 完整 Blueprint JSON |
| Topology | FloorPlanIR 拓扑契约 | 邻接、分区、动线、采光和湿区原则 | 材质、屋顶构件配方 |
| Geometry | 几何不变量 | 特殊轮廓、无障碍和跨层规则 | 固定尺寸整栋模板 |
| Openings | 宿主与通行契约 | 洞口净距、可达性、楼梯电梯规则 | 与门窗无关的建筑配方 |
| Blueprint | WILD Schema | 组件能力和装配规则 | 通用建筑百科 |

不要为了节省一次检索，让三个阶段共享完全相同的 `floor_plan_rag_context`。可以缓存相同 QueryPlan 的结果，但不同阶段必须有不同 metadata filter 和内容预算。

### 4.3 RAG 失败必须显式进入状态

节点诊断至少保存：

```json
{
  "retrieval_status": "ok|empty|error|fallback",
  "query_plan": [],
  "hit_count": 0,
  "injected_chunk_ids": [],
  "base_context_id": "floor_plan_contract_v1",
  "base_context_chars": 0,
  "retrieved_chars": 0
}
```

存在 `injected_chunk_ids` 时，界面可以显示“已注入知识片段”；只有命中但未注入时显示“检索命中，未注入”。检索异常、正常空结果和使用基础契约分别显示。片段注入不等于模型采用，采用引用也不等于产物满足规则，需分别记录声明与校验证据。

### 4.4 平面知识只保存约束和方法，不保存默认整栋答案

平面 RAG 应优先保存：

- 空间关系规则；
- 适用条件；
- 设计目标；
- 可计算约束；
- 允许降级方式；
- 规则来源和版本。

完整的“10×8 米别墅 Blueprint”可以保留为测试 fixture 或示例，但不应作为普通平面查询的高优先级生成上下文。

## 5. 拓扑优先与有限几何求解

### 5.1 先生成空间程序和邻接图

大模型第一步只回答：

- 需要哪些空间；
- 各空间大致面积范围；
- 哪些必须相邻；
- 哪些必须远离；
- 公共、私密和服务分区；
- 主入口与核心交通关系；
- 哪些空间必须接触外墙。

例如：

```json
{
  "spaces": [
    {"id": "living", "area": [24, 32], "zone": "public", "exterior": true},
    {"id": "kitchen", "area": [8, 12], "zone": "service", "wet": true},
    {"id": "dining", "area": [10, 16], "zone": "public"}
  ],
  "relations": [
    {"a": "kitchen", "b": "dining", "type": "must_adjacent"},
    {"a": "living", "b": "main_entrance", "type": "reachable"}
  ]
}
```

这一阶段不要让模型给出所有精确坐标，但必须预留跨层交通核心与 void 的位置约束和面积，不能把楼梯/电梯全部留到洞口阶段。

先统一面积语义：明确空间多边形表示的分区面积与房间净使用面积、墙厚的关系；按每层轮廓并集扣除明确 void 得到待覆盖区域；交通核心作为有归属空间预留，不能重复扣除或重叠计入房间面积。通高空间在上层是否扣除，由跨层规则提前确定。

当前 Prompt 同时要求房间面积之和接近单层面积，又把竖向交通推迟处理，见 [`prompts.py`](../../../wild-server/app/agent/prompts.py)。这项阶段冲突应在替换几何生成方式前先解决。

### 5.2 程序生成可行几何候选

LayoutEngine 根据外轮廓、面积范围和邻接图生成有限候选。首期先做矩形单层，再验证带同位交通核心的双层住宅；使用直墙和普通门窗。矩形并集、L/U、中庭、退台与曲墙作为后续扩展，现有 IR 能表达不代表新求解器已经能生成。

记录候选数与求解时间上限。结果区分 `feasible`、`proven_infeasible`、`unsupported`、`budget_exhausted`；启发式搜索失败不能直接证明需求无解。

程序适合负责：

- 面积分配；
- 矩形切分和组合轮廓覆盖；
- 多边形相交与越界；
- 共享边提取；
- 内墙派生；
- 门洞可放置区间；
- 连通图计算；
- 跨层核心投影。

LLM 可以对合法候选做语义排序，例如选择动静分区更合理、主卧更安静或商业流线更清晰的方案。

### 5.3 体量和平面需要双向可行性循环

建议增加 `PlanFeasibilityReport`：

```json
{
  "status": "proven_infeasible",
  "reason_codes": ["program_area_exceeds_envelope"],
  "required_area": 148,
  "available_area": 120,
  "suggested_actions": [
    "increase_width",
    "increase_depth",
    "move_optional_space_to_level_2",
    "relax_soft_area"
  ]
}
```

路由规则应区分：

- 空间清单问题 → 回到 Program；
- 几何排布问题 → 重跑 LayoutEngine；
- 体量容量问题 → 回到 Architecture；
- 用户取舍问题 → 暂停询问用户。

只有面积下界超过可用面积等已证明冲突才能返回 `proven_infeasible`。面积口径必须相同，并明确核心/void 已计入。用户锁定的体量不能自动放宽；未锁定参数可在任务总预算内调整，需要改变已批准约束时重新审核。所有反馈循环共享任务总预算。

### 5.4 模型调用改成按需触发

不建议固定执行三个串行 LLM 调用。更简单的起点是：

```text
一次 LLM：RequirementSpec + SpaceProgram + AdjacencyGraph
  ↓
程序：布局候选 + 墙线 + 洞口候选 + 校验
  ↓
仅当存在语义取舍时，再调用 LLM 排序或定向修订
```

预期能减少模型处理精确几何的负担，但 Token、等待时间和有效率是否改善，应在相同需求集上验证；候选求解、排序和重试也要计入总成本。

## 6. 候选保留与局部修复

### 6.1 校验问题必须定位到实体和字段

统一返回：

```json
{
  "code": "incomplete_space_coverage",
  "severity": "error",
  "level": 2,
  "entity_ids": ["bedroom_2", "corridor_2"],
  "constraint_ids": ["coverage_level_2"],
  "observed": 68.4,
  "expected": 72.0,
  "repair_level": "deterministic_fix",
  "repair_scope": "layout_geometry",
  "repairable": true
}
```

### 6.2 候选修复只改目标范围

建议修复顺序：

1. 数值吸附、墙体重建、宿主修复等唯一解问题，由程序确定性修复；
2. 局部空间边界冲突，由 LayoutEngine 重新求解受影响区域；
3. 需要设计取舍时，让 LLM 返回 `FloorPlanPatch`；
4. 只有整份 IR 不可解析或需求本身冲突时，才停止并要求重新规划。

每次修复都在候选副本上执行，先检查是否越过允许范围、违反已批准硬约束或引入新严重错误，再复检并提交。存在依赖联动时明确影响范围，不能为了保持单个实体不动而破坏相邻空间。

P1 先复用现有吸附、宿主修复并保存未通过的原始候选；需要 LayoutEngine 的区域重求解在 P2 实现。保留失败候选不等于允许批准或交付。

### 6.3 fallback 只用于诊断，不作为设计答案

可以保留单空间轮廓或条带布局帮助用户理解失败位置，但必须满足：

- `source=diagnostic_fallback`；
- 不能确认；
- 不进入 Blueprint；
- 不计入成功率；
- UI 明确显示原模型方案被拒绝的具体问题；
- 系统保留原始候选供开发者审计，不将其覆盖丢失。

`deterministic_template` 如果作为产品功能存在，应改名为“基础户型模板模式”，由用户主动选择，而不是在模型失败后静默接管。

## 7. 用户编辑与版本控制

### 7.1 先定义 FloorPlanPatch

首期先支持 `move_shared_boundary`、`move_opening` 和 `lock_entity`。`resize_space`、拆分/合并、新增/删除洞口等作为后续操作目录，不要求同时实现：

```text
resize_space
move_shared_boundary
split_space
merge_spaces
move_opening
add_opening
remove_opening
change_space_type
lock_entity
```

示例：

```json
{
  "base_revision": 3,
  "operations": [
    {
      "op": "move_shared_boundary",
      "wall_id": "wall_kitchen_dining",
      "delta": [0.8, 0],
      "preserve": ["main_entrance", "stair_core"]
    }
  ]
}
```

Patch 必须具备 `base_revision` 前置条件，拒绝把旧版操作提交到新状态。移动共享边界可能联动相邻空间、墙和洞口，应计算并展示依赖影响范围；范围外实体及锁定实体保持不变。

任何已批准平面的修改都生成新 revision，使依赖的批准状态、装配结果和校验报告失效，完成新审核后才能交付新产物。

### 7.2 SVG 交互必须回写 IR

前端流程应为：

```text
选择 SVG 空间或墙体
  ↓
拖动 / 输入尺寸
  ↓
生成 FloorPlanPatch
  ↓
后端在候选副本应用
  ↓
ValidatorSet
  ├─ 通过 → 新 revision + 新 SVG
  └─ 失败 → 拒绝操作并显示具体原因
```

任何时候都不能只修改 SVG DOM 而不修改 FloorPlanIR。

### 7.3 自然语言修改也转换成同一种 Patch

用户输入“厨房向东扩大 0.8 米”时，LLM 只负责把语言转换成 `FloorPlanPatch`。程序负责应用、校验和重新渲染。

这样鼠标编辑和自然语言编辑共享同一条执行链，不会形成两套状态。

### 7.4 同步迁移确认门禁

当前 `is_confirmable_spatial_plan()` 允许 `model` 和 `deterministic_template`，新链 `_merge_into_floor_plan()` 还要求各阶段都是 `source=model` 才视为模型方案。因此接入程序求解器时，必须拆开来源、质量和审核状态，不能仅给新来源改名就视为有效。

正常程序求解结果通过适用的需求与几何校验后可以审核；诊断 fallback 仍不可确认。模板模式必须由用户明确选择。旧检查点和旧单体节点需要同一适配与迁移测试。

## 8. FloorPlanIR 到 Blueprint 的映射与验收

当前 `ApprovedPlanAssembler` 的方向应继续保留，但需要增加显式的映射报告：

```json
{
  "floor_plan_revision": 4,
  "mapping": [
    {
      "source": "wall_kitchen_dining",
      "targets": ["bp_wall_level1_08"],
      "status": "realized"
    },
    {
      "source": "door_kitchen_dining",
      "targets": ["bp_door_level1_03"],
      "status": "realized"
    }
  ],
  "unrealized": []
}
```

至少验证：

- 每个批准空间边界是否落实为墙或明确的开放边界；
- 每个批准门窗是否生成且宿主正确；
- 竖向交通是否覆盖批准楼层；
- Blueprint 是否擅自改变已锁定空间；
- SVG、FloorPlanIR 和 Blueprint 是否来自同一 revision。

## 9. 评测方案

### 9.1 建立需求集

不能只使用“生成一个别墅”。至少覆盖：

- 信息不足的默认请求；
- 带层数、面积和朝向的住宅；
- 有明确房间数量与邻接约束的住宅；
- 商业、办公、庭院和高层；
- L/U/退台和中庭轮廓；
- 用户连续两到三轮局部修改；
- 故意冲突或无法满足的需求。

### 9.2 核心指标

| 指标 | 说明 |
| --- | --- |
| Structured Output Valid Rate | 模型输出能否通过阶段 Schema |
| Model Plan Retention Rate | 模型需求/拓扑决策进入有效 FloorPlanIR 的比例；程序合法派生坐标不算信息损失 |
| Geometry Pass Rate | 覆盖、重叠、越界、宿主和连通性通过率 |
| Hard Constraint Satisfaction | 用户硬约束满足比例 |
| Revision Preservation Rate | 预先声明的依赖影响范围之外，实体与关系的保留比例 |
| Fallback Rate | 降级预览触发比例 |
| RAG Hit / Adoption Rate | 分开报告命中、注入、采用声明和产物验证；因果贡献另做对照 |
| Topology Diversity | 不同候选邻接图和分区结构的差异 |
| IR-to-Blueprint Fidelity | 已批准平面关系在 Blueprint 中的落实比例 |
| Cost and Latency | Token、模型调用次数和总耗时 |

### 9.3 对照组

至少比较：

1. 当前三次 LLM 坐标生成；
2. 去掉建筑类型完整模板，只保留 FloorPlan Contract；
3. Requirement + Topology 由 LLM 生成、Geometry 由程序求解；
4. 方案 3 加阶段化 RAG；
5. 方案 4 加局部 Patch 修订。

只有在同一需求集和同一模型配置上比较，才能判断知识库、Prompt、拆节点或几何求解谁真正有效。

## 10. 对齐统一实施阶段

本专题是[统一路线](../统一实施路线与验收.md)的近期主线，使用同一套阶段和基线：

| 全局阶段 | 平面专项任务 |
| --- | --- |
| P0 | 定位检索错误；记录基础上下文、召回与注入；保存原始/归一化/最终候选；建立 10～20 个需求基线 |
| P1 | 最小 RequirementSpec、版本化平面契约、面积/核心预留语义；保留有效信息；复用现有局部修复；明确来源与质量 |
| P2 | 有限拓扑与几何求解，逐步替代固定三次模型手算；增加受预算限制的可行性反馈 |
| P3 | 有限 Patch、SVG 编辑、批准失效传播、装配映射及跨视图一致性 |
| P4 | 在证据支持下扩展复杂轮廓、重建门禁和阶段化知识优化 |

完整编辑器和复杂布局求解器不作为首期目标。每个工作包先在声明支持范围内验证，再决定扩展；无效候选保留供诊断，仍受确认门禁约束。

## 12. 验收标准

完成改造后至少满足：

- SVG 和 Blueprint 均由同一个已批准 FloorPlanIR revision 驱动；
- 平面阶段不再完整注入 Blueprint 构件规范；
- RAG 零命中或异常能够在节点状态中直接看到；
- 用户硬约束拥有稳定 ID 和验收证据；
- 体量不可行时能够回到 Architecture，而不是在固定边界内反复重画；
- 单个几何问题不会让全部模型设计被 fallback 清空；
- 用户修改的依赖影响范围明确，范围之外的楼层、空间和关系保持稳定；
- 确定性模板不能冒充模型设计或计入成功率；
- 同一评测集重复运行并报告波动；与基线比较设计保留率、硬约束、可确认率和成本，失败与重试计入成本；
- 有效需求、不支持输入和冲突输入分组统计，不通过排除失败样本制造提升；
- Blueprint 可以追溯到批准平面中的空间、墙、门窗和交通核心。

## 13. 面试表达

> 我最初以为平面图效果差是因为模型不理解 SVG，或者知识库给了固定模板。审计后发现，SVG 实际由程序从 FloorPlanIR 绘制，并不是主要问题。真实 Trace 里 RAG 零命中，平面节点却反复注入 Blueprint 基础规范；模型用三次串行调用手算空间、坐标和洞口，最后一个覆盖错误又让整份设计退化成 fallback。这是单次请求证据，不能代表平均表现或证明 RAG 导致失败。我的方案是保留两阶段架构，把用户需求先变成 RequirementSpec，让模型先做空间程序和拓扑，确定性 LayoutEngine 再生成合法几何；修改统一转换成 FloorPlanPatch，校验通过后更新 IR 和 SVG，最终由同一 revision 驱动 Blueprint。目前完成的是问题定位和方案设计，有限求解、Patch 和跨阶段验收尚待实现；预期收益需要同条件实验验证。
