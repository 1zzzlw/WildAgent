# 阶段三：门、窗、栏杆构件实现总结

## 阶段目标

选择三种具有代表性的高级构件，验证组合构件编译层能覆盖墙体依附、洞口生成、重复子构件和沿路径布置等主要复用场景。

## 已实现构件

### 门 `door`

输入核心参数：

- `id`
- `parentWall`
- `from`
- `width`
- `height`
- 可选门框宽度、深度及门框/门扇材质

展开结果：

```text
door
├── opening
├── primitive.box：左门框
├── primitive.box：右门框
└── primitive.box：上门框
```

当前 opening 的覆盖面承担静态门扇视觉。开合动画和独立厚门扇留到后续行为系统处理。

### 窗 `window`

输入除父墙、位置和尺寸外，还支持：

- `verticalMullions`
- `horizontalMullions`
- `frameWidth`
- `frameDepth`
- `frameMaterial`
- `glassMaterial`

展开结果：

```text
window
├── opening：玻璃覆盖面与墙洞
├── primitive.box × 4：窗框
├── primitive.box × N：竖向窗棂
└── primitive.box × N：横向窗棂
```

### 栏杆 `railing`

输入一条至少包含两个世界坐标点的路径，并支持：

- 栏杆高度
- 立杆间距和半径
- 横杆半径
- 一个或多个横杆高度比例
- 材质

展开结果：

```text
railing
├── primitive.cylinder × N：等距立杆
└── beam × 路径段数 × 横杆层数
```

栏杆路径可以随楼梯或坡道升高，横杆会沿相邻路径点生成倾斜 beam。

## 公共墙体依附能力

新增直线墙局部坐标辅助模块，统一处理：

- 查找并验证 `parentWall`。
- 计算墙体长度、沿墙方向和法线方向。
- 将 opening 局部坐标转换成框体世界坐标。
- 计算侧墙所需的 Y 轴旋转。
- 检查门窗是否超出父墙的水平和垂直边界。
- 拒绝第一版尚不能可靠生成框体的曲线墙。

## 安全边界

- 窗棂数量限制为每个方向最多 32 根。
- 栏杆横杆最多 8 层。
- 单个栏杆最多生成 2000 根立杆。
- 零长度路径段、重复横杆高度、非法尺寸会在编译阶段失败。
- 不进行静默截断或猜测，避免蓝图看似成功但实际结构不符合输入。

## 确定性 ID

子元素 ID 由组件 ID 和角色稳定生成，例如：

```text
front_door__opening
front_door__frame_left
side_window__mullion_vertical_001
terrace_railing__post_001
terrace_railing__rail_001_001
```

相同输入会产生相同 ID 和相同元素顺序，便于日志定位、快照测试和后续迁移。

## 测试

新增命令：

```bash
npm run check:compiler
```

当前测试覆盖：

- 注册能力列表包含 `door/window/railing`。
- 三种构件的元素数量与元素类型。
- 侧墙窗框旋转方向。
- 编译前后源 Blueprint 完全一致。
- 编译结果不存在重复 ID。
- 缺失父墙时返回 `COMPONENT_COMPILE_FAILED`，且不产生残缺子元素。

测试结果：

```text
Component compiler check passed: door, window, railing.
```

## 阶段结果

三种代表性组件已经证明该编译架构可复用现有 Core 能力，不需要新增 `door`、`window` 或 `railing` renderer builder。下一阶段将把编译器接入前端重建、前后端 ScenePatch 和服务器保存流程。
