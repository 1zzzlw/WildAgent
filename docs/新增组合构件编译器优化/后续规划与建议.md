# 组合构件编译器最终后续规划

## 当前已完成基线

截至 2026-08-02，组合构件链路已经覆盖：

- 10 类语义组件：`door`、`window`、`railing`、`canopy`、`balcony`、`ramp`、`bay_window`、`cornice`、`chimney`、`light`；其中 `light` 已包含裸灯泡与台灯两种业务外观。
- 墙、楼板、路径和基础屋面的共享依附定位。
- 直线墙及单段圆弧墙门窗开口，强化后的 `profile_sweep`。
- 左键选择高亮、右键双窗扇独立开合、灯光三态调光、显式开关控制的三轴拖动、组件专用属性编辑。
- 编辑先停留在浏览器草稿，只有顶部“保存”成功后才用完整 Blueprint 覆盖服务端会话文件；本地“导出”不改变服务端版本。
- 新建会话只创建浏览器草稿，不再提前生成空 `.wild`；AI 完整生成后通过禁用缓存的文件读取触发并等待画布重建。
- 组件依赖缓存、重复网格实例化、Worker 重建、旧版 Blueprint 显式迁移。
- Schema、ScenePatch、知识库、11 个 RAG 用例和 12 个几何用例的同步回归。

职责边界继续保持：

```text
业务知识与生成规则 → 知识库、Recipe、Agent
语义组件参数展开   → wild-compiler
通用几何重建       → wild-core
显示、拾取与动画   → renderer、Vue 编辑器
```

后续新增建筑名词时，先判断能否由组合编译器复用现有几何，不能因为出现一个新构件名称就新增 renderer 分支。

## 后续 P1：稳定性观察与缺陷修复

当前不再预排第三批组件。先使用真实建筑样例观察十类组件，优先处理可稳定复现的保存、编译、选中、定位或渲染缺陷。

近期需要人工补验门窗、灯光和拖动交互：确认左键只选中高亮，右键只操作实际命中的窗扇/门扇/灯泡，并检查三轴拖动和相机控制没有事件冲突。

## 后续 P2：拖动自动吸附与空间校验

本轮只实现“用户显式开启后自由拖动并写回 Blueprint”。后续自动对准不应塞进鼠标事件，而应形成独立、可测试的放置服务：

1. 为组件定义锚点、允许依附的表面类型和局部朝向，而不是仅凭包围盒猜测。
2. 拖动过程中生成墙面、楼板、屋顶、网格和相邻锚点候选，并显示预览，不立即修改源 Blueprint。
3. 松开时按距离阈值、法向、边界、碰撞和最小间距排序候选；用户可按键临时关闭吸附。
4. 通过确定性校验节点输出“接受 / 拒绝 / 修正建议”，最终仍以单个 ScenePatch 写回，确保撤销重做可靠。
5. 增加门窗不越墙、灯具贴顶/贴墙、家具落地、构件不穿插等固定评测。

在这些规则明确前，不把当前自由拖动伪装成自动校验；墙挂组件仍受已有父墙范围约束。

## 后续 P2：Core 通用几何能力

以下能力仍然需要 Core 专项设计，不应在组合层用近似几何冒充：

1. 复杂屋面真实穿透：烟囱、天窗与多片屋面之间的稳定裁切和封边。
2. 可靠布尔/CSG：先定义容差、退化面、法线和性能验收，再决定库或算法；必须有多个组件共同需求才引入。
3. 更完整的曲线依附：复合曲线路径、椭圆墙或其他曲面上的精确开口，以及负向圆弧和跨曲段开口的统一约定。
4. 高级屋面定位：非平面/双坡/四坡屋面的精确局部坐标、法线和边界裁切。
5. 地形与建筑贴合：基础标高、坡地支承和地形裁切应进入独立地形系统。

`opening` 已经能够扩展门窗开口，但它只解决几何孔洞和填充面；碰撞、声音、锁、双扇联动等仍属于行为系统。

## 后续 P2：门窗高级行为

当前行为层完成了平开、推拉和右键切换。以下能力等待真实需求：

- 折叠、旋转门、多扇联动以及双扇同步开合；普通双窗扇目前已经可以分别开合。
- 碰撞检测、开合受阻、自动回弹。
- 锁定、声音、交互权限和可访问性操作。
- 是否持久化“当前打开状态”的产品决策；当前仅保存初始状态，运行时状态不回写 Blueprint。

这些能力应扩展统一行为协议，而不是复制 door/window renderer 分支。

## 后续 P2：资产与高细节家具（明确暂缓）

按当前决定，沙发、洁具、电器、雕塑等高细节家具暂不实现。未来启动时采用 GLB/GLTF 资产层：组合编译器只保存资产 ID、尺寸、锚点、变体和材质覆盖，模型本体进入独立资产目录或对象存储。

在资产层稳定前，不迁移或删除既有 `furniture`、`body`、`dense_brick`；也不把高细节对象继续拆成大量 primitive，以免放大文件、顶点数和维护成本。

## 后续 P3：有证据驱动的性能与工程化

本轮已经完成缓存、实例化、Worker 和迁移器。下一步只在基准数据证明需要时推进：

- 建立 100/500/1000 构件样例，记录重建耗时、FPS、draw call、顶点数和内存。
- 根据基准拆分当前生产包；现有构建仍提示主包超过 500 kB。
- 增加 Worker 任务取消、性能 trace 和异常回退统计。
- 把组件、Core、RAG 固定评测接入 CI，并在 Phase 6 增加浏览器 E2E。
- 为 Schema 迁移建立多版本 fixture，验证读取旧文件和重新保存后的稳定性。

不以“感觉场景可能会大”为理由继续增加缓存层或并发机制。

## 与 Phase 3 LangGraph 的关系

组合构件编译器不会被 LangGraph 替换。LangGraph 负责复杂任务拆分、节点级 RAG、生成/校验/修复循环以及前端流水线日志；编译器仍是 Blueprint 进入 Core 前的确定性转换步骤。

Phase 3 可以把组件规划、空间校验和 Core 重建诊断做成图节点，但不应把确定性几何展开重新交给大模型。RAG 命中片段和节点事件也在 Phase 3 统一通过按请求隔离的事件流传给前端。

## 第二阶段结束后的验收口径

当前自动回归未发现阻塞性缺陷，可以结束项目路线中的第二阶段并进入稳定观察。结束不等于声明没有任何 bug，而是指本阶段承诺的 Agent MVP、RAG 基线和组合构件闭环已有可重复验证结果。

若人工门窗右键验收发现事件冲突，或真实样例暴露稳定复现的组件偏移，应先作为第二阶段缺陷修复；其余 LangGraph 编排、资产系统、通用 CSG 和高级交互按本文进入后续阶段。
