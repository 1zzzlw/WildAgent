# 阶段二：组合构件编译器基础框架总结

## 阶段目标

建立一个独立于 Vue 页面和 Three.js renderer 的纯 TypeScript 编译层，为后续新增组合构件提供统一注册、展开和诊断能力。

## 新增模块

```text
wild-web/src/wild-compiler/
├── types.ts
├── componentRegistry.ts
└── index.ts
```

## 核心接口

单个组件编译器遵循统一接口：

```ts
(component, context) => GeometryElement[]
```

Blueprint 级入口为：

```ts
compileBlueprintComponents(blueprint)
```

返回值包含：

- 删除了 `geometry.components`、追加了展开元素的 Blueprint 副本。
- 组件级结构化诊断列表。

## 已实现的框架能力

1. **组件注册表**：按 `component.type` 查找对应编译器。
2. **纯数据编译**：编译器只处理 JSON 数据，不操作 DOM 或 Three.js。
3. **源数据不变**：存在组合构件时先深拷贝，再展开，避免重复重建污染源蓝图。
4. **确定性 ID 前置保护**：检测原生元素、组件和编译结果之间的 ID 冲突。
5. **局部失败隔离**：一个组件失败不会阻止其他合法组件和原生元素继续渲染。
6. **统一诊断**：失败使用 `COMPONENT_COMPILE_FAILED`，同时携带组件 ID、组件类型和可读消息。
7. **能力查询**：可以通过 `getComponentCapabilities()` 获取当前已注册的高级组件类型。

## WILD 类型扩展

在语言类型中新增：

```text
ComponentSpec
├── DoorComponent
├── WindowComponent
└── RailingComponent
```

并为 `geometry` 增加可选字段：

```json
{
  "geometry": {
    "elements": [],
    "components": []
  }
}
```

`components` 只是编译输入，不是 wild-core builder 列表的一部分。它不会导致 renderer 将 `door`、`window` 或 `railing` 当作新的基础元素。

## 兼容策略

- 不包含 `geometry.components` 的旧 Blueprint 原样进入 wild-core。
- 现有 `geometry.elements/templates/instances/placements` 行为不变。
- 本阶段没有删除、改名或替换任何现有 builder。
- 新字段是可选字段，旧 `.wild` 文件不需要迁移。

## 阶段结果

组合构件的公共编译框架已经建立。下一阶段将在该框架上注册门、窗和栏杆三个代表性组件，并通过确定性几何断言验证展开结果。
