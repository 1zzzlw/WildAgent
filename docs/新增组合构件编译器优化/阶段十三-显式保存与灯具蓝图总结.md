# 阶段十三：显式保存与灯具蓝图总结

## 本阶段目标

把编辑器中的“当前草稿”和服务端 `.wild` 文件明确分开，并让 Agent 可以直接生成一盏具有真实光源的台灯，而不是只能生成裸灯泡或普通静态家具。

## 已完成

1. 顶部“保存”改为显式服务端保存：校验当前 Blueprint 后，以 `PUT /api/scenes/{session_id}.wild` 覆盖对应会话文件；只有请求成功才清除 `dirty` 状态。
2. ScenePatch、组件库添加、属性编辑和拖动都只修改浏览器内当前草稿，不再自动覆盖服务端文件。刷新或下次打开时，读取的仍是最后一次成功保存的服务端版本。
3. “导出”保持为本地文件下载，不再冒充服务端保存，也不会清除未保存标记。
4. `light` 成为完整 Blueprint 业务组件，并拆分两个互不混淆的维度：
   - `fixtureType: bulb | table_lamp`：裸灯泡或完整台灯外观；
   - `lightType: point | spot`：点光源或聚光灯算法。
5. 台灯由组合构件编译器展开为灯泡、底座、灯杆和灯罩，灯泡节点仍承载真实 Three.js 光源、右键三态调光和拖动元数据。
6. 前端类型、JSON Schema、组件库、属性面板、后端 Blueprint 校验、空间工具、Agent 提示词和知识库规范已经同步。
7. Agent 规则明确区分真实灯具与旧版 `furniture.subtype: "lamp"`：用户要求台灯、发光或可开关时必须生成 `light`，旧家具占位不会产生光照。

## 数据与交互边界

- `table_lamp.position` 表示底座所在支承面的锚点；`bulb.position` 表示灯泡中心。
- 右键只改变本次运行中的关灯、弱光、强光状态；运行时亮度不持久化，`initiallyOn` 只定义重新打开文件时的初始状态。
- `draggable: true` 允许手动拖动并写回草稿；自动贴桌面、碰撞检测和空间合法性校验仍属于后续放置服务。
- 保存失败时保留当前草稿和未保存状态，用户可以修正后重试，不会误报已保存。

## 验收口径

1. 应用 ScenePatch 添加灯具后，不发生任何场景文件写请求，且文档保持 `dirty`。
2. 点击保存时只产生一次 `PUT`，请求体包含最新台灯组件；成功后才清除 `dirty`。
3. `fixtureType: table_lamp` 必须稳定编译出灯泡、底座、灯杆和灯罩四个子元素，灯泡包含真实光源。
4. 前后端 Schema 与 Agent 提示词都接受 `light`，大模型可以输出严格、可保存、可重建的台灯组件。

## 明确未实施

本阶段不增加自动保存，也不持久化灯光运行状态；不实现自动吸附、空间碰撞、高细节灯具资产和复杂阴影控制。这些能力继续按最终后续规划推进。
