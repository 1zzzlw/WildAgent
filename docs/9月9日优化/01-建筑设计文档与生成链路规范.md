# 建筑设计文档与生成链路规范

## 1. 目的

现有链路已经能够产生 `architecture_plan`，但方案、材质和骨架后的 `design_brief` 分散在多个普通字典中。用户只能批准执行步骤，不能在几何生成前审阅建筑本身。该设计容易产生三类问题：方案约束在节点间丢失、提示词中的硬要求没有执行证明、用户只能在 Blueprint 完成后逐构件返工。

本规范引入正式的 `DesignDocument v1`，使每次生成都具有稳定类型、版本、审核状态和来源追踪。

## 2. 权威数据分层

### 2.1 DesignDocument

DesignDocument 保存本次建筑已经明确的设计决策：

- 原始需求、建筑类型、能力 profile 和风格意图；
- 体量边界、楼层、结构网格、围护系统、立面 pattern、屋顶和交通策略；
- 构件配额、必要构件、能力缺口和设计理由；
- 用户硬约束、引擎约束、已锁字段和规则执行追踪；
- `schema_version`、`design_id`、`session_id`、`revision` 与审核状态。

DesignDocument 不保存每一面墙和门窗的最终 WILD 坐标。坐标属于解析或编译结果。

### 2.2 ResolvedDesign

ResolvedDesign 只能由程序根据 DesignDocument 生成，当前包含楼层标高、体量范围、抽象立面门窗槽位、构件预计数量、设计内容哈希和无法编译的能力警告。同一 revision 的 DesignDocument 必须产生相同的 ResolvedDesign 和 `design_hash`。

### 2.3 SVG

SVG 是 ResolvedDesign 的审阅视图，不是数据源。当前审阅图同时显示体量平面、主立面和侧立面。图形节点使用 `data-design-path` 关联 DesignDocument JSON Pointer，为点击选择和后续属性编辑保留稳定定位。

### 2.4 Blueprint

Blueprint 是最终交付产物。它必须来自已批准 DesignDocument，并在 `meta` 中携带：

```json
{
  "designSchemaVersion": "design/1.0",
  "designRevision": 3,
  "designHash": "sha256:..."
}
```

## 3. 状态机

```text
draft -> approved -> compiled
   ^                     |
   +---- any change -----+
```

当前实现中，总体方案和受控材质解析完成后进入 `draft`；用户批准时进入 `approved`；修改任何可编辑字段时 revision 加一、清除 `approved_at` 并返回 `draft`。Blueprint 保存成功后进入 `compiled`，其 revision 和 hash 与批准版本保持一致。

## 4. Patch 协议

设计阶段使用 `DesignPatch`：

```json
{
  "type": "design_patch",
  "patch_id": "patch_001",
  "base_revision": 2,
  "source": "user",
  "operations": [{
    "op": "replace",
    "path": "/decisions/massing/width",
    "value": 24
  }],
  "summary": "建筑总宽度调整为 24 米"
}
```

执行要求：

1. `base_revision` 必须等于服务端当前版本；
2. 只允许修改 `/requirements`、`/decisions`、`/constraints` 和 `/locks`；
3. 锁定路径及其子路径不能修改；
4. Patch 应用后重新执行完整 Pydantic 和语义校验；
5. 校验成功后原子保存 DesignDocument、ResolvedDesign 和 SVG；
6. 所有历史 revision 单独归档；
7. 设计审核中的自然语言意见由建筑方案节点生成下一版 DesignDocument，而不是直接改 Blueprint。

Blueprint 完成后仍使用现有 `ScenePatch`，处理移动某一构件、调材质或删除实体等成品级修改。

## 5. Schema 维护

后端 Pydantic 模型是唯一 Schema 来源。JSON Schema、REST 入参、LangGraph 状态和前端 TypeScript 类型必须服从同一字段语义。

系统型字段采用判别结构：

- `envelope.system == curtain_wall` 才启用幕墙参数；
- `roof.type` 决定可使用的屋顶参数；
- `circulation.vertical_strategy` 使用 `none`、`stair` 或 `core_and_stair`；多层建筑必须有楼梯，核心筒方案同时生成核心筒与楼梯；
- `representation_mode` 决定全部楼层建模还是示意表达；
- `materials.resolved_plan` 校验受控材质角色、材质 ID、资产引用和拒绝清单的顶层协议；
- 构件类型必须来自当前组件注册表。

禁止用一个自由 `dict` 收纳暂时不确定的领域字段。新增字段需要同时完成：Schema 版本判断、前端类型、Patch 路径、resolver/compiler、validator 和回归测试。

材质角色中的 `material` 参数与 `resolvedAssets` 资产清单是受其他 WILD/资产协议管理的嵌套载荷，因此在 DesignDocument 中保留映射容器；它们的顶层角色、材质 ID、资产 ID、拒绝清单和幕墙标志仍由本 Schema 严格校验，不能借此增加新的建筑设计字段。

Schema 文件由代码生成，不手工修改：

```powershell
wild-server/.venv/Scripts/python.exe wild-server/scripts/design/export_design_schema.py
wild-server/.venv/Scripts/python.exe wild-server/scripts/design/export_design_schema.py --check
```

## 6. 生成顺序

普通模式：

```text
classifier
-> architecture
-> material_plan
-> DesignDocument + ResolvedDesign + SVG
-> design_review interrupt
-> skeleton
-> components
-> merge
-> final_validate
-> Blueprint
```

计划模式先审核执行计划，再执行上述建筑设计审核。执行计划批准不等于建筑方案批准。

## 7. 持久化

```text
wild-server/storage/designs/
  {session_id}.design.json
  {session_id}.resolved.json
  {session_id}.svg
  history/{session_id}/revision_{n}.json
```

每个文件都使用同目录临时文件后原子替换。会话删除时同时删除当前设计、解析结果、预览和该会话的历史 revision。
