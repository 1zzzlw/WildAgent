# WILD 蓝图设计语言 · 单文档直接生成版

版本：1.4 · 输出的 WILD 统一为 `1.1`（与本文件版本号无关） · 核对日期：2026-10-23 · 目标产物：可以直接导入 WildAgent 的完整 `.wild` JSON。保留招牌label和真实光源lightSource，新增前端/Core多边形楼板孔洞及显式扫掠端盖。后端设计/校验链本次未修改，需要经旧后端处理时仍用矩形拆板与旧字段。

## 给使用者

将**本文件全文**作为附件或上下文交给大模型，再给出建筑需求即可。推荐这样提问：

> 按附件《WILD 蓝图设计语言 · 单文档直接生成版》生成一座【建筑类型】，风格为【风格】，包含【主要功能】。请自行设计体量、平面、标高、交通、立面和材料，按本文的构造方法完善可见细节，最终只输出一份完整的 WILD JSON，不输出生成脚本。

文件扩展名是 `.wild`，文件内容是 UTF-8 JSON。如果聊天平台不能创建文件，将模型输出的 JSON 保存为 `建筑名.wild`。本规范不要求 Agent、检索工具、项目源码、外部图片、单独设计文件或另一份规则文档。导入时仍由 WILD 引擎解析、编译和显示几何。

本文件包括：**交付工作流（第 0 节）**、输出约定、空间语义、字段字典、装配公式、不同建筑类型的设计方法、精细构造方法、三个局部构造样例、**本次实测的引擎边界（第 10.1 节）**、自检清单和一个完整建筑示例。**字段支持与空间含义以本文件的明确说明为准；示例中的建筑形式、坐标和配色不是其他建筑的默认模板。**

适用于现有几何能够表达的住宅、凉亭/廊架、多层办公楼、商铺、咖啡厅及小型公共建筑等概念模型。建筑类型决定设计，不把所有需求都套成别墅。语言文档负责表达规则与设计方法；实际质量还取决于生成模型的空间推导能力、完整输出容量和查看器表现。接近高细化作品需要同时完成主体、开口、构造收边、材料、使用空间和检查，不是追加一句“高质量”即可。

阅读顺序：先用第 0 节选定模式（单文件直出 / 工程化交付）并记住验收闸门；再掌握第 1～4 节的任务、尺度与设计事实；使用第 5～8 节查字段和计算；按第 9 节完善与本方案有关的细部；用第 10～11 节排错和自检。第 12 节只展示一栋完整文件如何闭合，第 13 节给出不同类型的提问方式。

## 0. 交付工作流：从一句需求到可验收的成品

第 1～13 节是**规则库**（怎么设计、字段什么含义）；本章是**用法**（按什么顺序做、每步留下什么证据、什么时候才算做完）。

只背规则不走流程，典型结果是"文件能导入，但立面无细节、楼梯接不上、报告没看就宣布通过"；只走流程不看规则，会在坐标语义和承托关系上反复返工。两者必须一起用。

本章的四栋实测来源：新中式别墅、欧式别墅、木构凉亭、六层写字楼（2026-10-22）。所有判据都在这些任务上真实跑过，不是设想。

### 0.1 两种模式，先选定再动手

| 模式 | 适用条件 | 产物 | 允许脚本 | 能达到的验收深度 |
|---|---|---|---|---|
| **A 单文件直出** | 手里只有本文件，没有项目仓库、Python/Node 或浏览器 | 一份完整 `.wild` JSON | 不允许：输出里不得夹带脚本、不得夹带省略 | 只能做第 11 节的文本自检。**不得声称"已校验""已渲染""已通过测试"** |
| **B 工程化交付** | 有项目仓库，能跑 Python、Node 与 Chromium | `.wild` + 设计说明 + 生成脚本 + 每轮快照 + 命令原始输出 + 校验报告 + 真实四视图 + 剖切副本 + 指纹清单 | 允许且推荐：确定性脚本只负责把设计展开成 JSON | Schema → 后端流水线 → 引擎编译/重建 → 真实 Chromium 渲染 → 看图修订 → 跨建筑同条件比较 → 重放 |

判定方法很直接：**能拿到仓库路径就是 B，只拿到这份文档文本就是 A。** 模式决定后不要混用纪律——不要拿 A 的做法冒充 B 的结论，也不要用 B 的记录负担压垮 A。

B 模式有一条容易被误解的约定：**脚本是展开手段，不是交付物**。正式产物永远是那份可以直接导入的 `.wild`，它在不运行任何脚本、不启动 Agent 的情况下就能打开。

### 0.2 九个阶段（B 模式执行顺序）

| 阶段 | 要完成的事 | 产物 | 通过判据 | 不通过时 |
|---|---|---|---|---|
| **S0 环境自检** | 确认解释器、Node、Chromium 路径可用；确认只写当日目录、不动源码 | — | 版本命令有返回；既有改动与你无关（**不擅自 git 提交/回退/暂存**） | 先修环境，不要带着坏环境产出"解释" |
| **S1 需求与设计** | 写清用户要求、执行方式、方案（场地／体量／各层标高／屋面／立面／室内／景观）、验收口径 | `01-需求与设计/设计说明.md` | 层数、主入口朝向、屋面形制、各层完成面标高、功能清单各能用一句话读出 | 需求矛盾才回问；缺省参数自行合理确定并写明 |
| **S2 展开** | 写确定性脚本：材料表 → 场地/基座 → 墙板 → 柱梁檩 → 门窗 → 细部 → 家具景观 → 写盘 + 快照 | 正式 `.wild`、`03-过程记录/构件分层.json`、`03-过程记录/rN/` | 摘要含 `sha256/bytes/elements/components/materials/layers`；同参数重跑得到同一 SHA | 少一层快照就等于没有过程，不许事后补造 |
| **S3 只读校验** | 跑 Schema + 后端流水线 + 引擎编译/重建三道闸 | `04-校验/rN项目校验.json`、引擎诊断 | `schema_errors` 空、`pipeline_error_steps` 空、编译/重建错误 0、未映射材质 0 | 逐条读报告原文，按 0.5 归因，不要先改判据 |
| **S4 真实渲染** | 同一套相机/灯光/尺寸出四视图 | `rN/效果图/*.png` + `render_manifest.json` | `meshCount > 0`、包围盒全为有限数、四张图各 > 2KB | 渲染失败先看 exit code 与 stderr（常见 134 = 环境变量缺失） |
| **S5 看图** | 逐张看，在图上**指认**体量、入口、屋面、开间、室内、交通 | 归因清单（问题 → 归属 → 证据） | 每个问题都落到"设计错／脚本错／引擎边界"之一 | 图上看不清就补剖切或去顶副本，不许写"应该没问题" |
| **S6 修订** | 只改作者脚本，产出 rN+1，全套重跑 | 新快照 + 新报告 | 修的是根因；没有靠删构件、降标高、改校验来"通过" | 旧稿与失败报告一律保留，不覆盖 |
| **S7 剖切复核** | 只删遮挡层，记录删除 ID 与来源 SHA | `06-剖切查看/<层>/` | 保留构件与正式文件逐项相等；剖切副本自己也过校验与渲染 | 宿主被移除时，依附组件必须同批移除 |
| **S8 交付核对** | 指纹、上下文、错误计数、图存在性、剖切一致性、重放 | 核对 JSON、重放摘要 | 见 0.6 与 0.7 | 任一项不符就回到对应阶段，不写"基本一致" |

S5 是四个阶段里最容易被跳过的一步，也是四栋建筑真正改进的来源：写字楼 r3 全图校验已通过，看图才发现楼梯前隔墙距洞口只有 0.2m，人转不过身——这类问题任何自动检查都不会报。

### 0.3 目录与文件命名（B 模式）

```text
docs/<日期>/
├── 00-公共脚本/                 只读验收、命令记录、剖切、指纹核对；不含任何建筑方案参数
├── 00-质量参考/                 参考建筑的同条件重渲染 + 对照说明
└── <序号>-<建筑名>/
    ├── <建筑名>-<类型>.wild      正式文件：直接导入用，不依赖脚本/Agent/RAG
    ├── 01-需求与设计/设计说明.md
    ├── 02-生成脚本/生成<建筑名>.py      带 --revision 参数
    ├── 03-过程记录/
    │   ├── 流程日志.md           可审计的操作、输入、输出、取舍（不记录模型内部推理）
    │   ├── 构件分层.json          id → 层（roof/roof_detail/wall_upper/furniture…），剖切依赖它
    │   ├── 命令记录/01-….json    原始 command/cwd/started_at/ended_at/exit_code/stdout/stderr
    │   ├── r1/ r2/ r3/           <名>.wild + 生成脚本.py + 生成摘要.json（失败轮另存效果图）
    │   └── 重放核验/
    ├── 04-校验/                  每轮项目校验.json；失败报告原样保留
    ├── 05-效果图/                front/side/top/perspective + render_manifest.json
    └── 06-剖切查看/<层>/          剖切.wild + 来源.json + 四视图
```

三条命名纪律：**正式文件放在建筑目录根部**（不开脚本也能打开）；**每轮一个 rN 目录**（脚本副本与 WILD 同放）；**命令编号连续、失败也占号**（失败记录不覆盖、不重排）。

### 0.4 精确命令（Windows，仓库根目录执行）

```text
# 1) 展开：作者脚本自带 --revision，同批写 WILD + rN 快照 + 生成摘要.json + 构件分层.json
wild-server\.venv\Scripts\python.exe docs\<日期>\<建筑目录>\02-生成脚本\生成<建筑名>.py --revision r1

# 2) Schema + 后端只读流水线（auto_fix=False；有 error 步骤时退出码 1）
wild-server\.venv\Scripts\python.exe docs\<日期>\00-公共脚本\校验蓝图.py <正式.wild> <建筑目录>\04-校验\r1项目校验.json

# 3) 引擎编译 + 网格重建（wild-core 层，和浏览器看到的是同一份源码）
node wild-web\scripts\validate-generated.mjs <正式.wild>

# 4) 真实 Chromium/WebGL 四视图 + render_manifest.json
node wild-web\scripts\render-baseline.mjs <正式.wild> <建筑目录>\03-过程记录\r1\效果图

# 5) 只删遮挡层的剖切副本（依赖 03-过程记录/构件分层.json）
wild-server\.venv\Scripts\python.exe docs\<日期>\00-公共脚本\制作剖切.py <正式.wild>

# 6) 交付核对：指纹、渲染上下文、错误计数、图存在性、剖切保留几何逐项一致
wild-server\.venv\Scripts\python.exe docs\<日期>\00-公共脚本\交付核对.py
```

每条命令都用记录器包一层，才留下原始输出：

```text
wild-server\.venv\Scripts\python.exe docs\<日期>\00-公共脚本\运行建筑任务.py <建筑目录> 01-r1生成 <上面那条命令及其参数>
```

它会把 `command / cwd / started_at / ended_at / exit_code / stdout / stderr` 全量写成 `03-过程记录/命令记录/01-r1生成.json`，同时仍把输出回显到终端。

环境上有四个已实测的坑，与设计无关但会直接卡死流程：

| 现象 | 原因 | 处置 |
|---|---|---|
| `ncrypto::CSPRNG` 初始化失败、子进程 exit 134 | Windows 下子进程未继承 `SystemRoot` / `WINDIR` | 记录器已在 env 中显式补这两个变量；自己写调用时同样要补 |
| 打印输出时 GBK 编码异常 | 控制台默认代码页容不下非 ASCII | 强制 `PYTHONIOENCODING=utf-8`，读写文件统一 `encoding='utf-8'` |
| `No such file or directory: 根目录/.venv/...` | 本项目没有根级 venv | 一律用 `wild-server\.venv\Scripts\python.exe` |
| 校验/渲染找不到模块或路径 | 命令必须在**仓库根**执行 | 脚本内部按 `parents[n]` 定位根目录，不依赖当前工作目录猜路径 |

### 0.5 修订循环：怎么读报告，怎么归因

每轮固定动作：改脚本 → 重出 `rN+1` → 重跑三道闸 → 重出四视图 → 再看图。**不要在一轮里同时改五个互不相干的问题**，否则无法判断哪一步修好了什么。

| 现象 | 归属 | 正确处置 |
|---|---|---|
| 门窗悬空/穿墙、楼梯接不上楼板、屋面盖不住墙 | 设计或坐标语义 | 回查第 3 节锚点语义与第 8 节装配公式，重算，不要平移修补 |
| 字段被 Schema 拒（字段名、枚举、类型） | 脚本错 | 查第 5～6 节字段字典；**不许改 schema、不许给校验器加豁免** |
| 编译/重建报"退化""零长度""两端重合" | 脚本错或引擎吸附 | 按 10.1 的边界处理：换 box、移动采样点、让梁跨整段 |
| 后端报屋面覆盖不足 | 先归因 | 真错就加承托/改坡面；引擎局限就保留误判并做同函数逐组复核 |
| 后端报共面、重叠、井道未识别 | 脚本错 | 留真实间隙、删重复板、用稳定语义前缀 + 真实井壁 |
| 图上看不出问题但空间可疑 | 证据不足 | 补剖切/去顶副本；不以"数值对"代替"动线通" |
| 审美不满意 | 设计问题 | 加构造层次（第 9 节），不是加数量、不是调亮曝光 |

四条硬红线，违反即视为本轮无效：

1. **不修改校验器、不关闭检查、不用 auto_fix 让报告变绿。**
2. **不删用户要求的构件（屋面、楼梯、门窗）来消除报错。**
3. **不放宽已经正确的几何（降低标高、缩短墙、缩小出檐）去迁就某个检查。**
4. **不把局部复核写成全图通过**：局部必须写清范围——哪几个承托组、哪个函数、哪几个接触点。

### 0.6 证据纪律：这份交付凭什么可信

- **三方指纹一致**：正式文件 SHA-256 = `render_manifest.inputSha256` = 校验报告 `sha256`。三者不一致说明你看的报告和出的图不是同一份文件。
- **跨建筑可比**：`render_manifest.contextSha256` 与 `sourceDigest` 必须与参考建筑相同，才谈得上"我和参考条件一致"。
- **失败留痕**：失败轮的效果图、stderr、报告原样保留；重排编号或覆盖旧稿等于销毁证据。
- **确定性重放**：同参数再跑一次作者脚本，SHA-256 不变。变了就是脚本里有时间戳、随机数、字典序或未固定精度的浮点。
- **看图要能指认**：写"我看了透视和首层俯视，能指认转向平台、会议室、露台门的位置"，而不是写"外观良好"。
- **零错误不等于好**：网格数、材质数、构件数都不是审美证明。全绿只证明对应的自动检查通过，不含结构、消防、无障碍与施工图审查。

### 0.7 完成判据（少一条都不算交付）

- [ ] 正式 `.wild` 在建筑目录根部，独立可导入；不含 `_` 前缀内部字段、`slot_id`、工具调用状态。
- [ ] Schema 零错误；后端流水线零 error 步骤；编译与重建零错误；未映射材质 0。
- [ ] 存在无法消除的引擎误判时：原始报告保留 + 同函数逐组复核 + 范围写明 + 不冒充全图通过。
- [ ] 四视图真实出图并逐张看过，图上能指认体量、入口、屋面、开间、室内与交通。
- [ ] 剖切/去顶副本保留构件与原件逐项相等，删除清单可查。
- [ ] 每轮脚本、WILD、摘要、命令原始输出、失败记录齐全且编号连续。
- [ ] 交付核对与确定性重放通过；指纹与渲染上下文一致。
- [ ] 明确写出本次没做哪些验证（结构、机电、消防、逐帧动画、交互专项等）。

### 0.9 模式 A 的等价要求

没有执行工具时，第 0.2 节的 S3～S8 全部不可用，取而代之的是：按第 4.3 节顺序推演 → 按第 11 节 A/B/C 三组逐项自检 → 只输出 JSON。此时必须在正文之外（或单独的说明段落）写清"这是文本自检结果，未经引擎校验与渲染"，不得出现"已通过""已渲染""已验证"等字样。第 11 节 D 组列出的四层验证，只有真正执行过的层级才能勾选。

## 1. 给生成模型的任务与输出约定

你的任务是根据用户需求设计建筑，并直接交付一个完整 WILD JSON 对象。

1. 先确定体量、楼层、屋面、房间与交通，再计算坐标与构件，最后输出 JSON。设计和计算在本轮完成，不要求用户先提供 DesignDocument。
2. 用户明确的层数、风格、功能、尺寸、朝向与禁用项优先。缺失的普通设计参数由你合理确定；只有彼此矛盾或影响核心需求的条件才需要询问。
3. 仅收到“生成一个别墅”时，可以自行选择两层、常规住宅尺度、可辨认的入口、基本功能分区、室内上下楼路径、完整屋面和适量庭院；按这些事实重新设计，不照抄第 12 节。
4. 运用建筑常识选择形态，使用下列字段表达形态。不要把“精致”“欧式”“花园”“真实玻璃”等文字当作几何或材质效果。
5. 默认最终回答只有一个完整 JSON 对象；不输出 Markdown 围栏、解释、检查报告、JavaScript、Python、占位符或省略号。用户明确要求讲解时，讲解与可复制的 JSON 分开。此条针对第 0.1 节的 A 模式；B 模式下脚本属于过程产物，最终交付物仍是那份 JSON 文件。
6. 所有数组必须展开、闭合。不能使用循环、变量、公式字符串、引用另一文件、`...更多窗户...` 或“其余同上”。能够写脚本不等于已经交付 WILD。
7. 默认生成自足的静态建筑：不依赖网络纹理、外部资源包、脚本、行为系统、模板实例或贴图下载；门窗交互和本规范内置灯具可按需使用。
8. 不能凭空发明 `type`、`shape`、属性或枚举。现实中需要“厨房”“水池”“斗拱”“格栅”“洗手台”时，用已支持的元素组合表达。
9. 不输出以下运行时/Agent 字段：以 `_` 开头的内部状态、`slot_id`、任务状态、工具调用、`geometry.rooms`、`DesignDocument`、网格顶点或 Shader 源码。
10. 输出前完成第 11 节的自检。有执行工具时可实际校验；没有工具时，只能做推导和文本自检，不能声称“已运行编译器”“已渲染”“已通过全部测试”。
11. “精致”“详细”默认要求可见的构造层次与完整空间关系；按第 9 节选择与本建筑相符的细节，不自动增加楼层、门窗、装饰柱、喷泉或其他用户未要求的大型设施。

### 1.1 一次输出的规模安排

先保证空间关系和完整性，再增加细节。优先用门窗、栏杆、家具等已有构件表达其实际用途；它们在显示时会展开为多个零件。不要设“必须超过某个构件数”的目标，也不要为了文件短把不同功能的对象错误合并成一个组件。

设计时先求一组开间、标高与细部的统一规律，再将重复对象展开为各自独立 ID 和数值。只展开最终会出现的构件，不在 JSON 中保存参数表或生成算法。预估输出容量时，要同时计入主体、组件、材料与重复装饰；**大场景中的细部数量由实际可见价值和完整输出容量共同决定**，不把“每层必须几十扇窗”“每坡必须几百块瓦”当质量指标。

预计输出容量不足时，依次减少重复瓦片、逐块铺砖、小五金、逐叶植物和不可见装饰，保留用户要求的层数、体量、入口、屋面、楼板开口、上下楼通路及主要材质。不能用删掉楼梯、门洞、屋面或用户指定功能来换取文件更短。

遇到需求确实超出一次完整输出的容量，应在开始交付前说明限制并商定规模；不要交付截断 JSON，也不要擅自退化成一栋更简单的建筑。

## 2. 文件结构与命名

这是文件结构示意，空数组不是一栋已完成建筑：

```json
{
  "meta": {
    "version": "1.1",
    "type": "building",
    "name": "根据本次需求命名",
    "style": "本次建筑风格"
  },
  "geometry": {
    "elements": [],
    "components": []
  },
  "materials": {},
  "editor": {
    "revision": 1
  }
}
```

- 当前项目接受 `meta.version="1.0"` 和 `"1.1"`。本规范统一输出 `"1.1"`，它与本文档的版本号无关。
- `elements` 存放墙、板、柱、梁、屋顶、楼梯、基础几何和家具；`components` 存放门、窗、栏杆等组合构件。两者处于同一坐标世界。
- `meta` 必填 `version/type/name`；可选 `author/style/seed`，其中 `seed` 是数字。`style` 是说明性标签，不会自动替你改变外形。
- 每个元素和组件都必须有全局唯一、非空的 `id`。推荐英文小写、数字、下划线，例如 `wall_l2_s`、`window_l2_s_01`。不要使用 `__`，给组件展开的内部 ID 留出命名空间。
- `parentWall` 必须准确引用一个实际的 `wall.id`；材质名必须引用 `materials` 中存在的键。大小写保持一致。
- 同一门窗只建一份：使用 `components.door/window` 时，不再给它叠一份 `opening`、玻璃板或实墙。
- 输出严格 JSON：双引号、无注释、无尾逗号、无 NaN/Infinity、无算式。数字直接写计算结果，通常保留 3～4 位小数即可。
- 修改已有文件时保持未改构件的 ID，`editor.revision` 加 1；扩大、移动或改变宿主后重新计算依附构件。

源组件ID是编辑对象，编译产生的开洞、框、玻璃等ID由引擎管理。parentWall/parentFloor/parentRoof分别表达附墙混合坐标、楼板顶面局部坐标、屋面局部坐标；宿主与附件一起移动不得重复加位移。attachment.parent和排布onSurface.parent也参与引用检查/级联删除。编辑分组不等于几何宿主，不额外复制parentId/children。

项目以极小文件表达精细建筑为核心约束，不引入GLB/GLTF模型资产，也不在JSON内嵌网格/base64。优先用参数化构件、轮廓/路径、材料复用和有设计价值的细部；未来紧凑装配、实例和运动须实现后再写入，不能自行省略必填字段或发明repeat/spin语法。

assets仍是PBR纹理集。多边形楼板自身可绘制，但parentFloor附件当前仅支持矩形/圆形；带附件楼板/屋顶整体旋转、原生曲墙opening直接拖动限制入口，不假装已经支持完整变换协议。

## 3. 坐标、标高与尺寸：必须统一的语义

### 3.1 世界坐标

单位是**米**，向量顺序是 `[X,Y,Z]`。Y 向上。本规范约定 X 向东、Z 向北，主立面默认朝南，即朝 −Z。这只是本次布局约定，可按用户要求旋转整栋建筑。

建筑可以从 `X=0,Z=0` 开始，也可以采用其他原点；生成过程中保持同一原点。尺寸为真实的米制值，不随意把高层建筑缩小并假称原尺度。

### 3.2 各对象的锚点不能混用

| 对象 | 输入位置的实际含义 | 顶底关系 |
|---|---|---|
| 矩形 `floor`，厚度大于 0.01 | `from.y` 是**板底**；from/to 的 Y 相同 | 顶 = 输入 Y + thickness |
| `wall` | X/Z 是水平墙轴线；from.y/to.y 是墙底/墙顶 | 不是一根斜放的杆 |
| `primitive.box` | `position` 是几何中心 | 底 = Y − 高/2，顶 = Y + 高/2 |
| `primitive.cylinder/sphere` | `position` 是几何中心 | 圆柱底 = Y − height/2 |
| `column` | `base` 是柱底中心 | 顶 = base.y + height |
| 直线 `beam` | from/to 是梁截面中心线的两个端点 | 水平矩形梁上下各延伸 height/2 |
| `furniture` | `position` 是家具的**底面中心** | 顶 = position.y + dimensions.height |
| `door/window/opening` | from = [沿父墙左边距, 底部世界 Y, 法向偏移] | 不能直接填世界 XYZ |
| 无 parentFloor 的 `railing` | path 是栏杆基线的世界坐标 | 扶手中心线 = 基线 Y + height |
| `canopy` | from[1] 是雨棚板的**中心**高度 | 底 = Y − thickness/2 |
| `balcony` | from[1] 是阳台板的**顶面**高度 | 底 = Y − slabThickness |
| `roof` | 随屋型变化 | 见第 5.4 节，不能共用一个“屋顶中心 Y”解释 |

矩形楼板、屋面采用明确的实体厚度，通常大于 0.01m，避免意外进入无厚度平面显示模式。需要圆形板时，首次生成优先用短圆柱表达，并按圆柱中心计算 Y。

### 3.3 楼层的连续尺寸链

先定义每层室内完成面标高 `F[i]`、层间板厚 `T[i]` 和层高 `H[i]`：

```text
F[i+1] = F[i] + H[i]
上层楼板底 = F[i+1] − T[i+1]
本层墙底 = F[i]
本层墙顶 = F[i+1] − T[i+1]
本层净高 = H[i] − T[i+1]
```

例如首层地面顶 0.30、层高 3.20、层间板厚 0.20：首层墙底 0.30、墙顶 3.30；二层板底 3.30、板顶 3.50；二层门底和家具底都是 3.50。不能把二层板底再当成二层室内完成面。

同一层间板同时承担下层顶板和上层地板，按一组实体表达。可以有独立且明确的薄饰面层，但不能重复铺两块同位置结构板。

### 3.4 常用尺度是设计参考，不是引擎限制

| 项目 | 概念设计的尺度起点，按用途调整 |
|---|---|
| 层高 | 住宅常从约 3.0～3.6m 起；办公/公共空间可从约 3.6～4.5m 起，另核对梁、板及吊顶净高 |
| 外墙/内墙厚 | 约 0.20～0.30m / 0.10～0.18m |
| 结构板厚 | 约 0.15～0.25m |
| 主门/室内门 | 宽约 1.0～1.8m / 0.8～1.0m，净高约 2.1～2.5m |
| 楼梯净宽 | 住宅可从约 1.0～1.3m 起；多人使用的公共交通按用途另留更充分宽度 |
| 楼梯步高/步深 | 约 0.15～0.18m / 0.25～0.30m |
| 走道/家具主要通道 | 小型室内可从约 0.9～1.2m 起，办公/公共主通道按人数与交汇另加宽；家具拉出和开门位置另外留量 |
| 楼梯层间/楼层平台 | 至少满足转向和出门，先按不小于梯宽预留，再检查墙面、栏杆和门扇后的实际净空 |
| 阳台栏杆 | 常取约 1.05～1.15m |
| 门窗框 | 宽约 0.04～0.09m；深度与宿主墙相配 |

这些数值用于视觉和空间初设，不表示已经通过当地法规、结构或施工审查。不得把“某一栋示例的首层必须 +0.45”之类选择提升为所有建筑的语言规则。

## 4. 直接生成时的设计方法

### 4.1 先建立一组统一事实

在输出 JSON 前，确定下表中的设计结果。它们是本次生成所用的事实，不要求用户填写，不增加新的 WILD 字段，也不要求输出另一份设计文件。

| 设计事实 | 至少明确的内容 | 随后受其约束的对象 |
|---|---|---|
| 用户需求 | 类型、用途、明确层数/尺寸、风格、必需空间、禁用项 | 全部设计，不得用细节替代缺失需求 |
| 体量 | 各层足迹、主次关系、入口朝向、退台/院落范围 | 墙、板、柱、屋面、场地 |
| 标高 | 各层完成面、板厚、墙顶、平台、檐口/屋脊 | 门底、窗台、家具、楼梯、灯具 |
| 功能与交通 | 房间邻接、实际门口、走道、梯井、平台、候梯位、露台入口 | 分隔墙、洞口、家具占地、栏杆断口 |
| 立面 | 开间轴线、窗台/窗头、虚实分组、转角、收边、遮阳 | 每面墙上的洞口和装饰，不只主立面 |
| 材料分工 | 主墙、基座、屋面、框架、玻璃、木作、软装的实际材料 | 已存在几何的 material 引用 |
| 细节与容量 | 哪些边缘需要表达、重复规律、可删减的微细部 | 最终展开量与视觉可读性 |

先画清主次和通路，再计算实体。发现楼梯或候梯空间放不下，应调整房间/体量；不能先塞满房间，再把楼梯当装饰摆到剩余缝隙。复制一层前先确认上层是否退台、功能是否改变、交通是否继续。

### 4.2 根据建筑用途选择空间组织

| 建筑类型 | 应先解决的设计问题 | 适合重点细化的部位 |
|---|---|---|
| 住宅/别墅 | 入口到起居、餐厨、卧室/卫浴、楼梯及室外空间的关系 | 门庭、洞口深度、檐口、露台、主要生活家具 |
| 凉亭/廊架/水榭 | 柱网、屋面承托、净高、台基高差、开敞入口与坐凳 | 柱础、梁枋节点、檐下木作、瓦作、栏杆/坐凳 |
| 多层办公楼 | 标准层开间、连续楼梯/电梯井、前平台/候梯空间、工位及会议/服务区 | 基座与入口、立面遮阳、层间边带、退台与设备屋面 |
| 商铺/咖啡厅 | 街面入口、展示/就座区、服务台、后勤及基本服务空间 | 橱窗、招牌承载面、雨棚、家具成组与内外过渡 |
| 小型展馆/公共建筑 | 人流入口、主要空间跨度、辅助区、采光、屋面与出入口 | 入口尺度、结构节奏、采光构件、材料交接 |
| 其他类型 | 根据实际用途重新建立空间与承托关系，先确认形态能否用本规范表达 | 选择该类型真正可见、可用的特征，不强加院落或坡顶 |

明确需要的设施要有实际空间；只写“含卫生间/茶水间/会议室”不算完成。范围为外观模型时仍要保持入口和体量可信；用户要求室内时，按用途提供必要功能与家具，不能所有建筑都放床和沙发。不要主动宣称概念空间满足具体法规。

### 4.3 按依赖关系展开

按以下顺序在本轮中完成设计，再输出一个 JSON：

1. **需求与形态**：明确建筑用途、层数、风格、主要屋型、主入口方向、用户要求的空间和附属设施。
2. **体量与标高**：确定足迹、各层占地、退台位置、楼板范围和所有完成面高度。L 形、院落、多翼建筑分别确定每个体量的真实屋面。
3. **平面与交通**：划定房间、走道、楼梯、平台和露台。确认从室外到主门、从主门到各层、从房间到露台都有连续通路。
4. **主体几何**：建立地坪/基础、墙、楼板及开口留空、楼梯、屋面。共享墙只建一次，开放空间不人为加实墙。
5. **洞口与依附**：根据实际宿主墙重新求门窗位置，添加栏杆、雨棚、凸窗等。门窗数量由房间采光、立面构图与真实墙段决定。
6. **可见细节与材料**：入口门套、窗洞收边、檐口、压顶、踢脚、遮阳、栏杆层次、花池、必要家具和灯具。
7. **交付核对**：先检查语法与引用，再查几何、交通和用户需求覆盖，最后输出完整 JSON。

精细程度来自形体层次、洞口深度、构造收边、材料分工和合理的空间关系。不能靠铺满窗户、复制大量柱子、堆叠装饰条或者写一长串功能名称来代替。

尺寸修改也按上述依赖传播：足迹变化 → 墙/板/屋面边界 → 门窗投影 → 收边/遮阳/栏杆 → 室内占地与动线。层高变化 → 板底/墙顶 → 门窗底顶/楼梯踏步/平台 → 灯具/电梯停靠。保留一处旧坐标可能让其余对象全部正确但建筑仍不可用。

## 5. 基础元素字段字典

以下 JSON 均为**局部格式例子**；引用的墙和材质需在完整文件中存在。字段表没有列出的字段，首次直接生成不要使用。

### 5.1 墙 wall

必填：`type/id/from/to/thickness`；可选：`material/curve`。from/to 是长度为 3 的数值数组，厚度为正数。

```json
{"type":"wall","id":"wall_l1_s","from":[0,0.3,0],"to":[10,3.3,0],"thickness":0.24,"material":"plaster"}
```

- 水平墙长 L = sqrt((to.x−from.x)²+(to.z−from.z)²)，忽略 Y 差；墙高 = to.y−from.y，应大于 0。
- 墙厚围绕轴线两侧展开。整栋建筑的物理外缘应额外计入半墙厚。
- 正交墙在真实交点共享端点。例如南墙的平面终点 [10,0] 与东墙起点 [10,0] 相同；不同层 Y 按各自墙底/顶填写。不要为了“补角”再叠一个相同墙段。
- 分层切墙，门窗挂到对应楼层的实际墙段；不能挂到想象中的整层对象。
- `curve` 可表达曲线，但首次独立生成以直线墙为主。可用单段圆弧 `{"type":"arc","center":[cx,0,cz],"sweep":90,"segments":24}`；sweep 是度数。带门窗的曲墙优先采用已经理解弧长定位的单段圆弧，不能把直线距离直接当弧长。
- 多段复杂曲线、椭圆和悬链线不属于本文的门窗稳妥通路，不能据“存在 curve 字段”推断所有宿主组合都可用。

### 5.2 楼板 floor：矩形、圆形和带孔多边形

必填：`type/id/from/thickness`；本文矩形写法同时要求 `to`；可选：`material`。from/to 的 X/Z 是对角点，Y 相同。

```json
{"type":"floor","id":"floor_l2_front","from":[-0.12,3.3,-0.12],"to":[10.12,3.3,2.6],"thickness":0.2,"material":"stone"}
```

示例板顶为 3.50。需要屋内地板、露台或平台时分别确定范围；范围相接的板片可以共享边，但不要重叠铺板。

**楼梯口和挑空可以使用多边形真实孔洞**，旧引擎/后端兼容写法仍见第8.2节拆板。圆形用shape="circle"、radius、segments，不填to；圆形和多边形的板顶同样为from.y+thickness。

多边形使用shape="polygon"、polygon外轮廓和可选holes；轮廓点均为相对from的局部[x,z]米制坐标，至少三个点。允许简单凹轮廓，禁止自交；孔必须完全在外轮廓内，不能相交、相切或嵌套。顺逆时针均可，不必重复首点。

```json
{"type":"floor","id":"slab_with_void","shape":"polygon","from":[0,3.3,0],"thickness":0.2,"polygon":[[0,0],[10,0],[10,8],[0,8]],"holes":[[[3,2],[6,2],[6,6],[3,6]]],"material":"stone"}
```

此例板顶3.5m，洞贯穿板厚并包含洞壁，不自动生成楼梯/护栏。饰面、地板、天花必须同步避孔；不能叠放完整板补盖洞口。voids/openingId仍不是楼板字段。

### 5.3 柱 column 与梁 beam

柱必填：`type/id/base/height/bottomRadius/topRadius/style`；可选：`material/flutes/entasis/inclination`。

- style = `modern/chinese_wooden/doric/ionic/corinthian`。
- base 是柱底中心；height、上下半径为正数；flutes 是非负整数。
- 柱式可提供预设细节，但不等于整栋建筑获得对应风格。需要特定柱头、柱础时应明确建出可见层次。
- 方柱优先使用 primitive.box，避免把圆柱 style 当成“方柱”开关。

梁必填：`type/id/from/to/crossSection/width/height`；可选：`material/curve`。crossSection = `rect/circular/i-beam`。

```json
[
  {"type":"column","id":"porch_column","base":[2,0.3,-1],"height":2.4,"bottomRadius":0.12,"topRadius":0.11,"style":"modern","material":"wood"},
  {"type":"column","id":"porch_column_e","base":[8,0.3,-1],"height":2.4,"bottomRadius":0.12,"topRadius":0.11,"style":"modern","material":"wood"},
  {"type":"beam","id":"porch_beam","from":[1.7,2.8,-1],"to":[8.3,2.8,-1],"crossSection":"rect","width":0.2,"height":0.2,"material":"wood"}
]
```

水平梁底 = 中心线 Y − height/2。上例两柱顶 2.70、梁底 2.70，通长梁挑过柱线，形成正确贴接。不要按“梁 from.y 是梁底”放置。

当前引擎会将 X/Z 靠近 column 中心的 beam 端点吸附到柱顶，这一步没有按端点原有 Y 区分装饰木条，且吸附的是梁中心线，不是梁底。当前水平距离阈值为该柱 bottomRadius+0.05m。需要精确上下皮接触时，可以像上例一样让真实通长梁挑过柱线，或使用等价 primitive.box；不要将正好在柱轴上的 beam 端点输入 Y 当作必然保留。低位木格、柱边斜撑等不应吸附的杆件用第 8.5 节的方法定位。这个实现边界不改变梁中心线的定义。

### 5.4 屋顶 roof

必填：`type/id/roofType/span/depth/height/thickness`；本规范另外要求显式填写 `position`；可选 `material/ridgeAxis` 及下表中的屋型参数。

- `span` 按**世界 X 方向**填写，`depth` 按**世界 Z 方向**填写；position 的 X/Z 是屋顶中心。flat/gable/hip 的主覆盖矩形直接使用 span×depth；dome 和 chinese_pagoda 的实际范围见下表。
- X 范围 = cx ± span/2，Z 范围 = cz ± depth/2。检查覆盖实际承托墙外皮及设计出檐。
- 每个独立体量单独定位。缺少 position 可能触发自动包围盒定位，直接生成不依赖该行为。
- `ridgeAxis` 只用于 gable，显式写 `x` 或 `z`。不填写时历史默认沿 Z；不要给 roof 发明 rotation 旋转屋脊。

| roofType | 当前表达与定位 | 生成注意 |
|---|---|---|
| flat | position.y 是板底；thickness 向上增厚；height 可写为 thickness | 最稳妥的平顶表达；底标高可等于顶层墙顶 |
| gable | position.y 是两侧檐口**外表面**标高；脊顶 = position.y + height；实体最低面 = position.y − max(thickness,0.02) | 当前原生形体是封闭楔体，不能将其内部当成可用阁楼 |
| hip | 矩形四坡；檐口外表面在 position.y；坡面向下增加厚度 | 长边方向形成正脊，正方形时收成顶点；ridgeAxis 不控制它 |
| dome | 以 min(span,depth)/2 为水平半径的穹顶 | 原生形体用于外观表达，不承诺可用的内壳厚度；不作为中式攒尖顶替代 |
| chinese_curved | 中部檐口外表面在 position.y；脊顶为 position.y+height；角部额外抬升 eaveCurveHeight；内表面向下移厚度 | 屋脊沿 Z；可选 curveProfile="gentle"/"steep"，省略时使用默认曲率。已实现曲面，复杂端墙闭合仍要核对 |
| chinese_pagoda | position.y 为首檐基准；第 k 檐基准是 position.y+k×tierHeight，k 从 0 起；可加 tiers/tierHeight/eaveOutset/shrinkFactor | span/depth 是基体尺度，首层实际檐口另向两侧外扩 eaveOutset；檐层不自动生成主体楼层或交通 |

- `tiers` 为正整数；`tierHeight/eaveOutset` 为米；`shrinkFactor` 是 0～1 的比例，通常选择大于 0、小于 1。这些不是增加主体层数的捷径。
- chinese_pagoda 第 k 檐的 X 覆盖宽 = span×shrinkFactor^k+2×eaveOutset，Z 覆盖深同理；设定 tierHeight 后，叠檐总抬升由 tiers×tierHeight 决定。该形体最高层仍可能留有顶部开口，要求封闭时应实际添加顶盖或收顶几何。
- 对 gable，若以整个楔体的最低面承托在墙顶 Yw，可取 position.y = Yw + thickness。例如墙顶 6.50、厚 0.18，则檐口外表面 6.68，height=1.80 时脊顶 8.48。
- 四坡或曲面屋顶下的室内封闭、檐下封口、复杂山墙不是一句“屋顶贴墙”可以保证的。必要时显式设置顶板、封口或附属实体，并检查剖面。
- 需要有真实内部净空的阁楼或特定山墙截面时，使用明确设计的斜板、封口与墙体组合；先计算上下皮与开口，不能把 gable 楔体挖空的设想写成不存在的字段。

坡面附属物的高度必须从实际坡面计算。以 dx=x−position.x、dz=z−position.z 表示相对位置，在覆盖范围内：

```text
flat 顶面 = position.y + thickness
gable 脊沿 Z：顶面 = position.y + height×(1−abs(dx)/(span/2))
gable 脊沿 X：顶面 = position.y + height×(1−abs(dz)/(depth/2))
hip：r=min(span,depth)/2
     顶面 = position.y + height×min((span/2−abs(dx))/r,(depth/2−abs(dz))/r)
```

上述坡面公式用于屋面范围内的附属位置；gable 是实心楔体，不将坡面减厚公式误认为内部净空。曲面和重檐不能套用平顶/双坡公式。

平顶例子：

```json
{"type":"roof","id":"roof_main","roofType":"flat","position":[5,6.5,5],"span":10.9,"depth":6.9,"height":0.18,"thickness":0.18,"material":"roof_dark"}
```

双坡例子：

```json
{"type":"roof","id":"roof_gable","roofType":"gable","ridgeAxis":"x","position":[5,6.68,5],"span":10.9,"depth":6.9,"height":1.8,"thickness":0.18,"material":"roof_dark"}
```

### 5.5 楼梯 stair

必填：`type/id/from/to/width`；直接生成时**同时显式填写** `stepCount/stepDepth/stepHeight`；可选 `material`。

```text
总升高 R = to.y − from.y > 0
水平行程 D = sqrt((to.x−from.x)²+(to.z−from.z)²) > 0
步数 N 为正整数
stepHeight = R / N
stepDepth = D / N
```

```json
{"type":"stair","id":"stair_main","from":[1.5,0.3,1.4],"to":[1.5,3.5,6.2],"width":1.2,"stepCount":20,"stepHeight":0.16,"stepDepth":0.24,"material":"stone"}
```

- from/to 的 X/Z 在楼梯**中心线**上，width 向中心线两侧展开；from.y 是起步前地面，to.y 是到达层完成面。
- 第 i 步（i 从 0 起）中心位于水平行程的 (i+0.5)/N；踏步顶 = from.y+(i+1)×stepHeight。
- 当 D=N×stepDepth 时，最后踏步的**远边**正好到达 to 的 X/Z，顶面到达 to.y。不要沿用“末步距终点少一踏步”的旧描述。
- 两跑楼梯写成两段 stair 和实际平台；第二跑从平台完成面起步，第一跑在平台边缘到达。
- 当前 stair 是逐级踏步几何，不自动生成完整梯板、楼梯间墙、楼板洞口、扶手或平台。需要这些内容时另外建出。
- 不能只提高 to.y 而保留旧 stepHeight/stepCount，也不能把 `stepCount=0` 当成有效的完整楼梯。

### 5.6 基础几何 primitive

共同字段：必填 `type="primitive"/id/shape`；可选 `position/rotation/scale/material`。本规范要求显式位置和所需尺寸，不依赖单位尺寸兜底。

| shape | 几何字段 | 含义 |
|---|---|---|
| box | dimensions=[宽,高,深] | 三项均为正数；按 X/Y/Z 排列 |
| sphere | radius；可选 segments/heightSegments | 半径为正数，位置在球心 |
| cylinder | height；radius 或 radiusBottom/radiusTop；可选 segments | 沿局部 Y；上下半径为正数，按中心放置 |
| profile_sweep | profile=[[u,v],...]，path=[[x,y,z],...]；closedProfile、caps | 截面沿路径扫掠；省略profile时可用radius、segments；不是任意多边形布尔运算 |

rotation 是 `[rx,ry,rz]` 欧拉角，**单位弧度**。常用值：90°≈1.570796、180°≈3.141593。scale 默认 [1,1,1]，直接生成优先通过实际尺寸控制形体。

```json
[
  {"type":"primitive","id":"planter_base","shape":"box","position":[-1.2,0.25,1.8],"dimensions":[0.8,0.5,2],"material":"stone"},
  {"type":"primitive","id":"tree_trunk","shape":"cylinder","position":[-1.2,1.3,1.8],"height":2.1,"radiusBottom":0.09,"radiusTop":0.06,"segments":16,"material":"wood"},
  {"type":"primitive","id":"tree_crown","shape":"sphere","position":[-1.2,2.6,1.8],"radius":0.8,"segments":16,"material":"leaf"}
]
```

profile_sweep 至少两个不重合的连续路径点；封闭截面至少 3 点，`closedProfile=true` 只是闭合**截面**，不自动把路径首尾连起来。重复截面终点不必要；重复路径的起点作为最后一点可表达闭环路线，但连续点不能相同。

水平直线路径的截面 v 通常向上，u 的横向随路径方向变化。例如路径朝 +Z 时 u 朝 +X，路径朝 +X 时 u 朝 −Z。旋转扫掠实体前，注意 position/rotation 作用于整个局部 path；不要把世界路径与第二次世界平移叠加。

**端盖必须显式要求**：默认caps=false，保持既有开放端面；closedProfile=true且caps=true时生成首尾端盖，支持简单凹截面，拒绝自交/退化截面。closedProfile=false不能要求caps。端盖不负责修复急转路径或大截面造成的自相交，也不代表已做实体布尔挖洞。需要走未更新的旧引擎/后端时继续使用旧字段。

#### 5.6.1 建筑招牌与中文文字

招牌使用 `primitive.box`，在 `label.text` 中直接保存建筑名称。文字绘制在盒子的**局部 +Z 正面**，随构件平移、旋转、缩放；通过 rotation 调整朝向。无需外部图片或字体文件，不要用大量小杆件拼字。

```json
{"type":"primitive","id":"entrance_sign","shape":"box","position":[4,2.8,0.16],"dimensions":[3.2,0.7,0.12],"material":"wood","label":{"text":"栖光别墅","color":[0.9,0.77,0.47],"fontFamily":"serif"}}
```

`label` 仅支持 box；text 为 1～256 字符，允许 `\n` 换行，自动按牌面适配字号。可选 color 为 RGB 0～1，fontFamily 为 `serif/sans-serif`。文字默认金色，背景保留盒子的材质。牌面要贴在入口墙面外侧，保持正面露出并避开门窗；不要把文字面埋进墙里。雨棚、挑檐和柱子也可能遮字，宜把招牌放在雨棚前缘，或保留完整的上下净空，并用街道视角复核。不同机器使用本地中文字体，字形可能略有差别。

#### 5.6.2 自制灯具的真实光源

任意 primitive 都可通过 `lightSource` 绑定真实点光源或聚光灯，灯杆、灯壳、灯罩继续使用普通几何，不受预设灯型限制。只给实际发光面添加 lightSource，避免每个零件都创建光源。

```json
{"type":"primitive","id":"garden_lamp_emitter","shape":"box","position":[2,1.4,3],"dimensions":[0.12,0.28,0.12],"material":"lamp_glass","lightSource":{"lightType":"point","color":[1,0.82,0.58],"intensity":25,"distance":8,"initiallyOn":true}}
```

可选字段：`lightType=point/spot`、color、intensity（非负，默认 25）、distance（米，默认 8）、angle（聚光锥角，0～90 度，不含 0）、initiallyOn（默认 true）、offset、direction。光源位于发光几何的包围盒中心；offset 是相对该中心的局部偏移，direction 是聚光方向的局部非零向量，默认 `[0,-1,0]`。位置与方向随构件旋转、移动。右键循环关闭、弱光、强光，强光为 intensity 的 3 倍。`emissive` 只让表面看起来亮，不能替代 lightSource；完整的多段灯具也可继续使用第 6.5 节的 light.body。

### 5.7 家具 furniture

必填：`type/id/subtype/position/dimensions`；可选 `rotation/style/material`。

- subtype = `table/chair/sofa/bookshelf/bed/wardrobe/nightstand/tv_cabinet/lamp/tile`。
- dimensions 是对象 `{"width":宽,"depth":深,"height":高}`，不是 box 使用的三元数组。
- position 是底面中心，rotation 是弧度三元数组。不要写旧式的标量角度。
- 椅子、沙发默认正面朝 +Z，靠背在 −Z。围桌、靠墙或面向电视时按实际方向旋转。
- `furniture.lamp` 是家具外形；需要实际发光及开关时，使用第 6.5 节的 light 组件。

```json
{"type":"furniture","id":"sofa_living","subtype":"sofa","position":[8,0.3,1.3],"rotation":[0,0,0],"dimensions":{"width":2.4,"depth":0.9,"height":0.85},"material":"fabric"}
```

### 5.8 原生 opening 的使用边界

字段：`type/id/parentWall/from/width/height/style`；可选 `depth/material`。style = `rectangular/arched/gothic/circular`。

它会切割宿主墙，并生成洞口覆盖面；不能把它当作“只挖一个透明空气洞”。通常使用 door/window 组件，保留 opening 给已经明确理解覆盖面、材料和宿主的特殊局部需求。普通通道宜用真实门组件或拆开墙段留通路。

## 6. 组合构件字段字典

### 6.1 门 door 与窗 window

共同必填：`type/id/parentWall/from/width/height`。

| 类型 | 可选字段 |
|---|---|
| door | frameWidth、frameDepth、leafDepth、frameMaterial、leafMaterial、openingStyle、doorStyle、leafRows、interaction、draggable |
| window | frameWidth、frameDepth、glassDepth、verticalMullions、horizontalMullions、mullionWidth、frameMaterial、glassMaterial、interaction、draggable |

- door.openingStyle = `rectangular/arched`；door.doorStyle = `single/double`；leafRows 为 1～8 的整数。
- window 的横/竖窗棂数量是 0～32 的整数。window 没有 openingStyle 或 doorStyle。
- frameWidth 对 door 可为 0，对 window 为正数。保留明确净空：2×frameWidth < width，窗还需 2×frameWidth < height。
- frameDepth 和叶片/玻璃厚度均为正数，leafDepth/glassDepth ≤ frameDepth；frameDepth ≤ 墙厚+0.12。普通外窗优先 frameDepth=墙厚，glassDepth≈0.008～0.012。
- 法向偏移通常写 0。不能把门窗移出墙体，再用一圈框“贴回去”。框和覆盖面必须与墙深度有交叠。
- 双开门使用一个 door 组件和 `doorStyle="double"`，不拼接两个分别带半圆拱的门来冒充一个完整拱顶。

可选交互：

```json
{"mode":"swing","hingeSide":"left","openAngle":85,"initiallyOpen":false}
```

interaction.mode 只有 `swing/slide/lift`；hingeSide 只有 `left/right`；openAngle 是度数（大于 0、至多 180）；openDistance 是正的米数；initiallyOpen 是布尔值。不要使用 `hinge`、`sliding`、`openPercent` 等自创键。

- 当前平开双门按两侧铰链开合；拱门的门扇遵循完整拱顶分割。
- 推拉窗沿双轨在窗洞净空内移动；升降窗上下分扇移动。窗扇的玻璃、窗框和窗棂一起运动，行程由净空约束。
- 推拉/升降窗要有足够框深，本文建议 frameDepth≥0.12 且 glassDepth≤frameDepth×0.42。
- 门的 lift 是刚性门板向上移动，受父墙顶部净空约束；leafRows 只改变外观分节，不会生成真实可卷折门帘。
- interaction 在 Schema/渲染输入中可选，但当前项目后端的门构件检查要求显式填写它。为兼容两条通路，本文默认给 door 写明 `{"mode":"swing","openAngle":85,"initiallyOpen":false}`，推拉门按实际设计改 mode；window 按需填写。静态初始画面保持关闭，查看器可提供开合交互，不需要额外 Agent。

### 6.2 栏杆 railing

必填：`type/id/path/height`；可选：`postSpacing/postRadius/railRadius/railLevels/material/infillType/infillThickness/infillTopRatio/infillMaterial/parentFloor/draggable`。

- 本规范优先**省略 parentFloor，path 直接使用世界坐标**。path 至少两点；闭环需把第一个点再写到最后。
- postSpacing、postRadius、railRadius 为正数；railLevels 为不重复的比例数组，每项在 (0,1]。
- infillType = `glass/panel`，设置后生成栏板；infillTopRatio 是 (0,1] 的比例，infillThickness 是正厚度。
- 路径布置在有板支承的位置，转角使用共享世界点；门口、楼梯上口、通道入口有意断开，不能沿整个洞口闭合封路。
- 如果指定 parentFloor，path 就变为相对楼板最小 X/Z 角点、**顶面**的局部坐标，Y=0 表示板顶；不要再填世界标高。

### 6.3 雨棚 canopy、阳台 balcony 与凸窗 bay_window

共同定位：`parentWall/from/width`，沿墙定位见第 8.1 节；外挑方向由实际外墙和建筑轮廓决定。常规外墙上使用，复杂内院或局部宿主需要精确控制时可改用明确的基础几何。

| type | 额外必填 | 可选 |
|---|---|---|
| canopy | depth、thickness | supportCount、supportSize、material、supportMaterial |
| balcony | depth、slabThickness | railingEnabled、railingHeight、postSpacing、material、railingMaterial |
| bay_window | height、projectionDepth | frameWidth、frameDepth、frameMaterial、glassMaterial |

以上每种都还要 `type/id`。

- canopy.from[1] 是棚板中心 Y；supportCount 为 0～16 的整数，0 表示不生成支柱。内置支柱底跟随父墙底，若台阶/独立门廊地坪不同，优先用单独的柱与板明确落点。
- balcony.from[1] 是板顶 Y；内置 U 形栏杆默认开启。另画完整栏杆时填 `railingEnabled=false`，避免重叠。
- balcony 会造阳台板和栏杆，**不造通往阳台的门**，需要另设与板顶一致的门洞。
- bay_window 是依附墙体并向外投出的凸窗；height 是洞口高，from[1] 是洞口底部世界 Y。没有 projectionDepth 的普通大窗应使用 window。

### 6.4 坡道 ramp、檐口 cornice 与烟囱 chimney

| type | 必填字段（含 type/id） | 可选 |
|---|---|---|
| ramp | from、to、width、thickness | railingSides、railingHeight、postSpacing、material、railingMaterial、parentFloor |
| cornice | path、profile | closedProfile、material、parentRoof |
| chimney | position、width、depth、height | wallThickness、capHeight、material、capMaterial、parentRoof |

- ramp.railingSides = `none/left/right/both`。省略 parentFloor 时 from/to 是坡面上边的世界中心线路径；厚度沿局部坡面下方展开，按上边标高与平台顶衔接，并核对端部截面。
- cornice.profile 是至少三点的二维截面；path 至少两点。沿路径扫掠，不能自动修复相交或复杂转角的实体关系。
- chimney.position 是烟囱底部中心，height 向上；放在坡顶上要计算该点的实际屋面高度，不能统一填檐口高度。
- 本规范建议省略 parentRoof，将 path/position 显式算成世界坐标。使用 parentRoof 时，X/Z 相对屋顶中心，Y 相对组件附着算法推算的屋面高度；该推算不能保证精确贴合复杂曲面、穹顶、重檐或所有四坡几何。需要精确落点时按实际坡面计算世界坐标，不能把这个字段当作自动贴面保证。
- 复杂新组件先组合本规范元素表达；不要自创 `dormer`、`arch`、`pool`、`pergola` 等 type。

### 6.5 灯具 light 与电梯 elevator

light 必填 `type/id/position`；可选：

`fixtureType/lightType/color/lowIntensity/highIntensity/distance/angle/initiallyOn/bulbRadius/baseHeight/height/shadeRadius/material/baseMaterial/shadeMaterial/body/draggable`。

- fixtureType = `bulb/table_lamp`；lightType = `point/spot`；color 为 [0～1,0～1,0～1]。
- intensity、distance 为正数，highIntensity 不小于 lowIntensity；聚光角 angle 是大于 0、至多 90 的度数。
- 位置是灯具的光源/预设锚点；吊灯要留出灯座到天花的空间，台灯要实际落到桌面。先用简单 bulb；自定义 body 由无 type/id 的 primitive 几何字段组成，仅一段标记 `interactive=true`。body 内 box/sphere/cylinder 的 position 是**世界坐标**，省略时继承灯具 position，不能填写相对灯具的偏移；profile_sweep 的 path 也用世界坐标，position 省略或置零。
- 颜色的 emissive 可让灯罩看起来亮；实际照明使用 light 组件，或给 primitive 的发光面添加第 5.6.2 节的 lightSource。不要添加自造的 light 字段，也不要仅凭发光材质猜测真实光源。

elevator 必填：

`type/id/position/dimensions/floorHeight/floorCount`；可选 `initialFloor/material/frameMaterial/draggable`。

- dimensions = `{"width":宽,"depth":深,"height":高}`。
- position 是初始停靠层轿厢地板中心；floorCount 为正整数，initialFloor 为 0 起的楼层索引且小于 floorCount；floorHeight 与真实层高一致。
- 停靠面 `F[k]=position.y+(k−initialFloor)×floorHeight`。层高不等的建筑不能直接用一个恒定 floorHeight 电梯冒充全部停靠；先调整方案或明确其表达范围。现有默认轿厢前方/按钮在 +Z 侧，厅门和候梯位要对应；没有任意 rotation 字段。
- 电梯组件不自动建井道墙、各层楼板开口、厅门和候梯空间。普通小别墅没有电梯需求时省略它，不以增加电梯代替设计楼梯。
- 当前原生轿厢是简化实体加导轨/按钮，不是带可步入内腔、联动层门的完整设备仿真。项目后端有按 `wall_core_` 前缀识别井壁的检查约定；实际井壁可按 `wall_core_l1_s` 等命名以便该检查识别，但名字本身不能证明井道、开口或净空已经存在。

## 7. 材质：自足的颜色与物理参数

`materials` 是“材质名 → 参数对象”的字典。每个材质都显式写以下五个字段：

```text
baseColor: [r,g,b]，每项 0～1，不是 0～255，也不是十六进制字符串
roughness: 0～1，低值更光滑
metallic: 0～1，普通墙、木、石、玻璃通常接近 0
albedo: 0～1，本规范通常写 1
lightingCondition: 固定 "D65_noon"
```

可使用的附加物理字段：

`materialClass` = `standard/glass/clearcoat/fabric`；`opacity/transmission/clearcoat/clearcoatRoughness/sheen` 为 0～1；`ior` 通常在 1～2.333；`thickness`、`attenuationDistance` 为米；`attenuationColor/sheenColor/emissive` 为 0～1 RGB；`emissiveIntensity` 非负；`side` = `front/double`。

新增无贴图表面参数：`surfacePattern:"quartz"`配合`surfaceFamily:"mineral"`表达石英石细粒和抛光高光；`surfacePattern:"planks"`配合`surfaceFamily:"wood"`表达错缝木板。它们位于材质顶层，不是procedural.type，也不携带图片。石英石用metallic=0、roughness约0.22～0.3、clearcoat约0.2；木板roughness约0.5。当前图案按世界米制投影，木板0.18×1.2米，未开放方向/尺寸；有真实贴图或砖procedural则走原专用通路。本轮未构建/渲染，待用户验证。玻璃材质槽应引用玻璃，不能用水或实心材料替代。

```json
{
  "plaster":{"baseColor":[0.86,0.84,0.79],"roughness":0.85,"metallic":0,"albedo":1,"lightingCondition":"D65_noon"},
  "stone":{"baseColor":[0.58,0.6,0.56],"roughness":0.78,"metallic":0,"albedo":1,"lightingCondition":"D65_noon"},
  "wood":{"baseColor":[0.36,0.2,0.1],"roughness":0.55,"metallic":0,"albedo":1,"lightingCondition":"D65_noon"},
  "metal":{"baseColor":[0.14,0.17,0.18],"roughness":0.35,"metallic":0.65,"albedo":1,"lightingCondition":"D65_noon"},
  "glass":{"baseColor":[0.78,0.9,0.94],"roughness":0.08,"metallic":0,"albedo":1,"lightingCondition":"D65_noon","materialClass":"glass","transmission":0.82,"ior":1.5,"thickness":0.012,"side":"double"},
  "water":{"baseColor":[0.12,0.38,0.34],"roughness":0.1,"metallic":0,"albedo":1,"lightingCondition":"D65_noon","materialClass":"glass","transmission":0.55,"ior":1.333,"thickness":0.04,"side":"double"}
}
```

- 建筑玻璃用 glass 与 transmission 表达透射，不靠很低的 opacity 假装通透。透射与 alpha 透明是不同通路，普通玻璃无需同时设置低 opacity。
- 水使用可识别的水材质及约 1.333 的折射率；水池由池底、四周池壁/压顶和水面分别表达。水面放在池壁内，不把整块实心水体盖到花园地面上。
- 动态水纹、阴影质量、天气、相机与全局光影是查看器的显示能力，不是在 WILD 内随意增加 `waterAnimation`、`sun`、`camera` 就会生效。
- 查看器固定启用动态水面，透明度倍率1、波纹强度0.65；均衡/精细档自动提供主水平水位的建筑场景反射，低档/自适应降档/其他水位使用环境反射，渲染面板不再提供水面开关/滑块。水先有真实池底、池壁和未被板盖住的开口，再用transmission、attenuationColor/attenuationDistance调透射吸收。水材质不宜高金属度或叠多层。
- 局部实时灯按画质/相机分配，流畅/均衡/精细上限为4/8/12，精细档最多两个重点灯投影；灯具发光外观保留。非重点灯不能保证遮墙，光源offset不能埋进独立实心灯罩。emissive仍不替代真实光源。
- 墙、楼板和box的平面纹理使用逐面米制UV，uvScale=[2,2]对应每米两次重复；球、圆柱等采用专用展开，需要单独看尺度。真实纹理资源按Schema提供，不伪造URL/hash，不用纹理掩盖缺失构造。
- 材料只影响分配给它的实体。给 meta 写“白墙灰瓦”，不会自动把既有墙或屋顶改色。
- 默认不引用远程贴图，不填空的 base64，不捏造文件路径。砖、木、石可先用颜色、粗糙度、真实分缝和必要基础几何表达。
- 可选的已实现程序化纹理只有 `procedural.type="brick"`；不要发明 procedural wood/marble/water 枚举。砖参数包括 brickSize=[砖宽,砖高]、mortarWidth、mortarDepth、bond=running/stack、seed、secondaryColor、colorVariation、roughnessVariation、edgeWear 及 weathering。
- brickSize、mortarWidth、mortarDepth 使用米；mortarWidth 应小于最小砖边长的一半，避免砂浆吞没砖面。seed 用非负整数；secondaryColor 用 RGB；colorVariation、roughnessVariation、edgeWear 使用 0～1 的量。weathering 是对象，可选 amount、scale、efflorescence、verticalStreaks、baseDampness；amount/efflorescence/verticalStreaks/baseDampness 为 0～1，scale 为正数。
- 材质 effects 可按需使用 weathering、moss、edgeWear、grain，但它们不能补出缺失的门洞、瓦片、檐口或构造形体。首次生成可以完全省略。

如果填写 effects，每一项必须有 type，并使用对应字段，不只写一个效果名称：

| type | 条目内的字段 |
|---|---|
| weathering | dustColor=[r,g,b]、dustOpacity、crackIntensity、colorFade |
| moss | mossColor=[r,g,b]、coverage、pattern="base_up"/"patchy"/"edge" |
| edgeWear | wearColor=[r,g,b]、intensity |
| grain | intensity、scale |

上表的 RGB 和覆盖/强度/褪色量用 0～1；grain.scale 使用正数。不要把 effects.weathering 与 procedural.brick.weathering 的两套字段混写。

## 8. 装配关系与计算方法

### 8.1 门窗的沿墙坐标与四面墙速查

父墙在水平面的端点为 A=(ax,az)、B=(bx,bz)，门窗宽为 w：

```text
L = sqrt((bx−ax)²+(bz−az)²)
u = [(bx−ax)/L, (bz−az)/L]
n = [−u.z, u.x]
s = from[0]
b = from[1]
o = from[2]

门窗底边中心 Cxz = A + u×(s+w/2) + n×o
门窗中心 Y = b + height/2
```

如果先设计好了门窗底边中心 C，则：

```text
s = dot(Cxz−A, u) − w/2
o = dot(Cxz−A, n)
```

必须满足：

- `0 ≤ s` 且 `s+w ≤ L`，实际还要给转角、门套和墙垛留出空间。
- `墙底 ≤ b` 且 `b+height ≤ 墙顶`。
- 同一墙段上的门窗区间不能无意重叠，也不能被另一堵重叠墙封住。
- 门底和通行楼面一致；窗底 = 该层完成面 + 设计窗台高。
- 这里的“左边距”是**沿父墙 from→to 的起点距离**，不是站在建筑外看过去的屏幕左边。

若四面外墙顺序为：南墙西→东、东墙南→北、北墙东→西、西墙北→南：

| 父墙 | 门窗底边中心世界 X/Z |
|---|---|
| 南墙，A=[x0,z0] | [x0+s+w/2, z0+o] |
| 东墙，A=[x1,z0] | [x1−o, z0+s+w/2] |
| 北墙，A=[x1,z1] | [x1−s−w/2, z1−o] |
| 西墙，A=[x0,z1] | [x0+o, z1−s−w/2] |

例：北墙从 [10,0.3,8] 到 [0,3.3,8]，希望窗中心 X=7、宽 1.4、窗底 Y=1.0，则 from=[2.3,1.0,0]，因为 10−2.3−0.7=7。不能把 X=7 直接放入 from[0]。

### 8.2 楼梯口与挑空的拆板

整块楼板水平范围是 [x0,x1]×[z0,z1]，要留出矩形洞 [a,b]×[c,d]。当洞在板内时，可拆成以下四片，舍弃零面积片：

```text
左片：[x0,a] × [z0,z1]
右片：[b,x1] × [z0,z1]
前片：[a,b] × [z0,c]
后片：[a,b] × [d,z1]
```

四片使用相同板底和厚度。下方梯段需要的上部净空必须落在洞中，不能只给最后一踏留孔。首次直接生成优先让洞覆盖梯段的完整平面投影及转向平台；当前项目后端也按整段投影检查。确实需要在低位梯段上方保留楼面时，必须独立计算整段净空，并识别该保守检查的边界，不能凭肉眼猜测。

对某踏步，若其上方仍有楼板，应计算“楼板底 − 该踏步顶”的净空；概念住宅布局通常至少按约 2m 以上检查，再按实际项目要求调整。洞边、栏杆、平台、门扇及横梁也要一起检查。

双跑楼梯须满足：

1. 第一跑顶面接半层平台顶，第二跑起步标高等于平台顶。
2. 平台实际覆盖两跑转向所需的范围，两跑侧向错开，不互相穿插。
3. 上层到达边接可行走楼板，不停在空气里。
4. 上口留通道，洞边栏杆不横封到达口。
5. 梯段不能穿过完整层间板、另一段楼梯、卧室实墙或屋面。

6. **楼层前平台必须能转向出门**。末步接到地板只证明标高相接；如果前隔墙距洞口仅 0.2m，人仍不能从另一跑走到门口。先为梯宽、转向、门扇留真实平面空间，必要时后移隔墙。小数值示例见第 9.7 节，不能把它的尺寸当所有建筑的规定。

多个不相交的矩形孔不能把“每个孔的四块板”直接叠加。可按所有孔的 X 边界将整板分条，在各条内扣除该条经过的孔的 Z 区间，再为剩余区间建板。若孔相交，先求其并集；不把交叠面积重复扣两次。

拆板完成后同时核对三件事：各板片之间无重复面积；所有孔内均无板；全部板片面积之和等于原板面积减去孔并集面积。地毯、铺砖、吊顶和上方的其他楼板也不能补盖梯井/电梯井。楼梯的整段通行宽度需要净空，不只检查中心线。

### 8.3 入口、露台与门廊

- 室外地面 → 台阶/坡道 → 平台 → 门底 → 室内地坪，应是一条连续的高程链。
- 平台宽度覆盖门扇及必要站立空间，平台前缘与台阶末步远边接合。
- 门前有 0.30m 高差时，可以用两级 0.15m 台阶；不能用深到地面的门板遮住缺失台阶。
- 雨棚下皮高于门头并留合理余量；例如门头 2.70，棚厚 0.12、棚板中心 2.82，则棚底 2.76。
- 独立门廊柱底落在平台顶，柱顶接梁/棚下皮；柱不能埋进可见台阶的踏面里或从棚顶冒出。
- 露台板顶与出入口门底一致。三面临空时沿三面布栏杆，墙侧和真实通行口留开。
- 顶层露台和上方屋面退让分别计算；不能让所谓“露台”藏在一堵没有门的外墙后。
- 沿**实际临空边界**逐段核对防护，包含退台两端短回折边，不只画最长的一条正面栏杆。检查栏杆起止位置、门扇开合与家具拉出空间。

### 8.4 接缝、穿插与支承

检查的是实际实体与功能关系：

- 支承件有落点，雨棚、阳台、楼梯平台、柱、梁与墙/板的关系明确。
- 排除无关实体的可见穿插，例如柜体穿窗、栏杆穿门、墙顶戳出坡屋面。
- 门窗框嵌入洞口、柱梁连接、结构墙转角和饰面背后固定可以有设计明确的局部搭接。**不能将两个包围盒相交一概判为非法。**
- 共面重复表面会闪烁。删除重复实体或安排真实层次，不依赖随机偏移掩盖问题。
- 饰面、压顶、踏步等可见边缘要有对齐关系；不同厚度的对象不应只因为中心坐标相同就被认定已贴接。
- 每个封闭使用空间有地面、围护和顶部覆盖；庭院、露台、挑空等开放处是有意留空。屋檐装饰条不能代替屋顶。

坡屋面采用多段承托时，逐段检查“柱顶 → 梁底/斗拱 → 短柱 → 檩条 → 实际坡面下皮”。hip 在覆盖范围内的下皮可按第 5.4 节顶面减 thickness 求出；内侧柱线上的屋面通常高于外檐面，不能拿外檐标高替代柱线接触标高。封闭房间还要有实际封口，开敞凉亭则不必补成实墙。

现有部分后端检查用单个屋顶基准和最近承托件推断支承，对多段木构链或复杂屋面可能误判。不能因此删承托件、改变已经正确的坡面或降低尺寸要求；有工具时保留原始诊断，按实际几何复算并看图。文本生成模式只按本规范求正确关系，不预先输出“已通过”。

### 8.5 按两个端点放置实体杆件

木格、斜撑、屋面压条、支架等需要一根明确方向的矩形实心杆时，可以用 primitive.box，避免梁柱自动吸附。下面是**计算公式，不是 JSON 字段**：

```text
端点 P、Q；d=Q−P；L=sqrt(dx²+dy²+dz²)>0
position=(P+Q)/2
dimensions=[杆宽,杆截面高,L]
ry=asin(dx/L)
rx=atan2(−dy,dz)；纯 X 方向时 rx=0
rotation=[rx,ry,0]
```

这里把 box 的局部 Z 当长度轴；width/height 对应截面。结果是数值弧度，不在 JSON 中保存 asin/atan2 字符串。改变两个端点后重新计算中心、长度和方向；不能只转中心却保持旧长度。竖杆也可直接用按世界 XYZ 填尺寸的 box。

### 8.6 立面开间与洞口收边

先确定一段可用墙长 L、两端留量 m、开间数 N。等开间时可取节距 p=(L−2m)/N，第 j 个开间中心距墙起点为 c=m+(j+0.5)×p，j 从 0 起。窗宽 w 必须小于 p，组件 from[0]=c−w/2。**N 由用途、墙长与构图决定，不由精细等级决定。**

窗台、窗头、楼层边带应分别成组对齐。遇到楼梯间、卫生间、转角或退台，按实际房间调整窗口与间距，不机械复制。留够窗套宽度、转角墙垛和真实结构空间；内隔墙不要无意终止在一整片玻璃中间。

窗/门组件负责洞口和框扇；额外收边负责洞口外圈，不再铺一块玻璃或实墙。设外墙的**实际外法向**为 e，饰面厚 d，墙厚 t，背面嵌入墙的安装深度为 δ，外侧收边中心可放在墙轴线 + e×(t/2+d/2−δ)，其中 0≤δ<d。δ=0 是刚好接触；适合的实体套边可明确嵌固约 0.01～0.02m，形成有意义的实体交接，而不是随机挪动薄面。e 要根据建筑内外判断，不能把沿墙坐标公式的 n 一概当外侧。部分表面检查不能区分隐藏背面接触与可见共面，仍需按真实外露面和安装关系判断。

左右收边沿墙方向分别放在开口左右边界外半个收边宽；过梁/窗台放在洞口上下边界外，并核对构件上下皮。窗台可以有明确出挑与滴水表达。圆拱形门的外套跟随其弧线或只做适合该门的直线周边，不能用跨过拱顶的实心条把洞口遮住。第 9.5 节给出一组实际数值。

### 8.7 家具、服务区与可走动空间

先确定使用组，再放对象：沙发—茶几—观看方向，餐桌—拉出后的椅子，办公桌—椅子—屏幕，茶台—坐凳—出入口。家具 dimensions 是占地参考，转动后占地随之改变。先保留门扇、通道、楼梯前平台与候梯空间，再配置家具，不以塞满房间为目标。

没有内置 subtype 的洗手盆、操作台、接待台、坐凳、显示器等，按用途组合 box/cylinder：柜体与台面有厚度区别，椅凳有落脚点，屏幕有支架，软垫在座面上。细节留在可见且有用的层面。禁止把通道里的实心方块标成“楼梯/电梯/服务空间”来替代真实功能。

## 9. 风格与精细程度：把要求转成可见几何

本节将“精细”落实为可以生成的几何。它提供可变的方法，不规定统一平面、层数、配色、构件配额。用户提供图片或详细条件时优先遵循用户。

### 9.1 先让整体成立，再分配细节

先明确一个主导意图，例如围合庭院、轻盈开敞的屋盖、有节奏的办公立面、入口与街面的连续界面。体量、开口和材料服务于这个意图；不是每栋建筑都需要退台、泳池、花房、牌坊或塔尖。

从远到近检查三层可读性：远看能辨认体量、屋型、入口与建筑用途；中距离有基座、墙/玻璃、开间与檐口的主次；近看能读出洞口进深、构件厚度、支承、压顶、窗台和材料交接。前两层未成立时，先调整比例与分组，再加瓦缝或把手。

### 9.2 风格通过形态和构造体现

| 用户风格 | 应体现在建筑上的主要决定 |
|---|---|
| 现代别墅 | 体量主次、进退与悬挑、成组大窗、墙面与玻璃比例、平顶/简洁坡顶、入口和露台层次 |
| 新中式别墅 | 院落或半围合、收敛的檐口与深灰屋面、白/浅色墙和木石分工、框景、格栅、门庭；不靠增加牌坊和柱子体现 |
| 欧式别墅 | 合理开间节奏、门廊/山花或坡顶层次、窗套与腰线、石材基座、克制的柱式；不是把所有窗都改成拱形 |
| 木屋/乡村住宅 | 坡屋顶与出檐、结构与围护尺度、门廊、木石材质对比、适合体量的窗洞 |
| 咖啡厅/小型公共建筑 | 清楚的公共入口、主要开敞空间、服务区与交通、室内外过渡、屋面完整覆盖 |
| 中式凉亭/廊架 | 开敞柱网、台基、梁枋与真实屋盖、檐下木作、合适的屋脊/瓦作、坐凳或栏杆；不把全部开口封成窗 |
| 现代办公楼 | 基座/入口与标准层区分、统一开间及层间边带、玻璃分格与遮阳、交通核心、退台或设备屋面的合理收束 |
| 地域/混合风格 | 选择能共存的屋型、尺度、构造与材料，保持转角、侧背面及室内一致；不同时堆入互不相关的风格符号 |

### 9.3 用构造层次组织细部

| 部位 | 可以实际建出的层次 | 必须同时成立的关系 |
|---|---|---|
| 基座/台基 | 主体、压顶、边缘铺石、入口踏步/坡道 | 同一高程链、板块不重复，踏面不埋柱 |
| 门窗 | 墙洞、框扇、内退深度、外套、窗台或遮阳 | 不封洞、不穿隔墙，窗头/窗台有成组对齐 |
| 立面 | 墙/玻璃分组、开间、层间边带、竖向遮阳、侧面收口 | 外缘对齐，转角完整，竖片有实际厚度和支承关系 |
| 平屋面 | 主体板、防水面表达、女儿墙、压顶、设备屏风 | 顶板与墙接合；收边不只前面一条；设备不悬空 |
| 坡屋面 | 实际坡面、檐口/封檐、瓦垄/分缝、脊与角脊 | 坡向和标高正确，压条不漂浮或穿顶；山墙/顶棚按需闭合 |
| 木构/棚架 | 柱础、柱、主梁、次梁/檩条、短撑、椽或遮阳条 | 构件首尾连通；不是把一块屋顶悬在低柱上 |
| 露台/廊道 | 实际楼板、饰面、防护、转角回折、入口 | 板顶/门底接合，通行口留空，所有临空短边都有处理 |
| 室内 | 功能分区、主要家具组、必要操作面/收纳/灯具 | 家具方向、占地和拉出空间不封通道 |
| 场地 | 到入口的铺地、少量花池/树、池岸及边界 | 有实际使用目的，不用巨幅空地或树冠掩盖建筑 |

常见细杆可先从约 0.03～0.10m 截面考虑，边缘压顶/窗台从约 0.04～0.15m 厚度考虑，再根据建筑尺度和画面可读性调整。这些只是几何起点，不是所有细部的固定尺寸或工程设计值。构件过密、过薄会增加成本并产生摩尔纹，过厚又会吞没洞口。

### 9.4 可变的细部构造方法

**铺地与基座**：先建整体支承，再按铺装尺度分块，留可读接缝。仅需要分缝时，不必逐个砖块都建实体；可使用已支持的砖材质或少量真实分隔条。结构板与上部饰面厚度分开，饰面底贴结构板顶，不能重叠两块同厚实板。

**门廊/格棚**：柱 → 主梁 → 次梁/木条依次求上下皮；木条间隔有节奏，端部挑出合理，门扇上方留净空。自足 WILD 不需要虚构 pergola 类型。多个支柱与雨棚组合时，逐根确认脚部落点。

**四坡瓦作**：屋顶先使用真实 hip。瓦垄沿各坡从檐口走到该坡与相邻坡的分界，不能将平行压条穿过另一坡。设半宽 hx、半深 hz；固定 x 的前/后坡瓦垄可从 z=±hz 走到 z=±max(0,hz−(hx−abs(x)))；固定 z 的左/右坡同理，从 x=±hx 走到 x=±max(0,hx−(hz−abs(z)))。各端点 Y 按第 5.4 节坡面加小量可见抬升计算。脊线沿长边，正方形顶点处不生成零长正脊；角脊按角点与正脊端点连接。圆截面压条可用 profile_sweep 的 radius/path，端头藏在檐/脊下；需要可见封口时用封闭原语收头。根据输出容量选稀疏但可辨的瓦作，不能把一整面屋顶只铺成水平格栅后称为瓦坡。

**中式曲面与装饰脊**：需要真实曲面时选 chinese_curved，并遵守其沿 Z 的脊向及当前形体边界；不能在平直 hip 角上加一根上翘杆，就宣称屋面本身具有飞檐曲率。脊饰的高度跟随实际屋面，不单独浮在屋顶上方。

**办公层与遮阳**：按层高和开间规律展开实际墙、板、门窗、家具与交通；上层复制时保留所有梯井/电梯井孔。竖片/横向遮阳与墙面保持明确接触或支架关系，既形成节奏也避免横挡门口。退台层另算足迹与防护，不继续复制已退掉的外墙和遮阳片。

**屋面设备与光伏**：先有实体支架/落脚点，再放设备或倾斜面板。格条、框边与面板使用同一个倾斜平面计算；不能只转面板而让附属格条仍浮在水平面。不要为视觉细部捏造电气、排水或能源仿真字段。

**材料交接与软装**：石台面压在柜体上，坐垫在座板上，金属框包住玻璃，木格固定在梁/边框内。不同材料的关系由不同实体或已有组件字段表达，不能只把一个物体命名为“石木金属组合”。先配主材、辅材、框架、玻璃与软装角色，再建立统一色彩与粗糙度，避免所有材料同亮度、同粗糙度或过强金属反射。

**景观、水与灯具**：花池包括外壳和土面，树干落入土面、树冠留出门窗视线；水池包括池底、边壁/压顶、水体且水面低于池岸。灯具有支架/灯体和合适亮度，不用大面积 emissive 照亮整栋模型。景观服从入口与建筑尺度，不将所有建筑都附带泳池或密林。

下面三个 JSON 是**局部构造片段**，合入本次 geometry 后须重新命名、定位并添加所引用材料，不是三份完整建筑。局部尺寸用于演示相互关系，不是类型模板；最终交付仍按第 2 节输出完整文件。

### 9.8 完成度、成本与参考图

屋面分缝或瓦片、栏杆立杆、格栅等选择可读尺度，避免密到闪烁。优先完善主立面和入口，同时让侧背面、屋面及室内交通真实成立。不要只做一个好看的正立面。

细部投入优先放在改变轮廓/阴影的构件、洞口边界、转角/收头和主要使用空间；远处看不出的重复小五金、密集树叶或每块不可见瓦片可省略。同类细部保持一致截面与规律，在入口、转角、屋脊等节点有明确收束。不要为了细化把已经正确的主体和功能删掉。

正常查看距离下，至少应能指认本方案的体量组织、入口/室外联系、屋面收束、立面开口与材料层次。具体细部按类型选，不要求每栋建筑都具备上表所有项目。模型没有渲染工具时仍按几何与尺度完成这些事实，不以“需要 Agent 才能做”作为默认前置条件。

有参考图时，只把图中可辨认的层数、比例、屋型、开口和材料转成约束；被遮挡的背面和室内自行完成一致的合理设计。不能声称图中看不到的结构已经被精确还原。

## 10. 易错写法与修正

| 容易生成的错误 | 正确处理 |
|---|---|
| 把 floor 的输入 Y 当完成面 | 板底 = 完成面 − thickness |
| 把 beam.from/to 当梁底 | 按中心线放置，再减 height/2 求梁底 |
| 装饰梁靠近柱后变形、两端重合 | 核对梁柱吸附边界；需固定坐标的杆件按第 8.5 节用 box 定位 |
| 把 furniture.position 当几何中心 | 家具底面放到地面；box 才按中心放置 |
| 门窗 from 填世界坐标 | 用沿父墙投影求 s，底部 Y 保持世界标高 |
| 北/西墙照抄南/东墙的 from | 按实际 from→to 方向重新计算 |
| 门窗只画玻璃或在实墙前贴框 | 用组件裁切真实宿主墙，不重建同位置墙 |
| “拱门”写成 window.openingStyle | 用 door 的 openingStyle="arched"，或明确的特殊几何 |
| flat/gable/hip 共用一个屋顶 Y 含义 | 按第 5.4 节分别计算上下皮与承托 |
| 调整 ridgeAxis 后交换 span/depth 的世界含义 | span 仍沿 X，depth 仍沿 Z；只改变 gable 的脊向 |
| 阁楼放进原生 gable 楔体 | 换成经过计算的坡板与封口组合，保留内部净空 |
| 只有楼梯，没有上层楼板洞 | 拆板，并核对整段头顶净空和上口落点 |
| 末步已贴地板就认定通路成立 | 检查前平台深度、转向、实际门口和门扇，不让隔墙贴着梯口 |
| 每个孔都各自拆四块完整大板 | 对多孔按不重叠区域拆分，核对孔并集与板面积 |
| 退台只画正面长栏杆 | 沿全部临空边检查，包含两端短回折，入口保留断口 |
| 用同一个恒定 floorHeight 服务不等层高 | 重新组织层高/电梯表达范围，逐层计算实际停靠面 |
| 自定义灯体 position 填相对偏移 | box/sphere/cylinder 的 body.position 是世界坐标；省略则继承组件位置 |
| 只写 room、void、staircase、garden 等自造 type | 用已支持元素实际组合，不输出无法识别的类型 |
| materials 中用 color="#ffffff" | 用 baseColor=[1,1,1]，同时补全五个基础字段 |
| “大理石/木纹”材质名被当作外观保证 | 配置颜色、粗糙度和需要的实体分缝；不捏造纹理能力 |
| 瓦垄、脊饰、光伏格条悬空 | 从实际坡面或同一倾斜平面计算附属位置与落脚点 |
| 所有类型都套住宅平面或同款场景 | 根据用途重建功能、交通、承托与立面；细部服务于本次设计 |
| 把全局天气、相机设置写进 meta | 使用正确几何和材质；显示效果由查看器控制 |
| 看到 schema 允许额外键就认为它会生效 | 只有已有消费者支持的字段才有可见作用 |
| 调大物体后附件仍用原坐标 | 重算洞口、檐口、栏杆、支柱、平台、楼梯和覆盖范围 |

### 10.1 本次实测的引擎边界（四栋建筑的真实报错）

上表是"容易写错的写法"，本表是"当前引擎实际怎么反应"。每一条都在 2026-10-22 的四栋建筑上真实触发过，出处见各建筑的 `03-过程记录/流程日志.md` 与 `命令记录/` 原始 JSON。写文件前扫一遍这张表，比事后读报错便宜得多。

| 现象 | 实际原因 | 处置 |
|---|---|---|
| Schema 直接拒绝柱，报字段未知 | `column` 用 `bottomRadius/topRadius`；`primitive.cylinder` 用 `radiusBottom/radiusTop`，细分字段是 `segments`。两个类型字段名不同 | 按类型查第 5.3 / 5.6 节，不要凭印象套 |
| 编译报梁"退化"、两端重合 | 梁端点吸附**只比较 XZ 平面**：低位斜撑、竖木格的两端 XZ 相同，会被拉到同一点 | 跨整段并挑过柱线的构件用原生 `beam`；需要精确三维方向的杆件改用旋转 `box`（第 8.5 节） |
| 灯跑到世界原点 | 自定义 `light.body[].position` 是**世界坐标**，只有省略时才继承组件位置 | 直接写世界坐标，不要填相对偏移 |
| `profile_sweep` 报零长度段 | 相邻路径点重合，最常见是端点正好取在四坡角点 | 采样点移进坡面内部留余量；短脊另用独立小段表达 |
| 屋面"未覆盖整栋"、差一米多 | 后端覆盖检查用"单个屋顶基准 + 最近承托件"推断，不识别多段木构链，也不按 hip 内侧接触标高判断 | 实测：外檐 +4.05 对柱顶 +3.56 报错，而实际檩条顶与屋面板底同为 +4.54（凉亭 6 个接触点复算通过）。保留误判，同函数逐组复核并写明范围 |
| 小体量坡屋面被要求覆盖主楼全宽 | `get_roof_support_bounds` 经 `_stepped_support_y` 判断承托时，把"被下层大轮廓包围的高层小墙"解释为退台，于是把老虎窗降到主楼墙顶 | 引擎局限：不改源码，保留原始失败报告，用同一个屋面检查器分别传入主屋面、花房、每个老虎窗的真实承托组，并附墙厚包络与标高差 |
| 电梯井"未识别"或识别到空井 | 井道围合依赖 ID 前缀 `wall_core_`（另有 `shaft_wall_`） | 用稳定语义前缀，**同时**建真实井壁、层门与逐层板孔；只改名不建几何等于用命名冒充功能 |
| 剖切副本校验报宿主不存在 | 剖切删掉了墙，依附其上的门窗/装饰仍指向原 `parentWall` | 剖切时宿主被移除，依附组件同批移除，并记入删除清单 |
| 后端报板件重叠/碰撞 | 一块标高铺了两块板：入口小平台与门廊地板、首层板各自重叠 | 台阶末步已接平台就删多余板；不动台阶与平台轮廓 |
| 共面告警、表面闪烁 | 构件端部与墙面正好同面 | 留真实间隙（本次为格栅端部），不要靠随机偏移掩盖 |
| 流水线第 2 项报门"缺少必填字段 interaction" | 门必须显式声明交互；字段是 `mode`，不是 `motion/enabled` | 补 `interaction: {mode, hingeSide, openAngle, initiallyOpen}` |
| 楼梯上端与上层板差 0.10m、屋顶基准高于墙顶、墙端超出侧墙 | 上层板没有延伸到实际梯段上端；屋顶 `position[1]` 没有取承托墙顶；墙长超出体量 | 按实际梯段顶、实际墙顶、实际体量重算；这三类都是"主体对、一处旧坐标"的典型 |
| **全图检查全绿，但动线不成立** | 写字楼 r3 楼梯前隔墙距洞口仅 0.2m，末步确实接到地板 | 前平台深度按梯宽留（r4 把隔墙退到 Z=0 得 1.5m）；自动检查不覆盖"转得过身"，只能看图 |

一句话总结这张表：**引擎只保证"它检查的那些关系"，不保证"你设计想表达的东西"。** 字段名、吸附规则、坐标语义、检查器的推断方式都要按实测核对，不能按"应该这样"假设。

## 11. 最终自检清单

最终只输出 JSON 前逐项核对，不必向用户输出你的推敲过程。工程化交付（第 0 节 B 模式）的完整交付判据见第 0.7 节，本节只是自检要点。

### A. 格式与引用

- 一个完整根对象，所有括号与引号闭合，没有注释、代码、公式、占位或尾逗号。
- meta 有合法 version/type/name；elements/components 是数组。
- 所有 ID 全局唯一，没有占用 "__" 命名空间；没有运行时或 Agent 字段。
- 每个 parentWall 都指向现有 wall；每个材质引用存在；需要 parentFloor/parentRoof 时有正确类型的宿主。
- 类型、枚举、必填字段和数值类型都符合本规范；材质五个基础字段齐全。
- 没有在 root/geometry/components 中塞入未支持的 rooms、voids、dormers、faces 或布尔挖孔配置。

### B. 几何与高程

- 每层完成面、板底、墙底/顶、门底、楼梯到达和屋面标高来自同一组事实。
- 尺寸为正，墙长不为零，路径连续点不重合，板片有正面积。
- 门窗沿墙范围、垂直范围和深度关系均在宿主内；同墙洞口不重叠。
- 各体量有实际屋面，覆盖范围含墙外皮及设计出檐；没有无意的屋面穿插和大缺口。
- 台阶/梯段的升高与踏步数量一致，水平行程与步深一致；近似小数没有形成可见累积误差。
- 楼梯口/挑空由真实板片留出，其他层或饰面没有再次封住洞口。
- 多孔板片互不重叠、孔内无板，总面积与扣除孔并集后的面积一致。
- 柱梁/短柱/檩条按实际上下皮连接，屋面附属物依据实际坡面；固定杆件没有被自动吸附改变。
- 电梯跨越的每层有真实井壁、板孔与候梯/层门位置，停靠面与各层完成面一致。
- 支柱、平台、栏杆和家具各有支承；没有重复共面实体及无关物体的可见穿模。

### C. 使用与外观

- 用户指定的层数、风格、主要空间、附属设施与禁用项都有实际表达。
- 从室外可到达入口，从入口可到达各层，房间和露台有真实出入口。
- 上层到达口、室内门、主走道没有被家具、栏杆或门扇封死。
- 到达后有足够前平台转向出门，转角和交汇空间不是只有一条相接的边。
- 露台、梯井等临空边及短回折均已处理；防护不横封真实出入口。
- 门窗比例、材料分工、入口、檐口和侧背面与整体建筑一致。
- 按用途配置功能与家具，房间名称有实际空间和可用通路，服务区不靠标签冒充。
- 已选择适合本方案的基座、洞口收边、屋面/檐口、材料交接和使用细节，远中近三个层次均可读。
- 精细度来自可见设计与关系；输出容量控制没有删掉必需的建筑系统。

### D. 有工具时的验证层次

1. **JSON/Schema**：验证语法、类型和字段，并检查引用、重复 ID。
2. **组件编译与几何重建**：检查编译错误、空几何、有限坐标、实际包围范围。
3. **空间核对**：复算板顶/墙顶/门底、门窗依附、实际屋面承托、板孔并集、整段楼梯净空和前平台、电梯停靠、露台防护。
4. **真实渲染**：查看正面、侧面、俯视和透视；多层建筑增加剖切；有交互要求时实际开合。

第一层通过不等于后面三层通过，零错误也不能证明画面精致。没有执行工具的模型仍能生成文件，但不能据文本自检承诺引擎或视觉结果。导入后的编译器诊断与实际画面可用于下一轮局部修订。

## 13. 如何提出需求与反馈

给模型的需求可以包含：建筑类型、风格、层数、占地尺寸、朝向、主要房间、是否需要室内细节、露台/庭院/泳池、精细程度以及可选参考图。不需要用户自己提供每面墙的坐标；未指定的普通设计参数由模型按用途确定。下面三种需求可以分别使用，不需同时生成。

通用提问：

> 仅依据附件规则，生成一个【建筑类型】。风格【可指定或由你设计】，包含【主要功能】，精细程度为详细。自行确定缺失的普通尺寸，先统一体量、标高、功能与交通，再按本建筑类型完善基座、洞口、屋面/檐口、材料交接和使用细节。保证完整性和合理通路，重复细部控制在完整输出容量内。最终只输出一份自足、展开完整的 WILD JSON，不输出脚本、占位内容或额外设计文件；没有实际执行工具时不要声称已经渲染或运行校验。

住宅示例：

> 根据本文件生成一栋三层欧式别墅，主立面朝南，入口有门廊，二层有可到达的露台，包含住宅基本功能、室内楼梯和主要家具。重新设计本次平面和立面，以体量、门窗收边、坡屋面和材料分工体现精细度；所有必要系统完整，只输出完整 WILD JSON。

开敞建筑示例：

> 根据本文件生成一个中式园林凉亭，大小由你合理设计。有可到达的石台基、开敞入口、坐凳和中央活动空间，体现真实柱梁承托、檐下木作、屋脊及可读瓦作。不要封成住宅，不需要卧室或成排窗户。最终只输出完整 WILD JSON。

多层办公示例：

> 根据本文件生成一栋五层现代写字楼，有清楚的入口、接待、办公、会议与基本服务空间，连续室内楼梯、电梯井及各层开口，顶层有可进入的露台。立面有开间节奏、材料层次和合适遮阳，检查楼梯前平台、候梯空间及退台边缘。以精细和完整为目标，不以门窗数量为目标；最终只输出完整 WILD JSON。

如果导入后发现缺陷，可以同时提供原文件与问题，例如：

> 二层露台门口被栏杆挡住；其余已确认的体量和立面保留。请在原文件中修正相关门洞、栏杆断口和板边关系，重新核对联动尺寸，返回完整修订 JSON。

修复时保留未受影响的设计，不把所有问题都归因于“模型还不够强”。先判断是字段写错、坐标混用、缺少实际几何、依附关系失配，还是引擎能力边界。语言规则能减少表达错误；复杂交通、复杂屋面、超长输出与视觉审美仍需要实际验证。
