# 生成失败记录排查

生成失败时先按 request_id 对齐会话记录、检索记录和检查点。校验失败的蓝图不会保存到 `storage/scenes`，因此该目录没有新 `.wild` 不代表中间数据不存在。

## 1. 查看会话中的步骤和诊断

文件位置：`wild-server/storage/sessions/<session_id>.json`。

- `messages` 保存用户消息和最后反馈。
- `turns` 按请求保存生成过程；先用 request_id 选中目标请求。
- `turns[].steps` 包含节点名称、状态、摘要、思考文本和 diagnostic。
- `turns[].validation_steps` 包含保存下来的校验步骤。

在项目根目录使用 PowerShell，例如：

```powershell
$sessionData = Get-Content -LiteralPath 'wild-server/storage/sessions/session_1788879630652.json' -Raw -Encoding UTF8 | ConvertFrom-Json
$requestTurn = $sessionData.turns | Where-Object request_id -eq 'req_1788922258743_zkvy9h23h'
$requestTurn.steps | Select-Object node, status, detail | Format-Table -Wrap
$requestTurn.steps | Where-Object node -in 'architecture', 'skeleton', 'door_gen', 'door_val', 'window_gen', 'window_val', 'merge' | Select-Object node, diagnostic | ConvertTo-Json -Depth 30
```

替换为实际 session_id 和 request_id。重点比较生成节点与校验节点的 fragment_count：生成过组件、校验后变成 0，与根本没有派发节点是两类原因。

## 2. 查看 RAG 和模型调用

文件位置：`wild-server/storage/sessions/rag_traces/<session_id>/<request_id>.json`。

检查 `retrievals` 的过滤条件与命中、`contexts` 的实际注入、`llm_calls` 的调用错误和 token，以及 `final_answer`。Trace 的 `status=completed` 可能只表示请求追踪已结束，不能单独证明蓝图生成成功；必须结合会话最终状态和校验结果。

## 3. 查看失败时的实际蓝图

SQLite 文件：`wild-server/storage/sessions/langgraph_checkpoints.sqlite3`。

`checkpoints` 表按 thread_id 保存状态快照。生成任务的 thread_id 通常为 `generation:<request_id>`，最新快照按 checkpoint_id 降序读取。checkpoint 是序列化二进制数据，不能当作普通 JSON 文本打开。排查时使用只读连接，禁止修改任务记录来绕过校验。

下面在 wild-server 目录执行，读取本地可信检查点中的常见状态字段：

```powershell
@'
import json
import sqlite3
import ormsgpack

request_id = 'req_1788922258743_zkvy9h23h'
with sqlite3.connect('file:storage/sessions/langgraph_checkpoints.sqlite3?mode=ro', uri=True) as connection:
    row = connection.execute(
        'SELECT type, checkpoint FROM checkpoints WHERE thread_id=? ORDER BY checkpoint_id DESC LIMIT 1',
        ('generation:' + request_id,),
    ).fetchone()
if row is None:
    raise SystemExit('未找到该请求的检查点')
if row[0] != 'msgpack':
    raise SystemExit('此检查点不是 msgpack，应按实际序列化类型读取')
state = ormsgpack.unpackb(row[1])['channel_values']
for key in ('architecture_plan', 'skeleton_diag', 'skeleton_blueprint', 'design_brief', 'component_diagnostics', 'merge_diag'):
    print(key)
    print(json.dumps(state.get(key), ensure_ascii=False, indent=2))
'@ | & .venv/Scripts/python.exe -X utf8 -
```

此示例适用于能直接解码的本地 msgpack 状态。若遇到带扩展对象的检查点，应使用项目自身的检查点读取接口，不要用不受控的反序列化方法加载外来文件。

## 4. 按首个错误定位

先看 architecture 是否引入未实现的构件要求，再看 skeleton 是否具有有效宿主和已批准的几何关系，随后比较组件生成与校验数量，最后检查合并和修复。

门窗配额缺失可能是无效墙体导致组件被拒绝，不能直接增加门窗重试次数。墙体水平长度由 XZ 端点计算，不能把楼层高度当作墙长。修复新增几何后必须重新检查结构质量，避免先通过的检查结果掩盖后续产生的重复结构。
