# 建筑生成计划模式与当前优化

> 文档分类：Agent 与建筑生成专题。返回 [正式文档入口](../README.md)。

最后核对：2026-08-28。

## 1. 这次优化解决了什么

原有 LangGraph 使用一条固定流水线。它适合保证建筑生成顺序，但用户只能在平面和风格阶段停下，无法在执行前知道 Agent 准备做什么，也无法在长时间执行中追加新意见。

现在新增了一层“可审核执行计划”：

```text
用户需求
  -> 意图分类
  -> 只读研究（需求 + 当前场景 + RAG）
  -> 总体建筑方案（只读）
  -> 生成 ExecutionPlan
  -> 白名单、依赖和门禁校验
  -> 用户批准 / 提出修改
  -> 白名单调度器逐步执行 Plan2Build
  -> 最终校验零错误后才保存和加载
```

这不是用自由 Agent 取代建筑流水线，而是把“计划与决策”放到安全执行器之前。

## 2. 动态部分和固定部分

计划模式不等于“模型可以任意选择 Python 函数”。

### 动态的内容

- 计划目标、版本、当前状态和执行详情；
- 基于用户需求、场景和 RAG 的研究上下文；
- 用户在批准前提出的修改意见；
- 执行期间排队的新意见；
- 节点边界上的有限重规划，每次都会生成新版本并重新请求批准；
- 每个步骤的 `pending / in_progress / completed / failed / skipped` 状态。

### 固定的安全边界

- 计划只能引用服务端注册的能力，不能填写函数名或任意节点；
- 新建筑必须包含平面设计、平面确认、主体装配、风格确认、装饰装配、合并和最终校验；
- 用户确认平面前禁止生成三维；
- 主体仍由 `ApprovedPlanAssembler` 按批准平面确定性装配；
- G1-G7 和最终 Blueprint 校验不能被计划跳过；
- `status=complete` 且最终错误数为 0 时才允许保存、加载和显示三维；
- 执行期间最多自动重规划 3 次，避免循环消耗模型额度。

## 3. ExecutionPlan 是什么

`ExecutionPlan` 是可持久化、可审核的公开计划，不是模型隐藏思维链。它包含：

- `plan_id` 和 `version`；
- `intent` 和 `goal`；
- 安全约束 `constraints`；
- 明确假设 `assumptions`；
- 步骤数组 `steps`；
- 计划校验结果 `validation_issues`。

每个步骤包含能力类型、依赖、验收条件、权限类型和执行状态。前端展示的“只读/可变更”来自服务端能力注册表，不接受模型伪造。

## 4. 当前能力白名单

| 能力 | 节点 | 权限 | 作用 |
|---|---|---|---|
| 需求与知识研究 | `planning_research` | 只读 | 读取需求、场景和 RAG |
| 总体建筑方案 | `architecture` | 只读 | 形成体量、层数、立面和屋顶意图 |
| 平面设计 | `floor_plan_design` | 只读 | 生成 FloorPlanIR 与 SVG 审核图 |
| 平面确认 | `floor_plan_review` | 人工门禁 | 未确认时禁止三维 |
| 材质方案 | `material_plan` | 只读 | 解析材质角色和受控 PBR 资产 |
| 主体装配 | `skeleton` | 可变更 | 确定性生成主体并执行 G1-G6 |
| 风格确认 | `style_review` | 人工门禁 | 确认受控风格包 |
| 装饰装配 | `decor_assembly` | 可变更 | 生成 Decor IR 并执行 G7 |
| 结果合并 | `merge` | 可变更 | 引用闭合、归一化和合并 |
| 最终校验 | `final_validate` | 只读 | 运行完整 Blueprint 校验 |
| 场景修改提案 | `patch` | 只读 | 生成仍需用户单独应用的 ScenePatch |

## 5. 用户操作方式

AI 对话面板新增“计划”开关，新用户默认开启。

1. 发送建筑生成或场景修改需求。
2. 查看计划目标、步骤、只读/可变更权限和安全约束。
3. 直接点击“批准计划并开始执行”，不需要先输入意见。
4. 如果计划不合适，在计划卡片或聊天输入框提交修改意见。
5. 执行期间仍可在聊天输入框发送新意见。系统会先排队，然后在下一节点边界重新规划，不会中途改写正在计算的节点。
6. 重规划后必须再次批准新版计划。
7. 平面和风格仍保留原有两次专项确认。

关闭“计划”开关后，项目仍可走原有固定 LangGraph 流水线，用于兼容和对比。

## 6. 持久化与断线恢复

- LangGraph checkpoint 继续写入 `wild-server/storage/sessions/langgraph_checkpoints.sqlite3`；
- 计划审核使用 LangGraph `interrupt`，与平面、风格审核使用相同的持久化暂停机制；
- `execution_plan_ready`、`execution_plan_review_required` 和 `execution_feedback_queued` 是持久化事件，重连时可补发；
- 运行中意见保存在同一 `GenerationJob` 的 payload 中，不会创建第二条并发生成任务；
- 服务端通过 `ContextVar` 绑定当前任务的意见轮询器，不把不可序列化函数写入 checkpoint。

## 7. 停止条件

这次没有通过无限提高 `recursion_limit` 解决循环问题。计划模式额外预留了 40 个合法图步数，同时依赖以下真正停止条件：

- 计划校验失败时立即终止；
- 节点失败后将计划步骤标记为 `failed`，调度器不再继续派发后续节点；
- 执行期间重规划最多 3 次；
- 平面工程预审自动修改最多 2 轮；
- 最终建筑修复仍按失败目标使用有限 callback 预算；
- 模型额度、鉴权等服务错误不进入建筑几何修复循环。

## 10. 当前边界

- 计划的建筑执行能力仍来自当前 Plan2Build，计划层不会凭空补齐引擎不支持的几何或构件。
- 现在的动态规划是“受控能力上的动态目标、状态和重规划”，不是通用代码终端。
- 运行中意见在节点边界生效，不强制取消已经发送给模型的单次请求。
- 重规划会从只读总体方案重新进入完整安全链，优先保证正确性和可恢复性，而不是尝试复用不确定的半成品。
