# 建筑生成计划模式与当前优化

> 文档分类：Agent 与建筑生成专题。返回 [正式文档入口](../README.md)。

最后核对：2026-08-29。

## 1. 这次优化解决了什么

原有 LangGraph 使用一条固定流水线。它适合保证建筑生成顺序，但用户只能在平面和风格阶段停下，无法在执行前知道 Agent 准备做什么，也无法在长时间执行中追加新意见。

现在计划模式升级为“任务动态规划 + 固定安全编译”：

```text
用户需求
  -> 意图分类
  -> 只读研究（需求 + 当前场景 + RAG）
  -> LLM 生成本次建筑专属任务与验收条件
  -> 编译为 ExecutionPlan，并校验阶段白名单、依赖和门禁
  -> 用户批准 / 提出修改
  -> 批准后才生成总体建筑方案
  -> 白名单调度器逐步执行 Plan2Build
  -> 最终校验零错误后才保存和加载
```

这次最重要的变化是：旧版计划在总体方案之后才出现，而且展示的主要是固定流水线；新版计划先于总体方案生成，计划内容会随“高层玻璃幕墙综合体”“中庭办公楼”“修改入口”等具体任务变化。它仍不会让模型任意调用代码，而是把模型提出的建筑任务编译到受控执行器。

## 2. 动态部分和固定部分

计划模式不等于“模型可以任意选择 Python 函数”。

### 动态的内容：`dynamic_tasks`

- 模型基于用户需求、当前场景和 RAG，生成 3～8 项生成任务或 1～4 项修改任务；
- 每项任务包含标题、建筑目标、映射阶段、依据和可检查的验收条件；
- 例如高层任务会强调电梯和疏散，玻璃幕墙任务会强调真实玻璃、框架和材质关系；
- 用户在批准前提出的修改意见；
- 执行期间排队的新意见；
- 节点边界上的有限重规划、版本差异摘要和再次批准；
- 动态任务会随对应执行阶段更新 `pending / in_progress / completed / failed / skipped` 状态，而不只是展示文案。

模型额度耗尽、超时或输出无法解析时，系统不会让部署和生成直接失败，而是使用按建筑语义生成的确定性回退计划，并在界面标记“语义回退计划”。回退计划仍然会区分高层、商业、玻璃幕墙等关键需求。

### 固定的安全边界

- 模型任务的 `phase` 只能映射到服务端允许的建筑阶段，不能填写函数名、工具名或任意节点；
- 新建筑必须包含平面设计、平面确认、主体装配、风格确认、装饰装配、合并和最终校验；
- 用户确认平面前禁止生成三维；
- 主体仍由 `ApprovedPlanAssembler` 按批准平面确定性装配；
- G1-G7 和最终 Blueprint 校验不能被计划跳过；
- `status=complete` 且最终错误数为 0 时才允许保存、加载和显示三维；
- 执行期间最多自动重规划 3 次，避免循环消耗模型额度。

## 3. ExecutionPlan 是什么

`ExecutionPlan` 是可持久化、可审核的公开计划，不是模型隐藏思维链。它分成两层：

1. `dynamic_tasks`：本次建筑真正要解决的问题，由模型规划并由服务端归一化；
2. `steps`：不可绕过的安全主流程，由服务端固定生成。

主要字段包括：

- `plan_id` 和 `version`；
- `intent` 和 `goal`；
- 安全约束 `constraints`；
- 明确假设 `assumptions`；
- 计划来源 `planner_source`（`llm` 或 `fallback`）和公开摘要 `planner_summary`；
- 本次建筑任务 `dynamic_tasks` 与版本变化 `change_summary`；
- 安全步骤数组 `steps`；
- 计划校验结果 `validation_issues`。

动态任务不携带后端节点名。服务端会清洗文本、限制数量、过滤未知阶段、重排为安全顺序并重新生成依赖；无效结果整体降级为确定性计划。安全步骤才包含能力类型、依赖和执行节点，前端把权限准确显示为“分析/审核”或“写入产物”。

## 4. 当前能力白名单

| 能力 | 节点 | 权限 | 作用 |
|---|---|---|---|
| 需求与知识研究 | `planning_research` | 分析/审核 | 读取需求、场景和 RAG |
| 总体建筑方案 | `architecture` | 分析/审核 | 形成体量、层数、立面和屋顶意图 |
| 平面设计 | `floor_plan_design` | 分析/审核 | 生成 FloorPlanIR 与 SVG 审核图 |
| 平面确认 | `floor_plan_review` | 人工门禁 | 未确认时禁止三维 |
| 材质方案 | `material_plan` | 分析/审核 | 解析材质角色和受控 PBR 资产 |
| 主体装配 | `skeleton` | 写入产物 | 确定性生成主体并执行 G1-G6 |
| 风格确认 | `style_review` | 人工门禁 | 确认受控风格包 |
| 装饰装配 | `decor_assembly` | 写入产物 | 生成 Decor IR 并执行 G7 |
| 结果合并 | `merge` | 写入产物 | 引用闭合、归一化和合并 |
| 最终校验 | `final_validate` | 分析/审核 | 运行完整 Blueprint 校验 |
| 场景修改提案 | `patch` | 分析/审核 | 生成仍需用户单独应用的 ScenePatch |

## 5. 用户操作方式

AI 对话面板新增“计划”开关，新用户默认开启。

1. 发送建筑生成或场景修改需求。
2. 先查看“本次建筑任务”，确认它是否真正理解建筑类型、功能、结构和材质重点。
3. 如需了解底层控制顺序，展开“系统安全主流程”；它不是模型的任务分析，而是不可绕过的执行保护。
4. 直接点击“批准计划并开始执行”，不需要先输入意见；批准之前不会生成总体方案或三维。
5. 如果计划不合适，在计划卡片或聊天输入框提交修改意见，并查看新版的变化摘要。
6. 执行期间仍可在聊天输入框发送新意见。系统会先排队，然后在下一节点边界重新规划，不会中途改写正在计算的节点。
7. 重规划后必须再次批准新版计划。
8. 平面和风格仍保留原有两次专项确认。

关闭“计划”开关后，项目仍可走原有固定 LangGraph 流水线，用于兼容和对比。

## 6. 持久化与断线恢复

- LangGraph checkpoint 继续写入 `wild-server/storage/sessions/langgraph_checkpoints.sqlite3`；
- 计划审核使用 LangGraph `interrupt`，与平面、风格审核使用相同的持久化暂停机制；
- `execution_plan_ready`、`execution_plan_review_required` 和 `execution_feedback_queued` 是持久化事件，重连时可补发；
- 运行中意见保存在同一 `GenerationJob` 的 payload 中，不会创建第二条并发生成任务；
- 服务端通过 `ContextVar` 绑定当前任务的意见轮询器，不把不可序列化函数写入 checkpoint。

## 7. 停止条件

这次没有通过无限提高 `recursion_limit` 解决循环问题。计划模式额外预留了 40 个合法图步数，同时依赖以下真正停止条件：

- 计划校验失败时立即终止；
- 节点失败后将计划步骤标记为 `failed`，调度器不再继续派发后续节点；
- 执行期间重规划最多 3 次；
- 平面工程预审自动修改最多 2 轮；
- 最终建筑修复仍按失败目标使用有限 callback 预算；
- 模型额度、鉴权等服务错误不进入建筑几何修复循环。

本次已完成：

- 执行计划纯逻辑测试：8 项通过（包含动态任务编译和未知阶段安全回退）；
- 本次 Python 文件 `py_compile`：通过；
- 前端 `vue-tsc -b`：通过（使用本机 Node 18 备用运行时）；
- `git diff --check`：通过。

当前主机环境仍存在与业务代码无关的运行器故障：Windows Python 在导入 `asyncio` 时报 `_overlapped / WinError 10106`；默认 Node 运行 Vite 时触发 `ncrypto::CSPRNG` 断言失败，而能运行类型检查的 Node 18 又低于 Vite 8 所需版本；当前虚拟环境也没有安装 Ruff。因此需要先修复或重启当前宿主环境，再运行完整异步持久化测试、Vite 产物构建和 Ruff。

## 10. 当前边界

- 计划的建筑执行能力仍来自当前 Plan2Build，计划层不会凭空补齐引擎不支持的几何或构件。
- 现在的动态规划是“建筑任务动态、执行边界固定”，不是通用代码终端，也不是 Claude Code 的完整文件探索和任意工具执行能力。
- 运行中意见在节点边界生效，不强制取消已经发送给模型的单次请求。
- 重规划会先回到动态计划审核；批准后从总体方案重新进入完整安全链，优先保证正确性和可恢复性，而不是尝试复用不确定的半成品。
