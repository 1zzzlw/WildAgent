# Plan2Build 建筑生成链路（当前实现）

> 文档分类：Agent / 建筑生成专题。返回 [正式文档入口](../README.md)。

第一次阅读建议先看 [建筑生成 Agent 当前设计思路（入门版）](BUILDING_GENERATION_DESIGN_GUIDE.md)。

最后核对：2026-08-27。

## 1. 一句话理解

当前新建筑生成不再是“让多个大模型节点分别猜墙、门、窗和屋顶”，而是：

```text
总体意图
  → FloorPlanIR v2
  → SVG 平面审核
  → 用户第一次确认
  → ApprovedPlanAssembler 确定性主体装配
  → G1-G6
  → 用户第二次确认风格
  → StylePackage → Decor IR → DecorAssembler
  → G7
  → 全量校验、保存 .wild、一次性加载三维
```

“确定性”表示：相同的已确认方案和风格包会得到相同坐标、相同 ID 和相同组合关系，不受大模型额度、随机性或并行返回顺序影响。

## 2. 用户实际会经历什么

1. 用户描述建筑需求。
2. `architecture` 规划层数、体量、立面轴网和屋顶意图。
3. `floor_plan_design` 生成 FloorPlanIR，并由 Python 检查空间、墙、门窗和流线。
4. 页面显示各楼层 SVG。此时没有生成、保存或加载任何中间三维。
5. 用户可以直接确认，也可以反复发送修改意见；修改只回到平面节点。
6. 确认平面后，主体装配器生成墙、板、楼梯、电梯井、门、窗和屋顶，并执行 G1-G6。
7. 页面按用户原始需求和已确认建筑方案推荐最多四种风格。用户可以直接确认，也可以提交风格意见重新推荐。
8. 确认风格后，程序生成 Decor IR，参数化装配屋顶外观、檐口、入口雨棚和受控柱列，并执行 G7。
9. 最终 Blueprint 仍需通过项目原有完整校验流水线；只有零错误结果才会保存并加载到画布。

两次确认解决的是两个不同问题：第一次确认“空间和建筑主体是否正确”，第二次确认“外观风格是否正确”。

## 3. 三份中间数据分别做什么

### FloorPlanIR v2

描述建筑平面事实：

- 每层空间和轮廓；
- 直墙、斜墙和曲墙；
- 门窗的宿主墙、偏移和连接空间；
- 中庭、庭院、挑空和竖井；
- 楼梯、电梯服务楼层；
- 可选工程预审规则。

工程预审发生在人工确认之前。缺少全层电梯井等可确定问题由程序直接修复并用同一规则复检；需要改变空间取舍的采光、流线或对称问题会由平面节点自动重画最多两轮。自动处理仍失败时才暂停等待用户决定，避免把机械重试工作交给用户，也避免无上限循环。

SVG 审核图和后续主体坐标都来自这一份数据，不能各画一套。

### 主体 Blueprint

`ApprovedPlanAssembler` 消费已确认 FloorPlanIR，输出可编译的 `.wild` 主体：

- `geometry.elements`：墙、楼板、楼梯、井道墙、屋顶；
- `geometry.components`：有真实 `parentWall` 和局部坐标的门窗，以及方案明确要求的阳台、栏杆和入口壁灯；
- `materials`：受控材质角色；
- `design_brief`：真实墙 ID 对应的门窗、阳台、栏杆和分段屋顶槽位。

L/U 形和中庭顶层不会再用一块外包矩形屋顶填平凹口。装配器按顶层实际占用区域生成互不重叠的屋面单元。

### Decor IR

Decor IR 不直接保存为 `.wild` 字段，它是风格装配的审计记录。当前操作只有四类：

| 操作 | 小白解释 | 当前用途 |
|---|---|---|
| `set_roof` | 修改已有屋顶的受控外观参数 | 平屋顶、四坡屋顶、中式曲面屋顶 |
| `sweep` | 让一个截面沿路径扫掠 | 檐口 |
| `anchor` | 把构件锚定到真实宿主 | 主入口雨棚 |
| `array` | 按稳定顺序放置一组同类构件 | 入口柱列 |
| `set_material` | 修改受控材质色板 | 墙面、屋顶、强调色 |

模型不能通过 Decor IR 自由写坐标或创建 Schema 不支持的构件。

## 4. G1-G7 分别检查什么

所有闸门使用统一的 `GateReport`：`gate`、`name`、`passed`、`issues` 和 `metrics`。问题包含稳定错误码、相关实体 ID、严重程度以及是否可确定性修复。

| 闸门 | 检查目标 | 典型阻断问题 |
|---|---|---|
| G1 | 平面方案契约 | FloorPlanIR 缺失、空间重叠、洞口越界、规则未通过 |
| G2 | 主体完整性 | 没有墙/楼板、缺少 ID、重复 ID |
| G3 | 洞口与宿主 | `parentWall` 不存在、门窗超出墙、批准槽位漏生成 |
| G4 | 竖向交通 | 多层建筑没有楼梯/电梯、相邻标高覆盖不完整、楼梯标高方向错误；示意高层同时识别显式楼梯和模板实例 |
| G5 | 屋顶承托与覆盖 | 缺屋顶、覆盖不足、屋顶与承托墙顶有缝 |
| G6 | 引用与材质语义闭环 | 父墙/父楼板/父屋顶或材质引用悬空；连续幕墙壳体不是物理玻璃、龙骨不是金属 |
| G7 | 风格与装饰闭环 | 风格屋顶未应用、装饰 ID 冲突、装饰引入新的 G5/G6 错误 |

G1-G6 失败不会进入风格确认；G7 失败不会进入保存。闸门不会调用大模型给自己“判通过”。

## 5. AI 与程序的职责边界

AI 适合：

- 理解自然语言；
- 提出总体方案和平面候选；
- 在有真实 PBR 资产时提出材质审美意图；
- 根据用户修改意见生成下一版 FloorPlanIR。

程序必须负责：

- 坐标、墙线、标高和楼板拆分；
- 门窗宿主、局部坐标和批准槽位全量落实；立面轴网先产生候选槽位，再按配额跨标高均匀采样，并优先保留平面内门和阳台入口，未入选候选不进入 G3；
- 屋顶承托、覆盖和 L/U/中庭分段；
- 风格包白名单和装饰参数范围；
- 所有闸门、引用检查、保存门禁和重复生成一致性。

因此，模型服务返回 403 或额度耗尽时，不会再导致门、窗、屋顶等多个组件节点集体失败。平面模型失败仍会进入可审核的确定性基础方案；材质模型失败使用受控回退材质。

对于 24 层这类示意高层，`floors` 表示建筑语义层数，`modeled_floors` 表示规划阶段的代表层数。主体装配会把代表层的 `volumes` 区间重新映射到完整语义楼层，所以“商业基座 1～2 代表层、塔楼 3～10 代表层”可恢复成连续的 6 层基座和 24 层塔楼，而不是一根通高矩形盒子。楼板和标准楼梯使用 `templates + instances` 表达，四角结构柱按不超过 45 米分段，避免超高单构件。

玻璃幕墙高层采用“连续玻璃 wall + 逐层横梃 + 分跨竖梃”。这些龙骨是轻量 `beam`，不需要在四面通高墙上切数百个 `window` 洞口；只有入口门、内部空间方案明确批准的窗和以后显式声明的可开启扇才切墙。这样既能看出完整楼层分格，也能避免旧版“灰色外壳加六圈蓝色窗带”和墙体几十万顶点的问题。通高无洞口墙在 Wild Core 中仍有 36000 顶点预算保护，作为旧文件和异常输入的最后防线。

材质规划按骨架的“材质角色”工作，而不是按元素类型统一刷材质：幕墙壳体虽然属于 `wall`，仍使用 `glass`；幕墙龙骨虽然属于 `beam`，仍使用 `metal`；核心筒墙使用 `concrete`。其中 `glass` 必须是 `materialClass=glass`、`transmission>0`、有效 `ior` 的物理玻璃，不能用低 `opacity` 冒充。G6 会检查“材质是否真的被正确构件使用”，不再只检查材质 ID 是否存在。

组件最低配额在主体装配阶段确定性落实。例如方案要求两盏入口灯时，装配器会直接在主入口两侧生成壁灯；不会等到合并校验报错后再由回调节点补两个无语义台灯。

## 6. 风格包怎么改

风格包位于：

```text
wild-server/storage/style_packages/
  modern.json
  chinese.json
  european.json
  glass_corporate.json
  high_tech.json
  eco_contemporary.json
```

当前注册表包含现代简约、新中式、欧式古典、国际现代幕墙、高技派和生态当代六个包。页面不会固定展示全部六项；`StyleRegistry.recommend()` 会综合原始文字、`profile`、`massing.shape` 和 `curtain_wall` 推荐最多四项。比如“高层玻璃幕墙商业综合体”默认推荐国际现代幕墙，并同时提供高技派、生态当代和现代简约；明确写“新中式”时仍会优先选中新中式。

每个包只允许标签、关键词、屋顶类型、色板、檐口、入口雨棚和柱列等受控参数。`StyleRegistry` 会限制数值范围并拒绝文件名与 `id` 不一致、未知屋顶类型或未知柱式。

带 `parentRoof` 的檐口 `path` 必须使用“以屋顶中心为原点”的局部坐标。当前编译器只对 `flat/gable/hip` 提供确定性屋面依附；`chinese_curved` 使用无 `parentRoof` 的世界路径。G7 会在保存前检查这项坐标契约，前端仅为旧版误写的 world-space `parentRoof` 文件保留可判定的兼容迁移。

新增风格时必须同时补：

1. 一个合法 JSON 风格包；
2. G7 可验证的装配结果；
3. 参数化回归测试；
4. 必要的 WILD Schema/编译器能力。不能只增加 Prompt 形容词。

## 7. 为什么仍不做“动态三维逐节点渲染”

当前审核只展示 SVG，最终 Blueprint 通过全量校验后才一次性加载三维。原因是中间 Blueprint 尚未满足完整引用和几何契约，多个异步重建还可能乱序覆盖正式场景。

节点仍会实时展示公开执行说明，例如“正在按确认平面装配主体”“G1-G6 通过”“正在应用新中式风格包”，但不会伪造模型内部思考，也不会用半成品污染当前场景。
