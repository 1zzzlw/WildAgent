# 建筑生成 Agent 当前设计思路（入门版）

> 适合第一次阅读本项目的人。本文讲“为什么这样设计、每一步产生什么”，字段级实现见 [Plan2Build 建筑生成链路](PLAN2BUILD_PIPELINE.md)。

最后核对：2026-08-27。

## 1. 先记住一句话

这个项目不是让大模型直接写一份很长的 `.wild` 文件，而是让大模型负责理解和设计，让 Python 程序负责把已经确认的设计编译成可靠的建筑。

```text
用户需求
  ↓
总体建筑方案（体量、层数、风格倾向）
  ↓
平面方案（房间、墙、门窗、楼梯、电梯）
  ↓ 用户确认平面
确定性主体装配（真正生成 WILD 坐标）
  ↓ G1-G6
用户确认推荐风格
  ↓
确定性装饰装配
  ↓ G7 + 完整校验
保存 .wild 并加载三维
```

这样做的原因很简单：大模型擅长理解“我想要什么”，但不擅长长期稳定地保证几百个坐标、父子引用和洞口边界全部正确。

## 2. 为什么要分成这么多节点

每个节点只回答一个问题。节点越界，就容易出现“文字方案正确，生成结果却是另一个建筑”。

| 节点 | 它回答的问题 | 它不能做什么 |
|---|---|---|
| `classifier` | 用户是在生成、修改还是问问题？ | 不设计建筑 |
| `architecture` | 建筑多大、多少层、由哪些体量组成？ | 不写房间和 WILD 坐标 |
| `floor_plan_design` | 每层有哪些空间，怎么连通？ | 不直接加载三维 |
| `floor_plan_review` | 用户是否认可平面？ | 未确认时禁止生成三维 |
| `material_plan` | 各材质角色使用什么受控 PBR 参数？ | 不改变建筑空间关系 |
| `skeleton` | 如何把确认方案编译成墙、板、楼梯、井道、门窗和屋顶？ | 不再让模型自由猜坐标 |
| `style_review` | 哪些风格适合当前建筑，用户选哪个？ | 不直接修改主体 |
| `decor_assembly` | 如何按风格包装配檐口、雨棚、柱列和色板？ | 只能执行受控 Decor IR |
| `merge` | 分片和主体合并后是否满足设计配额？ | 不应凭空改变设计目标 |
| `final_validate` | 最终 `.wild` 能否安全保存和渲染？ | 有错误时禁止下发 |

页面展示的是这些节点的公开执行过程，不是伪造的大模型“内心思维”。

## 3. 三份最重要的数据

### 3.1 ArchitecturePlan：总体设计意图

它类似建筑师的方案草图，主要记录：

- `massing`：宽、深、总层数、层高、形状；
- `volumes`：裙房、塔楼、侧翼分别占哪里、从哪层到哪层；
- `structural_grid`：结构轴网；
- `facades`：四个方向的开间节奏；
- `component_quota`：某类构件允许或要求多少个；
- `detail_packages`：雨棚、栏杆、灯光等细部意图；
- `curtain_wall`：是否采用幕墙表达。

这里还没有真正的墙网格。它表达“设计是什么”，不是“怎么画出来”。

### 3.2 FloorPlanIR：可以审核的平面事实

它记录每层轮廓、空间、墙、洞口和竖向交通。SVG 平面图与后续三维都必须读取同一份 FloorPlanIR，避免平面预览和最终建筑各画一套。

用户可以在第一次确认前直接确认，也可以反复发送修改意见。电梯覆盖这类可确定问题会自动修复并复检；无法安全自动决定的功能取舍才交给用户。

### 3.3 WILD Blueprint：最终可渲染事实

它才是引擎真正读取的文件，包括：

- `geometry.elements`：墙、楼板、柱、梁、楼梯、屋顶；
- `geometry.components`：门、窗、栏杆、雨棚、灯等组合构件；
- `templates + instances`：高层重复楼板和楼梯的轻量实例；
- `materials`：真实材质参数；
- 所有 `parentWall`、`parentRoof` 和材质引用。

同一份已确认方案必须生成相同坐标和稳定 ID，这就是“确定性装配”。

## 4. 用“高层玻璃幕墙商业综合体”走一遍

### 第一步：总体方案

总体模型可以提出“商业裙房 + 居中玻璃塔楼”。假设方案包含：

- 语义总层数 30 层；
- 规划代表层 10 层；
- 裙房占代表层 1～2；
- 塔楼占代表层 3～10；
- 总轮廓 42m × 36m；
- 塔楼轮廓 28m × 24m。

`floors=30` 是用户理解的真实层数，`modeled_floors=10` 是规划时压缩复杂度所用的代表层数。

### 第二步：平面设计

平面节点设计商业空间、核心筒、楼梯和电梯。30 层建筑如果缺少覆盖全部楼层的电梯井，工程预审会自动补齐，并重新检查空间和流线。

### 第三步：主体装配

程序把 10 个代表层重新映射到 30 个语义层：

- 裙房 1～2 代表层映射为语义 1～6 层；
- 塔楼 3～10 代表层映射为语义 7～30 层。

因此最终三维是连续的 6 层裙房和 24 层塔楼，不是两层裙房上接八层矮楼，也不是一根 120 米高的矩形灰盒。

高层重复楼板和楼梯采用模板实例。校验器会展开实例标高后再判断柱、楼梯是否悬空，不能因为楼板没有重复写 29 份就把正确的分段柱拉回地面。

### 第四步：幕墙表达

幕墙使用：

```text
连续玻璃 wall
  + 每层横梃 beam
  + 每跨竖梃 beam
  + 主入口 door
  + 明确要求时才切可开启 window
```

旧方案把幕墙当作普通灰墙，再只在 6 个代表层切窗，所以看起来像“灰盒外面套六圈蓝条”，还会让通高墙洞口过多、网格顶点爆炸。当前方案不再用数百个 window 洞口冒充幕墙。

### 第五步：细部配额闭环

`component_quota` 是硬约束，所以必须与真正选择的细部包一致：

- 没选中的回退细部不能残留为最低配额；
- 连续高层幕墙未明确要求时不使用凸窗，改用入口照明；
- 退台裙房如果要求栏杆，程序沿可达屋面边缘生成安全栏杆；
- 入口灯在主体装配阶段直接生成壁灯，不等合并报错后补台灯；
- 入口雨棚由用户确认的风格包锚定到真实主入口门。

### 第六步：屋顶

电梯井和楼梯井是室内竖向空间，上方仍需要防水屋顶；它们不能像露天中庭一样把屋顶切成四块。只有 `atrium`、`courtyard` 和 `open_to_below` 等真正露天或挑空的空间可以影响屋顶分片。

退台高层最终只有覆盖最高塔楼的主屋顶；裙房顶部按露台和楼板处理。这样屋顶数量才与 `roof.max=1` 一致，也不会出现 0.3 米宽的屋顶碎片。

### 第七步：风格确认

风格不再固定为三个选项。注册表目前有六个受控包：

- 现代简约；
- 新中式；
- 欧式古典；
- 国际现代幕墙；
- 高技派；
- 生态当代。

页面根据用户文字和已确认方案推荐最多四个。“高层玻璃幕墙商业综合体”会优先推荐国际现代幕墙，同时提供高技派、生态当代和现代简约。

用户确认后才执行 Decor IR。风格只改变受控屋顶外观、色板、檐口、入口雨棚和柱列，不推翻已经确认的空间与主体。

## 5. G1～G7 可以怎么理解

把闸门理解为七道验收工序：

| 闸门 | 小白理解 |
|---|---|
| G1 | 平面方案本身是否合法？ |
| G2 | 墙、板、ID 等主体是否齐全？ |
| G3 | 门窗有没有真实宿主并完全位于墙内？ |
| G4 | 多层建筑是否有连续楼梯/电梯？ |
| G5 | 屋顶是否被最高墙体承托并正确覆盖？ |
| G6 | 父墙、父屋顶、材质引用及幕墙物理材质角色是否正确？ |
| G7 | 风格装饰有没有破坏前六道契约？ |

G1～G6 通过后才能选择风格，G7 和完整校验通过后才能保存。警告用于提醒比例或质量风险；错误会阻止文件加载。

## 6. 这次错误为什么会连续出现

这次不是单点错误，而是不同阶段各自使用了不同事实：

| 表现 | 根因 | 当前规则 |
|---|---|---|
| 固定三个风格 | 页面直接展示注册表里仅有的三个 JSON | 扩展六个风格包并按方案推荐四项 |
| 灰盒加几圈窗 | 骨架忽略 `volumes`，幕墙又只采样代表层窗 | 体量区间映射 + 连续玻璃墙 + 轻量龙骨 |
| 有玻璃材质却显示黑色墙面 | 材质节点按 `wall/beam` 类型覆盖，玻璃壳体和金属龙骨丢失语义 | 按骨架材质角色装配；G6 强制检查玻璃壳体、金属龙骨和物理玻璃参数 |
| 灯具数量先报错 | 装配阶段未落实最低配额 | 合并前生成入口壁灯 |
| 4 个屋顶且有薄片 | 电梯井被当成露天洞口 | 只允许中庭/庭院/挑空切屋顶 |
| balcony 无故缺少 | 回退候选配额泄漏到已选候选 | 只保留最终细部包的配额 |
| 幕墙还要求凸窗 | 总体模型用不相容细部凑复杂度 | 未明确要求时替换为灯光 |
| railing 缺少 | 旧代码只支持 U 形露台栏杆 | 退台裙房也生成边缘栏杆 |
| 分段柱变成重叠柱 | 校验器没展开楼板实例，修复器错误改标高 | 校验和修复共用实例化楼板标高 |

这些都是共享规则，没有针对某个会话 ID、某栋建筑或截图坐标写特殊判断。

## 7. 看日志时先看哪里

建议按这个顺序：

1. `architecture`：体量、层数和 `volumes` 是否符合需求；
2. `floor_plan_design`：空间、入口、楼梯和电梯是否合理；
3. `skeleton`：G1～G6 是否全部通过，元素/组件数量是否异常；
4. `style_review`：推荐风格是否符合建筑类型；
5. `validation_design`：配额是否与真正生成的构件一致；
6. `validate_model_quality`：是否有重复墙、重叠柱；
7. `validate_element_dimensions`：是否出现极薄屋顶或超高单构件；
8. 浏览器控制台：是否还有顶点数超限、父构件越界或编译失败。

“通过”表示结构契约正确，不等于建筑审美一定优秀；审美和功能需要在两次人工确认中判断。

## 8. 当前能力边界

当前已经实现的是方案级建筑生成，不是法定施工图系统。它可以表达多层空间、曲/斜墙、L/U/中庭、楼梯电梯、退台体量、幕墙分格、受控风格和确定性修复，但不会替代真实结构计算、消防审查、机电深化和所在地法规审批。

当前三维仍在最终 Blueprint 全量通过后一次性加载。逐节点动态渲染半成品会产生引用不完整、异步结果乱序和正式场景被污染的问题，因此没有重新开启。
