## 2. 这次到底如何生成

用户当时要求“生成一个别墅 wild 文件，我自己渲染”。没有提供完整的房间表、场地或粒度要求。两层、现代庭院、挑空客厅、书房、两间卧室、露台等是助手为这次示范自主选择的方案，不是用户强制要求。

这次没有运行项目的 classifier、architecture、plan 或 execute，没有先保存 `design_document` / `architecture_plan`，也没有调用额外供应商模型 API。助手在当前对话上下文内确定整体设计，按需读本地资料，编写并执行 Python 脚本，直接产出 WILD。

因此，下文的“设计表”“空间关系”和“对应节点”是对实际参数及行动的复盘，不是从某次 Agent trace 中提取出的 architecture 原始输出。迁移时需要把这些有效的决定与依据落实到项目现有图纸和执行过程。

## 4. 第一步：先确认可用表达，再确定整体方案

先读取 WILD 容器、字段、材料和构件语义，并核对当前引擎。这样可以避免已经设计好后，才发现楼板、门窗或屋面定位理解错误。

随后确定本次整体方案：后侧两层主楼与东侧单层侧翼，围合前侧庭院；主楼西端为通高客厅，侧翼为书房；上层安排两间卧室与交通、卫浴，侧翼屋顶作为从上层进入的露台。

关键选择彼此关联：

```text
L 形主次体量 → 围合庭院 → 客厅玻璃朝向庭院
通高客厅 → 二层楼板留空 → 房间与上层交通向东组织
单层侧翼 → 屋顶成为露台 → 二层门槛与露台板顶对齐
两层交通 → 双跑楼梯 → 平台、二层洞口、出口楼板共同安排
```

没有先写一个封闭长方体，再靠随机加窗和装饰凑出别墅。

## 5. 第二步：固定坐标、体量和标高

本例使用世界 X/Z 表示平面，Y 表示高度，单位为米。

| 部位 | 平面范围或标高 |
|---|---|
| 主楼设计墙线 | X=[0,16]，Z=[6,14] |
| 东侧翼设计墙线 | X=[10,16]，Z=[0,6] |
| 主要庭院 | 主楼前方、西侧翼左方，局部平台与水景位于该范围 |
| 一层楼面顶 F0 | 0.45 |
| 二层楼面顶 F1 | 3.75 |
| 主楼墙顶 TOP | 7.05 |
| 主要楼板厚 SLAB | 0.22 |
| 单层侧翼墙顶 / 露台板底 | 3.53=3.75-0.22 |
| 中间楼梯平台顶 | 2.10 |

实际楼板为覆盖墙体外缘而适量外伸，例如主楼地板 X=[-0.12,16.12]、Z=[5.88,14.12]。墙线、板边和屋檐不是同一个边界；不应强行全部重合。

所有主体坐标都从这一套关系展开。这样修改楼面标高时，可以追踪与之相连的楼板、门、家具底、梯段和露台，而不是分别猜一遍。

## 6. 第三步：用少量辅助函数表达底层几何

原始脚本定义：`material`、`box`、`bounds_box`、`floor`、`wall`、`window`、`door`、`furniture`、`cylinder`、`sphere`、`railing`、`light`，以及针对本例景观的 `planter`、`tree`。

它们减少重复书写，不替代方案设计。例如：

```python
# 从边界推导中心与尺寸
center = [(x1+x2)/2, (y1+y2)/2, (z1+z2)/2]
size = [x2-x1, y2-y1, z2-z1]

# 从行走面顶推导有厚度 floor 的输入 Y
bottom_y = top_y - thickness

# 重复构件由明确的起点和间距展开
z = start_z + i * spacing
```

随后生成完整 `geometry.elements/components`，只在最终序列化阶段统一处理浮点精度，并拒绝非有限 JSON 数值。

这不是一个已经存在的通用别墅生成器。函数只是本次临时编写的辅助，具体体量、屋面、房间、洞口和家具的坐标大多仍是这次方案的明确选择。迁移时不能把这些具体坐标藏进“通用函数”。

## 7. 第四步：按空间关系生成建筑实体

实际生成脚本从地面、基础与楼板开始，再组织围护、洞口、屋面、细部、楼梯、露台、家具、景观和照明。材料表在脚本前面先建立，所有实体引用相同材料 ID。

### 7.1 主体与空洞

主楼和侧翼各有地面与基座，交接处只建立一面共同接口墙。主楼西端客厅的上方不铺二层楼板；二层其余部分按楼梯洞口分成多片 floor。

二层四片 floor：

| ID | X 范围 | Z 范围 | 用途 |
|---|---|---|---|
| upper_west | [5.88,12.65] | [5.88,14.12] | 卧室及西侧部分 |
| upper_landing | [12.65,16.12] | [5.88,9.60] | 楼梯上行出口侧楼面 |
| upper_east_strip | [15.55,16.12] | [9.60,14.12] | 洞口东侧边带 |
| upper_rear_strip | [12.65,15.55] | [13.60,14.12] | 洞口后侧边带 |

楼梯洞口 X=[12.65,15.55]、Z=[9.60,13.60]。留空是通过实际板片范围实现，不是文字里写一个“挑空”就结束。

### 7.2 围护与门窗

墙先有稳定 ID，门窗再通过 `parentWall` 依附。客厅使用通高大窗；入口由双扇门与侧窗组织；侧翼书房有面向庭院的玻璃；上层卧室、卫浴与楼梯间各有对应开口。

窗框、分格与玻璃分别表达，玻璃不是一块不透明实心墙。框深按实际宿主墙厚填写。原始检查按每个实际墙 ID 检查同墙洞口重叠，未证明不同但共面的墙之间所有开口都不相交。

### 7.3 屋面与露台

主屋面：原生 flat roof，中心平面位置 [8,10]，span=17.2、depth=9.2，支承 Y=7.05、厚度 0.22。

侧翼屋面：原生 flat roof，中心平面位置 [13,2.82]，span=6.48、depth=6.12，支承 Y=3.53、厚度 0.22，得到露台顶 Y=3.75。露台门底同为 3.75。

檐口、底面、入口雨棚和木格栅另有真实实体。屋面由 roof 元素承担，不能拿几根檐口装饰代替覆盖面。该文件的屋面存在及尺寸明确；当时没有执行完整屋面覆盖面积校验。

### 7.4 双跑楼梯与楼板一起安排

| 部位 | 实际参数 |
|---|---|
| 第一跑 | X=13.3，Z:9.6→12.3，Y:0.45→2.10 |
| 第二跑 | X=14.9，Z:12.3→9.6，Y:2.10→3.75 |
| 每跑 | width=1.2，stepCount=10，stepHeight=0.165，stepDepth=0.27 |
| 中间平台 | X=[12.65,15.55]，Z=[12.3,13.6]，顶 Y=2.10 |
| 二层出口 | 第二跑到达 Z=9.6，与南侧现有楼板相接 |

每跑高差 10×0.165=1.65，水平行程 10×0.27=2.70，两跑总升高 3.30=3.75-0.45。扶手沿梯段和平台组织；洞口防护在到达方向留通行缺口。

当时检查了相关楼板的若干采样点，不是对所有梯段净空做连续空间证明。

### 7.5 材料与细节

先确定暖色浅墙、石材基座、橡木、深金属和青铜框的整体关系，再将材料 ID 分配给墙、地板、框架、家具、廊架和景观。玻璃使用 materialClass、transmission、ior 等实际参数。

通过木格栅、细檐、雨棚、露台廊架、家具与灯具增加尺度感；通过家具摆放区分客厅、餐厨、书房、卧室和卫浴；庭院水景及植物补充室外关系。

本例水景为抬高浅池及玻璃类材质水面，是视觉表达，不是可游泳设施或流体模拟；植物由几何组合表达，没有外部资产。

## 8. 第五步：执行脚本并检查真实 JSON

第一段生成脚本实际执行，写出初稿。随后第二段脚本读取刚写出的文件，执行以下检查：

| 检查 | 实际范围 |
|---|---|
| JSON Schema | 当前 `wild-core/schema.json`，结果错误数 0 |
| ID | elements 与 components 全局唯一；本例避免使用保留式双下划线 ID |
| 材料引用 | 元素 material，以及组件中实际使用的相关材料字段存在于材料表 |
| 门窗宿主 | parentWall 存在且为 wall |
| 洞口范围 | along≥0、along+width≤墙长，底与顶位于宿主竖向范围内 |
| 同墙洞口重叠 | 同一 parentWall 的沿墙区间与竖向区间不同时重叠 |
| 框深 | frameDepth 等于本例对应墙厚 |
| 梯段一致性 | stepCount×stepHeight 等于实际高差；stepCount×stepDepth 等于水平距离 |
| box 尺寸 | 本例所有 primitive.box 的 dimensions 都为正 |

这些检查读的是实际产物，不是复述设计说明。它们没有涵盖所有家具碰撞、建筑连通性、任意构件网格相交或规范条件。

后续 Agent 优化中出现的 asyncio / `WinError 10106` 是另一项环境问题，影响正式模块加载、分片预览与索引同步；不能把它混写成此别墅已经完成了 RAG 或完整服务验证。

## 11. 从本例应迁移和不应固定的部分

应迁移：整体设计次序、相关上下文连续传递、当前协议核实、可执行数值计算、生成后读取实际实体、有限关系检查、主动使用复核、最终版本追踪。

不应固定：两层、L 形、16×8 主楼、3.3 层间高、平屋面、双跑 U 梯、暖色配色、池塘、家具数量或廊架套餐。用户要求、形制和粒度不同，应得到不同建筑。

本例证明了这一条路线能产出一个用户喜欢的结果。它没有证明某个辅助函数或某段知识单独决定了效果，也没有证明把本例 JSON 放进知识库就能稳定复现质量。完整迁移与对照方案见[规划书](README.md)。
