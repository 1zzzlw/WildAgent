# 10 月 19 日优化规划：迁移“庭光别墅”的完整生成方法

日期：2026-10-19。状态：规划，尚未按本规划实施或完成真实生成验收。

本次用户要求先记录实际生成方法，再据此优化 Agent。本目录新增文档与参考产物，不修改业务代码、运行配置或知识索引。

## 1. 要迁移什么

目标是让 Agent 具备这次手工生成中发挥作用的完整能力：理解需求和建筑关系，形成整体方案，查明当前 WILD 协议，利用程序计算和展开几何，检查实际结果，主动复核空间使用，再交付用户渲染。

“庭光别墅”取得了用户的正向视觉反馈，但只有一个案例。它不能证明某份提示词、某套尺寸或某种模型一定有效，也不能证明当前 Agent 已达到相同水平。迁移对象是工作方法，不是把所有请求变成这栋两层 L 形别墅。

本目录的阅读顺序：

1. [实际生成复盘](01-庭光别墅实际生成复盘.md)：当时做了什么、用了什么知识、哪些检查真的执行了。
2. 本文第 3～8 节：能力差距、职责、实施阶段与验收。
3. [原始脚本与检查记录](02-原始脚本与检查记录.md)：三段实际执行的命令、结果及资料指纹。
4. [参考产物](参考产物/庭光别墅-Codex.wild)：用户认可的最终文件，仅作对照，不作为普通生成的整栋示例注入。

## 2. 对本次成功的判断边界

已经确认：原始文件有效落盘；当时执行的 JSON Schema、引用、开口、楼梯数值等检查通过；根据布局复核调整了部分家具和高窗；用户自行渲染后表示效果很好。

尚未确认：助手没有完成该文件的引擎编译和渲染，没有保存渲染截图，也没有完成全面碰撞、通行净空、结构或建筑规范检查。没有同模型、同需求、同粒度、同预算的对照实验，不能把效果差距全部归因于 Agent 架构。

前一轮优化已补充共享标高与体量边界、显式挑空检查和特定 U 形楼梯计算。这只是完整路线的一部分。其隔离检查通过，实际模型生成尚未验收；设计方法与粒度文档的正式索引同步仍受环境影响。不能把“代码存在”写成“真实运行已经采用”。

## 3. 当前 Agent 与手工路线的差距

以下现状以 2026-10-19 工作区源码为准，后续实施前需要复核。

| 能力 | 这次手工实际做法 | 项目当前已有 | 迁移重点 |
|---|---|---|---|
| 整体设计 | 在同一上下文中安排体量、挑空、入口、交通、露台、家具与景观 | architecture 输出完整图纸，支持意图与逐层平面 | 让关键空间选择成为可定位的数据，减少只写在概念里的特征 |
| 协议核实 | 按需读取当前 Schema、知识文档和引擎实现 | RAG、能力摘要、构件示例与校验 | 向模型提供核实后的简明输入语义，不要求每次阅读全部引擎源码 |
| 可执行计算 | 写 Python 辅助函数、循环与公式，再实际执行 | 门窗定位、部分楼梯路线、共享标高等确定性辅助 | 增加任务内参数化生成能力，避免让模型逐项心算和手抄大量 JSON |
| 关系检查 | 直接核对生成后的墙、板、洞口、梯段和露台门 | 局部片段验收、装配检查和最终候选检查 | 对已选择的关系生成实际证据，不能只检查类型、数量和字段 |
| 主动空间复核 | 发现并调整书架、庭院家具和高窗的位置 | 现有修订主要由错误反馈触发 | 对入口、使用空间、开口和家具进行整体复核，区分实现错误与设计取舍 |
| 连续上下文 | 同一套坐标和材料贯穿生成与修订 | 图纸、标记、上下文裁剪、实体与实现记录 | 每项任务拿到完整相关依赖；实际丢失要用 trace 证明，不能先假定 |
| 视觉验收 | 助手交付文件，由用户实际渲染 | 已有真实引擎验证和渲染脚本 | 建立相同视角的对照记录；视觉结果和数值检查分别结论 |

现有建筑主线是：

```text
architecture → material_plan → design_review → plan
    → execute / replanner → compile → final_validate
```

建筑分支的 `plan` 根据已批准标记确定性展开任务，当前 `model_calls=0`。实际构件研究和生成在 `execute`。迁移沿这条链进行，不另建第二条建筑生产线。

## 4. 保持清楚的职责与数据

### 4.1 architecture：决定建筑怎样组织

一次形成完整方案，按依赖顺序考虑：需求与形制、体量和标高、功能与交通、围护和洞口、屋面与附属、材料及所选粒度的细节。

关键不是额外写一段“我会检查”的文字，而是将选择落实：

| 设计选择 | 优先复用的表达 | 需要看到的实际结果 |
|---|---|---|
| 主楼与侧翼 | `volumes`、各体量 `facades` | 接口清楚，没有重复围护或错误封闭 |
| 通高或挑空 | `floor_layouts` 中对应层的 `room.void=true` 与范围 | 对应上层楼板确实留空，上方仍有设计要求的屋面 |
| 房间与入口 | 房间范围、内墙、门的宿主和位置 | 入口通向预期空间，隔墙和门不互相矛盾 |
| 楼层交通 | `components`、`floor_connections`、占地和形式 | 梯段、平台、楼板洞口和出口形成连续路径 |
| 可使用露台 | 体量屋面、连接门、防护等实例 | 板顶与门槛相接，入口处没有栏杆封堵 |
| 材料构图 | `design_intent.material_strategy`、材质角色及实例描述 | 最终构件采用相应材料，不只保留文字名称 |

没有室内布局要求的项目不必强迫生成完整房间表。已经选用了房间、挑空或交通关系时，相关范围和连接信息必须足够实现。屋顶的形制、归属和支承关系仍由 architecture 决定；具体 WILD 表达由执行阶段完成。

### 4.2 程序：计算已确定关系

模型负责设计选择；程序负责可复算的结果，例如边界到中心的换算、楼面顶到板底的换算、两点距离、梯段升高和行程、重复构件的间距与编号。

程序不能擅自决定建筑改成两层、把窗移到另一面墙、取消挑空或换一种材质。关系本身矛盾时，应报告设计路径与冲突数值。批准后的设计变更沿现有修订和审核流程处理。

### 4.3 plan / execute：安排依赖并实现

plan 保留确定性任务展开。execute 结合图纸、已采用实体、协议和相关知识，选择原生构件或组合表达，并获得数值计算与参数化展开工具。

所有实现路径最终返回现有片段格式，进入相同的材料绑定、实体所有权、宿主引用、尺寸与关系检查。参数化脚本不是绕过验收的第二入口。

### 4.4 compile / final_validate：检查实际建筑

compile 装配已采用片段并定位跨任务问题，final_validate 对真正交付的同一候选进行完整检查。局部通过不能代替整栋建筑通过；一个标记有实体也不能证明设计特征已实现。

`design_document` 继续作为批准设计的主数据。`architecture_plan` 是兼容投影，不再维护一份独立方案。派生坐标按设计版本计算；无需为了迁移再建立一套可独立修改的“空间总图”。

## 5. 参数化能力的迁移方式

只把几条公式放进提示词不能迁移这次的工作方式。此次实际优势之一是程序执行：公式计算出数值，循环展开实体，检查器读取实际产物。必须保留这一环。

两种可行路径及取舍：

| 路径 | 优点 | 局限 |
|---|---|---|
| 继续逐个增加固定构件函数，只让模型填参数 | 对已支持形态简单，易验证 | 很容易演变为按建筑类型堆模板；新组合仍需模型手算 |
| 在现有执行任务内增加受控参数化程序通道 | 能表达本例的数值计算、循环和临时组合，接近本次实际方法 | 需要可靠的执行边界、输出协议、追踪与相同验收 |

本规划选择第二条作为完整迁移目标，同时复用已有确定性计算。先验证一个任务内的最小闭环，不建设通用编程平台或多 Agent 体系。

最小能力范围：

1. 输入只读：当前图纸及版本、任务标记、必要的实际宿主、统一标高与边界、已批准材料、相关协议。
2. 程序可进行有限的数值、列表、循环与局部纯函数计算，调用少量 WILD 输出辅助函数，结果为现有 JSON 片段。
3. 普通原生构件仍可直接返回 JSON；大量重复或相互依赖的几何可返回生成程序。选择依据是表达复杂度，不按别墅、亭子等类型硬编码。
4. 程序执行不放在 API 主进程中 `exec`。独立受限执行环境不获得服务密钥、任意文件或网络访问，限制时间、内存、实体数及输出大小。语法过滤不能代替执行隔离；隔离不成立时该通道不进入正式服务。
5. 执行结束后重新读取真实输出，拒绝 NaN、重复 ID、无效引用和越权修改；任何说明文字都不能代替实体。
6. 记录输入版本、程序、实际返回、错误与采用结果。执行异常如实失败，不偷偷换成预制建筑。

首批辅助函数只覆盖低层表达，例如“由边界生成 box”“给定板顶生成 floor”“按墙局部坐标声明门窗”。不提供 `make_villa()`，不自动附加庭院、水景、廊架和家具套餐。

原始脚本可以启发接口，但不能直接作为线上执行器：它读写本机文件，使用本例硬编码坐标，并未遵循项目任务与片段所有权协议。

## 6. 分阶段实施

### P0：保存基准，打通真实验证入口

目的：先能比较，避免每轮优化凭印象判断。

工作：使用本目录已归档的参考产物与原始过程；固定一份明确需求和粒度；记录模型、参数、知识索引状态、图纸版本与调用费用。核对现有引擎验证及渲染入口可用；先记录环境问题，不将其误诊为设计问题。

验收：参考文件能按相同渲染设置出图；Agent 当前结果能保留图纸、最终 WILD、trace 和截图。环境仍不可用时，只能完成资料与离线核对，不能宣布效果基线已经建立。

### P1：让整体设计具有可实现的空间依据

入口：`architecture/workflow.py`、`design_workflow.py`、`prompts/planning.py`、`design/contracts.py`、`design/coordinates.py` 与现有设计知识。

工作：按实际生成顺序组织设计资料，核对粒度规则的真实召回；重要关系落入已有字段；统一派生世界边界、楼面顶、墙顶、屋面承托及显式空洞。针对本例重点检查挑空、翼楼露台和楼层交通。

验收：无需执行节点重新猜测，就能解释每个重要空间关系；首次图纸及修订记录可追溯。校验反馈给出路径与实际冲突，不要求模型反复整体简化。没有关系表达缺口的证据时不扩充 Schema。

### P2：实现任务内的参数化生成与执行

入口：`plan/implementation.py` 的输出协议、`run_marker_generate`、`_accept_fragment`，以及一个职责单一的受限执行模块。plan 的确定性展开保留。

工作：先选真实出现过的重复构件或多实体组合任务，支持模型在一次实现回复中给出可执行的生成逻辑；程序输入来自当前上下文，结果归一到已有片段。失败反馈仍使用当前局部修订和预算计数。

验收：能执行本例同类的坐标换算、重复排列和组合生成；相同参数重复执行得到相同结果。更换尺寸、位置和方向仍成立，不依赖本例 ID。直接 JSON 与程序产物进入同一检查链，不能绕过材料、宿主及标记验收。

这里不能省略真实运行，只展示脚本字符串不算完成迁移。确定性程序运行无需额外模型调用；需要模型修订时按真实调用计费，不提高原有次数上限来制造成功。

### P3：把关键设计关系核对到实际实体

入口：`design/coordinates.py`、`design/relations.py`、`design/markers.py`、`plan/implementation.py`、`validation/candidate.py`。

工作：复用已有检查，补足已复现缺口。先覆盖统一标高、门窗宿主、明确空洞、楼梯与平台、露台门槛和屋面覆盖；局部采纳及最终检查采用同一解释。允许合理的连接、贴合与构造搭接，不能用“任意包围盒相交就是错误”替代关系检查。

验收：每项声称实现的关键关系都能追溯到设计路径、实际实体、计算依据及结论。检查不支持的旋转、曲线或组合形态明确记录边界，不能自动标为通过。

### P4：补上主动整体复核

入口：首次设计的复核要求、当前上下文生成、现有 compile 装配反馈及审核流程。

工作：把本例主动调整的依据迁移为有限复核范围：入口和门的使用区、楼梯到达区、主要通路、家具占地与已选开口的关系、材料实际分布。先用程序检查可判定部分，再把未解决的少量关系和相关实体交给模型判断。

设计前复核尽量在 architecture 首次设计中完成；实现后的必要整体判断复用现有装配修订预算。不能变成每轮无条件重新评价并重做整栋建筑。审美取舍、家具允许遮挡的程度和需要重新设计的问题，应留下理由并进入适用的设计修订流程。

验收：本例“书架遮挡玻璃”“庭院家具侵占入口方向”“高窗与柜体争夺同一区域”能得到具体相关对象和处理依据；同样能保留合理的家具临窗、材料搭接。不能仅输出“布局合理”。

### P5：完整装配、真实渲染与对照

入口：`design_flow/compile.py`、`validation/candidate.py`、`validation/workflow.py`、`wild-web/scripts/validate-generated.mjs`、`render-baseline.mjs`。

工作：绑定实际交付候选的 hash，保存编译和重建诊断，以相同引擎、相机、灯光及尺寸渲染。分别对照批准图纸、Agent 实际产物与手工参考，定位最早发生偏差的位置。

验收：独立记录字段合法、关系落实、引擎可构建、视觉与使用感受。缺少重要建筑系统或无法满足批准设计时如实报告；不以“最终有一个文件”代替完成。

### P6：验证收益后清理被替代实现

入口以实际调用关系为准。

工作：清理此次迁移替代的重复坐标计算、转发包装、无消费字段和相同语义的重复提示。保留物件、编辑、视觉修订仍在使用的旧入口。

验收：每个删除项有调用方核对和替代位置；新路径只保留一套坐标与片段验收语义。不能先删除校验、降级约束或恢复默认建筑来让新路径更容易通过。

## 7. 知识应放在哪一层

| 内容 | 放置位置 | 维护原则 |
|---|---|---|
| 需求、形制、空间使用和材料构图方法 | 设计 RAG | 方法和取舍，不规定所有建筑的层数、尺寸与配色 |
| 各粒度交付范围 | 已有粒度规则 | 高粒度意味着层次与表达更精细，不是固定增加门窗数量 |
| WILD 字段、坐标、引用及实际能力 | 协议、能力资料与工具说明 | 按当前 Schema 和源码核实；矛盾先澄清，不能两套定义并存 |
| 稳定公式、边界换算与展开 | 共享纯函数和参数化执行工具 | 可复算，不让模型反复凭文字算坐标 |
| 已知有效的构件局部实现 | 构件 RAG | 带适用条件和宿主语义；尺寸由当前设计决定 |
| 某次生成的错误及运行证据 | trace、诊断与本次文档 | 证明缺口后再提炼通用规则，不把每个案例变成永久提示词 |
| 整栋“庭光别墅” | 本目录参考产物 | 对照和回放使用，不进入每次普通生成的检索上下文 |

知识入库需走现有 Markdown 分片、manifest 和增量同步流程，实际命中才算应用。完整工程迁移不应退化成继续向 architecture 提示词添加几十条补丁。

## 8. 如何判断完整迁移有效

先进行明确目标的少量对照，不在当前写文档阶段发起付费生成。

| 对照 | 固定条件 | 要回答的问题 |
|---|---|---|
| 已保存产物回放 | 同一图纸、相同参数和模型已返回内容 | 计算、解析、校验和装配是否正确，不混入模型随机性 |
| 明确需求的前后对照 | 同模型、请求、粒度、思考设置、调用上限和渲染设置 | 改进能否归因于路线迁移，而非换模型或暗中扩充设计范围 |
| 少量重复生成 | 每次记录实际用量、时延及失败原因 | 是否稳定一些，而非只展示最好的一次 |
| 不同需求的迁移检查 | 改变体量组合、方向、尺寸或建筑类型 | 是否学会同一方法，而非复刻参考建筑 |

手工文件包含家具、景观和立面细节，没有经过 classifier 的 `detail_level` 判定。不能把它当作当前 `minimal` 档的强制交付标准。对照时需明确这些内容是否在需求和粒度范围内；低粒度仍要正确保留所选形制与必要关系。

每次记录四类结果：

1. 设计：需求是否落入图纸，是否为了通过而删除原有重要特征。
2. 实现：关系是否落实到实际实体，重要构件是否缺失或被舍弃。
3. 视觉：同视角的体量、虚实、材料层次与空间使用反馈。
4. 成本：实际模型调用、token、费用、耗时、局部修订和程序执行次数。
