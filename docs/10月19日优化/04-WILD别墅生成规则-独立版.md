# WILD 别墅生成规则：可直接提供给大模型的独立文档

版本：2026-10-20。适用格式：WILD 1.0。目标：生成具有整体设计、明确空间关系、真实门窗、完整屋面和材料层次的别墅 `.wild` 文件，达到“庭光别墅”所体现的设计完整度。

使用方法：将**本文件全文和本次用户需求**一起提供给模型。希望接近“庭光别墅”时，使用第 12 节的参考任务；希望生成其他别墅时，替换任务，保留通用规则。接收模型不需要访问 WildAgent 源码、知识库、历史对话或原始文件。

本文件提供生成所需的字段子集、设计方法和关系约束，不保证任意模型一次成功或得到完全相同的观感。它不是施工、结构或建筑规范文件。材料和尺寸示例为表达与设计参考，不构成工程标准。

---

## 1. 给接收模型的任务约定

你同时承担建筑方案组织和 WILD 数据表达。结合自身建筑知识与用户需求作出设计选择，依据本文把选择落实成真实实体。

按以下顺序完成：

1. 理解需求，确定建筑最重要的空间和形制特征。
2. 确定体量、功能、交通、统一坐标和标高。
3. 按依赖生成主体、洞口、屋面、楼梯、附属、家具、景观和照明。
4. 读取实际生成的数据，复核尺寸、引用、承接、通行与材料。
5. 只修冲突部分，保留其他正确设计，输出完整文件。

设计过程可以使用简明表格、参数与计算，不必向用户输出内部推理。最终默认只返回**一个完整 WILD JSON 对象**；能创建附件时，交付 UTF-8 编码的 `.wild` 文件。

最终文件必须是实际建筑，不能交付方案说明、生成脚本、局部字段示例或待填模板来代替。用户另行要求脚本时，可以附脚本，但仍需明确是否已经执行并产生文件。

## 2. 设计质量来自哪些决定

### 2.1 先设计可使用的空间

先明确这几个问题，再布置几何：

- 入口经过哪里，进入什么空间，如何到达主要房间？
- 公共空间与私密空间如何组织，楼梯出口通向哪里？
- 哪些空间开敞、封闭或通高，哪些位置确实需要墙？
- 露台、庭院和室内怎样连接？有可到达的门，还是只有一块孤立的板？
- 家具如何服务于空间，人在门口、桌旁、楼梯出口是否有活动余地？

先在 X/Z 平面安排房间范围、墙线、连接口和主要通路。房间名称只是设计标签，不能替代围护、楼板和连接实体；开敞的客餐厅也不必为了房间名称而增加隔墙。

### 2.2 用少量关联选择形成建筑

一种可行关系是：主次体量形成庭院，客厅大窗面向庭院；局部通高使上层楼板退让，上层房间与交通在另一侧组织；单层附体的屋顶成为露台，露台门与其顶面相接。

这是一种设计思路，不是所有别墅的固定答案。建筑的层数、形状、坡顶或平顶、空间组织、颜色和材料由本次需求决定。

每个选定特征都要有实体证据：

| 设计选择 | 最终文件中必须出现的结果 |
|---|---|
| 通高客厅 | 客厅上方没有层间楼板，上方有实际屋面覆盖 |
| 玻璃立面 | 真实墙洞、透明玻璃和独立框料，不用蓝色不透明板冒充 |
| 可到达露台 | 实际板面、连接门和所需防护，门槛与板顶相接 |
| 双跑楼梯 | 两个梯段、中间平台、上层洞口和出口楼面 |
| 廊架 | 柱、梁和格栅的实际几何，相接标高一致 |
| 室内外联系 | 连续可行走表面与门，不仅在文字里写“流动” |

### 2.3 让层次有主次

按整体体量、虚实与开口、材料分区、构造细部、家具与环境逐层落实。主入口需要识别度，但不要求每个立面都成为主入口。

同组窗框、细檐、格栅可以保持尺度和材料一致；不同功能的立面允许不同开口。格栅、雨棚和廊架应该回应遮阳、入口或空间边界，不随机贴满所有墙面。

精细度提高，应体现在空间承接、框与玻璃的区分、板厚、檐底、节点和材料表达上，不能只靠增加窗户、椅子或装饰条数量。

## 3. 最终文件的容器与命名

`.wild` 是 JSON 文本，不是 XML、Markdown 或自定义脚本。本文采用四个根字段：

```json
{
  "meta": {"version": "1.0", "type": "building", "name": "本次建筑名称"},
  "geometry": {"elements": [], "components": []},
  "materials": {},
  "assets": {}
}
```

上述仅为容器格式。最终 elements、components 和 materials 必须填入实际设计，不能把空容器当作完成。

| 集合 | 本文使用的类型 |
|---|---|
| `geometry.elements` | `wall`、`floor`、`roof`、`stair`、`furniture`、`primitive` |
| `geometry.components` | `door`、`window`、`railing`、`light` |
| `materials` | 材料 ID 到完整材质参数的字典 |
| `assets` | 本文不依赖外部资产，使用 `{}` |

规则：

- 所有实体和组件的 id 全局唯一，建议采用语义前缀及序号，如 `main_wall_front_l1`、`pergola_slat_03`。
- 组件展开会产生内部 ID，手写 ID 避免使用双下划线 `__`。
- 所有材料引用都在本文件 materials 中定义，不能依赖接收方恰好有某个全局材质。
- 不把 `design_document`、`architecture_plan`、`massing`、`volumes`、`host`、`placement`、`size`、`form` 或 `program` 当成本文实体字段。它们可用于中间设计，交付前须转换成下面的 WILD 字段。
- 不手写 `_cutouts`、`_interaction` 等内部派生字段。
- 数值写实际有限数字；不允许注释、NaN、Infinity、尾逗号、省略号或未展开的循环。

## 4. 坐标和标高：全文件共用一套依据

### 4.1 基本约定

单位统一为米，坐标写 `[X,Y,Z]`。X/Z 是平面，Y 向上。本文示意图的主入口侧为较小 Z，后侧为较大 Z；这是设计朝向约定，不改变坐标规则。

角度字段 `rotation:[rx,ry,rz]` 使用弧度。本文对家具、box 仅使用绕 Y 的旋转；0、π/2、π 分别约为 0、1.570796、3.141593。

每一层先确定楼面顶 `F[k]`、板厚 `t[k]`、上层楼面顶和墙顶。相连构件从这些参数推导，不分别猜坐标。

### 4.2 不同字段的锚点

| 对象 | 输入含义 | 从设计标高转换的方法 |
|---|---|---|
| 有厚度的矩形 floor | from.y、to.y 是板底，向上增厚 | 输入 Y = 目标板顶 − thickness |
| flat roof | position 的 X/Z 是中心，Y 是支承底标高 | 屋面顶 = position.y + thickness |
| primitive box | position 是几何中心 | 中心 Y = 目标底标高 + 高度/2 |
| primitive sphere/cylinder | position 是几何中心，圆柱默认沿 Y | 落地圆柱中心 Y = 地面顶 + height/2 |
| furniture | position 是底面中心 | 落地时 position.y = 楼面顶 |
| wall | from/to 的 X/Z 决定墙线，两个 Y 决定底与顶 | from 写墙底，to 写墙顶；不是一根倾斜杆 |
| door/window | from 是墙局部沿线距离、底部世界 Y、法向偏移 | 详见第 6 节，不能直接填世界 XYZ |
| railing | 本文不填写 parentFloor，path 是栏杆基线世界坐标 | 水平栏杆基线 Y = 板顶，扶手顶 = 基线 Y + height |

本文件中的有厚度楼板和屋面统一采用大于 0.01m 的厚度，避免进入薄平面表达。具体厚度由设计决定。

### 4.3 边界到中心

需要一个包络 `[x0,x1]×[y0,y1]×[z0,z1]` 时：

```text
position   = [(x0+x1)/2, (y0+y1)/2, (z0+z1)/2]
dimensions = [x1-x0, y1-y0, z1-z0]
```

所有尺寸为正。墙线、板边、屋檐外缘可以因墙厚、包边和出檐不同；先定义它们的关系，不能把不同边界混成一个数值。

## 5. 主体、楼板与屋面

本节 JSON 均为**局部格式例子**，不是完整建筑；例子中的材质 ID 见第 9 节。

### 5.1 墙 wall

```json
{"type":"wall","id":"front_wall","from":[0,0.45,6],"to":[6,3.53,6],"thickness":0.24,"material":"wall_light"}
```

此墙在 X/Z 平面沿 X 从 0 到 6，墙底 0.45、墙顶 3.53，厚度围绕墙线展开。水平墙长是 `sqrt((x1-x0)^2+(z1-z0)^2)`，不是三维 from/to 的距离。

相接空间的共同界面只建一份物理墙；本来开敞的面不建实墙。墙分段时，门窗必须引用实际承载该洞口的墙段，并重新计算沿墙距离。不要为了挂门窗，另叠一堵同位置墙。

### 5.2 楼板 floor

```json
{"type":"floor","id":"ground_main","from":[-0.12,0.23,5.88],"to":[16.12,0.23,14.12],"thickness":0.22,"material":"stone"}
```

这是矩形板，顶为 `0.23+0.22=0.45`；from/to 的 Y 保持相等，X/Z 确定两个对角点。优先写小坐标到大坐标。

层间板既是下层的顶板，也是上层的地板。同一位置不要重复铺两块实体板。露台板、楼梯平台和室内板要分别确定范围与顶标高。

**挑空和楼梯洞口用实际板片范围留出。** 本文采用矩形拆板：先确定孔洞范围，再把周围板面分成互不重叠的矩形。不能在完整楼板上写“void”或“楼梯洞口”就以为孔洞存在，也不在本文 floor 上发明 holes 字段。

拆板后核对两件事：该有楼面的房间与出口有板支承；该留空的挑空和楼梯路线没有被其他板片覆盖。

### 5.3 平屋面 roof

```json
{"type":"roof","id":"main_roof","roofType":"flat","ridgeAxis":"x","span":17.2,"depth":9.2,"height":0.22,"thickness":0.22,"position":[8,7.05,10],"material":"roof_dark"}
```

本文的 flat roof 用 span 表示 X 覆盖宽，depth 表示 Z 覆盖深，position.y 表示底标高；厚度决定顶面，示例将 height 也写成厚度。平屋顶没有实际屋脊，ridgeAxis 不改变其矩形包络。

例子覆盖 X=[−0.6,16.6]、Z=[5.4,14.6]，底为 7.05，顶为 7.27。不要把 7.05 再减半厚或加半厚。

每个需要封顶的体量都有真实覆盖面。檐口条、雨棚和格栅不能替代整片屋顶。屋面、檐底、边框各自有厚度及位置，避免重复同一表面或无意形成穿插。

可用露台的屋面顶必须与连接门底、踏入露台的楼面一致。例如露台顶为 3.75、厚 0.22，其 roof.position.y 应为 3.53，露台门底为 3.75。

本文详述 flat 屋型。其他屋型不应仅替换 roofType 就沿用平顶定位推论；需另有其明确的输入语义，或用本文基础几何组合表达选定形态。

### 5.4 基础几何 primitive

```json
[
  {"type":"primitive","id":"entry_canopy","shape":"box","position":[8.35,3.02,5.335],"dimensions":[3.1,0.18,1.57],"material":"roof_dark"},
  {"type":"primitive","id":"tree_trunk","shape":"cylinder","position":[-1.7,1.25,4.8],"radiusTop":0.08,"radiusBottom":0.11,"height":2.4,"segments":16,"material":"wood"},
  {"type":"primitive","id":"tree_crown","shape":"sphere","position":[-1.7,2.8,4.8],"radius":1.0,"segments":16,"material":"leaf"}
]
```

box.dimensions 顺序是 `[X宽,Y高,Z深]`。沿 X 的横梁把跨度写入第一项，沿 Z 的横梁把跨度写入第三项；不依赖 description 或自造 orientation 字段改变几何。

柱、梁、框、檐条、橱柜、台阶、花池和植物可由这些基础几何组合。每个零件都要有明确尺寸和材料；不支持的新对象名称不能直接发明成 type。

## 6. 门窗：真实宿主、真实洞口

### 6.1 沿墙坐标

设实际父墙平面起点为 A=(ax,az)，终点为 B=(bx,bz)，长度为 L，单位方向为 u=(ux,uz)。

```text
L  = sqrt((bx-ax)^2 + (bz-az)^2)
u  = [(bx-ax)/L, (bz-az)/L]
n  = [-uz, ux]

door/window.from = [s, y_bottom, d]

洞口沿墙中心的世界位置：
x = ax + ux*(s+width/2) + nx*d
y = y_bottom + height/2
z = az + uz*(s+width/2) + nz*d
```

s 从蓝图中父墙 from 的 X/Z 起点沿 from→to 方向计量，是洞口起点，不是洞口中心；**不额外增加半墙厚**。y_bottom 已是世界 Y，不再加墙底。普通居中安装用 d=0。

若父墙反向，s 的计量方向也反向。门窗放在侧墙时，s 仍是沿墙距离，不能把世界 X 或 Z 生搬进 from[0]。

必须满足：

```text
L > 0
0 <= s
s + width <= L
wall_bottom <= y_bottom
y_bottom + height <= wall_top
```

### 6.2 门 door

```json
{"type":"door","id":"entry_door","parentWall":"front_wall","from":[1.0,0.45,0],"width":1.6,"height":2.4,"frameWidth":0.065,"frameDepth":0.24,"leafDepth":0.035,"frameMaterial":"metal","leafMaterial":"wood","openingStyle":"rectangular","doorStyle":"double","interaction":{"mode":"swing","hingeSide":"left"}}
```

必需字段为 type、id、parentWall、from、width、height。本文采用矩形洞口，doorStyle 用 single 或 double。interaction 为可选开合表达，不是补充门洞或通路的替代品。

### 6.3 窗 window

```json
{"type":"window","id":"living_window","parentWall":"front_wall","from":[3.1,1.1,0],"width":2.3,"height":1.8,"frameWidth":0.055,"frameDepth":0.24,"glassDepth":0.012,"verticalMullions":1,"horizontalMullions":0,"mullionWidth":0.025,"frameMaterial":"metal","glassMaterial":"glass"}
```

verticalMullions 和 horizontalMullions 是内部分格条数，写非负整数；不是窗扇总数。框宽与分格须能放入洞口，门扇或玻璃厚度不应超出框深。示例 frameDepth 与父墙厚度一致。

同一父墙上的两个洞口，其沿墙区间与竖向区间不能同时发生正面积重叠。多个墙 ID 若落在同一物理墙面，也要一起核对，不能利用拆墙命名避开冲突。

隔墙端部、柱、柜体和格栅不得无意穿过已选门窗。通高玻璃可以使用一面通高墙上的大窗；若选了分层墙，则按真实墙段分别设计开口。

**不要另写一个 opening 来重复同一个 door/window 洞口。** 原生门窗组件会形成真实开口；仅在完整墙前摆一块玻璃 box，不会让墙自动消失。

## 7. 楼梯、平台、洞口与栏杆一起设计

### 7.1 单个直梯段 stair

```json
{"type":"stair","id":"stair_first","from":[13.3,0.45,9.6],"to":[13.3,2.1,12.3],"width":1.2,"stepCount":10,"stepDepth":0.27,"stepHeight":0.165,"material":"wood"}
```

from/to 是路线起止点及起终标高，水平路线是梯段中心线。本文每跑明确填写整数 stepCount、正数 stepDepth、stepHeight，不能依赖未知默认值。

本表达的数值一致性：

```text
升高 = to.y - from.y = stepCount * stepHeight
行程 = sqrt((to.x-from.x)^2 + (to.z-from.z)^2)
     = stepCount * stepDepth
```

这里使用 N 个踏步与 N×步深的输入约定，不混用另一种 N−1 个步深的算法。需要下行时，仍从较低楼面向较高楼面定义梯段。

### 7.2 双跑与平台

两跑分别用 stair 表达，中间平台用 floor 表达；平台不是自动生成的。第二跑起点接平台顶，终点接上层楼面顶。

在上层楼板拆出真实洞口。洞口应包含本次楼梯需穿越楼板的部分，并保留足够的实际路线净空。只检查终点有板还不够，要检查沿途踏步与上方板底、梁底的关系。

梯段出口不能被隔墙、栏杆、家具或完整楼板封住。不同楼梯形式应重新确定占地和转向，不给所有项目强套 U 形。

### 7.3 栏杆 railing

```json
{"type":"railing","id":"terrace_guard","path":[[10.04,3.75,5.65],[10.04,3.75,0.12],[15.96,3.75,0.12],[15.96,3.75,5.65]],"height":1.08,"postSpacing":1.15,"postRadius":0.017,"railRadius":0.019,"railLevels":[1],"material":"metal","infillType":"glass","infillThickness":0.012,"infillTopRatio":0.94,"infillMaterial":"glass"}
```

path 至少两个不同点，本文使用世界坐标，不填写 parentFloor。railLevels 是相对 height 的比例，位于 (0,1]；`[1]` 只有顶扶手。infillType 可省略，或者写 glass/panel；infillMaterial 与栏杆框料分开引用。

楼梯栏杆基线可随梯段升高。露台和洞口防护按实际临空边安排；路径端点不会自动闭合，只有确实需要闭合时才回到起点。入口与楼梯到达口必须留出通行缺口。

本文示例栏杆高度、步高和宽度仅描述视觉设计，不代表已满足所在地规范。

## 8. 家具、景观和照明

### 8.1 家具 furniture

```json
{"type":"furniture","id":"living_sofa","subtype":"sofa","position":[3,0.45,10.6],"rotation":[0,3.141593,0],"dimensions":{"width":3.5,"depth":1.0,"height":0.86},"material":"fabric"}
```

本文可用 subtype：table、chair、sofa、bookshelf、bed、wardrobe、nightstand、tv_cabinet、lamp、tile。其他对象可以由基础几何表达，不自造 furniture 子类型。

dimensions 是 width/depth/height 对象，不是 box 的三元素数组。position 是底面中心，家具落在首层地面时 Y=首层楼面顶，不再加半高。

chair/sofa 默认面向局部 +Z、靠背在 −Z；绕 Y 旋转后面向 `[sin(θ),cos(θ)]` 的世界 X/Z 方向。不能让所有椅子默认同向，而声称已经围桌。

柜体、餐桌、床、沙发先按功能组织。摆放后核对：

- 入口和主要路线有连续通路，家具不会占住门洞、楼梯出口或必要转身位置。
- 高柜与窗洞比较平面投影和竖向区间；不是所有家具都不能临窗，但不能无意遮住本次要保留的玻璃。
- 椅子面对桌面或交谈方向，床和柜有合理的使用面。
- 家具底部有板支承；上层家具不落进挑空或楼梯洞口。

旋转后不能继续用未旋转的宽深估计占地。仅绕 Y 旋转的矩形，其世界轴包围尺寸为：

```text
X_extent = abs(width*cosθ) + abs(depth*sinθ)
Z_extent = abs(width*sinθ) + abs(depth*cosθ)
```

该包围框适合筛选潜在冲突；旋转物体包围框相交并不必然是实体相交。

### 8.2 景观与配套

庭院平台、路径、草地、水面、花池和植物服从入口、视线与活动区。按功能需要采用，不强制每栋别墅都带水池。

景观的地面顶与室内楼面顶有高差时，设计实际台阶或坡道连接；不要出现可以看见入口却走不到入口的台地。用 box 表达台阶时，高度可逐级变化，所有落点仍从同一地面标高计算。

浅池可由池底、池壁和薄水面组合，平台围绕其范围安排。水面可用透射材质作视觉近似，这不表示支持流体或游泳设施。植物可用圆柱树干与球体冠幅组合，不依赖未提供的外部模型。

### 8.3 灯光 light

```json
{"type":"light","id":"living_light","position":[3,3.0,9],"body":[{"shape":"sphere","radius":0.08,"material":"warm_light"}],"lightType":"point","color":[1,0.86,0.67],"lowIntensity":2,"highIntensity":12,"distance":8,"initiallyOn":true}
```

light 位于 components。position 为世界安装位置；body 是灯体几何数组，局部段不写 type/id。body 段**省略 position 时继承灯的世界位置；显式填写时也是世界坐标，不是灯下的相对偏移**。不要把每段 position 都写 [0,0,0]，除非确实要把灯体放在世界原点。

本文 body 只使用 box、sphere、cylinder。lightType 用 point 或 spot；lowIntensity、highIntensity、distance 为正数，highIntensity≥lowIntensity。spot 的 angle 单位是度，范围大于 0 且不超过 90，与 rotation 的弧度不同。

emissive 材质只表达表面自发光，不代替 light 的实际光源。有限地安排基础照明与重点照明，不用大量灯掩盖材料或构图问题。

## 10. 生成顺序与数值计算

### 10.1 先形成简明设计账本

在中间草稿中列出：需求、体量范围、逐层楼面顶、各墙段、洞口宿主、楼梯路线、板洞、屋面、主要材料以及需要保留的特征。它用于关联计算，不必加入最终 JSON。

每项关键关系写成可计算的记录，例如：

| 关系 | 需要绑定的数据 |
|---|---|
| 露台可达 | 露台顶、连接门底、室内楼面顶、门外落脚板范围 |
| 双跑连续 | 起层、平台、终层标高与两跑起终点 |
| 通高成立 | 空洞平面范围、上层板片范围、上方屋面范围 |
| 开口安装 | 实际父墙 ID、墙线方向、沿墙起点、洞口宽高 |
| 廊架相接 | 柱底/顶、梁底/顶、格栅底/顶及整体平面边界 |

### 10.2 再展开实际实体

建议依赖顺序：材料表 → 场地和地基 → 地面与层间板 → 外墙与内墙 → 门窗 → 屋面 → 楼梯和平台 → 防护 → 檐口、雨棚和格栅 → 家具 → 景观与灯。

楼板、洞口和楼梯应在设计时一起确定，上述书写顺序不表示先铺完整板，最后才猜哪里拆洞。

有计算工具时，使用普通 Python/JavaScript 的变量、公式、循环和 JSON 序列化，最后读取实际写出的 JSON。不要依赖 WildAgent 私有的 program 执行器。重复构件用稳定编号展开：

```text
若有 N 根等距条，中心起点 c0、中心终点 c1：
N=1 时中心为所选单点；N>1 时 spacing=(c1-c0)/(N-1)
第 i 根中心 = c0 + i*spacing，i=0..N-1
条的外边界还需考虑半厚度，不能只检查中心线。
```

没有代码工具时，仍用同一套参数计算并输出完整 JSON，不能声称已经运行过检查。输出长度不足时先说明需要分段或文件工具；不得悄悄删掉已选系统，也不能把截断 JSON 宣称为完整文件。

## 11. 交付前复核实际结果

复核对象是**准备交付的 JSON**，不是设计说明或较早的草稿。

### 11.1 格式与引用

1. 根字段与集合位置正确，所有实体 ID 唯一，JSON 完整。
2. 每个材料引用已定义；每个门窗 parentWall 存在且确为 wall。
3. 尺寸与需要为正的参数为有限正数；向量长度和字段类型正确。
4. 没有中间图纸字段、伪构件类型、内部派生字段或未展开模板。

### 11.2 建筑关系

1. 地面、楼层、平台、门槛和露台的标高接得上。
2. 屋面确实覆盖所选体量；不是只剩屋檐边条。
3. 挑空和梯井确实留空，上层房间及梯段出口有实际楼板支承。
4. 梯段步数、升高和行程一致，平台相接；上方板、梁与路线的净空已核对。
5. 门窗在父墙范围内，物理同面洞口不重叠，隔墙和柱不穿洞。
6. 主次体量交接不重复建墙，不因某一面开敞就误删相邻空间需要的围护。
7. 防护覆盖需要的临空边，同时没有封死出入口。

### 11.3 使用与观感

1. 从入口能到主要空间、楼梯和露台；不是只有门的几何，没有连续路线。
2. 家具不占门洞或梯口；高柜与窗的高度、位置及用途协调。
3. 材料确实分配到实体；玻璃透明参数、框料、板厚、檐底等有实际表达。
4. 格栅、梁、柱没有因半厚度计算错误而悬空或无意穿插。
5. 可视重点与用户要求一致；没有为了通过格式检查而把已选形制全部简化掉。

发现问题时，列出具体对象及实际值，只修改相关数据，并联动受影响的实体。例如改变楼面顶，就检查楼板、门底、家具、梯段和栏杆；不能只改一处文字。

有对应工具时，可进一步运行 JSON Schema、引用、几何和引擎检查，并渲染主立面、侧面、俯视及透视。没有执行就不写“已通过”；文本复核、程序检查、引擎可构建与视觉确认应分别说明。

## 12. “庭光别墅”参考任务与参数

### 12.1 可直接复制的任务
