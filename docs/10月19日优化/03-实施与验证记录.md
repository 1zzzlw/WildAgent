# 10 月 19 日实施与验证记录

本轮将“整体设计、程序计算、读取实际产物、空间使用复核”接入现有流程。低粒度真实生成及引擎渲染通过，保存的模型程序也能实际运行并接受生产校验。**尚不能证明 Agent 已稳定达到手工“庭光别墅”的效果：两次高粒度试跑均超时，没有完整高粒度建筑可作效果验收。**

## 1. 实施边界

用户允许优化知识库、设计图纸与代码，要求及时清理被替代代码，临时测试文件用完删除；节点改动需先商量。本轮保留现有节点、职责和路由，在内部增加计算与复核能力，没有新增、删除或重分配节点，没有增加修订次数，没有修改 `.env`。

现有流程仍是 `architecture → material_plan → design_review → plan → execute / replanner → compile → final_validate`。建筑分支的 plan 仍确定性拆分任务，不调用模型；构件研究和实现仍在 execute。

## 2. 实际迁移的能力

### 2.1 设计选择和共享数值

architecture 按需求与形制、体量与标高、功能交通、围护开口、屋面附属、材料表达组织完整图纸。规则与粒度仍由 RAG 提供，没有将整栋参考别墅放进每次生成的提示词。

在既有 circulation 中增加可选 `paths`，由本次设计明确通路的楼层、世界 X/Z 折线、净宽和净高。宽高取自设计，不是写死的建筑规范；未选择该表达时不自动增加通路。

`design_document` 仍保存展开后的批准设计，`architecture_plan` 仍为兼容投影。程序不是新的设计主数据。

### 2.2 模型可以提交程序，系统执行计算

共享入口：[generation/program.py](../../wild-server/app/agent/generation/program.py)。

| 阶段 | 模型回复 | 实际结果 | 接下来的检查 |
|---|---|---|---|
| architecture | 完整设计 JSON，或仅含 `program` 的对象 | 程序从变量和公式生成完整图纸字典 | 原图纸契约、关系检查与审核 |
| execute | `implementations` 中直接几何，或每项 `program` | 程序生成原有 geometry/materials/assets 片段 | 原宿主、材料、所有权、尺寸、设计关系及候选检查 |

例如，模型可用同一组楼层标高计算构件中心，用循环展开遮阳片，而不必心算并逐项抄写。辅助输出函数只提供 element、component、material、box、slab、opening 等低层表达，没有 `make_villa()` 或固定庭院、家具套餐。

程序在独立 Python 进程内解释有限语法，不使用 eval/exec，也不提供导入、文件和网络能力。输入及嵌套对象只读；模型自己创建的局部列表、字典可以 append/extend/update。支持有限循环、推导式、函数和数值计算。

当前限制包括源码 40,000 字符、语法树 12,000 节点、计算 50,000 步、实体 4,096 个、累计赋值和容器操作数据 16 MB、输入输出各 4 MB、进程 5 秒。数据限额不等于操作系统进程 RSS 硬限制；此入口也不是任意 Python 的通用沙箱。

追踪保存源码、输入/输出 hash、步数、输出模式及采用结果。计算本身不额外调用模型；失败沿原任务修订次数报告，不套默认建筑。已取得完整草稿后，设计格式修订仍提交 operations 局部补丁。

### 2.3 根据真实实体复核空间使用

共享入口：[spatial_review.py](../../wild-server/app/design/spatial_review.py)。局部片段采纳、完整候选检查和最终交付使用同一套实际实体解释。

- 通路核对直墙、矩形实体及仅绕 Y 旋转的家具；穿墙处扣除净宽高足够的真实 door/opening，避免把有门的墙判成整面阻挡。
- 家具物理侵入门洞时给出具体对象和错误；近窗家具的沿墙和高度投影重叠作为可能遮挡的观察，不当作强制移动家具的规范。
- 原生 furniture 的 position 按底面中心解释，图纸 position 按整体中心解释；尺寸与中心核对不依赖家具名称恰好出现在目录中。
- 不支持的旋转、未知组合和其他形态列为待复核。检查不证明路面支承、弯角完整净空、任意网格碰撞或专业规范。

compile 可以在原有一次集中修订机会内处理空间观察。采纳时需保留已有实体 ID、批准几何和已满足的设计，不得引入新错误或新观察。仅有观察而修订失败时，保留原有效建筑并记录未解决事项；不会把“可能遮挡”伪装成模型已修好。

### 2.4 上下文和失败语义

execute 获得图纸版本、相关楼层和平面、通路及附近已采用的真实几何；同时保留相关宿主和开口。附近筛选范围只用于上下文检索，不成为建筑尺寸标准。

材质模型调用失败、未返回有效角色时，现在明确报告失败，不再以固定材质结果冒充模型成功。合法的已有材质复用和无设计路径不受此改动影响。

## 3. 真实运行暴露并修复的问题

| 证据 | 根因 | 本轮处理 | 验证方式 |
|---|---|---|---|
| 真实构件程序修订返回 `material(...)` 的结果作为材质引用 | helper 原先返回 None | material 返回实际材质 ID；显式材质参数优先 | 回放同一真实回复，进入原片段验收后通过 |
| 回复仅定义一个 `implement(ctx)` 函数 | 没有顶层调用，未生成实体 | 单一入口函数可自动调用；多函数仍须明确入口 | 同一真实回复回放通过 |
| 真实设计程序以 `components.append(...)` 构造列表 | 有限解释器缺少常用局部容器操作 | 支持局部 append/extend/update，保留嵌套输入只读 | 首次真实设计程序展开并通过图纸契约；4 个输入变更反例被拒绝 |
| 高粒度格式修订仍长时间思考 | 首次设计与格式修订共用 thinking 开关 | 只有首次设计可深度思考，后续格式修订关闭 | 生产函数回放观测到 `[True, False]`，原次数不变 |
| program 回复误报缺少 massing | JSON 提取入口只认展开的图纸根 | 支持 massing/program 两种根，后续分别验收 | 同一保存输出正确解析 |
| 维护命令触发多份 Loader 和后台同步 | 导入全局服务后又创建第二个服务 | 复用单例，当前维护进程只主动同步一次 | 正常增量同步成功，未重建集合 |

原始构件程序第一次把中心 Y 从 1.05 写成 1.65，修复 helper 后仍被拒绝；没有为了成功扩大容差或忽略中心错误。

## 6. 10 月 20 日：主体程序语法与修订上下文修复

最新记录为 `session_1792454139954 / req_1792454141883_fcs4ugfi5`，用户需求为“生成一个别墅”。主体三次尝试依次失败于 Python 第 31 行语法、程序字符串的 JSON 未转义换行、Python 第 27 行语法；两次 Python 错误均包含非法的 `from=` 实参。模型调用正常结束，主体没有生成实体，后续附属构件因此停止。

本次修正程序说明：WILD 的 from 字段通过 `**{'from': start, 'to': end}` 字典展开传入，不写 `from=` 或擅自改名为 from_。设计与构件程序共用 JSON 源码转义说明。语法错误反馈增加行、列和实际错误代码；发现 from= 时给出对应说明。JSON 控制字符错误明确指出换行和制表符的转义要求。

同时补足修订上下文：程序执行失败时，完整的未采用 program 保存在既有 failed_implementations 中，下一次修订能读取原稿；此前仅传错误文本，原程序没有进入该上下文。

节点、执行语法限制、几何校验及修订次数不变。没有自动改写错误程序或宽松解析非法 JSON；失败仍如实报告。本次按用户要求仅修改代码与记录，未执行测试、回放、构建或真实生成，修复效果由用户验证。
