# WildAgent RAG 知识文档 Skill 制作提示词

> 用途：将本文完整交给 AI，让其创建一个专门用于编写、审查和重构 WildAgent RAG 知识文档的 Skill。
>
> 目标不是让 Skill 负责向量入库，而是让它产出“天然适合语义分片、向量检索和模型生成”的 Markdown 知识文档，并在写入知识库前发现规范冲突和未经证实的字段。

---

## 可直接交给 AI 的提示词

你需要为我的 WildAgent 项目创建一个可复用 Skill，建议命名为：

```text
wild-rag-doc-author
```

这个 Skill 用于编写、补充、重构和审查 WildAgent 的 RAG 知识库 Markdown 文档。请先阅读我提供的知识库目录说明、蓝图规范、构件文档和相关源码，再按照下面的要求设计和实现 Skill。

不要只生成一份通用 Markdown 写作规范。这个 Skill 必须理解 WildAgent 知识库的业务分类、WILD 蓝图约束、语义分片方式和事实来源优先级，能够阻止不受渲染引擎支持的字段进入知识库。

### 一、项目背景

WildAgent 的主要链路是：

```text
用户自然语言
→ 检索 RAG 知识
→ AI 生成或修改 WILD 蓝图
→ 确定性工具校验
→ 前端解析
→ wild-core / Three.js 渲染
```

知识库目前包含以下类型：

| 路径或文件 | 职责 |
|---|---|
| `BLUEPRINT-SPEC-MINIMAL.md` | 稳定且最重要的蓝图铁律，直接注入 System Prompt，不参与普通 RAG 扫描 |
| `BLUEPRINT-SPEC-FULL.md` | 完整 WILD 表达规范，参与 RAG |
| `building_types/catalog/` | 用户只描述“别墅、木屋、凉亭”等名称时的轻量默认入口 |
| `building_types/` | 按建筑用途或类型组织的构件配方 |
| `components/` | 墙、门、窗、屋顶等构件族的参数、变体和组装规则 |
| `recipes/` | 跨构件组合方式、建筑配方和速查矩阵 |
| `patterns/` | 用户确认过的案例、偏好和可复用模式 |
| 各级 `README.md` | 导航和目录说明，默认不应作为高权重生成知识 |

当前 RAG 大致采用：

```text
Markdown 标题分片
→ 超长片段按长度继续分片
→ 合并过短片段
→ embedding
→ 写入向量数据库
```

Skill 生成的文档必须适配这个流程，同时指出现有分片器无法安全处理的结构。

### 二、Skill 的触发场景

请在 Skill 的 `description` 中覆盖以下触发方式：

- 用户要求为 WildAgent 新增门、窗、墙、楼梯、屋顶、家具等构件知识；
- 用户要求新增建筑类型、建筑配方、组装规则或项目模式；
- 用户要求修改、整理、拆分或审查现有 RAG Markdown；
- 用户要求判断一份知识文档是否适合向量检索；
- 用户要求检查文档中的 WILD 字段是否得到源码或规范支持；
- 用户要求把零散研究材料整理成可入库的 WildAgent 知识；
- 用户要求优化标题、元数据、知识粒度、示例或检索关键词。

### 三、核心原则

#### 1. 先验证事实，再改善表达

每次编写或修改文档前，必须确认相关字段、构件类型、坐标含义和引用关系是否被当前版本的渲染引擎、Schema、类型定义或校验代码支持。

事实来源优先级必须固定为：

```text
当前渲染引擎源码 / Schema / 类型定义 / 校验代码
> 当前版本的完整 WILD 规范
> 已通过渲染和校验的 WILD 样例
> 项目维护者确认的规则
> 建筑领域资料
> AI 推断
```

低优先级资料不能覆盖高优先级事实。发现冲突时，不得静默选择其中一种写入正文，必须列出：

- 冲突内容；
- 各自来源；
- 当前可信结论；
- 仍需用户或源码确认的部分；
- 对现有 RAG 的可能影响。

未经源码或规范验证的能力必须标记为：

```text
status: proposed
```

不得把它写成当前已经支持的 WILD 语法。

#### 2. 一个知识块解决一个完整问题

不要以固定字符数作为第一分片依据。优先按照业务语义划分：

- 一个构件类型；
- 一个构件变体；
- 一条完整约束；
- 一个坐标规则；
- 一种跨构件组装配方；
- 一个经过验证的案例；
- 一个常见错误及其修复方式。

每个知识块应尽量能够独立回答一个问题。例如：

```text
如何用 WILD 表达落地窗？
opening 的 from[0] 表示什么？
中式支摘窗由哪些子构件组成？
屋顶覆盖范围如何校验？
```

不要把“落地窗参数”的前半部分和“落地窗约束”的后半部分机械分开，也不要把门和窗因为片段过短而合并。

#### 3. 标题必须真实表达分片边界

Markdown 标题是当前分片器识别语义层级的主要依据，因此：

- `#`：一个文档的领域主题；
- `##`：一个可独立检索的业务实体或规范大类；
- `###`：该实体下的独立知识主题；
- `####`：具体变体、规则、错误或示例。

禁止使用下面这种仅靠粗体模拟标题的方式：

```md
**A. 直棂窗**
**B. 槛窗**
**C. 支摘窗**
```

应改为真实标题：

```md
#### 直棂窗
#### 槛窗
#### 支摘窗
```

如果“直棂窗”本身已经很长，可以继续拆成：

```md
#### 直棂窗
##### 定义与适用场景
##### WILD 组装规则
##### 参数与空间约束
##### 最小有效示例
##### 常见错误
```

标题文字必须包含实体名称，避免大量同名的“参数说明”“示例”“注意事项”失去父级上下文。

#### 4. 标题路径必须进入片段上下文

生成的每个分片都必须保留或重建完整标题路径，例如：

```text
components / 窗构件 / 中式传统窗 / 支摘窗 / 参数与空间约束
```

如果实际分片器会去除标题，Skill 必须提示调用方：

- 设置 `strip_headers=False`；或
- 在 `page_content` 前重新拼接标题路径；或
- 把完整标题路径存入 metadata，并在召回后重新注入内容。

#### 5. 长度分片只能作为兜底

推荐决策顺序：

```text
业务实体分块
→ 标题主题分块
→ 判断片段是否超长
→ 优先按子标题或自然段继续拆
→ 最后才使用递归长度分片
```

不得无条件对每个标题块再次按固定长度切割。

如果必须长度切分：

- 不要切断 JSON、表格、公式、字段定义和对应解释；
- 不要让示例与它所证明的规则彻底分离；
- 子片段必须继承完整 metadata 和标题路径；
- overlap 只用于维持相邻语义，不得依赖 overlap 修复错误的文档结构；
- 应记录 `parent_chunk_id` 和 `part_index`。

#### 6. 小片段只能在同一语义父级内合并

允许合并：

- 同一个窗型下连续且共同回答一个问题的两个短段落；
- 同一条约束的说明、公式和极短示例；
- 相同实体、主题、版本和可信等级下的相邻内容。

禁止合并：

- 门与窗；
- 两种不同窗型；
- 当前支持能力与未来提案；
- Schema 定义与建筑风格推荐；
- 两个不同 WILD 版本；
- 来源可信等级不同且可能冲突的内容。

合并前至少检查以下字段一致：

```text
doc_type
knowledge_layer
entity_type
entity_name
topic
wild_version
status
authority
parent_id
```

#### 7. 不要让导航文档污染生成知识

`README.md`、目录索引、Mermaid 思维导图和超大分类总表主要用于人类导航，不应默认与精确 WILD 规则使用相同权重进入向量检索。

Skill 应根据当前项目能力选择以下一种处理：

- 从普通 RAG 扫描中排除导航 README；
- 设置 `doc_scope=index` 和较低检索优先级；
- 仅把其中每个建筑类型的轻量摘要转化为独立 catalog 文档；
- 不把大型 Mermaid 源码作为核心 embedding 内容。

### 四、统一元数据规范

Skill 应要求每个准备入库的知识单元携带结构化元数据。具体格式可以根据现有 Chroma 入库代码调整，但语义至少包括：

```yaml
doc_type: component | building_type | recipe | blueprint_spec | pattern
knowledge_layer: architecture | constraint | wild_schema | project_pattern
entity_type: window | opening | wall | roof | stair | building | material
entity_name: floor_to_ceiling_window
topic: definition | schema | parameters | constraints | assembly | example | error
wild_version: "1.1"
status: supported | experimental | proposed | deprecated
authority: engine | schema | verified_example | maintainer | domain_reference | inferred
source: 相对文件路径或源码位置
parent_id: 可选的父知识块 ID
keywords:
  - 落地窗
  - floor-to-ceiling window
  - opening
  - window
```

说明：

- metadata 用于过滤、追踪、父子关联和冲突处理；
- metadata 不能替代正文，正文仍须自包含；
- `keywords` 用于补充中英文别名和 WILD 字段名；
- `status=proposed` 的内容默认不得用于正式蓝图生成；
- `authority=inferred` 的内容必须明确告诉用户尚未验证。

### 五、不同文档类型使用不同模板

不要强迫所有文档都使用同一个“适用范围—构件清单—参数建议—组装规则”模板。

#### A. WILD Schema / 蓝图规范

```md
# WILD `<type>` 规范

> 用途：
> 适用版本：
> 事实来源：
> RAG 关键词：

## 定义与能力边界

## 最小字段集合

## 字段说明

## 坐标与引用规则

## 约束与校验

## 最小有效 JSON

## 常见错误与错误 JSON

## 与其他构件的关系
```

#### B. 构件族文档

```md
# `<构件族>` 分类与组装规则

> 用途：
> 适用版本：
> 事实来源：
> RAG 关键词：

## 构件族定义

## 当前引擎能力边界

## `<具体变体一>`

### 定义与适用场景

### 所需 WILD 构件

### 参数与空间约束

### 最小有效 JSON

### 常见错误

## `<具体变体二>`
```

每个具体变体必须使用真实标题，能够成为独立语义块。

#### C. 建筑类型文档

```md
# `<建筑类型>` 默认生成配方

> 用途：
> 适用版本：
> 事实来源：
> RAG 关键词：

## 默认语义

## 最小构件集合

## 推荐尺寸与比例

## 构件组合顺序

## 风格变体

## 最少可行蓝图

## 必须校验的约束

## 不支持或需要降级的能力
```

#### D. 跨构件 Recipe

```md
# `<配方名称>`

> 目标：
> 输入条件：
> 输出构件：
> 适用版本：
> 事实来源：

## 前置条件

## 组装步骤

## 参数关系

## 最小有效示例

## 验证清单

## 失败与降级方式
```

#### E. Pattern / 已确认案例

```md
# `<模式名称>`

> 来源会话或项目：
> 用户确认状态：
> 适用范围：
> 适用版本：

## 用户目标

## 可复用决策

## 蓝图摘要

## 不应泛化的内容

## 已验证结果
```

### 六、JSON 示例规则

所有标记为“有效”的 JSON 必须：

- 是严格 JSON，不能包含 `//` 或 `/* */` 注释；
- 字段必须被当前版本 Schema 或源码支持；
- 所有引用的 `parentWall`、`parentOpening`、材质 ID 等必须存在；
- 示例本身能通过已有确定性校验工具；
- 示例中的尺寸和坐标必须与文字说明一致；
- 如果只展示 `geometry.elements` 的片段，明确注明“片段，不是完整 `.wild` 文件”；
- 错误示例必须明确标记为错误，禁止与正确示例混在同一个代码块中；
- 不得为了说明建筑概念而发明 WILD 字段。

如果源码暂不支持某种建筑构件，使用以下表达：

```md
当前能力：不支持直接表达。
可用降级：使用现有 primitive 或多个受支持构件近似组合。
未来提案：字段或类型仅作为设计建议，不进入正式生成知识。
```

### 七、每次执行 Skill 的工作流

#### 步骤 1：识别任务

判断用户是在：

- 新建知识文档；
- 修改已有文档；
- 把资料转换为 RAG 文档；
- 审查事实一致性；
- 优化分片结构；
- 设计目录或元数据。

#### 步骤 2：确定文档类型

在 `component / building_type / recipe / blueprint_spec / pattern` 中选择。无法判断时只询问一个最关键的问题。

#### 步骤 3：读取必要事实来源

按事实优先级读取与本次主题直接相关的源码、Schema、完整规范和已验证样例。不要为了写一个窗型文档而加载全部无关建筑知识。

#### 步骤 4：执行冲突审查

制作内部事实表：

| 声明 | 来源 | 可信等级 | 是否支持 | 处理 |
|---|---|---|---|---|

发现冲突先报告，不能把冲突内容直接润色成确定事实。

#### 步骤 5：规划语义知识块

在写正文前列出预期 chunk：

| chunk_id | 标题路径 | 回答的问题 | 预计长度 | 父块 | metadata |
|---|---|---|---:|---|---|

如果一个片段回答多个相互独立的问题，继续拆分；如果一个片段无法独立理解，补充标题路径和必要上下文。

#### 步骤 6：按对应模板编写

优先生成最小、正确、自包含的内容。避免重复粘贴完整 Schema；需要引用时使用精简字段表，并保留事实来源。

#### 步骤 7：执行 RAG 就绪检查

逐项检查：

- 标题是否真实对应语义边界；
- 是否存在粗体伪标题；
- 每个块是否能独立回答一个检索问题；
- 标题被移除后是否仍能识别实体；
- 是否有跨实体的小片段合并风险；
- JSON 是否会被长度分片切断；
- metadata 是否足够过滤版本和状态；
- 是否存在相互冲突的重复规则；
- 导航内容是否可能抢占 top-k；
- 关键词是否同时覆盖中文名、英文名和 WILD 字段名。

#### 步骤 8：输出结果

输出顺序固定为：

1. 新建或修改后的 Markdown；
2. 冲突与待确认项；
3. 建议的 chunk 清单；
4. 建议 metadata；
5. RAG 就绪检查结果；
6. 对现有分片器的必要调整建议。

### 八、对当前样例必须特别检查的问题

在使用我提供的现有文件进行第一次测试时，至少检查：

1. `components/windows.md` 中具体窗型使用粗体 A/B/C，而不是 Markdown 标题，标题分片器不能识别；
2. “中式传统窗”“欧式古典窗”“现代窗”章节过长，可能在 JSON 或单个窗型中间被长度切断；
3. `window`、`mullion`、`cornice`、`railing` 等类型是否在当前引擎和 Schema 中真实存在；
4. `opening.parentRoof` 是否受到当前实现支持，还是与 `parentWall` 必填规则冲突；
5. `opening.material` 在规范中标记为必需，但多个示例中缺失；
6. `style`、`sashType`、`patternName` 等枚举是否有当前源码依据；
7. 示例代码块含 JSON 注释，是否会让解析器误认为是可直接使用的严格 JSON；
8. `README.md` 和大型 Mermaid 分类图是否应该进入普通生成检索；
9. `BLUEPRINT-SPEC-FULL.md` 中同一章节同时包含 Schema、坐标解释、正确示例和错误示例，是否需要按问题拆成父子知识块；
10. 重复出现的开口坐标规则是否内容完全一致，避免多个版本同时召回。

### 九、建议的 Skill 文件结构

遵循 Skill 的渐进披露原则，保持 `SKILL.md` 精简，不要建立无用的 README。

```text
wild-rag-doc-author/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── document-templates.md
│   ├── metadata-schema.md
│   └── rag-readiness-checklist.md
└── scripts/
    └── lint_wild_rag_docs.py
```

各文件职责：

- `SKILL.md`：触发条件、事实优先级、核心工作流、何时读取哪个 reference；
- `document-templates.md`：五类文档模板和少量正确示例；
- `metadata-schema.md`：metadata 字段、允许值、父子块关系和合并条件；
- `rag-readiness-checklist.md`：分片就绪、冲突、JSON、标题和导航污染检查；
- `lint_wild_rag_docs.py`：只做可确定的静态检查，不负责判断建筑知识真伪。

脚本建议检查：

- 粗体伪标题；
- 标题层级跳跃；
- 重复标题；
- 超长标题块；
- 过短且可能被错误合并的标题块；
- JSON 代码块能否解析；
- JSON 中的注释；
- 缺少来源、用途、版本或关键词；
- `status=proposed` 是否被写成当前支持能力；
- metadata 必填项是否缺失。

不要在脚本中硬编码未经源码确认的 WILD 类型和字段；如需校验允许值，应从当前 Schema、类型定义或独立配置中读取。

### 十、验收用例

创建完成后，至少使用以下任务验证 Skill：

#### 用例 1：重构窗构件文档

```text
请使用该 Skill 审查并重构 windows.md，使每一种窗型都能被标题分片器识别，并检查示例字段是否受当前 WILD 引擎支持。
```

合格结果：

- 具体窗型成为真实标题；
- 不会把两个窗型合并成一个知识块；
- 未验证字段不会被当成正式语法；
- 正确 JSON 可以解析；
- 输出 chunk 规划和冲突清单。

#### 用例 2：新增建筑类型

```text
请使用该 Skill 编写“现代木屋”的 RAG 建筑类型文档。
```

合格结果：

- 使用 building_type 模板；
- 区分默认语义、构件配方、约束和最小蓝图；
- 不发明引擎不支持的构件；
- 每个 chunk 可独立检索。

#### 用例 3：审查蓝图规范

```text
请使用该 Skill 检查 BLUEPRINT-SPEC-FULL.md 的 opening 章节是否适合当前标题加长度分片策略。
```

合格结果：

- 识别坐标规则、字段表、示例和错误案例的不同检索意图；
- 给出父子块或子标题拆分方案；
- 保持核心坐标规则一致；
- 不仅建议修改 `chunk_size`。

#### 用例 4：阻止幻觉字段

```text
请使用该 Skill 把一篇建筑资料整理成“玫瑰窗”知识文档，资料中包含当前 WILD 不支持的彩色玻璃和复杂放射窗棂字段。
```

合格结果：

- 先查当前源码或 Schema；
- 将受支持内容、近似降级方案和未来提案分开；
- 不把研究资料中的概念直接转换为虚构字段。

### 十一、创建和验证要求

- 按正式 Skill 创建流程初始化；
- `SKILL.md` 只保留必要工作流，详细模板放入 references；
- 所有指令使用清晰的命令式表达；
- 脚本必须实际运行测试；
- 对上述验收用例进行前向测试；
- 如果输入文档与源码冲突，Skill 必须停下来报告，不能自行“补全”；
- 创建完成后说明 Skill 的适用范围、文件结构和验证结果。

最终目标：

> 让 AI 编写出来的每一份 WildAgent 知识文档，在事实层面受当前引擎约束，在结构层面天然对应语义知识块，在检索层面能够被准确召回，在生成层面不会因为上下文混杂或虚构字段而输出不可渲染的建筑蓝图。
