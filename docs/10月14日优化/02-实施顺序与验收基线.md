# 实施顺序与验收基线

以下是后续实施建议，不表示本次已修改代码或执行验收。范围始终围绕当前建筑主线，优先复用现有函数、状态字段、测试和诊断设施。

## 1. 第一阶段：先让失败原因与成功标准可信

对应 A1、A2、A3、A6 的最小部分。

| 顺序 | 改动范围 | 完成标准 |
|---|---|---|
| 1 | 核对当前未提交楼梯修复，运行既有相关回归 | 老图纸的高差矛盾在审核前明确报出；合法三层、入口台阶、屋面通行不被误拒绝 |
| 2 | 现有设计入口中的连接/宿主/支承关系契约 | 对可计算矛盾返回设计路径与数值，禁止批准后静默改尺寸 |
| 3 | 标记落实与任务结束的展示/统计 | “落实 0，舍弃 1”不再被业务指标解读成该构件成功 |
| 4 | 修订归属与失败候选无进展记录 | 同设计、同宿主、同失败几何不反复当新进展；归属失败不默认重做主体 |
| 5 | 运行版本与逐调用任务/stage 关联 | 每次生成能知道用的代码、设计、模型配置和提示词输入版本 |

针对本次失败样本，先用保存数据验证“错误图纸会被提前识别”，再让设计阶段重新产出一致方案，经审核后做新生成。不能只修改旧 Blueprint 的楼梯坐标后宣布主线稳定。

局部源码入口：`coordinates.py`、`architecture/workflow.py`、`plan/implementation.py`、`validation/issues.py`、`design_flow/compile.py`、`markers.py`、`rag/trace.py`。若已有字段能表达结论，优先使用已有字段。

## 2. 第二阶段：使一次正确实现更容易

对应 A4、A5、A8。

1. 收敛设计事实：标高、宿主方向、相对/世界坐标转换、原生尺寸映射各有一个权威计算入口。
2. 提示词保留设计意图、任务边界、输出协议和当前关系，按类型注入适用规则。知识库提供构造参考，实际尺度来自批准图纸。
3. 对已有原生构件与组合构件采用一致的关系验收；不能只对原生参数检查尺寸、组合后就默认落实。
4. 测量批次输入/输出，再对大批次按宿主、楼层和依赖拆分；保留低档同类门窗合批收益。
5. RAG 返回本次调用的独立结果，再调整异步执行。并发不破坏来源归属、材料资源和实体所有权。
6. 若剖析证实局部验收反复计算同一 `implementation_errors(base)` 是热点，再按精确候选指纹复用只读结果。任何缓存都必须随依赖、Schema 和校验版本失效；不能绕过最终完整校验。

不设置“必须减少多少行代码”的虚假目标；真正衡量规则是否重复、同一事实是否被不同模块重新解释，以及修改一种关系是否需要改四五份互不校验的约定。

## 3. 第三阶段：用可复现基线证明低档稳定

对应 A7，先离线再真实生成，最后按同一体系扩展四档。

### 3.1 固定样本矩阵

样本用于覆盖关系，不用于规定产品只能生成这些建筑。复用 `tests/fixtures` 和保存回复，避免把运行 ID 写进业务逻辑。

| 组 | 低档场景 | 核心检查 | 参数变化 |
|---|---|---|---|
| B1 | 单层单体，必要门窗、平屋顶 | 宿主、洞口、楼板与屋面覆盖 | 尺寸、世界平移、四向墙面 |
| B2 | 单层坡屋顶 | 屋脊轴、出檐、承托、墙顶封闭 | X/Z 坡向，长宽交换 |
| B3 | 两层与三层简洁别墅 | 实际楼面连接、平台、楼板洞口 | 等高/非等高、台基、梯段方向 |
| B4 | 主楼加翼楼 | 共用界面唯一实体、屋顶归属 | 接口方向、高差、宽深 |
| B5 | L/U 形或庭院 | 保留真实空缺、不填整栋包围盒 | 翼宽、开口侧、整体位移 |
| B6 | 开敞凉亭或柱廊 | open/empty 不混淆，屋面有支承 | 开敞面、柱位、台基 |
| B7 | 有少量隔墙的建筑 | 房间表达、真实内门和动线 | 开放式/封闭式、内墙方向 |
| B8 | 任意低档建筑的失败输入 | 拒绝矛盾、部分交付说明、可恢复诊断 | 缺字段、无进展、模型截断、无效引用 |

对 B1—B7，不主动删除用户明确要求的构件以适配低档。B8 是负向用例，正确拒绝属于测试通过，不能计入正向建筑生成成功率。

### 3.2 分层验收，不混写结果

| 层 | 方法 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 静态 | 阅读、差异、字段/路径检查 | 改动范围和明显契约问题 | 程序运行正确 |
| 离线单测/保存回复回放 | 固定设计及模型回复经过实际入口 | 已知失误不会再次落入同一代码缺陷 | 新模型回复稳定 |
| Core 重建 | 同一 `.wild` 经过真实 TypeScript 编译/几何重建 | 网格、引用、构件和相关数值诊断 | 建筑完整美观、材质效果理想 |
| 新生成 | 固定请求集，真实模型、实际检索、审核流程 | 真实主线成功率、修订率、成本 | 所有造型已覆盖 |
| 浏览器/人工 | 同一 Blueprint 多视角和必要剖切查看 | 外观、楼梯通路、缺件、空间表现 | 专业建筑工程合规认证 |

每层结果都绑定同一 design hash、Blueprint 指纹及运行版本。截图附相机视角；不能用 SVG 示意、包围盒或 proxy 分数代替真实渲染。

### 3.3 建议的第一轮稳定性基线

这是建议目标，需要运行后填写实测值；目前没有足够固定版本样本宣称已达到。

- 从 B1—B7 选 6 个代表性正向请求，每个独立新生成 5 次，共 30 次。需求可相同，设计允许变化，但验收关系一致。
- 固定代码内容、模型配置、知识索引版本和生成参数；所有开始的请求保留结果，失败不删样本。
- 建议第一轮“端到端完整通过”至少 29/30；其中已交付的必需关系不能有已知错误，也不能靠舍弃必要构件满足比例。几何或 Core 已知错误零容忍是样本验收要求，不是承诺模型永不失败。
- 将首次实现通过率、依靠修订通过率、设计返修率分开，避免只看最终总通过。
- 30 次只是进入下一轮的工程基线，不是统计意义上证明长期成功率达到 95% 或 99%。一次失败要保留根因和回归，再进行版本明确的新一轮评估。
- 用户取消、服务不可用、检索故障和生成/校验失败分别归因。报告全部启动请求的完成情况，同时可另列排除明确取消后的条件成功率，分母必须公开。

不需要默认由 Agent 连续跑完 30 次。本轮任务只是总结，真实调用数量、费用和执行安排在后续明确的测试任务中决定。

### 3.4 必须同时报告的指标

| 指标 | 口径 |
|---|---|
| 任务结束率 | 已结束任务 / 已派发任务，舍弃可结束但不能算落实 |
| 标记落实率 | implemented 标记 / 批准标记；列出必要项缺口 |
| 设计完整率 | 全部批准标记及可验证必需关系落实的建筑 / 正向样本 |
| 后端通过率 | 最终候选通过交付门禁的建筑 / 正向样本 |
| Core 重建通过率 | 无 error 诊断且预期构件有对应产物的建筑 / 已执行重建样本 |
| 外观验收率 | 按设计和固定视角人工通过 / 已做外观验收样本；未审核单列 |
| 端到端完整通过率 | 上述必需层全部通过 / 正向样本；未验收不能算通过 |
| 修订成本 | 每任务、每类关系的修订次数、重复候选数、关闭 issue 数 |
| 模型成本 | 全链路 input/output/total token、逻辑调用、供应商尝试数分别统计 |
| 时延 | 总墙钟时间、审核等待、设计、检索、实现及编译时间分别记录 |

并行 LLM 耗时之和不是整轮墙钟时间。本次 trace 的 `elapsed_ms` 累加活跃执行分段，不应直接当作包含人工审核等待的用户全程等待时间。

## 4. 如何验证优化同样影响中、高、极高档

当前真实映射为：

| 界面档位 | 内部值 | 当前默认设计范围 |
|---|---|---|
| 低 | `minimal` | 主体、必要门窗、屋顶、多层楼梯和基础照明 |
| 中 | `simple` | 按功能增加阳台、露台、雨棚、栏杆和基本材质层次 |
| 高 | `standard` | 更完整的立面、开口分格、檐口、柱饰、屋面与材质细节 |
| 极高 | `detailed` | 在完整外观上增加功能分区、家具、室内外照明等 |

`simple` 不是界面“低”，脚本或测试填错值会让评估失真。四档定义见 [profile.py](../../wild-server/app/agent/generation/architecture/profile.py) 的 `DETAIL_LEVEL_GUIDANCE`。

低档基线通过后，选同一建筑需求逐档提升，验证基础宿主/坐标/通行关系不退化；再分别增加组合深度、体量数、标记数和宿主共享程度。规模与精细度分开测，不要求极高档单纯拥有更多窗。

| 档位提升 | 新增验证重点 | 共用底线 |
|---|---|---|
| 低 → 中 | 雨棚承托、阳台板顶、栏杆真实边缘、入口关系 | 不破坏原有门窗、楼梯与屋面 |
| 中 → 高 | 多实体构造、分层材质、构件间连续关系 | 组合后仍落实批准尺寸与宿主 |
| 高 → 极高 | 家具占地、空间分区、通路和照明 | 不穿墙、不阻断已批准交通、不重复建构件 |

优化通过的判据是“相同关系在不同档位都正确，成本增长可解释”，而不是四档都完成了图流程。

## 5. 现有检查入口与后续执行边界

以下供后续实施者安排，不代表本次已执行，也不建议不分修改范围每次全部重跑：

- 后端优先复用 `tests/design/test_stair_story_span.py`、`tests/plan/test_drawing_stair_assembly.py`、`test_drawing_fragment_retries.py`、`test_drawing_handoff.py`、`test_drawing_execution_cost.py`、`test_drawing_integration.py`，以及 `tests/agent/test_agent_delivery.py`、`tests/rag/test_llm_trace_payload.py`。
- 跨关系改动后覆盖相应 `tests/design`、`tests/plan`、`tests/validators`；物件共用入口改动同时跑物件回归。
- 前端/Core 现有命令为 `npm run check:core`、`npm run check:compiler`、`npm run check:rendering`、`npm run build`，工作目录 `wild-web`。
- 真浏览器出图已有 `wild-web/scripts/render-baseline.mjs`，先核对当前参数与已有诊断流程，再用同一个 `.wild` 进行多视角验收。
- CI 配置需要确定实际采用 GitLab 还是 Jenkins，统一关键验收集合，不能把“某条可选流水线可能全测”当作每次 PR 的保证。

所有实施阶段保持小步、可追溯。每项提交记录“改了什么共用契约、哪个旧样本被覆盖、哪些层真正验证、哪些仍待验收”，不再以新增规则数量或单次好看的截图作为完成标准。
