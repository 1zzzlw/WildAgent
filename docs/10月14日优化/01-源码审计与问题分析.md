# 源码审计与问题分析

## 1. 当前架构与扫描范围

建筑实际流程以 [graph.py](../../wild-server/app/agent/graph.py) 为准：

```text
classifier → architecture → material_plan → design_review
          → plan → execute / replanner → compile → final_validate
                                          ↓
                              必要时回到原条目作装配修订
```

建筑的 `final_validate` 不再进入物件使用的 callback 循环。建筑 plan 根据 `resolved_design.component_markers` 展开；不能把旧骨架编译或物件策略误认为当前建筑主线。

| 层 | 本次主要核查内容 |
|---|---|
| 设计 | `generation/architecture/{workflow,design_workflow,profile}.py`、`prompts/planning.py`、`design/{contracts,coordinates,compilation,markers}.py` |
| 实现 | `plan/{expand,workflow,implementation,knowledge_tool}.py`、`design/relations.py` |
| 校验与交付 | `design_flow/compile.py`、`validation/{candidate,workflow,issues,design_constraints}.py`、`services/agent_delivery.py` |
| 模型与检索 | `llm/invocation.py`、`rag/trace.py`、`spec/loader.py`、当前知识示例和检索记录 |
| Core 与前端 | `wild-core/src/compiler/index.ts`、`wildCoreAdapter.ts`、`reconstructionDiagnostics.ts`、`sceneStore.ts`、`agentBridge.ts` |
| 工程与证据 | `.gitlab-ci.yml`、`Jenkinsfile`、相关测试源码、10 月 10 日文档、近期会话/trace、两轮最终 checkpoint |

这是围绕稳定性的主干扫描，不是逐文件安全审计，也没有对所有引擎算法做几何正确性证明。

## 2. A1：设计审核前，需要检查可计算的跨字段矛盾（P0）

**证据类型：历史运行直接证据 + 当前源码部分已修复。**

失败请求 `req_1791935105839_8qneh91ma` 的图纸同时包含：

| 字段 | 原值 | 含义/冲突 |
|---|---|---|
| 楼层楼面 | `0.45, 3.45, 6.45` | 1—3 层连接高差为 6m |
| 楼梯 description | 连接 1—3 层 | 没有要求屋面通行 |
| `size.height` | 8.85 | 超出连接高差 |
| `form.flights × rises × riser_height` | `3 × 18 × 0.15 = 8.1` | 与 6m、8.85m 都不一致 |
| 实现稿最高终点 | 9.45 | 到达顶层墙顶，缺少真实目标楼面 |

第一稿楼梯 JSON 本身也不合法。修订后虽修复了语法，空间矛盾仍在；反馈要求为 9.45m 补承托平台，后续确实出现 `arrival_L4`。最终因平台错位舍弃楼梯，再被必需楼梯校验阻断。

当前 [coordinates.py](../../wild-server/app/design/coordinates.py) 的 `stair_span_conflicts()`（第 72 行）、[architecture/workflow.py](../../wild-server/app/agent/generation/architecture/workflow.py) 的审核前调用及 [test_stair_story_span.py](../../wild-server/tests/design/test_stair_story_span.py) 已覆盖上述总高矛盾；实现上下文也增加了 `available_floor_connections`。这些应标为已有修复，不能重复立项。

仍可优化的共性：

- [contracts.py](../../wild-server/app/design/contracts.py) 的 `ComponentInstance.form` 仍是开放字典，`floor_layouts` 等通过扩展字段承载；开放表达有价值，但字段合法不等于关系成立。
- 当前楼梯检查主要是“全楼可用高差”与显式数值相容，不能单独证明每段到底连接哪两层、是否漏连、平台是否可达。
- [compilation.py](../../wild-server/app/design/compilation.py) 已检查内墙字段和部分房间冲突，但“存在内墙附着构件”的提示条件不能证明存在真正的通行开口，更不能证明入口到各功能空间连通。

**最小方向：** 在现有设计契约/坐标入口中，优先规范已经影响实现的关系：目标楼层、宿主面、支承标高、覆盖范围。已知关系结构化，未知造型保留扩展；对可计算矛盾返回字段路径、期望值和实际值，交设计阶段修订。不要要求模型在批准之后修改设计数值，也不要用楼梯专用字符串规则逐案打补丁。

验收要包含不同层数、平移、旋转、非等高层、入口台阶、显式屋面通行及分段楼梯；对缺少必要设计信息的情况明确标记待审核，不能把不明关系自动判错。

## 3. A2：流程终态与建筑成功口径仍混用（P0）

**证据类型：当前源码确认 + 本地运行直接证据。**

- [markers.py](../../wild-server/app/design/markers.py) 第 262 行，`implementation_complete()` 同时接受 `implemented` 和 `abandoned`。这是“尝试流程已经结束”的判据。
- [implementation.py](../../wild-server/app/agent/plan/implementation.py) 第 739—745 行，非主体标记即使全部舍弃，执行结果仍可返回 `succeeded`。
- 失败样本的楼梯记录为“落实 0，舍弃 1”，最后一次 replanner 展示 6/6 done，最终建筑却失败。compile 随后将最终计划纠正为 5 项 done、楼梯 abandoned；不能把中间展示误写成最终 checkpoint 仍是 6/6 done。
- [agent_delivery.py](../../wild-server/app/services/agent_delivery.py) 明确允许合法但设计不完整的结果保存；[test_agent_delivery.py](../../wild-server/tests/agent/test_agent_delivery.py) 第 84 行也专门验证“舍弃后仍交付并说明缺口”。这是现有政策，不是偶然绕过门禁。
- [candidate.py](../../wild-server/app/agent/validation/candidate.py) 已生成 `implementation_summary.design_complete`，但最终 `status` 主要由校验错误决定。

**最小方向：** 保留有界流程终态，不把舍弃改回无限重试；展示和统计同时给出“已结束任务”“已落实标记”“未落实必需关系”“可交付文件”“设计完整”这几个不同事实。复用已有 `implementation_summary`，不要新增一套相互竞争的状态机。

允许部分文件保存可以保留，但部分成果不得进入“完整建筑成功”分子。必需楼梯等已有阻断继续保留；其他必需性从批准设计和明确需求派生，不能用固定组件配额代替。如果以后调整部分交付政策，应单独定义产品行为，不在质量修复中偷偷扩大或收紧。

## 4. A3：修订次数有界，但错误归属和无进展判定仍不够稳定（P0）

**证据类型：当前源码确认 + 重复输出直接证据。**

当前已经限定 `generate → repair_1 → repair_2`，最终装配另有一次 `assembly_revision`。问题不是无限循环，而是有限调用也可能没有有效进展。

失败样本中，`repair_2` 与 `assembly_revision` 的楼梯 geometry SHA-256 都是：

```text
798fe946b0f32203c0b20462541be47068b8ff779c8a56947677f1d210b92577
```

二者仍报告相邻梯段平台错开 1.20m。该摘要只用于本次两稿比对，算法见证据 JSON 的生成口径，不等同于项目的 Blueprint 指纹算法。

源码上的放大因素：

- [issues.py](../../wild-server/app/agent/validation/issues.py) 第 104 行起仍从自然语言和表情标记解析实体、错误类型及缺少构件；新的错误文案会影响归属。
- [design_flow/compile.py](../../wild-server/app/agent/design_flow/compile.py) 第 119—127 行：无法定位失败标记时回退到 `building_body`；多个失败标记又会移除主体。它是启发式归属，并不证明主体是最早出错的层。
- [plan/workflow.py](../../wild-server/app/agent/plan/workflow.py) 第 432 行对 design marker 链排除了旧的全局无进展条件。现有重复检查主要保护已采用实体，不能等价为识别所有失败候选的重复。

**最小方向：** 校验器尽量直接产出 `code / design_path / marker_id / entity_ids / related_entity_ids / expected / actual`，文本由这些字段生成；兼容旧文本即可，不必一次重写所有校验器。跨条目错误在共同候选上定位责任和依赖。

对同一图纸版本、相同依赖上下文，记录“失败候选指纹 + 未闭合 issue 集”。新稿只有文字变化、重命名或相同几何时，不能记为进展；缺陷减少但未通过可以继续使用原有剩余尝试。依赖宿主确实变化时允许复验。输出返回后识别重复只能避免后续浪费，不能宣称挽回已经花掉的这次调用。

设计自身矛盾应返回已有设计修订/审核入口；无法归属的问题保留明确诊断，不盲目要求主体重做，不用删除错误构件来制造设计完成。

## 5. A4：确定性事实仍由模型重复推导，组合表达的验收覆盖不均衡（P1）

**证据类型：当前源码确认；影响程度需要回归测量。**

当前已经有 `levels`、`diagram_hosts`、`opening_hosts`、`native_size_targets`、`attachment_geometry`，这是正确方向。但 [implementation.py](../../wild-server/app/agent/plan/implementation.py) 的 `run_marker_generate()` 同时承担检索、类型协议、各类提示词、模型调用、材料绑定、局部接受、修订和诊断。坐标/标高规则散布在设计提示词、实现提示词、关系函数和知识示例中。

值得关注的具体边界：

- `_accept_group()` 第 174—184 行的通用尺寸检查，仅在“单一实体且类型与标记族一致，且实体含对应字段”时生效。
- 门窗、屋面、栏杆另有专门关系验收，楼梯也有平台校验；因此不能笼统声称组合构件没有校验。
- 其他多实体组合可能只能证明 JSON、引用和基本空间合法，不能据此证明批准的总体尺寸、位置和形态全部落实。指纹证明未被改写，不证明第一次实现就符合设计。

**最小方向：** 继续由模型决定造型与组合；把已批准且能唯一推出的宿主坐标、楼面连接和尺寸映射放在共享事实/关系函数中，设计预览、实现上下文和验收共用。提示词引用计算结果及适用规则，避免让模型重复算同一事实。

验收按关系选择有限的共享检查，例如洞口范围、覆盖、承托、连接、占地和材料角色。不能一律以 AABB 代替曲面/旋转形态，也不能把未知形态禁止掉；无法验证的方面保留 `needs_review`，不伪装成已验证。

代码整理只围绕这些责任迁移，优先减少重复规则；不以拆文件数量、工厂类或层数作为优化成果。

## 6. A5：分批与成本需要依据实际负载，而不只依据类型和标记数（P1）

**证据类型：当前源码确认；超长输出/并发冲突属于待验证风险。**

[expand.py](../../wild-server/app/agent/plan/expand.py) 的 `expand_design_markers()`（第 507 行）主要把依赖就绪的标记按构件名称分组，低档门、窗、灯还会按原生族合批。每批没有显式的输入/输出规模边界；依赖无法展开时，剩余标记统一进入 `assembly`。预算按 `标记数 × 4` 估算。

低档已有合批，不能建议退回“一窗一调用”。但一个建筑有很多同类窗时，整批实现 JSON、Schema 和宿主上下文都可能增大；高档未知组合更多，单纯的标记数也不能代表真实成本。

[plan/workflow.py](../../wild-server/app/agent/plan/workflow.py) 最多并发 3 项，共用同一前序状态；这是正常的有界并发。没有直接依赖并不等于几何完全独立，空间冲突仍需最终检查。目前未证明本次楼梯失败由并发导致。

**最小方向：** 先记录每批实际输入、输出、耗时及失败率，再以依赖闭包、宿主/楼层和上下文预算分批，保留标记 ID 与顺序确定性。环形依赖先区分共同装配与图纸引用错误，不无条件把所有剩余标记交给一次大调用。

统一记录设计、材质、实现、装配修订、传输重试的真实成本；不要把 plan 内部调用预算冒充整轮成本上限。先减少重复工作，再考虑并发和预算调整。

## 7. A6：诊断资料很多，但还不能精确还原每次调用输入和运行版本（P1）

**证据类型：当前源码及本地记录确认。**

现有 session、RAG trace、checkpoint 保存了大量有用数据，本次已能还原设计、模型原稿、检索文本、尝试错误和最终结果。缺口集中在可复现性：

- [trace.py](../../wild-server/app/rag/trace.py) 的 `record_rag_llm_call()`（第 350 行）保存响应、思考、用量、耗时，没有逐调用实际 messages、任务/stage 标识、完整模型参数及提示词版本。
- 并发调用按完成顺序进入列表，仅凭数组序号不能稳定关联某个任务；节点 model 标签也不等于每次调用的完整配置快照。
- 当前未提交源码有楼梯修复，但旧 trace 没有绑定完整工作区内容摘要，不能证明旧进程运行过这些修复。
- [invocation.py](../../wild-server/app/llm/invocation.py) 第 146—158 行先用默认 `result.retry_count` 写 trace，随后才把 `attempt` 赋给结果。成功重试的本地 trace 有低估传输重试次数的源码路径。本次样本未确认实际发生传输重试，不能用它解释本轮失败。

**最小方向：** 扩展现有 trace，在同一个 call_id 下关联 request、item、stage、设计 hash、候选指纹、实际输入快照/摘要、模型配置、知识版本、输出和反馈。来源内容与密钥分开处理，不保存认证信息。运行版本至少能区分提交和未提交工作区，已有进程实例标识可复用。

输入体积大时按内容摘要去重存储，避免每个 checkpoint 重复嵌套全文；先统计体积与复现需求再改存储。本次 checkpoint SQLite 约 1.76GB，仅说明诊断存储值得测量，不构成删除历史记录的理由。

## 8. A7：需要打通测试覆盖、真实生成与渲染验收（P1）

**证据类型：当前流水线/测试源码确认。**

- [.gitlab-ci.yml](../../.gitlab-ci.yml) 的建筑门禁仅显式列出 8 个测试文件，没有纳入当前 `tests/plan`、`tests/design` 大部分图纸实现回归；RAG 门禁运行 `tests/rag` 和 hash embedding 检索检查。
- [Jenkinsfile](../../Jenkinsfile) 第 248 行起确实有全量 `pytest tests -q`，不能说项目完全没有全量测试。但该阶段只在非 PR 且 `REMOTE_VALIDATE_ENABLED` 时执行；前端该路径仅 build。GitLab 则运行 Core/compiler/rendering 三类检查。
- 现有 drawing 测试中有参数化几何与 mock 模型测试，能证明指定输入的代码行为，不能证明供应商新回复稳定。已有历史文档也多次区分“保存回复回放通过”与“真实新生成尚未验收”。
- [validation/workflow.py](../../wild-server/app/agent/validation/workflow.py) 明确将视觉结果标为 `complete=false`，等待 render/human_review，这是正确边界。
- [wildCoreAdapter.ts](../../wild-web/src/renderer/wildCoreAdapter.ts) 聚合编译和重建诊断；[agentBridge.ts](../../wild-web/src/agent/agentBridge.ts) 第 911 行起对有网格但存在错误的结果显示“部分加载”。后端 `complete` 不等于前端没有构件缺失，更不等于外观合格。

**最小方向：** 在实际使用的 PR/发布流水线上对齐同一组关键离线回归和 Core 检查，明确锁文件处理策略。固定同一设计和 Blueprint 在 Python 验收与 TypeScript 重建中对照关键宿主、屋顶、楼梯、坐标和材料，不只比对 Schema 字段。

真实生成基线另外记录图纸完整、几何通过、Core 重建、图像/人工审核；缺任何一层就标对应未验收，不把截图是否好看全部变成后端确定性规则。

## 9. A8：RAG 查询的异步边界与结果归属可改进（P2）

**证据类型：当前源码路径；并发串读尚未复现。**

[architecture/workflow.py](../../wild-server/app/agent/generation/architecture/workflow.py) 使用 `asyncio.to_thread()` 执行设计检索；[implementation.py](../../wild-server/app/agent/plan/implementation.py) 在异步函数内直接调用同步 `search_knowledge_result()`，可能在检索期间占住事件循环。两个样本的检索累计分别为 1.206s 和 8.424s，但不能仅凭累计值认定其是整轮主要瓶颈。

[knowledge_tool.py](../../wild-server/app/agent/plan/knowledge_tool.py) 先调用 loader 得到文本，再读取共享 `spec_loader.last_results` 重组输出；[loader.py](../../wild-server/app/spec/loader.py) 用实例字段 `_last_results` 保存最近结果。跨请求的线程检索存在覆盖风险。当前实现侧同步调用会阻止同事件循环任务在这段代码中正常切换，因此不能简单声称“每次三任务并发就一定串读”。

**最小方向：** loader 一次返回本次文本、hits、注入 chunk IDs，调用方不依赖共享“最近结果”；之后再把阻塞检索移出事件循环。针对两个同时查询不同类型构件的请求验证来源隔离。不要只加线程而保留共享 last_results。

本次楼梯已经命中楼梯 JSON 与平台/洞口说明，证据不支持“只是知识库没楼梯资料”。网络搜索的真实有效性也需单独验证，不能用无结果时的模型继续作答替代资料质量证明。

## 10. 不建议作为本轮优化方向

- 增加门窗、装饰数量来证明精细度，或给低档强制套固定住宅。
- 默认打开更深思考、加长所有提示词、提高所有重试次数/模型预算。
- 仅因最终缺楼梯就补一个任意楼梯，忽略批准设计的连接与占地。
- 降低 expected、放宽容差、把错误降警告，或把舍弃算完整成功。
- 为每个失败建筑新增 ID、坐标、关键词特判。
- 在没有剖析数据时大改缓存、引入多 Agent、多一层规划或新增修复系统。

这些措施可能让个别输出更容易结束，却不能建立四档共用的稳定生成能力。
