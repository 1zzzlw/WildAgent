## 1. 概述

后端核心链路（FastAPI + WebSocket + LangChain/LangGraph + Chroma RAG + 15+步校验流水线 + 18 个空间工具 + scenes REST API）**整体已接通**。但存在 2 项高优先级缺陷、4 项中优先级缺陷和 3 项低优先级/架构风险，主要集中在致命错误拦截不一致、文档与代码脱节、以及流水线健壮性不足。

### 后端核心架构（当前实现）

```
ws_agent.py                         # WebSocket 传输层
  ├─ precision_mode=true → LangGraph 精密模式
  │     graph.astream_events()
  │       ├─ skeleton_node          # 骨架规划（RAG + LLM + 组件建议）
  │       ├─ {component}_gen_node   # 各组件并行生成（11 种）
  │       ├─ {component}_val_node   # 各组件工具校验
  │       ├─ callback_node          # 失败组件修正 + 重试
  │       ├─ merge_node             # 数据合并
  │       └─ final_validate_node    # 15+步校验流水线
  │
  └─ precision_mode=false → LangChain 快速模式
        AgentService.query_structured()
          ├─ SpecLoader.load()          # RAG 知识库检索（默认 RAGSpecLoader）
          ├─ build_system_prompt()       # System Prompt 组装
          ├─ LLM 生成 Blueprint / Patch
          └─ run_validation_pipeline()   # 15+步确定性校验

scenes.py                           # REST API: GET/PUT/DELETE /api/scenes/{file}
```

## 2. 缺陷 B1：完整 Blueprint 致命 ❌ 错误未拦截就下发（🔴 高优先级）

### 2.1 问题定位

**文件**: `app/api/ws_agent.py:686-744`

```python
# ===== 完整 Blueprint 结果处理路径 =====
if result.blueprint is not None:
    # 遍历校验结果并展示
    for pr in result.pipeline_results:
        if pr.output.startswith("⏭️"): continue
        status = "❌" if pr.has_error else "⚠️" if pr.has_warning else "✅"
        await send_step("validating", f"{status} [{pr.step}] {pr.name}: {pr.output[:300]}")

    if result.error:
        logger.warning(f"[{request_id}] 流水线校验警告: {result.error}")
        # ⚠️ 仅打日志！不拦截！

    # 照常保存文件
    file_path = save_blueprint_file_as(result.blueprint, SCENES_DIR, rel_path)

    # 照常下发前端
    await ws.send_json({
        "type": "blueprint_generated",
        "request_id": request_id, "session_id": session_id,
        "filename": filename, "file_url": f"/api/scenes/{filename}",
    })
```

**对照**：Patch 路径（`ws_agent.py:746-764`）对 `result.error` 是**明确拦截**的：`if result.error: await ws.send_json({"type":"error",...}); return`。

### 2.2 影响

当 `run_validation_pipeline` 报出碰撞/结构类致命 ❌（如 `validate_collision` 顶点爆炸、`validate_element_required_fields` 缺失关键字段），代码：
- 仅 `logger.warning` 一行
- 照样保存 `.wild` 文件到 storage/scenes/
- 照样发送 `blueprint_generated` 到前端
- 前端 `loadBlueprint` 用已知损坏的蓝图替换场景

这违反"校验失败应拦截 / 用户保留最终决策权"的设计原则，且**与 Patch 路径行为不一致**。

### 2.3 修复方案

在 `result.blueprint is not None` 分支开头增加致命错误拦截：

```python
if result.blueprint is not None:
    # ── 新增：致命错误拦截 ──────────────────────
    fatal_errors = [pr for pr in result.pipeline_results 
                    if pr.has_error and not pr.output.startswith("⏭️")]
    if fatal_errors:
        error_lines = []
        for pr in fatal_errors:
            error_lines.append(f"❌ [{pr.step}] {pr.name}: {pr.output[:300]}")
        error_msg = "\n".join(error_lines)
        logger.error(f"[{request_id}] 蓝图校验致命错误，拒绝下发: {error_msg}")
        await ws.send_json({
            "type": "error",
            "request_id": request_id,
            "error": f"蓝图校验未通过:\n{error_msg}",
        })
        return

    # ── 原有逻辑：通过后才保存和下发 ────────────
    for pr in result.pipeline_results:
        # ... 展示校验结果 ...
```

**设计考量**：
- 仅拦截 `has_error=True` 的步骤（对应 ❌ 级别）；`warning` 级别只展示不拦截
- 给出可定位的诊断信息（步骤编号 + 工具名称 + 输出摘要），方便用户或 Agent 修正后重试
- 跳过项（⏭️）不参与拦截判断（因其输出被跳过是因为前序步骤的 blockable 错误导致该步被忽略）

## 4. 缺陷 B3：`blueprint_generated` 协议字段缺失（🟡 中优先）

### 4.1 问题定位

**协议注释** (`ws_agent.py:28`)：

```python
# blueprint_generated: {
#   "type": "blueprint_generated", "request_id": "...", 
#   "blueprint": {...}, "file_path": "..."
# }
```

**实际发送** (`ws_agent.py:732-738`)：

```python
await ws.send_json({
    "type": "blueprint_generated",
    "request_id": request_id,
    "session_id": session_id,
    "filename": filename,
    "file_url": f"/api/scenes/{filename}" if filename else "",
})
# ❌ 缺少内联 "blueprint" 字段
```

### 4.2 影响

前端必须额外发一次 `GET /api/scenes/{filename}` HTTP 请求拉取蓝图文件，**协议注释声明与实际发送不符**。功能可用（前端 `agentBridge.ts:467-477` 已适配 REST 拉取模式），但若任何代码按注释期待的"内联 blueprint"接入，会因字段缺失而失败。

### 4.3 修复方案

二选一：
1. **修复注释**（推荐，当前实现已满足需求）：将注释改为 `"file_url": "/api/scenes/{filename}"` 模式
2. **内联 blueprint**：若希望减少前端一次 HTTP 往返，可将完整 blueprint JSON 嵌入消息体（注意 WS 帧大小限制）

## 5. 缺陷 B4：校验流水线对畸形数值坐标无类型保护（🟡 中优先）

### 5.1 问题定位

**文件**: `app/tools/spatial_tools.py:217`

```python
from_vec = op.get("from", [0, 0, 0])
along_dist = from_vec[0]      # ← 若 LLM 输出字符串坐标（如 from: ["3","0","0"]）
                               #    或嵌套数组（如 from: [[1,0],[2,0]]），
                               #    此处隐式假设为数值类型
# ...
if along_dist < -0.3 or along_dist > wl + 0.3:  # ← TypeError 若 along_dist 为 str
```

类似问题存在于所有校验/修正工具中（`validate_element_dimensions`、`validate_opening_fit`、`fix_opening_coords` 等），它们均假设 `blueprint` 中的坐标/尺寸字段为数值类型。

### 5.2 影响

若 LLM 生成了非数值型坐标（字符串、嵌套数组、None），工具抛出 `TypeError` → `run_step` 未捕获 → 异常冒泡到 `ws_agent.py` 的 `try/except` → 整次请求以 `error` 终止（非优雅降级），用户得到一条不包含定位信息的错误消息，无法知道是哪个构件的哪个字段出了问题。

### 5.3 修复方案

在每个工具入口增加统一的类型安全保障：

```python
def _safe_coords(vec: Any) -> list[float]:
    """将坐标或尺寸强制转为 float 列表，非数值元素抛可定位异常。"""
    if not isinstance(vec, (list, tuple)):
        raise ValueError(f"期望数组，实际为 {type(vec).__name__}: {vec!r}")
    result = []
    for i, v in enumerate(vec):
        try:
            result.append(float(v))
        except (TypeError, ValueError):
            raise ValueError(f"坐标[{i}]={v!r} 不是有效数值")
    return result
```

在 `validate_opening_coords` 等工具中对坐标/尺寸字段调用 `_safe_coords`：

```python
try:
    along_dist, height, normal_offset = _safe_coords(from_vec)
except ValueError as e:
    issues.append(f"❌ [{oid}] from 字段格式错误: {e}")
    continue
```

## 7. 缺陷 B6：`extract_patch_from_text` 死代码（⚪ 低）

### 7.1 问题定位

**文件**: `app/utils/blueprint_parser.py:63-88`

```python
def extract_patch_from_text(text: str, ...) -> dict | None:
    """从 AI 输出文本中提取并校验 ScenePatch JSON"""
    # ... 校验 operations 非空、补 summary ...
```

该函数在 `agent_service.py` 中**未被调用**。实际的 Patch 检测走的是通用 `extract_blueprint_from_text` + `"operations" in json_data` 判断（`agent_service.py:718/750`）。

### 7.2 影响

### 7.3 修复方案

```python
# 当前：
if "operations" in json_data and current_blueprint:

if "operations" in json_data and current_blueprint:
    patch = extract_patch_from_text(raw_text)  # 走校验增强
    if patch is None:
        return QueryResult(error="无法提取有效 ScenePatch")
```

## 8. 缺陷 B7：`fix_*` 原地修改在 LangGraph 节点路径的风险（⚪ 低）

### 8.1 问题定位

所有 `fix_*` 工具（如 `fix_opening_coords`、`fix_roof_coverage` 等）均**原地修改**传入的 `blueprint` dict：

```python
op["from"][0] = 0.0   # 直接修改传入 dict
r["span"] = new_span   # 同上
```

在 `agent_service.run_validation_pipeline` 主链路中，传入的是同一个 dict，原地修改是预期行为（流水线步骤顺序依赖前序修正结果）。

### 8.2 潜在风险

在 **LangGraph validate_node**（`app/agent/nodes/`）中，LangGraph 的节点状态管理可能对 state 做 `deepcopy` 或通过 Pydantic schema 校验。若节点接收到的是 state 的深拷贝，fix 工具的原地修改会丢失（节点返回的 output 仍是修正前的 blueprint）。

### 8.3 验证与修复

- **当前**：`app/agent/nodes/validate_node.py` 实际路径需核实；在 agent_service 主链路中无此风险
- **Phase 3 接入 LangGraph 全链路时需验证**：节点输出是否携带修正后的 blueprint
- 若发现丢失，修复方向：
  - 工具改为返回修正后的 blueprint（非原地修改）
  - 或在 validate_node 中显式将修正结果写回 state

## 9. 缺陷 B8：RAG 静默降级（⚪ 低 — 可观测性）

### 9.1 问题定位

**文件**: `agent_service.py:549`

```python
try:
    spec_loader = RAGSpecLoader(...)
except Exception:
    spec_loader = FileSpecLoader()    # ← 静默退回，仅一行 error 日志
```

### 9.2 影响

若部署环境 embedding 接口不可达（网络问题、API key 错误、额度耗尽），`RAGSpecLoader.__init__` 内 `sync_index()` 调用的 `collection.upsert` 抛异常 → 被 except 捕获 → 静默退回 `FileSpecLoader`。**无任何告警前缀**（仅一行 `logger.error`），运维无法察觉 RAG 实际上已被降级。

### 9.3 修复方案

在降级路径上增加明确的告警日志和状态标志：

```python
try:
    spec_loader = RAGSpecLoader(...)
    logger.info("RAG 向量索引已就绪")
except Exception as e:
    logger.warning(f"⚠️ RAG 不可用（{e}），已降级为全量注入模式")
    logger.warning("  检查: EMBEDDING__NAME/API_KEY 配置及 embedding 服务可达性")
    spec_loader = FileSpecLoader()
```
