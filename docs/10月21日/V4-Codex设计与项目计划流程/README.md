本轮已生成 [栖庭 V4 WILD](栖庭V4-新中式别墅.wild)，完成真实引擎渲染。[透视图](09-真实渲染/perspective.png)、[正面图](09-真实渲染/front.png)、[俯视图](09-真实渲染/top.png)、[侧面图](09-真实渲染/side.png) 可直接查看。

## 这次谁完成什么

用户要求本轮不用项目配置的模型，由 Codex 自身完成流程。本轮图纸、材质选择与构件实现均由当前对话中的 Codex 编写；没有通过项目客户端调用当前对话模型，也没有调用项目的聊天、嵌入模型。

为使效果和先前手工基线可以对照，沿用本次 V1 栖庭的 16×13 米 U 形布局、两层主楼与单层厢房，按当前契约重新输出图纸。它不是另一个模型从同样提示词独立生成的对照实验，也不把 V2/V3 的失败稿伪装成成功稿。

| 环节 | 本轮实际执行 |
| --- | --- |
| 设计、材质 | Codex 编写正式 `DesignDocument`，含平面、墙、门窗、屋面、楼梯、造型细部、命名材质与动线 |
| 图纸投影与确认 | 原 `DesignRepository.save/approve` 与 `project_drawing`；使用本目录内独立设计仓库；确认者为 Codex runner，不代表用户视觉批准 |
| plan | 实际调用原 `plan_node`，按标记、宿主与依赖拆出 9 个任务；建筑分支此步确定性运行，不调用模型 |
| execute | 实际调用原 `execute_node`；仅在脚本进程中将 `HANDLERS['generate']` 替换为 Codex 编写的实现处理器 |
| 片段交接 | 原 `_item_context`、`_bind_materials`、`_accept_group`：使用实际任务上下文与原验收条件 |
| replanner | 实际调用原 `replanner_node` 对账，5 轮后全部 9 个任务完成，0 个舍弃 |
| compile | 先经原装配入口及纯校验预检，再调用原 `compile_node`；未进入项目模型集中修复 |
| final_validate | 实际调用原 `validate_node`；保存原始验收结果与指纹 |
| 渲染 | 原 `wild-web/scripts/render-baseline.mjs`，真实 Chromium / WebGL；输入就是本轮最终 WILD |

这次是由脚本顺序调用原项目节点函数，生成处理器由 Codex 提供；没有宣称运行原始完整 LangGraph、原 architecture 模型节点或原模型工具循环。项目应用源码、`.env` 与模型设置没有为 V4 改动。生成进程关闭 RAG 并将聊天客户端替换为禁止调用对象，外部 socket 连接被拦截；Windows asyncio 所需的本地 socketpair 保留。

## 流程与设计字段

1. [00-创建设计图纸.py](00-创建设计图纸.py) 输出 [原始草稿](02-栖庭V4-设计图纸-草稿.json)。相比 V1，将楼梯位置、占地、每跑级数、方向与楼层连接写入当前正式字段；材质改为 `materials.definitions`，格栅使用 `repetition` / `placement.position` / `material_bindings`，补充三条明确动线。
2. 保存与确认后产生 [批准图纸](03-批准设计图纸.json)、[设计投影及标记](03-设计投影与构件标记.json)、[一层图](03-第1层设计图.svg)、[二层图](03-第2层设计图.svg)。51 个显式构件加 1 个主体标记，共 52 个。批准后没有改写设计取舍。
3. 原 [plan 节点输出](04-plan节点输出.json) 包含完整任务、标记分配、宿主和材质脚手架。主体先行，门窗、楼梯和屋面按依赖安排；栏杆任务依赖楼梯，不以构件数量代替依附关系。最终计划见 [05-plan完成状态.json](05-plan完成状态.json)。
4. [任务证据](任务证据/) 保存每项任务的真实上下文、Codex 产物与项目验收记录；[节点证据](节点证据/) 保存 execute / replanner 的原始节点输出。主体楼板使用项目统一的体量并集减挑空结果；U 形楼梯使用统一路线结果，没有另写尺寸补丁。
5. [装配输入状态](05-装配输入状态.json)、[预检](06-装配预检.json)、[compile 输出](06-compile节点输出.json)、[最终校验](07-final_validate节点输出.json)、[验收快照](07-validation_snapshot.json) 保留可回放数据。最终 WILD 指纹与验收快照一致。
6. [真实渲染清单](09-真实渲染/render_manifest.json) 记录引擎、相机、灯光和源文件指纹。[剖切脚本](02-制作剖切副本.py) 仅移除实际最终 WILD 的屋面、二层墙等 49 个实体，保留二层楼板、梯井、楼梯和栏杆，未重建保留实体；[来源清单](10-剖切来源.json) 与 [剖切图](10-剖切渲染/top.png) 可核对。剖切副本不是最终交付文件。

- 9 个计划任务、52 个标记全部实现，0 个舍弃；项目聊天、嵌入调用为 0，无外部网络调用尝试。
- 项目最终校验 17 项通过，0 错误、0 警告；原引擎渲染 488 个网格，编译错误、重建错误、未映射材质均为 0。图纸和最终文件的 hash 见结果及清单。
- Codex 已查看四幅外观图及剖切俯视、透视图：庭院、高低屋面、真实洞口、木格栅与井口可见。保留既定渲染参数，未调亮画面来改变对比条件。
- `design_fulfillment` 仍有 13 项 `needs_review`：11 项组合造型，2 条涉及梯段的动线。入口动线已满足当前净空检查；梯段占用没有完整导航证明。`relationships_verified=false` 和这些缺口保持原值；零校验错误不等于全部关系已证明，也不代表用户已认可审美效果。
- 室内仍是房间与隔墙分区表达，没有完整家具布置；灰瓦屋面是原生四坡屋顶表达，没有逐片瓦构造。此轮目标是走通设计到可渲染 WILD 的流程。

执行脚本曾遇到两项启动适配问题（网络拦截误拦 asyncio 本地管道、Windows 缺少 tzdata），以及一项本轮实现器对门窗上下文的读取错误，日志单独保留为 `00-启动拦截日志.log`、`00-时区初始化日志.log`、`00-首次实现适配日志.log`。随后只修正本目录脚本：允许本地管道、使用 UTC+8 固定时区、读取已有门窗定位；图纸几何未因这些错误修改，没有放宽验收或增加模型重试。成功记录为 [00-执行日志.log](00-执行日志.log)。

## 对“是不是模型的问题”的判断

已有证据能确认两类问题。V2/V3 中，项目模型实际返回了非法 JSON 数值表达式、退化墙段、房间与隔墙冲突，以及楼梯级高、梯段与平台占地不一致，说明其在当前任务下的输出可靠性不足。项目侧也已出现根 JSON 解析、反馈截断和修订路径交接的缺陷，后者已经修复并做了此前的定向回归；V3 又表明校验早退分批暴露问题、重复填写派生数值等困难仍存在。

V2/V3 都止于 architecture，未运行 plan。因此不能说是 plan 执行导致设计失败；可能影响设计难度的是上游为后续实现准备的契约要求。它们需要在设计阶段被正确、完整地满足。

V4 表明：一致图纸在当前项目的真实 plan、验收、装配与渲染链上可以完成。它没有隔离“只更换模型”这个变量——Codex 手工编写、脚本实现与自动模型循环的工作方式不同。因此不能据此断言换模型就解决所有 bug；模型输出质量和项目设计/反馈机制都需要对最终可靠性负责。

## 复跑

在仓库根目录，用项目 venv 分别运行 `00-创建设计图纸.py`、`01-执行项目流程.py`，再运行 `node wild-web/scripts/render-baseline.mjs <本目录最终.wild> <输出目录>`。剖切先运行 `02-制作剖切副本.py`，再将副本传给同一渲染入口。Windows 子进程须带 `SystemRoot=C:\Windows`、`WINDIR=C:\Windows`；这些操作无需项目模型密钥，但依赖当前项目 Python/Node 环境及本机 Chromium。复跑会覆盖本目录同名产物，先另存要保留的实验版本。

当前源码指纹及执行方式见 [00-运行来源与指纹.json](00-运行来源与指纹.json)，源码归档与证据一致性见 [11-交付核对.json](11-交付核对.json)。
