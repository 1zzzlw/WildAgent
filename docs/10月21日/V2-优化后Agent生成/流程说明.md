# V2：优化后的完整 Agent 生成

本目录调用项目的 `build_generation_graph`，让配置的模型形成新图纸、材质和构件。没有传入 V1 的设计几何、手工 plan 或预制构件。

## 输入与版本

- 自然语言需求和 detailed 档位沿用 V1，完整输入保存于 `01-运行输入.json`。
- V1 是 Codex 手工设计与实现，V2 是项目模型生成；作者与执行方式不同，不能把所有视觉差异都解释为优化带来的提升。
- V1 / V2 是实验编号，项目软件包仍为 0.1.0，图纸和 WILD 协议保持当前标记。
- 源码、提示词、知识和 Schema 指纹及实际模型名保存于 `02-运行版本.json`；使用项目 `.env`，不复制密钥到证据目录。

## plan 节点是否必要

必要。上次 V1 的 `02-编译图纸.py` 使用 `TopologicalSorter` 排序 `component_markers`，调用手写 `implement()` 产生每个片段，再调用 `_accept_group` 与 `_assemble_with_relations`。这替代了运行时的任务分配、模型实现和重规划；没有调用 `plan_node`、`execute_node` 或 `replanner_node`。

V2 使用现有主线：

`classifier → architecture → material_plan → design_review → plan → execute / replanner → compile → final_validate`

当前建筑分支的 plan 不额外调用模型选择另一份建筑设计，而是确定性展开已审核图纸。这不等于省略 plan：

| 图纸或投影字段 | 当前处理 |
| --- | --- |
| components.type / id | 投影为稳定设计标记，按类型及负载分组成为 generate 条目 |
| host / relation.target / connections.target | 转为 depends_on；先实现宿主和连接目标，再实现依附件；相互依赖时共同实现 |
| facades、roof.volumes、floor_layouts.walls | 生成相应开口、屋面或主体宿主标记；避免只凭构件数量分配任务 |
| placement、size、form、floor_connections、repetition、material_bindings | 随标记交给具体执行任务；plan 保留设计决定，execute 结合统一派生坐标实现 |
| construction、floor_layouts、circulation.paths | 进入共享几何上下文，主体铺板、梯井与各构件避让共用同一份事实 |

`component_quota`、`required_components` 仍是兼容字段，不能用配额完成代替标记和关系落实。当前建筑 plan 的实际入口为 `app/agent/plan/expand.py::expand_design_markers`；任务、依赖、执行状态和预算写入 `04-plan.json`，节点调用写入 `节点顺序.jsonl`。

## 审核与证据

按照用户本次端到端生成请求，运行器在项目的设计审核中断处确认继续，并完整保存中断图纸、投影和确认来源。它不表示用户已人工批准这份具体方案或通过视觉验收。图纸存在编译阻断时不强行确认。

每个节点的原始输出保存在 `节点输出/`；完整状态、构件片段、实现诊断、编译与验收记录分别落盘。模型与检索追踪使用项目自己的 `rag_trace_scope`。SQLite 检查点用于恢复同一轮运行，不绕过项目节点。

首次启动因继承 SOCKS 代理但缺少 socksio，停在客户端初始化，尚未发出模型请求。仅向当前虚拟环境安装 socksio 1.0.0；uv 第一次也因工具进程缺少 Windows 系统环境失败，补齐当前进程 SystemRoot/WINDIR 后安装成功。未修改项目 `.env`、依赖锁、模型、预算或重试次数。原始异常保留在 `异常记录/`。

本轮不运行无关的测试套件。生成过程中节点自身的图纸、构件及最终验收属于真实 Agent 流程；后续渲染直接读取本次最终 WILD，不再按图纸另造替代文件。
