## 为什么使用 plan 后看起来更难通过图纸

plan 本来就在项目主线中，V1 的专用手工脚本替代了它和 execute，并非只绕过一个节点的受控对比。V2 在 architecture 结束为 failed，plan 根本没有执行，因此不是 plan 执行后反过来造成图纸失败。

V1 由 Codex 手工选择并协调参数，V2 / V3 由项目配置的模型生成；同时优化后的正式空间、构造、材料与关系字段增加了设计协调要求。V2 和用户两次测试又证实解析误取局部对象、反馈截断、修订范围滞留及宿主上下文不足等实现缺陷。这些首先属于设计节点的输出和修订交接问题；不能通过去掉 plan、放宽图纸检查或增加重试次数制造通过。

## 新证据说明什么

旧的解析、截断和修订范围缺陷确已得到定向验证，但仍不能说设计节点已稳定。V3 暴露出独立检查分阶段早退的问题：平面冲突存在时，`project_drawing` 提前返回，楼梯几何检查尚未运行；模型修好前一类问题后，才收到后一类问题。

最终候选的楼梯连接高差 3.9m，半层 1.95m；每跑 11 级、级高 0.177m，相乘为 1.947m，相差 3mm，触发当前判据。同时，按这份原稿的踏步进深 0.26m 和平台进深 1m，所需沿梯方向占地为 `11×0.26+1=3.86m`，原稿只声明 3m。后一个矛盾是本次结束后的静态核对，不冒充已执行的后续校验。

因此，不能把困难归因于 plan：它从未执行。下一步应检查设计节点为何同时要求模型协调多个可派生量，以及为何可独立发现的冲突不能一起反馈；当前没有修改这些新问题的源码，也没有自动开始 V4。先明确设计参数与派生参数的职责，再验证完整生成，比重复相同调用更有依据。
